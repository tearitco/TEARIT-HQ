  - `ffmpeg .*video4linux2`
  - `ffmpeg .*x11grab`
  - and clears stale webcam/record pid files under hosted Wraith projects

Important CPU-safety lesson from this epoch:

- the main Wraith render loops were already capped near 60 FPS
- the real throttle source was orphaned host `ffmpeg` capture processes
- stale pid-file cleanup alone was not enough
- startup/stop guards must also kill residual ffmpeg by project-owned session/output path

That guard is now added locally in the project ops:

- `web-cam/ops/src/wraith_webcam_capture.c`
  - kills residual capture processes referencing `session/current_frame.png`
- `screen-record/ops/src/wraith_screen_record.c`
  - kills residual capture processes referencing `session/recordings/`

Observed host failure mode that caused the slowdown:

- multiple orphaned `ffmpeg` `x11grab` recorders were still alive after prior sessions
- they were each consuming roughly 150%+ CPU
- they had to be killed directly on the host

Current status at handoff:

- live orphaned host capture processes were verified gone after direct kill
- rebuilt binaries are present and timestamped:
  - `web-cam/ops/+x/wraith_webcam_capture.+x`
  - `screen-record/ops/+x/wraith_screen_record.+x`

Remaining work before copying this lane wider:

1. Prove `web-cam` quit-path cleanup end-to-end:
   - start webcam
   - quit Wraith normally
   - verify no webcam ffmpeg survives

2. Prove `screen-record` quit/stop cleanup end-to-end:
   - start record
   - stop record
   - quit Wraith
   - verify no x11grab ffmpeg survives

3. Re-prove `screen-record` output validity after the new guard path:
   - valid mp4
   - audio muxed
   - poster extracted

4. Only after those proofs:
   - copy the updated Wraith lane to `x0.moke-`
