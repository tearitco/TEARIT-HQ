WRATH-PM-CODEX-J2
Super Plan for wraith-pm: Sovereign Map-Composer Desktop

Status:
Planning document for the new wraith-pm project.

Name note:
The requested filename is wrath-pm-codex-j2.txt. The project name inside the plan is wraith-pm.

1. One-line goal

wraith-pm is a Sovereign Map-Composer project that orchestrates a dynamic ASCII desktop. It treats windows as sovereign map entities (Pieces) with pos_x, pos_y, and pos_z, composing them into an auditable text grid (view.txt) that is rendered by the standard TPMOS CHTPM parser via the ${game_map} projection.

2. What we are remaking

We are not remaking the legacy glos path, nor are we building a virtualized markup parser.

We are remaking the working GL-OS desktop and window-management concept using the high-performance 'fuzz-op' map-rendering standard:

- The Desktop: A sovereign map composed of dynamic pieces.
- The Windows: Transient map entities (Pieces) spawned and deleted by the manager.
- The Orchestration: Manager-driven mutation of piece coordinates and Z-levels in windows_state.pdl.
- The Input: A standard TPMOS input-routing pipeline that translates keys and mouse clicks into map-entity movements.

Wraith keeps the good parts of GL-OS behavior (focus, drag, Z-order) but implements them within the absolute auditability of the TPMOS Piece/Map hierarchy.

*Note: This document has been corrected from historical unclarity (the 'Virtual Parser' assumption) to further up-to-date iterative clarity. It remains flexible until final data structures are achieved.*

3. Existing TPMOS rules to preserve

The TPMOS bible says the hierarchy is PIECE -> MODULE -> OS, and the OS/theater composes frames but must not discover project Piece state or synthesize Piece methods. See !.TPMOS_ONBORD_BIBLE_10.md lines 8-20.

Managers own project projection and publish flat UI data to gui_state.txt. See lines 17-29.

The marker-file discipline matters: frame_changed.txt and pulse files wake the renderer instead of blind polling. See lines 51-57.

Parser ownership matters: current_frame.txt is owned by the parser, and daemons should trigger render by writing frame_changed.txt. See lines 93-101.

Testing stays frame-based: inject keys into pieces/keyboard/history.txt, verify current_frame.txt or session_frame_history.txt, then record frame snippets and state diffs. See lines 106-110.

wraith-pm should copy these rules instead of inventing a hidden-memory desktop.

5. Why CHTMGL needs shape and color metadata

CHTMGL should carry metadata for shapes and colors because wraith-pm has two render products:

1. ASCII frame:
   A character-cell desktop that humans and AI can read.

2. Graphics/RGB frame:
   A raster frame that can be presented in GL or streamed to future RGB/HDMI devices.

If the layout only says "font text here", then the converter can only draw fonts. That is too weak.

If the layout says:

- tag type: window, panel, canvas, button, slider, image
- geometry: x, y, width, height
- color: bg, border, foreground, accent
- shape: rect, rounded_rect, line, sprite, tile, glyph, canvas primitive
- semantic id: object_id, role, focusable, hit region

then the same layout can produce:

- an ASCII approximation
- a graphics primitive list
- an RGB frame
- a hit-test layer for mouse
- an AI-readable audit frame

The metadata is not decoration. It is the bridge from ASCII to real graphics.

6. Target architecture

Pipeline:

input events
  -> wraith-pm state
  -> Wraith CHTMGL parser
  -> semantic scene tree
  -> ASCII frame
  -> audit frame
  -> optional graphics primitive frame
  -> RGB frame
  -> output backends

Backends:

- CLI presenter: prints ASCII frame and captures keyboard/mouse terminal events.
- GL presenter: consumes RGB frame and displays it in an OpenGL window.
- RGB/HDMI presenter later: consumes the same RGB frame without needing GL.
- AI/debug presenter: reads ASCII frame, audit frame, object map, and frame diffs.

The frame must exist before GL renders. GL is not the source of truth.

8. Contracts

8.1 CHTMGL layout contract

Minimum tags:

- window
- panel
- header
- menu
- menuitem
- button
- checkbox
- slider
- text
- textfield
- scroller
- canvas
- img
- video placeholder

Minimum attributes:

- id
- role
- title or label
- x, y, width, height
- color, bg, fg, border
- shape
- onClick
- href or layout
- source/src
- value/min/max for sliders
- focusable
- object_id or auto-generated stable object id

8.2 Scene tree contract

The Wraith parser should produce nodes like:

node|id=btn1|tag=button|role=button|x=10|y=40|w=180|h=30|fg=#ffffff|bg=#333333|shape=rect|text=Test Button|onClick=EVENT:test_click|focusable=1

This scene tree is the bridge between CHTMGL and every renderer.

8.3 ASCII frame contract

current_frame.txt remains a readable text frame:

- fixed terminal width/height
- visible focus markers
- menu selection markers
- window titlebars
- panel boundaries
- text content
- simplified slider bars
- simplified canvas placeholders or map content

8.4 Audit frame contract

audit_frame.txt should include:

- timestamp
- project_id
- active_layout
- frame_index
- terminal size
- window_count
- active_window_id
- selected_index
- mouse/cursor position
- list of windows
- list of controls
- active menu/options
- dirty regions
- links to RGB/object/hit maps

This is the AI/debug frame.

8.5 RGB frame contract

current_frame.rgb.txt should be sparse and inspectable:

pixel x y r g b a object_id

For speed later, add binary:

current_frame.rgba.bin
current_frame.object_id.bin

But keep text RGB because it is useful for audit and AI.

8.6 Object and hit-map contract

object_map.txt:

object_id|tag|id|role|x|y|w|h|label|action

hit_map.txt:

cell_x cell_y object_id

or for pixel precision:

x y object_id

This makes CLI mouse possible. A terminal click maps to a cell, the cell maps to object_id, object_id maps to action.

9. Rendering approach

9.1 ASCII renderer

Input: scene tree.
Output: current_frame.txt.

Rules:

- draw windows and panels as box characters or ASCII fallback
- draw focused controls with [>]
- draw active controls with [^]
- draw buttons as [label]
- draw sliders as [====|-----]
- draw checkboxes as [x] or [ ]
- draw canvas as either a text canvas, map projection, or named placeholder
- draw images as metadata-backed colored blocks or labels until graphic conversion is enabled

9.2 ASCII-to-graphics converter

Input:

- current_frame.txt
- current_frame.meta.txt
- object_map.txt
- CHTMGL scene tree

Output:

- graphics primitive list
- current_frame.rgb.txt
- current_frame.rgba.bin later

Important:
The converter should not be "font renderer only." It should use CHTMGL metadata to turn ASCII UI into graphics:

- window border -> rectangles/lines
- panel -> filled rect
- button -> filled rect + text/glyph label
- slider -> track rect + thumb rect
- checkbox -> rect + check mark
- canvas -> tile/sprite/primitive region
- text -> glyph pixels only where text is actually intended

This is why shape and color metadata belongs in CHTMGL.

9.3 GL presenter

Input:

- current_frame.rgb.txt or rgba.bin

Output:

- OpenGL window showing the exact RGB frame.

This should copy the frame-first idea from the wraith rgb-font project:

- write RGB frame first
- GL only uploads/presents the frame
- GL does not become the source of UI truth

The closest current reference is the older report's 105.rgb_gl]2d path: it reads pixel records into a buffer and uploads them to a GL texture.

10. Input routing

Keyboard:

- CLI keyboard writes session/input_events.txt or history.txt.
- GL presenter keyboard writes the same event file.
- Events are logical, not backend-specific.

Mouse:

- CLI mouse event gives terminal cell x/y.
- Convert cell to frame pixel region.
- Lookup hit_map/object_map.
- Dispatch onClick/href/focus/select.

GL mouse:

- GL presenter receives pixel x/y.
- Lookup object_map directly.
- Dispatch the same event format as CLI.

Event format:

EVENT key code=...
EVENT mouse x=.. y=.. button=.. state=..
EVENT click object_id=.. action=..
EVENT slider id=.. value=..
EVENT canvas id=.. x=.. y=..

Keep GL-OS prefixes where useful:

- SLIDER:<id>:<val>
- CANVAS:<x>,<y>
- EVENT:<name>
- VAR;<name>=<val>

These are already documented in GL-OS_ARCHITECTURE.md lines 57-63.

11. Project loading

Copy the working GL-OS pattern:

1. Read curated project list.
2. Scan projects/ for project.pdl.
3. Extract app_title or title.
4. Extract entry_layout.
5. Register in Project Explorer.

References:

- GL-OS spec lines 22-35 describe the discovery lifecycle and launch priority.
- gl_desktop.c lines 179-218 read PDL values.
- gl_desktop.c lines 278-344 load curated KVP and project.pdl projects.
- gl_os_projects.kvp lines 1-8 show curated GL project ids.

wraith-pm change:

- Prefer .chtmgl layouts.
- Support .gltpm only as compatibility input while remaking layouts.
- Do not route CHTMGL through CHTPML/CHTPM parser.
- Wraith owns CHTMGL parsing.

13. Non-goals

- Do not revive legacy glos.
- Do not make GL required for the first usable desktop.
- Do not make the renderer depend on screenshots.
- Do not make CHTMGL require CHTPML/CHTPM parsing.
- Do not infer UI semantics from colors after the fact.
- Do not make RGB output the only audit file. Keep ASCII and audit text.

14. First milestone definition

Milestone J2.1 is complete when:

1. wraith-pm renders a desktop.chtmgl layout to session/current_frame.txt.
2. It writes session/audit_frame.txt with windows, controls, selected index, and object ids.
3. It supports keyboard navigation in CLI.
4. It has object_map.txt and hit_map.txt ready for mouse mapping.
5. It can parse at least window, panel, text, button, slider, canvas from CHTMGL.
6. No GL window is required.

15. Second milestone definition

Milestone J2.2 is complete when:

1. ASCII frame converts to current_frame.rgb.txt.
2. CHTMGL color/shape metadata affects graphics output.
3. GL presenter displays the RGB frame as a texture.
4. GL input and CLI input write the same event format.
5. The same frame can be audited as ASCII, metadata, and RGB.

16. Final intention

wraith-pm starts as an ASCII project. It remakes the useful current GL-OS desktop and CHTMGL layout behavior, but it makes frames sovereign.

The core product is not a GL window. The core product is:

- an ASCII frame
- a semantic scene tree
- an audit frame
- an RGB frame

GL is optional. GL can render the ASCII-derived RGB frame. Later, RGB/HDMI screens can consume the same RGB data. This gives us a desktop that is visible in CLI, debuggable by AI, convertible to graphics, and ready for real screen output without changing the underlying project state or layout logic.
