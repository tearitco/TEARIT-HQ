# XOKE-PET README

This document is the working handoff for the XO-PET / moke-pet bundle in this session.

It is written for both humans and agents. The goal is to explain the real pipeline, the launcher contract, the current control model, the known pitfalls, and the assumptions that should stay fixed unless a future change explicitly updates them.

## What This Project Is

XOKE-PET is a compatibility layer between:

- `moke-pet`, which remains the simulation engine
- `xo-pet`, which provides the optional human-control / projection layer
- TPMOS / CHTPM, which provide the shared launcher, parser, frame, and menu conventions

The project is not trying to invent a new UI pattern. It is trying to preserve the existing TPMOS shape while making controller support optional, modular, and scalable.

## What The Pet Is

The "pet" is the simulation actor. In the current codebase, a pet is a sovereign entity with state, methods, and a turn in the epoch loop.

What the pet does now:

- exists as a named entity in the world/map enclosure
- has visible state such as health, hunger, and turn position when the manager logs it
- performs turn-based actions like `breathe`, `scan`, `rest`, `eat`, and `check_death`
- can be possessed by a controller when the XO surface is active
- can also run fully autonomously when no controller is attached
- can expose extra methods such as `ai` for delegated one-step control

Why the pet exists:

- to make the simulation visible and auditable
- to let the same entity support autonomous runs and human-in-the-loop control
- to provide a stable base for future learning systems

The pet is not just a UI object. It is the living simulation unit whose state is advanced by the manager and whose behavior can later be driven by:

- simple rule logic
- FSM-based behavior
- reinforcement learning
- local lightweight models
- API-backed models
- knowledge distillation into corpuses

What is already present:

- the autonomous manager loop
- turn-based entity actions
- per-epoch logging
- state snapshots
- controller possession and release semantics
- a dynamic methods menu for active control

What is intended next:

- richer decision policies
- FSM layers for predictable behavior
- RL training over logs and rewards
- local small-model inference
- API model assistance when desired
- distillation pipelines that convert experience into reusable corpuses
- rewind / replay support based on saved frames and state
- visible buffered-selection feedback in the live frame before `Enter`

## Current Architectural Model

The current rule is:

- `project -> controllers/enclosure -> map -> entities`

Interpretation:

- the project owns the bundle
- controllers are modular and can be dropped into or removed from an enclosure directory
- map/world data sits below the controller layer
- entities are the simulation actors

Important nuance:

- `moke-pet` should stay autonomous when no controller is present
- `xo-pet` should be the optional control / possession surface
- the visible switcher name is `xolector`
- `xelector` may remain as a compatibility alias in code and old paths
- controller nav should be buffered, with `Enter` acting as the commit signal

## Control Model

The current control model is:

- `xolector` is the pet switcher
- `xolector` is not a world pet
- `xolector` methods are only pet-selection methods
- project controls are always visible
- when a pet is possessed, that pet's methods replace the switcher methods
- `release` or `esc` returns control to `xolector`
- `AI` is a pet method
- `AI` should behave like one-step delegated control unless `resume` is active
- the manager should emit a visible turn summary after an end-turn commit

The intent is that the same code path can support:

- fully autonomous simulation
- one controller
- future multi-controller control

## Pipeline

Autonomous path:

1. `sh button.sh auto`
2. root launcher enters the autonomous manager path
3. the manager writes frame snapshots and state logs
4. the display pulse files are touched after frame updates

Controller path:

1. `sh button.sh r` or `sh button.sh controller`
2. the nested bundle launches the CHTPM surface
3. the project loader selects `xo-pet-v1`
4. the XO-PET layout renders the project controls, switcher, active methods, and log
5. controller commands are written into `projects/xo-pet-v1/history.txt`
6. the manager consumes those commands and updates the session state

Compile path:

1. `sh button.sh c`
2. `xo-pet-launch.sh build`
3. `#.dev-storage/#.tools/compile_all.sh`

## What Has Been Verified

The following were verified in this session:

- `sh button.sh auto` starts the autonomous manager path
- `sh button.sh r` lands in the live ASCII CHTPM/XO-PET flow
- the live XO-PET frame now shows populated state fields instead of blank placeholders
- the controller runner writes to `projects/xo-pet-v1/history.txt`
- the controller manager accepts command-style controls and ASCII digit input
- `start`, `pause`, `step`, `possess`, `release`, and `ai` are part of the control model
- the startup cleanup prevents stale controller commands from replaying into a fresh session
- `sh button.sh c` now uses the legacy bundle-local compile script
- a direct manager smoke test proved `KEY_PRESSED: 51` only buffers nav and `KEY_PRESSED: 13` commits it
- after commit, the manager advances one epoch and writes the compact `acts:` turn summary into the visible frame state

## Known Pitfalls

- The API shell can block `/dev/tty`-dependent controller tests.
- Some stale files existed in older runs and caused replay confusion.
- The monolith is a reference, not the active XO-PET bundle.
- The controller surface must stay CHTPM-shaped or older tools will misread it.
- Do not replace the dynamic methods menu with a bespoke terminal panel unless the layout contract is also updated everywhere.
- `manager.c` still exists outside a fully TPMOS-compliant directory layout in this bundle; that is a cleanup concern, not a blocker for the current control flow.
- If the frame shows `Input consumed:` but no epoch advance, the user likely forgot `Enter`.
- If `button.sh controller` is blocked in the API shell, use direct manager smoke tests and inspect `projects/xo-pet-v1/pieces/manager/gui_state.txt`.

## Assumptions To Keep

Unless a later doc explicitly changes them, keep these assumptions:

- `moke-pet` is the simulation truth
- `xo-pet` is the optional control / projection layer
- `xolector` is the visible switcher name
- `AI` is one-step control unless resume is active
- project controls always remain visible
- possessed pets expose their own methods directly
- `release` / `esc` returns to `xolector`
- the compile path must remain reachable through `button.sh c`
- the compile action should use the legacy bundle-local `compile_all.sh`

## Future Plans
