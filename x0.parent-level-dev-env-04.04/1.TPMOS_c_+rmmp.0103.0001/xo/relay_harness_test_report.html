Summary

Tested the tomom chatbot (C-based neural network with Mixture of Experts) through four relay interface approaches: direct binary, iqa-fork ask.sh relay (LAN Mac ollama), HTTP relay (http_server.c), and local ollama. The gem-dev harness and bot5 are available but are concurrent agent frameworks, not LLM chat relay harnesses. No "middle-house" solution exists in the codebase.

Relay Approaches Tested

1. Direct Binary Working

.//+x/chatbot_moe_v1.+x curriculum_bank.txt "What is math" 5 0.8

Result: Works. Loads 2610 vocab words across 15 curricula. Response is weak (e.g., "their their the language the") — the model is untrained/synthetic, producing word-order artifacts. Expected behavior for a prototype without trained weights.

2. iqa-fork ask.sh Relay Working

bash 44xyz.01.00/iqa-fork/ask.sh gemma3:270m "What is math?" 15

Result: Works well. This is a curl-based relay to 10.0.0.144:11434 (LAN Mac ollama). Returns coherent, well-formed responses:

Mathematics is a branch of science and mathematics that deals with the study of numbers, shapes, and concepts.

The ask.sh script uses curl to POST to /api/generate on 10.0.0.144:11434, pipes response through json_parser.+x to extract content. This is a valid LLM relay harness.

3. HTTP Relay (tomom http_server.c) Broken

./+x/http_server.+x  (serves on port 8080)
curl http://127.0.0.1:8080/api/chat

Result: BROKEN. The HTTP server compiles and serves the HTML web interface (GET / returns a Bootstrap page with title "3-Stage LLM Chatbot Interface"). However, the API endpoint /api/chat (POST) has a request-parsing bug: it scans the HTTP buffer for \r\n\r\n to find the JSON body, but the buffer parsing logic corrupts the JSON payload, causing the chatbot to attempt loading files named "number", "start-token", "end-token", etc.

  • All "Error opening vocab file: No such file or directory" messages
  • "Merged vocabulary size: 0"
  • Segmentation fault (null pointer dereference on empty vocab)

Root cause: The buffer tokenization at lines 351-353 uses strtok() which mutates the buffer before body extraction happens. The tokenizer corrupts the HTTP body content before it reaches handle_chat_request().

4. Local Ollama (llama3:latest)

curl http://127.0.0.1:11434/api/generate -d '{"model":"llama3:latest","prompt":"Hello","stream":false}'

Result: Slow startup (~10s) but works. Local llama3:latest model is available. Larger models have significant startup latency.

Recommendations

  1. Use iqa-fork ask.sh as the relay: It's the most practical working relay. For tomom specifically, a wrapper can pipe the LLM response through the tomom vocab comparison (calculate similarity against vocab embeddings).
  2. Fix http_server.c: The /api/chat endpoint has a parsing bug at lines 351-353. The strtok() call mutates the buffer before body extraction via strstr(buffer, "\r\n\r\n") can safely read it. Fix: extract the body pointer before tokenizing the request line, or copy the body to a separate buffer before tokenizing.
  3. Local ollama for offline use: Local llama3:latest works but has ~10s startup. For quick tests, use the LAN Mac gemma3:270m which responds in under 2s.
