1. ROOT CAUSE (the headline)
================================================================================

The agy-text-editor manager has NO BINARY on Windows, and is NOT IN THE WINDOWS
BUILD SCRIPT AT ALL.

  Evidence 1 - the binary does not exist:
    projects\agy-text-editor\manager\  contains ONLY:
        agy-text-editor_manager.c   (40021 bytes, source)
        gui_state.txt               (3597 bytes)
    There is NO +x\ directory.      (Test-Path -> False)

  Evidence 2 - the build script never builds it:
    button.ps1 c -> pieces\buttons\windows\compile.ps1 (8 lines)
      -> pieces\buttons\legacy\compile_all.ps1 (92 lines)
    compile_all.ps1 line 39-44 enumerates the project managers by hand:
        Compile-Piece "projects\op-ed\manager\op-ed_manager.c" ...
        Compile-Piece "projects\fuzz-op\manager\fuzz-op_manager.c" ...
        Compile-Piece "projects\user\manager\user_manager.c" ...
        Compile-Piece "projects\man-pal\manager\man-pal_module.c" ...
    It is a HARDCODED list, not a glob. "agy" appears ZERO times in all 92
    lines. agy-text-editor is simply absent from the Windows build.

  Evidence 3 - the consequence, observed live:
    projects/agy-text-editor/layouts/editor.chtpm:2 declares
        <module>projects/agy-text-editor/manager/+x/agy-text-editor_manager.+x</module>
    That path does not exist, so the parser cannot launch it. Confirmed at
    test time: after engaging interact mode and injecting 3 printable keys,
    the only live TPMOS process was chtpm_parser.+x. Zero agy processes.

  WHY LINUX WORKS AND WINDOWS DOES NOT: this is not a logic difference in the
  key path. It is that the Windows compile script never learned about this
  project. My earlier hypothesis (that the bug lived in the Windows key
  capture muscle) was WRONG for this symptom and is withdrawn - see section 5.

3. INCIDENTAL FINDING - the gate field cannot be trusted (Rule 10 violation)
================================================================================

K9 Rule 10 requires reading the actual interact-gate field at the moment the
test key is sent. For this parser the obvious candidate is
pieces/display/active_gui_index.txt. IT IS NOT SUFFICIENT.

  Observed: active_gui_index.txt read "1" both in nav mode AND in active
  interact mode. It did not change when the gate engaged.

  Why, in source: chtpm_parser.c:2242-2243
      if (active_index != -1) active_gui_idx = elements[active_index].interactive_idx;
      else                   active_gui_idx = elements[focus_index].interactive_idx;
  When focus and active are the same element (index 1 here) both branches
  write 1, so the file cannot distinguish the two states.

  The ONLY reliable gate signal found is the frame text itself:
      "Active [^]:  (ESC to exit)"
  and the [^] marker replacing [>].

  This directly substantiates section 5 finding B.5: agy-text-editor_manager.c
  cannot see the frame, and the exported gate file cannot tell it either, so
  the manager genuinely has no way to know whether interact mode is engaged.

4. TEST-METHODOLOGY ERRORS I MADE, recorded per K9's own practice
================================================================================

K9's SCOPE ADDENDUM 2026-08-13 says to keep self-corrections in the testing doc
precisely so the next agent repeats them less. These are mine, kept here too.

  M1 - I launched without checking for existing processes (K9 Mistake #3).
       A live stack from a 04:20 session was already running
       (chtpm_parser PID 19712, clock_daemon, loader_module,
       response_handler). My new parser exited on contention.
       Also, I had truncated pieces/keyboard/history.txt to 0 while a live
       parser held a byte offset ~800 into it. Per chtpm_parser.c:3062
       (fseek to last_history_position) that live parser would then skip
       anything appended. I desynced a running process in about 30 seconds.
       This is exactly the byte-offset fragility logged as a latent risk.

  M2 - I drew a false conclusion from a stale artifact. The frame I read
       first had mtime 04:20:12 - it was LAST NIGHT's render, not live. I
       briefly treated it as proof the renderer worked. Frame evidence must
       be mtime-checked, not just read.

  M3 - My first injection test used 'h', which in nav mode hits the else at
       chtpm_parser.c:2851 (digit_accum = 0) and changes nothing visible. I
       compared frame CONTENT, saw no change, and nearly concluded injection
       was broken. It was not - I had picked a key with no visible effect.
       This is K9 Pitfall 7 / "Mode/context sensitivity" biting exactly as
       documented. Fix: inject a key with an OBSERVABLE effect (arrows move
       the focus marker) and check mtime as well as content.

  M4 - On Windows, a .+x binary cannot be run by invoking it directly from
       PowerShell; it raises "Cannot run a document in the middle of a
       pipeline" because the +x extension is not a recognised executable.
       My first three "parser exited immediately" readings were this
       PowerShell artifact, NOT real crashes. The house's own path works:
       run it under MSYS2 bash, as pieces/buttons/windows/run.ps1:22 does
       via bash -lc "... run_orchestrator.sh".

5. CORRECTIONS TO THE BUG LOG (win-open-bugs-s26.txt)
================================================================================

  WITHDRAWN - the AsciiChar / six-virtual-key theory as the cause of the
  reported interact-mode symptom. It is a real Windows-only weakness of
  keyboard_input_win.c (single-byte AsciiChar at :81, discarded when zero at
  :88, only 6 VK codes at :83-87) and it MAY still affect the PHYSICAL
  keyboard, but it is demonstrably NOT why interact mode fails, because
  interact mode fails identically with relay injection that never touches
  that code at all. The cause is the missing binary.

  STILL TRUE and unaffected by this test:
    - B.2 backspace swallowed at agy-text-editor_manager.c:580
    - B.3 '2'/'6' stolen as commands at agy-text-editor_manager.c:652-657
    - B.5 no interact-mode bit in the injected-key protocol, now with live
      evidence from section 3
    - Bug A entirely (frame unicode / codepage) - untouched by this test.
      The frame file was confirmed correct UTF-8 during this session.

  STILL UNTESTED: the physical-keyboard capture half. Relay injection
  bypasses keyboard_input_win.c completely, so K9 Rule 11 applies - testing
  the capture path itself needs a REAL synthetic keypress. The Windows
  equivalent of the XTest injector K9 prescribes on Linux is SendInput,
  which writes into the same console input buffer ReadConsoleInput reads.
