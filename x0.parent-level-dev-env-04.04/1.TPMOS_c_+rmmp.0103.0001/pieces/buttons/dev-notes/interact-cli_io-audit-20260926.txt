================================================================================
INTERACT-MODE AUDIT -- WHICH MANAGERS ACTUALLY HAVE THE B.2/B.3 DEFECT
================================================================================

Written 2026-09-26, on branch kilo. Audited after fixing agy-text-editor's
backspace and stolen digits, because that fix turned out to rest on a signal
only ONE of eight managers was reading. This file records which of the others
share the defect, which do not, and -- importantly -- which could not be
verified at all on Windows, so nobody repeats the work or assumes a verdict
that was never tested.

*** CORRECTED 2026-09-28. READ THIS FIRST. ***
The original version of this file said cpp-llm, gem-dev and groq-ollama were
NOT BUILT ON WINDOWS and that their conclusions were code-read only. All three
are now built, running and partly runtime-verified. That statement was correct
when written and is now wrong, and it was wrong in the most expensive possible
way: it invited the next agent to either repeat the ports or to distrust the
results. Sections 5-7, the verdict table and section 9 have been rewritten
against what was actually tested. slop-ed-dev is the only one of the four still
unbuilt.

THE SIGNAL, FOR REFERENCE. chtpm_parser.c's export_active_index() (:2259)
writes pieces/display/active_gui_is_typing.txt every frame: "1" when the
focused element is genuinely active and accepting keystrokes, "0" when merely
focused. active_gui_index.txt alone cannot express that difference. Only
wraith-alpha_manager.c read the companion file
(sync_active_gui_index_from_display(), :6247, default 0). The other seven read
only the conflated file.

Reading the conflated file is NOT automatically a bug. It only matters where a
manager uses it to decide "is a text element holding the keyboard?" So each
manager was checked for that specifically, not pattern-matched.

1. wraith-alpha -- NOT A BUG (the reference implementation)
--------------------------------------------------------------------------------
Already reads active_gui_is_typing.txt and defaults to 0. Nothing to do. It is

2. agy-text-editor -- FIXED (two separate commits)
--------------------------------------------------------------------------------
TWO genuinely different bugs, often conflated:

  a) Its editor is a plain document edited by text_edit_key.+x, not a cli_io.
     Backspace was intercepted and routed to a cli_buffers.txt "e"-prefixed
     line, but the typing path never writes an "e" line, so that buffer was
     always empty and the key was dropped in silence. And '2'/'6' ran
     SET_CLEAR_FILE/SET_NEW_FILE, so those characters were untypeable. One
     early gate in process_key() -- when the layout is editor.chtpm AND
     active_gui_is_typing is 1, every key goes to handle_interact_key() --
     fixed both at the shared root. Commit 3a2a0027.

  b) Its file_browser cli_io fields were hit by the shared parser bug below.

  LANDMINE, NOT FIXED, NEEDS AN OWNER DECISION:
  projects/agy-text-editor/agy-text-editor_manager.c (the TOP-LEVEL copy) is a
  near-duplicate of projects/agy-text-editor/manager/agy-text-editor_manager.c
  and still contains the ORIGINAL unfixed backspace branch and the original
  stolen '2'/'6' handling. It is not built (compile_all.ps1 builds the
  manager/ one), and editor.chtpm points at manager/+x/, so it is inert today.
  But it is the file with the most obvious name, and editing it would change
  nothing while looking correct. Either delete it or replace it with a
  one-line pointer to the real file. NOT DONE HERE: deleting a source file is
  not this audit's call, and a stale duplicate is a trap worth flagging
  loudly rather than quietly removing.

3. op-ed -- FIXED by the shared parser change; its own branch is dead-but-kept
--------------------------------------------------------------------------------
file_browser.chtpm has cli_io id="search_query" and id="file_path_input".

CORRECTION TO AN EARLIER CLAIM IN win-open-bugs-s26.txt: I previously wrote
that op-ed and slop-ed-dev carry "a structurally identical DEAD
cli_buffers.txt backspace branch". That was wrong about "dead". The branch
writes "s"- and "f"-prefixed lines, and chtpm_parser.c keys cli_buffers
prefixes by the element id (username->U, password->P, answer->A, else the
first character of the id -- :2990-2992). op-ed's ids start with 's' and 'f',
so those lines ARE the live wire format. The branch is correct; it is merely
unreachable, because the parser never forwards key 8/127 to the manager (see
section 8). Left in place as a no-op fallback rather than deleted, since a
future path that does forward the key would want it.

Verified live on op-ed (it is built and runs on Windows): typed x,y,z
published 'sx'/'sxy'/'sxyz'; backspace published 'sxy'. Before the fix,
nothing was appended at all.

--------------------------------------------------------------------------------
4. fuzz-op -- NOT A BUG
--------------------------------------------------------------------------------
Has a button onClick="INTERACT" but NO cli_io and no text field anywhere, and
no cli_buffers reference at all. Its key handling is entirely map-control:
'9'/ESC/2008 exit, WASD and 1000-1003/2100-2103 movement, 'x'/'z' actions,
'6' an action, Enter confirm. There is no typing surface for a key to be
stolen FROM, so the whole bug class is inapplicable. Its use of
active_gui_index.txt (sync_focus(), :297) is legitimate focus tracking for its
own gui_state, not a mode decision. Nothing changed. Do not "fix" this one.

5-7. cpp-llm, gem-dev, groq-ollama -- NOW BUILT AND RUNNING (was: not built)
--------------------------------------------------------------------------------
SUPERSEDED IN PART. The original text here said none of the three was in
compile_all.ps1, none had a built manager, none could be launched or tested
here, and that their conclusions were code-read only. All three have since
been ported and added to the build. Commits 2350046d (cpp-llm), f9d8820c
(groq-ollama), c4751492 (gem-dev), all on kilo.

THE OMISSION WAS REAL AND WAS THE ACTUAL BUG. None of the three was in
pieces/buttons/windows/legacy/compile_all.ps1, so none had ever been built on
Windows -- they could not run, not badly. All three failed to compile on the
same pre-existing error at line 7, `#include <sys/wait.h>`, and each carried
agy's exact POSIX profile: 3-4 fork(), 8 execv, 3 waitpid, 4-5 setpgid,
WEXITSTATUS.

WHAT THE PORT ACTUALLY REQUIRED, since this is the part a future agent will
otherwise rediscover the hard way:
  - The easy fixes are mechanical: guard sys/wait.h and unistd.h, #undef
    MAX_PATH (windows.h defines it as 260, these files define it as 4096),
    shim getline/mkdir/usleep, widen log_pid() to long and make flock()
    POSIX-only.
  - The NON-mechanical one is executable resolution. These managers call
    their ops by BARE NAME ("connect_op") and let execvp find them. On
    Windows there is no file of that name -- compile_all.ps1 writes
    "connect_op.+x" -- and CreateProcess does not search PATH the way execvp
    does. So win_resolve_tool() tries "", ".exe" and ".+x" against each base
    path and walks PATH explicitly for real system tools like curl. Without
    the ".+x" arm every op lookup returns NULL and the app silently does
    nothing; without the PATH walk every curl call does. The first cpp-llm
    build appeared to succeed and still found zero ops. That is what exposed
    it.
  - run_tool()'s pipe/fork/dup2/read loop becomes CreatePipe/CreateProcess,
    and the pipe's read end needs HANDLE_FLAG_INHERIT cleared or the child
    keeps a duplicate and the read loop never sees EOF.
  - groq-ollama additionally fork()s and does ALL the work IN THE CHILD for
    its gemini branch (popen the SSE stream, parse, flatten, _exit). There is
    no fork on Windows, so that body moved verbatim onto a worker thread, and
    g_ai_handle holds the THREAD handle -- still a HANDLE, so the existing
    WaitForSingleObject poll in check_ai_status() keeps working. Because that
    handle is a thread in one branch and a process in the other, their exit
    codes need GetExitCodeThread vs GetExitCodeProcess respectively; that
    split is tracked with g_ai_handle_is_thread. Getting it wrong returns a
    meaningless value while looking like it worked.
  - gem-dev built its curl argument vector INSIDE the forked child. A forked
    child inherits the parent stack so that was free; a CreateProcess child
    cannot see those locals at all, so the vector had to be hoisted into the
    parent for both branches.

All three use <cli_io id="input_text">, the legacy single-slot form with no
target_id, and none has an onClick="INTERACT" element -- so the B.2/B.3 shape
(backspace swallowed, nav digits stolen) does not apply: with no INTERACT
element there is no key-forwarding path a manager could misinterpret.

WIRE FORMAT, MEASURED LIVE. The parser writes cli_buffers.txt whether or not a
manager is running, so this much was testable without any port. Running the
parser alone against gem-dev.chtpm and typing a,b,c into its
<cli_io id="input_text"> published exactly:

    'ia'   [i=0x69 a=0x61]
    'iab'  [i=0x69 a=0x61 b=0x62]
    'iabc' [i=0x69 a=0x61 b=0x62 c=0x63]

The leading 'i' is the generic-fallback prefix (first character of the element
id), confirmed at byte level. This is the format any consumer of that field
has to expect. Re-measured independently on 2026-09-27 under cpp-llm and got
the same 'i' prefix ('ih','ihe','ihel').

  a) gem-dev -- SUSPICION REFUTED, and the earlier claim in this file was
     WRONG. I previously wrote that gem-dev "appears never to strip that
     prefix, so its view of the user's text would begin with a spurious 'i'",
     which would have meant a phantom 'i' reaching the model and, worse,
     breaking the permission prompt at :1172 (strcasecmp(trimmed,"y") would
     never match a typed "y"). That was based on a grep context window that
     began at line 1288 and cut off the line above it. gem-dev actually does
     it correctly at :1286:

         if (line[0] == 'i') {
             strncpy(last_line, line + 1, sizeof(last_line) - 1);
             ...
         }

     It filters on the 'i' prefix AND strips it, then removes the trailing
     newline. The chain to the model is sound: parser -> 'i'-prefixed line ->
     stripped at :1286 -> g_last_buf_input -> set_input_text_override() ->
     gui_state input_text= (:1141-1142) -> process_input_trigger(). There is
     no phantom 'i'. gem-dev is NOT BUGGY on this point. The lesson is the
     one the khtpm skill warns about -- do not diagnose from a truncated read
     window, and above all verify before publishing a claim in writing.
     STILL TRUE AFTER PORTING: re-checked against the ported file, gem-dev
     strips the prefix correctly.

  b) cpp-llm and groq-ollama -- REAL, AND NOW FIXED. Both had this in their
     autocomplete-accept path (cpp-llm :363, groq-ollama :376):

         FILE *bfw = fopen("pieces/apps/player_app/cli_buffers.txt", "w");
         if (bfw) { fprintf(bfw, "%s\n", chosen); fclose(bfw); }

     Two defects. "w" TRUNCATES, and cli_buffers.txt is a single global file
     shared by every project on the desktop, so accepting one autocomplete
     suggestion in one app silently destroyed every other app's field
     history. And the value was written with NO prefix, which is a format the
     parser never emits and that every prefix-keyed consumer ignores -- so the
     line could not be matched by the very "frontend" the adjacent comment
     says it is keeping in sync, which defeated the stated purpose.

     Fixed to append ("a") and to carry the 'i' prefix, matching the measured
     wire format above. Note these two apps read their typed text from
     get_gui_var("input_text") (cpp-llm :929) -- i.e. from gui_state, not from
     cli_buffers -- so they were never themselves victims of the prefix, only
     perpetrators of the truncation.

     STILL NOT RUNTIME-VERIFIED, and the reason is specific rather than
     general: handle_choose_path() returns before its write whenever no
     completion labels are loaded, and the parser consumes digits while the
     cli_io holds focus, so the autocomplete-accept path is not reachable
     from this harness. What IS verified: the changed statements compile
     clean, and the append semantics are real -- a fragment doing the same
     fopen("a")/fprintf into a file already containing "preexisting-line"
     produced "preexisting-lineihello world", i.e. the prior content
     survived. With "w" it would have been destroyed. The prefix character
     itself was measured off the real parser, not assumed.

  RUNTIME EVIDENCE, 2026-09-27. This is the part that could not exist before.
  Each manager was launched under the real chtpm_parser.+x against its own
  layout, so the layout's <module> tag resolved to the built artifact:

    - cpp-llm -- FULLY input-tested, and it is the one that demonstrates the
      section 8 backspace fix in an app that previously could not run at all.
      Typed h,e,l,l,o into <cli_io id="input_text">; cli_buffers.txt received
      'ih','ihe','ihel','ihel','ihelo'. Backspace twice republished 'ihel'
      then 'ihe', and the manager's gui_state read input_text=he -- current,
      not the stale pre-backspace value. manager_debug.log confirmed

      (MinGW has no ifaddrs.h).

    - groq-ollama -- manager and parser both alive, gui_state.txt written, all
      18 keys published, 6 API endpoints resolved from config/apis.txt. NOT
      input-tested.

    - gem-dev -- manager and parser both alive, gui_state.txt written, the
      Gemini endpoint resolved, completion slots published. NOT input-tested.

  NOT VERIFIED FOR ANY OF THE THREE, and this is the load-bearing caveat: NO
  LIVE AI ROUND TRIP. The endpoints in these projects' apis.txt are 10.0.0.x
  machines not reachable from here. So for all three the curl spawn, the
  exit-code handling and groq-ollama's thread-vs-process handle split are
  proven ONLY by compilation and by the manager starting cleanly -- not by a
  reply arriving. The groq-ollama handle-kind split in particular is the piece
  most in need of a real gemini run before anyone relies on it.

  Also flagged, still unfixed and now MEASURABLE: all three write

8. THE ONE THAT WAS ACTUALLY SHARED -- cli_io backspace, chtpm_parser.c
--------------------------------------------------------------------------------
This is the real find of the audit, and it is not a per-manager bug at all.

A cli_io has two sinks:
  - cli_buffers.txt -- what managers actually READ their field values from.
  - gui_state.txt   -- written via save_cli_io_gui_state().

Printable characters wrote to BOTH, so the sinks agreed. Backspace truncated
the element's own input_buffer and wrote gui_state.txt ONLY, and -- unlike the
Enter branch, which calls inject_raw_key(13) -- it never called
inject_raw_key() and never touched cli_buffers.txt. So the keystroke reached no
manager at all, the field looked correct on screen, and every manager went on
serving the pre-backspace value. Affects every project with a cli_io.

Verified live BEFORE the fix: typing "abc" published sa/sab/sabc, and a
following backspace left cli_buffers.txt still ending in "sabc" while the field
correctly showed "ab".

Fix (commit 2aabe1cb): the prefix rule was extracted into
append_cli_buffer_line() and called from the backspace path too, so both edits
publish identically. star_count is a separate parameter because the password
mask historically counted from the length BEFORE the newly typed character was
appended; the printable path passes the pre-append length to preserve that
exact output, and backspace passes the post-truncate length so the mask matches
the characters that remain.

Verified live AFTER, agy file_browser: typed a,b,c -> 'sababa','sababab',
'sabababc'; backspace x2 -> 'sababab','sababa'; on-screen field "ababa_",
matching the last published value exactly. Also verified on op-ed (section 3).
