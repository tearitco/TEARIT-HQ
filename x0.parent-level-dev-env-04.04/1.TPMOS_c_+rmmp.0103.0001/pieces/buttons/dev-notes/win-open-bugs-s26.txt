## BUG A — CLI FRAME UNICODE RENDERS AS MOJIBAKE
================================================================================

### A.0 What is actually on disk (verified — this is NOT the bug)

pieces/display/current_frame.txt starts with these bytes:

  E2 95 94 E2 95 90 E2 95 90 E2 95 90 E2 95 90 E2 95 90 E2 95 90 E2 95 90
  UTF-8 decode ->  ╔═══════

So the frame file itself is CORRECT UTF-8. `╔` is U+2554 and encodes as
E2 95 94. The parser is not corrupting anything on the way out. If you see
`â•”â•Ð` on screen, that is correct UTF-8 bytes being decoded as CP1252
somewhere AFTER the file is written. The corruption is in the output pipeline,
not in compose_frame().

Reproduce the corruption yourself with this, which mimics a CP1252 read:
  Get-Content pieces\display\current_frame.txt -TotalCount 3
PowerShell 5.1 Get-Content defaults to the ANSI code page, so it shows
`â•”â•Ðâ•Ð` even though the file is fine. Do NOT trust PowerShell's view of
these files — read them with [System.IO.File]::ReadAllText($p, [Text.Encoding]::UTF8).

### A.1 Where the frame is written

pieces/chtpm/plugins/chtpm_parser.c
  2454  compose_frame() — builds the frame buffer
  2383  append_colored_text() — concatenates layout label text into the buffer
  2491  bottom border built from the ASCII BOX_* macros (+ = +)
  2562  build_path_malloc("pieces/display/current_frame.txt")
  2563  fopen(..., "w")
  2564  fprintf(out_f, "%s", frame)   <-- raw UTF-8 bytes, no transcoding
  2567  appends "P\n" to pieces/display/renderer_pulse.txt

The BOX_* macros at chtpm_parser.c:38-51 are ALREADY ASCII:
  BOX_TL "+"  BOX_TR "+"  BOX_H "="  BOX_V "|"  etc.
The comment there says "ASCII for consistent display". So the macro layer is
fine — the Unicode comes from somewhere else (see A.2).

### A.2 Where the Unicode actually comes from (the real source)

The glyphs are NOT coming from the BOX_* macros. They are hardcoded literals
in two places:

1) Layout files, as literal text in label attributes:
   projects/agy-text-editor/layouts/editor.chtpm:5,7,8,10,15
   projects/agy-text-editor/layouts/file_menu.chtpm:5,6,9,10,16,17,19
     e.g.  <text label="╔════════════ A G Y   E D I T O R ════════════╗" />

2) agy-text-editor manager, 14 hardcoded `║` literals written into gui_state.txt:
   projects/agy-text-editor/manager/agy-text-editor_manager.c
     379, 467, 475, 709, 711, 716, 725, 738, 857, 864, 879, 891, 902, 903
     e.g.  snprintf(formatted, sizeof(formatted),
                     "<text label=\"║  %-40.40s ║\" /><br/>", line);

pieces/chtpm/layouts/os.chtpm (lines 2-20) WAS converted to ASCII (+ = |).
That is why the OS menu looks fine and the agy editor looks broken. The
March 31 claim in pieces/buttons/dev-notes/win-lin-parity-m31.txt:589-596
("Replaced all hardcoded Unicode in C source files", "Converted all .chtpm
layout files to ASCII") was only ever true for the OS-level layouts. The
per-project layouts and the agy manager were never converted. That doc is
stale and should be corrected.

### A.3 Where the frame is printed (the actual suspect)

The ACTIVE Windows render path is NOT windows_renderer.c. On Windows the
orchestrator inlines the render loop in its own thread and never spawns
renderer.+x, because _spawnl does not inherit the parent console stdout.

pieces/chtpm/plugins/orchestrator.c
  320  void* render_thread_func(void* arg)
  322  #ifndef _WIN32 branch spawns renderer.+x; the Windows branch skips this
  325  const char* pp = "pieces/display/renderer_pulse.txt"
  328  polls st.st_size for new frames
  330  history mode:  printf("\n\n\n\n\n--- FRAME UPDATE ---\n")
  331  static mode:   system("cls")
  333  char buf[4096]; while (fgets(buf, sizeof(buf), f)) printf("%s", buf);
  334  fflush(stdout)

pieces/display/windows_renderer.c (192 lines, NOT on the active path)
  46   FillConsoleOutputCharacterA(h_console, ' ', ...)   <-- ANSI variant
  91   fopen("pieces/display/current_frame.txt", "r")
  100  fread(content, 1, file_size, frame_file); printf("%s", content);

pieces/display/renderer.c (the cross-platform one, also not on the win path)
  20-36  clear_screen() uses FillConsoleOutputCharacter (TCHAR variant)
  85    printf("%s", content)

Every one of these three paths is byte-level with ZERO encoding awareness.

### A.4 The missing codepage call (root cause candidate, high confidence)

I grepped the whole tree for every plausible fix. ALL OF THESE ARE ABSENT
from every .c/.h/.ps1/.sh in the repo:

  SetConsoleOutputCP          NOT FOUND  (only inside vendored stb_image.h)
  SetConsoleCP                NOT FOUND
  WriteConsoleW               NOT FOUND
  _setmode(..., _O_U8TEXT)    NOT FOUND
  chcp 65001                  NOT FOUND  (no .ps1, .bat or .sh sets it)

Only Console API calls in the whole render path are FillConsoleOutputCharacterA
(windows_renderer.c:46), FillConsoleOutputCharacter (renderer.c:32), and
SetConsoleCursorPosition. None of them touch the output code page.

Therefore: UTF-8 bytes from current_frame.txt reach the console's output
code page untouched, and whatever that code page is, it decodes them as
single-byte legacy characters. The glyph `╔` (E2 95 94) becomes three
mojibake characters. That matches the reported symptom exactly.

There is a second, compounding hop. run.ps1 does not run the orchestrator
directly:

  button.ps1:26-28   "run"/"r" -> pieces\buttons\windows\run.ps1
  run.ps1:22         & C:\msys64\usr\bin\bash.exe -lc "... run_orchestrator.sh"

So stdout goes orchestrator (C runtime) -> MSYS2 bash -> PowerShell console.
That is THREE encoding boundaries, and MSYS2's own translation layer sits in
the middle. Any one of the three can be the one doing the wrong decode.

NOTE: the GL renderer is NOT affected. pieces/display/gl_renderer.c:219-245
has a decode_utf8() that turns UTF-8 into codepoints for FreeType. That is a
separate raster path and proves the house already knows how to do this
correctly; the console path just never got the equivalent.

### A.5 What I could NOT prove from source alone

I cannot tell from reading the source WHICH of the three hops corrupts the
bytes, because no code anywhere reports the active output code page. I will
not guess. To pin it, add a one-time diagnostic to orchestrator.c:320 before
the render loop:

  HANDLE h = GetStdHandle(STD_OUTPUT_HANDLE);
  UINT cp = GetConsoleOutputCP();
  fprintf(stderr, "[DIAG] console output CP=%u\n", cp);
and read the same from inside the MSYS2 bash hop:
  python -c "import sys;print(sys.stdout.encoding)"     # or
  locale
If CP is 437/850, the orchestrator is the culprit. If CP is 65001 but the
screen is still wrong, the MSYS2 hop is the culprit.

### A.6 Candidate fixes (do NOT apply yet — pick one after A.5)

Fix A1 (smallest, most likely correct): set the code page at the top of the
  Windows branch of orchestrator.c main(), before any printf:
      SetConsoleOutputCP(65001);
  This is the standard, documented fix for "UTF-8 text renders as mojibake in
  a Windows console". If MSYS2 is the corrupting hop instead, this alone will
  not be enough and A2 is needed too.

Fix A2 (belt and braces): make the renderer encoding-explicit regardless of
  code page. Replace the printf at orchestrator.c:333 with a WriteConsoleW
  path: MultiByteToWideChar(CP_UTF8, ...) then WriteConsoleW. This is
  immune to whatever the code page happens to be and to any MSYS2
  translation. Cost: a per-frame conversion loop, which is fine at 17ms.

Fix A3 (house-consistent, kills the whole class): finish the March 31 ASCII
  conversion that was only half-done. Strip the ║ from the 14 literals in
  agy-text-editor_manager.c and convert editor.chtpm / file_menu.chtpm to
  +, =, | like os.chtpm already is. This sidesteps encoding entirely, but it
  throws away the nicer glyphs and it is a content change to a project's
  layouts, so it is a product decision, not a bugfix. Note the agy manager
  writes the box markup at runtime (agy-text-editor_manager.c:379 et al), so
  this is a code change, not just a file edit.

A1 and A2 are complementary. A1 is the root fix; A2 is the guarantee.

    FRAME_REPORT_20260926-1540_agy-interact-inject.txt section 7. ***

  1. BUILD TARGET MISSING. agy-text-editor was absent from the hardcoded
     project-manager list in compile_all.ps1 -- and so were all four shared
     Ops it invokes (text_edit_key, text_editor_view, file_copy,
     dir_browse). It could not have worked with only the manager built,
     because run_op()'s binaries would not exist either.
  2. THE MANAGER NEVER COMPILED ON WINDOWS. Being unbuilt, it was POSIX-only
     in four places: <sys/wait.h>, setpgid(), and a fork/execv/waitpid
     run_op(). Replaced with a CreateProcess path mirroring orchestrator.c:33.
     Also had to #undef windows.h's MAX_PATH. run_op was kept LOCAL on
     purpose: pieces/system/win_spawn.h's win_spawn() drops every argument
     (it builds a cmd_line then passes NULL to _spawnl), and
     chtpm_parser.c calls that live -- so fixing the shared header is a
     separate, riskier change and is deliberately not bundled here.
  3. dir_browse.c used strcasestr(), a GNU extension MinGW does not provide.
     Added a small ASCII case-insensitive fallback.
  4. THE REAL SECOND-LAYER BUG, and the one that actually made the editor
     look dead: text_edit_key.c:96,:120 and file_copy.c:55 used the standard
     write-.tmp-then-rename idiom. POSIX rename() atomically replaces the
     destination; MSVCRT's rename() FAILS if the destination exists, leaving
     the .tmp stranded beside the untouched original. Observed live:
     document.txt.tmp was written at 34 bytes (the edit WAS computed) while
     document.txt sat unchanged at 33 bytes. Every keystroke was computed
     correctly and then silently thrown away. Fixed with a replace_file()
     helper using MoveFileExA(MOVEFILE_REPLACE_EXISTING) on Windows.
  5. Incidental, pre-existing: joystick_input called gcc directly instead of
     via Compile-Piece, so it never got its +x\ dir and never linked. Routed
     through Compile-Piece.

### B.8 CONFIRMED LIVE: the exported gate field cannot be trusted
New finding, and it substantiates B.5 with evidence.

K9 Rule 10 says to read the actual interact-gate field at the moment you send
the test key. The obvious candidate, pieces/display/active_gui_index.txt, is
INSUFFICIENT. It read "1" in nav mode AND "1" in active interact mode - it
did not change when the gate engaged.

Cause, chtpm_parser.c:2242-2243:
    if (active_index != -1) active_gui_idx = elements[active_index].interactive_idx;
    else                   active_gui_idx = elements[focus_index].interactive_idx;
When focus and active are the same element, both branches write the same
value, so the file cannot distinguish nav-focus from active-mode.

The only reliable gate signal found is the FRAME TEXT: the "[^]" marker
replacing "[>]", and the "Active [^]:  (ESC to exit)" line.

This matters because agy-text-editor_manager.c cannot read the frame, and
the exported gate file cannot tell it either. So the manager really does have
no way to know whether interact mode is engaged - which is the root of both
B.2 and B.3, and it is the protocol gap B.5 describes. Fixing B.2/B.3
properly requires the fix in B.5, not a local branch reorder.

### B.2 BUG (confirmed by source): BACKSPACE NEVER REACHES THE DOCUMENT

agy-text-editor_manager.c:580
    if (key == 127 || key == 8) {
        if (strcmp(layout, "editor.chtpm") == 0) {
            read_editor_line();
            ... truncates input_line_buffer by one char ...
            ... appends "e<buffer>" to pieces/apps/player_app/cli_buffers.txt ...
            processed = 1;
        }
        ...
    }

This branch is entered BEFORE the editor's interact branch at line 651, and
it never calls handle_interact_key(). So pressing Backspace in the agy editor
does not delete a character from the document. It mutates a buffer and
appends a line to cli_buffers.txt that nothing in the editing path reads back.

Windows relevance: on Windows, Backspace arrives as AsciiChar 8, and Delete
arrives as AsciiChar 127. Both are swallowed here. On Linux the same two
codes are produced by the arrow-escape parser, so this is cross-platform, but
it is the single most visible "my key does nothing" in interact mode.

### B.3 BUG (confirmed by source): '2' AND '6' ARE STOLEN BY COMMANDS

agy-text-editor_manager.c:651
    } else if (strcmp(layout, "editor.chtpm") == 0) {
        if (key == '6') { handle_command("SET_NEW_FILE");   processed = 1; }
        else if (key == '2') { handle_command("SET_CLEAR_FILE"); processed = 1; }
        else { handle_interact_key(key); return 1; }
      }

handle_command("SET_NEW_FILE") at line 552 and SET_CLEAR_FILE at line 560
rewrite or truncate the document file. So in agy interact mode, typing the
character 2 wipes the file you are editing and typing 6 replaces it. Any text
containing a 2 or a 6 is mangled.

The buttons that use these codes are declared in editor.chtpm:11-12
(onClick="KEY:6" and onClick="KEY:2"), and the intent was clearly
button-triggered, not free-typed. But agy's process_key has no way to tell
"the user pressed 2 on a button" from "the user typed 2 in the document" —
see B.4. Fix direction: only honour '2'/'6' when the parser is NOT in
interact mode, or move the mapping to a non-typing key (Ctrl+N / Ctrl+K).

### B.4 BUG (Windows-specific, confirmed): KEYS WITH NO ASCII BYTE ARE DROPPED

pieces/keyboard/src/keyboard_input_win.c:30-31 (enableRawMode)
    DWORD mode = ENABLE_EXTENDED_FLAGS | ENABLE_WINDOW_INPUT
               | ENABLE_MOUSE_INPUT | ENABLE_PROCESSED_INPUT;
    SetConsoleMode(hIn, mode);
  - ENABLE_VIRTUAL_TERMINAL_INPUT is NOT set. Nothing downstream parses VT
    sequences, so pasted or VT-native input does not arrive.
  - ENABLE_PROCESSED_INPUT IS set, and line 35 intercepts key==3 and fires
    GenerateConsoleCtrlEvent. Ctrl+C never becomes a key event.
  - ENABLE_QUICK_EDIT_MODE is not explicitly cleared, so console text
    selection can steal keystrokes when the user drags in the window. This is
    a classic Windows-only "some keys just don't register".

pieces/keyboard/src/keyboard_input_win.c:78-92 (the read loop)
    if (ir[i].EventType == KEY_EVENT && ir[i].Event.KeyEvent.bKeyDown) {
        char c = ir[i].Event.KeyEvent.uChar.AsciiChar;      // line 81
        if (vk == VK_LEFT)       key = 1000;
        else if (vk == VK_RIGHT) key = 1001;
        else if (vk == VK_UP)    key = 1002;
        else if (vk == VK_DOWN)  key = 1003;
        else if (vk == VK_ESCAPE) key = 27;
        else if (c != 0) key = (unsigned char)c;              // line 88
        if (key != 0) writeCommand(key);                      // line 90
    }

Four separate drop mechanisms, all Windows-only:

  1. AsciiChar is a single ANSI byte. On any non-US keyboard layout, and for
     AltGr combinations, and for any Unicode character, AsciiChar is 0.
     Line 88's `else if (c != 0)` then discards the key completely. Nothing
     is logged, so the drop is invisible. The fix is to read
     ir[i].Event.KeyEvent.uChar.UnicodeChar instead, and to fall back to
     wVirtualKeyCode when that is also 0.
  2. Only 6 virtual keys are mapped (4 arrows + Escape). F1-F12, Insert,
     Delete, Home, End, PageUp, PageDown, the numpad operators, and every
     modifier-only key all produce AsciiChar 0 and are dropped. They need
     their own key codes in the same 1000-series as the arrows.
  3. Only bKeyDown is handled (line 78). Auto-repeat arrives as repeated
     key-down records with dwRepeatCount > 1; nothing filters on
     dwRepeatCount, so holding a key floods the history file with duplicates.
     You can see this in the live log: pieces/keyboard/history.txt tail shows
     `1002` four times in one second, `1003` five times in one second.
  4. The `if (key != 0)` guard at line 90 means key 0 can never be emitted.
     Combined with chtpm_parser.c:3072 `if (key > 0)`, code 0 is dead in two
     places.

### B.5 BUG (design, confirmed): agy CANNOT TELL IF INTERACT MODE IS ENGAGED

First, the parser knows. chtpm_parser.c:2726 `if (active_index == -1)` is the
nav/active split, and 2846/2999 are the only places that consult it. But the
only thing that crosses the file boundary to the app is the bare key code:

  chtpm_parser.c:1310  fprintf(fp, "%d\n", code);   // no mode flag

agy-text-editor_manager.c:651 then calls handle_interact_key for ANY key on
editor.chtpm, whether or not interact mode is engaged. So agy edits the
document even while you are just navigating the menu with arrows. That is the
mirror image of B.2 and they have the same root cause: there is no "am I in
interact mode" bit in the protocol.

Fix direction: have the parser write a marker alongside the key, e.g. a
separate pieces/apps/player_app/interact_active.txt that agy polls, or prefix
injected keys. Then agy can scope B.1 and B.2 to real interact mode only.
This is a protocol change and needs the other app managers (fuzzpet,
playrm, user) checked before it lands.

### B.6 Lower-confidence items, listed for completeness

  - chtpm_parser.c:3073-3077, the "Windows CRLF Debounce": if key==10
    follows 13, or 13 follows 10, the key is skipped. On Windows the
    keyboard muscle only ever emits 13 for Enter, so this should be inert
    here — but if any other writer appends a 10, the next Enter is eaten and
    interact mode will look like it "sometimes won't take the Enter".
    Worth watching; not proven.
  - The nav-mode global quit at chtpm_parser.c:2850
    `else if (key == 'q' || key == 'Q') exit(0);` runs in nav mode, i.e.
    before interact mode is entered. Pressing q while navigating kills the
    parser. In active mode q is forwarded normally, so this only bites
    outside interact mode.
  - pieces/apps/gl_os/plugins/gl_desktop.c:3260 and 3293 apply tolower()
    before forwarding. Not on the CLI path, but it means any key arriving
    through the GL desktop is already case-folded, which is a second, hidden
    way "the key I pressed is not the key that arrived".
  - Both history consumers track position by byte offset
    (chtpm_parser.c:3062 last_history_position, agy-text-editor_manager.c:975
    last_pos) and neither handles the file being rotated or truncated upward
    except by resetting to 0 (agy-text-editor_manager.c:1004-1006). A
    truncation-and-regrow that ends up the same size silently loses keys.
    I have not observed this happening; it is a latent risk only.

================================================================================

Testing Bot that "plays" the OS by injecting keys into history.txt.

  pieces/apps/bot_tester/   DOES NOT EXIST
  nav_bot / state.txt        DOES NOT EXIST anywhere in the repo
  interact_relay.txt         exists in 2 livedesk pals, 0 bytes, and NO code
                             in pieces/ or projects/ reads it (grep for
                             "relay" returns only unrelated comments in
                             playrm_module.c:336 and chtpm_parser.c:445,
                             :1742, :1768, :1776)

So CH9 is a design chapter, not a working harness. The MECHANISM it describes
does exist and works today with no bot binary: the parser tails
pieces/keyboard/history.txt (chtpm_parser.c:3060) and acts on lines containing
"KEY_PRESSED: ". Appending a correctly formatted line to that file IS a relay
injector. That is the whole of it.

*** THE CRITICAL LIMIT — A RELAY TEST CANNOT DETECT BUG B ***
The input chain has two halves, and a relay bot only ever exercises one:

  HALF 1  capture        WINDOWS-ONLY, NEEDS A REAL KEYBOARD
    physical key -> ReadConsoleInput -> AsciiChar / wVirtualKeyCode
    -> keyboard_input_win.c -> append "KEY_PRESSED: N" to history.txt

  HALF 2  relay/consume  PLATFORM-IDENTICAL, FULLY SYNTHESISABLE
    history.txt -> chtpm_parser.c process_key -> inject_raw_key
    -> app history.txt -> agy process_key -> handle_interact_key

history.txt is the BOUNDARY BETWEEN THE TWO HALVES. A relay injector writes
there, so it enters at the top of half 2 and never executes a single
instruction of half 1. It cannot observe AsciiChar, the six-virtual-key map at
keyboard_input_win.c:83-87, the console mode flags at :30, or the
dwRepeatCount gap at :78. Every one of the four candidate mechanisms in B.4
lives in half 1 and is therefore invisible to it.

CONSEQUENCE, and this is the dangerous one: a relay test will report PASS on
a machine whose physical keyboard is completely broken in interact mode. It
is a false green, and it is worse than no test, because it would let us close
Bug B while the reported symptom is still there. Do not let a relay result be
cited as evidence that Bug B is fixed.

Therefore:
  B.4 (the muscle)       HUMAN AT THE KEYBOARD. No bot can substitute.
  B.2 backspace          RELAY-TESTABLE. Should fail on BOTH platforms.
  B.3 '2'/'6' hijack     RELAY-TESTABLE. Should fail on BOTH platforms.
  B.5 no interact bit    RELAY-TESTABLE, but it is a protocol change so it
                         needs the other app managers checked too.
  Bug A (frame unicode)  NOT a key-path bug at all. It is tested by reading
                         current_frame.txt bytes and the console output code
                         page, not by injecting keys.

Running the relay test for B.2/B.3 on this Windows box is still worth doing,
precisely because it is the control: if backspace fails identically here and
on Linux, that is a clean cross-platform bug and is NOT the Windows
regression, which keeps the two findings separate.

IF A RELAY INJECTOR IS WRITTEN, these four details will bite:
  1. Format must match keyboard_input_win.c:56 exactly --
        [<YYYY-MM-DD HH:MM:SS>] KEY_PRESSED: <int>
     The parser matches on the literal substring "KEY_PRESSED: "
     (chtpm_parser.c:3066) and atoi's the text after the first colon.
  2. CH9 Pitfall 1 applies verbatim: the pipeline is polled, not pushed, so
     sleep 100-200ms between injections or keys are coalesced.
  3. The CRLF debounce at chtpm_parser.c:3073-3077 will eat a 13 immediately
     following a 10, or a 10 immediately following a 13. Do not script a
     10/13 pair and conclude the second one is lost.
  4. chtpm_parser.c:3072 is `if (key > 0)`, so key 0 can never be delivered
     by any injector, scripted or physical.
