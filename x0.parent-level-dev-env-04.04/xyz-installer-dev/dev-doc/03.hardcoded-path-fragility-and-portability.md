# 🗺️ Hardcoded Path Fragility — What Broke, Why, and Why It'll Bite Us Again at Ship Time

**Date:** 2026-08-10
**Origin:** a real, live-diagnosed regression chain (book-stack's "Read" button, event-ez editor button) found and fixed during the livedesk-taskbar pals-registry migration. Written up here because the exact same failure class will resurface — likely worse — once this house ships as an installable product with per-user, per-machine install paths.

---

## 1. The trigger (context, not the point)

The livedesk taskbar moved from spawning entities directly out of their dev-tree location (`*.monads/*.widget/entities/<name>`, always the same fixed nesting depth) to spawning them from a per-user **pals registry** (`xyzfs/users/<uuid>/home/livedesk/pals/<name>`, a completely different depth). This is a real, deliberate, good architectural change — but it exposed something worse than one bug: an entire **class** of latent fragility that had been silently correct only by coincidence (the old location happened to always be at a fixed depth), never because the code was actually portable.

## 2. The bug class, precisely

Multiple scripts derived "where am I, and where's everything else I need" by **climbing a fixed number of `..` hops** from wherever they happened to be told they currently were. Two sub-patterns, both broke, for related but distinct reasons:

### 2a. Climbing from the ENTITY's location (breaks the instant the entity moves)

```bash
# open_event_ez.sh, ORIGINAL (broken for pals):
MUCHI_RANCHER="$(cd "$PKG_DIR/../.." && pwd)"
HOUSE_ROOT="$(cd "$MUCHI_RANCHER/../.." && pwd)"
```
`$PKG_DIR` is the entity's own current package directory — passed in fresh, correctly, every time. The bug is assuming that wherever it currently lives is a *fixed number of levels* under house_root. That assumption was true 100% of the time under the old architecture (only one possible location existed) and false as soon as a second valid location (pals) existed at a different depth.

**This pattern was found in:** `open_event_ez.sh`, `open_rp_menu.sh` (worse — see §3), several `meta.pdl`/`objects.pdl` METHOD/OBJECT lines across `m8_redhorned`, `m6_golddeity`, `book-stack`.

### 2b. Climbing from the SCRIPT's own location (correct, and a useful contrast)

```bash
# play_event.sh, dispatch.sh — CORRECT pattern, never broke:
SCRIPT_DIR="$(cd "$(dirname "$0")" && pwd)"
HOUSE_ROOT="$(cd "$SCRIPT_DIR/../.." && pwd)"   # (however many hops)
```
This works regardless of which entity invokes it, or from where, because **the script itself never moves** — it lives at a fixed, permanent location in the dev tree (shared code, not per-instance data). Climbing from *your own* fixed location is safe. Climbing from *someone else's variable* location is not. This is the load-bearing distinction of this whole document.

### 2c. A third pattern: no way to pass context down an exec chain at all

`book-stack`'s "Read" button chain is: `meta.pdl METHOD` → `sh -c` → `prisc+x` (exec, one literal arg only, confirmed limit — see `!.HOUSE_STDS.md` §H.5.1) → `dispatch.sh` (exec'd by the PAL script, zero extra args) → `khtpm_show_choices.+x` → one of three `branches/*/run.sh`.

Every hop after `prisc+x` had **no positional argument available** to receive the entity's real live location — `prisc+x`'s own `exec` opcode can't forward it. `dispatch.sh` (correctly reading its OWN fixed location) computed `HOUSE_ROOT` fine, but then **hardcoded a guess** at the entity's package dir, because it had no other way to know it:
```bash
PACKAGE_DIR="$HOUSE/*.monads/*.book-stack/entities/book-stack"   # a guess, not derived
```
**The fix:** environment variables survive `exec` even when positional arguments can't be forwarded. The top of the chain (`meta.pdl`'s `Read` method) now does:
```bash
sh -c 'H="$1" && export PACKAGE_DIR="$0" && exec ".../prisc+x" ".../event.pal"'
```
and every downstream script reads `"${PACKAGE_DIR:-<old hardcoded guess>}"` — real value if the caller set it, safe fallback if launched some other way. This is the general answer to "how do I get real context through a fork/exec chain that only supports one literal argument": **environment, not argv, when argv is constrained.**

## 3. The sneaky variant: a script that silently reproduces its own bug forever

`open_rp_menu.sh` doesn't just read a broken path once — it **regenerates `objects.pdl` from scratch every time "Menu" is clicked**, using its own (broken) path derivation to build the `action=` lines it writes. Fixing the *generated* `objects.pdl` by hand would have been immediately overwritten and re-broken the next time a human or agent clicked Menu. **The generator itself had to be fixed, not just its output.** This is worth remembering as a general debugging principle: when a config file looks wrong, check whether something is *regenerating* it before assuming a one-time hand-fix will stick.

## 4. What was actually fixed (2026-08-10)

- `&.widgits/tile-picker/ops/tp_desktop_window.c` — METHOD/OBJECT dispatch now passes `house_root` as an explicit second argument (it already had it in scope; the fix cost nothing, and every downstream script can now use it instead of guessing).
- `*.monads/*.muchi-pet/ops/open_event_ez.sh` — reads the new explicit arg; old climb kept only as a fallback for anything not yet updated.
- `*.monads/*.muchi-pet/ops/open_rp_menu.sh` — the self-perpetuating generator, fixed to derive its root from its own script location (§2b pattern), not the entity's variable location.
- `book-stack`'s `meta.pdl` (both dev-tree source and the live pals copy) — "Read" now exports `PACKAGE_DIR` before exec'ing `prisc+x` (§2c pattern).
- `dispatch.sh`, `branches/bible_text/run.sh`, `branches/tao/run.sh` — read `$PACKAGE_DIR` from environment, falling back to the old guess only if unset.
- `m8_redhorned`'s pals `meta.pdl` "Ledger" line — rewritten to reference its own data via `$0` (its own live package dir), the simplest possible fix since that file already lives *inside* the entity's own package.

**Deliberately NOT fixed (by direct instruction, 2026-08-10):** `bible_text/run.sh`'s hunt for Bible source text, and `tao/run.sh`'s `TAO_FILE`, both still hardcode a specific developer's own machine (OneDrive path under a literal Windows username; a specific external disk UUID + Linux username on this dev machine). These are external, large binary/text assets that live *outside* the house's own tree entirely — a different, bigger problem than anything else in this document (see §6). Left as dev-convenience placeholders, not production paths — noted here so they aren't mistaken for "fixed" by a future reader.

## 5. Why this will matter *more*, not less, once this ships

Everything above was triggered by **one new valid install location existing inside a single developer's own house** (pals vs. dev-tree). `xyz-installer-dev`'s whole point is that this software will run on **arbitrary end-user machines**, with:
- Arbitrary install directories (not this exact `/home/no/Desktop/🤖️🪤️🏠️/...` tree — a real end user will *never* have this path).
- Arbitrary usernames (every hardcoded `jbro8`/`jbez`/`no` reference in this house is a landmine for exactly one person's machine).
- Arbitrary drive letters/mount points on Windows, arbitrary disk UUIDs on Linux.
- Potentially: sandboxed/portable install modes where "climb N levels from wherever I am" may not even correspond to a real, meaningful directory relationship at all (e.g., an AppImage/portable-exe extraction location).

**Every script in this house that computes a path by climbing a fixed number of `..` from *anything other than its own permanent location* is a future installer bug, not a hypothetical one.** This session found and fixed six real instances triggered by ONE new location existing. A real multi-machine install introduces far more variation than that.

## 6. The bigger, separate problem this surfaced (not fixed here, needs its own design)

`bible_text/run.sh` and `tao/run.sh` reveal that some content is genuinely **external to the house's own version-controlled tree** — large text/binary assets (a full Bible translation, TTS engine dependencies, the Tao Te Ching source) that were never meant to live inside the git-trackable project, so they got referenced via ad-hoc, hardcoded, single-developer-machine paths as a stopgap. This is architecturally different from the path-climbing bugs above (those were about a *known* file inside the house being found via *fragile arithmetic*; this is about a file that **isn't even part of the shippable tree at all**).

**This needs a real, dedicated design before shipping**, likely something like:
- A documented, versioned **asset manifest** (what external content a given piece/widget depends on, where it's expected to be installed).
- A real **asset resolution order** (env var override → an installer-populated config file → a documented default install location), replacing the current ad-hoc "try four different absolute guesses" pattern.
- Decide whether large assets ship *inside* the installer package, get *downloaded on first run*, or are *user-supplied* (e.g., "point us at your own Bible text file") — a real product decision, not a path-fixing exercise.

This document intentionally stops short of designing that system — it's flagged here so it isn't lost, and so whoever picks up `xyz-installer-dev`'s asset-provisioning story knows exactly which real files in this house already hit the problem, concretely, not hypothetically.

## 7. Practical checklist for future path-derivation code (what "good" looks like)

Before writing `cd "$X/../.." ` anywhere in this house again, ask:

1. **Is `$X` a script's own fixed location, or something else's variable location?** Climbing from your own `dirname "$0"` is safe (§2b). Climbing from an argument someone else passed you is not (§2a) unless you've verified that argument's depth is truly invariant — and if there's now more than one valid install shape (dev-tree vs. pals, or dev machine vs. installed product), it probably isn't invariant anymore.
2. **If you need context you don't have positional-argument room for** (an `exec` chain, a PAL script's one-arg limit, a shell function boundary), use an **exported environment variable**, not a guess (§2c).
3. **If a script regenerates a config file, audit the generator, not just the output** — a hand-fix to generated content doesn't survive the next regeneration (§3).
4. **If a path points outside the house's own tree entirely** (external assets, user data, machine-specific tool locations), that's not a climbing-arithmetic bug — it needs a real resolution-order design, not a quick relative-path fix (§6).
