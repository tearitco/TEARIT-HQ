# 🌳🪵️ dev-doc — Versioning with gitlet

> Status: **STRATEGY DRAFT — for review, not yet wired.** Everything below is
> grounded in gitlet's real source (read, not assumed). The goal: manage
> updates and rollouts (alpha/beta/stable) for `~/xyzos/` installs.

## 🧰 What gitlet is (verified from source)

A tiny, pure-C git clone: 822 lines, no dependencies, content-hash blobs with
**8-char alphanumeric hashes** (same style as the house's list-dir tool).

| Command | Behavior (verified) |
|---|---|
| `init` / `init --bare` | Create a repo; `--bare` = remote-ready (no working tree) |
| `add <file>` | **Single file only** — hashes contents → blob in `.gitlet/objects/`, appends `file hash` to index |
| `commit <msg>` | Snapshots the **whole index** into a "tree" object; commit = `tree + parent + date + msg` |
| `log` / `status` | History / staged + untracked (cwd only, non-recursive) |
| `branch [name]` | Create (ref to current commit) or list |
| `checkout <branch>` | Restores tree blobs into files; **parent dirs must already exist** |
| `rm <file>` | Remove + unstage |
| `push <path>` / `pull <path>` | Copy objects + refs to/from a **local-path remote** (bare repo); pull overwrites local |
| `merge <branch>` | **Fast-forward only, must be on master** — brings a branch's tip onto master |
| `fork <path>` | Bare copy of the repo + registers it as a remote |

**Honest limits:** no dir recursion on `add`, no tags, no author/identity, no
conflict resolution (pull overwrites), merge only on master. It is a
**descriptor/ledger VCS**, not a whole-tree transport.

## 🎯 The model: version DESCRIPTORS, transport PAYLOADS

Trying to blobsnapshot an entire app tree (`find … | xargs gitlet add`) fights
gitlet's file-level design and checkout-dir pitfalls. Instead, split the job:

- 🧭 **gitlet versions the *descriptors*** — the files that DECIDE upgrades:
  `catalog.pdl`, `installed_apps.pdl`, `paths.pdl`, and per-app `RELEASE.pdl`.
- 📦 **The installer transports the *payloads*** — the existing one-way copy +
  in-place compile already does this and is harness-proven.

A descriptor says: *app X at version V, channel C, source commit H, here's the
manifest.* The installer reads it and syncs the app tree from the dev tree.
gitlet stays the ledger of truth about *what release exists on which channel*;
the filesystem copy stays the mechanism.

## 🚦 Channels as branches

One **bare release repo** (a local dir, e.g. `~/xyzos/.release/` or
`xyz-installer-dev/release/`) holds the channels as branch refs:

```
master  = STABLE  (what everyone should run)
beta    = what's queued for stable after the gates pass
alpha   = bleeding edge, harness-proven only
```

```
gitlet init --bare            # the release repo (one copy of objects+refs)
gitlet branch stable          # channel refs
gitlet branch beta
gitlet branch alpha
```

## 🔼 Promotion ladder

Push to `alpha` → test → promote to `beta` → test → promote to `stable`.
Since `merge` is master-only fast-forward, promotion = **moving a ref** to a
newer commit, then syncing the tree via checkout/push-pull:

```
# from a channel workspace (or the release repo directly):
gitlet checkout alpha        # or: gitlet pull <release-repo> && gitlet checkout alpha
… commit the new descriptor …
gitlet push <release-repo>   # publish alpha

# promote alpha → beta (re-point the beta ref at alpha's tip, then publish):
gitlet checkout beta && gitlet pull <release-repo>/alpha …
```

> ⚠️ gitlet has no `branch -f`, so re-pointing a channel = checkout the target
> channel, pull the source channel's tree, commit, push. A tiny `promote.sh`
> wrapper will encapsulate this (same class of tool as the installer).

## 📝 What gets committed (v1)

```
app-store/catalog.pdl            ← the dev catalog (what's available)
app-store/installed_apps.pdl     ← THIS install's ledger (what's installed)
paths.pdl                        ← the pointer (logical name → real path)
apps/<name>/RELEASE.pdl          ← per-app: version, channel, source-commit,
                                   date, manifest (added by the installer)
```

Each commit message = a release note: `bump avatar 0.2.0 → beta`.

## 🧭 Example session (concrete)

```bash
# on the dev machine, in a release-workspace:
gitlet init
gitlet add app-store/catalog.pdl paths.pdl
gitlet commit "v1: catalog login+avatar"
gitlet branch stable && gitlet branch beta && gitlet branch alpha

# cut an alpha:
gitlet checkout alpha
# … edit catalog.pdl / add apps/<name>/RELEASE.pdl …
gitlet add app-store/catalog.pdl apps/avatar/RELEASE.pdl
gitlet commit "avatar 0.2.0-alpha"
gitlet push ../release-repo        # publish alpha

# promote alpha → stable (after gates in 02.rollout…):
gitlet checkout stable
gitlet pull ../release-repo        # pull the alpha tree (overwrites = fine,
                                   # descriptors are small and controlled)
gitlet commit "stable == alpha tip"
gitlet push ../release-repo

# on an install, update to stable:
gitlet pull ../release-repo        # get new descriptors
# installer reads installed_apps.pdl → syncs changed apps via one-way copy
```

## 🚫 What NOT to do (yet)

- ❌ Blob-version whole app trees — checkout needs pre-made dirs; `add` is
  file-level; pull overwrites. Wrong tool for payload transport.
- ❌ Try conflict-merge workflows — gitlet is fast-forward only by design.
- ❌ Rely on it for multi-machine sync — remotes are local paths; that's a
  feature (offline), not a bug.

3. **RELEASE.pdl shape** — propose: `version=x.y.z`, `channel=alpha|beta|stable`,

4. **promote.sh** — should it live in `xyz-installer-dev/` next to the installer?
5. Is **descriptor-versioning (v1)** the right first cut, or do you want
   whole-tree versioning despite gitlet's limits (would need a gitlet feature pass)?

## ✅ Recommendation

Ship **descriptor-versioning v1**: gitlet commits the four descriptor files,
channels are branch refs, the installer stays the payload transport. It uses
gitlet where it's genuinely strong (deterministic local release history,
channels, no network) and doesn't fight its limits. Whole-tree versioning can
come later as a gitlet feature pass (dir recursion + tags + conflict handling).
