USER'S COMPLAINT
-----------------
"clicking on the indexes nor pressing enter on them, activates the tb cell
buttons and their functions any more"

In other words: the taskbar's X11 GUI no longer responds to clicks on
header cells or Enter key presses. The cells visually display but do nothing
when interacted with.

SUSPECTED ROOT CAUSE
---------------------
Commit 1 is the primary suspect. Here's why:

The old code had TWO dispatch paths:
  Path A (inline): Inside the `while(XPending(dpy))` loop, after capturing
    each event, it was immediately dispatched (hit-tested + send_code()).
  Path B (deferred): `poll_captured_input()` reads strip_input_history.txt
    and dispatches from there.

The new code (after Commit 1) has ONLY Path B:
  The XPending loop now ONLY captures events into strip_input_history.txt
  (write-only). Then poll_captured_input() reads them back and dispatches.

The problem may be in how poll_captured_input() dispatches mouse clicks.
The flow is:

  1. X11 ButtonPress arrives
  2. mirror_mouse_history() writes to strip_input_history.txt:
     `MOUSE_EVENT: <button> <x> <y> 1 <window_name>`
  3. poll_captured_input() reads strip_input_history.txt
  4. Calls apply_captured_mouse()
  5. apply_captured_mouse() does hit_test() against g_header_hits[]
  6. If hit, calls dispatch_onclick(header_doc, elidx)
  7. dispatch_onclick() reads the onClick attribute from the layout doc
  8. For header cells: onClick is like "ACTIVATE:2" → lay_activate() + send_code(KSC_HQ_HEADER_BASE + n)
  9. send_code() appends the decimal code to strip_history.txt
  10. Manager reads strip_history.txt and executes the action

THE KEY QUESTION: Are g_header_hits[] (the hit-test rectangles) being
populated correctly before poll_captured_input() tries to use them?

The hit rects are built during the render walk (draw_header_win()). If the
render walk runs BEFORE the XPending loop captures the mouse event, the
rects should be valid. But if there's a timing issue — or if the rects
are stale/empty on the first tick — hit_test() would return -1 and the
click would be silently dropped.

ADDITIONAL THINGS TO CHECK
----------------------------
1. Does strip_input_history.txt actually get written when you click?
   Check: `cat #.desktop/strip_input_history.txt | tail -5` during a click.

2. Does poll_captured_input() actually read it back?
   The function uses a cursor (g_capture_cursor) that skips to EOF on first
   call (never replays backlog). If the file existed before the parser
   launched, initial cursor = file size, and no new events get dispatched.

3. Does dispatch_onclick() actually call send_code()?
   The onClick attribute must be non-empty and match one of the known
   prefixes (ACTIVATE:, STRIP:, TAB:, SHORTCUT:, HQITEM:, BACK).
   Check the .chtpm layout files for what onClick values the header cells
   actually have.

4. Does send_code() successfully write to strip_history.txt?
   Check: `cat #.desktop/strip_history.txt | tail -5` after clicking.

5. Does the manager read and dispatch strip_history.txt?
   Check the manager log: `cat #.desktop/khtpm_strip_parser.log | tail -20`

6. Is flush_cells_pdl() (Commit 2) accidentally interfering?
   It runs inside draw_header_win() — right in the middle of the render
   walk. If it has a side effect on the hit rects or the layout doc state,
   that could break dispatch. The function writes to disk, which shouldn't
   affect in-memory state, but verify.

KEY ARCHITECTURE (for context)
-------------------------------
The taskbar is a two-process system:
  - khtpm_strip_parser.c (X11 process): owns all windows, drawing, hit-testing,
    writes strip_history.txt (action codes for the manager)
  - khtpm_taskbar_manager_main.c (pure logic): reads strip_history.txt,
    manages state, writes strip_state.txt, strip_var_*.txt

File relay:
  - livedesk_agent_relay.txt: agent → parser (digits, Enter, Escape, etc.)
  - strip_history.txt: parser → manager (resolved action codes)
  - strip_state.txt: manager → parser (published state)
  - strip_frame.cells.pdl: parser → ASCII renderer (per-cell frame data)
  - strip_frame_changed.txt: parser → ASCII renderer (size-poll redraw trigger)
  - strip_input_history.txt: parser ↔ parser (internal capture→dispatch file)

VERDICT
-------
Frame unification (cells.pdl pipeline) works correctly — the ASCII renderer
reads cells.pdl and outputs the right frame. But the X11 GUI's cell
activation (click/Enter → action) is broken, most likely by Commit 1's
dispatch path consolidation. The old inline dispatch was removed but the
deferred poll_captured_input() path may not be fully equivalent for all
click scenarios.

SAFE TO PROCEED: the cells.pdl changes (Commit 2) and ASCII renderer
changes (Commit 3) are sound. The fix should focus on Commit 1's dispatch
consolidation — specifically whether apply_captured_mouse() in
poll_captured_input() handles all the same cases the old inline dispatch
did.

FOLLOW-UP (2026-08-19, same day): the real remaining bug, FOUND + FIXED
=====================================================================

Boss's live retest found the click/index issues above were minor/
one-off (a double-click-to-wake-up quirk, not reproduced as a real
bug). But arrow-key navigation INSIDE an open submenu was reported as
genuinely broken: "arrow nav doesn't work in it, it looks like it
immediately jumps back up to 1" — while digit-index input and clicking
both worked fine.

ROOT CAUSE (confirmed by direct code read, not guessed)
---------------------------------------------------------
A file-name collision between Commit 2 (cells.pdl writer) and
pre-existing code, both in khtpm_strip_parser.c:

  - frame_changed_dirty() (pre-existing, UNCHANGED) polls
    #.desktop/strip_frame_changed.txt to decide whether to reload/
    reparse the layout docs from disk (was_dirty, main loop ~L2170).
  - flush_cells_pdl() (Commit 2, NEW) was ALSO touching
    #.desktop/strip_frame_changed.txt as ITS OWN "cells changed"
    signal — and flush_cells_pdl() runs unconditionally every tick.

Effect: was_dirty was true on EVERY tick, so the layout docs got
reloaded from disk every tick. Digit-index and click navigation
survive a reload because they round-trip through the manager's
published state (g_st/strip_state.txt), which the reload re-applies
correctly. Arrow-key submenu navigation (lay_focus_delta()) is
LOCAL, in-memory state that is never persisted anywhere — so every
single reload wiped it back to whatever the fresh parse produced,
which looked like "instantly snaps back to 1."

FIX APPLIED (not a rollback — a 2-file rename)
-------------------------------------------------
Gave the cells.pdl signal its own dedicated file instead of sharing
the manager-state dirty signal:
  - khtpm_strip_parser.c: flush_cells_pdl() now touches
    #.desktop/strip_cells_changed.txt instead of
    #.desktop/strip_frame_changed.txt (frame_changed_dirty() itself
    untouched — still watches strip_frame_changed.txt for real
    manager-state changes only).
  - khtpm_strip_render_ascii.c: its own pulse-poll loop (main(),
    ~L262) now watches #.desktop/strip_cells_changed.txt to match.
  - Both files' header comments updated to document the split and WHY
    (so nobody re-merges these two signals back together later).

Rebuilt via build_khtpm_strip.sh (clean build, warnings only,
pre-existing/unrelated to this fix) and relaunched via the sanctioned
run_khtpm_strip.sh new (kills old PIDs, confirms new PIDs via pgrep,
never trusts a bare exit code) — now running as PIDs 168031/168035.
