## When to delegate to Harnecient instead of doing it in-session

Good candidates (mechanical, well-specified, low architectural risk):
- Boilerplate C following an EXISTING house pattern closely (a new
  `khtpm_*_render.c` window that's 90% copy-shape of an existing one)
- Persona/prompt-file authoring once the shape is decided
- Repetitive relay-test sequences that don't need judgment calls
  (running the SAME scenario across N models, collecting receipts)
- Straightforward find/grep/summarize passes over known file sets
- Writing scenario/assert scripts once the harness shape (Phase 4,
  `13.AUG.13-HAI-2do.txt`) is established

Keep in Claude (architectural judgment, cross-file consistency,
correctness-critical):
- Anything touching shared state multiple processes read/write (e.g.
  `strip_state.txt`, `livedesk_theme.pdl`) where a wrong write corrupts
  live state
- New wiring decisions (which enum value, which file owns which write)
- Anything the "verify architecture survives" lesson applies to -
  confirming a piece actually satisfies a stated goal, not just
  looks plausible

## Standing offload opportunities (update as these get built)

- **Phase 4 harness scenario scripts** (`13.AUG.13-HAI-2do.txt`,
  `relay-harness/scenarios/*.sh`) — once T4.1's C assert ops exist,
  writing individual scenario drivers against a KNOWN, fixed contract
  is exactly the kind of scoped, well-specified work a Harnecient
  model (or Haiku, for anything needing more judgment than a
  Harnecient model can reliably give) should be doing, not Claude
  hand-writing each one.
- **Repetitive multi-model relay test sweeps** — running the same
  scenario across stable-code/gemma3:1b/gemma3:270m/llama2 and
  collecting receipts is mechanical once the scenario itself is
  designed; a BT/FSM-style test-runner op (see below) should own this
  loop, not Claude manually sequencing relay codes per model.

## BT/FSM/RL ops worth building (usability tools that pay for themselves)

Not built yet — flagged here as real candidates, not a commitment:
- A small deterministic **behavior-tree or FSM test-runner** that
  drives a relay sequence, waits on receipts, and scores pass/fail -
  this is EXACTLY Phase 4's `run_all.sh` + `scenarios/*.sh` shape
  (`13.AUG.13-HAI-2do.txt`), so building it once serves every future
  harness, not just one.
- Once that exists, an RL-flavored "try variations, score, keep the
  best" loop for prompt/persona tuning (T2.1's "persona tweaking per
  model" flagged risk) is a natural next layer, using the same
  scoring plumbing.
