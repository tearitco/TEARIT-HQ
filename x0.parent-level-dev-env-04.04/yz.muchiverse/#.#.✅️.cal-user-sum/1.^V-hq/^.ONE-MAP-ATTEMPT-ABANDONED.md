# 🛑 "One map" perspective 3D — attempted 2026-08-31, ABANDONED same day. Don't retry this without new evidence.

**Direct instruction that closed this out:** "well i dont want the
stacking z levels on desktop either i think we just introduced bugs
... roll back the git ... leave desk like this."

## What was attempted

Per `CURSWORD-DESKTOP-3D-AND-PIECECRAFT-INSCENE-DESKS-DESIGN.md` §13
and `ONE-MAP-PERSPECTIVE-3D-DESIGN.md`: a single shared X11 window
(`khtpm_one_map_render.c`, a real standalone compositor process) that
raymarched every desktop entity's phymoji voxels together into one
perspective scene, "like a transparent version of piececraft," toggled
by cursword's own `0` key. The real goal was full background
transparency — the compositor's own empty space should show the real
desktop (icons, sidebar) through and clickable, exactly like every
individual entity window already does via `XShapeCombineMask`.

## Why it's dead: a real, confirmed compositor limitation

Live-tested, clean-room proof: an override-redirect window with a
real, non-empty `ShapeBounding` mask (only a small corner shaped "in")
sitting directly over a solid color test window still painted fully
**opaque** across its entire rectangle — not just the shaped-in
corner. `XQueryPointer` confirmed click-routing DOES honor the shape
(clicks landed on the window underneath), but the compositor
(Mutter/XWayland here) never clips what it actually **paints** for a
window that's continuously redrawn via raw `XPutImage`, only for
click-through. This is the opposite of what every individual entity
window relies on (their `ShapeBounding` — set once from a static
sprite's alpha, not rebuilt every frame — genuinely does clip both
paint and clicks, confirmed working many times over this house's
history). The difference appears to be the *continuous per-frame
XShapeCombineMask* pattern specifically, not shape masking in general.

**No app-side fix was found.** Real options considered and rejected:
- Real 32-bit ARGB visual + true per-pixel alpha instead of Shape —
  would need a live compositor to actually honor per-pixel alpha
  (untested whether this house's Mutter does; the whole point was to
  avoid depending on that), and even if it worked, empty pixels still
  wouldn't be click-through (alpha-blended ≠ shaped-out).
- Reducing to a smaller windowed (not fullscreen) view — fixed the
  "takes over the whole screen" complaint but not the core
  transparency problem; the visible rectangle was still opaque.

## Also reverted: per-desktop z-level "stacking" in 3D mode

A related, smaller change was tried in the same pass: relaxing the 2D
z-level visibility filter so 3D mode showed every z simultaneously
(with a per-entity vertical screen offset to visually separate a
stack), instead of only the single active z. Direct instruction:
**"well i dont want the stacking z levels on desktop either."** Not
because it was broken (untested end-to-end — see the compaction
summary for why: real registry/nav-claims plumbing made a bare,
manually-launched clone entity an unreliable way to test it headless)
— reverted because the user does not want this feature at all, full
stop. Don't re-propose it.

## What actually happened, and the real lesson

Testing this (real, live `desktop_camera_mode.txt` / `desktop_camera_
state.txt` state left at `4` / non-zero pan from manual `xdotool`-driven
verification) caused two real, separate regressions after the code
itself was rolled back:
1. A stray `desktop_one_map_active.txt = "1"` left every non-cursword
   entity self-unmapping forever (the toggle key that could turn it
   back off had already been removed) — tiles appeared to "flash black
   then vanish." Real fix, now applied: deleted the dead self-
   suppression code entirely, not just the stray file, so a leftover
   flag can never do this again.
2. Leftover `desktop_camera_mode.txt`/`desktop_camera_state.txt`
   runtime values (not source, so `git reset --hard` never touched
   them) made cursword respawn at a bizarre offset ("familiar location"
   report) purely because it was still reading a stale 3D pan from
   disk — not a code bug at all.

**The real lesson for next time:** this house's `#.desktop/*.txt`
runtime state files are NOT reset by a source rollback. Any live
testing session that writes camera/mode/pan state directly (bypassing
the normal key-driven `bump_camera_changed()` path) must clean those
files back up before calling a feature "abandoned" — otherwise the
NEXT session inherits invisible, hard-to-diagnose leftover state that
looks exactly like a fresh code regression.
