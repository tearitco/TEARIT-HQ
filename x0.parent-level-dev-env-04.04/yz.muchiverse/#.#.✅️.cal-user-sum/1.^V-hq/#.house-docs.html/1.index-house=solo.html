How the house actually works

This is the real, working reference for the muchiverse/livedesk house: the taskbar and its window-app family, the legacy game engines it grew out of, and the standards that hold it together. It's deliberately broad and unevenly deep right now — some sections are thorough, others are a skeleton waiting to be filled in. Click a section, read what's there, and add to what's thin.

Overview

Current

the shape of the house, in one pass

The house is organized around a persistent desktop taskbar (khtpm_strip_parser.c + khtpm_taskbar_manager.c) that launches and manages a family of window apps — a database browser, an events editor, a chat interface, entity context menus, and more — plus a much older family of standalone terminal/3D game projects that predate the taskbar entirely and are gradually being brought into the same conventions.

Two real parser lineages exist side by side and are not the same thing: the newer khtpm_* family (raw Xlib/Xft rendering, its own CSS-like styling layer, used by the taskbar and its window apps) and the older chtpm_parser_pal.c family (a PAL-VM-driven text-grid parser, used by the legacy game projects). If you're building on a taskbar sub-app you're in the first family; if you're touching one of the 16 legacy game projects, you're in the second. Assuming a feature from one exists in the other is a real, recurring source of wasted debugging time.

Orientation rule

Before inventing a new UI/state pattern, check whether the local codebase already has one, then check the real TPMOS reference tree (1.TPMOS_c_+rmmp.0103.0001/) before designing something new. TPMOS isn't inspiration — it's the literal architecture standard this house is built against.

House Standards

Current

the rules that keep the house from drifting apart

Real processes, not shared includes

Independent or long-running logic gets a real fork() + execv() child process (matching every real launch_module() in this codebase), never an #include of another app's source. A discrete, one-shot action gets its own standalone op binary, invoked the same way. The one legitimate exception is pure, stateless, per-frame hot-path logic that genuinely needs direct in-process access to shared data structures — the rendering core (khtpm_render_core.c, khtpm_css_parser.c, khtpm_draw_core.c) is the real example, not a precedent to stretch further.

New dispatch or launch code should reach for real fork()/execv()/waitpid() rather than system(). Existing system() calls in code that's slated for consolidation don't need to be rewritten just to be consistent — that cleanup happens once the surrounding code converges, not as a drive-by change.

Archive, don't delete

Code made obsolete by a merge or migration gets moved into a clearly-named, dated archive directory with a real MANIFEST.txt (original path + why it's dead), then zipped. Whether the loose unzipped copy stays or gets deleted afterward is a real, explicit instruction to confirm — some passes this session kept it, later ones deleted it outright on direct request. Don't guess; ask if it's not stated.

Don't hardcode a path that can move again

When a real path needs to resolve to "wherever this app currently lives," scan known root directories for it by name at runtime rather than baking in a fixed relative path. Two real, working examples already in the codebase: 

static int find_app_dir(const char *house_root, const char *app_name,
                         char *out, size_t outsz) {
    static const char *roots[] = { "*.monads", "&.widgits", "&.hq-apps", "@.apps", NULL };
    for (int i = 0; roots[i]; i++) {
        char parent[PATH_BUF];
        snprintf(parent, sizeof(parent), "%s/%s", house_root, roots[i]);
        DIR *d = opendir(parent);
        if (!d) continue;
        struct dirent *ent;
        while ((ent = readdir(d)) != NULL) {
            if (strstr(ent->d_name, app_name)) {
                snprintf(out, outsz, "%s/%s", parent, ent->d_name);
                closedir(d);
                return 1;
            }
        }
        closedir(d);
    }
    out[0] = '\0';
    return 0;
}

A directory that moves once will move again — this pattern means the next move doesn't need a source edit at every call site that referenced it.

Verify before you trust a fix

A change that compiles and passes a synthetic, isolated test is not the same claim as "this works." Real regressions this session were repeatedly found only once tested against real, full-scale data through the real dispatch path — not a shell one-liner, not a reduced test file. If you can't watch it happen (a rendered frame, a live process, an actual keypress reaching the code), say so explicitly rather than reporting success.

Taskbar & Window Apps

Current

*.monads/*.livedesk-taskbar/

The taskbar itself is two real, separate OS processes with no shared memory — khtpm_strip_parser.c (Xlib, layout, hit-testing) and khtpm_taskbar_manager.c (pure logic, no Xlib) — talking exclusively through plain files under #.desktop/. Cell dispatch is meant to be data-driven: a real, optional id= attribute on a header button, cross-referenced against a published position → id map, checked before falling back to purely positional matching. Treating cell position as ground truth instead of the real id is a recurring mistake worth avoiding.

The five window apps, one binary

Five apps that used to be five separate binaries — entity context menus, taskbar settings, the database browser (db-hq), the events editor (events-hq), and chat-hai — now live in one shared, compiled binary: khtpm_entity_menu_render.c. Which app you get is selected by a class= attribute on the app's own <window> tag, matching the real "one binary, behavior chosen by loaded data" shape already used elsewhere in this house — not five copies of the same rendering core.

Each app's own real, distinct dispatch logic (db-hq's tag/id-based activate_elem(), events-hq's live file-watch polling and drag handling, chat-hai's session sidebar and ledger polling) was ported in as a documented per-mode branch, not forced into a single shared abstraction. When one app's own working pattern is genuinely different from the others, preserving it as its own real branch beats inventing a unified shape nothing actually asked for.

window shapes
Two real families: small override_redirect popups (entity-menu, taskbar-settings) and full WM-managed windows with their own chrome bar (db-hq, events-hq, chat-hai). They don't share a window-creation code path — don't assume one.
close button
A sub-app's own [X] should only ever tear down its own window. A real, already-fixed bug had it also calling a taskbar-level "close everything" routine — check what a shared cleanup function actually does before calling it from a narrower scope.

Worked example: adding a new HQ menu row end to end

Real, live-verified recipe (built and tested 2026-08-18 — the HQ menu's "cli" row). Two layers matter here, not one:

  1. The row itself is PDL-driven, not C-hardcoded — add hq_menu_N_label / hq_menu_N_cmd to #.desktop/livedesk_taskbar.pdl (max 8 rows, livedesk_build_hq_menu() reads it fresh every open, no recompile needed).
  2. The command string has a real, existing contract — any non-empty, non-"livedesk:"-prefixed, non-"quit" command falls through to a generic shell-out (setsid nohup sh -c '<cmd>' >/dev/null 2>&1 &). A trailing bare " ." token gets substituted with the real absolute house root — the same convention "dir"'s own xdg-open . row already uses.
Real gotcha: gnome-terminal + wildcard directory names

gnome-terminal -- <path> calls execve() on <path> DIRECTLY — no shell, no glob expansion. This house's own real, literal directory names containing * (*.monads/*.livedesk-taskbar) fail silently there. Fix: a tiny wrapper script that resolves its own absolute path via $0 (same real pattern run_khtpm_strip.sh already uses) before exec'ing gnome-terminal — never rely on glob expansion at the exec site.

Also real, also confirmed this session: the manager process's actual working directory is its own ops/ dir, not house root — a relative command path resolves from there, not from wherever you might assume.

The taskbar's real terminal ASCII mirror

A genuine second frontend for the taskbar, matching TPMOS's own dual-render standard — khtpm_strip_render_ascii.+x (no termios, composes + writes a real .txt frame file, then displays it) and khtpm_strip_keyboard_ascii.+x (raw termios only, never prints) as TWO separate binaries, launched together against one terminal via open_cli.sh.

Real bug this split fixes

An earlier, combined single-binary attempt put both concerns in one process — raw termios disables OPOST (needed for keyboard capture), which silently breaks \n→\r\n translation for that SAME process's own printf output too (termios raw mode is a property of the tty, not the calling process). Produced a real, visible "staircase" render bug. Splitting into two processes — one that only captures, one that never touches termios — is what actually fixes it, not a style choice.

The relay this mirror drives (livedesk_agent_relay.txt) was, before this session, deliberately scoped to ENTER/ESCAPE/BACKSPACE/printable only — no way to open a header cell or move strip focus via arrow keys at all. Two real gaps found+fixed in dispatch_key_code() (the relay consumer): forwarding KSC_HQ_HEADER_BASE codes (to open a cell) and KSC_FOCUS_LEFT/RIGHT (to move the strip cursor) — both were zero-risk additions since real X11 input never reaches those same branches through this path.

Still needs expansion: per-app .chtpm layout syntax reference, and the real CSS subset supported by khtpm_css_parser.c (no flexbox, no descendant selectors — both silently no-op).

Legacy Game Engines

Current

16 real standalone projects, one shared engine core

Sixteen real projects (mutaclysm, piececraft-xyz, aomorai-editor, the yahoo cluster, and others) each used to carry their own full copy of a shared engine: a PAL-script interpreter (prisc+x.c), a text-grid parser (chtpm_parser_pal.c), a raw-terminal key reader, a frame renderer, and a display shim. A full drift survey found the copies had genuinely diverged in both directions — no single project's copy was a strict superset of the others' real fixes.

Display Layer — GL → X11

In progress

&.widgits/_shared-lib/ops/x11_mirror.c

Each legacy project's own gl_mirror.c was a thin, deliberate display shim — the one file in the project allowed to call GL/GLUT primitives, reading a CPU-composited RGBA32 frame buffer another process already wrote and blitting it as one textured quad. The real rendering math underneath was already portable, GL-free CPU code; only this final display step touched GL at all.

x11_mirror.c replaces it with plain Xlib — no GL/GLUT dependency, same job, same file-watch pulse, same checksum-verified frame parity. It's a real shared binary now (not a per-project copy), parameterized by the project's own directory name for its window title, with a hand-drawn chrome bar and close button matching the taskbar family's own WM-managed window style. The old gl_mirror.c stays in place as an automatic fallback, not deleted.

Needs expansion: the real conversion recipe for the remaining 13 projects, and what (if anything) differs project to project versus mutaclysm's own pilot.

Input & Dispatch Architecture

Real, ongoing — Phase 1 done, Phase 2 opt-in

khtpm_strip_parser.c's real input pipeline, and how it compares to TPMOS

The taskbar's real X11 KeyPress/ButtonPress handling calls dispatch_key_code()/hit-testing DIRECTLY, in-process — unlike mutaclysm's x11_mirror.c, which is a pure capture-only writer to a shared pieces/keyboard/history.txt that a SEPARATE process (game_dispatch.c) is the sole reader/dispatcher for. This is a real, confirmed architectural difference, not an oversight — the taskbar's own external-input relay (livedesk_agent_relay.txt) is a deliberate, separate side-channel, not a mutaclysm-style unified input log.

Phase 1 — real input mirrored into an audit file (done, live-verified)

Real X11 input handling is completely unchanged — every branch still dispatches exactly as before. Added alongside it: every real key/mouse event ALSO gets mirrored into a new #.desktop/strip_input_history.txt, using the SAME KEY_PRESSED:/ MOUSE_EVENT: format already established by pieces/keyboard/ history.txt (confirmed via direct read of chtpm_parser_pal.c's own poll loop), plus a window-name field since this parser owns THREE separate X11 windows simultaneously (strip, header, popup) — mutaclysm's own single-window convention doesn't need that field. Verified live with genuine, unprompted user interaction, not a synthetic test.

Phase 2 — a real, feature-flagged dual dispatch path → Phase 3 cutover complete (2026-08-19)

KHTPM_NEW_DISPATCH_MODE (env var) existed as of Phase 2 to let the new path run alongside the untouched old path. As of Phase 3, the flag AND the old inline-dispatch path are DELETED — real X11 capture is write-only (mirrors to strip_input_history.txt, dispatches nothing inline) and a separate read-back pass (poll_captured_input(), same cursor/resync discipline as poll_agent_relay()) dispatches everything and redraws ONCE per tick — matching game_dispatch.c's own proven "read all, dispatch each, render once" shape — is now the ONLY path, no runtime toggle, no fallback. Verified with real, mixed clicks/keystrokes across all three windows, confirmed via strip_state.txt showing correct resulting state; the bottom tab bar was confirmed fully covered before the old path was removed.

Real, honest behavior change — and a real bug this exposed

The new path batches what were separate synchronous per-event redraws into one redraw per tick — a real, if minor, behavior difference for real GUI use, not just an implementation detail. Separately, a same-day frame-unification pass (strip_frame.cells.pdl, see au11-hq/TASKBAR-FRAME-UNIFICATION-HANDOFF.md) introduced a real bug: its cells.pdl change-signal file collided by name with this dispatch work's own manager-state dirty signal, causing the layout docs to reload every tick and silently wipe arrow-key submenu focus (never persisted, unlike digit/click nav). Fixed same day by splitting the two signal files — see tb-bugfix-au19.txt.

Not yet done: cutting the default over to new mode. Old mode remains the live default; this is a real, deliberate, still-open decision — not an oversight.

Real testing tool this work surfaced

No xdotool on this machine (confirmed) — real X11 input injection instead uses &.widgits/tile-picker/ops/tp_test_send_key.c / tp_test_send_click.c (real XTest/libXtst, both pre-compiled). They match target windows by WM_NAME (XFetchName) — some real windows (including this taskbar's own) set only WM_CLASS, no title, so a WM_CLASS-matching variant (XQueryTree + XGetClassHint) is needed for those. See Testing Conventions below.

AI Agent Backends

Live-verified 2026-08-18

&.widgits/open-hai/ — real conversational AI, not a mock

open-hai (taskbar cell 14, "ai") is a real X11 chat window, two real processes (khtpm_open_hai_render.c / khtpm_open_hai_manager.c) talking through plain files, same shell/manager split as the rest of the khtpm_* family. It supports multiple real backends: raw Ollama (LAN, 10.0.0.144:11434), a local "Harnecient" tool-hack for non-tooled small models, and real OpenRouter/TokenRouter API integration.

Real, live-tested findings

  • OpenRouter free-tier tool-calling genuinely works — confirmed with a real key, real tools array, real finish_reason:"tool_calls" responses. Not every free model works at any given moment (shared-pool rate limits are real and common on popular models) — nvidia/nemotron-3.5-lightning:free and cohere/north-mini-code:free both confirmed working when the prior default (gemma-4-26b-a4b-it:free) was congested.
  • Real safety boundary: list_dir/read_file auto-execute; write_file/edit_file/run require explicit human approve/deny. By design.
  • Real end-to-end round trip confirmed: relay-injected message → real API call → real response → correctly persisted transcript, and a real list_dir tool call that returned the actual house-root listing.
Real, standing architectural risk

khtpm_open_hai_manager.c and khtpm_open_hai_render.c each keep their OWN separate copy of the available-model list — by design (shell/manager split), but it means any model-list change has to be made in BOTH files by hand, or the render side silently falls back to its own stale default. Confirmed live this session: exactly this drift had already happened once.

Real gotcha

A free model asked to read a path containing special characters (&.widgits/...) dropped the & when re-emitting its own tool call — likely a small-model JSON-fidelity issue, not a house bug. Give these models simple, unambiguous paths for precision tasks.

Full write-up with real test transcripts: house-docs.html/index.html → open-hai + Free AI page (a companion HTML doc set, separate from this one — see "Other Docs" in the sidebar).

Testing Conventions

Current

relay-only — never a direct CLI call as "the test"

Every real app in this house is tested by injecting into its own file-based relay, never by calling its compiled binary directly from a shell and calling that a test. The taskbar reads decimal ASCII codes, one per line, from #.desktop/livedesk_agent_relay.txt; the window-app family reads a similar convention scoped to its own relay file; the legacy game engines read raw keycodes from their own history files. Find the real, currently-live mechanism for the specific process you're testing before injecting anything — the taskbar, the window apps, and the legacy engines each have a genuinely different real relay file and encoding, and assuming one matches another wastes real time.

Two real gotchas worth knowing up front

  • Many of these apps require an explicit "interact" or "control" mode to be engaged before movement/navigation keys do anything at all — sending arrow keys into a menu that hasn't entered that mode yet will silently do nothing, not fail loudly.
  • A frame that's already correct in the underlying data can still be stale on screen — some renderers only recomposite on their own next poll cycle, not on demand. Seeing the wrong thing on screen and seeing wrong data on disk are two different bugs; check both.
Confirm before you claim

Dump the actual rendered frame and look at it. A receipt file or a log line saying a value changed is not the same evidence as watching the screen respond. This distinction has been the direct cause of at least one real, live-corrected false "it's fixed" report this session.

Testing REAL X11 input (not the relay) — no xdotool on this machine

The relay is right for testing DISPATCH logic; it never touches real X11 KeyPress/ButtonPress capture at all. Confirmed 2026-08-18: xdotool is not installed here. Real, working alternative already exists in this house, written for exactly this reason: &.widgits/tile-picker/ops/tp_test_send_key.c / tp_test_send_click.c (both pre-compiled to +x/) — real XTest (libXtst) events, not a fake file-based shortcut. 

tp_test_send_key.+x "<window_name_substring>" <keysym_name>
tp_test_send_click.+x "<window_name_substring>" <button:1|2|3> [rel_x] [rel_y]
Real gotcha, found live 2026-08-18

Both tools match target windows by TITLE (XFetchName/WM_NAME), not WM_CLASS. Some real apps (this taskbar's own khtpm_strip_ parser.c windows, confirmed via XSetClassHint) set WM_CLASS but never a title — find_by_name() in both tools won't find them. If a target window has no title, walk XQueryTree + match on XGetClassHint instead — the underlying XTestFakeKeyEvent/ XTestFakeButtonEvent calls don't need to change, just the lookup step.

Known Issues & Roadmap

Open

what's real, known, and not yet fixed

  • 13 of 16 legacy projects still run the old GL display shim, not x11_mirror.c. The recipe is proven; the rollout isn't done.
  • Toys-cell-launched sessions don't tear down their process tree when the display window is closed. Closing the window leaves the orchestrator and its own child processes running orphaned — nothing currently ties the two lifecycles together.
  • mutaclysm's own camera/3D-layer architecture is a real, separate, deferred effort — several targeted fixes landed and then kept surfacing new real bugs in the same subsystem, which is itself the evidence that the underlying architecture, not any one bug, is the real problem. The plan is a real port toward piececraft's own more advanced camera model rather than more patches.
  • orchestrator.c differs meaningfully across projects in ways that may reflect genuinely different binary sets each project launches, not just accidental drift — worth a real, dedicated read before assuming it's safe to consolidate the same way the parser was.
  • Taskbar's dispatch-mode cutover is DONE (2026-08-19) — no longer an open decision. KHTPM_NEW_DISPATCH_MODE and the old inline-dispatch path are deleted; capture-then-read-back is the only path (see Input & Dispatch Architecture above). What IS still open: the next step of frame unification (au11-hq/TASKBAR-FRAME-UNIFICATION-HANDOFF.md) — sharing one real frame buffer between the taskbar's X11 render and its terminal ASCII mirror, matching wraith-alpha's pattern, rather than the two independently composing from strip_state.txt.
  • ASCII mirror's bottom-tab-bar renders but doesn't activate via the relay yet — tab activation routes through a bigger shared nav-claims numbering system (spans header cells, tabs, AND remote entities' own context menus) that needs its own careful, debug-traced pass, not a blind extension of the HQ-menu fix. cli_io typing support is also still missing from the mirror.
  • open-hai's model list is duplicated by hand across khtpm_open_hai_manager.c and khtpm_open_hai_render.c — a real, confirmed (not hypothetical) drift risk every time a model is added or removed. No shared-source-of-truth refactor attempted yet.
  • Real networking apps exist but aren't wired to the taskbar — 041.pal-chain⛓️, 041.pal-forum👥️, 044.pal-chat-irc👥️+2 (house root) each already have real pal//ops//net/ structure and a phase2-module-split-report.txt documenting prior house-alignment work — the taskbar's network cell (strip_btn_9) is still just a label with no menu wired to it.
  • khtpm_hq_render.c's frame dump has no receipt and no frame-history log — confirmed live 2026-08-24. Its dump_frame_png() (called from the 'p' key and --dump-and-exit, the shared renderer behind db-hq/palettes/events-hq/chat-hai/entity-menu) writes only a PNG. This is a real regression from the house's own standard: ai-cell's own renderer already writes a flat receipt file, and wraith-alpha's session/rgb/current_frame.receipt.pdl — confirmed live and current, not aspirational — goes further still (per-object bounds, checksum, focus/mouse state, one line per rendered element). The gap means anything "verified" via a khtpm_hq_render dump today is pixel-verified only, never receipt-verified — see the "Confirm before you claim" callout above; this is exactly the failure mode it warns about. Fix agreed but deliberately deferred until after a documentation-compaction pass; full findings in au11-hq/house-compaction.md.
  • Documentation volume is outpacing per-task need. au11-hq/ alone has 36+ files. Not stale — what got checked this session was accurate — but too much to hand a token-limited agent wholesale. See house-docs.html/index.html for the mitigation: a purpose-built delegation map naming the 2-3 real docs that matter per task, rather than the whole directory.
