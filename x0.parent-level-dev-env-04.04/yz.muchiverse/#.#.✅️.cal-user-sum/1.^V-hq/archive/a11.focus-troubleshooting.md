# a11.focus-troubleshooting.md — Focus and input bugs in entity windows (2026-08-11)

## Issue 1: Arrow navigation fails on second menu open ✅ FIXED

**Location**: `44.xyz❤️‍🔥️00.17/&.widgits/tile-picker/ops/tp_desktop_window.c`

**Problem**: Arrow Up/Down keys stop responding after opening a context menu a second time (after closing the first). Affects both keyboard event path and NAV_KEY relay path.

**Status**: FIXED — Both NAV_KEY (line ~2003) and XK keyboard (line ~2505) handlers now guard modulo operation with `if (n_methods > 0)` before executing.

**Root cause**: Missing guard check for `n_methods > 0` before modulo operation:
- **NAV_KEY handler** (lines 2004-2008): `popup_focus_row = (popup_focus_row ± 1) % n_methods` with no `n_methods > 0` check
- **XK keyboard handler** (lines 2505-2512): Same modulo without guard
- If `n_methods` becomes 0 or invalid between menu opens, modulo arithmetic is undefined behavior

**Secondary issue** (NAV_KEY only): Missing `popup_digit_accum = 0;` after arrow key handling in NAV_KEY Up/Down paths (present in XK handler but not NAV_KEY). This creates inconsistent state between the two input paths.

## Issue 2: Context menu steals focus from other windows (browser, etc.) ✅ FIXED

**Location**: `44.xyz❤️‍🔥️00.17/&.widgits/tile-picker/ops/tp_desktop_window.c`, `open_context_menu()` line ~1407

**Problem**: When a context menu is open on an entity window and user clicks on a different window (e.g., browser), that window does NOT receive focus. The context menu stays open and modal, blocking input to the other window entirely.

**Status**: FIXED — Pointer grab now skips entirely when `menu_stay_open = 1`. Changed condition from `if (g_grab_pointer && (!g_menu_stay_open || g_grab_pointer_while_stay_open))` to `if (g_grab_pointer && !g_menu_stay_open)`. Allows focus to transfer to other windows while keeping menu open for relay-based navigation.

**Solution applied**: When `menu_stay_open = 1`, the pointer grab is now skipped entirely, allowing focus to transfer to other windows. Keyboard grab remains active for relay-based keyboard control (which doesn't require X11 focus anyway). Menu stays open and interactive via relay even when focus is elsewhere.

## Testing notes

- **Issue 1** (arrow nav): Reproducible via harness with `NAV_KEY:Down` / `NAV_KEY:Up` relay commands after second `OPEN_CONTEXT`
- **Issue 2** (focus): Only reproducible with real mouse click on another window; harness relay cannot test this (as designed)
- Both issues observed live on bookstack entity (4-item context menu: Read, Dir, Close, Cancel)
