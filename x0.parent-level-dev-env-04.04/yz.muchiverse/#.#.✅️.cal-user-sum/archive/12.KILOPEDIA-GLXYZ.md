## 2. Core Architecture: CHTPM Pattern

File: `#.DOX/CHTPM_ARCHITECTURE_GUIDE.txt`

### 2.1 Signal Flow (Data Thro Files)

```
User types 'w' (keycode 119)
  → system/keyboard_input writes "119" to pieces/keyboard/history.txt
  → system/chtpm_parser_pal reads & filters → pieces/apps/player_app/interact_relay.txt
  → pal/main_loop_chtpm.pal reads interact_relay.txt, dispatches to ops
  → ops/game_turn_input <action> appends to data/master_ledger.txt
  → ops/game_compose_frame reads ledger → writes pieces/display/current_frame.txt
  → appends 'x' to pieces/display/renderer_pulse.txt
  → system/renderer watches pulse file → reads current_frame.txt → outputs to terminal
```

### 2.2 Process Architecture (Four Processes)

| Process | Mode | Purpose |
|---------|------|---------|
| `system/keyboard_input` | Foreground (blocking) | Raw-mode stdin, writes keycodes |
| `system/renderer` | Background | Watches pulse file, renders frames |
| `system/chtpm_parser_pal` | Background | Parses .chtpm layout, relays keycodes |
| `system/prisc+x pal/main_loop_chtpm.pal` | Background | Event loop, dispatches to ops |

Launch order (critical):
1. Initialize state files (empty)
2. Launch renderer (so it's ready)
3. Launch chtpm_parser_pal (auto-launches prisc+x)
4. Launch keyboard_input (blocking foreground)

File: `#.DOX/CHTPM_ARCHITECTURE_GUIDE.txt` lines 39–88

### 2.3 CHTPM Layout Format (.chtpm)

File: `#.DOX/CHTPM_ARCHITECTURE_GUIDE.txt` lines 90–116

```
<panel>
  <module>system/prisc+x pal/main_loop_chtpm.pal</module>
  <interact src="pieces/apps/player_app/interact_relay.txt" />
  <text label="[W] Say Word" />
  <button label="[E] End Turn" onClick="ACTIVATE_END" />
  <text label="${game_map}" />
</panel>
```

Elements:
- `<module>PATH</module>` — prisc+x binary + .pal event loop
- `<interact src="PATH" />` — file to relay keycodes to
- `<text label="..." />` — static or `${placeholder}` output
- `<button label="..." onClick="ACTION">` — menu item

### 2.4 Keycode Dispatch (.pal file)

File: `#.DOX/CHTPM_ARCHITECTURE_GUIDE.txt` lines 118–150

```
read_history pieces/apps/player_app/interact_relay.txt x2, x1
li x3, 119        # 'w'
beq x2, x3, do_word
li x3, 101        # 'e'
beq x2, x3, do_end
do_word:
  game_turn_input 1
do_end:
  game_turn_input 3
```

| Key | Keycode | Action |
|-----|---------|--------|
| `w` | 119 | say word |
| `m` | 109 | move |
| `e` | 101 | end turn |
| `q` | 113 | quit (handled by keyboard_input) |
| `1`-`9` | 49–57 | menu selection |
| Arrow Up | 1002 | — |
| Arrow Down | 1003 | — |
| Arrow Left | 1000 | — |
| Arrow Right | 1001 | — |

## 4. OPS Architecture (Self-Contained Binaries)

File: `#.DOX/CHTPM_ARCHITECTURE_GUIDE.txt` lines 211–275

Each op is a standalone C program called by prisc+x:

| Op | Input | Output | Purpose |
|----|-------|--------|---------|
| `game_compose_frame` | config.txt, master_ledger.txt | current_frame.txt (+ pulse) | Render map game state |
| `game_turn_input <action>` | action code (1=word, 2=move, 3=end) | Appends to master_ledger.txt | Process player action |
| `word_compose_frame` | config.txt, master_ledger.txt | current_frame.txt (+ pulse) | Render word game state |
| `word_turn_input <action>` | action code (1=word, 2=end) | Appends to master_ledger.txt | Process word game action |
| `game_hit_frame` | none | Signals frame ready | Placeholder |

Pattern: **Ledger-driven state** — game state is reconstructed from the append-only
ledger (`data/master_ledger.txt`), not stored in memory or mutable state files.

## 5. button.sh Initialization

File: `#.DOX/CHTPM_ARCHITECTURE_GUIDE.txt` lines 245–281

Launcher script must:
1. Compile all ops (`gcc`)
2. Create directory structure: `data/`, `pieces/display/`, `pieces/system/`,
   `pieces/apps/player_app/`, `pieces/keyboard/`, `pieces/chtpm/layouts/`
3. Initialize marker files to empty
4. Initialize `data/master_ledger.txt` with header row
5. Export env vars: `PRISC_PROJECT_ROOT`, `PRISC_PROJECT_ID`
6. Launch processes in order (renderer → chtpm_parser → keyboard_input)
7. Set trap to kill PIDs on EXIT/INT/TERM

## 6. Registry + Dispatcher + Strategy Pattern

File: `404.architecture-bible/AI-ARCHITECTURE.txt`

This pattern appears across the codebase for pluggable, data-driven behavior:

### 6.1 General Pattern

```
REGISTRY (what behaviors exist)
  → SWITCH OP (look up id, update state.txt)
  → DISPATCHER (read mode, look up op_name, shell to it)
    → STRATEGY OPS (independent binaries that compute results)
```

### 6.2 Concrete Examples

| Domain | Registry | Switch Op | Dispatcher | Strategy Ops |
|--------|----------|-----------|------------|--------------|
| AI strategies | `pieces/registry/ai/ai_strategies.txt` | `switch_ai_mode.c` | `pick_ai_strategy.c` | `decide_chase.c`, `decide_weighted_flee.c`, `decide_wander.c` |
| LLM providers | `model_list.txt` or `provider_list.txt` | `switch_model.c` | `send_message.c` | provider-specific send code |
| Terrain types | `terrain_types.txt` | — | `glyph_walkable()` | `raymarch_walls_3d()` |

### 6.3 AI Strategy Architecture Detail

File: `404.architecture-bible/AI-ARCHITECTURE.txt` lines 1–322

**Registry** (`pieces/registry/ai/ai_strategies.txt`):
```
id|name|op_name|description
0|preset_chase|decide_chase|Always step directly toward hero
1|weighted_flee|decide_weighted_flee|Chase normally but flee if health drops
2|wander_with_detection|decide_wander|Random walk until hero detected, then chase
```

**Switch op** (`ops/switch_ai_mode.c`):
- Usage: `switch_ai_mode.+x <monster_state_path> <strategy_id>`
- Looks up strategy_id in registry, updates `ai_mode` field in state.txt

**Dispatcher** (`ops/pick_ai_strategy.c`):
- Reads `ai_mode` from monster `state.txt`
- Looks up `op_name` in registry
- Shells to `./ops/+x/<op_name>.+x` with args
- Validates result, writes `action.txt`

**Strategy ops** output format: `"target_x target_y action_type reason"`

Adding a new strategy:
1. Write `ops/decide_myname.c`
2. Compile: `gcc -o ops/+x/decide_myname.+x ops/decide_myname.c -lm`
3. Add row to `ai_strategies.txt`

## 10. Testing Conventions

File: `404.architecture-bible/AI-ARCHITECTURE.txt` lines 255–289

**File-injection testing** is the preferred approach:
- Write to config/state files
- Call ops directly
- Verify output files changed

Example test flow for AI switching:
```bash
# 1. Check initial state
grep ai_mode pieces/.../zombie_02/state.txt
# 2. Run switch
./ops/+x/switch_ai_mode.+x pieces/.../zombie_02/state.txt 1
# 3. Verify change
grep ai_mode pieces/.../zombie_02/state.txt
```

**HONEST LIMIT**: file-injection tests verify DATA correctness but not RENDERING
(terminal display, X11 windows). For visual verification, run a real game session.

See also: `#.DOX/drag-drop-how2.md` for X11 drag-drop testing with xdotool.
