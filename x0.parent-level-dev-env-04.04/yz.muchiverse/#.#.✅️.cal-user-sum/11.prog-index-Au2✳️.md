1. WHAT "XYZOS" AND "TPMOS" ACTUALLY MEAN (read this before anything else)
================================================================================
**XYZOS** (`❤️‍🔥️.XYZOS_README.md`) is not an app, it's a *local operating
culture*: a house of small, file-mediated processes (games, tools, identity,
widgets, future `@apps`) where a GL window is the primary UX and the ASCII
terminal is secondary/dev-only. Core laws, stated directly in that file:
  - files are the API — no DB, no JSON-as-state, no sockets unless real
    cross-machine networking is genuinely needed (same law as the 2.muchi-
    verse-0.0 tree, just restated house-wide here)
  - exactly ONE visible-frame writer per session (chtpm owns
    `current_frame.txt` — an op never writes it directly)
  - idle must not spam frames
  - harness-before-hype — don't claim a feature works without a harness run
    that proves it
  - "don't build the `@app-store` before the desk" — i.e. don't build
    packaging/distribution before the actual desktop experience is real and
    lived-in (this is why `@.app-store/` is still a genuinely empty
    directory today — that's not neglect, it's the stated order of
    operations)

**TPMOS** is a real, defined standard — not just a vibe-reference the way it
reads in `!.!.tpmos-first.txt` (that file is dev brainstorming that
*assumes* the reader already knows TPMOS; it is not the definition). The
actual spec lives in `#.haiku+/tpmos-re-dox/!.TPMOS_ONBORD_BIBLE_10.md`:

  **TPMOS = "True Piece Method" + "OS"**, a three-layer hierarchy:
    - **PIECE** ("Soul") — a directory with its own `piece.pdl` + `state.txt`
    - **MODULE** ("Brain") — a background daemon that owns one piece's logic
    - **OS / CHTPM** ("Theater") — the shared layout/variable-substitution/
      input-routing layer every module renders through

  Mantra: **"if it's not in a file, it's a lie."** The concrete build
  pattern ("TPMOS parity") is in `#.DOX/TPMOS_PATTERN_FINAL.md`:
  `orchestrator.c` (meta-launcher) → `button.sh` (starts services, then
  exits — it is not the long-running process) → `game_manager.c` (polls
  input, drives ticks) → `chtpm_parser_pal` (renders). Several projects in
  this push were explicitly converted to match this shape this month —
  see `!.!..j25-conversion-task.md` for the mutaclsym/wsr-pal/pal-chat-irc/
  muchi-pal-agent conversion log (added `orchestrator.c`, `kill_all.sh`, a
  `--pal` launch flag to each).

  Practical upshot for anyone touching a project in this push: **"is this
  project TPMOS-standard yet?"** is a real, checkable question (does it have
  `orchestrator.c` + the button.sh/game_manager split?), not a vague
  aspiration — check `!.!..j25-conversion-task.md` for the current
  conversion status per project before assuming.

There is no single canonical "vision statement" doc beyond the XYZOS
README's closing line: *"small processes + honest files + GL surfaces +
widgets can feel like an OS for games and tools."* Longer-range, informal
ideas (avatar/pet economy, gacha, social/marketing) live in `wussup.4xyz.txt`
and `quick-summar-j26.txt` — treat these as raw brainstorm, not roadmap.

3. THE MULTIWINDOW DESKTOP + WIDGET ("WIDGIT") LAYER
================================================================================
House spelling note, stated explicitly in `&.widgits/WIDGIT_BIBLE.md` line
2: **it's "WIDGIT," not "widget," deliberately, in every commit.** The
request that produced this doc used the standard spelling — noting the house
convention here so it doesn't get silently overwritten later.

**Widget architecture** (`WIDGIT_BIBLE.md`, 804 lines, unusually thorough):
strictly two separate programs — a host and a widget — that only ever talk
via files: `interact_relay.txt` (key-forwarding), an `inbox.txt`/`status.txt`
command bus, and a peer-discovery ledger at
`xyzfs/users/<uuid>/home/runtime/ledger.txt` (pipe-delimited: timestamp,
event, type, project_id, session_root, pid, display_name, inbox_path) —
this ledger-based discovery replaced an earlier `focus.txt`-scanning
approach (§2.6). The render pipeline is a 4-stage chain — compose_frame →
chtpm_parser_pal → chtpm_rgb_render → gl_mirror — with checksum receipt
files (`rgb_frame.receipt.txt`, `gl_display.receipt.txt`) so a harness can
prove real pixels actually moved end to end, not just that a file was
written.

The bible's §2 ("FALSE ASSUMPTIONS vs TRUTH") is worth reading in full
before touching this layer — 12 documented cases where an agent got the
architecture wrong, e.g.: `chtpm_parser_pal` resolves its root via
`getcwd()`, not `PRISC_PROJECT_ROOT`; the canonical `gl_mirror.c` (with
`interact_relay` forwarding) lives in `014.wsr-pal`, not the newer
`045.muchi-pal-agent` copy; `frame_changed.txt` never fires in widget mode
— `renderer_pulse.txt` is the real trigger; font glyphs must be a
project-local copy, never symlinked.

**Widgets that exist today**: `file-menu` (most mature — real system/
scripts/projects tree, `USER_REPORT.txt`), `event-editor` (chrome + nav
built, GL mock via freeglut for RMMV-style preview — but Save/Load/Import/
Export are status-line stubs only per `ARCHI_TEST_SUM-J28.txt` §11),
`map-picker`, `tile-picker`, `proc-monitor` (these three are lighter —
button.sh + ops + README only).

**Desktop surfaces**:
  - `#.desktop/` — a shared "file desktop tray" (`events/`, `entities/`,
    `tiles/`, `inbox/`) where widgets and mutaclysm exchange portable
    "piece packages" as plain directories, offline-editable before import
    into a live world. Has real seeded content already (a demo tile, a demo
    event, a logged inbox request) — built and exercised, not a stub.
  - `150.gl-canvas/` — minimal X11/Xdnd proof-of-concept for real
    drag-and-drop between GL windows (a pet window dragged into a drop
    target). Compiles, has a `test-harn/` with drag-sim + screenshot ops,
    but `proof/` is empty — no recorded run. Built, unconfirmed.
  - `151.screen-rec+01.02/` — Wayland-appropriate screen recorder
    (xdg-desktop-portal + PipeWire + libx264, matching the house's receipt-
    file pattern). Architecture doc claims a confirmed GNOME 42 capture, but
    `recordings/` is empty in this tree — no artifact backs that claim here.
  - `200.glut-craft/` — standalone (no chtpm/prisc dependency, by design)
    voxel sandbox. Has a dated, harsh `CRITIC_REPORT.md`: compiles and runs,
    but graded NEEDS_WORK, 4.5/10 visual — unbatched immediate-mode
    rendering, ~110% idle CPU, no atlas/AO/skybox. Per
    `!.clone-clowning-handof.md`, this and its sibling clones are
    deliberately parked (P1, "ignore unless user re-opens") in favor of
    `205.ttg-tactics`, `201.rpg-maker-clone`, `204.sw-battlefront`.

**Testing/harness discipline** — this is one of the most mature parts of
this push and worth internalizing as the standard to hold new work to:
`%.harnesses/<a>+<b>/` holds cross-project interaction tests (event-
editor+desktop, file-menu+editor, file-menu+mutaclysm, map-picker+
mutaclysm, proc-monitor, tile-picker+mutaclysm), each with real timestamped
`proof/` run directories containing ~10 numbered artifact files per run
(state snapshots, before/after diffs, save-tree dumps). `muta-zoo.md`'s own
status table marks file-menu+editor, file-menu+mutaclysm, map-picker,
tile-picker, and proc-monitor **GREEN**; a `muta-zoo-pets/` harness is
explicitly listed as TODO/out of scope — i.e. even the harness layer itself
flags the pet/zoo direction as not yet started. Per-project `test-harn-same/`
dirs exist for 8 of the pal-VM projects; `arch-re&test.txt` documents real,
live, key-injected multi-user tests (not synthetic/API-only) specifically
because synthetic tests had already missed 3 real bugs this push — treat
"harness exists but empty `proof/`" (gl-canvas, screen-rec) as a real signal
that a claim is unverified, not a formality.

6. THE AI-HARNESS ENDGAME — WHERE THIS PUSH IS HEADED
================================================================================
The stated long-term vision (from this request, cross-referenced against
what's actually in motion in this push and in `2.muchi-verse-0.0`'s zest-er-
summary §4) is a powerful **local AI harness**: LLMs, distillation/RL, and
pal-scripts that can be generated — or even trained — on the fly. This push
doesn't have that built yet, but it has landed real, load-bearing pieces of
the path to it, and it's worth being explicit about which pieces are which:

  - **The provider abstraction is real and multi-backend today**:
    `045.muchi-pal-agent` already runs gemma-local/gemini/ollama/llamacpp
    behind one registry+switch interface (`model_list.txt` / a `/model`
    command), with a deterministic, **pre-LLM** tool-execution layer (a
    keyword/strategy dispatcher decides + runs the tool *before* the LLM is
    even called, logging the result as a normal turn) rather than parsing
    tool-calls out of a model's own completion text. This is the
    foundation any "pal-script written by an LLM" flow would sit on top of
    — the agent already knows how to safely act on a filesystem via a
    fixed op surface.
  - **The harness/proof discipline (§3) is the missing ingredient RL needs
    for a reward signal**: every harness run in this push already produces
    structured, timestamped, machine-readable pass/fail artifacts
    (`proof/*.txt`, receipt files, FRAME_REPORTs). That's not currently
    wired to any training loop, but it is *exactly* the kind of signal an
    RL-from-verified-execution loop would consume — a genuinely useful
    asset that already exists, not something that needs inventing from
    scratch.
  - **The distillation loop itself is designed, not built** —
    `2.muchi-verse-0.0`'s zest-er-summary §4.2 lays out the concrete plan
    (teacher model + IQABELLA/iqabod student in the same chat room,
    harvest-to-corpus, train, iterate, then add human-in-the-loop RL
    feedback) and explicitly prefers gemma-lan as teacher over gemini for
    cost reasons. Nothing in this push shows that loop actually running yet
    — no harvested corpus, no retrain artifact was found in this survey.
  - **Gemma's tool-use scaffolding already pivoted once** — the original
    plan (teach gemma a `TOOL: verb args` marker syntax and parse it back
    out) was tried and explicitly reversed in favor of the pre-execution
    approach now live in `045.muchi-pal-agent` (see zest-er-summary §4.1's
    own correction). Anyone reviving the marker-syntax idea for "generate a
    pal-script on the fly" should know that direction was deliberately
    walked back once already, for a documented reason — read
    `045.muchi-pal-agent🤖️+1/!.GRAND-PLAN-TOOL-SCAFFOLD.txt` before
    resurrecting it.
  - **"Pal-scripts generated on the fly"** has no dedicated design doc yet
    anywhere in this push (checked `#.DOX/`, `#.haiku+/`, `pal-scripts/` in
    2.muchi-verse-0.0). The closest existing precedent is
    `pal-scripts/pal-chat-agent.pal` in `2.muchi-verse-0.0` — a thin,
    hand-written meta-orchestration script that launches and drives another
    pal-VM instance via file injection. That's a real, working example of
    one script controlling another process's session — genuinely useful as
    a template if/when a future agent designs LLM-authored pal-scripts, but
    it is hand-written, not generated.

**Honest summary of the gap**: the pieces that make a local AI harness
*safe* to build (a real multi-provider agent, a deterministic tool layer,
and a harness/proof system that already produces structured verification
data) exist and are proven. The pieces that make it *learn* (the
distillation loop, an RL signal wired to harness proof output, and any
form of on-the-fly pal-script generation/training) are still at the
design-doc or pure-concept stage. The single highest-leverage next step,

### 9.4 A significant, house-wide finding directly relevant to §6's own
"AI-harness endgame" — small local LLMs can't reliably self-classify a
verdict, even when they demonstrably know the content
Full detail: `PITFALL 69` in `#.haiku+/!.xyzos-pitfalls+1.txt`, `§42` in
`#.haiku+/!.xyzos-standards+1.txt`, and the dedicated theory doc
`#.haiku+/!.gemma-judge-tomo&iqa.md` (written specifically to connect
this finding to 045-agent's tool-calling pattern, §6's own RL-judge-loop
plan, and IQABELLA/T@Q's own training-data harvest — read it in full,
it's the direct continuation of this section). One-paragraph version:
asking `gemma3:270m` to directly classify content into a binary verdict
was live-measured as unreliable (wrong 2/3 times on an obviously-lethal
test case in `my-biotech`'s own FDA_REVIEW mechanic, §9.1 above, even
reframed multiple ways) — but the SAME model, asked to openly DESCRIBE
the same content instead, gave real, accurate answers 6/6 times. Fix:
never ask a small model to self-classify; ask it to describe, then run
your own deterministic keyword scorer over the real response text.
Matched a bigger model's own accuracy without needing to upgrade.

**Direct relevance to §6's own "AI-harness endgame" section above**: that
section names `ROADMAP-models.txt` §11.2's own LLM-as-judge RL
auto-training loop as designed-but-unbuilt. This finding is a concrete,
real warning for whoever builds it — a naive "rate this 1-5" judge
prompt against a small/cheap model (the natural choice for a
high-volume RL reward loop) risks producing a reward signal that looks
plausible but doesn't track real quality, silently poisoning the whole
training loop. The describe-then-deterministically-score pattern is the
fix, and it should be tried BEFORE that loop is built, not discovered
after a training run already burned compute on a bad signal.
