# 🧱 Platform Primer — the one file you almost always attach

**Purpose:** this IS your "1 context file" for most prompts. Paste this whole doc (or trim
the sections irrelevant to the task) as the CONTEXT upload alongside your PROMPT and CODE files.
It's written so a browser-window AI with zero prior exposure to this house can orient in one read.

---

## 🏠 What this codebase is

A file-backed, module-driven desktop OS ("the house" / "muchiverse"), built as a spiritual
successor to **TPMOS** (`1.TPMOS_c_+rmmp.0103.0001/`, a sibling dir one level up). Everything
real is a **file on disk** — "if it's not in a file, it's a lie." No hidden memory-only state
that matters survives a restart.

## 🧩 The core shape: PIECE → MODULE → OS

- **PIECE** 🧬 — a directory with `state.txt` (+ a `.pdl` descriptor). Owns its own state.
- **MODULE** 🧠 — a background daemon (`*_manager.c`) that orchestrates pieces. "Thin" —
  delegates real work to standalone **ops** (small, independently-testable `.c` → `+x/*.+x`
  binaries), never inlines business logic into the manager itself.
- **OS / renderer** 🎭 — the "theater" layer. Substitutes `${var}` into layout files, routes
  input, composes the visible frame. Should NOT contain business logic or piece-specific lookups.

**➡️ You will almost always need BOTH a layout file (`.chtpm` markup) AND a manager (`*_manager.c`)
back from any real feature — yes, this is a safe assumption to build around.**

## 🖥️ TWO separate parser/renderer families — know which one you're in

| Family | Used by | Engine | Notes |
|---|---|---|---|
| Legacy `chtpm_parser_pal.c` | mutaclysm, piececraft-xyz, older projects | PAL-VM, text-grid | `!.HOUSE_STDS.md` §A |
| `khtpm_*` family | livedesk taskbar + every tb-launched sub-app (db-hq, chat-hai, open-hai, events-hq) | Raw Xlib/Xft, own `khtpm_css_parser.c` | **No flexbox, no descendant CSS selectors** — silently no-ops, don't assume they work |

If your task touches a taskbar sub-app, you're in `khtpm_*` — don't reach for legacy `.chtpm` tag
knowledge, they've drifted apart.

## 🔌 Input flow (the real, house-standard shape)

```
KEYBOARD/MOUSE capture (raw termios, or Xlib KeyPress/ButtonPress, or XTest-injected for testing)
       ↓ writes decimal codes / KEY_PRESSED:/MOUSE_EVENT: lines
a shared relay/history FILE (e.g. livedesk_agent_relay.txt, pieces/keyboard/history.txt)
       ↓ ONE reader polls it
DISPATCHER (game_dispatch.c-style, or khtpm's dispatch_key_code())
       ↓ mutates state.txt, composes a frame
RENDERER (never touches raw input itself — pure "read state, print/draw")
```

**Rule of thumb:** capture and render should be SEPARATE concerns/processes. TPMOS's real
`system/renderer.c` never touches termios; `system/keyboard_input.c` never prints. Combining
them causes real, subtle bugs (raw termios disables `\n`→`\r\n` translation for ANY writer on
that tty — a real staircase-rendering bug this house hit in August 2026).

**2026-08-28 — mapping khtpm windows (do not steal the human):**
- WM-managed HQ (db-hq / events-hq / chat-hai): `XMapWindow`, not `XMapRaised`.
- Override-redirect popups (Settings / entity-menu): `XMapRaised`, no `XSetInputFocus` on map.
- Poll each window's own `*_history.txt` even when it does not have X focus.
- Full table: `1.^V-hq/HQ-WINDOW-MAP-AND-AGENT-INPUT.md` (do not invent a third map rule).

## 📐 State/config conventions

- **PDL files** (`.pdl`): pipe-delimited, `SECTION | KEY | VALUE` — the house's `.ini`-equivalent.
- **State files**: `key=value\n` per line, or the pipe-delimited PDL shape depending on subsystem.
- **Marker/pulse files**: append a byte (`"P\n"`) to signal "something changed, redraw" — never a
  `dirty=1` flag inside a state file. `stat()` the marker's size to detect growth cheaply.
- **One-writer rule**: exactly one process ever writes a given state/frame file. If two things
  need to write it, that's a bug waiting to happen (real house pitfall #17/#36).

## 🗂️ Directory shape (top-level, informal)

- `@.apps/` — system tool apps (editor, user auth, etc.) — some drift/lag behind current
  conventions, verify before trusting.
- `&.widgits/` — shared reusable widgets/libraries (`_shared-lib/` is the real single source of
  truth for code copied build-time into multiple projects — check there before assuming
  something's unique to one project).
- `xyzfs/bin/<app>/` — the "installed app" convention (only `muchi-pet`/`livedesk-clock` fully
  migrated here so far — most things, including the taskbar and mutaclysm, are NOT yet moved in).
- Numbered project dirs (`101.mutaclsym…`, `103.media-studio/`, etc.) — individual games/apps,
  each usually self-contained with their own `system/`/`ops/`/`pieces/`.
- `#.desktop/` — the taskbar's own live runtime state (PDLs, relay files, session state).

## ✅ Before you build anything new

1. Check if the pattern already exists elsewhere in this codebase.
2. If not, check TPMOS (`1.TPMOS_c_+rmmp.0103.0001/`) — it's the grandfather program, often more
   feature-complete, and this house was explicitly built to converge toward its shape.
3. Don't invent a new state-file format, relay convention, or dispatch pattern without checking
   both of the above first.
