# 🎨🧰 Palettes (Tile/Sprite Picker) as Toys/Pals — delegation map

**Goal:** figure out how palettes (tile/sprite pickers) should associate to projects, whether
they're also "pals" (get a bottom-toolbar slot + their own save-state per file/desk).

## 🧠 Real starting point (confirmed location)

`&.widgits/tile-picker/` — the existing tile-picker widget IS the real reference implementation
for "palette" already. It also owns the real `tp_test_send_key.c`/`tp_test_send_click.c` XTest
input-injection tools (see `2.house-shape-status-report.md` for why those matter beyond this
topic). `au11-hq/TASKBAR-MENU-ARCHITECTURE.md`'s own "Building a NEW sub-app from scratch" section
covers real pitfalls this exact widget family hit (elem-pool exhaustion, CSS-apply clobbering,
ledger tail-vs-head reads) — read that BEFORE assuming a palette is a simple copy-paste of an
existing sub-app.

## 🤔 The real open design question (don't let a browser AI guess this — decide first)

Is a palette:
- (a) **A pal** — a placed entity instance with its own `state.txt`, gets a bottom-toolbar tab
  slot, saves state per-desk like any other pal, OR
- (b) **A project-scoped tool** — lives inside `3.<file>`'s own scope, no toolbar presence, opened
  contextually from within the project it's editing?

These are architecturally different (pal = first-class taskbar citizen with its own tab; tool =
subordinate to whatever project opened it). **Answer this yourself before prompting** — a browser
AI given ambiguous scope here will guess wrong more often than not, per the platform primer's own
"don't invent a new pattern" rule (there's no existing precedent for a "tool that's ALSO a pal" to
copy from).
