# 🍜 CHAT-HAI DESIGN — The Side-Bar Multi-Model Conversation Engine 🎭

> **🍜 WHAT THIS IS:** Design plan for a new livedesk app — a slender, always-on side-bar chat feed where multiple small models (gemma270, qwen-ladder) constantly converse, remember, and react, overseen by slower "manager" models that curate, reprompt, and delegate. Selectable from h-ai (cell 14). Proof-of-concept first, user-facing later.

---

## 🧩 PART I — THE CONCEPT 🎯

### The One-Line Dream
> **A side-bar of minds that never sleep, always talking, always remembering — and you can lean in whenever you want.** 🍜

`chat-hai` is not a chat window for a human typing to one model. It is a **persistent multi-agent conversation theater** — a slender vertical pane docked to the side of the desktop, constantly scrolling with messages from 4+ small models talking to each other, with bigger models moderating their memories and reprompting them in the background.

### How It Sits in the House
- Lives under **cell 14 (h-ai)** as a **selectable backend/mode** — just like BACKEND_HARNECIENT is a mode, `chat-hai` is another.
- Opens as a **real X11 managed window** — same `_MOTIF_WM_HINTS` discipline as h-ai, db-hq, events-hq.
- GUI is **slender, vertical, side-docked** — think Discord's chat channel list width, but it's a live feed, not a list of rooms.
- **Does not steal focus** — it is ambient infrastructure, like a clock or a ticker.

## 🎭 PART II — THE CAST (ENTITIES & PERSONALITIES) 👥

### The Smalls (4x gemma270 / qwen-ladder)
**Always on. Always chatting. Fast.**

| Role | Model | Job | Personality |
|---|---|---|---|
| 🧠 **Thinker-1** | `gemma3:270m` or `qwen2.5:0.5b` | Raw association, free-association, connection-making | Curious, scattered, makes jumps |
| 🛠️ **Thinker-2** | `gemma3:270m` or `qwen2.5:0.5b` | Tool-shaped thinking, procedural steps | Precise, literal, asks "how?" |
| 💬 **Thinker-3** | `gemma3:270m` or `qwen2.5:0.5b` | Social mirror, reflection, synthesis | Empathetic, summarizes, validates |
| 🎨 **Thinker-4** | `gemma3:270m` or `qwen2.5:0.5b` | Pattern art, aesthetic, metaphor | Poetic, visual, makes analogies |

> **Ladder rule:** Qwen 2.5 Coder sizes are 0.5B, 1.5B, 3B, 7B, 14B, 32B. For local LAN speed, we run the **0.5B/1.5B ladder** as the smalls. The 7B is our **fast upper-mid** — used sparingly as a "manager" when a smoll needs a smarter nudge, not for every turn. We do NOT call the 14B/32B unless the user explicitly invokes a heavy query.

### The Managers (1-2x qwen2.5:7b or haiku)
**Called less often. Slower. Smarter.**

| Role | Model | Job |
|---|---|---|
| 🎓 **Moderator** | `qwen2.5:7b` or `haiku` | Reads all smol memories, trims noise, marks priorities, reprompts smols when they loop |
| 🧘 **Organizer** | `qwen2.5:7b` | Pieces fragments from smols into coherent threads, adjusts "joints" (personality weights) per entity, curates relationship graphs |

> **Why haiku works here:** Haiku can prompt the manager. The manager does not need to do the task — it just needs to decide *who* should do it next and *what* they should think about. That is a classification/description task, which small models do well. The describe-then-score pattern (`HARNECIENT-HACK.md`) applies directly.

### The Human (You)
**You can jump in anytime.**
- Type a message → it appears in the feed as a **special user-entity message**.
- The moderator sees it and decides: **reply itself?** delegate to a specific smol? start a thread?
- You can also act as **moderator** — tell the manager "focus on X" or "tell Thinker-1 to stop rambling about Y."

## 🧠 PART IV — MEMORY & PERSISTENCE 💾

### Memory File Structure
Every entity has a **memory ledger** — a real text file, per the house law.

```
chat-hai/
├── entities/
│   ├── thinker-1/
│   │   ├── memory.ledger       ← chronological memory entries
│   │   ├── joints.txt          ← personality weights / prompt bias
│   │   └── state.txt           ← current mood, topic focus, energy
│   ├── thinker-2/
│   ├── thinker-3/
│   ├── thinker-4/
│   ├── moderator/
│   │   ├── memory.ledger
│   │   ├── joints.txt
│   │   └── queue.txt           ← smols waiting for reprompt
│   └── user/
│       └── memory.ledger
├── threads/
│   └── thread_<id>.txt         ← tagged conversation threads
├── priority/
│   └── hot_topics.txt          ← topics the moderator has marked high-priority
└── config.txt                  ← model assignments, ladder config
```

### Memory Entry Format
Each line in `memory.ledger`:
```
TS | KIND | ENTITY | TOPIC_TAG | TEXT | PRIORITY
```

- `KIND` ∈ `SAY | THINK | RECEIVE | ACTION | SILENT`
- `PRIORITY` ∈ `0-3` (0 = noise, 3 = keep-forever)
- The **moderator** periodically reviews and re-tags priorities, truncates noise, and marks entries for deletion or archival.

### The Priority & Recall System (FSM/RL-shaped)
Memory recall is **NOT free-text search**. It is **deterministic selection**:

1. The moderator (or a scheduled daemon) scans `memory.ledger` for `PRIORITY >= 2` entries.
2. It tags them with `TOPIC_TAG` based on keyword extraction (deterministic, not model-classified — DESCRIBE-don't-CLASSIFY).
3. When an entity is about to speak, the system **deterministically selects** which tagged memories to inject into its prompt based on:
   - Current conversation topic match
   - Recency decay (older entries need higher priority to survive)
   - Relationship weight (entities that interact often share more memory)

> **This is the FSM/RL-shaped part:** The selection policy is deterministic (keyword + decay + weight). The model never picks what to remember. The model only ever speaks. We sculpt the statue.

### Relationship Graph
A real text file: `relationships.txt`
```
thinker-1,thinker-2,0.8   ← high affinity
thinker-1,thinker-3,0.3   ← low affinity
thinker-2,thinker-4,0.6   ← medium
```
- Weights shift based on interaction frequency (more replies to each other = higher weight).
- The moderator adjusts these weights when it detects loops or toxic patterns.
- High-affinity pairs get **more shared memory injected** — they "know each other better."

## ⚙️ PART V — THE MODERATOR LOOP 🔄

### What the Moderator Actually Does
The moderator is **not** a chat participant. It is a **background daemon process** that wakes up on a schedule (or when triggered by a smol getting stuck).

| Trigger | Moderator Action |
|---|---|
| Smol repeats itself 3x | Reprompt with a nudge: "you just said that — say something different" |
| Smol goes silent > N seconds | Inject a topic prompt from `priority/hot_topics.txt` |
| Memory ledger > N lines | Truncate PRIORITY=0 entries, archive PRIORITY=1 entries |
| User jumps in | Read user message, decide which smol(s) should respond, adjust their `joints.txt` to orient them |
| 2 smols arguing in circles | Inject a synthesis prompt: "summarize both positions and find the common ground" |
| New topic detected | Tag all recent entries, create a new `thread_<id>.txt` |

### The Organizer (Smarter, Slower)
The organizer runs **less frequently** (e.g., every 5 minutes vs every 30 seconds):
- Reads all smol memory ledgers.
- Identifies cross-entity patterns ("thinker-1 and thinker-3 keep circling the same idea").
- Writes **synthesized insights** into `threads/` as new persistent artifacts.
- Adjusts `joints.txt` personality weights to break loops or amplify productive patterns.

> **Haiku as a reprompter:** Haiku can be the organizer for very small tasks — "look at these 3 messages, pick which smol should respond next, and write a one-line nudge." It is fast enough for this and cheaper than running a 7B for every cycle.

## 🔁 PART VI — THE PROOF-OF-CONCEPT LADDER 🪜

### Phase 0: The Jump Rope (Week 1)
**Goal: Prove 4 smols can talk to each other without a human in the loop.**

1. Launch 4 `gemma3:270m` (or `qwen2.5:0.5b`) Ollama instances on the LAN Mac.
2. Each entity has a minimal system prompt: name, personality, one-line behavioral rule.
3. The conversation loop: entity A speaks → entity B reads A's message + its own memory → B speaks → C reads → C speaks...
4. Round-robin for now — no moderator intelligence yet.
5. **Success:** 4 entities produce 50+ coherent message pairs in 1 hour without crashing, looping forever, or producing gibberish.

### Phase 1: The First Memory (Week 2)
**Goal: Add persistent memory and priority tagging.**

1. Each entity writes its messages to `memory.ledger`.
2. A simple daemon (bash + pure C parser) tags each entry with a topic keyword.
3. Entities have their last 10 messages + 5 priority-memory entries injected as context.
4. **Success:** Entities reference things said 30 minutes earlier. Conversations show continuity.

### Phase 2: The Moderator Arrives (Week 3)
**Goal: A bigger model curates the smols.**

1. Introduce `qwen2.5:7b` as the moderator.
2. Moderator wakes every 60 seconds, scans `memory.ledger` for repeats and silence.
3. Moderator writes reprompt notes to a smol's `queue.txt`; the smol reads this before its next turn.
4. Moderator marks priorities and writes `hot_topics.txt`.
5. **Success:** Smols stop looping. Conversations diversify. The feed stays readable.

### Phase 3: The User Leans In (Week 4)
**Goal: Human-in-the-loop works.**

1. User types a message via the side-bar input line.
2. Moderator receives it, decides which smol(s) should engage, and orients them.
3. User can also directly address the moderator: "tell thinker-1 to focus on physics."
4. **Success:** User intervention changes the conversation trajectory within 2 turns.

### Phase 4: The Organizer & Joint Tuning (Week 5-6)
**Goal: Smarter model curates art from noise.**

1. Introduce the Organizer (`qwen2.5:7b` or `haiku`).
2. Organizer runs every 5 minutes, reads all memory, writes synthesized threads, adjusts `joints.txt`.
3. Haiku is tested as the lightweight organizer for simple reprompt tasks.
4. **Success:** The system produces coherent "thought chains" — not just chat, but evolving ideas.

### Phase 5: Tasks & Delegation (Week 7+)
**Goal: From chatting to doing.**

1. User gives a real task via h-ai: "design a small game using these event commands."
2. Moderator breaks it down: "thinker-1, brainstorm mechanics; thinker-2, draft the event structure; thinker-3, write the dialogue."
3. Smols produce artifacts → moderator assembles them → presents to user.
4. **Success:** A real deliverable (event files, a plan doc, a code snippet) emerges from the chat.

## 🔌 PART VII — TECHNICAL ARCHITECTURE ⚡

### The Loop (Deterministic, Not Model-Routed)
```
state = ROUND_ROBIN
entities = [thinker-1, thinker-2, thinker-3, thinker-4]
cursor = 0

while running:
    speaker = entities[cursor]
    context = build_context(speaker)  # memory + relationships + priority recall
    reply = ollama_call(speaker.model, context)
    speaker.memory.append(reply)
    broadcast_to_feed(reply)
    
    # Moderator check (every N turns OR on trigger)
    if should_moderate():
        moderator_action = ollama_call(moderator.model, moderator_context)
        apply_moderator_action(moderator_action)
    
    cursor = (cursor + 1) % len(entities)
    sleep(speaker.rate)  # smols are fast; moderator is slow
```

### Why the Model Never Routes
- The **round-robin** is deterministic code.
- The **moderator** is consulted, but it only writes to files (`queue.txt`, `joints.txt`, `hot_topics.txt`). It does not call tools directly.
- The **FSM/recall** is keyword + priority + decay — no model classification.

This is the **Harnecient Way** applied to multi-agent chat: the model generates text; the app decides who speaks next and what they remember.

### The Relay Integration
- `chat-hai` can be **driven by relay** from h-ai, just like h-ai can be driven by relay from nav.sh.
- A relay command like `nav.sh row 14` (h-ai cell) could cycle to a `chat-hai` sub-mode.
- Or `chat-hai` could be its own cell in the taskbar (cell 15 candidate — see below).

### Model Routing on LAN
```
Mac (10.0.0.144) runs Ollama:
  - qwen2.5:0.5b   (fast small, ~2GB VRAM)
  - qwen2.5:1.5b   (medium small, ~4GB VRAM)
  - qwen2.5:7b     (manager tier, ~8GB VRAM)
  - gemma3:270m    (alt small, ~0.5GB VRAM)

Local livedesk machine calls via:
  curl http://10.0.0.144:11434/api/generate
```

> **Speed logic:** 4x 270m calls in parallel round-robin = ~1-2 tokens/sec per entity, which is fast enough for ambient chat. A 7B call happens every 60 seconds = acceptable latency for a moderator. We do NOT fire 14B/32B locally — too slow, too much VRAM, no benefit for this use case.

## ⚠️ PART IX — RISKS & HOUSE RULES 🚧

### The Looping Death
4 small models in a room will loop. "Yes, I agree." "Yes, I agree too." Forever.
- **Mitigation:** Moderator detects repeat patterns (deterministic: same first 3 words in last 3 messages from same entity → reprompt).
- **Mitigation:** Random topic injection from `hot_topics.txt` when silence or loop detected.

### The Hallucination Cascade
One smol hallucinates a fact → the next smol cites it → the third smol builds on it.
- **Mitigation:** Memories are tagged `SAY` not `FACT`. No entity treats another entity's output as ground truth.
- **Mitigation:** Moderator can flag hallucinations and inject corrections.

### The Token Firehose
4 models chatting forever = infinite API calls.
- **Mitigation:** Hard token budgets per entity per day. Truncate old memory. Priority 0 entries get deleted first.
- **Mitigation:** Smols run at reduced context (last 10 messages only). Only the moderator has long-term view.

### The "Smol Can't Do Tools" Rule
Smols have no tool calls. They only generate text.
- **Mitigation:** If a smol needs to "do" something (write a file, run a command), the **moderator** translates the intent into a deterministic tool call via the same `detect_tool()` pattern used in h-ai. The smol never sees the tool schema. The app does the work.

## 🔮 PART XI — THE ROADMAP BEYOND 🚀

### Near-Term (After Phase 5)
- **Entity movement in the feed:** Smols can "move" between topics (visual metaphor: their message color shifts or a topic tag changes).
- **Voice synthesis:** Each smol has a distinct synthesized voice (local TTS) — the feed becomes an audio experience.
- **Relationship events:** Two high-affinity entities can trigger a "bond" event that writes a new memory type (`BOND`) and permanently shifts their relationship weight.

### Mid-Term
- **External world integration:** Smols can post to pal-chat-irc, read from the events engine, or trigger game events.
- **User-crafted personalities:** The user edits `joints.txt` or uses a GUI to tune an entity's personality weights in real-time.
- **Training data harvest:** Every conversation is a corpus. IQABOD (the local transformer) can eventually be trained on real smol conversations.

### Long-Term
- **The factory pattern:** chat-hai is not just a demo — it is a **productizable conversation engine**. Other apps can embed a "side-chat" using the same entity/moderator/memory architecture.
- **Multi-user:** Multiple humans can have their own "lean-in" moments, each seen as a special user-entity by the moderator.
