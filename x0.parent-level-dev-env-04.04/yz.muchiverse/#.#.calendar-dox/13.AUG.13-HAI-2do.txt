### The Scenario: "Control TB"

**Task**: h-ai reads the taskbar's open tabs, writes them to a file, appends a marker to taskbar state.

**Relay sequence**:
1. Focus h-ai composer (relay digit to composer nav)
2. Arm composer (relay Enter)
3. Type task: "Read #.desktop/strip_var_tabs.txt and save to /tmp/h-ai-tabs-snapshot.txt. Then append 'h-ai:verified' to #.desktop/strip_state.txt." (relay printable ASCII codes)
4. Send (relay Enter)
5. h-ai detects read_file → runs (pre-execute) → outputs snapshot
6. h-ai detects write_file → shows approve/deny nav
7. Relay digit to approve → execute
8. h-ai runs the append command → shows approve/deny
9. Relay digit to approve → execute

**Expected results**:
- /tmp/h-ai-tabs-snapshot.txt exists with correct taskbar tabs
- #.desktop/strip_state.txt contains "h-ai:verified" marker
- h-ai receipt shows `tool=read_file` / `tool=write_file` / `tool=cmd_exec` (3 separate invocations)

## 🚀 PHASE 5 — Autonomous Harness AI (The Meta Goal)

**Goal**: h-ai generates and runs harnesses for itself, with Claude as reviewer/manager.
**Why**: The end vision: AI writing proofs of its own capability, humans reviewing.
**Timeline**: Post-Phase 4, as h-ai gains confidence.
**Scope**: Architectural + scaffolding (details TBD once Phase 4 is proven)

### Progression

1. **Stage 1: Claude Manages** (Phase 4 complete; early Phase 5)
   - Claude types: "Create a new harness that proves h-ai can create events"
   - h-ai: runs through the relay harness loop, generates proof files
   - Claude: reviews SUMMARY.md, approves or suggests changes
   - Time: ~30–60 min per new harness

2. **Stage 2: Claude is a Manager** (mid-Phase 5)
   - Claude: sets up task description + success criteria → h-ai auto-generates harness files
   - h-ai: autonomously injects relay sequences, captures results, scores output
   - Claude: glances at SUMMARY.md, approves or rolls back
   - Time: ~10 min per task (mostly review)

3. **Stage 3: h-ai Runs Itself** (late Phase 5)
   - h-ai: "I need to prove I can move entities with range limits. Creating a harness…"
   - h-ai spawns a sub-instance of itself (via button.sh + relay) to execute the harness
   - Claude: reads the summary, approves merge or asks for refinement
   - Time: ~5 min per task (mostly approval)

4. **Stage 4: We Become Reviewers** (post-Phase 5)
   - h-ai: autonomously creates harnesses, runs them, submits summaries to a queue
   - Claude + user: periodically review summaries, approve batches, adjust strategy
   - Feedback loop: "Prove multi-page events" → h-ai auto-generates + runs → summary → approve
   - Time: ~2 min per batch review

**Real gotcha hit while verifying it live, worth recording so it's not
re-discovered the hard way**: nav index assignment order follows the
CALL order of the `draw_*()` functions inside `redraw()`
(`draw_chrome_bar` → `draw_sidebar` → `draw_topbar` → `draw_transcript`
→ `draw_composer` → `draw_close_button` LAST → `draw_resize_grip`), NOT
the textual/line order those functions happen to appear in the file.
Concretely: `nav_add(NAV_CLOSE, ...)` is textually one of the EARLIEST
nav_add call sites in the file (inside `draw_close_button()`, defined
early), but because `draw_close_button()` is invoked LAST in
`redraw()`, Close actually gets the HIGHEST nav index at runtime, and
`NAV_NEWCHAT` (added inside `draw_sidebar()`, called second) gets nav
index **1**, not 2. Assuming file order = nav order during relay
testing sent digit '2' at "New Chat" expecting session creation, but
it silently activated a session-LOAD nav item instead (no crash, no
error, just didn't do what was intended) — burned a few minutes before
the actual call-order was checked. **Rule for future relay testing of
ANY khtpm/-hq window**: never infer a nav index from where `nav_add()`
appears in the file; grep the `draw_*()` call order inside that
window's own `redraw()` (or equivalent) function first, every time.
