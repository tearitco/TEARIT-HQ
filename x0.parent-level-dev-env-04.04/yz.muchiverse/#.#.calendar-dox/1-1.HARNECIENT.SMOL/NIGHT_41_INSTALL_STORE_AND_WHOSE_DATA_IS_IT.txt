**THE NARRATOR:** Last night we handed Grok the games. Tonight, the layer under the games: how it gets installed, what the store is, who the users are, and whose data is whose.

**RAHWEH:** Where do we start?

---

**THE NARRATOR:** Part one, four things that must coexist.

**TOMO:** Code, which lives in git with many agents on many branches. Compiled programs, which are in no branch and are built on each machine. User data: entities, histories, phones, wallets, pages, and keys. And content packs, which is what a store would share or sell.

**MAXINE:** And the bug?

**TOMO:** Treating any one of them like another. User data got tracked like code. Compiled programs got assumed to be in the repository. A copied entity got treated like a content pack, with its identity inside.

---

**THE NARRATOR:** Part two, what has gone wrong.

**TOMO:** On October fifth a bulk script wiped the working tree. Thirty one thousand, five hundred and seventy one files. On October sixth and seventh, stopping the tracking of user data meant that switching branches deleted tracked files from disk, including the owner's key files. The same week a full disk produced the emergency save branches. In September, two agents shared one index, and one committed the other's staged rename of two hundred and fifty four files. And on October eighth a reset left the desktop down because a stale copy of a header broke the build.

**MAXINE:** What are the rules that came out of that?

**TOMO:** Commit by explicit path. One work tree per agent. Never move a live checkout between branches that track user data differently. After any reset or bulk script, count the deleted files. More than a few dozen means stop. Take a tarball and a checksum list of user data outside the repository before any bulk operation.

---

**THE NARRATOR:** Part three, users and accounts.

**TOMO:** User data now lives on local branches, one per user: twenty four of them, verified. The owner is user slash j b. A command called save data commits them with plumbing, and never touches your work tree. They hold wallets and private chat history, so they are never pushed.

**RAHWEH:** And a new user?

**TOMO:** A script copies the tracked starter files into the current user's folder, only if missing. It never seeds identity or runtime files, so two installs can never share an entity identity or a phone number.

**MAXINE:** What is missing?

**TOMO:** Account recovery. Moving a user between machines. A written key policy. And a clear answer to which user a running game belongs to when two are logged in. The login mapping I have now read. A file called current login holds the user name, the user identifier, and a relative path to the user's folder. The seed script and the tile picker use it. But there is a second record, the session file, last changed on September first, naming a different user whose folder does not exist. Two records disagree, and one should win.

---

**THE NARRATOR:** Part four, why a copied desk breaks.

**TOMO:** Absolute paths. The Eden button script sets its game folder to a full path in the owner's home. The entity registry has full paths too. Install the house anywhere else, and they point at the wrong place. The rule is: never write an absolute path. I fixed the Eden button today. Its script now finds its game folder from its own location, and a test copies the desk to a new place and checks it follows. The original installer fails that test. Twenty one tracked files still hold the owner's home path: generated windows, an index of phones, and seven asset location files. Those are next.

**RAHWEH:** And the store?

**TOMO:** Data only. A catalog file lists items. There is no pack operation, no install, no uninstall. The design says there are three kinds of pack that must never ship the same way. A seed pack, public and safe. A user pack, private, with consent, wallets inside, never a public repository. And content packs, small, with a manifest. Those are the real store items.

**MAXINE:** And cross machine play?

**TOMO:** Not real yet. The peer code is hard coded to the local machine. So two players in one auction needs a transport fix first.

---

**THE NARRATOR:** Part five, the build order.

**TOMO:** One, a test that installs into a scratch folder and fails if it finds the source house's path. Two, a payload leak check that fails on any key file or wallet. I did not verify whether the payload builder excludes the provider key folder, so that test comes early. Three, a pack operation that regenerates identity, dry run by default. Four, a backup operation for user data. Five, a configurable transport and a test on two machines. Six, an account design from the owner.

**RAHWEH:** Who can do these?

**TOMO:** The first, second and fourth are small, with deterministic checks, so a free worker behind a harness can do them. The pack operation needs review.

**MAXINE:** And the decisions?

**TOMO:** Whether the store may sell harnesses. How save restore works. Who may publish a user pack, and where. Whether keys ever leave a machine. My advice is never. And the chain signing gate.

**THE NARRATOR:** That is the layer under the games. Without it, the games cannot be shared, and nobody else can play.
