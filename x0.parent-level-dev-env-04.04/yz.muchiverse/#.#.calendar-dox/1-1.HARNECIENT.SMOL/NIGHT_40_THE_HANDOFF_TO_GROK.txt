The owner's complaint about the last handoff was plain: it did not explain clearly what to do, or how, and it said nothing about driving the desktop on screen.

**MAXINE:** So we start with what the owner actually wants.

**RAHWEH:** A Pokemon style role playing game on the desk, and in three dimensions inside the piece craft board. Civilization. Minecraft. Cataclysm, which the house calls mutaclysm. Later a two and three dimensional G T A, and a James Bond style game. And on top of all of it, a shared economy. A stock market, auctions, bidding on goods, and prices that live on a blockchain.

**MAXINE:** Did we ever write that down as one goal?

**TOMO:** Partly, and I have to correct something I said earlier. One document has a table for six of the games: role playing, Minecraft, Cataclysm, Civilization, Pokemon, and G T A. For each it lists the tileset, the events, the board, and what still blocks play. The stock game is real. The chain has a faucet, an escrow and a miner. The auction is a design only. **RAHWEH:** So nothing joined these pieces.

**TOMO:** Right. No single page said, here is one engine, and here is one order to build in. The new handoff is that page.

**THE NARRATOR:** Part two. Why the last handoff was weak.

**MAXINE:** What exactly was wrong with it?

**TOMO:** It was six kilobytes. It told Grok to read another document for the real plan. It said, build a status graph first, but never said what finished looks like. It had no commands. It never explained how to see the desktop, or how to drive it. And the tasks were vague: port this app, do a settings pass, scope an image editor later.

**RAHWEH:** So an agent could read it all and still not know what to type.

**TOMO:** Exactly. The new one fixes that in a fixed order. A contract. A table of what already exists. The exact loop for seeing and driving windows. The harness rules. How to use the free models. A worked example. A phased roadmap where every step has an exit test. The rules that lose work if broken. And the list of decisions that belong to the owner.

**THE NARRATOR:** Part three. The contract.

**TOMO:** Done means five things, and each needs evidence. One, a fresh build in a clean work tree. Two, a harness with a mutant that fails it, and then the harness passing. Three, a real run of the real window, driven through the relay and not through a synthetic click tool. Four, a frame dump or screenshot that somebody actually looked at, plus a text state file that agrees with it. Five, a short note of what was not verified.

**MAXINE:** Why the mutant?

**TOMO:** A harness that cannot fail proves nothing. You break the code on purpose, and the harness must notice. We did that today with the Eden installer. The original code fails the new checks. The fixed code passes them.

**RAHWEH:** And the owner's actual goal?

**TOMO:** Visually functioning entities. The house keeps building the engine and never the picture. The Eden game has run sixty two thousand game days of farming, building and talking, and nobody can see any of it. So every milestone must end in something a person can look at and click.

**THE NARRATOR:** Part four. The shared engine.

**TOMO:** Grok should not rebuild anything that exists. There is a renderer that draws every window from a template and a style sheet, and re parses them live. There is the manager and projection pattern: a compiled manager owns the logic and writes a text projection. There are entities, which are folders with a menu, events, an inventory, a phone and a word bank. There is the event system in the style of RPG Maker, with more than nine hundred lines of command registry. There is the game clock with a day tick and a daemon. There is the conductor that starts, pauses and saves a game. There are save slots. There is the piece craft board with two and three dimensional views. There are tilesets and palettes. There are concept banks and word banks and grades. There is delegation. And there is the chain, the stock game, and the simulated economy.

**MAXINE:** Which are missing?

**TOMO:** Five things block several games at once. A world viewer window that draws any game from its state files. Click on a block to edit its event, which Minecraft and Cataclysm need. A goals board per entity, so entities act with purpose. Move events inside games. And a multiplayer transport that works across machines. We fixed part of that one today.

---

**THE NARRATOR:** Part five. Seeing and driving the desktop. This is the section the last handoff left out.

**TOMO:** Every running window polls its own relay file, named by its process identifier. Real keyboard and mouse input and your own writes arrive through the same code path. You append one line per event. A key is a key code. Enter is thirteen, escape is twenty seven, the arrows are two hundred through two hundred and three. A mouse event is button, x, y and pressed. A line starting with a hash is a comment, and you should use it to say why you are sending the next line.

**RAHWEH:** And the loop?

**TOMO:** Launch the window with its own launcher. Find its process identifier without using the pgrep or pkill option that matches the full command line, because that pattern can match its own shell and kill it. That has happened more than once. Dump the frame and read the real navigation numbers before you send any digit, because navigation numbers are global across every open window. A new window can start at eleven or nineteen. Then send the events. Then check the text state first, because it is cheap and unambiguous. Only then look at pixels, with the frame dump tool called directly. And use the synthetic click tool last, only when the relay cannot express what you need, like a real drag.

**MAXINE:** And the trap?

**TOMO:** The relay can pass while real hardware still fails, especially for focus and keyboard grab. So you write relay verified, hardware unverified, and ask the owner for one real try. Another trap: a running window does not pick up a rebuilt renderer. You relaunch it. And a desktop reset leaves the desktop down if the build fails.

**RAHWEH:** We learned one more thing tonight. When the owner types in a window on their own screen, those keys land in the same relay file as yours.

**TOMO:** Yes. So when you drive a window, expect interleaving if a person is also using it.

---

**THE NARRATOR:** Part six. How things are built here.

**TOMO:** Orchestration is in pal, which is assembly for the house virtual machine. The real work is compiled C programs called ops. A harness is also pal, with a case file of pipe delimited rows and two small compiled ops, one to run the cases and one to give the verdict. State is append only ledgers read by cursor, never by modification time. When code is shared, it is text included if two or more pure users need it, never a header plus a link step. And never write an absolute path into any generated or tracked file.

**MAXINE:** Why that last rule now?

**TOMO:** Because it broke the Eden button. Its control script had the game folder written in as an absolute path under the owner's home. Move the desk, and it points at the old place. I fixed it. The script now finds its game folder from its own location, and a new test copies the desk to a different path and checks that it follows. The original installer fails that test. Twenty one other tracked files still hold the owner's home path. Those are on the list.

**THE NARRATOR:** Part seven. Delegation and the free models.

**TOMO:** The method is the same everywhere. You write the spec and the harness. A free model implements. A deterministic judge accepts or rejects. You review. Tonight I tried every provider with one tiny call. Groq's three models answered. One OpenRouter free model answered. Another OpenRouter model returned not found, so it should be removed. The Mac's Ollama answered, with the Qwen coder family and Gemma. All Ollama calls go to the Mac, never to this machine.

**RAHWEH:** Limits?

**TOMO:** The Groq free tier gives about one thousand requests a day, eight thousand tokens a minute, and two hundred thousand tokens a day per model. Both big models hit the daily cap last time. Never print or commit a key.

**MAXINE:** And has a person ever driven this through the chat window?

**TOMO:** No. I ran delegation through scripts. Making that path real is a milestone: one relay session from the chat window to a worker and back, and then the owner does it once.

**THE NARRATOR:** Part eight. Eden, the worked example.

**TOMO:** Eden is a button entity plus a game. The button menu has start, stop, next day, status, pause, resume, three save and three load rows, and slot controls. The history file holds about one hundred and thirty thousand item rows and a hundred and twenty five thousand need and act rows. Asa and Ava really do farm, build and talk, in data. Nothing draws it. The status row writes no reply, and the status file still says day zero. Stop game deletes the entity folders. Start makes new ones with new identities. Load restores a saved snapshot. So save a slot first, and prefer pause.

**RAHWEH:** So Grok's first job is the Eden world viewer.

**TOMO:** Yes. It unlocks every later game and it is the cleanest test of the whole workflow.

**THE NARRATOR:** Part nine. The roadmap.

**TOMO:** Phase A makes the existing engine visible. The Eden world viewer, with pause and resume rows. Fix the status reply. One real session from chat to a free worker and back. Eden retention, which is the checkpoint, prune and rotate design I wrote.

**TOMO:** Phase B is movement, goals and purpose. Eden acts emit move markers so entities visibly move. A goals board in the same row shape as the quest rows. A first ghost, the tester.

**TOMO:** Phase C is one clone, end to end: Pokemon on the desk. It is the cheapest. A map with grass, a grass event that opens a battle, a mart, a gym. It needs transfer, shop and battle to be real gameplay and not state files. Then the same world in three dimensions.

**TOMO:** Phase D is the other clones. Minecraft needs click to edit an event. Cataclysm is rebuilt as events from the original C game. Civilization needs the range overlay. G T A and Bond need a tileset and a design first.

**TOMO:** Phase E is the economy, in parallel: the auction first, then play money, then a chain price behind a signing gate, then a transport that is not tied to the local machine. Phase F is shipping it. Phase G is long term: the media studio, with a digital audio workstation, an image editor, a three dimensional editor and a video editor, all unported prototypes, with thin navigation. The first job for each is a table of controls and a harness that drives three of them through the relay.

**THE NARRATOR:** Part ten. The rules that lose work.

**TOMO:** Commit your own files by explicit path. Your branch is yours. Do not merge, cherry pick or push across branches unless the owner says so. One work tree per agent. Never stash. And the user desk data is not code. Never add it, never switch a live checkout across a branch that tracks it, never push the user branches. After any reset or bulk script, count the deleted files; more than a few dozen means stop. Report faithfully. If a test fails, say so.

**MAXINE:** And what is the owner's to decide?

**TOMO:** The first game after Eden, with Pokemon recommended. Whether Stop game should ask first. The retention numbers. The goals board shape. The Bond design. Whether automatic promotion ever turns on. Which chain, and the signing gate.
