**RAHWEH:** Say why that's not a small style complaint.

**MAXINE:** So what replaced it, concretely, on disk, tonight.

**RAHWEH:** Two compiled ops and one `.pal` file. `move_entity_init.+x` reads the current position, snaps it to the desk grid, clamps it to the screen, computes waypoints, writes them to an append-only ledger, and launches `move_entity.pal`. `move_entity_tick.+x` gets ticked by that loop — same shape as `world_manager.pal` already used — and consumes exactly one waypoint per tick, cursor-based, never re-reading old lines.

**TOMO:** And it still broke the first time it ran for real, which is the part worth keeping.

**MAXINE:** Say it.

**TOMO:** First fix made the tick op kill the live entity process and relaunch it fresh at every waypoint — same idiom the shell version used, just correctly confirmed-dead this time instead of a blind kill and a fixed sleep. The entity's own event loop polls that marker's size — never mtime, the house already knows why — and moves itself with one `XMoveWindow` call when it changes.

**MAXINE:** And a third bug, smaller, but worth naming because of what it reveals.

**TOMO:** `move_entity.pal`'s own `sleep 90` line. Read as ninety milliseconds, matching the doc comment on `world_manager.pal`'s identical-looking `sleep 16`. The entire waypoint queue drained in under a millisecond — looked like an instant jump, not an animation. `world_manager.pal`'s own `sleep 16` is very likely the same thousand-times-too-fast, undiscovered, because nobody happened to be staring at that exact loop today.

**RAHWEH:** Say why that detail belongs in a vision night at all, instead of a bug-log line.

**TOMO:** Because it's the same lesson NIGHT 22 already learned from a stale binary sitting next to its own fixed source — a documented claim and the actual running code had quietly drifted apart, and nobody would know without opening the real file and reading the real number. **THE NARRATOR:** One more correction from tonight, smaller, but it's the one that sets tonight's actual rule for how code gets organized going forward. Say it.

**RAHWEH:** Say the rule that leaves behind, because it's the rule tonight's whole vision runs on.

**MAXINE:** Exactly one real consumer — the code lives in one file, plainly, no split for its own sake. Two or more real consumers, pure logic, no I/O — a real text-included `.c`, the house's own already-accepted pattern. Two or more real consumers, anything stateful or process-shaped — a separate compiled op plus fork, exec, and file-backed IPC. Never a header-and-link split for in-house code. Three shapes. No fourth.

**THE NARRATOR:** Now the part that has to be built carefully in this room tonight, the way NIGHT 22 built hub-and-spoke carefully in its own room. Say the naive version first, and say why it's wrong before it gets corrected.

**RAHWEH:** Mini-bot creation. A "bot DNA bank" — one Concept Bank per creature or bot instance, its own spokes, its own weights, its own trait genome, same record shape NIGHT 22 already specified. Naive version: every new bot gets its own fresh, fully-populated Bank, disk and memory sized the same as every other one.

**MAXINE:** Say the actual problem with that before it gets built on.

**RAHWEH:** Scale. A thousand terumon, each with their own full Concept Bank, means a thousand nearly-identical copies of the same spoke weights — most bots that share a species, or a starting curriculum, converge to near-identical trait patterns almost immediately. Storing each one in full is storing the same information a thousand times, and worse, means a real improvement discovered by one bot's promotion ledger doesn't help any of the others unless it's separately re-discovered in each one.

**TOMO:** So say what replaces it.

**RAHWEH:** Compaction. Trunking. A shared TEMPLATE bank per real cohort — species, curriculum, whatever the actual grouping turns out to be — holding the common spoke weights. Each individual instance holds only a DELTA bank: the slots where it genuinely diverges from its template, same sparse-storage discipline NIGHT 22 already specified for a single bank's own mostly-empty slots, just one level up. Reading an instance's real, effective weight means resolving template plus delta, the same two-step resolution a spoke's own forward record plus a master's derived mirror table already uses.

**MAXINE:** Say the part that makes this not just compression for its own sake.

**TOMO:** A promoted improvement can be written to the TEMPLATE once, and every instance still holding no delta at that slot inherits it for free, immediately, without re-running its own promotion ledger from scratch. That's the actual payoff — not disk savings, propagation. One terumon's genuinely earned insight becomes every other same-species terumon's starting point, the moment it's promoted, the same way NIGHT 22 already wanted one feedback signal to propagate across FSM, GOAP, and RL at once. This is that same propagation, applied across population instead of across subsystem.

**RAHWEH:** And the failure mode to name honestly before it's ever built, the way NIGHT 22 named its own open corpus-meta-weight question honestly instead of quietly deciding it.

**TOMO:** When does an instance's delta grow large enough that it should split off and become its own template — a genuinely new sub-species, not just individual variance? Unresolved. Could be a fixed delta-size threshold. Could be derived from how much of the delta actually gets independently re-confirmed by promotion, the same evidence-based instinct the rest of this whole pipeline already runs on. Say it plainly: not decided tonight. Whichever way it resolves, it's the same shape as every other open question this substrate has produced — a number, or a mechanism to compute the number, sitting on top of a design that doesn't change either way.
