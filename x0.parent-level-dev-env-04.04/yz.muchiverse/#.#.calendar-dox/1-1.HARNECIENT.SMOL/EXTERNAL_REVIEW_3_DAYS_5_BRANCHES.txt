3. HORN_CHAT IN DETAIL (the reviewable engineering)
--------------------------------------------------------------------------------

3.1 The security model is the part to review hardest
----------------------------------------------------
This is the section where a reviewer should be most sceptical and most
useful, because a model with write and shell access is a genuinely dangerous
thing to hand to a program that reads whatever files it is pointed at.

THE ALLOWLIST. tools/horn_tools.json maps a tool name to the op that
executes it. ops/horn_tool_exec.c refuses any tool not in that map. A
hallucinated tool name becomes a refusal, never a process launch. Adding a
tool needs no C: drop a binary in ops/+x/, name it in the map.

  Six tools: list_dir, read_file, grep_files (ungated, read-only);
            edit_file, write_file, run_script (approval-gated).

THE APPROVAL GATE. Ported from gem-dev's ops/src/cmd_exec.c, which the
house already had and which an agent initially and wrongly claimed did not
exist. Deny is the default; a 60s timeout is also a deny, because silence
must never be read as consent. config/yolo.flag arms auto-approve, same
mechanism and same path as gem-dev.

  One adaptation, stated plainly: gem-dev reads y/n from stdin because its
  exec is foreground. HORN's terminal belongs to the chtpm window, so the
  prompt renders in the window and the answer returns through the window's
  own key path (gem-dev's own <button onClick="KEY:n"> mechanism). The gate
  list and the allowlist live in ONE file so that the single edit a model
  could make to escalate — add a tool, drop it from "gate" — is in one
  reviewable place.

SANDBOX (run_script). bwrap, verified live on this box:
  --ro-bind / /          whole filesystem read-only
  --bind <proj> <proj>   except the project, writable
  --tmpfs <house>/&.widgits   BLANK — this is where every provider key
                                lives, and it is a SIBLING of the project
  --tmpfs /root /tmp     no shell rc files; scratch that cannot outlive
                         the command
  --unshare-net          no network: stops a read tool becoming an
                         exfiltration channel
  If bwrap is missing the tool REFUSES rather than falling back to an
  unsandboxed shell.

  Verified: parent-dir write refused, /etc write refused, DNS blocked,
  provider key unreadable from inside, project write allowed.

WRITE CONTAINMENT. Confined to the project root, lexical (not realpath)
normalisation so a symlink cannot escape, denied paths explicit:
  .git  chats  pieces  system  ops/+x
  tools/horn_tools.json   <-- THE ALLOWLIST ITSELF
  any key-shaped file (*api_key*, raw_*, *.pdl)
Writes are atomic (temp + fsync + rename). Directory creation is refused.

  >> REVIEW THIS: writing the allowlist must not become possible. It is
  guarded by path_deny(), which is C code, not manifest policy. That is a
  deliberate choice (a manifest cannot reliably forbid editing itself) and
  it means the guarantee lives in one function you should read.

4. THE PROCESS PROBLEMS  (the most important section)
--------------------------------------------------------------------------------

4.1 The CPU-safety documentation was not read, and four rules were broken
------------------------------------------------------------------------------
House docs that existed, are short, and were directly on point:
  03-pitfalls/hq-cpu-safety.md
  06-testing/CPU-AND-SESSION-SAFETY.md

Four violations, in the agent's own code, all now fixed and MEASURED:

  (a) IDLE CPU. horn_publish_pending ran on EVERY tick of the pal loop,
      opening and reading two files per tick to discover there was nothing
      pending. This is the exact shape hq-cpu-safety.md 3c names: "an
      expensive function called unconditionally inside a tick loop, with no
      gate at all".
      Measured with the four CPU fields the doc specifies (utime+stime+
      cutime+cstime — the ones ps ignores by default):
          before  1.48% of a core, idle
          after   0.56% of a core
      The house's own prior incidents were 12% and 5%, so this sat below
      the alarm line and was still the wrong shape. "Below the alarm line"
      is not a defence; the doc's rule is about shape.

  (b) KILLING THE USER'S OWN SESSIONS. horn_chat.sh cleanup ran
        pkill -9 -f "keyboard_input"
        pkill -9 -f "./system/renderer"
      BOTH ARE HOUSE-WIDE NAMES. pieces/system/input_dispatcher/plugins/
      keyboard_input.c and pieces/display/renderer.c are core house
      binaries shared across every project in the tree. Running that
      cleanup while the user had another project's window open would have
      killed it. CPU-AND-SESSION-SAFETY.md: "Never touch the user's own
      live testing sessions."
      Now every kill is `ps` + grep on THIS PROJECT'S ABSOLUTE PATH +
      `kill <pid>`.

  (c) ASSUMING pkill WORKS. Same doc: "pkill may be sandboxed/blocked in
      some environments (every invocation can return non-zero regardless of
      pattern)". The old teardown treated pkill's exit status as success.

  (d) UNBOUNDED TEST, NO REAP. "Every automated test must be
      timeout-wrapped" and "timeout does not reliably kill backgrounded
      children ... verify no leftover process afterward". e2e.sh had
      neither. This was the actual mechanism by which orphan processes
      accumulated: interrupt a run, leave a live parser + renderer +
      keyboard_input + pal loop behind. Two were later found alive at 2.4
      and 2.6 hours, reparented to init.

  >> The pattern worth naming: the agent worked from ONE relevant document
  (the J2 input-injection testing guide) and treated it as sufficient. It
  was not. Reading a relevant doc is not the same as reading the relevant
  docs.

Two horn_turn processes survived 2.4 and 2.6 hours with every wait in the

>> If you take one action from this document, take this: verify the orphan
   fix before trusting it. It is the one safety mechanism that is believed
   rather than demonstrated.

4.3 The "green but skipping" failure mode
------------------------------------------
Twice, the suite reported success while silently not testing the important
part:

  - api_available() judged the provider probe by exit code 0 only. Since
    tools were added, models often answer a probe BY ASKING FOR A TOOL
    (exit 10), so a perfectly healthy provider read as unavailable. Every
    live assertion skipped; summary still green.

  - a sandbox test asserted on `head -c 30` of an error message, cutting
    off the very words it was grepping for. It "failed" while the sandbox
    was working correctly.

>> For a reviewer: this is the most transferable lesson in the package. A
   skip and a pass print the same character. Ask what ran, not what the
   exit code was.

4.4 Bugs found only by running, not reading
--------------------------------------------
Roughly a dozen defects were found by execution after passing review. Three
worth naming because they are the kind that survive careful reading:

  - `--ro-bind /` pushed with ONE slash. --ro-bind takes source AND dest, so
    every subsequent argument shifted by one and bwrap tried to exec the
    project root as the command. A shell bisect of the identical flags
    PASSED THE WHOLE TIME, because the shell version had both slashes. Only
    strace found it.
  - `asprintf(&out, ...)` on a `char *out` PARAMETER wrote through the
    local pointer and never filled the caller's buffer, so write_file
    reported "file does not exist" for files that plainly existed.
  - A background publish was SILENTLY EATING WHATEVER THE USER WAS TYPING.
    state_changed.txt growth forces chtpm to re-parse the layout, which
    empties the active cli_io buffer; its sync then skips the active element
    so it is never refilled. Found only by sampling gui_state and the
    rendered frame together — gui_state still said "Hi" while the box was
    empty, which proved render regression rather than lost keystrokes.
