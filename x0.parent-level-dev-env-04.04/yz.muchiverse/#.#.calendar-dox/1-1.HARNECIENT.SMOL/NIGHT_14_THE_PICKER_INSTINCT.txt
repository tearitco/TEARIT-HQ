**MAXINE:** Recap first, plain. Three real things landed on top of NIGHT 13's step 1 (one sidebar row, one read-only viewer).

**TOMO:** One - the FSM viewer stopped being a raw text dump. cursword's `fsm_table.pdl` now draws as real bordered "scratch blocks," one per state, each showing its own real NEXT= edges, the live-running state highlighted in a different color. Same visual family as events-hq's own Scratch view - not invented, reused.

**RAHWEH:** Two?

**MAXINE:** A real `<tabbar>` - Viewer, New State - h-ai-lab's own already-proven action-plus-var mechanism, not db-hq's older bespoke embed logic. And three: "New State" itself, which went through two real shapes before landing on the right one.

**THE NARRATOR:** Tell the two shapes. The failure is as much the lesson as the fix.

**TOMO:** Shape one: a single `cli_io` field, type `name` or `name|NEXT1,NEXT2`, Enter to submit. Built to dodge a real, separate bug - arming a second field silently wiped whatever the first one held - so ONE field, comma-parsed, was the honest fix for THAT bug. It worked. It was also, on its own terms, a bad interface: a human typing exact existing state names into a comma list by hand, no validation, no picking, one typo from silently creating a dangling edge.

**RAHWEH:** And the direct question that ended it?

**MAXINE:** "It should have same kind of setup that add commands from events has, right?" Yes. events-hq's real "+ Add Command" is a PICK from a real list - the registry's own command types - never typed free text for anything with a closed, real set of choices. A state's NEXT targets are exactly that closed set: the fsm's own other STATE rows. Typing them was always the wrong shape; events-hq already had the right one, sitting one tab over.

**THE NARRATOR:** So the rebuild.

**TOMO:** Same two-stage shape events-hq's picker uses end to end: a name field stays typed - a BRAND NEW state genuinely has nothing to pick from yet, same honest reasoning events-hq's own field editor uses typed `cli_io` for genuinely free-text params - then a real, toggleable list of the fsm's own existing states, click to mark a NEXT target, `[.]`/`[x]`-style, Save commits, Cancel discards. Backend: four new small verbs in `ai_lab_scan.sh` - open/name/toggle/commit - state living in its own one-writer-per-file markers, same convention `selected.txt`/`view_mode.txt` already used.

**RAHWEH:** Was it clean the first time?

**MAXINE:** No - and worth naming honestly, since this whole track only means something if the failures are on the record too. Three real bugs, live-caught, in order: a bare item sitting after the panel's first `<scrolllist>` got swept into the wrong scroll region entirely, scrambling the whole render order - db-hq-pal's own working picker never hits this because its Cancel/fields are always nested INSIDE their scrolllist, never siblings after it, so that's the fix that carried over. Then: two real scroll regions ended up live at once because the new picker's `show=` flag wasn't ANDed with the tab that was supposed to gate it - this panel's layout only tracks one live scroll region at a time, and having two silently blanked one's row text while still numbering it. And under both of those, the actual root cause: `<repeat bind="pk">` expands `${pk.name}` to a var named `pk_N_name`, but the backend was publishing `as_pick_N_name` - a plain prefix mismatch, invisible until you go looking, because the nav badges show up fine either way; only the label text goes blank.

**TOMO:** Fixed by making the bind name literally equal to its own backend var prefix - `bind="as_pick"` - the exact convention the already-working `inst` and `block` repeats elsewhere in this same file already followed without anyone having named the rule out loud until it broke.

**THE NARRATOR:** Verified how?

**RAHWEH:** Live, not assumed. Opened the picker on cursword - a real, existing fsm instance, not a mock. All eleven of its real states appeared as toggle rows. Clicked OFFER, watched its own mark flip and its own `_on` flag flip in the published state file. Then called the backend commit directly and watched it append a real `STATE | ... | NEXT=OFFER` row matching that exact toggle, before cleaning the test row back out.
