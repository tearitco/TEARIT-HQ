How to actually use the house

Muchiverse House — User Guide

Start the desktop, use every taskbar feature, run a window headless for testing, and hand scoped dev work to an AI agent without re-explaining the house each time. The niche stuff is here too — the cli terminal mirror, running IRC/chain from many ports, the marker-file rule. Companion to the Browser Prompting Guide (agent-delegation focused) and the House Docs (architecture).

Two paths through this

Using the house: sections 1–5. Developing it (yourself or via an agent): sections 6–7. Everything is file-driven — no hidden state — so the same mechanisms serve both.

1 · First run

The house is a real X11 desktop shell. You need a running X server (a Linux desktop session; DISPLAY defaults to :0). macOS and Windows have their own start scripts ($.crypts/mac-start-livedesk.command, $.crypts/win-start-livedesk.ps1).

Build & start

From the house root (…/yz.muchiverse/44.xyz.01.00/):

# build the launcher + the taskbar/renderer binaries
$.crypts/button.sh compile
sh "*.monads/*.livedesk-taskbar/ops/build_khtpm_strip.sh"

# start the taskbar + autostart entities
$.crypts/button.sh run          # or:  ./^.START_BUTTON_4.sh
button.sh verbwhat it does
run (aka r, start, restart)launch the taskbar + everything in $.crypts/autostart.pdl. Safe to re-run.
resethard kill every house process, rebuild the renderer, relaunch. Use when something is stuck/orphaned.
quit / closekill all taskbars + entities, no relaunch.
on / offtoggle whether autostart runs at all (edits autostart.pdl).
install-xdgregister button.sh run as a GNOME login autostart.
status / checkshow enabled state + running house PIDs / verify the launcher built.
If a window won't open after a code change

Running khtpm windows do not hot-reload a rebuilt binary — relaunch them (or button.sh reset). A rebuild only affects windows opened afterward.

First login

The house has real per-user state under xyzfs/users/<uuid>/ (home, avatars, livedesk layout, pals). The User taskbar cell → New User / Switch / Logout; signup-hq (first-cut) is the fuller flow. Your private key lives at xyzfs/users/<uuid>/…/priv.*.txt and is git-ignored — never commit it.

The HQ button menu

Every window has an HQ button (top-left). Its menu: always-on-top, restart, hide/show, dir, quit, settings, stats, cli (§3), cursword, kill, debug. Mostly window-chrome actions.

Driving nav

Arrow keys move focus; typing a number jumps to that nav index (multi-digit accumulates); Enter activates; Esc closes a dropdown or clears the digit buffer. Nav numbers are global across all open khtpm windows — a fresh window can start at nav 11, not 1. Always read the actual rendered number before relying on it.

3 · The cli terminal mirror

HQ button → cli opens a terminal that is a live, bidirectional ASCII render of the taskbar strip. Drive the strip with the mouse and the terminal follows; press arrows / digits / Enter in the terminal and the real strip follows. Useful for testing and for driving the house over SSH.

  • It runs two small binaries (a presenter and a raw-keyboard relay) — never combined, because raw terminal mode would staircase the output.
  • Updates are marker-driven at 60 Hz (a file whose size grows one byte per frame) — the same discipline as the original TPMOS renderer. No polling on timestamps.
  • The same treatment for any window (not just the strip) is §6.

Ports & P2P

Peers (palnet_peer.+x) bind from base port 9950 and scan forward, so multiple nodes on one machine each get a distinct port automatically. Presence files under $PRISC_NET_ROOT/ advertise port=. Verified: two chain nodes on :9950 / :9951 reconciled a 16-block mine A→B over the mesh. To test many nodes, launch each with its own PRISC_PROJECT_ROOT / PRISC_NET_ROOT and read each one's state files (§6).

6 · Headless / dev testing

Every khtpm window — the strip and every other window — writes a live text mirror of itself and reads keystrokes from a plain file. That is the whole test surface: no screenshots, no xdotool.

The strip: open_cli.sh

*.monads/*.livedesk-taskbar/ops/open_cli.sh — the cli HQ-menu row (§3) as a standalone script.

Any window: open_window_cli.sh <pid>

Same dir. Attaches a presenter + keyboard terminal to an already-running window by its renderer PID (pgrep -f khtpm_core_render).

Headless: window_headless.sh

$.crypts/scrypts/headless/window_headless.sh — the headless entry point. ($.crypts is the house's session-script area; per-window helpers stay in the taskbar ops/ dir.)

$.crypts/scrypts/headless/window_headless.sh \
    <house_root> <window.xhtpm> [x] [y] [--attach]
  • No DISPLAY, no Xvfb. --headless opens no X connection at all — it runs the real layout with estimated text metrics and loops writing the text frame. Works over plain SSH / in CI.
  • Run the binary directly with env -u DISPLAY khtpm_core_render.+x --headless <house> <window.xhtpm>.
  • --attach also runs the live viewer + keyboard in your current terminal.
  • Verified on taskbar-settings, events-hq, irc-chat-hq and strip mode. Text widths are estimates, so a pixel-exact wrap point can differ from the windowed path — the mirror shows structure and nav, not geometry.

It prints PID=<n> and the two paths:

frame : #.desktop/ascii_frames/<pid>.frame.txt     # cat it — the live window as text
relay : #.desktop/entity_menu_history/<pid>.txt   # append one line per event

# examples
cat "#.desktop/ascii_frames/$PID.frame.txt"
printf 'KEY_PRESSED: 201\n'      >> "$RELAY"   # Down   (200 Up, 202 Left, 203 Right)
printf 'KEY_PRESSED: 13\n'       >> "$RELAY"   # Enter  (27 Esc, 8 Backspace, 9 Tab)
printf 'KEY_PRESSED: 65\n'       >> "$RELAY"   # a literal 'A' (any 32–126)
printf 'MOUSE_EVENT: 1 40 12 1\n'>> "$RELAY"   # left-click at x=40 y=12
Many windows at once

Call window_headless.sh once per window. Each gets its own PID-keyed frame / pulse / relay triple, fully independent — this is how you run IRC + chain from several ports and watch them all.

The relay file is append-only and cursor-based — never truncate it; a line starting # is an ignored audit comment. The <pid>.pulse.txt marker grows one byte per repaint; that is the change signal (never the frame file's timestamp).

7 · Prompting an AI agent for house dev

Hand an agent (Claude Code, Grok, a browser window) a scoped task without it re-deriving the house. Attach the right doc, state the rule, point at the sibling that already works.

Always attach / state

  • 02-architecture/CENTROID_GOLD_STD.md — the rendering architecture. Non-negotiable: one shared renderer, a compiled manager per app publishing plain text, zero new per-app C, static .xhtpm parsed through the real pipeline (never hand-build the element tree).
  • 02-architecture/reference/TPMOS-DIAMOND-render-chain.md — the "DIAMOND standard": change-detection is an append-only marker file's size growth, never mtime. Input handlers write the marker; they never call the composer directly.
  • 10-user-docs/FEATURE-CATALOG.md — what already exists and its status, so nobody rebuilds a shipped thing.
  • Testing: drive windows through the per-PID relay file (§6), not xdotool/XTest. Dump/read the text frame or a manager's *_ui.txt to verify.
  • Git: commit only to your own branch; stage explicit paths (never git add -A); don't touch main or another agent's branch; runtime state files are never committed.

The single most common failure

An agent rebuilds something that already exists (a hand-rolled parser, a duplicate window renderer) because it read one standards doc once and then improvised. Make it grep for the app's own button.sh / open_*.sh and read that first — the launcher header often says "this replaces the old X".
