🤝🎲 Collaborative Entity Games — architecture explainer + delegation map

Goal: multiple entities operating on the same game mechanic simultaneously (roguelike, business sim, farming, etc.) — e.g. your business-sim plan (banks/stores trading, players working for salary, buying/selling to farmers/miners/scientists). See project-starters/14. for that specific starter.

🧠 The real, existing building blocks (attach-this-file-as-context version)

  • Sessions = games. Each game instance is a session folder.
  • Desks = maps. A session can have multiple desks; a desk is one playable map/screen.
  • Pals = placed entities. A pal is an entity instance living on a desk, with its own state.txt — the SAME piece-containment model as everything else in the house (PIECE → MODULE → OS).
  • Multiple entities on one desk is already the base case, not a special mode — the taskbar's own tab bar tracks multiple open entities per session today.
  • The real open question for "collaborative" specifically: how entities on the SAME desk read/write SHARED state (a bank's ledger, a market's price list) without a one-writer-rule violation. This needs a real answer before building — see file 8 (data storage ledger) for the real mechanism to reuse (master_ledger-style append-only ledgers, one canonical writer per ledger, readers poll).

📒🔒 Backend Data Storage & Sharing Ledger — architecture explainer + delegation map

Goal: understand (and extend) how the house's data storage/sharing ledger actually works — you flagged existing docs on this as "too much, unsure if current." This file is the numbered, dated, deliberately-small replacement.

🧠 The real mechanism (as verified this session, dated 2026-08-18)

  1. One-writer rule — every state/ledger file has exactly ONE process that ever writes it. Anyone else only reads. Violating this is a real, named house pitfall (#17/#36 in TPMOS's own pitfalls doc) — causes frame lag / stale-looking UI, not a crash, which makes it sneaky.
  2. Append-only ledgers for history/audit — master_ledger.txt-style files: every meaningful action gets ONE appended, timestamped line, never edited/rewritten. This session's own real example: strip_input_history.txt (KEY_PRESSED:/MOUSE_EVENT: lines, one writer, growing forever, readers stat() the size to detect new lines cheaply rather than re-reading the whole file).
  3. Marker/pulse files for "something changed" — a SEPARATE tiny file, appended with a single byte, exists purely so readers can stat() it (cheap) instead of re-parsing a big state file on every poll tick (expensive). The marker's SIZE is the signal, not its content.
  4. Cursor-based incremental reads — a reader remembers how many bytes of a growing file it's already consumed (a "cursor"), and only reads new bytes past that point each poll — never re-reads from the start. Real, proven pattern (poll_agent_relay(), poll_captured_input() in this session's own taskbar work) — first-sight NEVER replays backlog, truncation resyncs without replay.
  5. Shared state = a dedicated piece that owns it, not a free-floating file everyone touches. If N entities need to see "the bank's gold total," the bank IS a piece with its own state.txt; the bank's own manager/ops are the only writer; everyone else reads.

🎨🧰 Palettes (Tile/Sprite Picker) as Toys/Pals — delegation map

Goal: figure out how palettes (tile/sprite pickers) should associate to projects, whether they're also "pals" (get a bottom-toolbar slot + their own save-state per file/desk).

🧠 Real starting point (confirmed location)

&.widgits/tile-picker/ — the existing tile-picker widget IS the real reference implementation for "palette" already. It also owns the real tp_test_send_key.c/tp_test_send_click.c XTest input-injection tools (see 2.house-shape-status-report.md for why those matter beyond this topic). au11-hq/TASKBAR-MENU-ARCHITECTURE.md's own "Building a NEW sub-app from scratch" section covers real pitfalls this exact widget family hit (elem-pool exhaustion, CSS-apply clobbering, ledger tail-vs-head reads) — read that BEFORE assuming a palette is a simple copy-paste of an existing sub-app.

🤔 The real open design question (don't let a browser AI guess this — decide first)

Is a palette:

  • (a) A pal — a placed entity instance with its own state.txt, gets a bottom-toolbar tab slot, saves state per-desk like any other pal, OR
  • (b) A project-scoped tool — lives inside 3.<file>'s own scope, no toolbar presence, opened contextually from within the project it's editing?

These are architecturally different (pal = first-class taskbar citizen with its own tab; tool = subordinate to whatever project opened it). Answer this yourself before prompting — a browser AI given ambiguous scope here will guess wrong more often than not, per the platform primer's own "don't invent a new pattern" rule (there's no existing precedent for a "tool that's ALSO a pal" to copy from).
