🧪🤖 open-hai Live Test Findings — 2026-08-18

Real, live-tested results — not guessed. Answers the question "is open-hai + free-tier OpenRouter usable for nontrivial prompting yet?"

✅ What's confirmed working, right now

  1. Your OpenRouter API key works. Confirmed via /api/v1/auth/key (valid, free tier, $0 used) AND via real chat completions.
  2. Free-tier tool-calling works — but not on every model. Live-tested 4 free models with a real tools array: nvidia/nemotron-3.5-lightning:free ✅ and cohere/north-mini-code:free ✅ both returned real finish_reason:"tool_calls" on the first try. google/gemma-4-26b-a4b-it:free (open-hai's prior default) and z-ai/glm-5.2:free both hit the SAME real, live 429 ("temporarily rate-limited upstream... shared pool") — a provider-side congestion issue on popular free models, not a key problem.
  3. Fixed the real cause of "my key doesn't work": added the two confirmed-working models to BOTH khtpm_open_hai_manager.c AND khtpm_open_hai_render.c's own g_models[] (these two files keep SEPARATE copies by design — a real, documented drift risk if you only edit one). Switched the active model to nvidia/nemotron-3.5-lightning:free by writing sessions/model.txt directly (bypasses a real, separate nav-reachability issue — see below).
  4. End-to-end real conversation confirmed: relay-injected message → real API call → real response → correctly persisted to transcript.txt. Not a mock, a live round trip.
  5. Real tool execution confirmed: list_dir (path=".") correctly executed and returned the ACTUAL house-root directory listing, unattended, no approval needed.
  6. Real safety boundary confirmed: list_dir/read_file auto-execute; write_file/ edit_file/(and presumably run) require explicit human APPROVE/DENY via the sidebar or a state/request.txt write of "APPROVE"/"DENY". This means unattended read/list testing is safe to automate; unattended edit/run testing is NOT — by design, not a gap.

⚠️ Real, concrete gotcha found live

Asking the model to read a path containing special characters (&.widgits/open-hai/README.md) produced a WRONG path in its tool call — the & got dropped (.widgits/open-hai/README.md). Root cause not yet isolated to a specific layer (model-side JSON re-emission is the most likely culprit given list_dir path="." worked fine with no special characters) — flag this, don't assume it's fixed: give free-tier models SIMPLE, unambiguous paths, or better, resolve the path yourself and hand it a value with no punctuation-heavy directory names when precision matters.

🪲 Real bug status correction (found while investigating)

README.md's own "nav items beyond index 9 unreachable via relay digit-jump" warning is STALE — the actual code (handle_key(), checked directly) already has correct greedy multi-digit accumulation, ported from chtpm_parser.c's real house standard. Corrected in the README this session. If you see other "known bug" notes in this house's docs, verify against the live code before assuming they're still true — this is a real, recurring drift pattern, not a one-off.

📝 Best prompts to give it (real, tested shape)

SEND|Use your read_file tool to read the file at path <FULL, UNAMBIGUOUS PATH RELATIVE TO
HOUSE ROOT>, then <specific, bounded ask - e.g. "summarize in one sentence">.
  • Always give a full path relative to house root, not "the current directory" or a bare filename — tool paths resolve relative to house root, not to open-hai's own directory or whatever project you're discussing.
  • Keep asks narrow and single-purpose per message — this matches the house-wide testing discipline already established (TESTING_STRATEGY.md's own relay-only, one-action-at-a-time rule) and avoids the free-tier model losing track mid-multi-step-task.
  • For anything requiring write_file/edit_file/run, expect to manually APPROVE each action — plan for a human in the loop, don't script an unattended multi-edit pipeline yet without also scripting the APPROVE side.

🎯 Honest bottom line

Yes, open-hai + free-tier OpenRouter is usable for nontrivial prompting right now — real conversations and real read-only tool use both confirmed live. The two real caveats: (1) pick a model that isn't currently congested (this session found 2 working alternates when the default was rate-limited — check GET https://openrouter.ai/api/v1/models for current :free + tools-capable entries if these two stop working later), and (2) write/edit/run actions need a human to approve each one — this isn't yet a "let it run unattended and check back later" tool for anything beyond read-only exploration.
