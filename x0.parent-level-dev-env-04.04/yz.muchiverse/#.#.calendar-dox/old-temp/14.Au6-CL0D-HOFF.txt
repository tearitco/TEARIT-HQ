WHY THIS WASN'T WORKING EARLIER THIS SESSION - THE REAL BUG: while
proving the above, found and fixed a SEPARATE, SEVERE, ROOT-CAUSE bug

book-stack's own): `parse_line()`'s own `char original[128]` buffer
silently truncated ANY line over 127 bytes - which is EVERY real
"exec <absolute path>" line in this house, since directory names here
are routinely emoji-heavy (4+ UTF-8 bytes per emoji, several combined
with variation selectors/ZWJ sequences - a single "❤️‍🔥️" is more than
ten raw bytes). Confirmed via `strace -f -s 500 -e trace=execve` -
prisc+x's own event.pal `exec` line was handing `/bin/sh -c` a
COMMAND STRING CUT OFF MID-PATH, so `sh -c` genuinely couldn't find
the file (real, correct behavior given a truncated argument - not an
sh/dash quirk). This means EVERY RUN_METHOD-triggered PAL script this
whole session that shells out via `exec` to a long absolute path may
have been silently failing the same way, not just book-stack's own -
worth a broad regression check next session (grep other .pal files
under `event_pkg/` trees for `exec <long path>` and re-verify each one
now that this is fixed).

FIX APPLIED (real, minimal, already compiled and verified):
`original[128]` -> `original[512]` + `snprintf` instead of
`strncpy` (also fixes a secondary missing-null-terminator risk
`strncpy` had). Rebuilt in place:
`cd "<house>/101.mutaclsym🧟‍♂️️+18.01/system" && gcc -Wall -O2 -o prisc+x prisc+x.c`
- confirmed via strace that the full path now survives intact.

NOTE: other 256-byte buffers exist throughout prisc+x.c (arg1/arg2/
arg3/literal_arg/literal_arg2/the two other `line[256]` buffers) -
NOT touched this pass since they weren't the confirmed bug and have

3. WHAT'S STILL BROKEN - THE REAL UNRESOLVED PROBLEM
================================================================

Keyboard navigation inside context menus (arrow keys / Enter / digit
jump) is fundamentally unreliable, DESPITE FOUR SEPARATE FIX ATTEMPTS
this session, each addressing a real bug that was found - but the
underlying problem was never fully solved:

  1st attempt: XGrabKeyboard/XGrabPointer return values were never
  checked; added a 5-attempt retry loop for a real, documented X11 race
  (AlreadyGrabbed on rapid close-then-reopen). Real fix, but insufficient
  alone.

  2nd attempt: added XSetInputFocus + XRaiseWindow to every popup open,
  intending to guarantee input priority. This was a REAL REGRESSION -
  it's a global fight over ONE X focus/stacking order across every
  entity's own separate process, so one entity's popup opening could
  yank focus away from a DIFFERENT entity's already-open popup. REVERTED.

  3rd attempt (the real root cause, finally found): THIS IS A WAYLAND
  SESSION (GNOME Shell/Mutter, confirmed via
  $XDG_SESSION_TYPE=wayland). Every popup here is a plain X11 window
  running under XWayland. Mutter DELIBERATELY restricts XGrabKeyboard
  from XWayland clients by default (a real, intentional Wayland
  security policy - `gsettings describe
  org.gnome.mutter.wayland xwayland-allow-grabs` explains this
  directly). No amount of retrying the grab call inside our own C code
  can override a compositor-level restriction. Real, partial fix
  applied: popups now set a real WM_CLASS ("MuchiverseLivedesk") via
  XSetClassHint, and a NEW script, $.crypts/enable_xwayland_grabs.sh,
  sets `org.gnome.mutter.wayland xwayland-grab-access-rules` to
  allowlist that one class (NOT the global xwayland-allow-grabs switch -
  the user specifically chose the narrower, per-app allowlist over a
  house-wide security downgrade). THIS SCRIPT WAS RUN AND THE SETTING
  WAS CONFIRMED CHANGED (gsettings get shows it took), but the user
  STILL reported broken keyboard nav after this - meaning either (a)
  Mutter needs the X11 client itself restarted/reconnected after the
  gsettings change to pick it up (untested - try restarting
  tp_desktop_window AFTER confirming the gsettings value, in a clean,
  isolated test), or (b) there's a second layer to this restriction not
  yet understood, or (c) the WM_CLASS isn't actually reaching Mutter
  correctly (verify with `xprop WM_CLASS` on a LIVE popup window, not
  just code review - this was never actually re-verified live after the
  rebuild).

  4th attempt (in response to the grab approach still not working):
  pivoted away from XGrabKeyboard entirely. Real idea: the TASKBAR's
  own input box already reliably holds real X input focus via plain
  XSetInputFocus (a normal focus assignment, NOT a grab - the
  Wayland restriction is specifically about grabs, not normal focus).
  So make the taskbar a remote keyboard: while its input box is active
  and no digits have been typed, Up/Down/Enter get relayed as a NEW
  "NAV_KEY:<key>" command into whichever entity's interact_relay.txt
  currently owns an open popup (found via the first KIND=row line in
  livedesk_nav_claims.txt - that state only exists while a popup is
  genuinely open). Implemented on both sides (tp_desktop_window.c's
  NAV_KEY relay handler, tp_taskbar.c's find_open_popup_path() +
  input-box key handling). USER'S IMMEDIATE FEEDBACK: "u didn't add a
  key logger yet, so its not picking up the keys" - meaning the
  fundamental assumption (taskbar's own window reliably receives real
  KeyPress events once "active") was NEVER independently verified
  before building relay logic on top of it. THIS IS THE FIRST THING TO
  CHECK NEXT SESSION - see §5 step 2.

ADDITIONAL, SEPARATE, UNDIAGNOSED BUG: clicking a taskbar tab (or
possibly anywhere on the taskbar - not narrowed down) while a DIFFERENT
window's context menu is currently open closes that open popup. Never
investigated - could be an intentional side effect of XSetInputFocus

7. LESSON LEARNED, WORTH REMEMBERING
================================================================

Every "focus problem" reported this session had a DIFFERENT real cause
(X11 window-ID reuse, a self-inflicted global-focus-fight regression, a
genuine cross-process grab race, a blocking-lock-induced input backlog,
and finally a Wayland/XWayland compositor restriction) - resist the urge
to treat a new focus complaint as "the same bug again." Diagnose each
one fresh, from the actual live system (xev, xwininfo, xprop, the new
livedesk_nav_debug.+x tool), before writing a fix. Guessing produced at
least two real regressions this session (the XSetInputFocus/XRaiseWindow
