**human developer** who needs to understand this codebase well enough to
**hand small, exact jobs to a weak AI agent** that will do most things by
hand. It assumes you know how to program in C and use a shell, but that

it is only for a high-context AI. Everything a human needs is right here.

## 1. 🏠 What the house actually is (the 60-second model)

- It is a **file-backed desktop operating system**, written in C, that
  runs as a bunch of cooperating Unix processes drawing their own X11
  windows on your real Linux desktop. Internally it's called **"the
  house"** or **"muchiverse"**; the git repo is **TEARIT-HQ**.
- The **taskbar strip** at the bottom of the screen (`livedesk`) is the
  shell. It launches everything else: little apps ("**HQ windows**"),
  games, tools, and desktop "**entities**".
- **The iron law: "if it's not in a file, it's a lie."** 📄 Every piece
  of state that matters — what's open, what a button does, what colour
  something is, what the user typed — lives in a **real file on disk**,
  in plain text. An in-memory variable that vanishes on restart is not
  allowed to be the source of truth for anything. This is not a style
  preference; it is *the* architectural decision, and almost every
  convention below falls out of it.
- Consequences you will feel immediately:
  - You debug by **reading files**, not by attaching a debugger.
  - You drive and test the UI by **writing lines into relay files**,
    not by scripting mouse clicks.
  - Config is **edited in `.pdl` text files**, not recompiled.
  - Two processes writing the same file is **a bug**, always.

## 3. 🧬 The core shape: PIECE → MODULE → OS

Everything is built from three layers. Learn these three words.

- **PIECE** 🧩 — a directory that owns some state. Has a `state.txt`
  (or similar) and usually a `.pdl` descriptor. That's it. A pal on the
  desk, a session, a document — all pieces.
- **MODULE / manager** 🧠 — a **separate compiled binary**, named
  `<something>_manager.c` → `<something>_manager.+x`. It runs as a
  background loop: read input requests, do the real work, **publish a
  plain-text state file**. A manager is deliberately **thin** — it
  shells out to tiny standalone **ops** binaries for real work rather
  than inlining logic.
- **OS / renderer** 🎭 — the shared drawing layer. It reads a layout
  file + a manager's published state file, substitutes `${variables}`,
  lays out rectangles, and paints them. **It must contain no
  app-specific business logic** — only generic "read state, draw it".

➡️ **Practical rule:** any real feature = **a layout file** (`.chtpm` /
`.xhtpm` markup) **+ a manager** (`_manager.c`). If you find yourself
writing a parser loop or an X11 draw call inside the shared renderer,
you are doing it wrong — stop and move it to a manager.

Why so strict? Because logic baked into the shared renderer becomes
un-removable, un-testable, and breaks other windows. This has happened,
been condemned, and is rule #1 of the "gold standard" (§7).

## 4. 🖥️ X11 in five minutes (you said you know nothing — here it is)

You do **not** need to become an X11 expert, but you need this vocabulary
or the pitfalls section won't make sense.

- **X server / display** — the process that owns the screen, keyboard and
  mouse. Programs ("X clients") talk to it over a socket to create
  windows and draw. `$DISPLAY` (usually `:0`) says which server.
- **Window** — a rectangle the server manages for a client. Creating one
  and drawing to it is all client library calls (**Xlib**); text drawing
  uses **Xft**. The house renderer is raw Xlib + Xft — no toolkit, no
  GTK/Qt.
- **Window manager (WM)** — a *separate* privileged client that decides
  where windows go, draws title bars/borders, and — critically —
  **routes the keyboard to whichever window has "focus."** On this
  machine the WM is **Mutter**, running under **Wayland** with
  **XWayland** translating X11 for our old-school programs.
- **`override_redirect`** — a flag a client can set on a window meaning
  "WM, keep your hands off this one." Good for a **short-lived popup /
  dropdown** (you want it to appear instantly, exactly where you put it,
  no title bar). **Bad for a long-lived window** — because by X11
  definition the WM then never gives it keyboard focus back after the
  user clicks elsewhere. Under Mutter/XWayland this is worse: a real
  hardware keypress often **never reaches** an `override_redirect`
  window at all, and `XGetInputFocus()` will *lie* and say it did.
  - 🔑 **House rule:** a **persistent** top-level window must be a real
    **WM-managed** window with its decorations hidden via
    `_MOTIF_WM_HINTS` (see any HQ window's setup in
    `khtpm_core_render.c`, search `dock_managed` / `render_managed_wm_hints`).
    A **transient** popup stays `override_redirect`. There is a
    house-wide PDL toggle `#.desktop/livedesk_override_redirect.pdl`
    that must **never** be flipped globally — it broke every taskbar
    dropdown twice (2026-09-04, 2026-09-05). Scope any such change to
    one window.
- **Focus-follows-mouse** — this desktop is set so the window under the
  pointer has focus. Move the mouse off a window while typing and your
  keys can silently go elsewhere. This is why armed text inputs in the
  renderer do an `XGrabKeyboard` while active.
- **Why we never use `xdotool click`** — it clicks whatever pixel is
  physically there on the **user's real shared desktop**. And **XTest**
  key injection needs *global* focus and will **steal it from a human
  who is using the machine right now.** Both are last-resort only. The
  house-standard way to drive a window is **relay files** (§10).
- **Seeing pixels** — normal screenshot tools return **solid black** in
  this sandbox. Use `dump_frame_png_op.+x <hex_window_id> <out.png>`
  (convert a decimal window id with `printf '0x%x\n' <n>`), or better,
  just read the window's published text state.

## 5. 🎭 The two rendering families (and why both exist)

There are **two** layout/render engines in the house. Know which one your
task is in.

| | **chtpm_parser_pal** (legacy) | **khtpm** (current standard) |
|---|---|---|
| Output | plain character grid, no box model | positioned, styled `Elem` tree (real x/y/w/h + CSS) |
| Looks like a real GUI? | no, structurally | yes |
| Used by | mutaclysm, piececraft-xyz, IRC/forum/chain CLIs, most `101./2xx.` games, most `@.apps/` still | every HQ window, the taskbar strip, all new UI |
| Files | `chtpm_parser_pal.c`, `chtpm_rgb_render.c`, `prisc+x` (its little VM) | `khtpm_render_core.c` + `khtpm_css_parser.c` (parse) + `khtpm_draw_core.c` (paint) |
| Posture | not deprecated, no forced migration; migrate opportunistically when you're already touching it | build everything new here |

- The markup file is called **`.chtpm`** (legacy) or **`.xhtpm`** (the
  khtpm/HQ dialect). Same idea: tags like `<window> <sidebar> <panel>
  <row> <item> <text> <text_area> <scrolllist> <grid> <canvas> <tab>
  <cli_io>` plus `${var}` substitution.
- `khtpm_core_render.c` is **one big merged binary (~14.7k lines)** that
  contains several old renderers squashed together, each still selected
  by a mode flag at startup. The end goal is "one generic engine, all
  behaviour in managers." **Do not add a new `g_is_<yourthing>` global
  or a new `strcmp("yourapp")` branch to it** — that's the #1 thing the
  gold standard forbids.
- Inside khtpm there are *also* two tree systems mid-convergence:
  **LayDoc** (the taskbar strip's own engine, `khtpm_strip_layout.*`)
  and **Elem/CSS** (every HQ window). You'll almost always be in
  **Elem/CSS**.

## 6. 🏗️ How to build a new HQ window / app — the fixed shape

Every X11-HQ app is the **same three parts**. There is no fourth part and
no shortcut.

1. **A static `<name>.xhtpm` + `<name>.css`** — layout and colours only,
   **zero logic**. Rendered by the shared `khtpm_core_render.+x`. You
   write **no C** for the front end. Dynamic values come in as
   `${vars}`; repeated rows use `<repeat count="${n}" bind="row">` and
   the manager publishes `row_0_field`, `row_1_field`, …
2. **A real compiled manager** `ops/<name>_manager.c` (a `<module>`).
   Owns **all** state/logic. Runs a poll loop. **Publishes**
   `state/<name>_ui.txt` (plain `key=value` lines). **Consumes**
   `state/<name>_action.txt` (`seq=<n>` / `cmd=<verb>`). It **never**
   touches X11, never draws.
   - argv contract it is launched with: `<house_root> <package_dir>
     [<id-if-set>]` — with env fallbacks `KHTPM_HOUSE` / `KHTPM_PKG`.
     Do not invent a different argv order (a real, repeated mistake).
3. **A `button.sh`** launcher (derives `house_root` itself from `$0`,
   never from a passed-in path) + a **`toy.pdl`**
   (`SECTION | title | <Name>` / `SECTION | launch | button.sh`) if it
   should show in the toys menu.

**Cross-app communication** is *also* just files: app A writes
`result=… / result_action=LOAD` into its **own** `_ui.txt`; app B polls
that file. No sockets, no callbacks.

**The gold-standard rules (`02-architecture/CENTROID_GOLD_STD.md` §3),
compressed:**
1. Author a real `.xhtpm` + `.css` and **parse them through the real
   pipeline** — never hand-build the Elem tree in C, no matter how small.
2. Business logic in a **separate manager process** — never in the
   shared renderer file.
3. Parse + layout + CSS run **once**, producing the `Elem` tree.
4. Every display target is a **thin renderer of that same tree**
   (X11 today, ASCII/headless tomorrow) — never a second composer.
5. Real `nav_index` / digit-jump semantics for every renderer.
6. Real **receipt** files for renderer output (dimensions/checksum).
7. **Never** a new `g_is_<project>` flag or per-project branch in
   `khtpm_core_render.c`.

**The manager is the ideal thing to delegate to a weak agent** — it's a
pure, bounded problem (given a complete spec: the argv contract, exact
`_ui.txt` keys, exact `_action.txt` shape, any `\n`-escaping, and the
gcc line to self-check). The four File-Explorer-era managers were all
written by a fresh Haiku agent and compiled first try. You then make the
small integration corrections yourself.

**Converting a GUI mockup to the tag vocabulary** has a real recipe
(4 window skeletons, a widget→tag table, nav ordering rules, the CSS
subset). It lives in the media-studio delegation doc's "DESIGN / LAYOUT
PLAYBOOK" section — the browser-prompting HTML guide reproduces it under
"Grok's Lanes" if you want it rendered.

## 7. 📝 PDL — the config format you WILL be editing

**PDL** = the house's `.ini`. Plain text, one record per line, fields
separated by ` | ` (space-pipe-space is the readable convention; parsers
`strtok` on `|` and trim spaces):

```
SECTION | KEY | VALUE
COLOR   | bg  | #101014
SHORTCUT| $   | some command
```

- **First field is a tag/section** (`SECTION`, `COLOR`, `CLOCK`,
  `SHORTCUT`, `STATE`, …). Some record-style PDLs put an **id** in field
  2 and then `k=v` pairs: `CLOCK | clk1 | scope=day | label=Wake`.
- **✍️ How to edit it:** just open it in any text editor and change the
  VALUE. No build, no recompile — the manager re-reads the file (usually
  every poll tick, or on a change-marker). Keep the ` | ` spacing;
  don't add or remove columns for a given tag.
- **💬 Can you comment?** Yes, with care:
  - A line whose **first character is `#`** is skipped by the common
    readers (`if (line[0] == '#') continue;`). **Blank lines** are
    skipped too.
  - **Put `# ` (hash + space) at column 0.** No leading indentation —
    ` # foo` is *not* recognised as a comment by most readers. A bare
    `#` immediately followed by `|` (`#|…`) is treated as **data**, not
    a comment, by at least one parser — so always use `# ` with the
    space.
  - **No trailing/inline comments.** `KEY | VALUE   # note` makes
    `# note` part of the value. Comments must be **their own full line**.
  - Comments and blank lines are **not preserved** if a tool
    *rewrites* the file programmatically (e.g. sql-hq writing a table
    back). They survive only as long as humans are the only editors.
- **🧷 Gotchas:**
  - A `${var}` value containing a bare `"` **hangs the xhtpm parser at
    100% CPU** and the window never appears (looks like a WM bug). Never
    put an unescaped double-quote in a substituted value.
  - Missing keys must **fall back to a safe default** in code — don't
    assume every key is present.
  - **Runtime-configurable values belong in PDL, not C.** Position,
    colour, size, label, a toggle — if a user might want to change it
    without recompiling, it goes in the nearest existing `.pdl`. Don't
    invent a new config file; extend the closest one.
  - Asset locations live in a **PDL pointer key** (e.g. `img_root` in
    `$HOUSE/shared/RMMV-ASSET-SOURCE-LOCATION.pdl`) so a drive/OS/move
    needs zero C change. **Do not** put those PDLs in calendar-dox or
    in `#.NNEST_ASSETS` (the latter is optional and often missing).

## 8. 🗂️ State files, markers, the one-writer rule

The whole house runs on a few simple file patterns. Internalise them.

- **One-writer rule** ✍️ — every state/frame/ledger file has **exactly
  one** process that ever writes it. Everyone else only reads. Two
  writers = stale-looking UI, frame lag, races — sneaky because it
  doesn't crash. If two things need to write, you have a design bug:
  make one of them a **piece that owns the file** and have the other
  ask it.
- **Append-only ledgers** 📒 — history/audit files get **one timestamped
  line appended** per event, never edited. Readers `stat()` the file
  **size** to notice growth cheaply.
- **Marker / pulse files** 📍 — a tiny separate file that gets **one
  byte appended** to mean "something changed, redraw." Readers check its
  **size**, not its contents. Never a `dirty=1` flag inside a big state
  file. (House rule, restated in memory: *change detection = marker file
  growth, never `st_mtime`* — mtime has 1-second granularity here and
  bites you.)
- **Cursor reads** 📖 — a reader remembers how many bytes it has
  consumed and only reads past that. First sight never replays backlog;
  a truncation resyncs cleanly.
- **Receipts** 🧾 — a renderer writes its own output dimensions/checksum
  to an adjacent `*.receipt.txt` so the next stage doesn't guess.
- **Runtime files are git noise** 🔇 — `*_ui.txt`, `*_action.txt`,
  `*_buffer.txt`, `module_parent.pid`, `text_area_*.txt`, `history.txt`,
  `entity_menu_frame_*`, live `.pdl` under `#.desktop/`, logs. A
  `git status` full of these is **normal**. Never stage them.

## 9. ⌨️ Input & the relay — how a keypress reaches the screen, and how YOU drive it

### The real pipeline
```
real keyboard / mouse   (Xlib KeyPress/ButtonPress)   ── OR ──   an agent writing a line
        │                                                              │
        └──────────────►  a per-PID history/relay FILE  ◄──────────────┘
                          #.desktop/entity_menu_history/<render-pid>.txt
                                       │  (one reader polls it every tick)
                                       ▼
                          dispatcher  → mutates state.txt / composes a frame
                                       ▼
                          renderer  (pure "read state, draw" — never touches raw input)
```
A human keypress and an agent-written line are **byte-identical**; the
dispatcher cannot tell them apart. That is the whole basis of
relay-driven testing.

### The file format (one event per line, appended — never truncate it)
```
KEY_PRESSED: <decimal>          # 13=Enter 27=Esc 8=Backspace 9=Tab
                                # 200/201/202/203 = Up/Down/Left/Right
                                # 204/205 = PageUp/PageDown
                                # printable ASCII 32–126 = that character's code
MOUSE_EVENT: <button> <x> <y> <is_press>
# a line starting with # is an inert audit comment (still advances the cursor)
```

### How to actually drive a window (preferred order, strict)
1. **Relay file injection** as above — find the render PID from
   `ps aux | grep khtpm_core_render` (it's argv-visible) or the window's
   `module_parent.pid`. Drive nav/dispatch exactly like a human would.
2. **Read a text state file** (`<app>_ui.txt`, or the manager's
   action/frame files) to confirm what changed — cheaper and less
   ambiguous than decoding a PNG.
3. **`dump_frame_png_op.+x <hex-window-id> <out.png>`** for real
   pixel/layout proof.
4. **`xdotool` / XTest** — *last resort only*, e.g. real mouse-drag
   physics. Reaching for this first is the classic mistake.

- ⚠️ On this Mutter/XWayland desktop, real hardware **clicks** are not
  delivered as `ButtonPress` to `override_redirect` windows (mouse
  handling there polls `XQueryPointer`); real **keys** do reach
  `handle_key()`.
- ⚠️ The strip has its **own** relay layer:
  `#.desktop/livedesk_agent_relay.txt` (raw keys) and
  `#.desktop/strip_history.txt` (resolved action codes). Its nav helper
  is `#.desktop/harnesses/khtpm-livedesk-taskbar/nav.sh`, which needs
  `HOUSE=<house_root>` in the environment or it defaults to `$PWD` — an
  easy footgun if you `cd` first.

### nav_index / digit-jump
Every navigable row in a window gets a number badge `[ ]1. [ ]2. …`
assigned **in document order** to each `<item>/<tab>/<cli_io>` that has a
label or action (`<text>/<text_area>/<title>` get **none**). Press the
digit to jump focus there; arrows move; Enter activates. The `[X]` close
is auto-appended last.
- Numbering **restarts at 1 per window** — this is deliberate, not a
  bug. A cross-window address is the literal **Tab** key (`^` marks
  which window has Tab-focus, `>` is the local cursor).
- **Before sending any digit, dump/read the frame and check the ACTUAL
  numbers.** With multiple windows open, nav numbering can legitimately
  start at 11, 19, whatever. Never hardcode an index across more than
  one action.
- Sub-lists/pickers keep their **own** counter but use the **same** nav
  convention — never a bespoke "press 1/2/3 directly" scheme.

## 10. 🔨 Build & restart — and the trap that eats an hour every time

- **Compilers/scripts live in** `*.monads/*.livedesk-taskbar/ops/`.
  Key ones:
  - `build_core_render.sh` — the shared render core.
  - `build_khtpm_strip.sh` — the whole taskbar binary + helpers.
  - `run_khtpm_strip.sh new` — rebuild-and-restart the live taskbar
    stack. Now takes a **single-restart lock** (`#.desktop/.khtpm_restart.lock`) —
    a 2nd click while one is building is refused, not queued.
  - Per-app: `build_<app>_manager.sh`, or the app's own
    `ops/build_*.sh`.
- 🆕 (2026-09-09) `build_khtpm_strip.sh` has a **freshness gate** — it
  skips the ~28s build when the binaries are already newer than every
  first-party source (`KHTPM_FORCE_BUILD=1` overrides; `$.restart` and
  the desktop start button set it). When a forced build does run and
  `LIVEDESK_START_SPLASH=1` is set, an X11 **"Building livedesk…"**
  window (`+x/livedesk_splash.+x`, themed, compile-watching progress
  bar) shows until the build ends. A **colour change no longer builds
  or restarts** anything — `apply_theme_op` just bumps
  `livedesk_theme_changed.txt` and every window reloads live.
- After editing `&.widgits/_shared-lib/khtpm_render_core.c` /
  `khtpm_draw_core.c` / `*.monads/*.livedesk-taskbar/ops/khtpm_core_render.c`:
  run **`sh build_core_render.sh` AND `sh build_khtpm_strip.sh`**, then
  **`sh run_khtpm_strip.sh new`** for the desktop to pick it up.
- 🪤 **THE TRAP: a running window keeps running the binary it was
  launched with.** Rebuilding does **not** hot-swap an open window. If
  you rebuild and the bug "isn't fixed," you are almost certainly still
  looking at the **old process**. After any renderer rebuild: kill every
  `khtpm_core_render.+x` (pids in `#.desktop/livedesk_hq_windows_*.txt`)
  **and reopen the window** before concluding anything.
  - Sanity check you're on fresh code: `time <the dump command>` — if
    `real ≈ user+sys` you're doing real work on new code; if
    `real ≫ user+sys` you're X-round-trip bound (or stale).
- 🪤 **Build scripts sometimes `cp` a canonical shared file over your
  local edit, every build, with no error.** Before editing anything that
  looks generated/copied, `grep` the relevant `build_*.sh` for a `cp`
  line targeting it, and edit the **source it copies from** (usually in
  `&.widgits/_shared-lib/`). The `ops/` copies show as permanently dirty
  in `git status` — **never stage them.**
- 🪤 A **legacy session's `.pal` script + its copied `ops/` binaries
  load once at startup** — a rebuild needs a **session restart**, it
  never applies live.
- 🪤 `#.desktop/*.txt` runtime state is **not** reset by a `git`
  rollback of source. Stale state can masquerade as a code bug.
- House-root emergency scripts: `EMERGENCY_CLOSE.sh`, `EMERGENCY_KILL.sh`,
  `EMERGENCY_CLEAN.sh`, and `button.sh reset` (the real "restart
  everything cleanly").

## 11. 🧪 Testing & verification discipline (non-negotiable)

- **Never say "fixed" without: a fresh build + a fresh run + real
  evidence** — a screenshot you actually looked at, a real file diff, or
  a round-tripped action file. **A clean compile is not evidence.**
- If a fix doesn't visibly work, **confirm the first fix even executed**
  (a one-line stderr trace) before stacking a second fix on top.
- Shared-code refactor? Do a real **A/B**: `git stash`, rebuild "old,"
  screenshot; restore, rebuild "new," screenshot; diff.
- **A hypothesis in a code comment is not a fact.** Re-derive from
  actual source when a doc, a comment, and a live bug disagree.
- **Kill your children.** A rendered window forks a real manager
  (`*_manager.+x`). The taskbar reaps everything in the **single**
  ledger `#.desktop/livedesk_proc_list.txt` (5-field

  TERM→KILL — and the renderer registers + reaps its own `<module>`s

  `PROC-LIFECYCLE-CONSOLIDATE-REGISTRIES.md`). Engine children now
  register too **when spawned via the canonical path**: `mpg123`

  that with a `fork+exec+waitpid+watchdog` (`3681ad63`), but a truly
  stuck child still needs a manual `kill`. After a test, `ps aux |

- Test against a **dedicated sandbox entity**, never a real-looking

- `pkill` may be sandboxed/blocked here — prefer `ps aux | grep` +

## 13. 🪤 The gotcha wall (condensed — the greatest hits)

Skim once now; come back when something behaves impossibly.

- **Stale binary** — a rebuilt renderer doesn't touch open windows;
  kill + reopen. (§10)
- **Stale runtime state** — `#.desktop/*.txt` survives a source
  rollback.
- **`cp`-on-build clobber** — your edit silently reverted; edit the
  source it's copied from.
- **`override_redirect` focus** — persistent window ⇒ must be WM-managed;
  never flip the house-wide PDL. `XGetInputFocus` lies. (§4)
- **`q` must never quit anything** — standing rule; verify any binary
  honours it.
- **Bare `"` in a `${var}`** — hangs the parser at 100% CPU, window
  never maps.
- **`label=` is not newline-safe** — multi-line goes in `content=` /
  `${var}` (which is escaped). Any new per-element runtime field must be
  added to **both** the serialize and the parse function or it never
  reaches `draw_elem()`.
- **`<scrolllist>` needs a `<sidebar>` AND `<panel>`** under `<page>`, or
  a `<panel>` parent — a bare top-level `<scrolllist>` never gets sized
  (w/h = 0).
- **First `<page>` must be named `main`** — `g_current_page` defaults to
  `"main"`; any other name ⇒ 0-height window.
- **`vars=` path doubling** — a relative `vars=` resolves against the
  `.xhtpm`'s own dir first; use the bare filename when you're already in
  that dir.
- **`<tab>` scoping** — a `<tab>` traps nav only with an explicit
  `target_id=`. A menu-bar action tab (New/Open/Save) must **not** have
  one or the main content becomes unreachable.
- **Tall element height** — a `<text_area>`/`<grid>`'s layout height must
  exactly match what its draw code consumes, or the focus box floats.
- **New scroll/grid branch in the renderer** — must **clip** (park
  off-screen children at huge negative y), **never translate** a
  laid-out subtree; must not add key handling or write a `g_*_scroll`
  directly; must nav-number only visible rows. Usually you don't need a
  new branch at all — reuse `layout_sidebar_panel` /
  `layout_scroll_region` / the swatch-grid path.
- **`assign_nav_and_layout()` runs many times per frame** — every
  mutation it makes must be idempotent. Context menus share it too.
- **`kill(getppid(), SIGTERM)`** to "end a session" actually kills
  `systemd --user` and **logs the whole desktop out.** Never.
- **`system() + &` is not a new process group** — use `setsid` for
  anything that must outlive/ignore the spawner's signals.
- **Relative commands via `system()` are CWD-dependent** — a launched
  process's CWD is whatever it inherited, **not** house root. Anchor
  relative tokens to `house_root` (or `chdir` first).
- **Climbing a fixed number of `..` from an argument** breaks the moment
  that thing can live in two places. Climb from `dirname "$0"` (your own
  fixed location) instead; when argv has no room for context, use an
  exported **env var** (survives `exec`).
- **`pkill -f <pattern>` where the pattern also matches your own command
  line kills your shell** (exit 144). Put the pattern in a separate
  script file, or grep a `ps > file` dump for a string that isn't on the
  command line.
- **A width from `measure_text_px(label)` is too small if the box also
  carries a nav badge** — add `+34`, not `+20`.
- **"Currently focused" ≠ "what the user just clicked"** — navigating to
  a button already moved focus onto it; don't read global focus inside
  its own handler.
- **`FocusIn/FocusOut` fire a `NotifyGrab/NotifyUngrab` pair whenever
  *any* process grabs the pointer anywhere** — a handler that repaints
  on raw focus events must ignore `mode` grab/ungrab and pointer-detail
  events or it repaints forever (flicker).
- **`Expose` arrives once per damaged rectangle** — drain the burst
  (`XCheckTypedWindowEvent`) then repaint once.
- **`draw_core.c` `alloc_pixel()` must stay cached; `xft_color()` must
  NOT** (its callers `XftColorFree` it). An uncached palette repaint is
  ~1000 X round-trips ≈ 0.5 s/frame ("palettes are so slow").
- **Zombie PID** — the bottom bar says an entity is open but it's not on
  screen: `kill(pid,0)==0` can't tell a live process from an unreaped
  zombie. `ps aux | grep <old-binary>`, `kill -TERM` strays.
- **Delegated subagent findings need independent verification**,
  especially confident root causes.

## 14. 🤖 Guiding a weak agent by hand — practical patterns

You are the router. The agent is fast but forgetful, over-confident, and
will happily rewrite the wrong file for an hour. Structure the work so it
can't.

- **Give it one bounded job with a complete spec.** For a manager:
  the exact argv contract, every `_ui.txt` key, the `_action.txt`
  `seq/cmd` shape, escaping rules, and "compile-check with *this* gcc
  line before you're done." Bounded, self-contained problems (a manager,
  an ops binary, a pure parser) are where a weak model succeeds.
- **Do the integration yourself.** Argv wiring, the `dispatch()` verb
  block in the renderer, the `.xhtpm`/`.css`, launch scripts, and any
  change to a shared file — keep these in your own hands.
- **Never let it touch `khtpm_core_render.c`'s structure.** Adding a
  generic, data-driven capability there is a reviewed, deliberate act —
  not something to delegate. No new per-app branch, ever.
- **Force "read before write."** Tell it explicitly which file to read
  and to quote the relevant lines back before proposing an edit. The
  standing incident: an agent rebuilt a deprecated renderer for a whole
  session while the real, compliant version sat unused next to it.
- **Make it verify, not assert.** Require a fresh build + a real
  artifact (a frame-file diff, a screenshot description) with every
  "done." Reject "it should work."
- **Feed paths simple.** Small local models drop special characters
  (`&`, `#`) when they re-emit a path in a tool call. Give full paths
  from house root with no punctuation-heavy directory names, or resolve
  the path yourself and hand it a clean value.
- **One action per test step.** Match the house's relay-only,
  one-action-at-a-time testing discipline — a weak model loses track
  across multi-step tool sequences.
- **Expect to approve every write.** In the house's own AI tooling,
  read/list auto-runs but write/edit/run needs a human APPROVE each
  time — plan for a human in the loop; don't script an unattended
  multi-edit pipeline.
- **Keep the spec files small.** ~2–3 attachments max is the working
  budget for a browser-window model. If the context won't fit, the job
  is too big — split it.

## 15. 🧠 Compaction wisdom — staying effective across memory resets

This section is what a long-running agent (or a returning human) should
re-anchor on after losing context. It's the stuff that's expensive to
re-derive.

- **Re-establish the invariants first, not the task.** In order:
  (1) house root path (§2), (2) "if it's not in a file, it's a lie",
  (3) PIECE→MODULE→OS, (4) which render family you're in, (5) relay-not-
  xdotool, (6) one-writer rule, (7) your git branch. If any of those
  feels fuzzy, re-read that section before doing anything.
- **Trust files over memory, and over your own earlier conclusions.**
  A summary of a doc can be stale the day it's written. Open the real
  file and check its own latest dated line. Re-derive a claimed fact
  from source when a doc, a comment, and a live symptom disagree.
- **Carry forward the *shape* of what you were doing, not a transcript.**
  "I was converting X's menu to be PDL-driven; player/ai/db done;
  directory-scanning builders deferred" is worth more than 40 lines of
  what you tried.
- **Record decisions and their *why*, and dead ends.** "Chose vendored
  sqlite over hand-rolled — need real JOIN/GROUP BY" and "tried
  WM-managed via a new xhtpm attribute — never took effect, switched to
  a class check" both save a future you from re-litigating.
- **Convert relative dates to absolute immediately** ("today", "last
  week" → `2026-09-08`). They rot instantly across a reset.
- **Name the exact files and line-anchors you care about**, and
  **re-verify they still exist** before recommending anything — the
  house renames and merges files (the input relay fix that lived in
  `khtpm_strip_parser.c` was silently lost when that file was replaced
  by `khtpm_core_render.c`'s dock mode).
- **Know what's a live entity vs. a fixture.** Before you kill/click/
  test anything, assume the user has real windows open right now.
- **End every block committed** (§12). Uncommitted = fire-able = it has
  actually been lost here.
- **When you hand off** (to a human, to another agent, to future-you):
  give them this file plus a 5-line "here's the shape, here's what's
  done, here's the next concrete step, here's the one gotcha."

## 17. 📚 Mini-glossary

- **house / TEARIT-HQ** — the whole repo; a file-backed desktop OS.
- **livedesk** — the taskbar + desktop shell.
- **entity** — one running app/game/tool on the desktop, its own process.
- **pal / PAL** — the tiny scripting VM (`prisc+x`) that glues ops in a
  loop; *also* the "muchi-pals" pet apps — context disambiguates.
- **piece** — a directory that owns some state (`state.txt` + `.pdl`).
- **manager / module** — a separate compiled process owning a feature's
  logic, publishing a plain-text state file.
- **PDL** — plain-text config, `SECTION | KEY | VALUE` rows.
- **chtpm / xhtpm** — the layout markup file; `.xhtpm` is the khtpm/HQ
  dialect.
- **Elem** — the positioned, styled tree node in the khtpm family; the
  "centroid" every renderer walks.
- **HQ window** — one of the merged khtpm-family app modes.
- **relay** — a plain file used to inject input, polled every tick; the
  house's standing alternative to synthetic X11 events.
- **nav_index / digit-jump** — numbered rows, jump-focusable by digit.
- **receipt** — a small adjacent file recording a renderer's own output
  dimensions/checksum.
- **session** — `pieces/sessions/<timestamp>-<pid>/`, an isolated
  per-instance working copy.
- **Harnecient** — the house's harness-authoring / test-delegation
  subsystem and its lesson series.
- **override_redirect** — X11 flag: "WM, ignore this window." Fine for
  transient popups, forbidden for persistent windows.
- **XWayland / Mutter** — the compositor stack our X11 programs actually
  run under; the source of most focus weirdness.
- **Interact** — play *input* routing on a WM-managed board; not hide-chrome.
- **desk-as-map** — a livedesk desk is an RM map (pals = events, z, transfers).
- **shared/** — in-zip SOURCE PDLs; clones optional under `#.NNEST_ASSETS`.
- **range overlay** — per-cell tint file + BFS; not `tint_screen`, not
  `tp_range_grid`.
