# 🎨 DESIGN / LAYOUT PLAYBOOK — translating a GUI mockup to the generic vocabulary

You do NOT invent tags or CSS. Every media app maps onto the same
~12 tags. This section is the recipe. Read `02-architecture/
XHTPM-PARSER-REFERENCE.md` §2/§9/§10/§11 for the full facts; this is
the "what do I actually type" layer.

## A. First decision: which of the 4 window skeletons?

Pick ONE. All four are already implemented in the renderer — you're
choosing, not building.

| Skeleton | Use when | Trigger |
|---|---|---|
| **1. sidebar + panel** | a list/tree on the left, a detail/edit area on the right (DAW track list, video clip bin, image layers) | `<window>` has BOTH `<sidebar>` and `<panel>` |
| **2. sidebar + panel + `<canvas>`** | same, but the right side is a live pixel view (image canvas, 3D viewport, video preview, DAW visualizer) | as above, with `<canvas>` inside `<panel>` |
| **3. flat toolbar + full-bleed `<canvas>`** | the app IS a viewport with a thin control strip (piececraft board) | `<page>` has a `<canvas>` and a `<row class="toolbar">`, no `<sidebar>` |
| **4. multi-column `<page style="display:flex">`** | genuinely 3+ side-by-side regions (DAW: tracks │ piano-roll │ mixer) | `<page style="display:flex; flex-direction:row">` with N `<panel>` children |

**All three media apps are skeleton 2 or 4.** img+3D = 2 (tools sidebar
+ canvas panel). DAW = 4 (arrangement / piano-roll / mixer columns) OR
2 with a `show=`-gated mixer drawer — start with 2, it's simpler.
Video = 2 (timeline sidebar + preview/inspector panel).

## B. "Do I need a new tag / a new HTML-ish category?" — almost certainly NO

If a mockup element isn't in this table, it's still one of these — pick
the closest. Do **not** ask the owner for a new tag unless you've
genuinely exhausted this table AND the thing is used by 2+ apps.

| GUI thing in the mockup | Generic construct | markup |
|---|---|---|
| menu bar (File / Edit / …) | `<tabbar>` of `<tab>` (action buttons) | `<tabbar class="tab-bar"><tab .../></tabbar>` |
| toolbar / tool strip (brush, eraser, grab…) | `<row class="toolbar">` of `<item>` | one `<item>` per tool; active tool via `class="${tool_cls}"` from state |
| transport bar ( \|◀ ▶ ⏹ ⏺ ⟳ ) | `<row class="toolbar">` of `<item>` | labels are `${play_label}` etc. so the manager flips ▶/⏸ |
| LCD / timecode / BPM readout | `<text>` (NOT an item — non-interactive) | `<text label="${bars}.${beats}.${ticks}  ${bpm} BPM"/>` |
| status bar | `<text class="status">` | one line, `${var}`-filled |
| track lanes / timeline rows / clip blocks | `<scrolllist>` of `<row class="sprite-grid-row">` OR of `<item>` rows | each lane = a row; clip blocks = `<item>` children or a `<canvas>` strip |
| piano roll / grid editor | `<grid>` (see GRID-ELEMENT-DESIGN.md) OR `<canvas>` | `<grid rows="16"/>` for a real cell grid; `<canvas>` if you draw it yourself |
| image canvas / 3D viewport / video preview | `<canvas id="view">` + manager-fed framebuffer | manager writes an RGBA `.raw`; `kh_draw_canvas` blits it (piececraft board is the reference) |
| layers list / outliner / clip bin | `<scrolllist>` of `<item>` in the `<sidebar>` | visibility toggle = `backspace_action=` or a 2nd `<item>` per row |
| inspector / properties panel | a second `<panel>` (skeleton 4) OR a `show=`-gated block in the main panel | `<text>` rows + `<cli_io>` for editable numeric fields |
| mixer / inserts drawer | `show="${drawer_open}"` on a `<row>` or `<panel>`; toggled by an `<item>` | manager owns `drawer_open` in `_ui.txt` |
| tabs that switch WHAT the panel shows | `<tab ... target_id="side">` (scopes nav) | with `target_id` it confines nav; without, it's just a button |
| a text field the user types in (rename, BPM, path) | `<cli_io target_id="fieldname" rows="1">` | never a fake `<input>`; `<cli_io>` is the only input element |
| multi-line notes / script area | `<text_area rows="12" content="${buf}">` | |
| scrollbars, sliders, spinners, checkboxes, radio, dropdowns | **do not exist as elements.** slider → +/- `<item>` pair + a display-only `<text>` bar. dropdown → a `<tab>`/`<item>` that opens another menu page (`GOTO:`). checkbox → an `<item>` whose label/class flips from state. | (music-player-hq does seek/volume exactly this way — copy it) |

## C. Ordering the nav `[ ]` items — the rules

`nav_index` (`[ ]1. [ ]2. …`) is assigned **in document order** to every
`<tab>`, `<item>`, and `<cli_io>` that has a `label` or an
`action`/`onclick`. `<text>` / `<text_area>` / `<title>` / `<module>`
get **no** nav number. So:

1. **Order = the order you write them in the template.** Put the
   control the user reaches for most FIRST. Put destructive / rare
   ones LAST.
2. **The chrome `[X]` close is auto-appended after everything.** Don't
   add your own `<item id="close">` unless you deliberately want it
   earlier in the run.
3. **`<tab>`s come first** in a sidebar+panel window (they're the 1st
   child of `<page>`). If a tab has `target_id=`, clicking it *scopes*
   nav into that region — `[^]` on the tab, arrows stay inside, Esc
   pops out. Use `target_id` when "pick a tab, then navigate its
   contents" is the flow (record lists, layer lists). Omit it when the
   tab is just a one-shot action (File → New).
4. **Scroll regions nav-number only the VISIBLE rows** — a 500-item
   list is fine, off-screen rows have `nav_index=0` and PageDn/wheel/
   the `^`/`v` sbar arrows bring more into range. Never emit 500 bare
   `<item>`s outside a `<scrolllist>`.
5. **Keep ~20 nav items visible per screen.** More than that = you
   need a scroll region or a second page (`GOTO:`), not a wall.
6. **Group with `<row class="toolbar">`.** Items in one toolbar row
   still each get a nav number but read as a visual cluster — that's
   how you make a transport bar or a tool strip.
7. **A `[ ]N.` badge is ~46px of the element's width.** In CSS give a
   short-labelled button enough `width:` or the label clips to just
   the badge.

## D. CSS is a tiny subset — plan around it

Supported: `background-color`, `color`, `border` / `border-width`,
`font-family`, `font-size`, `font-weight`, `padding`, `width`,
`height`, `display:flex` + `flex-direction` + `flex-wrap` + `gap`,
`flex-grow`, `position:absolute` + `top`/`left`.

**NOT supported** (silent no-op → element renders 0px or unstyled):
`min-width` / `max-width` / `width:auto`, `margin` (mostly), `%`
widths on most elements, any color/gradient/shadow/radius/transition,
`grid`, floats. **If an element has no explicit `width:` it is very
often laid out at 0 and you'll swear it "didn't render" — pitfall #16's
sibling.** Set real px.

Set every color as a literal in the rule (there are no CSS variables).
Dark theme by default (`#121214` bg, `#e6e6ea` text, `#24242a`
buttons) — match the other `@.apps/*.css`.

## E. Worked example — the DAW (`media-daw-hq`)

`HOW2_DAW.md`'s pass-2 layout table → this skeleton. Nav numbers
annotated in comments; `${…}` all come from `media_daw_hq_manager.c`'s
published `_ui.txt`.

```xml
<window label="Muchi DAW - ${lcd}" class="database-window" vars="state/media_daw_hq_ui.txt">
  <module src="@.apps/media-daw-hq/ops/+x/media_daw_hq_manager.+x" id="_"/>
  <page name="main">

    <sidebar id="tracks" class="daw-side">
      <tabbar class="tab-bar">
        <tab id="addtrk" class="tab" label="+ Track"                              <!-- [ ]1 -->
             action="'${HOUSE}/@.apps/media-daw-hq/ops/media_daw_hq_action.sh' 'ADD_TRACK'"/>
        <tab id="mixtgl" class="tab" label="Mixer (B)"                            <!-- [ ]2 -->
             action="'${HOUSE}/@.apps/media-daw-hq/ops/media_daw_hq_action.sh' 'MIX_TOGGLE'"/>
      </tabbar>
      <text label="tracks - ${n_tracks}" class="quiet"/>
      <scrolllist>
        <repeat count="${n_tracks}" bind="t">
          <!-- one nav item per track header (color chip + name + M/S/R live in the label/class) -->
          <item id="trk${t.#}" class="daw-trk ${t.cls}" label="${t.hdr}"          <!-- [ ]3.. -->
                action="'${HOUSE}/@.apps/media-daw-hq/ops/media_daw_hq_action.sh' 'SEL_TRACK:${t.#}'"
                backspace_action="'${HOUSE}/@.apps/media-daw-hq/ops/media_daw_hq_action.sh' 'DEL_TRACK:${t.#}'"/>
        </repeat>
      </scrolllist>
    </sidebar>

    <panel id="edit" class="daw-main">
      <!-- transport: one toolbar row, 5 items -->
      <row class="toolbar daw-transport">
        <item id="tp_rew"  class="daw-btn" label="|<"   action="'…' 'REW'"/>       <!-- [ ]N   -->
        <item id="tp_stop" class="daw-btn" label="[]"   action="'…' 'STOP'"/>      <!-- [ ]N+1 -->
        <item id="tp_play" class="daw-btn" label="${play_label}" action="'…' 'PLAY'"/>
        <item id="tp_rec"  class="daw-btn daw-rec" label="(o)" action="'…' 'REC'"/>
        <item id="tp_cyc"  class="daw-btn ${cycle_cls}" label="cyc" action="'…' 'CYCLE'"/>
      </row>
      <text label="${lcd}   ${bpm} BPM" class="daw-lcd"/>            <!-- NOT nav -->
      <text label="${bar_ruler}" class="daw-ruler"/>                <!-- NOT nav; ascii ruler string from manager -->

      <!-- arrangement lanes: a canvas the manager draws (clip blocks + playhead),
           OR a scrolllist of sprite-grid rows if you want per-clip nav -->
      <canvas id="arrange" class="daw-arrange"/>

      <!-- piano roll underneath -->
      <grid id="proll" rows="12"/>                                  <!-- [ ]last-1 (grid is one nav slot) -->

      <!-- mixer drawer: show-gated, toggled by [ ]2 above -->
      <row class="toolbar daw-mixer" show="${mixer_open}">
        <repeat count="${n_tracks}" bind="m">
          <item id="mx${m.#}" class="daw-mx" label="${m.fader}" action="'…' 'FADER:${m.#}'"/>
        </repeat>
      </row>
      <text label="${msg}" class="daw-msg" show="${msg}"/>
    </panel>
  </page>
</window>
```

Nav run reads: `+Track, Mixer, track1..trackN, |<, [], play, rec, cyc,
proll, fader1..faderN, [X]`. Most-used (add track, transport) early;
`[X]` auto-last. Everything else (LCD, ruler, arrangement view) is
`<text>`/`<canvas>` and correctly gets no number.
