## 🔌 PART II — THE RELAY (THE BLOODSTREAM) 🩸

### What Is the Relay?
A **plain text file** sitting in `#.desktop/` that a window's code polls every ~300ms. Each line = one bare decimal ASCII keypress. You don't click the window — you **write numbers to a file**. ✍️

**Why?** A file is auditable, reproducible, and scriptable. You can't easily script a human hand, but you can script a file. So the house made the file the hand.

### nav.sh — The Bash Driver
| Command | What It Does |
|---|---|
| `nav.sh nav <n>` | Type digit(s) `<n>`, press Enter |
| `nav.sh row <n>` | Same as nav (alias) |
| `nav.sh key <name>` | Send one key (Return, Esc, BackSpace, or char) |
| `nav.sh type <text>` | Type text char-by-char (no Enter) |
| `nav.sh esc` | Short for key Esc |
| `nav.sh frame` | Print current state (the ground truth) |
| `nav.sh wait [sec]` | Sleep (default 0.6) |

### 🔑 The Digit Rule (Critical!)
A **digit key moves focus, it does NOT activate.** You always need a separate Enter. Like a real bracket-badge system: `[1]` means "look at item 1", Enter means "do it." ✅

**The Boss confirmed it directly:** "i do expect to press enter. (as usual)."

### ⚠️ Relay Timing Traps
- 🐢 **Digit + Enter sent too fast** can fire Enter before the digit round-trips — activating the wrong (previous) focus target. After digits, **sleep well past two full poll cycles (~0.8s)** before Enter.
- 🔢 Digits accumulate server-side regardless of pacing, so back-to-back digits are fine — only the final Enter needs the settle time.
- 🧾 **Never hardcode "6 = composer"** — always read the current frame first. Nav indices shift as sessions are added/removed.

### 🧾 Receipts Over Pixels (House Law)
Do NOT trust `xwd` or screenshots. A covered or dragged window can make a screen capture return another window's content. The house rule: **use the app's own PNG dump** — it reads from its own compose buffer, so stacking can't fool it.

Press `p` in the window (or via relay injection) → writes `ai-cell-frame.png` **plus a receipt** (`ai-cell-frame.png.receipt.txt`):
```
ok=1 w=1000 h=680 t=1692345678 nav=2 n_nav=6 n_sessions=3 n_msgs=4 toolpending=0 tool=readfile
```

**A PNG can exist half-written; a receipt existing means the frame finished.** The receipt fields tell you the exact app state at that instant. Check the receipt, not just the PNG's existence. ✅

### 🔄 Parser Layer vs Manager Layer
- **Parser layer** (nav/row/key/type): Raw keycodes, hit-testing, rendering. Tests the full human path.
- **Manager layer** (hqcell/mgrcode): Resolved codes straight into `strip_history.txt`. Bypasses hit-testing. Tests resolved actions.

When a test fails, ask which layer you're actually driving. Both are legitimate; knowing which is exactly how you debug without guessing. 🩺

## 🪄 PART III — THE HARNECIENT HACK (THE CORE PATTERN) 🧠🛠️

### The Six Components (Each One Is Required)

| # | Component | What It Means |
|---|---|---|
| 1 | **Plain API calls only** | `POST /api/chat` with exactly `{"model":"<anything>","stream":false,"messages":[...]}`. No `tools`, no `format`, no special schema. Works on ANY model. |
| 2 | **Persona file + simple plain-text question** | System persona actively forbids structure: "Give short, direct, plain-text answers — never a list, never markdown, never JSON." Then ask ONE simple question. |
| 3 | **Tolerant extraction** | `json_parser.+x` strips ` ```json ` fences defensively, walks dot-notation paths, unescapes. Whatever mess comes back, we try to read it. Tolerance is not a luxury — it's the interface. |
| 4 | **Deterministic tool dispatch** | **The model never picks a tool.** The app does. Keyword match → run tool → fold result back in. The model's job is to be a cheap text generator, never a router. |
| 5 | **Real, player-visible artifacts** | The "tool" writes REAL files (`data/cases/<id>/<side>_case.txt`) that grow turn by turn and can be opened directly. The audit trail is the artifact. |
| 6 | **Hand-hold + fallback everywhere** | Every step has a non-LLM fallback. Noisy output is tolerated, not rejected. The hack never depends on the model being clean. |

### 🎨 The Golden Rule: DESCRIBE, Don't CLASSIFY
**Small models describe reliably. They classify unreliably.** So we use them for raw material, and we use code for decisions.

**The judge pattern:**
1. 🗣️ Ask the model to compare in its own words — "In two sentences, which side has the stronger case and why?"
2. 🧮 Feed that text into a deterministic, hand-authored keyword scorer (`classify_comparison()`)
3. ⚖️ Tiebreakers, in order: argument count → document length → default
4. **Code decides, always.** The model produces the clay. We sculpt the statue. 🗿

> **⚠️ PITFALL 69 / xyzos-standards §42:** Never let the LLM be the final decider. Keep outcome decisions out of the LLM; use the LLM for raw material, and score it yourself.

### 💥 War Stories (Why We Don't Trust Models)

**The Directory Crash (LEARNINGS.md §9):**
The 3B, rambling on a harmless prompt, embedded a fake Python `readfile ./example.txt` dict in its reply. Our parser accepted it, and the unparseable path resolved to... the working directory. On Linux, `fopen()` on a **directory succeeds**. `fseek()` returns 0. And `ftell()` returns... LONGMAX. 9.2 quintillion. Our code then did `malloc(LONGMAX + 1)` and the process segfaulted. 💥

**Fix:** `readwhole()` now rejects any size <= 0 or bigger than 8MB before allocating. **Never trust paths or sizes that came out of a model.** 📜

**The 8B Drama:**
Even the "smart" 8B (`llama3-groq-tool-use:8b`) does native tools. Native readfile PASSES. Native execcmd PASSES. But ask it to read-then-edit and it fires both calls in parallel — editing before the read lands — guesses the wrong search block, and then hallucinates success. It believed it fixed a bug it never touched. 🎭

**Conclusion:** No model routes tools. Only we do. That's why the hack isn't a workaround — it's the better architecture.

### 🔄 The Proposed FSM Pipeline (Not Built Yet, Fully Designed)
```
state = INIT
plan = [] # ordered list of (tool, args) — built once, not re-decided per step
while state != DONE and state != FAILED:
    case state:
        INIT: plan = build_plan(goal, tool_registry); state = EXECUTE
        EXECUTE: step = plan[cursor]; result = dispatch_tool(step.tool, step.args)

```

├── condition.pdl   — the trigger + conditions for firing (if)

### The Runtime Flow
```
Event triggers → condition decides → PAL list runs → each command does its thing

**Multi-page rule:** The runtime picks the **highest-numbered page whose conditions are met**. Page 3 can say "boss is dead → victory text", page 1 can say "no boss yet → hint". ## 💡 PART XIV — BRAINSTORMING SOLUTIONS & APPLICATIONS 🧩

### 1. The "Fill-in-the-Blank" Code Generation Pattern
**Instead of asking a model to generate a whole file** (which fails — see §8.2/8.3 of EVENTS-PAL-BUILDOUT-PLAN.md), **give it a verified template and ask it to fill in 2-4 blanks.**

```
Template:  li x15, 6
           li x13, {{KEY}}
           ecall "{{PATH}}" "{{KEY}}"
           addi x12, x12, {{DELTA}}
           li x15, 7
           ecall "{{PATH}}" "{{KEY}}"
           halt

Model job: Extract 3 short facts from natural language
Harness job: Substitute into template, run, verify
```

**Application:** This applies to EVERY repetitive task — event commands, test harnesses, UI layouts, config files. The model never touches the boilerplate. It only ever fills the blanks. 🧩

### 2. The "Ops Bank" / Mini-Prompt Library
Build a bank of known-working primitives:
```
prisc_ecalls.txt    — one line per ecall: name, args, one-line description
pal_templates/      — parameterized .pal templates with {{BLANK}} placeholders
house_ops.txt       — existing op binaries: name, args, description
```

A `FILL_TEMPLATE` plan-step reads a `.tmpl` file, asks the model ONLY for the blank values, substitutes deterministically, and hands the result to the existing STEP/APPROVE + verification machinery. **This is the natural evolution of DESCRIBE-then-resolve applied to code generation.** 🏦

### 3. The "Self-Coding" Loop (Proven, But Needs More Data)
A harness can ask a model for a one-line shell snippet, write it to a file via the tool-approval path, and verify by actually RUNNING the script (stdout content AND exit code, not just grepping).

**Real finding:** For narrow, single-line code-gen tasks where verbosity is the failure mode, **a smaller Harnecient model can be MORE reliable than a larger one.** `gemma3:1b` beat `stable-code:latest` on a self-coding task because it doesn't over-elaborate. 🐎

### 4. The "Choose Model Automatically" Pattern
A cheap classifier model looks at the upcoming task and picks which worker model should handle it — but using DESCRIBE-not-CLASSIFY:

1. Ask the model to **describe** the task's shape in one plain sentence
2. Count real structural signals in that description (commas, "and" occurrences — a genuine proxy for "how many parts did the model enumerate")
3. Compare against `COMPLEXITY_THRESHOLD` (tunable joint, default 2)
4. Pick the worker model

**Verified 4/4:** simple task → 0 signals → `gemma3:1b`; complex task → 4 signals → `stable-code:latest`. Both switches independently verified against real live state. 🎛️

### 5. The "Observation Log" as Training Data Substrate
Every STEP/NAVIGATE decision appends one line to `observations.log`:
```
TS | KIND | GOAL | RESOLVED_LABEL | RESOLVED_IDX | VERDICT
1786634899 | NAVIGATE | switch model | Model: gemma3:1b | 8 | PASS
```

This is valuable regardless of which future approach gets built on top: a human auditing harness reliability, a future heuristic reweighting pass, or eventual RL all need the SAME underlying dataset. **Building it now costs almost nothing and is never wasted work.** 📊

### 6. The "Clock as Event" Pattern
The clock cell's own event package (`#.desktop/clocks/<id>/event_pkg/`) is editable via event-ez. A reminder can fire an event or a common event. **"Clock is like an event: it doesn't have to be common but can still be common."**

**Application:** ANY time-based trigger in any system can be modeled this way. Alarm clocks, scheduled tasks, timers in games — all the same pattern. ⏰
