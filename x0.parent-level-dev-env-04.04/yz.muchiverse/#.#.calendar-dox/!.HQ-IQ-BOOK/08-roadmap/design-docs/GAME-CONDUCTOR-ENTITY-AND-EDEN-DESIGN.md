## 1. The pattern: a conductor entity ("game start entity")
A **conductor** is an ordinary entity (a button glyph such as 🔘 on the desk) whose job is to **run one game**. It is the answer to "how does a game start without the Player menu": the button *is* the start, and its **context menu is the game's control panel**.
- **Context menu (METHOD rows in its `meta.pdl`):** `Setup`, `Start`, `Pause`/`Resume`, `Speed`, `Save` / `Load` (slots), `Rewind`, `Status`, `Add participant`, `Reset`, `Stop`. Each row fires an event page; nothing is hardcoded in the renderer.
- **Appears as a toy:** a `toy.pdl` makes it listed in the taskbar Toys cell (the Toys scan lists any directory under the house root, `@.apps`, `&.widgits`, `&.hq-apps` that has `toy.pdl`). So Eden is reachable from Toys *and* as a button on the desk.
- **Owns the game's manifest** (`game.pdl`-shaped: `GAME` title, `SETUP` rows, `PARTICIPANT` rows, `KIT` rows, the scenario seed), the **main clock** of the game, and the **game's save slots**. It does not own its participants' identity.
- **Does the same for every game:** Eden now; **a `dsr-test` conductor next** (the owner expects one); the digipet, ring board and Footrace Fu already have New Game rows that a conductor would generalize. One pattern to compare with the other ways of running games (Player menu play mode, `game.pdl`-driven start): this is **experiment 1**, and the question it answers is "which way are we comfortable running games thru".

## 2. Setup: kits, grants and not being tied to the entity
- **Participants** are *any entities* (Asa, Ava, an entity spawned from a template, a DSR store). The conductor **attaches** a game to them, it does not become them.
- **Kit** = a bundle of what a role needs, given at setup as **ledger rows**: `GRANT | game | entity | kind=item|skill|param|state | id | amount | ts` using the registered commands (`change_items`, `change_skill`, `change_parameter`/`change_hp`, `change_state`). Examples: Asa and Ava each get `seed x5`, `water jug`, `hoe`, HP 20, skills `plant`, `water`, `collect`, `trade`, `talk`.
- **Not tied to the entity:** grants are **idempotent and reversible** (the ledger knows what the game gave, so `Stop`/`Reset` can take back exactly those items/skills and leave the entity's own data alone), a participant can **leave and join** mid-game, and the same kit can be applied to a **dynamically spawned** entity (a template copy via the `desk_copy_op` pattern, with its own fresh identity, never a copied one) or to an **existing** entity (Asa, Ava on the owner's desk).
- **Dynamic spin-up:** `Add participant` creates an entity from a template, places it on the desk, applies a kit, and registers it in the manifest; `Remove participant` retires it (tombstone, per the essence design) rather than deleting.

## 3. Items imply skills, skills offer actions ("act")
- **Item rows** declare what they enable: `ITEM | seed | label | grants_skill=plant | nutrition=0 | ...`; `ITEM | jug | grants_skill=water`; `ITEM | hoe | tool=farm`. Holding the item makes the skill **available** (RPG Maker: skill learned or granted by an item/equipment).
- **Skill rows** define the action: `SKILL | plant | needs_item=seed | needs_place=field | cost_ticks=1 | event=eden_plant`, similarly `water`, `collect`, `trade`, `build`, `talk`, `eat`, `rest`, `study`.
- **The "act" menu is generated**: the entity's context menu has an **Act** group whose rows are the **skills it currently has and can afford** (inventory-driven, like the digipet's Feed). A human clicks an act; an **agent seat** picks one by the **same event page**.
- This is the existing RPG Maker model (actors, skills, items) plus a data table; no new engine.

## 4. Autonomy and the clock: what happens as time passes
- The conductor's **main clock** drives a **Day Tick** common event (as in the digipet and DSR step 1), which, per participant: applies needs (hunger rises), applies **weather**, grows crops, and lets an **agent seat** take its **acts** for the day.
- **Agent seat** = a deterministic, seeded **weighted choice** among currently available acts, with the **critical-need gate** (digipet M1): if hungry, eat; if a seed and a field exist, plant; if a crop is ripe, collect; if surplus, trade; sometimes talk. Weights are tunables in a `.pdl` (and later tomom/TEARIT-tunable; models never decide, they may only describe). A **human** seat uses the same acts by clicking.
- **Weather:** a clock-driven event: each day a seeded roll against season/rain chance sets `weather=rain|clear|...`; rain **waters fields** (crops grow without the water act), affects mood/needs later. Rain rate is a tunable; reuse WSR's `weather_update` formula only if it fits, else a small rule (to be checked, not assumed).
- **Farming:** a plot is an entity or a variable row (`CROP | plot | kind | planted_day | water | stage`); plant -> grows N days with water -> ripe -> collect yields food/seed. **Building:** acts that spend items for structures (a hut raises shelter, a field gives plots). **Trading:** Asa and Ava exchange items/coins between them and, later, with stores. **Talking:** `talk` writes messages through the **phone/ledger** (each entity's phone), so conversations are append-only rows that can be read, scored, and later word-bank-tagged.
- **Learning and training nodes:** skills have **levels (exp)**; a **node graph** (`NODE | skill | requires | exp_to_unlock`) lets practice or **school** unlock more (the school design: lessons, report card, accelerated age). Going to school = a clock-scheduled attendance event (or enrollment) as designed; **buy stocks** = the DSR economy hooks (section 6).

## 5. Save/load/rewind through the button
The conductor's context menu rows **Save / Load / Rewind** call `game_snapshot_op` over the **game's tree** (the conductor folder, its participants' game-relevant files, the clock state and schedule ledger via `--extra`), exactly what the clock-restore harness proved on scratch roots. **Load while entities run** is still the unsolved step (`DSR-AS-PHYSICAL-WSR-PLAN.md` section 5): the conductor is the natural place to do it (pause the clock, restore files, signal each participant to reload, resume). Timeline-fork and cones-never-rewind rules apply. All rehearsed on scratch copies first; live user data (Asa and Ava live on the owner's desk) is **not touched** until the owner approves.

## 6. How Eden and DSR evolve into each other
Same blocks, different scale: Eden is two entities with items and skills on a field; DSR is dozens of entities (stores, banks, castles, populations) with money. The bridge is **data and kits**: as Eden's farm produces surplus, `trade` goes to a **store entity**; stores/banks are just more participants with their own kits; **population pools** appear when Eden grows past a few named citizens (DSR-SIMULATION L2); the Eden conductor and the dsr-test conductor can share a clock chain or one can be a child "page" of the other (a chained clock, section 7.1 of the clock doc). So the Eden experiment is **the beginning of the DSR page**, not a separate game: the same Day Tick, the same acts, the same ledgers. **Note for dsr-test:** it gets its own **DSR conductor** (button) with the same context menu, kits for stores/banks/castles/populations, and DSR step 1's day tick; build it after the Eden conductor proves the pattern.

**Proposal (inferred; the owner may rename): reuse the ghost pal type with `role=soul`.** One soul ghost per participant, bound 1:1 (`SOUL | entity | ghost_id | mode | since`). A soul is the entity's **agent seat** made visible: it is the thing that picks which act to take. Nothing new is invented: the acts, the day tick and the ledgers are the section 3 and 4 ones.
**Automation versus soul (keep them separate):**
- **Automation = clock events, deterministic, no ghost.** A garden is `common:garden_tick` on a daily schedule (water dry plots if the jug holds water, collect ripe crops, replant if seeds remain), exactly like the digipet Day Tick. It needs no mind, is reproducible by seed, and works for any entity with the right items. This is the "garden automation".
- **Soul = judgment, chooses among acts.** It decides priorities (eat vs plant vs trade vs talk vs study) with weights. Same `act.weight.*` joints as the roadmap's Joint contract.
**Soul modes (the toggle, a switch on the entity plus a menu row `Soul: off|assist|auto|train`):**
| mode | who picks the act | learning |
|---|---|---|
| `off` (manual / self control) | the human clicks Act; the entity does nothing on its own except clock-driven automation events | none |
| `assist` | the soul proposes one act per tick (a `CAND` row on the entity's phone/history); the human approves or ignores | proposals only |
| `auto` | the soul acts through the same act pages, inside the critical-need gate (hungry: eat first), with a per-day action budget | weights frozen |
| `train` | like auto, on a **scratch copy or a sandbox game**; weights may be proposed to the review file after the day's Watch rows | proposals reviewed (Joint contract: grow, learn, train, heal; default autonomy 0) |
Switching modes appends `SOUL|mode|ts|by=human` to the entity ledger. `off` is always reachable and wins: a human click overrides the soul. A soul **cannot** grant itself items, change the clock, change another entity, or edit its own weights without the gate.
**Where the soul gets its brain (cheap to expensive):** (1) a weighted table with the seeded choice (v0, deterministic, free); (2) a local student model; (3) HORN worker. Models only **propose acts from the currently available list**; deterministic code validates and executes (the house law: models never decide numbers).
**Phones in the game:** (a) **talking**: `talk` writes to the other entity's phone inbox (single writer = the server pattern, so the conductor plays server); the history file is the readable conversation and later word-bank-tags the words used. (b) **tasks between entities**: Asa posts `kind=task` ("trade 2 seeds for 1 food") to Ava's phone; her soul (or she, by click) answers `answer/done/fail`; trades settle through the same cash_transfer/items ledger. (c) **human tasks**: a soul that needs a person (approve a purchase, a risky act) sends `ask-human` and the phone glyph rings. (d) **conductor as server**: the Eden conductor routes messages and writes the day report to each phone, so a person can follow the story by reading phones.
**Ghosts of the dead:** when an entity dies (the `entity_died` event, not built), its soul detaches and becomes a graveyard ghost (a record of the character's history and weights, readable on the 🪦). Reviving or reincarnating into a new entity with inherited weights is an open design question (and the natural "learning across lives" joint).

## 12. Correction to section 11 (owner, 2026-10-07): a soul IS a ghost, and it possesses the entity
Section 11 treated the soul as a separate role and as only an "agent seat". The owner's clarification replaces that:
- **Soul and ghost are the same kind of thing** (one pal type, the 👻 of `GRAVEYARD-GHOSTS-DESIGN.md`). "Soul" is just the name for a ghost that is **associated with a living, active entity**.
- A soul is the **task/quest doer for its entity**. Its tasks are quests on its own list (the grave's quest model: id, status, log). You **manage the entity by managing its soul's tasks**; the soul **tells the entity what to do**, which is possession in the sense of `XELECTOR-CURSWORD-POSSESSION-DESIGN.md` (possessor to body: `possessed_id`, `last_possessed_id`), here with the soul as possessor and the entity as body.
- A soul can be **talked to**, exactly as one talks to any ghost entity (its phone / chat history), by the owner, by other entities, or by other souls. It can **grow and evolve** (its weights, word bank, skills and history accumulate and are reviewed under the Joint contract).
- It is **portable**: if the body dies the soul can still be saved (its folder and history persist as an ordinary ghost) and can **possess other entities**, carrying its weights and history (the "learning across lives" joint). A body without a soul is a plain entity run by automation, or by a human click.
**Data model update (replaces the `SOUL` row of section 11):** `POSSESS | ghost_id | entity_id | since | by | mode` appended to the ghost's ledger and mirrored as `possessed_id` on the entity; releasing or dying appends `RELEASE | ghost_id | entity_id | ts | reason=death|moved|human`. One ghost possesses at most one body at a time; a body has at most one possessor (extension: stacked possessors is an open question). The four modes (off/assist/auto/train) remain the **possession mode** of the link, not of the ghost. Quests assigned to a ghost survive moving to a new body; each quest records which body it ran on.
**Consequences:** (1) Asa's and Ava's souls are two ghosts, listed on the 🪦 board with their quests and history; (2) the Eden conductor hands quests ("plant before the rain", "trade seeds") to ghosts rather than coding the choice into the entity; (3) `possess/release/transfer` are menu rows on the ghost and on the entity, with the conductor refusing a transfer into a body that already has a possessor; (4) death moves the ghost to the graveyard list and keeps it eligible for `possess` on another body; (5) the pc-hq possession key chain (xelector, cursword, hero) and the game possession model are the same mechanism at two scales and should share the `possessed_id` convention. Still design only; Eden v0 keeps the weighted-table seat until the first `POSSESS` row is built.

(4) `common:<name>` resolves to one package per house, so a second game on the same house cannot reuse the event. (5) `game_snapshot_op` cannot overwrite a slot, and Load needs `--prune` or participants created after the save survive it. (6) Load while entities run is still not solved for live processes; here Load is safe because the game is files and the clock is stepped, not a daemon with entities holding state in memory.

### COMPARISON NOTE for section 8 (conductor vs Player menu play mode vs `game.pdl` start)
- **Easy with the conductor:** one place owns the game's manifest, clock, ledgers and save slots, so Save/Load/Reset are just rows that call the one snapshot op over a named tree; participants are attached by kit and detached by tombstone (dynamic add/remove worked first time, own data intact); the same pages run from the menu, from `sh -c`, from the clock and from the harness, so the player path and the test path are the same code; discoverable in Toys by file presence.
- **Hard with the conductor:** the context menu is static data, so anything that needs an argument (which slot, which name, which act for which entity) is a family of triggers or a generated file (`acts_menu.pdl`); a conductor cannot see the house root without wiring, and setup order matters (Setup before Start is enforced only by an error file); nothing yet makes "Play ON" start it, and a live desk still needs a row for the folder.
- **Versus the Player menu:** the Player menu is global and knows the active desk, so it has the house root and the play-mode flag for free, but it has no per-game state, no slots, and a game cannot be run without the menu; the conductor gives the opposite trade (own state, no ambient context). Best next step to test: a Player-menu row that merely fires the conductor's Start/Status triggers.
- **Versus `game.pdl`:** `game.pdl` is a good manifest (the conductor uses the same shape) but is passive: nothing runs it, grants from it, saves it or ticks it. The conductor is `game.pdl` plus a verb set. Recommendation after v0: keep `game.pdl` as the manifest format and use the conductor as the runner; do not choose between them.
- **Not answered by v0:** load while live entity processes hold memory, play-mode composition, a desk button, the real taskbar listing, and whether Asa and Ava (real, on the owner's desk) accept grants the way scratch copies do.

## Build report: eden button install (2026-10-07, claude, branch eden-button-work)

Goal: make the Eden conductor a playable desk button. Three findings fixed, installer and harness added; **no GUI run, no live install** (everything on /tmp scratch livedesks).

- **Finding 1 (nothing advanced the game):** `eden_op` verbs `daemon-start` / `daemon-stop` / `daemon-status`. Start = fork + setsid + execv of `<G>/lc.+x <G> daemon` (no shell, no system()), env `LC_CLOCK_NO_POPUP=1`, `LC_CLOCK_EVENT_RUNNER=<G>/&.widgits/digipet/ops/+x/event_page_op.+x`, `EVENT_PAGE_TRIGGER=parallel`, `EVENT_PAGE_PRISC=<G>/prisc` (from wiring keys `event_runner` / `prisc`; an already-set variable is never overwritten), pid in `<G>/eden_daemon.pid`, `DAEMON|...` rows in the control ledger. Stop = SIGTERM to the recorded pid only, and only when `/proc/<pid>/cmdline` argv0 is the lc binary; a live pid that is not the clock makes both start and stop REFUSE (never signalled). Start twice = one process. `WIRING | daemon | 1` (written by the installer; default off so eden_loop/eden_conductor are unchanged) makes Start game and Resume start it, Stop game and Pause stop it. No stop-flag file: SIGTERM to the recorded pid is the one mechanism. New **Next day** row (page 17, verb `nextday`): `cmd g1 advance 1d` then `step 0` (exactly one Day Tick); with a daemon running only the advance is queued (lc `step` must not run beside a daemon), the daemon fires it.
- **Finding 2 (layout):** `install_eden` builds `<livedesk>/eden_game` (= G) as `G/game/conductor`, `G/lc.+x`, `G/gso`, `G/prisc`, `G/store/`, `G/common_events/eden_day_tick`, `G/&.widgits/digipet/ops/+x/event_page_op.+x` and the desk pal `<livedesk>/pals/eden_button/` (pal.pdl, glyph.txt, meta.pdl, ctl.sh; no hash/uid).
