## 1. The pattern: a conductor entity ("game start entity")
A **conductor** is an ordinary entity (a button glyph such as 🔘 on the desk) whose job is to **run one game**. It is the answer to "how does a game start without the Player menu": the button *is* the start, and its **context menu is the game's control panel**.
- **Context menu (METHOD rows in its `meta.pdl`):** `Setup`, `Start`, `Pause`/`Resume`, `Speed`, `Save` / `Load` (slots), `Rewind`, `Status`, `Add participant`, `Reset`, `Stop`. Each row fires an event page; nothing is hardcoded in the renderer.
- **Appears as a toy:** a `toy.pdl` makes it listed in the taskbar Toys cell (the Toys scan lists any directory under the house root, `@.apps`, `&.widgits`, `&.hq-apps` that has `toy.pdl`). So Eden is reachable from Toys *and* as a button on the desk.
- **Owns the game's manifest** (`game.pdl`-shaped: `GAME` title, `SETUP` rows, `PARTICIPANT` rows, `KIT` rows, the scenario seed), the **main clock** of the game, and the **game's save slots**. It does not own its participants' identity.
- **Does the same for every game:** Eden now; **a `dsr-test` conductor next** (the owner expects one); the digipet, ring board and Footrace Fu already have New Game rows that a conductor would generalize. One pattern to compare with the other ways of running games (Player menu play mode, `game.pdl`-driven start): this is **experiment 1**, and the question it answers is "which way are we comfortable running games thru".

## 2. Setup: kits, grants and not being tied to the entity
- **Participants** are *any entities* (Asa, Ava, an entity spawned from a template, a DSR store). The conductor **attaches** a game to them, it does not become them.
- **Kit** = a bundle of what a role needs, given at setup as **ledger rows**: `GRANT | game | entity | kind=item|skill|param|state | id | amount | ts` using the registered commands (`change_items`, `change_skill`, `change_parameter`/`change_hp`, `change_state`). Examples: Asa and Ava each get `seed x5`, `water jug`, `hoe`, HP 20, skills `plant`, `water`, `collect`, `trade`, `talk`.
- **Not tied to the entity:** grants are **idempotent and reversible** (the ledger knows what the game gave, so `Stop`/`Reset` can take back exactly those items/skills and leave the entity's own data alone), a participant can **leave and join** mid-game, and the same kit can be applied to a **dynamically spawned** entity (a template copy via the `desk_copy_op` pattern, with its own fresh identity, never a copied one) or to an **existing** entity (Asa, Ava on the owner's desk).
- **Dynamic spin-up:** `Add participant` creates an entity from a template, places it on the desk, applies a kit, and registers it in the manifest; `Remove participant` retires it (tombstone, per the essence design) rather than deleting.

## 3. Items imply skills, skills offer actions ("act")
- **Item rows** declare what they enable: `ITEM | seed | label | grants_skill=plant | nutrition=0 | ...`; `ITEM | jug | grants_skill=water`; `ITEM | hoe | tool=farm`. Holding the item makes the skill **available** (RPG Maker: skill learned or granted by an item/equipment).
- **Skill rows** define the action: `SKILL | plant | needs_item=seed | needs_place=field | cost_ticks=1 | event=eden_plant`, similarly `water`, `collect`, `trade`, `build`, `talk`, `eat`, `rest`, `study`.
- **The "act" menu is generated**: the entity's context menu has an **Act** group whose rows are the **skills it currently has and can afford** (inventory-driven, like the digipet's Feed). A human clicks an act; an **agent seat** picks one by the **same event page**.
- This is the existing RPG Maker model (actors, skills, items) plus a data table; no new engine.

## 4. Autonomy and the clock: what happens as time passes
- The conductor's **main clock** drives a **Day Tick** common event (as in the digipet and DSR step 1), which, per participant: applies needs (hunger rises), applies **weather**, grows crops, and lets an **agent seat** take its **acts** for the day.
- **Agent seat** = a deterministic, seeded **weighted choice** among currently available acts, with the **critical-need gate** (digipet M1): if hungry, eat; if a seed and a field exist, plant; if a crop is ripe, collect; if surplus, trade; sometimes talk. Weights are tunables in a `.pdl` (and later tomom/TEARIT-tunable; models never decide, they may only describe). A **human** seat uses the same acts by clicking.
- **Weather:** a clock-driven event: each day a seeded roll against season/rain chance sets `weather=rain|clear|...`; rain **waters fields** (crops grow without the water act), affects mood/needs later. Rain rate is a tunable; reuse WSR's `weather_update` formula only if it fits, else a small rule (to be checked, not assumed).
- **Farming:** a plot is an entity or a variable row (`CROP | plot | kind | planted_day | water | stage`); plant -> grows N days with water -> ripe -> collect yields food/seed. **Building:** acts that spend items for structures (a hut raises shelter, a field gives plots). **Trading:** Asa and Ava exchange items/coins between them and, later, with stores. **Talking:** `talk` writes messages through the **phone/ledger** (each entity's phone), so conversations are append-only rows that can be read, scored, and later word-bank-tagged.
- **Learning and training nodes:** skills have **levels (exp)**; a **node graph** (`NODE | skill | requires | exp_to_unlock`) lets practice or **school** unlock more (the school design: lessons, report card, accelerated age). Going to school = a clock-scheduled attendance event (or enrollment) as designed; **buy stocks** = the DSR economy hooks (section 6).

## 5. Save/load/rewind through the button
The conductor's context menu rows **Save / Load / Rewind** call `game_snapshot_op` over the **game's tree** (the conductor folder, its participants' game-relevant files, the clock state and schedule ledger via `--extra`), exactly what the clock-restore harness proved on scratch roots. **Load while entities run** is still the unsolved step (`DSR-AS-PHYSICAL-WSR-PLAN.md` section 5): the conductor is the natural place to do it (pause the clock, restore files, signal each participant to reload, resume). Timeline-fork and cones-never-rewind rules apply. All rehearsed on scratch copies first; live user data (Asa and Ava live on the owner's desk) is **not touched** until the owner approves.

## 6. How Eden and DSR evolve into each other
Same blocks, different scale: Eden is two entities with items and skills on a field; DSR is dozens of entities (stores, banks, castles, populations) with money. The bridge is **data and kits**: as Eden's farm produces surplus, `trade` goes to a **store entity**; stores/banks are just more participants with their own kits; **population pools** appear when Eden grows past a few named citizens (DSR-SIMULATION L2); the Eden conductor and the dsr-test conductor can share a clock chain or one can be a child "page" of the other (a chained clock, section 7.1 of the clock doc). So the Eden experiment is **the beginning of the DSR page**, not a separate game: the same Day Tick, the same acts, the same ledgers. **Note for dsr-test:** it gets its own **DSR conductor** (button) with the same context menu, kits for stores/banks/castles/populations, and DSR step 1's day tick; build it after the Eden conductor proves the pattern.

## 7. First build (Eden conductor v0, alpha, scratch only, harness first)
`&.widgits/eden/` (template files; never writes to live user data): conductor entity (button glyph, `toy.pdl`, context menu rows Setup/Start/Pause/Save/Load/Status/Add participant/Reset), `scenario.pdl` (participants: scratch copies named like Asa and Ava, seed), `kits.pdl`, `items.pdl`, `skills.pdl`, `nodes.pdl` (training nodes), Day Tick pages (hunger, weather, crop growth, agent acts, talk), tiny ops only where the registry cannot express a rule. **Harness:** setup grants kits idempotently and Reset takes back exactly them; a 20-day seeded run where both participants plant, water or are rained on, grow, collect, eat, trade and talk (rows exist for each; determinism; invariants: food conserved, no negative items, hunger within bounds); weather days appear; an entity added dynamically gets a kit and acts; a participant removed leaves its own data intact; save at day K, mutate, load, continue equals the uninterrupted run; a case shown able to fail. Not in v0: school, stocks, building beyond one hut, any window beyond the entity menu, live install.

## 8. Comparing ways to run a game (what the experiment should tell us)
Criteria to record after v0: setup effort; save/load reliability; can it spin up/attach entities dynamically; independence from entity identity; discoverability (Toys + button); control without the Player menu; how it composes with play mode (should Play ON also start the conductor?); failure modes. Candidates: **A** conductor button (this doc), **B** Player menu play-mode hook, **C** `game.pdl`-driven start. Report the comparison in this doc after the build.
