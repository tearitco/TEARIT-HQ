# rpg-edit-hq: a "palettes" left sidebar instead of the "pets" one (research only, 2026-11-02; nothing built)

Owner ask: remove the pets sidebar from the editor; add a minimizable left sidebar "palettes" showing the palette list, or one palette's tiles, with a back button (href-like); tiles stacked vertically (the taskbar shows them horizontally). Keep pets as a minimized bar that SWAPS with palettes when chosen. Also: the pets bar has no scroll thumb in short windows.

## What exists today (read, not run)
- File: `@.apps/rpg-edit-hq/board/pchq-board.xhtpm`. Left bar = `<row id="side-l" class="canvas-overlay-left ov-pin ov-chrome pchq-hotbar theme" show="${side_left}">` (pets, stats, party buttons). Right bar `side-r` = chat. The footer cells `sl-toggle` ("pets") / `sr-toggle` ("chat") run `layout-studio/ops/+x/side_toggle.+x board/state/sides.txt side_left|side_right toggle`; each bar's `_` runs it with `hide`. Flags live in `board/state/sides.txt` (`side_left=1`, empty = hidden). Width from `board/side_style.pdl` (`STYLE | pin_width | 160`). A pinned bar TAKES its width out of the canvas (renderer `khtpm_core_render.c` ~6929-7140).
- **The missing scroll thumb is a one-word fix.** The renderer already has class `ov-scroll` for pinned bars (owner request 2026-10-23, ~line 7130: parks items that do not fit off screen, registers the generic scrollbar: track, thumb, arrows, wheel, page keys). rpg-pet, cdda-hq, rpg-space, gta-hq, df-hq, rpg-dust, civ-rpgce, dsr-rpg, tcg-rpgce, mcl-hq use it; rpg-edit-hq's `side-l` and `side-r` do not (grep count 0). Add `ov-scroll` to the class list. Not tried: whether it behaves with a `repeat` of image tiles.
- `href`: the renderer has an `objects.pdl` href + BACK page stack (`khtpm_core_render.c` ~19812-19823, 22371), made for `.chtpm` pages. Not verified for `.xhtpm` pinned bars. A pinned bar is a `row` inside one page, so the simpler, proven mechanism is the one this window already uses everywhere: a state key + `show="${...}"` (same as `side_left`).
- Palettes data: categories are rows in `&.widgits/palettes/pallets.pdl` (`CATEGORY | key | label | ...`: emojis, elements, rmmv, piececraft, cdda, df, doom, paint, ...). In the taskbar each opens a window `palettes-<key>.xhtpm` with a swatch grid fed by a per-category manager (`palettes_manager`/`elements_palette_manager`), and `palettes_menu.sh place|arm-rmmv|arm-pc|arm-cdda|arm-df|arm-doom ...` arms a brush. rpg-edit-hq itself has NO palette code today: its tiles come from `catalog.pdl` (shop items from RPG Maker sheets). So "place from the palette" needs a decision on which palettes feed THIS editor (see questions).
- Sprites in item labels exist (`sprite="${ent.sprite}"` + `sprite-inline sprite-big` in the footer), so a vertical list of tile thumbnails is a `repeat` of `<item sprite=...>` rows.

## Proposed shape (for approval)
1. Two pinned left bars in the same slot: `side-l` (pets, kept, default minimized) and a new `side-p` (palettes). A single state key `left_mode=pets|palettes|none` in `sides.txt`, written by one op (extend `side_toggle` or a tiny new verb); the footer cells "pets" and "palettes" set the mode, `_` sets none. `show="${left_pets}"` / `show="${left_palettes}"` so only one is drawn = they swap places.
2. `side-p` has two views driven by `pal_view=list|tiles` + `pal_key=<category>`: LIST = one button per `CATEGORY` row (from pallets.pdl, via the projector); TILES = a "< back" item (sets `pal_view=list`) then the category's tiles as a vertical `repeat`; clicking a tile arms the brush (the same `palettes_menu.sh arm-*` / placer chain the taskbar uses, or the editor's own placer).
3. Add `ov-scroll` to both bars (fixes the missing thumb; needed anyway for long tile lists).
4. Width: 160 px holds ~2 tiles of 48 px per row only if the bar can lay out a grid; a plain vertical list is 1 per row. Owner said "vertically", so 1 column, scrolling.

## Open questions (owner)
- Which palettes should the editor show: all categories from pallets.pdl, or only the ones that make sense for a pets-like room (rmmv, emojis, piececraft, cdda, df)? Does choosing a tile place a floor tile, furniture, or arm the existing placer?
- Where do the tiles come from at runtime: reuse the taskbar's palette managers (extra processes per open palette; footprint) or read the category's tile list files directly in `rpg_edit_hq` (lighter)?
- "href": OK to implement with the state-key mechanism above instead of a real href page stack?
- Should the pets bar stay minimized by default, and should the choice survive a restart (sides.txt already persists)?

## Step 4 RESEARCH (2026-11-02): placement - what the Move placer is, and what a placed voxel can be. Nothing built.
**Found, read from code unless marked run:**
1. **The 3D engine of the editor is not running.** RUN: no `bv_render_3d` process; the session's `rgb_frame.raw` was last written 22:37 (about 50 min before this check); the in-view clock reads 53:11 in every screenshot of this day. The 3D pictures in steps 1-3 are therefore a stale frame (the side bars are live, they are drawn by the window itself). The known recurring "engine died" problem (rpg-space-board-driving skill, section 7). A live 3D placement test needs the editor board relaunched (`board_ctl recover`-style), which closes and reopens the owner's editor window.
2. **The Move placer** (`bv_menu_input.c` ~400-455, `bv_move_range.c`): the file `pieces/display/move_range_matrix.txt` is the mode switch (present = Move active). While active: the green selector (`pieces/display/placer.txt`: armed, x, y, z) is moved by arrows, a typed cell ref + Enter jumps ("jump: g15_"), Enter with nothing typed = `bvr_confirm` (checks range + board edge, plans the animated path, closes), Esc cancels, z/x change z. For brush placement the same shape is wanted: a mode file (e.g. `pieces/display/brush_mode.txt`, written by `pal_side arm`), Enter = append one request row (x y z) to an append-only `place_requests.txt` and STAY armed, Esc = disarm + delete the mode file. This is a change to `bv_menu_input.c` (the collision file: placer work is what it is reserved for) and needs the engine rebuilt and the session relaunched.
3. **The editor's world is not the chunk files.** `rpg_edit_hq.+x` rebuilds each room (`pet_own_export_room`) and rewrites the book's `maps/rpg-edit-hq/<room>/map.txt`, `cells.txt`, atlas every time, so stamping a glyph into the chunk files (the piececraft-hq `pchq_place_cell.sh` way) would be wiped. Everything placed is a ROW in the editor's own ledger `state/house.txt` (`PLACE|id|ts|item|x|y|room`), `item` an index into `catalog.pdl` (an RPG Maker sheet tile); both the 2D painter (shared `petslike_core.c` `render()`) and the 3D export (a 1 high block over the floor cell, `rpg_edit_hq.c` ~431) draw it from `pl[]`. Rooms are 2D grids: a block is 1 high; **z from the placer cannot be used yet** (stack = future).
4. **A palette sprite is a `sprite.csv`** (header `# resolution=48`, then `r,g,b,a` rows, 48x48): not an RPG Maker sheet tile, so it is not drawn by either painter today.

**Proposal (needs a yes before building, it touches the shared core and the engine):**
- Make a voxel a normal furniture `Placed` row whose catalog item is generated from the brush: on arm, `pal_side` (or a new op) appends the sprite as one tile into a generated sheet `state/voxels_sheet.png` and a catalog row; the skin's existing sheet hook (`PET_SECTION 72`, how `!edit...` sheets are found) resolves that sheet. Then BOTH painters draw it with no new render code (2D/3D parity by construction), `house.txt` stays the single ledger, undo = the existing REMOVE row, and moves use the existing MOVE row.
- Cost/limits: `MAXI` (catalog size) is 40 in the shared core (one constant, nine games share it; raise it for this skin only if possible, else a separate voxel table); `check_place` rules apply (no overlap, walls); a sheet of generated tiles is a small PNG written only when a new brush sprite is first used.
- Placement trigger: the Move-placer shape above (mode file, Enter appends a request, consumer applies `PLACE` rows). Until the engine change exists, a keyboard path through the editor's own relay (`interact_relay.txt`, the editor daemon already follows the xelector) can place at the xelector cell, with no engine change.
- Placement mode: `place_mode` key (default `voxel`); modes beyond voxel later.

## Step 4 BUILT (2026-11-02): placing the armed brush as a voxel (editor side). What is proven and what is not.
**Built:** the armed brush (`board/state/brush.txt`) becomes a normal furniture item. `rpg_edit_hq.c` (skin sections 10, 48, 56, 72, 73, 76): `vx_item` reads the brush sprite's `sprite.csv` (48x48 RGBA), writes a one-tile PNG `state/vox/!v_<hash>.png` (own uncompressed PNG writer) and one catalog row in `state/voxels.pdl` (loaded after `catalog.pdl`, same columns); `vx_place` runs the house's own `check_place` then appends `BUY|..|0` + `PLACE|..` to `state/house.txt`, replays, and runs `export3d` so the 3D book is rewritten (0.34 s measured). Verb: `rpg_edit_hq.+x voxel <x> <y>`. Key: `b` (code 98) places at the selector cell (`xelector_01/state.txt` pos_x/pos_y) in the daemon's INT key loop. Undo = the existing `remove <id>`; move = the existing `place <id> x y`. Shared core `petslike_core.c`: `MAXI` 40 -> 200 and the sheet cache 24 -> 128 (both were too small for one generated item/sheet per sprite; rpg-pet compiled against it, the other seven games were not rebuilt). The daemon reloads the catalog when `voxels.pdl` changes size (section 48).
**Proven (run):**
- Scratch app inside the house (deleted afterwards): ledger rows correct; the PNG decodes (CRCs ok, 9264 raw bytes, first pixel 99,103,142 = the csv's first pixel); same sprite reuses one catalog row; the house rules apply ("spot taken by #1", "someone is standing there"); `export3d` with the voxel vs after `remove`: exactly ONE cell of the 3D `map.txt` differs (12,14: `f` vs `G`), `cells.txt` differs, and removing reverts it.
- LIVE editor (School room = the viewed room): `pal_side tiles piececraft` + `pal_side arm 6` + `voxel 12 14` -> `house.txt` rows, School `map.txt` cell (12,14) `.` -> `f`, `remove` + export -> `.` again.
