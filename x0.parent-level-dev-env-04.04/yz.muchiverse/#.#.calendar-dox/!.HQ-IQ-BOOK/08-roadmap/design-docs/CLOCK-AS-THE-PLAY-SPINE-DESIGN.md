# The game clock as the spine of play (design)

Status: DESIGN, 2026-10-07, claude. Nothing new built. Owner: "the clock is connected to play. It starts the clock for all entities in the game, chained off the main clock. It shows in the toolbar time (tb) or pc-hq. The clock is editable and customizable when the game is off, but can be used when it's on to schedule events, even per month, per year, etc., based on WSR-like time-based in-game ledger reader / game manager. ... Customizable: how it works in play is by how it's set up under Time. ... or events can be made to change the in-game clock ... like how WSR can be slowed or sped up."

## 1. What already exists (read in `&.widgits/livedesk-clock/ops/lc_clock.c` and the taskbar manager; pc-hq daemon header)
- **A real game-clock system** (`lc_clock`, the headless daemon, one binary with subcommands). Files under `#.desktop/clocks/`: `clocks.pdl` (`CLOCK|<id>|scope=<s>|desc=<d>`), one state file per clock (`gameclock0000.pdl`: `game_time_epoch_ms`, `tick`, `running`, `rate`), `reminders.pdl`, `endturn.txt` (a mailbox: `endturn <id> [ms]`), `daemon.pid`. The daemon is the **only writer** of `game_time_epoch_ms`, `tick` and `fired`. **Rates:** `off, cent, sec, min, hour, day` (a rate is game time per real time). **Calendar:** proleptic Gregorian from Year 0 A.D., Month 1, Day 1, 00:00. Scope values exist (`user`; others not verified).
- **Reminders = scheduled events:** `r<id>|clock=<id>|at=<game ms>|text=|event=common:<name>|note=|enabled=|fired=<wall ms>|repeat=`. When the clock's `game_time_epoch_ms >= at`, `fire_reminder` shows a popup and runs the named **common event** (`common_events/<name>` via `play_event.sh`, detached).
- **A taskbar clock cell** (cell 15, date/time) with clock/calendar menus (`khtpm_taskbar_manager.c`, "Cell 15 (date/time) clock menu"), and a manual **End Turn** via the mailbox.
- **pc-hq has its own clock daemon** (`pc_clock_daemon.c`): `world_01/state.txt` fields `game_time_epoch_sec`, `autotick_enabled`, `autotick_speed`; it advances the world tick once per game minute and moves the sun, moon and animals from the epoch. Both daemons use the same flock read-modify-write protocol, and the lc_clock header says so.
- **WSR** advances by day (`day_loop`, a near-stub that appends; WSR's own schedule line is `1_day ./day_loop`); I found in WSR only that the day cadence exists. **I did not find a "game manager ledger reader" there, and I did not read how WSR is slowed or sped up; I am relying on your description. Point me at the file and I will read it.**

## 2. Gaps found (important)
1. **`repeat=` is parsed and saved but never acted on.** `poll_reminders` skips any reminder whose `fired` is non-zero, so every reminder fires **once**; there is no "every day / month / year" recurrence yet.
2. **No catch-up.** If the clock jumps (rate change, fast-forward, load), a one-shot fires once when its time has passed, and a repeating schedule has no rule for the occurrences it skipped. A speed-up can silently skip daily work.
3. **Events are fire-and-forget:** the common event is started with a detached `system(... &)`; no watchdog, no wait, no result row (the house rule elsewhere is fork+exec+waitpid with a watchdog).
4. **No chaining:** a clock has `scope` but no `parent`/`ratio`; there is no per-entity or per-place clock derived from a main clock.
5. **Two clock implementations** (`lc_clock` in ms with rates; pc-hq's daemon in seconds with `autotick_speed`) are not linked: the pc-hq world time and the desktop game clock can disagree.
6. **No link between "play" and the clock:** starting/stopping/saving/loading a game does not start, stop or restore a clock (verify: `change_save_access`, `game_slot_op` and the clock files were not checked for this).
7. **Setup-when-off is not enforced:** nothing marks some clock fields as editable only while the game is off.

## 3. The design
**3.1 Play drives the clock.** Starting a play session sets `running=1` on the game's **main clock** (one per game/session); pausing or leaving sets `running=0`. **Chained clocks:** a clock row gains `parent=<id>` and `ratio=<n>`: `CLOCK|city|parent=gameclock0000|ratio=1`, `CLOCK|planet-mars|parent=gameclock0000|ratio=1.0275` (a body's day length from its physics node `rotation_period`), `CLOCK|school|parent=...`. A child's time is a pure function of its parent's time (derived, never separately advanced), so all entities in the game share one source; "start the clock for all entities" means every entity/page runs against a child of the main clock. Entities read their clock by **cursor** (the tick/ledger design of `ENTITY-NEEDS-AND-CARE-DESIGN.md`).
**3.2 Setup under Time (game off).** A **Time** section in game setup (`game.pdl` `SETUP` rows, `DSR-SIMULATION-DESIGN.md` section 8) edits: start date/time, rate, calendar (months/year lengths for non-Earth planets), chained-clock ratios, and which schedules exist. **Fields locked while the game is on:** start date, calendar and the clock set; **adjustable while on:** rate (speed), pause, and scheduled events. This is the customization: how time behaves in play is exactly how it is set up under Time.
**3.3 Schedules (reminders grow up).** `repeat=` becomes real: `repeat=every:<n><unit>` with units `min|hour|day|week|month|year` (calendar-aware: "month" follows the game calendar, not 30 days), plus optional `until=`. A schedule's `event=` is a **common event** (RPG Maker primitive), so Day Tick, rent due (monthly), corporate earnings (quarterly), school year (yearly), election cycle, seasons and tax day are all **rows**, not code. **Catch-up rule:** when the clock passes several occurrences at once, fire **every missed occurrence in order**, up to a per-schedule cap (default e.g. 400; beyond it, collapse into one "caught up N" row and flag it), so fast-forward never silently skips a day of hunger or rent. Each firing appends a row to a **schedule ledger** (`SCHED | id | occurrence_time | fired_at | result`); the ledger is the cursor (so load/replay never double-fires).
**3.4 Events change the clock (owner's last point).** Registered commands in the event system control the clock: `set_clock_rate <clock> <rate>` (slow/speed: WSR-style), `pause_clock`, `advance_clock <clock> <amount>` (a sleep skips to morning), `set_clock_time`, `end_turn`. They are ordinary commands (registry rows) that write the clock's **mailbox** (like `endturn.txt`), so the single-writer rule holds: the daemon applies them. Safety: an event may change the clock only within limits set under Time (min/max rate, whether `set_clock_time` backwards is allowed, which scopes), with an audit row per change. This is how a store closing, a nap, a wormhole or a time-dilation planet changes game time from inside the game.
**3.5 Display.** The taskbar cell 15 and the pc-hq HUD show the main clock's calendar time (`YYYY-MM-DD HH:MM`, rate indicator, paused flag); the toy/DSR dashboard shows the same value. All read the clock file; none keeps its own time.
**3.6 One engine.** Make `lc_clock` the engine and let pc-hq read its clock (or run a child clock whose epoch is derived from it) instead of keeping a second, separate epoch; migrate `autotick_speed` onto the clock's `rate`. The sun/moon/animals then follow the game clock like everything else.
**3.7 Real-time mode** (`REAL-3D-PLANET-EXPLORATION-AND-REALTIME-MODE-DESIGN.md`) is just a high rate on the same clock with fixed-timestep ticks; stepped mode is rate `off` with manual End Turn.

## 6. Owner additions (2026-10-07, same session)
**6.1 Flexible by design: how time advances is a per-game setting under Time, not code.** Time modes (all write the same tick row type, so every rule works in every mode; digipet M4):
- **Continuous (real-time):** rate-driven (`cent..day`, or a custom ratio), as WSR can be slowed or sped up.
- **End Turn changes the day:** a turn button advances a **configured span** (one day, one phase of the day, or N hours), so the economy/WSR style steps by day.
- **Roguelike / action-cost:** each action costs time units (a move, a craft, a rest take `cost` minutes from an **action-cost table** in the game's Time setup), and the clock advances by the cost; nothing moves until the player acts. Sleeping or waiting is an `advance_clock`.
- **Mixed:** real-time clock **and** End Turn available; or turn-based on one page (a dungeon) and continuous on another, because clocks are chained and each page picks its mode.
Mode, span per turn, action costs, rates and limits are rows under Time (`SETUP | time.mode | continuous|endturn|roguelike|mixed`, `SETUP | time.turn_span | 1day`, `ACTIONCOST | move | 10min` ...), locked when the game is on except where marked adjustable.
**6.2 A calendar window.** An X11-HQ window (not just the taskbar menu; the taskbar already has menu 154, "calendar view of a chosen clock", `khtpm_taskbar_manager.c`, and menus 151-153 for clocks list, reminders and game-clock controls: **a menu-only view exists; no window found**). The window: a month/year grid for the chosen clock (the game calendar of that world or planet), the current time marker, day cells showing scheduled events and past firings; select a day to see its schedule and history; **create/edit/delete schedules** there (writing the same schedule rows as 3.3, with audit rows and undo, tomom-hq style, default to scratch/test clocks until trusted); switch clocks (main, chained, a planet's); zoom day/week/month/year. **Locked fields follow 3.2** (calendar structure is read-only while on; schedules and rate are adjustable).
**6.3 Histories.** The schedule ledger (`SCHED | id | occurrence | fired | result`) and clock-change audit rows (who/what changed rate, time, pause) are the **history**: the calendar window reads them (read-only projection by cursor), so you can scrub back through what fired, what was caught up, and what an event changed in the clock. Per-entity histories (needs ticks, school year) appear as filters over the same ledger (a calendar layer per entity or place).
**6.4 Build additions.** After step 3 of section 4: a **time-mode setup** (rows + validation + harness: each mode advances correctly, roguelike cost table advances by cost, End Turn span, catch-up still correct in every mode), then the **calendar window** (read-only month grid first, then schedule edit, then history overlays) with a relay-driven harness check.
**6.5 Open:** default mode for a new game; action-cost table defaults; whether the calendar window opens from taskbar cell 15 (replacing menu 154) or both.

## 7. Owner answers (2026-10-07): many clocks, one displayed, rewind
**7.1 Clocks are cheap and numerous.** Any number of clocks, "as often as needed". **One master clock is displayed** (taskbar cell 15 / pc-hq HUD). Every other clock is either **chained** (`parent=<id>`, `ratio=`: derived from its parent) or **separate** (independent: its own rate, start and calendar, e.g. a planet in another system, a school's own term clock, a countdown). Registry: `CLOCK|<id>|scope=|desc=|parent=|ratio=|master=0|1`; exactly one `master=1` per game; the display setting names which clock is shown; the calendar window (6.2) can switch to any clock. This also settles open question 5 (section 5): clocks are per game, a master per game, any number of others.
**7.2 Rewind = restore a saved state, not run time backwards.** Owner: "we can rewind saved games back to states, as well as in play-test mode." So time never runs backward inside a running game (events cannot move it back, answering open question 4: **no**); instead a **checkpoint** (a save slot, or an automatic checkpoint) is **restored**, and the restored state includes the clock epoch, tick, `fired`/schedule-ledger position, all entity variables, and the schedule ledger position.
**7.3 Prerequisite that does not exist yet (read in `game_slot_op.c`):** today's save/load is **v1 and auditable only**: `save N` writes a SHA-256 **manifest** of the user's entity tree (every file's hash, size and path) plus `meta.pdl` and one ledger line; it **copies nothing and changes no entity data**; `load N` only **compares** the current tree against the manifest and reports same/changed/missing/new. **It restores nothing**; its own header says restoring running entities "needs the owner's design" (and the clock files under `#.desktop/clocks/` are not part of the user's entity tree, so clocks are not saved at all). So a real rewind needs, in order: (1) **content snapshots** (store file contents by hash, a content-addressed store, so a manifest can be turned back into a tree); (2) **clock state included** in a checkpoint (clock pdl + schedule ledger position); (3) **a safe restore procedure** (quiesce running entities, restore files, restart/reload; rehearsed on a scratch copy and in beta, with a backup first, per the data rules); (4) **what is allowed to rewind**: game-owned state (entity variables, play money in the game's own ledgers, clocks) yes; **append-only ledgers are never truncated**: a rewind appends `REWIND|<from>|<to>|<ts>` and the restored state is a **new branch of history** (the old branch stays readable and can be re-entered, a timeline fork), so audit trails and the schedule ledger stay honest; **cones/real-chain transactions can never rewind** (a game that touches them must refuse rewinds or isolate to a test chain).
**7.4 Play-test mode** (`khtpm_play_mode.state.txt`: `mode=on` + `playtest=1`, built 2026-10-07 per `GAME-SETUP-PDL-DESIGN.md` section 9): rewind is **free and encouraged**: play-test checkpoints are automatic (e.g. at each End Turn or day change, ring buffer of N), a play-test session is **discardable** (return to the pre-test checkpoint), and nothing from a play-test run is allowed to touch the real (non-test) chains. In normal play, rewind is a **setting under Time** (off / manual slots only / automatic checkpoints), and a game can mark itself non-rewindable (an ironman option, off by default).
**7.5 Build order change:** insert **before** the "play hook" step (section 4 step 5): (a) content-addressed snapshot store + restore for a scratch entity tree with a pal harness (save, mutate, restore equals original byte for byte, clock state included, schedule ledger position correct, no double-firing after restore); (b) rewind row + timeline fork; (c) play-test auto-checkpoints; (d) the Time settings for rewind. All in alpha/beta against scratch data first; **live user data is not touched** until the owner approves the restore design.
**7.6 Open:** snapshot storage budget (per-slot full copy vs shared content store), how many automatic checkpoints, whether rewind keeps player-visible "what I did" log across the fork.

## 11. Owner direction (2026-10-07): the taskbar reads the clock from a .txt written by a daemon; a pdl (or game input) says which clock to watch
**Architecture (the house's own strip-variable pattern, extended):**
- **Reader side already exists.** The taskbar strip reads plain text files `#.desktop/strip_var_<name>.txt` (`khtpm_strip_parser.c` reads `strip_var_datetime.txt` into `${datetime}`, cell 15). Today the **taskbar manager itself** writes that file on every dispatch from the **system clock** (`khtpm_taskbar_manager_main.c`: `format_datetime(...)`, language from the `datetime_lang` key in `#.desktop/livedesk_taskbar.pdl`). So the real Linux clock stays as it is.
- **New writer: the clock daemon.** `lc_clock` (the daemon that is the sole writer of game time) additionally publishes **display files** under `#.desktop/clocks/`: `display_<clock id>.txt` for each clock and `display_master.txt` for the master (formatted game date from its own `format_gamedate`, plus rate/paused flags), rewritten atomically only when the text changes. First line carries the daemon's **wall-ms stamp** so a reader can tell it is **stale** (daemon dead) and fall back to the real clock. (An append-only `display_changed.txt` marker can drive redraw by size growth, per the house rule; no mtime.)
- **Which clock to watch = a pdl key (or game input).** In `#.desktop/livedesk_taskbar.pdl` (next to `datetime_lang`): `datetime_source=real|master|<clock id>`, optional `datetime_mode=real|game|both` (both = `14:05  Eden D3`), `datetime_lang=zh|en`. **Game input** writes the key: a conductor's `Start` sets `datetime_source=master` (or its own clock id), `Stop`/`Reset` restores `real`; a person can edit the same pdl by hand or from a menu row. **Default stays `real`**, so nothing changes until a game or the owner asks.
- **Taskbar manager change (small, shared file, later):** in the datetime step, read `datetime_source`; `real` = today's code path; `master`/`<id>` = copy the daemon's display file into `strip_var_datetime.txt` (falling back to real when the file is missing or stale). The strip parser needs no change (it already reads that file). The **pc-hq HUD and any other display** read the same `display_*.txt` files, so there is **one writer, many readers**.
- **Why this shape:** no clock arithmetic in the taskbar (it only copies text), one writer per file, the real clock is untouched, the displayed clock is chosen by data, and it works for any number of clocks.
**Build order:** (a) `lc_clock` writes `display_*.txt` + stamp (alpha, my lane, harness first: text matches `gamedate`, stale detection, atomic, master switch moves the file); (b) the `datetime_source` rows in the taskbar pdl and the conductor's Start/Stop writing them (harness on scratch roots); (c) the taskbar manager reading the key (**needs the taskbar owner's review; shared file `khtpm_taskbar_manager_main.c`; rehearse in beta, relay check**); (d) pc-hq HUD reads the same file. **Open:** show real and game together by default when a game runs, or game only?

## Build report: game_snapshot_op (backlog item 2, build order step 7.5 (a)+(b), 2026-10-07)

Built in alpha only, scratch data only; `game_slot_op` and the live taskbar are untouched, and nothing calls the new op yet.
- **Op:** `&.widgits/_shared-lib/ops/game_snapshot_op.c` (+ `build_game_snapshot_op.sh`). `save <id> [--extra FILE]...`, `list`, `verify <id>`, `restore <id> <dest> [--apply] [--prune] [--extra-dir DIR]`, `diff <id>`. Header of the .c has the layout, skip list and exit codes (0 ok, 1 failure, 2 usage/REFUSED, 3 corrupt/missing object or manifest-vs-meta mismatch, 4 diff differs). SHA-256 is the house `ph_sha_hex` via the same text-include `game_slot_op` uses.
- **Store:** `objects/<sha[0:2]>/<sha>` (each content once, mode 0444, shared by all checkpoints), `checkpoints/<id>/{manifest.txt,meta.pdl}` (published by renaming a temp dir, so all-or-nothing), append-only `ledger.txt`, `head.txt` pointer (the next save's parent).
- **Clock state:** `--extra` files ride inside the checkpoint as `__extra__/<basename>`; restore reports them and writes them only to an explicit `--extra-dir`, so the caller decides where the clock state and schedule ledger go. It does not itself reload a running clock or entity (quiesce/relaunch is still step 3 of 7.3 and is not built).
- **Rewind row + fork:** `restore --apply` appends `<ms>|rewind|from=<manifest sha of the previous head, or ->|to=<id>` and moves head to the restored id, so the next save has `parent=<restored id>` and the old branch stays readable and verifiable.
- **Safety:** restore is a dry run by default; the whole plan is validated first (manifest sha vs meta, every object re-hashed, no `..`/absolute path, no symlink in any dest path component) and a failure writes nothing; writes are temp file + fchmod + atomic rename; files not in the manifest are left and reported unless `--prune`; setuid/setgid/sticky are never recorded or restored.
- **Proof:** `harness/game_snapshot.pal` + `cases/game_snapshot.pdl`, 118 checks on a scratch tree (nested dirs, binary, zero-byte, executable, mode 600): dedup, B stores only changed objects, restore A byte-for-byte (tree hash equal, modes kept), dry-run changes nothing, tampered/missing object refused, path-escape and symlinked-dest refused, extras round-trip, ledger append-only with REWIND row. A copy with one wrong expectation gave `VERDICT|FAIL`.
- **Not done / open:** no quiesce-and-reload of running entities, no schedule-ledger "no double firing after restore" proof (needs the lc_clock side to read a restored ledger), no automatic checkpoints or Time settings (steps (c), (d)); no object garbage collection; storage budget (7.6) is answered only in that objects are shared, not pruned.

## Build report: lc_clock recurrence + catch-up + harness (backlog item 1, build order steps 1-2, 2026-10-07)
- **Harness first:** `harness/lc_clock_base.pal` (27 checks) and `lc_clock_recur.pal` (54 checks) run the real `lc_clock` on `/tmp/hc_*` scratch roots. lc_clock had no deterministic path, so a `step <real_ms>` subcommand was added (the daemon's ticker body, mailbox and reminder poll as one pass, no sleeping); the daemon loop calls the same `advance_clocks`. A `daemon` smoke case still runs the real loop. Hooks (default unchanged): `LC_CLOCK_NO_POPUP=1`, `LC_CLOCK_EVENT_RUNNER`, `LC_CLOCK_EVENT_TIMEOUT_S`.
- **Gap evidence (before):** the ORIGINAL binary, daemon mode, scratch root, a `repeat=every:1day` reminder on a fast clock (about 11 game days in 3 s) fired once and was then skipped for ever (`fired=` set). Now it recurs.
- **Recurrence:** `repeat=every:<n><unit>`, units min/hour/day/week/month/year, optional `until=<ms>` (inclusive). Occurrence k is a pure function of anchor/n/unit/k, so month and year steps keep the anchor day and clamp (Jan 31, Feb 28 or 29, Mar 31; Feb 29 yearly gives Feb 28 in common years). Unknown or zero-n `repeat` is refused by `reminder-add`; an unparseable stored `repeat` is treated as a one-shot (legacy unchanged, `until=` is only written when set).
- **Catch-up + ledger:** `schedule_ledger.txt` rows `SCHED|id|occurrence_ms|fired_wall_ms|result`; the ledger is the cursor (read incrementally by byte offset, never mtime). A 1000-day jump on a daily schedule gives 400 `ok` rows + one `caught up 600` row (occurrence = the last collapsed one) + a `schedule_flags.txt` row; the next day resumes normally. A stale or restored `reminders.pdl` (fired=0) fires 0 new, one-shots included (ledger guards replay). A ledgered id is never reused by `reminder-add`. During catch-up only the last firing of a batch shows a popup; every occurrence runs its event.
- **Event run safety:** `system(... &)` for events replaced by fork + `setpgid` + exec (no shell) + `waitpid` poll with a 30 s watchdog that kills the process group; result `ok|fail|timeout` in the SCHED row. The popup stays detached.
- **Decisions 3 and 4 (backlog):** cap 400 + collapse flag implemented; time never runs backward (no such command added).
- **Not done / limits:** the daemon blocks while an event runs (up to 30 s per event; 400 slow events in one poll could stall the ticker); `reminders` listing does not show `until`; no harness bank seed for the two new harnesses; the calendar assumes `game_time_epoch_ms >= 0`.

## Build report: clock commands, chaining + master, clock-restore check (backlog item 3 part, build order 3-4 + 7.5 restore proof, 2026-10-07)
- **Commands (3.4):** the `endturn.txt` mailbox grew `rate|pause|resume|advance|settime` next to `endturn` (old grammar unchanged). `lc_clock <root> cmd <clock> <verb> [arg] [--source S]` only queues; the daemon pass applies, so the daemon stays the sole writer of epoch/tick. Per-clock limits live in the state file (`limit_min_rate`, `limit_max_rate`, `allow_settime_back=0`, `allow_commands=1`; set with `lc_clock <root> limit ...`). Every accepted or refused command appends `ts|clock|cmd|args|result|source` to append-only `clock_audit.txt`. Decision 4 enforced: advance/endturn must be > 0, settime earlier than now is refused unless `allow_settime_back=1` (then logged `ok:backwards-allowed`; the schedule ledger is untouched, so nothing fires twice). Rate `x<ratio>` added (x1 = real time). Registry: `set_clock_rate`, `pause_clock`, `resume_clock`, `advance_clock`, `set_clock_time` in `#.ref/menu/event_commands.registry.pdl` (the old blocks are byte-identical; the five TEMPLATE lines were run as the generated cmd_N.sh would and all landed as audited `ok` rows; there is no registry parse harness to run).
- **Chaining + master (3.1, 7.1):** `CLOCK|id|scope=|desc=|parent=|ratio=|master=`; `chain <child> <parent> <ratio>` / `unchain` / `master [id]` / `info <id>`. Child epoch = round(parent*ratio) + `child_offset`, derived every pass (`derive_children`), never advanced; `chain` keeps the child's current epoch (no time jump). Rate/pause on a child are refused (give them to the parent); advance/settime on a child move its offset. Exactly one master: setting clears the old, `master none` is refused, a hand-edited file with two reads as ambiguous (exit 2) until an explicit `master <id>` heals it. Cycles, self-parent, unknown parent, ratio <= 0 refused. `gamedate master` is the display read; the taskbar itself is untouched. Legacy rows and state files are byte-unchanged until a new command touches them.
- **Clock-restore check:** harness case `lc_clock_restore`. A REAL BUG was found and fixed: a long-lived daemon kept its in-memory ledger cursor (byte offset + max occurrence per id) after a restore replaced `schedule_ledger.txt`, so after restoring to day 3 the daemon (cursor day 5) would NOT fire day 4 (silent missed firings; no double firing). `ledger_refresh` now drops and re-folds the cursor when the file's inode/device changes or it shrinks (identity by inode, never mtime). Against a binary without the fix the live-daemon case fails 3 checks; with it the case passes. Stepped (fresh-process) restores never had the problem. Restore must still be quiesced in the 7.3 sense for entity files; clock files were restored under a running daemon without trouble in the harness.
- **Small stalls:** the popup `system()` no longer runs when the popup binary is missing (`access(X_OK)` guard). NOT rebuilt: the daemon still blocks up to 30 s per slow event (400 slow events in one poll can stall the ticker); a worker/queue design is needed.
- **Limits / not done:** legacy ctl `rate` and `ticker` write directly and bypass limits and audit (owner panel path); `endturn` is not subject to `allow_commands=0` (it is the player's End Turn button); a command takes effect on the NEXT pass (the ticker of the pass that reads it runs first); `delete_clock` leaves children of a deleted parent frozen and does not repair masters; `settime` on a child cannot be below its current derived time; no UI wiring, no pc-hq epoch unification, no Time-setup lock rules (steps 5-6 unchanged).
