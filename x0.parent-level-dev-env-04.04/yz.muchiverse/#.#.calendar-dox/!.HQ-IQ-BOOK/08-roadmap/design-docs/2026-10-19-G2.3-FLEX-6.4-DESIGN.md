# G2.3 flex — the 6.4 renderer-half design decision

**Written 2026-10-19, branch `opencode`, before any 6.4 code.** The burndown
(`2026-10-18-BROWSER-BURNDOWN.md` §6.4) reserves this specific call for the
owner and says it "deserves its own note before code". The owner's answer was
option **(b), generalize the layout pass**. This note is that generalization,
written after reading the real code rather than a summary of it
(`CENTROID_GOLD_STD.md`'s own standing rule).

## 0. The headline: there is nothing to invent

The burndown's 6.4 framing assumed the renderer needed new work — "(a) a new
content row *kind* in the template that is a `<row>`, or (b) generalizing the
layout pass past the chrome classes". **Both framing options are wrong**, and
the reason is a real, already-shipped capability nobody noticed:

**`css_layout_pass()` in `&.widgits/_shared-lib/khtpm_render_core.c:572` is
already a complete, general flexbox engine.** It implements:

| capability | where | notes |
|---|---|---|
| `display:flex` detection | `:601` | `style.has_display && style.display_flex` |
| `flex-direction` row/column | `:604` | `is_row = has_flex_direction ? flex_row : 0` |
| `flex-grow` weighted share | `:650-685` | `grow_total`/`fixed_total` accounting |
| `flex-wrap` wrapping grid | `:613-635` | own line-flush loop |
| `padding` / `gap` | `:647-648` | real box-model insets, additive main-axis gap |
| `position:absolute` | `:653` | out of flow entirely |

And the *CSS layer already carries all of it* — `khtpm_css_parser.h:42-45`
declares `has_display`/`display_flex`, `has_flex_direction`/`flex_row`,
`has_flex_grow`/`flex_grow`, `has_flex_wrap`/`flex_wrap`, and
`khtpm_css_parser.c:118-131` parses and cascades every one of them.

So the engine and the style model are done. What is missing is a **caller**.

### It is already reachable from CSS, and documented as such

`khtpm_core_render.c:7155-7170` (the `<page>` layout) reads:

> `if <page style="display:flex; flex-direction:row">` the shared flexbox
> engine (css_layout_pass, khtpm_render_core.c) sizes every region child
> (sidebar + N panels) from its own width / flex-grow - exactly like a CSS
> flex row. This is how a 3-column (recipes | bench | inventory) window is
> authored, **no per-app renderer code**.

At `:7314` and `:7385` the same `display_flex` check routes `<sidebar>` and
`<panel>`. **This is the "generalize the layout pass" the owner asked for —
it already exists.** It was generalized once (2026-09-11, per `:575-593`) and
the generalization is live.

### Why the browser does not get flex today

Not because the engine lacks it, and not because of a chrome-class gate. The
browser's content pane is a fixed per-kind `<repeat>` and its `<page>` declares
**no** `display:flex` (`grep display\|flex network-browser-hq.xhtpm` → none).
The CSS simply never asks for a flex content row, so `page_is_flex` is false
and the classic sidebar+panel split runs.

## 1. What is actually missing — and it is the worker, not the renderer

`nb_flex_test.sh` reads `getBoundingClientRect()` out of a worker `eval`. **The
test measures the worker's box tree, not the renderer's painted rows.** Its own
closing note says why this matters:

> This test is RED BY DESIGN until the worker models flex rows **AND** the
> manager projects them so the renderer lays them out the same way - doing
> only the first would re-open G2.2.

That is the real constraint, and it is a *sequencing* constraint, not an
architectural one. The two halves must land such that the worker's box tree and
the renderer's rows agree, or `nb_gbcr` (G2.2, K2, 100%) breaks.

Measured worker state (handoff §5a, unchanged):

```
worker:   c1 x=0 y=30 w=389   c2 x=0 y=60 w=389   c3 x=0 y=90 w=389
renderer:    x=200 y=180 w=389    x=200 y=210 w=389    x=200 y=240 w=389
```

Both stack and therefore agree. The work is to make **both** produce a row.

## 2. The plan, in order, each step independently provable

The burndown's 6.1 landed (`e19a0f0bd`: `nb_css.c` retains the display
keyword). Remaining:

### Step 6.2 — worker x-axis (`ops/nb_js_worker.c`)
`layout_xy()` ends `*out_x = 0` unconditionally (`:1251`). This is why a flex
div reports `x=[0,0,0]`: **the worker has no horizontal axis at all.** Flex is
the first x-accumulation the model will ever have. Add one, used only when the
parent is flex.

### Step 6.3 — worker flex semantics (three small changes)
- `nb_box_w()` (`:1176-1180`) fills the parent width for block children → a
  flex child needs a **share**.
- `layout_xy()` accumulates sibling heights → a flex parent accumulates
  **widths** and holds `y`.
- `nb_content_h()` sums children (`:1193`) → a flex container's height is the
  **max**, not the sum.

The red test's four clauses map onto exactly these (one row / shared edges /
x advances / widths fit).

### Step 6.4 — renderer side: **wire the existing engine, do not build one**
Because `css_layout_pass()` is complete, this half is CSS + one call site, not
a new layout branch *if* the browser's content can be expressed as flex
children of the `<page>`.

**This is the one genuine design decision left, and it is small:** how the
browser's content `<repeat>` children become flex children of the page. Two
options, with the recommendation:

- **(i) RECOMMENDED — author flex into the template's `<page>`/content
  container** (`display:flex; flex-direction:row` on the page or the content
  wrapper), so the existing `page_is_flex` path at `:7163` consumes it.
  No new C. Matches `CENTROID_GOLD_STD.md` §1a's reuse corollary and the
  comment's own "no per-app renderer code".
- (ii) Only if (i) proves impossible for the `<repeat>` projection: extend the
  `display_flex` check to one more container. Still no new engine.

**One concrete detail the two existing call sites disagree on, which step 6.4
must handle:** the `<page>` flex path (`:7165-7169`) styles **direct children
only** (one `css_compute_style` per child, no recursion), whereas the
`<panel>` path (`:7386-7388`) calls `kh_css_deep(panel)` — a full recursive
style pass — *before* `css_layout_pass`. A flex content row whose
**grandchildren** carry the widths the test measures needs the recursive pass;
one level is not enough. This is the real reason the `<page>` path alone may
not suffice for (i), and it is a one-line difference (add/keep a deep style),
not an engine change. Verify which the chosen container needs before wiring.

**Do not add a new `layout_*` branch.** Distilled from
`HOUSE_CODE_PITFALLS.md` #14 (a real 2026-09-06 incident): any new layout path
must clip by parking off-screen children at `y=-100000` (never translate), must
add **zero** new key handling, and must nav-number only visible rows. The
existing flex engine already does the first; a new branch is how that incident
was born.

## 3. The gate that must not be crossed

`CENTROID_GOLD_STD.md` rule 7: **the shared renderer never gains a new
`g_is_<project>` global or a per-project `strcmp` branch.** Everything above
routes through CSS and the generic engine, so this is satisfied by
construction — but it is the constraint that rules out "just special-case the
browser in `css_layout_pass`".

Rule 2 also holds: no business logic enters the renderer; the worker/manager
owns the box tree.

## 4. Definition of done, and the proof bar

1. `nb_flex_test.sh` PASS — one row, columns share edges within **1 px**, x
   advances, widths fit the span.
2. `nb_gbcr_test.sh` **stays 100%** after *every* step (K2; the burndown's own
   rule).
3. Worker and renderer agree — the test's own stated requirement; G2.2 is the
   check.
4. Fresh build + window restart before any live claim (a resident worker keeps
   the pre-rebuild binary; see burndown §3.1).

## 5. What this note changes about the burndown

§6.4's "(b) touches every window" caution is **too pessimistic**: the
generalization already happened on 2026-09-11 and its only consumer is this
browser. The honest revised estimate is the ladder's original one —
**wiring, not invention** — with the real risk being the worker/renderer
agreement (step 6.4's sequencing), not the layout engine.

The earlier caution that this "deserves its own note before code" was still
right, for a different reason than expected: not because the design is hard,
but because the engine is invisible unless you read `css_layout_pass()` — and
an agent who does not would build a second flex implementation, which §1a
condemns on sight.
