# G2.3 flex — the 6.4 renderer-half design decision

**Written 2026-10-19, branch `opencode`, before any 6.4 code. REVISED
2026-10-20 after that code's first step contradicted it** — the revisions are
marked inline and kept visible rather than silently rewritten, because the
mistake is the useful part. The burndown
(`2026-10-18-BROWSER-BURNDOWN.md` §6.4) reserves this specific call for the
owner and says it "deserves its own note before code". The owner's answer was
option **(b), generalize the layout pass**.

## 0. The headline: the engine is done, and the first draft still got the caller wrong

**What is right in this note:** the renderer needs no new layout engine.
`css_layout_pass()` in the shared `khtpm_render_core.c:572` already implements
`display:flex`, row/column direction, `flex-grow`, `flex-wrap`, padding/gap and
`position:absolute` — and it is already live (this browser's own 3-column
layout is that path; see §0.1).

**What the first draft got wrong:** it concluded the missing piece was "a
caller" reachable by putting `display:flex` on the browser's `<page>`. That is
not how page *content* reaches the renderer — content is projected by the
manager as flat typed rows, never as a container. The corrected shape is the
burndown's original option **(a)**, a flex content row *kind*. §2.1 has the
measured reason, §2 step 6.4 has the corrected plan.

The engine detail, unchanged and still the point:

| capability | where | notes |
|---|---|---|
| `display:flex` detection | `:601` | `style.has_display && style.display_flex` |
| `flex-direction` row/column | `:604` | `is_row = has_flex_direction ? flex_row : 0` |
| `flex-grow` weighted share | `:650-685` | `grow_total`/`fixed_total` accounting |
| `flex-wrap` wrapping grid | `:613-635` | own line-flush loop |
| `padding` / `gap` | `:647-648` | real box-model insets, additive main-axis gap |
| `position:absolute` | `:653` | out of flow entirely |

And the *CSS layer already carries all of it* — `khtpm_css_parser.h:42-45`
declares `has_display`/`display_flex`, `has_flex_direction`/`flex_row`,
`has_flex_grow`/`flex_grow`, `has_flex_wrap`/`flex_wrap`, and
`khtpm_css_parser.c:118-131` parses and cascades every one of them.

So the engine and the style model are done. What is missing is a **caller**.

### It is already reachable from CSS, and documented as such

`khtpm_core_render.c:7155-7170` (the `<page>` layout) reads:

> `if <page style="display:flex; flex-direction:row">` the shared flexbox
> engine (css_layout_pass, khtpm_render_core.c) sizes every region child
> (sidebar + N panels) from its own width / flex-grow - exactly like a CSS
> flex row. This is how a 3-column (recipes | bench | inventory) window is
> authored, **no per-app renderer code**.

At `:7314` and `:7385` the same `display_flex` check routes `<sidebar>` and
`<panel>`. **This is the "generalize the layout pass" the owner asked for —
it already exists.** It was generalized once (2026-09-11, per `:575-593`) and
the generalization is live. (Confirmed live 2026-10-20: this very browser's
`<page class="nb-cols">` is `display:flex` via its `.css`, and
`khtpm_pane_geom.state.txt` shows the 3-column row laid out — `content_x=200`.)

The limit, though, is that this path lays out a page's **regions** — the
`<sidebar>` and `<panel>` children of `<page>`. It does **not** reach a page's
*content*. That distinction is the whole of §7 below, and the first draft of
this note missed it.

### Why the browser does not get flex today

**CORRECTED 2026-10-20 — the first draft of this section was wrong, and the
mistake is worth leaving visible.** It claimed the browser's `<page>` declares
no `display:flex`, so `page_is_flex` is false and the classic split runs. Both
halves were wrong:

- It grepped only `network-browser-hq.xhtpm`. The renderer also loads the
  `.css` sitting next to the window's `.chtpm` by stem
  (`khtpm_core_render.c:23425-23431` — `dashboard.chtpm` → `dashboard.css`),
  and `network-browser-hq.css:97-100` contains
  `.nb-cols { display: flex; flex-direction: row; }` with `.nb-body`
  `flex-grow: 2` and `.nb-console` `flex-grow: 1`.
- So `page_is_flex` is **true** and the 3-column flex path **is** what lays
  this window out. Measured: `#.desktop/khtpm_pane_geom.state.txt` reports
  `content_x=200`, i.e. the sidebar took its 200px and the body/console
  panels share the rest — the flex row, not the classic split.

**The real reason a page-side flex div gets no flex is one level down, and it
is not the page at all.** The browser's *content* is projected by
`network_browser_manager.c` as flat typed rows — one `<text>`/`<item>` per
element, gated by `c_<n>_is_*`, from a `<repeat>` in the template. The manager
carries **no** concept of a container: `grep -c flex network_browser_manager.c`
→ **0** across 7,410 lines (negative-tested: the grep does fail, and the file
is not empty). The renderer therefore never receives the fact that a page-side
`div` was `display:flex`; it receives rows. A flex content container has no
path to the engine because **the projection drops the structure**, not because
the CSS forgot to ask.

**What this means for step 6.4's shape (and it reverses this note's own first
conclusion):** the original burndown's option **(a) — a new content row
*kind* in the template that is a `<row>`** was right and this note was wrong
to dismiss it. Wiring the page-level `page_is_flex` path was never going to
reach page content, because page content is not a page *region*. The renderer
half is: project a flex container as a `<row>`-kind content row, then let the
existing `css_layout_pass()` lay that row. See §7.

## 1. What is actually missing — and it is the worker, not the renderer

`nb_flex_test.sh` reads `getBoundingClientRect()` out of a worker `eval`. **The
test measures the worker's box tree, not the renderer's painted rows.** Its own
closing note says why this matters:

> This test is RED BY DESIGN until the worker models flex rows **AND** the
> manager projects them so the renderer lays them out the same way - doing
> only the first would re-open G2.2.

That is the real constraint, and it is a *sequencing* constraint, not an
architectural one. The two halves must land such that the worker's box tree and
the renderer's rows agree, or `nb_gbcr` (G2.2, K2, 100%) breaks.

Measured worker state (handoff §5a, unchanged):

```
worker:   c1 x=0 y=30 w=389   c2 x=0 y=60 w=389   c3 x=0 y=90 w=389
renderer:    x=200 y=180 w=389    x=200 y=210 w=389    x=200 y=240 w=389
```

Both stack and therefore agree. The work is to make **both** produce a row.

## 2. The plan, in order, each step independently provable

The burndown's 6.1 landed (`e19a0f0bd`: `nb_css.c` retains the display
keyword). Remaining:

### Step 6.2 — worker x-axis (`ops/nb_js_worker.c`)
`layout_xy()` ends `*out_x = 0` unconditionally (`:1251`). This is why a flex
div reports `x=[0,0,0]`: **the worker has no horizontal axis at all.** Flex is
the first x-accumulation the model will ever have. Add one, used only when the
parent is flex.

### Step 6.3 — worker flex semantics (three small changes)
- `nb_box_w()` (`:1176-1180`) fills the parent width for block children → a
  flex child needs a **share**.
- `layout_xy()` accumulates sibling heights → a flex parent accumulates
  **widths** and holds `y`.
- `nb_content_h()` sums children (`:1193`) → a flex container's height is the
  **max**, not the sum.

The red test's four clauses map onto exactly these (one row / shared edges /
x advances / widths fit).

### Step 6.4 — renderer side: **the content is projected as rows, so the row kind is the answer**

**REVISED 2026-10-20. The first draft of this step recommended putting
`display:flex` on the page/content container and letting `page_is_flex`
consume it. That cannot work, and §2.1 explains why: the `page_is_flex` path
lays out page *regions* (`<sidebar>`, `<panel>`), while page *content* is
projected by the manager as flat typed rows and never arrives as a container
at all.** So there is nothing for a page-level flex container to hold.

The renderer half is therefore the burndown's **option (a)**, which the first
draft was wrong to dismiss:

**(a) RECOMMENDED — a flex content row *kind*.** The manager already emits one
`c_<n>_is_<kind>` flag per projected element (`network_browser_manager.c`,
the `UI_PUT("c_%d_is_...")` sites). Add a `flex` row kind: when the worker
reports a page-side element with `display:flex`, the manager projects that
element as a `c_<n>_is_flexrow` row carrying its children as sub-cells, and
the template gains one `<row class="nb-flexrow">` shown on that flag. The
existing `css_layout_pass()` then lays that `<row>` — the engine is done, this
is a new *caller*, and it is per-app in the **template**, not in the shared C
(CENTROID_GOLD_STD rule 7 is satisfied: the template is the browser's own).

**(b) Only if (a) proves impossible** for the `<repeat>` projection: generalize
one more container in `khtpm_core_render.c`. Still no new engine, but it
touches the shared file and needs the #14 discipline below.

**The rule for either:** do not add a new `layout_*` branch in the shared
renderer. Distilled from `HOUSE_CODE_PITFALLS.md` #14 (a real 2026-09-06
incident): any new layout path must clip by parking off-screen children at
`y=-100000` (never translate), must add **zero** new key handling, and must
nav-number only visible rows. The existing flex engine already does the first;
a new branch is how that incident was born. Note also that
`css_layout_pass()` assigns **no nav** — the existing region call sites
number their items afterwards (see the comment at
`khtpm_core_render.c:7310-7313`), and a content row kind must do the same or
the flex row becomes unreachable by keyboard.

**The latent default reversal found while shipping 6.2/6.3 (2026-10-20):**
`khtpm_render_core.c:604` computes
`is_row = style.has_flex_direction ? style.flex_row : 0` — so an unset
`flex-direction` is treated as **column**, where CSS says the default is
**row**. The worker's first cut had the identical bug and it kept
`nb_flex_test.sh` red until fixed. This is a real, separate defect in the
shared engine: any window that writes `display:flex` without
`flex-direction` currently gets a column where a browser would give a row.
Fix it with the *same* shape the worker now uses
(`!(has_flex_direction && !flex_row)`), and prove it with a fixture rather
than by inspection — it changes behaviour for every existing consumer that
omits the property, so it needs the burndown's full gate (§4).

## 3. The gate that must not be crossed

`CENTROID_GOLD_STD.md` rule 7: **the shared renderer never gains a new
`g_is_<project>` global or a per-project `strcmp` branch.** Everything above
routes through CSS and the generic engine, so this is satisfied by
construction — but it is the constraint that rules out "just special-case the
browser in `css_layout_pass`".

Rule 2 also holds: no business logic enters the renderer; the worker/manager
owns the box tree.

## 4. Definition of done, and the proof bar

1. `nb_flex_test.sh` PASS — one row, columns share edges within **1 px**, x
   advances, widths fit the span.
2. `nb_gbcr_test.sh` **stays 100%** after *every* step (K2; the burndown's own
   rule).
3. Worker and renderer agree — the test's own stated requirement; G2.2 is the
   check.
4. Fresh build + window restart before any live claim (a resident worker keeps
   the pre-rebuild binary; see burndown §3.1).

## 5. What this note changes about the burndown

§6.4's "(b) touches every window" caution is **too pessimistic**: the
generalization already happened on 2026-09-11 and its only consumer is this
browser. The honest revised estimate is the ladder's original one —
**wiring, not invention** — with the real risk being the worker/renderer
agreement (step 6.4's sequencing), not the layout engine.

The earlier caution that this "deserves its own note before code" was still
right, for a different reason than expected: not because the design is hard,
but because the engine is invisible unless you read `css_layout_pass()` — and
an agent who does not would build a second flex implementation, which §1a
condemns on sight.
