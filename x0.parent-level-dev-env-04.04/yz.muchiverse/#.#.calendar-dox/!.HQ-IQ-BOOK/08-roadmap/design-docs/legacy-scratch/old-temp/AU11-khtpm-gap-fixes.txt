LEADING HYPOTHESIS — concrete, reasoned, NOT YET CONFIRMED, check this
FIRST
===========================================================================
khtpm_strip_header.chtpm's real structure (read the file directly,
*.monads/*.livedesk-taskbar/khtpm_strip_header.chtpm):

    <panel>                                          <- likely index 0
      <button label="HQ" onClick="ACTIVATE:1">        <- likely index 1
        <row>${strip_hq_items}</row>                  <- likely index 2  <-- SUSPECT
      </button>
      <button label="USER" onClick="STRIP:2"/>        <- likely index 3
      <button label="file" onClick="ACTIVATE:3">      <- likely index 4
        <row>${strip_hq_items}</row>                  <- likely index 5
      </button>
      ... (9 more cells, most with their own nested <row> child)
      <cli_io target_id="cliio" label="${cliio_label}"/>
    </panel>

IF the tag-tree builder (khtpm_strip_layout.c, lay_build_tree(), line 264)
assigns indices in simple depth-first document order (append each element
as encountered, recursing into children immediately), then index 2 is
HQ's own nested <row>${strip_hq_items}</row> — NOT USER, NOT any real
header cell.

Why this would produce EXACTLY the observed symptom (wrong index AND
invisible cursor):

1. draw_header_win() (khtpm_strip_parser.c, line 548) only iterates
   ROOT-LEVEL <button> elements when drawing header cells — its own loop
   condition is `if (doc->elements[i].parent_index != -1) continue;`
   followed by `if (strcmp(type, "button") != 0) continue;`. HQ's nested
   <row> has parent_index == HQ's own index (NOT -1), so this loop would
   NEVER visit index 2 at all while drawing the header row.
2. lay_cursor_prefix(doc, idx) (khtpm_strip_layout.c, line 514) is only
   ever CALLED by the render loop for the indices it actually draws. If
   focus_index=2 is never one of those indices (per point 1), the [>]
   bracket for "whatever is focused" never gets drawn ANYWHERE in the
   header row — exactly matching "there is no '>' this time."
3. This would mean lay_load()'s own "seed to first navigable element"
   loop (khtpm_strip_layout.c, line ~357-361: `for i in 0..count, if
   lay_is_navigable(doc,i) break`) incorrectly returned true for the
   <row> at index 2, OR skipped index 1 (real HQ button) for some other
   reason and landed on index 2 next.

THE ONE THING THAT DOESN'T CLEANLY FIT THIS HYPOTHESIS (verify this
specifically, don't just assume the hypothesis is right):
lay_is_navigable() (khtpm_strip_layout.c, line 426) calls
lay_is_interactive() (line 406) FIRST, which is:

    return strcmp(el->type, "button") == 0 || strcmp(el->type, "cli_io") == 0;

A <row> element's type should be the literal string "row", which fails
both comparisons — lay_is_interactive() should return 0, and
lay_is_navigable() should return 0 immediately (line 429: "if
(!lay_is_interactive(el)) return 0;") without ever reaching the deeper
ACTIVATE-scope logic. So on paper, is_navigable() should ALREADY exclude
a <row> element correctly, which means the hypothesis above has a real
gap: something else must be going wrong for index 2 to get selected.

Concrete things to check, in order, to resolve this gap:
(a) Is index 2 REALLY the <row>? Don't hand-count from the file — use the
    debug tool (below) to get the ACTUAL type/label/onClick string for
    whatever focus_index currently is. This answers the question directly
    instead of more arithmetic-by-hand, which is exactly what caused this
    round of back-and-forth to take longer than it should have.
(b) If index 2 genuinely IS the <row> (type=="row" confirmed via the
    debug tool) — then there's a real bug in lay_is_interactive() or how
    LayElement.type gets set during tree-building for a <row> tag
    specifically. Read lay_build_tree() (line 264) in full, specifically
    how it sets el->type for each token — check for anything that could
    leave type empty/wrong for a <row> (e.g. an uninitialized buffer, or
    the tokenizer mis-parsing "<row>" vs "<button>" tag names).
(c) If index 2 is something else entirely (e.g. actually USER, and the
    "should be 1 not 2" complaint is really about lay_load()'s seed loop
    skipping index 1/HQ for some reason) — then the bug is in why HQ
    itself fails is_navigable() on a fresh load. Read
    lay_is_navigable()'s global-mode branch (line 442-463) — the walk-up-
    parent-chain check for ACTIVATE-scope ancestors — and verify it
    correctly returns 1 for HQ specifically (HQ's own parent is <panel>,
    which is never an ACTIVATE marker, so the walk should terminate
    immediately and return 1).
