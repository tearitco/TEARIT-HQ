What “done” means here — read this first

For every Actor / Party / Character / Screen command, done = it compiles to real PAL, runs, and writes a correct key=value line to a flat state file. It does not mean anything appears on screen — no sprite, battle, map, or render layer consumes those state files yet. This boundary is consistent across everything shipped. Message commands (show_text, show_choices) do produce visible output.

Event commands — what's left, easiest first

From sep-1-events-SOS.md “WHAT'S ACTUALLY LEFT TO CODE” — categories with zero registry entry today, confirmed by grepping the registry file.

Tier 1~5 min · 0 C
Access toggles — Change Menu Access, Change Save Access, Change Encounter, Change Formation Access.

Registry-only. Copy the control_switch block, point it at a system_flags.txt key. Shows up in the picker on the manager's next poll — zero recompile.

Tier 220–30 min · 1 op
Screen effects & actor graphics — Fadeout / Fadein / Tint / Flash / Shake Screen; Change Actor Graphics.

One small op binary, mr_character.c (~48 lines) is the template. Writes state; nothing renders it (same boundary as above).

Tier 3op + audio dep
Play SE / BGM / BGS / ME

Op binary shelling to a real audio player. First confirm aplay / paplay / ffplay exists on the target — don't ship a silent no-op.

Tier 4wiring, not greenfield
Movement / Transfer / Scroll Map

Position systems already exist — see “Plan going forward” below. This is wiring event commands to the live livedesk desk grid (desks/*.pdl: px xy + grid col/row + z, bounded by desk_grid.pdl) or board-viewer (the 3D/2D grid renderer 5 apps already use), plus one small tick consumer. Not a new subsystem.

Tier 4real subsystems
Shop · Battle · Script command

shop_open is an empty stub folder — needs real buy/sell UI + price/inventory math. Battle needs a battle system (also what Enemies/Troops/States/Animations tabs wait on). A raw Script command is a deliberate architecture change. Check in before starting any of these.

How it fits together

Solid lines are wired and tested. Dashed = a link that is planned but not built. The desk grid and board-viewer are real and running — events just don't call into them yet; only Shop and Battle are genuinely absent subsystems.

Plan going forward

The order the SOS doc implies, corrected for the position systems that already exist. Tiers 1–3 are unchanged; Tier 4's map commands drop from “blocked” to a scoped wiring job.

1now · 0 C
Access toggles → the registry

Append 4 COMMAND blocks copied from control_switch, each pointed at a system_flags.txt key (menu_enabled, save_enabled, …). Prefer the SELECT2 1:0 route so it needs no C hook. Verifiable the moment the manager re-polls.

21–2 ops
Screen effects & actor graphics ops

Twin mr_character.c into mr_screen.c (fadeout|fadein|tint|flash|shake → screen_state.pdl) and add string modes to mr_actor_string.c. Registry blocks mirror show_animation. Still write-only state for now — the consumer is step 5.

31 op + dep check
Audio: Play SE / BGM / BGS / ME

which aplay paplay ffplay on the target first. If one exists, a ~30-line mr_audio.c shelling to it; 4 registry blocks. If none, say so and skip — don't ship a silent no-op.

4wiring job
Transfer Player / Set Movement Route / Scroll Map — on the desk grid

The substrate is live already: desks/<name>.pdl rows carry px_x px_y grid_col grid_row … z, desk_grid.pdl sets cell_px and an optional map_cols/map_rows wall, and the taskbar manager already clamps & rewrites those rows. Steps:

  1. Pick the entity that is “the player.” Simplest: a designated desk entity (e.g. the user's avatar / a player pal). Its desktop_pos.txt + DESK| row are the position of record.
  2. mr_transfer.c (~48 lines, mr_character.c shape): writes x y map to the player's pos file and rewrites its DESK| row so it visibly jumps. Registry: transfer_player (params x, y, map).
  3. mr_move_route.c: appends a step list (up down left right wait) to move_route.pdl. Registry: set_movement_route (params target, route).
  4. mr_scroll_map.c: writes a camera/pan offset to camera.pdl. On the desktop substrate this pans the whole desk; on board-viewer it drives its real camera directly.
  5. One small tick process (map_tick, the only genuinely new binary): reads move_route.pdl, applies one step per tick, clamped to desk_grid.pdl's bound (set map_cols/map_rows — they're commented out today). Reuses the common-events manager's own tick cadence.
  6. Second substrate, same commands: point the ops at board-viewer's grid instead when the event runs inside a board-viewer game (civ-txt / tactics-txt / piececraft-hq all use it). The registry entries and event API don't change — only which coordinate file the op writes.
5consumer
Make the write-only commands visible

Give the desktop tile renderer (khtpm entity mode) and/or board-viewer a pass that reads screen_state.pdl / actor-graphic state and reflects it. This is what turns every Tier-2 “writes state nobody draws” command into a real effect — do it once, after Tiers 2 & 4 have state to show.

6real builds
Shop & Battle

Genuinely new. Shop = buy/sell UI + price math + gold (reuses change_gold + the Items/Weapons/Armors tabs). Battle = the missing subsystem the Enemies / Troops / States / Animations tabs all wait on. Each is its own design pass — not on this ladder's critical path.
