## 3. The coordinate convention (owner file `^.cube-legend_v1.2.txt`)
X red left/right; **Y green UP**; Z blue forward/back; faces: top green, bottom brown, front (z-) white with eyes, back (z+) black, right (x+) red, left (x-) blue; API order `[z, y, x]` = layer, row, column, stored `[x, y, z]`. ## 4. The review standard (how a 3D control or view is "reviewed")
One row per control or view. A row is done only when ALL of these are filled:
1. **Intent** in the owner's words or the doc that states it (quote + path); if none exists, write "NO INTENT STATED" and ask, do not invent.
2. **Expected state change**: which file and key change (e.g. `bv_state.txt camera_mode`, `cam_yaw`, `render_mode`, `pieces/xelector_01/state.txt pos_*`).
3. **Method**: engine key through `bv_keys <session>` (preferred, no owner focus needed) or the window relay; never the owner's window while they use it (ask first); one change per run; start from a recorded state and restore it.
4. **Evidence**: the state diff (before / after values, from a real read: confirm the file exists before trusting a count) AND a photo you opened (`dump_frame_png_op`) saved next to the row; a picture alone is not proof of which key did it.
5. **A negative check**: the same read after a key that must NOT change it (a positive control), so the check can fail.
6. **Verdict** per owner expectation: MATCHES / DIFFERS (say how) / UNKNOWN, with the date and the build time of the engine binary used (sessions run their own copy of `bv_render_3d`: a rebuilt engine reaches an open board only through a NEW session).
Rows that DIFFER become a bug row with the owner's expected behaviour in his words. The runner for steps 2-5 is to be a harness case (pal + case `.pdl` + a C op; no Python, no new `.sh`), built after the owner approves the list of rows; until then every row above is READ or UNTESTED and a claim about it needs a fresh run.

### R13 and R14 ANSWERED (READ, `game_core.c` driver loop 1262-1300 and the rpg-edit `keybinds.pdl`)
**R13 (play vs make):** `mode_play` is 1 once a game was started (`new_game`/start verb, line 1165) or found in progress (1253); a game TICKS only when `live = mode_play && running() && KIND != K_EDITOR && S.phase == PH_PLAY && !stuck` (`running()` = the editor's `state/world/switches.txt` `running=1`). The Make document (`KIND == K_EDITOR`) never ticks; it only redraws the scene when the document hash changes (`scene_on && LEVELDOC`). So a play-mode-only possession step belongs in the `live` branch (or right after it, guarded by `mode_play && KIND != K_EDITOR`), and an `if (!play) possessed_id=none` release when `mode_play` falls to 0.
**R14 (keys):** a platform game reads human keys in the driver loop: `keys_poll(relay, ...)` on `<EDIT>/state/interact_relay.txt` (EDIT = the app that owns the window; for Teario `@.apps/teario-make/state/interact_relay.txt`) and `plat_keys_apply` turns them into `input` ledger rows: arrow left / right = run, down = stay, up or space (32) = jump, `f` / `x` = fire (applied only when `mode_play && running && S.phase == PH_PLAY` and a human seat exists). The file is written by the khtpm WINDOW itself in INTERACT mode from the app's `keybinds.pdl` (`KEY | arrow_left | 1000`, right 1001, up 1002, down 1003, `<code> <ms>` lines), as rpg-edit does (its `state/interact_relay.txt` exists and holds lines such as `1001 1`).
**GAP FOUND (not yet tested): the Teario-Make package has NO `keybinds.pdl` and NO `state/interact_relay.txt`** (`ls @.apps/teario-make`: board, button.sh, game.pdl, harness.pdl, layout.pdl, layouts.pdl, nav.pdl, rooms.pdl, rulesets, state, state.pdl, tests, tuning.pdl, verbs.pdl, ...). The driver of the own window tails a file nothing in that window writes, so ARROW KEYS PRESSED IN THE OWN WINDOW MAY NEVER REACH THE GAME (Play from the editor works because rpg-edit-hq has the table). Test before building anything: in the Teario window turn In: ON (`pchq_board_action.sh '<session>' 'interact'`), press an arrow through the window relay (`KEY_PRESSED: 203`), and see whether `@.apps/teario-make/state/interact_relay.txt` appears; control: the same in the rpg-edit window (owner's window: ask first) or compare with `rpg-edit-hq/state/interact_relay.txt`. ### R14 TESTED 2026-11-19 (step 1 of the revised order; RAN on the Teario-Make window, everything restored byte for byte, layout identical to HEAD)
**Confirmed:** with In: ON, a REAL arrow key in the own window moves the CURSOR (xelector `pos` changed by 1 per press; arrows are camera-relative: at the Teario `default_yaw=90`, Right moved `pos_x` on one run and `pos_y` on another depending on the view) but **nothing delivers it to the GAME**: `@.apps/teario-make/state/interact_relay.txt` stayed absent after every press; the engine's history file `bv_h2` holds only Enter / Esc lines (arrows are NOT written there, so there is no durable arrow trail); `bv_h1` (the engine's own relay) is emptied by the engine; the host inbox `pieces/system/widget_cmds/inbox.txt` is empty (the engine forwards `MOVE` there only when possessing `hero_01`) and `game_core.c` reads no inbox (0 references). rpg-edit's `state/interact_relay.txt` has no writer in its code either (92 bytes of leftover lines such as `1001 1`). **So in the editor too, a human arrow press probably never reaches a platformer game** (the Teario runs so far were driven by `game_core ctl` verbs and harness ticks, not by physical keys); UNTESTED in the rpg-edit window (the owner's window, ask first).
**How a window routes keys (READ, `khtpm_core_render.c` 9341-9430):** the tab with `relay="<path>,<path>,..."` (here `tb-in`, `relay="${bv_h1},${bv_h2}"`) holds the list; up to 4 paths (`g_interact_relay_paths[4]`); while armed every key is appended to each path as a bare decimal and as `KEY_PRESSED: N` (the "dual write"). The attribute is copied into `char relay[300]` (`khtpm_render_core.c` line 216, `snprintf` at `khtpm_core_render.c` 1454): in the live session the two paths are 197 + 183 characters, joined 381, so ONLY 299 characters survive.
**Attempts that did NOT deliver keys to `state/interact_relay.txt` (fresh launch each time where marked):** (a) layout `relay="${bv_h1},${bv_h2},${HOUSE}/@.apps/teario-make/state/interact_relay.txt"` edited LIVE (no relaunch): invalid, the running window kept its armed list (the cursor still moved with a layout that listed only the app path); (b) the same three-path layout after a NEW launch (session 1795096473): file never created; (c) the same with the file pre-created empty: still 0 bytes, so "the window only appends to an existing file" is ruled out. **Two explanations remain and are NOT separated:** the 299-character cut-off dropped the third path (strongly suggested by the numbers; a stray truncated-name file was NOT found, which only shows the writer does not create files), or `${HOUSE}` does not expand inside the `relay` attribute. **Discriminating test (needs one more relaunch, not done):** layout `relay="<literal absolute app path>,${bv_h1}"` (app path FIRST, 141 + 1 + 197 = 339 characters: h1 loses its tail but the app path is whole): if the app file receives `<code>` lines, truncation and a working literal path are both proven and `${HOUSE}` is the only unknown.
**Options (design-choice test pending; recommendation at the end):** (A) raise the shared `relay` buffer (`khtpm_render_core.c` `char relay[300]` and `g_interact_relay_raw[300]` in `khtpm_core_render.c`) so 3 to 4 long paths fit: one small shared change that also fixes the probable truncation of the history path in every pc-hq window, but it needs a rebuild of the renderer and a relaunch of EVERY window to take effect. (B) a forwarder op that copies keys from the engine relay to the app file: raced against the engine's drain, rejected. (C) extend decision D1: for a game-driven possession (an id with no piece file) the engine, which today "moves nothing", also APPENDS the arrow / jump codes to the host inbox (`widget_cmds/inbox.txt`, the existing `send_action_to_host`), and `game_core` tails that inbox with a byte cursor (new reader, same shape as its `action.txt` tail): the keys arrive in order, no renderer change, no race, and it is the SAME contract as D1 (the engine holds the possession and lets the daemon drive). Cost: one more engine edit in `bv_menu_input.c` plus one reader in `game_core` plus a harness case; Make mode is untouched because the forwarding only happens when a game-driven possession is held. **Recommendation: (C)**, after the discriminating test above is skipped on purpose (it only matters for (A)); (A) is worth a separate fix because of the probable history-path truncation, but is a larger blast radius.
