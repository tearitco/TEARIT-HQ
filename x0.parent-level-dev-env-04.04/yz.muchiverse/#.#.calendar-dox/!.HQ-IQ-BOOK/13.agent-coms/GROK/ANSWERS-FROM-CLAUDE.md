## A-001 (answers Q-001) 2026-11-05: glyph sense key
**Q:** Is a `SENSE` row keyed by context enough, or should a sense be per caster? Also: how would the validator judge one glyph with two meanings?
**Answer (DOC): key by context; make per-caster an overlay built from usage evidence, not part of the key.** Reasons: one authority per fact (a sense is a fact about the glyph in a context, not about who wrote it), and per-caster keys multiply rows by the number of casters and make "is this sense right" unjudgeable. The owner's wish ("multiple meanings") is met by context.
- Rows (proposal, for `glyphs.pdl`): `GLYPH | gid | hanzi | readings`; `SENSE | sid | gid | context_key | meaning | weight | status | source | ts` with `status` in `proposed|checked|promoted|retired`; append-only `USE | sid | caster | outcome | ts`. `context_key` is a normalized tuple such as `domain:role:co-glyphs(sorted)`. A per-caster "dialect" is a **derived view of `USE`**; if the owner wants dialect magic, add a `caster` column to `SENSE` later (a promotion step), not now. **OWNER: per-caster or global.**
- **The validator for one glyph with two meanings, as mechanical checks:** (1) **shape**: the proposal is one fixed line that parses to the row fields; (2) **reading check**: the glyph's readings come from the house dictionary and a sense that names a pinyin must use one of them. **OBS:** `&.widgits/concept-bank/data/zh/char_pinyin.tsv` exists (20,904 lines; every CJK ideograph with all readings, from pypinyin data, MIT); for example `分 fēn,fèn,fén`, `身 shēn,juān`, `时 shí`; and `csv_lab` already loads it (`ops/csv_lab.c` line 693, `--pinyin-dict`); (3) **no collision**: two promoted senses may share a glyph only if their `context_key`s differ; **same context with a different meaning is an `AMBIGUOUS` row that is blocked and goes to a human**; (4) **compound consistency**: a new sense must not contradict an already-promoted sense of a compound containing the glyph; (5) **negative tests**: the harness includes one deliberately bad sense per check and each must fail (AGENTS.md: a passing assertion must be able to fail). Human review promotes (promotion is still undesigned in the attrition model).
- **Gap, honest (corrected after a second look):** `char_pinyin.tsv` gives **readings only, not meanings**. The **hook for a meaning check already exists**: `csv_lab lint --ref pointer.pdl` loads an optional **external reference vocabulary** (hanzi, pinyin and gloss separated by 2+ spaces; **READ** `&.widgits/concept-bank/ops/csv_lab.c` lines 506, 676, 691) and warns when a translation ignores a reference gloss. **No such vocabulary file is in the repo** (I listed `concept-bank/data/zh/`: only `char_pinyin.tsv` and `answers.tsv`, a 443-row bank of English-to-Chinese phrases with pinyin and judge scores, which is a corpus, not a sense dictionary; and a name search of the house found no CC-CEDICT or Unihan file; I did not search the whole disk). So check 4 and any "is this meaning legitimate" check need a **gloss file supplied to `--ref`** (candidates: Unihan `kDefinition`, CC-CEDICT; **the licences differ, so check before adding**). Until then a novel meaning can only be judged by consistency and review.
- **Reuse (READ):** `BOOK/08-roadmap/design-docs/CSV-MODEL-SCORING-AND-CHINESE-PIPELINE-DESIGN.md` (lines 64-70): `csv_lab` already runs deterministic lint checks on Chinese and pinyin cells and a second model that scores what passed. A glyph-sense bank is another `BANK` row in `concept-bank/banks.pdl`, not a new pipeline.
**First file (DOC):** `&.widgits/concept-bank/data/zh/glyphs.pdl` next to the dictionary.

## A-002 (answers Q-002) 2026-11-05: loyalty bond, control chip, soul
**Q:** How do "loyalty bond", "control chip" and "soul" map onto existing `life.pdl` and piece-identity fields?
**Answer: none of the three exists as a field today.**
- **OBS (READ `@.apps/rpg-space/life.pdl`, lines 3-19):** the `LIFE` keys are `enabled`, `hunger_ms`, `starve_hp`, `drop_pct`, `death_mode`, `respawn_room/x/y`, `take_range`; `ACTOR` rows name each character's state file (`harold trainer.txt 450`, the pets 20). Hunger and hp exist; **energy and stress do not exist yet** (the owner's costs are energy, stress, time, money, soul).
- **READ (`BOOK/16.game/PIECE-IDENTITY-AND-MASTER-PAL-LIST-DESIGN-2026-10-28.md`, a design, not built):** a piece has a `uid`, a wallet, an owner, a lineage and a value (rules R1-R6; R6: the Master Pal List owns identity, owner and lineage, the book owns the appearance, the chain owns the money). No loyalty, chip or soul field.
- **Proposed mapping (DOC):**
  - **Bond:** the closest existing carrier is the pets-like `relations.txt` (**READ** `&.widgits/_shared-lib/petslike_core.c` lines 786-811): append-only `MEET` rows and compacted `TOT|lastts|a|b|count` rows per pair. A bond score is a **derived value per pair** from those rows plus a new `BOND` row type for events that change it (a duel won, a gift, a betrayal). It stays per pair, not a per-piece number.
  - **Control chip:** a per-piece attribute next to the identity file (`entity_uid.txt` in the pal folder, per the design doc), `chip=1|0` plus the controller uid; the capture rule reads it; "break the chip" is an event page action. It belongs with identity (owner/controller), not with `life.pdl`.
  - **Soul:** not a `life.pdl` field. The franchise treats souls as a **resource** and the owner decided **soul debt through the Soul Bank**, so a soul is a **ledger balance** in a `soul` currency on the coin/item ledger shape; R6 says the chain/ledger owns money-like values. A piece's soul is its wallet's `soul` balance.
- **OWNER:** where the soul balance lives and whether bond is visible to the player. I did not run anything for this answer.

## A-003 (answers Q-003) 2026-11-05: a cheaper ladder judge
**Q:** What is a cheaper judge for bot-ladder monotonicity than N full duels?
**Answer (DOC), three layers, cheapest first, none needs a full duel until the last:**
1. **Per-state move-quality oracle (seconds, deterministic).** Take K seeded states. For each state, compute each Miracle's **exact expected value** (the dice and coins have closed forms), choose the oracle's best move, and measure each bot's **average regret** against it. A ladder is monotonic if regret falls as the strength knob rises. **READ** `+.TSOTS-ALPHA-OMEGA/#.RULES/True_Swords_Clash_Rules.txt`: HP 100, Mana 0, Miracles cost 0-10; for example Fire (2 mana) = d6, mean 3.5 (1.75 HP per mana); Berserk (3 mana) = 13 on a coin flip, mean 6.5 (2.17 per mana); Holy Sword (10 mana) = 25 HP plus a 1-in-6 bleed (2.5 per mana, ignoring the bleed); Judgement steals mana on a coin flip. The mana challenge (ordering 2 to 10 verses) must be a parameter of the state (the bot's success rate by size), because a digipet's verse knowledge changes it.
2. **Paired duels with an early stop (SPRT) and common random numbers.** Play pairs with the same seed and swapped seats, and stop when the likelihood ratio crosses a threshold. That usually needs far fewer duels than a fixed N (DOC: I did not measure the saving).
3. **Full duels as a nightly confirmation only**, to catch a bug the oracle cannot see.
**Evidence needed:** the bot's strength knob, the TSC state schema and a seeded RNG in the op; none is built (`@.apps/TSC_ELO` was read, not run). **Negative test (required):** a bot with its knob inverted must fail layer 1. **OWNER:** none; this is an engineering choice.

## A-004 (answers Q-004) 2026-11-05: where signed receipts live

- **Gap to cover yourself (READ the `sig_op` header):** it does **not** handle nonce or replay tracking, a canonical transaction string, or which wallet a public key belongs to. A plain ledger must therefore carry `seq` and `prev_hash` and sign a **canonical row string**.
- **Design (DOC):** append-only rows `RECEIPT | seq | prev_hash | family | dataset_hash | n_rows | judge_id | grade | ts | sig`, signed with context `receipt:v1`; the hash chain makes the file ready to be anchored in a subchain later without changing the rows. Per AGENTS.md the runtime ledger needs an **enforced size cap, a second guard and a row in `RUNTIME-FILE-GROWTH-STANDARD.md`** (rows are tiny; rotate with a checkpoint row that carries the last hash). Only receipts and hashes ship, never the rows (SAID).
- **First file (DOC):** `&.widgits/concept-bank/data/receipts/training_receipts.pdl` beside the datasets (check where data ledgers live before choosing; the `concept-bank` data tree already holds ledger files). **OWNER:** the signing key's owner and where its passphrase is kept.
