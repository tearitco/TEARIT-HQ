The product is not a Gemma reply and not an OpenRouter chat.

🧱 The AI is trained to bootstrap its own game mechanics.
   A mechanic is an event-command brick. The same brick can sit on
   an NPC, an enemy, a game manager, or a scaler. That is the
   "AI for legos" line in H-AI-LAB-DESIGN.md Part 5, and the
   one-rulebook line in DUSTOPIA-HACK.md: one command, many bodies.
   Chemistry, battle, hunger, and a pet are content hung on that
   switch. They are not separate AIs.

🧠 The learner that remains is local, deterministic, and auditable.
   FSM + tomom / IRL + the Concept Bank.
   Weights live in files. Every change is an EDIT record.
   A page looks, then acts. The model does not press the key.
   ai_fsm_transition is still not a registered command. The local
   learner does not take a turn yet. That is the thing to build.

📞 Gemma (LAN, gemma3:270m) still fills the constrained bank line.
   open-hai's OpenRouter models do more than describe. They help
   bootstrap and finish tasks: train a bank layer, hand-tune a
   tomom weight, place an event brick, and make tool calls.
   Those calls are demonstrations. IRL learns from the trace the
   same way it learns from a player's actions. A weight edit
   stays an auditable record. OpenRouter does not become the
   runtime. When the local bank can do the next brick itself,
   the outside call can be turned off.

🔁 Bootstrap loop, in that order:
   watch a real event → tutor writes TARGET | STRENGTH | REASON
   → C scorer writes an EDIT → validator checks it → ledger promotes
   → the new weight is a command another actor can carry.
   Chat text and OpenRouter quizzes are fuel and a second tutor.
   They are not the architecture.

Open-hai is a junior with a narrow window. I stay the one who
decides the slice, checks the result, and keeps the architecture.

🟢 I will hand it a slice when ALL of these are true
   • One file, or one already-pasted excerpt.
   • The success check is cheap for me (a line in a file, a
     transcript line, a build line, a number that was planted).
   • A wrong answer is annoying, not a silent rewrite of a pal,
     a desk file, or the validator.
   • The model has already passed the competency quiz for this
     KIND of task. "It explained a function once" does not mean
     "it may patch the function."

🟡 How a slice actually runs
   • Model name written to sessions/model.txt. Exact slug.
     A misspelling falls back to local Ollama. I will read the
     file back before SEND.
   • printf 'SEND|...\\n' into state/request.txt
   • Wait until busy.state.txt is 0. A SEND while busy is dropped.
   • Read active_session.txt, then the tail of that transcript.
   • I do not trim or rewrite transcript.txt. That is the audit.
   • list_dir / read_file may run alone.
   • write_file / edit_file / cmd_exec wait for YOUR approve
     in the open-hai sidebar. I will not approve a write I have
     not read. I will tell you what the pending line says.

🔴 I take the task back myself when
   • The model skips the approval line and a gated tool runs.
     That is a harness bug. I stop and say so. I do not quietly
     "fix" the gate by widening it.
   • The answer does not match the file I can see.
   • The task needs a second tool hop, a desk relaunch, a pal
     restart, or a judgment about which copy of khtpm is live.
   • The quiz for that task type has not been run, or it failed.
   • The slice is the command registry, DESCRIBE/SCORE/VALIDATE,
     or anything that writes a live entity.

🔧 When the harness itself is wrong
   I fix the C / the script / the state file in this repo, on
   branch grok, with a build and a live transcript line.
   I do not ask the model to patch its own approval gate.
   cmd_exec's first bug was "the tool was never offered." That
   was a one-object JSON add, then a real echo test. That is the
   shape of a harness fix: small, gated, proven in the transcript.
