# blueprintz as the IDE for the book, and concept links on events (2026-10-14)

Hand-off plus design summary. Full design with phases: BOOK `08-roadmap/design-docs/BLUEPRINTZ-DESIGN.md`, **section 11** (this file points there; if they differ, section 11 wins). Written from the owner's words and from reading the real files. **Nothing in this file is built.**

## 1. The idea in the owner's words
The blueprint is an event page of event pages. It shows the entire book. It compiles all the events in a book and its pages, the common events and the plugins, as one code file that works like the game's event loop and calls the "events on page". It can modify entity events or common events as an alternative to editing by entity. It is an IDE for the book:page events. Separately: events should get concept-bank associations, because they are the most important pieces for automatic coding. Decisions given: the associations are shared (stored with the IR, read by the compiler), per event for now.

## 2. What exists (verified by reading files and counting)
- **Event format**: `event_pkg/pages/page_N/{condition.pdl, event.ir.pdl, event.pal, cmd_N.sh}`. IR rows: `NODE | id=N type=<command> | args`. Chain: IR > `event.pal` > `cmd_N.sh` > `mr_<command>.+x`. Source: `EVENTS-PAL-BUILDOUT-PLAN.md`.
- **3,662 `event.ir.pdl` files** in the house (counted 2026-10-15, sessions excluded; 12,838 NODE rows, 52 command types): 2,487 are imported tsots maps in piececraft-hq, 109 are rpg-pet's, about 105 each in the game scaffolds. (An earlier version said 109 for the whole house; that was rpg-pet only, my counting mistake.) The largest file is 8,494 bytes and no file has over 128 NODE rows. Command types by count: comment 2,692; if/end 2,554 each; show_text 1,160; show_choices 773; choice_to_switch 770; control_self_switch 563; ret 294; the per-game `*_pet_says` and `*_verb` rows; about 30 types in all. Mostly imports and scaffolds, few hand-written.
- **Command registry**: `#.ref/menu/event_commands.registry.pdl` (1,268 lines). Do not hard-code command lists.
- **blueprintz**: window `&.hq-apps/blueprintz/` (B0 shell, B1 read-only list for dsr-rpg, cdda-hq, df-hq, gta-hq), design doc B0-B5.
- **Editors that write the IR**: events-hq (`khtpm_events_hq_manager.c`), event-editor, event-ez, plus the converter `tsots_event_ir.py`. Only events-hq's ops were read for this.
- **Plugins**: `PLUGINS-ARCHITECTURE-SCOPING.md` (2026-08-25): per-project list, toggle on/off, ordered, `.pal` that triggers ops. Scoping only, no code.
- **Concept bank**: `&.widgits/concept-bank/` (masters, spokes, physics and chem stubs, image words, an unwired promotion rule). It has no game, door or command nodes yet.

## 3. What is new in the design (section 11 of the BOOK doc)
1. Blueprintz also produces **`book.pal`**: one generated program for the book that calls page events, common events and enabled plugins in order. Generated from the IR, never the source.
2. Plugins are part of the book (depends on the plugin manager, which does not exist yet).
3. `META | concept | <node> | source=hand|rule|model` rows on events; a validator that rejects nodes missing from the bank; concept grouping in the book view; "events for concept X" query.

## 4. Why concepts on events
Automatic coding needs (a) retrieval of the closest existing events for a new one ("shopkeeper greets the player" finds `greeting` and `trade` events), (b) a typed vocabulary (the ~30 command types as nodes with usual parts), (c) a judge (the IR must parse, compile and run through the relay), and (d) scored outcomes for the bank's still-empty promotion ledger. Links give (a) and (b); (c) exists; (d) starts when generated events pass or fail.

## 5. Facts found while checking that the links are safe (read, not run)
- The readers I looked at take only `NODE` rows, so an added `META` row is ignored by them.
- events-hq edit and delete copy other rows forward, so a concept row survives; add appends.
- **Hazard, reproduced and fixed 2026-10-15**: edit and delete held the whole IR in an 8,192-byte buffer. Scratch test: an 11,016-byte, 110-row IR lost 29 rows on one delete (81 left, cut at 8,164 bytes). Fixed with a growing buffer; the fixed build kept 109/109 after delete and after edit, and kept concept rows at the top and the end. One real file (8,494 bytes) was already over the old limit. Scratch copies only; the running events-hq manager has the old binary until rebuilt.
- Not run: the events-hq window itself; event-editor, event-ez and the converter with a concept row. `compile_page` also stops silently at 128 NODE rows (largest real file: 61).

## 9. Update 2026-10-15: blueprintz as the debugger (play, pause, step)
Owner: blueprintz should also sit under **player**; it is about stepping through the visual code. It shows **all events on the page**; Play runs the page; an event such as Change Gold **waits for its trigger**. Full design: BOOK `BLUEPRINTZ-DESIGN.md` **section 12** (it wins if they differ).
- **Exists (read):** the desktop play switch `#.desktop/khtpm_play_mode.state.txt` (`mode=on`, optional `playtest=1`); triggers only fire while it is on; every event is run by one script, `play_event.sh <pkg> [house] [trigger]` (called by the touch script, `rpg_pet.c`, the pals' Play method, the events-hq Play button). Triggers in the house: on-click 2,634, on-touch 87, parallel 65, Autorun at least one.
- **Does not exist:** pause, step, trace, breakpoints. The old inert pause row was removed 2026-09-14.
- **Plan:** a tiny gate in `play_event.sh` (missing debug file = run as today); paused triggers go to an append-only queue; Step event runs the oldest queued event; Step command runs one command (needs a decision: run the Nth `exec cmd_N.sh`, or single-step the pal in the VM, not checked); per-row Fire; page view with a state column (waiting, queued, running, done, error) and before/after values.
- **First example:** `m8_redhorned` (template in `_.muchi-pet/entities`): on-click, Change Gold +10 and +25, has `gold.txt`. The owner's live copy is owner data: read only. Demo on a scratch page with copies of it and `greet_player` (Autorun, +1 and +777, and a malformed duplicate `id=4`).
- **Owner decisions (second pass):** step with the **prisc VM**; first build is **visualize and flag problems only**; `m8_redhorned` (an inventory item of `cursword`) fires through cursword's Play method; **all event firing should go through `play_event.sh`**. Details and the flag list: design doc section 12.8.
- **Findings (read, not run):** cursword's Play goes through a 1,066-byte shim that forwards to the real script, so one gate covers it. The live `m8_redhorned` has its own Play object pointing at a script in another checkout that does not exist (owner data, not touched). `doom_event.sh`/`chess_event.sh` are verb executors that 2,557 event commands call (already inside `play_event.sh`); the real gaps are direct callers: `pc_entity_ctx.sh`, `pc_menu_input.c`, `pchq_board_action.sh`, `chess/open.sh`.
