## 1. Where it stands (RAN 2026-11-17)
The phone app `rpg-edit` (v1) is a LAUNCHER: its screen opens the desktop editor window (guide section 9). It is NOT this design. Done and reusable here: the phone app package and install path, the `emoji_icon_op` icon setting, the corner-map click-to-move (3D and 2D), the relaunch that reopens the last page.

## 2. Facts that decide the shape (READ)
1. **A per-instance editor is cheap.** `@.apps/piececraft-hq/ops/pchq_instance_init.sh <data dir>` creates one pc-hq data folder (world_01, hero, xelector, `pieces/system/*` config, `pieces/sessions`); the programs are shared, only data is per instance; the folder NAME must be unique in the house (engine sessions are scoped by it). The real editor links each book into `<its data dir>/pieces/system/maps/<book>` (`board/open_board.sh`, `ln -s`), which is how data stays shared: a second instance linking the SAME book folders reads and writes the same files.
2. **The editor window = layout + projector + engine session.** `board/pchq-board.xhtpm` (212 lines: a `rail` sidebar, bars, `<canvas id="view" sprite="${canvas_raw}"/>`) with `<module src=".../pchq_board_projector.+x" args="rpg-edit-hq-pchq"/>`. The projector writes `<pkg>/state/ui.txt` (bv_session, canvas_raw, interact label, clock, menu state, desk list) only on change; the 3D engine session is created by the launcher from the data folder.
3. **The renderer already routes a window's canvas to ITS session** when the window has a `bv_session` var (`kh_session_display_path` in `khtpm_core_render.c`): the canvas size goes to `<bv_session>/pieces/display/board_view.txt` and clicks to `canvas_click.txt` there, and the engine (`bv_prefer_session_file`) reads that copy first. **But** both writes are gated by `kh_is_pchq_board()`, which is true only when the layout file is named `pchq-board.xhtpm` (lines ~7445 and ~10151). A phone screen is `plus-phone.xhtpm`, so today its canvas would never report its size or take clicks. The fix must be GENERIC (house rule: zero per-project C in the shared renderer): "a window that has a `bv_session` var and a canvas publishes size and clicks into that session; the house-wide fallback files stay for the pc-hq board only".
4. **A phone window's module is always `phone_projector`** (guide section 8 item 2); an app screen's own module is started by it as a child and ends with its window. So the embedded editor's engine and projector are started by the app op (`redit_op`), not by a window launch.
5. **The top bar and the footer are tokens** (`${PHONE_BARS}`, `${PHONE_FOOTER}`), the bottom bar is a window list (item 5) with minimized cells; the editor's sidebars can be cells there.

## 3. Design-choice test (the five questions; the log row is D88 in 02-architecture/DESIGN-CHOICE-TEST-AND-DECISION-LOG.md)
Shapes: (A) a phone-size screen that reuses the editor's own projector and engine through a bridge, with its own per-phone data folder; (B) a separate phone-native mini editor (new code for map, pickers, tools); (C) keep the launcher. Chosen: A. One authority: the editor's code and book data stay the only editor; the phone adds a screen and a bridge, no second editor. Modular: the bridge is one op; the renderer change is generic. Scalable: the 10th phone is another data folder; the 10th embedded app that wants a canvas reuses the same renderer rule. Long term: it is the owner's stated end state (the editor in phone view). House shapes: op plus file IPC, a per-instance data folder, text files, harnesses that can fail. Cost/risk: the shared-renderer gate (mitigated by a case and a before/after of the real board), one more engine session (CPU: measure idle and active before claiming).

## 4. The plan (slices; each ends with a picture and a harness that can fail)
- **S0 DONE 2026-11-17 (RAN):** `kh_canvas_size_path()` in `khtpm_core_render.c` (two call sites): a window with a `bv_session` var writes its own session size file, the house-wide file stays the pc-hq board's. Harness `canvas_session_size` 8 (the real renderer in scratch windows: no session var writes nothing and leaves the house-wide file byte for byte; a session var writes its session; the old renderer binary fails the second, restored). Regression: the real editor board relaunched on the new renderer still reports its session size (1127 x 741) and the house-wide file is unchanged. Windows keep the OLD renderer until relaunched.
- **S0 (renderer, generic):** `kh_is_pchq_board()` stops gating the SESSION writes: any window with `bv_session` writes size and clicks into that session; the global files stay pc-hq-board-only. Proof: the real editor board still works (the size file and a click land where they did), a window without `bv_session` writes nothing, a scratch window with `bv_session` does. Needs a renderer rebuild (`LIVEDESK_NO_SPLASH=1`, through `cpu_gate`) and a relaunch of every window to test.
- **S1 (the screen and the bridge):** `redit_op` grows from launcher to host: per-phone data folder `<phone inst>/editor-pchq/` (unique name) from `pchq_instance_init.sh` plus the book links; starts the projector and the engine session for it; copies the projector's ui vars (`canvas_raw`, `bv_session`, the page list) into the phone ui.txt each change (a marker-driven bridge, no polling beyond the existing 5 s); `screens/edit.xhtpm` = `${PHONE_BARS}`, the page picker row (book and page dropdowns, `In:` switch), the canvas filling the middle (about 364 x 600), `${PHONE_FOOTER}`. Shared data: the links point at the same book folders as the desktop editor.
- **S2 (sidebars):** every editor sidebar starts MINIMIZED as a bottom-bar cell (palettes, pets, chat); tapping the cell shows that sidebar over the map; the state is a preference file, not game state. UNKNOWN: how `pal_side` and `state/sides_history.pdl` map onto phone cells; read before S2.
- **S3 (controls):** the phone window already takes keys (SAID); corner-map click-to-move and taps work from S1. An on-screen touch/click navigation keyboard (arrows, camera keys) is DOCUMENTED here and waits (owner: "we can doc and wait").
- **S4 (tools and Play):** later; palette picking and placement, then the Play button.

## 5. Not decided / UNKNOWN (check, do not assume)
- Whether the engine session of a second pc-hq data folder starts cleanly beside the desktop editor's (CPU and the "one heavy job" gate apply; `cpu_gate` and measure).
- What the editor does when two instances edit the same page at the same moment (shared files: the existing marker-file polling picks up the other's change; conflicting edits are not designed).
- The projector's `args` (host project id) and how its `state/ui.txt` path is derived from a phone-owned data folder.
- Whether `<canvas>` inside a phone screen is laid out with the generic region code (`kh_layout_canvas_in_region`) or needs the sidebar-panel path the board uses (the board layout takes `layout_sidebar_panel`).
