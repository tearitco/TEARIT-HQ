## 3. Design (DOC)
### 3.1 One authority per fact
- The **message** lives in the sender's `outbox.txt` and the recipient's `inbox.txt` (router-written). `history.txt` is the per-phone projection. The app never writes an inbox.
- The **audit trail** is `^.hai-server/ledger.txt` (append-only, no text). The app reads, never writes it.
- The app keeps only a **view cache**: `<instance>/texting/` (contacts, the open thread projection, byte cursors). Safe to delete; rebuilt from the phone files (same rule as every projection, NO-GHOST-DATA).

### 3.2 The app: `texting` (phone app package, standard icon a speech bubble)
Screens (phone layout rules: `PHONE_BARS`, `APP_CHROME`, `PHONE_FOOTER`):
1. **Threads**: one row per peer, newest first, last line and an unread mark (inbox bytes past the app's own read cursor).
2. **Thread**: the lines exchanged with one peer (from `inbox.txt` and `outbox.txt`, filtered by number, merged by `<ms>`), a `<cli_io>` field, **Send** = `phone_op`-style verb of the app's op `text_op` which calls `phone_send_op` (kind `say`, ref = the thread id).
3. **Contacts**: see 3.3. Tap = open (or start) the thread.
Ops in the app's `ops/` (C only, no new `.sh`): `text_op contacts|threads|thread|send|read`.

### 3.3 Contacts auto-populate
Source = `phones.index` (the only list; the server never rescans the house). Order: (1) my own phone's thread peers, (2) **entities I own** (their `entity_dir` is under my own user folder), (3) other users and their entities. A contact shows the `label` and the number only. Other users' folders are private: the app reads **only** the index row, never the other user's files; delivery into their inbox is the router's job, not the app's.
Blocking: a per-user `block.txt` (numbers) honoured by the router (a router change, one more joint); default = nobody blocked, a phone may set "only owned" (DOC).

### 3.4 Privacy and the ledger (OWNER: hashed or whatever)
- **Slice 1 (safe, no chain change):** extend the router's ledger row with `sha256(text)` and a message id (`<ms>-<n>`), so a message is committed without its text. The numbers are already pseudonymous (derived from hashes).
- **Slice 2 (chain):** a commitment tx `MSG | <msg_id> | <from> | <to> | <sha256(text)>` appended to the chain as a new tx type. **This needs `PAL-CHAIN-STANDARD` changed first** (v1 only knows money TX lines, no signing, tx_id is a local dedup key): read the standard, add the type and the miner rule, add a harness, then wire it. Never inject into the real chain before that. The text itself stays off-chain (phone files); the chain proves "this message existed at this time".
- Encryption of the text at rest is NOT in slice 1 (phone files are plain text today): say so in the app's help, do not claim privacy the files do not have.

### 3.5 Entities answer (OWNER: AI/FSM via an event trigger)
- **Trigger:** the router already knows when an inbox grew. A small op `phone_reply_op <phone_dir>` (resident or fired by the router after delivery) reads the entity's inbox from its own byte cursor (size growth, never mtime) and for each new `say` line asks the entity's **reply policy**: `<entity>/reply.pdl` rows `REPLY | <match> | <action>` where action is `text <fixed reply>`, `event <page>` (plays an event page, which may call `phone_send_op`), or `ai <backend>` (the house AI layer, rate-limited, off by default). **Default (OWNER decision 3):** a phone with no `reply.pdl` of its own uses the shared template `^.hai-server/_TEMPLATE/default-reply.pdl` (one default reply event, editable in plain text: change the text, the `event` page or `ai` rule, or set `REPLY | * | none` to go silent); the router never overwrites an edited file. The default text says it is automatic.
- **Safety:** an auto-reply is a normal outbox line (kind `say`) so it passes the same rate limit and ledger; a per-pair reply cap (for example 3 per minute) stops two entities talking forever; the loop guard is a joint in `tunables.conf`.
- **Test case (documented for users and agents, harness `texting_reply`, scratch house, NO network, no real entity):** two scratch phones A (a human-like sender) and B (an entity with a `reply.pdl`). Steps: (1) A sends `say` to B with `phone_send_op`; (2) one `server_route_op` pass: B's inbox has the line, the ledger has one row and no text; (3) one `phone_reply_op` pass: B's outbox has the reply addressed to A; (4) a second router pass: A's inbox has the reply; (5) negatives: a phone whose `reply.pdl` says `none` stays silent; a phone with no file gets the template default reply, marked automatic; an EDITED reply.pdl is used instead of the template; a message from a blocked number gets no reply; the loop cap stops a ping-pong after N messages; a spoofed sender number is refused by `phone_send_op`; sabotage proof for each (remove the cap, remove the block check). The same steps, as prose with the exact commands, go into this doc and into `XO/31.Nov/nov-16/` when the case passes.

**SUPERSEDED IN PART (OWNER 2026-11-16: "the auto reply should use events"): the reply is an EVENT PAGE, not a `reply.pdl` rule file. Section 3.5e below is the design; the `reply.pdl` wording in 3.5 stays only as the history of the idea.**

### 3.5e The auto-reply is an event (OWNER 2026-11-16)
**FOUND (read 2026-11-16):** the house event system is `event_pkg/pages/page_N/` inside an entity (or a book): `condition.pdl` (`COND | trigger | <name>`), `event.ir.pdl` (NODE rows), generated `event.pal` + `cmd_N.sh` (compiled by `khtpm_events_hq_manager` on every save, from the command registry `#.ref/menu/event_commands.registry.pdl`: 170 `COMMAND` blocks, adding one is DATA ONLY, no recompile), played by `&.widgits/events-hq/ops/play_event.sh <package> <house> <trigger>` (runs the HIGHEST-numbered page whose trigger name matches exactly; **trigger names are free text; switches/variables as conditions are NOT supported yet**). Pages are edited in events-hq / event-ez (the "ez" editor) and programmatically by `bp_edit_op`. A harness recipe for a scratch house that runs AND edits real pages exists: cases `eat_page`, `book_db` (real `play_event.sh`, the registry, the events-hq manager, `bp_edit_op`, `wo.+x`, a scratch `101.mutaclsym` system dir with `prisc+x`).
**Design (DOC):**
1. **A new trigger name `on-message`** (a text arrived in this entity's inbox). No engine change: it is a string in `condition.pdl`.
2. **New registry command(s), data only:** `phone_reply` (FIELD1 = the reply text; TEMPLATE runs the existing `phone_send_op.+x` with the entity's own phone, to `$MUCHI_MSG_FROM`, kind `say`, ref `t:<from>`), later `phone_say` (to a fixed number) and `phone_reply_ai` (the house AI layer, rate-limited, off by default). The page's NODE rows use these types, so the reply is the same kind of page every other event is.
3. **The event source = one small op `phone_event_op`** (the "phone.on-message" event; C, like `server_route_op`): reads each entity's inbox by BYTE CURSOR (size growth, never mtime), and for every new `say` line runs `play_event.sh <entity event_pkg> <house> on-message` with the context in the environment (`MUCHI_TARGET_ENT`, `MUCHI_PHONE`, `MUCHI_MSG_FROM`, `MUCHI_MSG_TEXT`). It runs from the router loop (`router.pal`: `exec server_route_op` then `exec phone_event_op`), so it costs nothing while nothing arrives. It never writes an inbox or an outbox itself: the page's `phone_send_op` writes the outbox, the router delivers (one writer per file).
4. **The default reply = a shared event package** `^.hai-server/_TEMPLATE/default-reply-event/event_pkg/` with one page (trigger `on-message`, one `phone_reply` node, text `[auto] <name> got your message and will answer later`, OWNER 2026-11-16: marked automatic). An entity with its OWN `on-message` page uses that; an entity without one falls back to the template (the trunk-and-branch standard, level L1: the branch page replaces the trunk page; nothing is copied until someone edits). **Editable ez** = open the entity's event in events-hq/event-ez and change the node text (or the page); saving writes the entity's own page (the branch). A phone can go silent by an `on-message` page with no nodes.
5. **Safety (named joints in `tunables.conf`, every decision an `observations.log` row):** never reply to a line whose text starts with `[auto]` (two bots never chain), `reply_max_per_pair_per_min` (default 3), `reply_batch_max` per pass, and `reply_enabled` (default 1; 0 = the whole source off). A reply is an ordinary outbox line, so the router's per-sender rate limit and ledger apply too.
6. **Test case (harness `texting_reply`, scratch house, NO network, no real entity), documented for users and agents in this doc and in XO when it passes:** (a) A texts B (an entity with NO page): one router pass, one `phone_event_op` pass, one router pass: B's outbox holds the template reply `[auto] ...`, A's inbox holds it; (b) give B its own page with other text via `bp_edit_op` (the editable-ez proof): the reply text changes, the template is NOT used; (c) negatives: a line starting `[auto]` gets no reply; a page with no nodes stays silent; the pair cap stops a third reply in a minute; `reply_enabled=0` stops everything; a spoofed sender is refused by `phone_send_op`; the cursor makes a second pass reply to nothing new (idempotent); (d) sabotage proof for each negative (cap removed, `[auto]` guard removed, cursor ignored), binary deleted/rebuilt/verified.
**The AI reply (`phone_reply_ai`):** how an entity's model is reached, tested and used safely is in `17.ai/ENTITY-LLM-ENDPOINTS-HOW-TO-TEST-AND-USE-2026-11-16.md` (the shared LAN Ollama endpoint, the `ai_chat*` contract, a live test recipe that RAN, the quota and privacy rules). Call `ai_chat.+x <entity_dir> <house> "<text>"` and take the last line of `chat_history.txt`; opt-in per entity, off by default.

### 3.6 Group chats (later)
A group = one append-only **group ledger** `^.hai-server/groups/<gid>/messages.txt` plus `members.txt` (numbers). The router fans each group line out to every member's inbox (one `say` line each, `ref = g:<gid>`); membership changes are rows (`JOIN`, `LEAVE`, `KICK`) so history is replayable. The thread screen is the same screen filtered by `ref`.

### 3.7 AV (voice/video) later
Signalling is the same text path (`command` kind: `call <gid-or-number>`); media is a separate transport (palnet peer or WebRTC) and is NOT designed here; the phone has no camera or mic API yet. Out of scope until text and groups pass.

### 3.8 Caps and costs (RUNTIME-FILE-GROWTH-STANDARD rows to add when built)
`inbox.txt`, `outbox.txt`, `history.txt` rotate at the phone's own caps (2000 lines / 262144 bytes, 3 generations, server-rotated, already in `phone.pdl`); `ledger.txt` and `observations.log` need a rotation row (check the standard); the app's `<instance>/texting/` cache is capped at 64 KB per contact list and 256 KB per open thread. Idle cost: the router loop (2 s sleep, one exec per pass; measure with a browser running before shipping, as the standard requires).

### 3.9 Search, added contacts, notes (OWNER 2026-11-16: "that stuff can be searchable, add contacts, note, etc.")
- **Address book = a user-owned, append-only file** `<my phone dir>/contacts.txt` (it lives with the human's phone, NOT in the phone instance, so deleting a phone window or instance never loses it). One row per change: `<ms>|CONTACT|<number>|<name>|<tags>`, `<ms>|NOTE|<number>|<text>`, `<ms>|RENAME|<number>|<name>`, `<ms>|DELETE|<number>`. The current book is derived by replaying the rows (a projection, safe to rebuild; same rule as every ledger here). A contact can be a number typed by hand (it need not be in `phones.index` yet: the router answers an unknown number with a `fail` message, so a typo is visible), or picked from the auto list (3.3). The auto list and the address book are merged by number; the user's name wins over the index label.
- **Notes** are private: a note about a contact or a thread, never routed, never in the ledger, never on the chain, never sent to another phone (the router does not read `contacts.txt`). Tags (`friend`, `bot`, `owned`) are free words.
- **Search verb** `text_op search <query>` (C, case-insensitive substring, no shell): looks in (1) contact names, numbers, tags and notes, (2) message text in MY OWN `inbox.txt` / `outbox.txt` / rotated generations (only my phone's files, never another user's). Results are rows `contact: <name>` or `<name>: <line snippet> (<date>)`; tap opens the thread. Slice 1 scans with caps (stop after 200 hits or 4 MB read); if it gets slow, add a derived `search.idx` projection with a byte cursor (never mtime), rebuilt from the same files. The house already has a search-field pattern (`@.apps/layout-studio/templates/menu-search.xhtpm`, the Tools dropdown search): reuse the `<cli_io>` + results-list shape, do not invent a second one.
- **Privacy note:** because search reads message text, it works only on files the user already owns; a hashed ledger row (3.4) is not searchable and does not need to be.
- **Tests (added to `texting_app`):** add a contact by hand then see it in the list; a note is found by search and is NOT in the router ledger or the other phone's inbox (negative); a search term in another user's file finds nothing (negative); a rebuilt projection after deleting the cache is identical; a DELETE row removes the contact but keeps the thread; the caps stop a huge scan.

### 3.10 Shared contacts: a trunk and branches, like git (OWNER 2026-11-16: "contacts can be shared, and stem from a trunk, like gits")
**This is an instance of the house standard `02-architecture/TRUNK-AND-BRANCH-SHARED-DATA-STANDARD-2026-11-16.md` (decision D87): the rules, the row format and the shared op `trunk_op` are defined THERE; Texting only adds its keys (contact number) and its privacy flags. Where this section and the standard differ, the standard wins.**
- **Model:** the address book is not one file but a **trunk** (a shared book) plus **branches** (one per phone, or per user). A branch **inherits** every trunk row and adds its own rows on top; a row on a branch wins over the same number on the trunk for that branch only. Nothing is copied: a branch stores only its own rows plus a pointer to the trunk (`TRUNK | <path or id> | <trunk head>`), so a trunk edit shows up in every branch that has not overridden it.
- **Rows carry an id** (`<ms>-<phone number>-<n>`) so books can be combined without conflicts: **sharing = publishing rows to the trunk**, **updating a branch = replaying trunk rows newer than the branch's recorded head** (a fast-forward), and **merge = the union of rows by id, then the latest row per number wins** (the same replay rule as the ledger; no hand merging, no ghost state). A DELETE on a branch hides a trunk contact for that branch only; a DELETE on the trunk removes it for everyone who has not overridden it.
- **What is shared and what is not:** names, numbers and tags can be published; **notes are private by default** (a row flag `private`, never published, never read by another phone's app); the user chooses per contact what goes on the trunk.
- **Who may write the trunk:** the owner of the trunk (initially the human's own book); entities the user owns can READ it (so an owned entity "knows" the contacts) but write only to their own branch; a published row from another user is a pull request in spirit: it lands on that user's branch, never silently on someone else's trunk.
- **Files (still plain append-only rows, DOC):** `<trunk dir>/contacts.txt` (the trunk), `<phone dir>/contacts.txt` (a branch) with its `TRUNK` row; verbs of `text_op`: `contact add|rename|delete|note`, `contacts publish <number>` (copy a row to the trunk), `contacts sync` (fast-forward the branch). The git analogy is for the mental model only: no git is used, the format is rows and replay.
- **Tests (in `texting_app`):** a trunk row appears in two branches; a branch override changes only that branch; a trunk edit after the branch override does not clobber it; publish copies a non-private row and refuses a private one (negative); sync is idempotent (second run changes nothing); deleting the cache rebuilds identical books.
