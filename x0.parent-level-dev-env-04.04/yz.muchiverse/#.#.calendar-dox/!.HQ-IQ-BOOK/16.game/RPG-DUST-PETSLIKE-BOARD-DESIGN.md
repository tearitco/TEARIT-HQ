# rpg-dust as a real pets-like board: Regen + tilesets on the left (design, 2026-10-23)

Owner, 2026-10-23, after opening the first rpg-dust window from the toys menu: "the hot bar doesn't minimize. and theres no chat yet or pets? should have all the same things as petslike, day night, etc" and "in left instead of pets, we will have 'regen' and different 'tilesets' to pick and change, doom, rpg maker cdda mineclonia etc" and "document this stuff if u need".
Companion of `RPG-DUST-DESIGN.md` (the world) and `PETSLIKE-FRAMEWORK-PLAN.md` (the core). Written by the claude engineer. Labels: **READ** from files, **PROPOSED** design, **UNKNOWN** not yet checked.

## 1. What is wrong with the first window (READ)

The first rpg-dust window (commit `da8fc7da9`, entry in the toys menu 2026-10-23) is a **plain pc-hq board**: `board/open_board.sh` exports a map book and opens the shared board with a copy of **piececraft-hq's default template**. That template has no chat, no clock, no pets bar and a hotbar overlay drawn by `hotbar-hq` that has no minimize cell. The pets-like boards get all of those from somewhere else:

| What the owner expects | Where it comes from (READ) |
|---|---|
| chat (right bar, `cli_io` as the selected entity) | `petslike_core.c` verbs and `state/ui.txt` keys `chat_0..5`, `active_name` |
| day / night, Time menu (speed, skip +1 h / +1 d) | core clock (`clock_ui.txt`, `run_label`), `publish_sky`, the engine's sun light from `game_time_epoch_sec` |
| hotbar with a minimize cell (`hb-min`, `toggle hb`) and `_` buttons on both side bars (`sl-min`, `sr-min`) | the pets-like **board template** (`&.widgits/_shared-lib/petslike/board.xhtpm.in`), verbs of the core op |
| pets / stats on the left | `party` rows in `state/ui.txt` from `party.pdl` |

All of these call the **core op of the game** (`rpg_edit_hq.+x clock rate min`, `... toggle hb`, `... fire use <key>`). A game without a skin on the core has no op to call. So the fix is **not** to patch the template: rpg-dust must become a **skin on `petslike_core`**, like the nine existing games.

## 2. The target (PROPOSED)

A pets-like board named **rpg-dust** with the same frame as the others and two differences, both owner decisions:

1. **Left bar = Regen + tilesets** instead of the pets list: a `regen` button and a list of tilesets (rpg maker, doom, cdda, mineclonia, df, ... one row each) that re-skin the same world.
2. The world is the rpg-dust world: pages come from the seed (`dust_gen`), zoom is the zoom ledger (`dust_zoom`), not the island painter of rpg-edit-hq.

Everything else is inherited: chat, clock and day / night, hotbar (with its minimize), side bars (with their `_`), Player / Time / Menu tabs, save / load, INT.

## 9. Owner direction, same day: zoom is the SHIP's size, not the camera's (changes the roadmap)

Owner: "as far as zoom in or zoom out, the ship is what will change in size relative to the surroundings, so it could go underwater and become very small, to see shrimp. or as it teleports, it's near the size of the planet, but it can also be the size of a car, or of a flea. ... it could even go to molecular size. you may want to document that because it may change how you planned the roadmap."

**D19.** The world stays where it is; the **ship scales** relative to it. Planet-sized when it arrives above a planet, car-sized, flea-sized, down to molecular. Nothing "zooms" a camera over one map; what you see around the ship is the world at the size the ship has now. Underwater the ship can shrink to look at shrimp. The ship's **interior** (bridge, quarters, hold, doors, pets) keeps its own human scale at every ship size; only the ship's footprint in the surroundings changes.

What this changes against `RPG-DUST-DESIGN.md` and the code built so far (READ from the code, not yet reworked):

| Piece | Before | After D19 |
|---|---|---|
| zoom events | `dust_zoom zoom_in/zoom_out` move a **camera address** region -> area (ledger START / ZOOM rows) | they become **ship size events**: the ship's size level is state (a ledger row per change, replayed), the address of the ship's **position** is separate and fixed while it shrinks |
| address | one chain `globe:3,4/region:0,1/cell:7,9` that zoom walks down | the ship has a **position** (a point on a planet, or in space) that yields an address at EVERY level (planet, region, area, play, body, tissue, cell, molecule); shrinking reads the next level of the same position |
| scale ladder (`scale.pdl`) | the levels you zoom through | the levels the ship's size can take; `log2_m` of the ship picks which level's page is drawn around it (cells about the ship's size) |
| conservation rule (area heights sum to the parent cell) | proves a zoom invents nothing | **still needed and now more important**: when the ship shrinks the surroundings must agree with the coarser view it just left |
| generators | terrain heights only | need a **vertical dimension** (the sea has a depth, the shrimp live in it) and creatures / structures as entities that exist at the levels where they are visible (shrimp at about shrimp size, not before) |
| "play" level | a page of cells you walk on | the ship at about human / car size; the pets walk the ship's own rooms, not the terrain |
| roadmap order (design section 9: R4 species, R5 reactions, R6 cook, R7 menus, R8 on-demand pages, R9 society) | anatomy and chemistry reached by zooming the one map | reached by **shrinking the ship** at a position: anatomy appears when the ship is shrimp-sized beside a shrimp, molecules when it is smaller; **R8 (on-demand pages) moves to the front**, because every ship size at every position needs its page made on demand |

Re-ordered next steps (PROPOSED): (1) ship state: position + size level + heading as ledger rows (`ship.pdl` / `space.pdl` with suns, planets, ship position, light by distance: D16); (2) turn `dust_zoom` into ship size events and keep the address chain per position; (3) on-demand page seam in the core (old R8); (4) vertical dimension (depth under water); (5) the first creature at its size level (old R4); (6) bigger planets (D17), structures (buildings, cars, towns) as generator layers at the levels where they are seen (D11); (7) molecular level (old R5).

## 12. Shared code with the other pets-like skins (2026-10-23)

`&.widgits/_shared-lib/petslike_skin_lib.c` is a pure text-include used by the two skins that paint their own maps (rpg-edit-hq, rpg-dust): `sk_solid`, `sk_drop_sheet` and the pet roster (pictures, generated character sheets, 3D walk frames). ## 13. Flying the ship: helm panel, flyable planets, a star map (owner 2026-10-23; PROPOSED, nothing built)

Owner: "add controls to the ship, some kind of computer or panel event that when we interact lets us fly the ship; all planets flyable by ship; on the minimap or some other map; nothing's on the minimap currently?"

**Minimap today (READ, bv_render_3d.c bv_draw_minimap):** an engine overlay: top-down columns of the CURRENT desk plus the selector dot. It has no idea of planets or the ship's place in space, so it cannot show them. A space map therefore is a separate thing (below), not a tweak of that overlay.

**Design:**
1. **Helm panel** = a decoration object (the bridge's monitor/console tile) that is also an EVENT cell: interacting with it (Interact key / click next to it, like a door cell) plays an event page `helm`, which turns on **flight mode** (flag `state/flag_fly.txt`) and sets the controlled entity to the ship. 2. **Ship state** (new ledger `state/ship_ledger.txt`, append-only, replayable like the look ledger): position in a star-map plane (x, y), heading, speed; `SHIP|t|x|y|heading`. Flight verbs `thrust`, `turn`, `stop` (arrow keys while flying), each one row.
3. **Flyable planets**: each planet in planets.pdl gets a position (new fields x, y, radius) in the star map. Entering a planet's radius = "over planet" = today's `planet <id>` event (same page, same ledger row); leaving = deep space. So the planet buttons in the left bar become shortcuts that move the ship to that planet's position, and flying there by hand gives the same result. `New planet` places the new planet at a free position.
4. **Star map**: a new board page/window (a 2D desk, `SK_STAR`) painted by the skin: planets as discs (labelled), the ship as an arrow, the route; shown as a panel in the toolbar or its own tab. Own painter, because the engine minimap cannot do it.
5. **Order of work:** (a) planet positions + ship ledger + `fly`/`thrust` verbs with a plain text test, (b) star-map painter, (c) helm event cell on the bridge console + flight keys, (d) planets enter/leave by distance, (e) harness cases (determinism by replay, a flight into and out of each planet, wall of the ledger).

## 14. Lights in the board engine (owner 2026-10-23: "its always dark in space, the ship's rooms should have lights ... we can build light into the engine, it was supposed to be doing that from the sun")

**Before (READ):** the engine had ONE light number for the whole picture: `compute_sun_light_level` from the game clock (sine, 12 h light / 12 h dark, floor 0.15) multiplied every hit; the GPU shader had a single `u_light`. So a ship in deep space went dark at night and nothing local could be lit.
**Built (&.widgits/board-viewer, opt-in per desk):** a desk's `lights.pdl` (next to `parallax.pdl`): `AMBIENT | level` REPLACES the sun for that desk (a room lit by its own lamps looks the same at noon and midnight); `LIGHT | x | y | z | radius | r | g | b | strength` adds `colour * strength * (1 - d/radius)^2` at a hit d cells from the lamp (x column, y row, z cells above the floor top; at most 8 per desk). GPU path only (the painted-map boards run with `use_gpu_render=1`; the CPU path does not draw painted maps). A desk with no `lights.pdl` is drawn exactly as before.
**RAN:** `ops/bv_gpu_light_test.c` (headless GL): old vs new shader unlit picture byte-identical (172,800 bytes); ambient 0.6 is about 4x brighter than the night sun, ambient 0.15 darkens a noon desk; a lamp lights blocks near it (10 of 72 blocks >= 1.8x) and leaves 47 exactly unchanged; a red lamp adds only red; the test fails when the lamp line is removed from the shader (2 FAIL, exit 1). Live in rpg-space at night: bridge brightness 33.6 with lamps, 12.0 without the file, 33.6 again when restored.
**rpg-space:** `lights.pdl` of the app (AMBIENT and LIGHT rows per ship room, colour per room: cool white bridge, warm quarters, yellow hold, red-orange engine); the skin writes each ship room's own `maps/rpg-space/<room>/lights.pdl` at export. Planet desks have none, so planets still follow the sun.
**Not done:** no visible lamp objects (the light comes from invisible points 3 cells above the floor); no shadows from lamps (the old CPU path has sun shadows, the GPU path none); the sun itself is still one global number, not a position (the "sun lights it" model: a sun point light per planet is the natural next step and fits the two-suns plan); the engine only reloads a desk's `lights.pdl` when the desk reloads (touching `cells.rgba` forces it), not every frame; relaunch needed for other boards to pick up the new engine; lamp positions are guesses, check the look.
