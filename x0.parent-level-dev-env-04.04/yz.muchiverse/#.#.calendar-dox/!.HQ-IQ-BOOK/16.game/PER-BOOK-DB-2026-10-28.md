# Per-book db (2026-10-28): the db is not house-wide

Owner, 2026-10-28: the `db` tab is the db; **each game / book has its own db; it was never meant to be house-wide.** This is the first fix. Labels: RAN = I ran it today, READ = read in a file, MINE = proposal.

## 1. What was true before (RAN / READ)
- The `db ▾` tab of every game window opens **db-hq** (and sql-hq): one RPG-Maker-shaped, 15-tab database in the single folder `&.widgits/db-hq/data/` (14 files, 128K, 775 actors). **No game had a db of its own.** Six games read the same party rows (`party_row` = `DsrRpgParty` etc.).
- The game core (`petslike_core.c load_party`) read that shared folder; only the environment variable `PET_DB` could point it elsewhere.

## 2. What changed (step 1, built and tested)
- **Resolution order in the game core:** `PET_DB` (kept) > the game's own `<app>/db/` > the shared `&.widgits/db-hq/data` (fallback only for a game with no db yet).
- **New verbs:** `db` says which db the game uses; `db seed` copies the shared db into `<app>/db/` **once** and never overwrites.
- **All 11 petslike games were rebuilt and seeded** (each `<app>/db/` = 14 files, byte-identical to the shared source, verified by sha256). Behaviour is unchanged until a game's own db is edited, because the copy equals the source.
- **Evidence:** harness `book_db.pal` **14/0** (no own db, seed, second seed refuses and keeps a marker, own db wins, `PET_DB` still wins, removing the own db falls back); 5 mutations each fail it; the earlier core harnesses still pass (fridge 29, eat_page 17, page_follow 44); the core adds no new compiler warning (409 before, 408 after, same set).

## 3. What STILL reads the shared db (not done; these are the next steps)
1. **The db window itself (db-hq-pal).** I did not find where it resolves its data folder, and its launcher only receives the house path. It must be given the loaded book's `<app>/db` (a launch argument or a state file) before the `db ▾` tab edits a book's own rows. *Spike first: where does the 15-tab projector read from?*
2. **The window templates and the tab action:** every game's `db-hq` menu row launches `db-hq-pal/button.sh <house>` with no book; it should pass the book's db.
3. **Other readers of the shared path:** `_.monads/_.livedesk-taskbar/ops/actors_hq_manager.c` and `terms_hq_manager.c`, `&.widgits/entity-cli/ops/entity_cli_commit.sh` and `act_row.sh`, `@.apps/pet-trainer/ops/pet_event.sh`, `@.apps/rpg-pvp-hq/ops/rpg_pvp_hq.c`, the harness `playthrough_op.c`, the command registry, and a harness event page (`two-facts`). Each needs the same rule or a conscious "stays house-wide".
4. **Games outside the 11** (rpg-pvp-hq, game-dev-hq, bet-rpg ...) are not covered.

## 4. Open design questions (owner)
- **Copy or overrides?** Today a book's db is a full copy (simple, local edits). The alternative is a thin layer of overrides on top of the shared rows (smaller, shared fixes flow in, but every reader must merge). I chose the copy because it is the smallest thing that makes the db the book's own.
- **Where does a *desk* book keep its db?** Today the db lives with the game package (`<app>/db`). A desk book under `sessions/<book>/` has no db folder; if the editor opens a desk book for a game, it should use that game's `<app>/db`. Should a pure desk book (no game) get `sessions/<book>/db/`?
- **Seed policy for new games:** `db seed` is manual; should creating a game or a book seed it automatically?

## 5. Limits
Only the game core (party loading) uses the per-book db so far; no window was launched, so there is no picture of a game running on its own db; the db window, the taskbar managers and the entity tools are untouched.

## 6. UPDATE, later the same day: the copy became a LAYER over a shared TRUNK (owner: "share a common trunk of data till branched ... to save space")
**Why (RAN):** a hash scan of `@.apps` found that **54% of the bytes of the 11 petslike games (56 of 104 MB) are exact duplicates across games**, 41% (89 of 216 MB) over all of `@.apps`; the biggest are the pc-hq board folders (`parallax.rgba` alone: 23 copies of ~2.7 MB), the db is only 0.9 MB of it. `/` is ext4 at 94% and refuses `cp --reflink` (tested), so sharing has to be done by house code. Hard links were rejected (an in-place write would change every book at once).
**Model (built for the db):** a reader takes `<app>/db/<file>` when it exists, else the trunk `&.widgits/db-hq/data/<file>`; the layer holds ONLY files the book changed. `db edit <file>` is the branch point (copies one trunk file in, stamps `BASE | <file> | <hash of the trunk file then>` in `<app>/db/LAYER`); `db` reports `N file(s) overridden: ...; trunk moved (review): ...` (nothing merges by itself); `db trim` drops layer files byte-identical to the trunk; `db seed` makes the EMPTY layer (it copies nothing). `PET_DB` stays a plain folder and wins. The hash is FNV-1a 64 (change detection, not security).
**Evidence:** `book_db.pal` **30/0** (empty seed, branch one file, second edit keeps the book copy, per-file fallback, trunk-moved reported only after the trunk changes, trim keeps changed files, bad names refused, `PET_DB` wins); 6 mutations each fail it (layer ignored, branch overwrites, no BASE stamp, trim drops changed files, trunk-moved never reported, `PET_DB` ignored); fridge 29, eat_page 17, page_follow 44 still pass; no new compiler warning (408, same set as before). Found on the way: the fixture copied the game's seeded db into the scratch house, and a harness command with `&` in a path ran in the background (quote paths containing `&`).
**NOT done, and the reason:** the 11 games still hold the old **full copies** (14 files each, verified byte-identical to the trunk by sha256 today) plus a new `LAYER` file, so each says "14 file(s) overridden" although nothing differs. Converting them to empty layers needs a removal that the safety check blocked in a scripted loop, so it is left to the owner: for each game run its own tested verb, e.g. `@.apps/<game>/ops/+x/<game_with_underscores>.+x db trim` (drops only files identical to the trunk, 14 per game). Until then behaviour is unchanged and only the disk saving is not realised (1.4 MB for the db, trivial; the pc-hq folders are where the bytes are).
**Still open:** (1) **what writes the db ROWS?** `dbhq_action.sh` only maintains the window's tab/selection state (my earlier "only write path" reading was wrong), so the place where "copy on first write" belongs is unknown: spike. (2) the db window, the taskbar actors/terms managers, entity-cli, `pet_event.sh`, rpg-pvp-hq still read the trunk directly. (3) the same trunk + layer idea for the pc-hq board folders (the 54%): the lookup is pure, so it should become a text-include once a second consumer needs it. (4) desk books with no game have no layer folder yet.

## 7. Spike result (2026-10-28): how the db window and the db rows really work (READ, no window run)
- **The window is a VIEWER of a house-level mirror.** `db-hq-pal`'s projector reads `#.desktop/db_hq_<tab>.state.txt` (15 files, path built as `<house>/#.desktop/<file>`), not `db-hq/data`. Its only action script, `dbhq_action.sh`, only records the open tab, the selected record and "open common events" in `<pkg>/state/active.pdl`: **I found no in-window row editing.**
- **One-way mirrors:** the taskbar managers `actors_hq_manager.c` (canonical `data/actors.pdl` -> `#.desktop/db_hq_actors.state.txt`, a byte copy re-done when the source mtime changes; it also seeds `actors.pdl` when missing), `terms_hq_manager.c` (`System.json` -> `db_hq_terms.state.txt`) and `khtpm_hq_manager.c` (common events list). None of the three is running right now.
- **Who WRITES rows:** `&.widgits/entity-cli/ops/act_row.sh` and `entity_cli_commit.sh` (an entity command such as `attack` calls `#.desktop/harnesses/two-facts/apply_range.sh` with BOTH the state mirror and `data/actors.pdl`), plus hand edits. So there is **no single "write a db row" function**: the copy-on-first-write point has to be added to those writers.
- **Consequence for per-book:** the mirror files in `#.desktop` are house-wide, so a per-book db needs either (a) the mirror to follow ONE *open book* (the managers read a `db target` state file naming the book and publish its layered view into the same `#.desktop/db_hq_*.state.txt`; the window needs no change), or (b) one mirror folder per book and the window pointed at it. (a) is the smaller change and matches "the db window is the db of the open book".
- **Plan (not started):** (1) a `db target` state file written by the game's `db ▾` menu action and by Synch (the desk's open book); (2) the three managers publish `layer-over-trunk` for the target (a pure lookup, so the lp_* code becomes a text-include `_shared-lib/layer_path.c` now that there is a second consumer); (3) `act_row.sh` / `entity_cli_commit.sh` / `apply_range.sh` branch the file they write into the layer first (`db edit`) and write there; (4) harness per step. Touches the LyfeDesk taskbar monad (restart needed): do it on a staging copy first.
- **Question for the owner:** which book does the db window show when you click `db ▾`: the game window you clicked it in, or the desk's open book (they differ until Synch)?
