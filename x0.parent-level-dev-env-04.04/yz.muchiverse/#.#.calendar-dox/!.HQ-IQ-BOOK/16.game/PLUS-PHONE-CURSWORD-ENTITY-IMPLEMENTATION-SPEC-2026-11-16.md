## 1. Goal (SAID 2026-11-16)
Put the **cursword** entity on the phone the way LyfeDesk has it, **both surfaces**: (a) a **tile on the phone's home grid** (the phone's desktop surface) and (b) a **cell in the phone bottom bar** (names only; entities after the app cells). **Both open the same context menu: the same nine rows with the same actions, Close included** ("use the same as LyfeDesk"; the desktop respawns cursword). No video. Entities in general come later (a hotbar); build it from a LIST so the second entity is data, not code.

## 3. What an entity is on the desk (READ; details in the LyfeDesk reference)
A folder (a pal) under the user's `pals/` with `menu.chtpm` (the context menu), `meta.pdl`, `stats.pdl`, `glyph.txt`, a sprite. The desktop shows it as a sprite window and as a bottom-bar cell. **Its menu is `menu.chtpm`**: a `<window class="entity-menu"><page name="main">` of `<item label=... action=...>` rows and one `<cli_io>`. Seed copy for tests: `44.xyz.01.00/xyzfs/_seed/livedesk/pals/cursword/menu.chtpm`. **The user's real cursword folder is private (`xyzfs/users`): never open, copy, or commit it.** Cursword is always open and pinned at the top left (`livedesk_ensure_cursword`); the phone is another VIEW of it, never a second process or a copy.

## 4. Data: where the phone learns which entities exist (DOC)
- **One authority:** the taskbar manager's projection `#.desktop/strip_ui.txt` already lists the active desk's entities: `n_tabs`, `tab_N_label` (name), `tab_N_sprite` (the entity folder), `tab_N_action`. The phone READS it (never writes it). Cursword is `tab_0` on this desk (SEEN) but is outside the desk model, so do not assume index 0: find the tab whose label is `cursword`.
- **Which entities the phone shows:** a phone preference list `phone_prefs.pdl` row `ENTITY | cursword` (data, like `BOOK | ...`); default `cursword` only. Adding an entity later = adding a row.
- **Validation:** the entity name must be a word (`[A-Za-z0-9_-]`); its folder must resolve (`realpath`) to a directory named exactly that under `<HOUSE>/xyzfs/users/*/home/livedesk/pals/`; refuse anything else (no `..`, no symlink out). Never print the user id in logs or docs.

## 5. The three surfaces (DOC)
**5.1 Bottom-bar cell.** Extend `phone_footer` so the footer is: open/minimized APP cells first, then one ENTITY cell per `ENTITY` row: label `<name>` (no emoji window prefix; the sprite is the marker, like LyfeDesk's entity cells), `sprite` = the entity folder, class `phone-ft`, action `phone_op entity <inst> <name>` (see 5.3). Names only, no function buttons (owner).
**5.2 Grid tile.** The picker (`plus-phone.xhtpm` and landscape) shows apps as `class="swatch"` tiles from a `<repeat count="${n_apps}" bind="app">`. Add `${n_entities}` / `ent_N_label` / `ent_N_sprite` / `ent_N_act` variables published by `phone_projector.c` (the one ui.txt writer for the picker) and a second `<repeat>` of tiles after the apps, same shape, `sprite` = the entity folder, action = `phone_op entity <inst> <name>`.
**5.3 The tap and the menu.** `phone_op entity <inst> <name>` writes `screen.txt = @entity:<name>` (a reserved prefix; `is_word` must accept only after the `@entity:` check) and calls `refresh_layout`; the window shows an **entity screen** (a layout generated from the entity's `menu.chtpm`, same window, same stack: phone bars, an `APP_CHROME`-style row whose name is the entity name, `_` and `x`, then the nine rows as full-width buttons, then the phone footer). Why a screen and not a floating popup: it keeps one window (owner), it reuses the existing swap machinery, and the phone has no right-click. **Default for the tap: open the menu** (see Open question). The phone projector for an `@entity:` screen is `phone_projector` itself (no child); the rows are static text from `menu.chtpm`.
**5.4 Running a row.** `phone_op entity-run <inst> <name> <row>` reads the row `<row>` (1-based, the same numbers the desktop menu shows) from the entity's `menu.chtpm`, then runs its `action` exactly as LyfeDesk does: `sh -c <action> <entity folder> <house>` via **fork/exec with a watchdog** (the `run_out` pattern in `phone_op.c`), never `system()`, with `WIN_X`/`WIN_Y` set to the phone window origin. Special rows: `action="CLOSE"` writes `CLOSE` to the entity's `interact_relay.txt` (what the manager does) and returns the phone to home; `action="void"` (Cancel) returns to the picker (minimize semantics are not needed); the `<cli_io>` row (Cli-io:) is a text field: a phone `<cli_io>` that runs the row's `action` with the typed value as the last argument (`entity_cli_commit.sh`), shown only if the renderer's `<cli_io>` works in this window (check; otherwise leave the row visible but disabled and say so).
**Most rows open other desktop windows** (Dir, Inventory, Chat, Bookmarks, Play, Act): that is expected ("same actions"); native phone screens for Chat and Cli-io are a LATER step, one row at a time.
**5.5 No process, no copy, no state:** the phone writes only its own files (`screen.txt`, the layout, `ui.txt`); the entity's folder is read-only to the phone except the single relay word for Close. No game state anywhere (the ledger rule; everything shown is a projection).

## 7. Open question to settle first (DOC default in bold)
What does a TAP on the tile or cell do? LyfeDesk: a LEFT click on the cursword sprite ARMS it; right-click or the bottom-bar cell opens the menu. A phone has no right-click, so (a) **tap = open the menu** (the same as the bottom-bar cell), (b) tap = arm, long-press = menu, (c) the tile opens an entity screen of its own. Also: does the phone show the armed halo at all? (Ask the owner before building (b) or (c).)

## 11. As built (2026-11-16), and where it differs from sections 4 to 10
**Built and SEEN on a phone (real cursword, Cancel only):** the bottom bar has a `cursword` cell next to the app cells; the grid has a `cursword` tile (gold sword, generated `&.hq-apps/plus-phone/entity-icon/`); tapping either shows the entity screen IN THE SAME WINDOW (same pid): the phone's stack of three, then the eight rows of the real menu (Dir, Inventory, Chat, Bookmarks, Play, Act, Close, Cancel), then the bottom bar; Cancel returns to the picker; the desktop cursword sprite stayed at +0+0. Tap = open the menu (my default; arming and the halo are NOT on the phone).
**How:** `phone_op entity <inst> <name>` writes `screen.txt = @entity:<name>` and generates `<inst>/entity-screen.xhtpm` from the entity's `menu.chtpm` (projection, rewritten each open); `phone_op entity-run <inst> <name> <row>` runs row N: `void` = home, `CLOSE` = the one word CLOSE appended to the entity's `interact_relay.txt` (what a click on Close does on the desktop: the entity ends and the manager respawns it), `sh -c '<script>'` rows = `/bin/sh -c <script> <entity folder> <house>` by fork/exec (no outer shell string, `WIN_X/WIN_Y` set, detached, output discarded), any other form refused. Which entities: `ENTITY | <name>` rows of `phone_prefs.pdl` (default cursword), each accepted only when `#.desktop/strip_ui.txt` names its folder and `realpath` ends in `/pals/<name>` under `/xyzfs/users/` with a readable `menu.chtpm` (shared text-include `ops/phone_entity.inc`, used by `phone_op` and `phone_projector`).
**Differences from the spec:** rows are not drawn as a dropdown but as a full screen (same window rule); the entity screen has no `x`-closes-entity (both chrome buttons go home; Close is the menu row); the footer cell width went from 240 to 168 px in every phone stylesheet so two cells fit in 360 px; the footer cells carry NO emoji now (they drew as empty boxes); the bar holds at most 3 cells (app cell + entities, `ft-narrow` 108 px when there are 3; entities past the third stay on the grid; harness `phone_entity` 61).
**NEVER test Close or Dir/Chat/... on the owner's real cursword** (Close ends it, the others open real desktop windows): the case uses a scratch entity whose actions only touch marker files.
**Cli-io (added 2026-11-16, reuse of the house `<cli_io>` element, as in rpg-pet):** the screen shows `Cli-io:` under Cancel when the entity menu has a `<cli_io>` wired to `entity-cli/ops/entity_cli_commit.sh`; the renderer commits `<action> <instance> <house> <text>`, `phone_op entity-cli` checks the entity again and runs that ONE script with the entity folder, house and text as separate argv words (harness `phone_entity` 76). Seen as a row on the phone; typing into the real cursword was NOT done (it would append to its cli_commands.txt).
**Not built:** native Chat screen, the armed halo, more entities in the list UI.

## 12. Icons (2026-11-16)
The cursword grid tile shows the entity's OWN picture: `<entity folder>/sprite.csv` (the file the desktop draws it from), accepted only as a regular file (no link) of 1 byte to 4 MB, else the shipped gold sword `&.hq-apps/plus-phone/entity-icon/`. Apps use the **standard icons until a custom one is made** (owner's list): tsc = crossed swords, settings = gear, store = shop, any other app (stock+x too) = the bento box, which is also `&.hq-apps/plus-phone/default-icon/` (used when an app has no icon folder or no `sprite.csv`). Made with the house pipeline: `emoji_gen_atlas.+x <emoji> <png>` then `emoji_xtract.+x <png> 0 64 <csv>` (64 = resolution; 16 is too small). Harness `phone_entity` 82 covers own sprite, symlink refused, no-icon fallback. The footer cells carry no emoji (they draw as boxes in the text renderer); the tiles use the sprite files.
