## 1b. THE STANDARD ALREADY EXISTS, and the games are simply not on it (📖 READ, `18.pc-hq/PAGE-FILE.md`, 2026-09-30)
* **"Book and session are the same thing. Page and map are the same thing. A book holds many map pages. The livedesk page file is the older standard. pc-hq changes to match it."**
* **A page is one desk file** `sessions/<session>/desks/<page>.pdl`; `session.pdl` names the book (`STATE | name`) and the open page (`STATE | active_desk`). **A row is one entity:** `DESK | name | path | x_px | y_px | cell_x | cell_y | glyph | n`, where `path` is the entity's **pal folder**. `cursword`, `book-stack`, `door_civ`, the terumon and `robot_chat_001` are already rows of this shape. **Terrain stays the map grid of that page**; the page file is the *entity list*, not a terrain format.
* **pc-hq 2D and 3D read and write the same row** (a move in either window shows in the other); 3D "is that same page stood up" with no entity list of its own. **Proved in that doc (steps 1 to 6, with pixel counts):** `hero_01`, `tree_small`, `chicken`, **`xelector_01`** (cell, z, `possessed_id` in the glyph field) and **`camera_01`** (mode, yaw, pitch, pan, height packed in the glyph field) are rows in the open page file; the camera follows the xelector row; a taskbar Synch carries book and page between windows.
* **So the owner's "manifest AND tb format, both" is the existing design, not a new one.** What is missing is that **rpg-space, rpg-dust and rpg-edit are `source=board`** (📖 `open_book_page.txt` in both rpg-space's and rpg-dust's pc-hq folders): they keep **private state files** (`pieces/hero_01/state.txt`, `pieces/xelector_01/state.txt`, the board state's `camera_*` keys, the skin's `bar.txt`) which PAGE-FILE.md lists as exactly the things that must stop being authorities.
* ⚠️ Not verified: whether the proofs in PAGE-FILE.md still hold on today's engine (I did not re-run them), and whether the **camera-starts-in-the-floor** bug (owner, 2026-10-28) is the board-owned camera/selector state this standard retires. It is a lead, not a finding.

## 2. The model (📝 PROPOSED; one thin layer over what exists, no conversion of the maps)
* **Book = a game** (id `rpg-space`, `rpg-dust`, `rpg-edit`...). **Page = a map** inside it, addressed **`<book>:<page>`**: `rpg-space:quarters`, `rpg-space:region`, `rpg-space:space`, `rpg-dust:region`. A page has a **kind**: `interior` (reached by a door or a teleport: the ship rooms), `surface` (a planet page), `space` (blank space).
* **Entity = a placed thing with identity** (a **PAL**, section 7a), a position on a page (`at=`), and optionally **`pages=<page,page,...>`**: the pages it can teleport you to. The **ship is an entity** (`kind=ship`, `hull=pieces/ship_01`, `pages=bridge,quarters,hold,engine`) placed on a surface or space page. **The book owns every page**; the ship's menu is the way to reach its rooms (a door from a surface page into the ship is also a teleport to `rpg-space:bridge`). "The whole ship teleports into a planet map" = **the ship entity's `at=` changes page**, nothing is copied under the bridge. (The painted-backdrop copy then becomes a *view* of the page the ship stands on, not a second source of truth: ❓ see 7.3.)
* **Rows, not code** (house rule). **Where PAGE-FILE.md already says it (entity rows, book name, open page) the page file wins; this layer only adds what it does not carry** (page kinds, an entity's `pages=` list, labels), either as a small `book.pdl` or as extra `STATE` rows of `session.pdl` (S1 decides after the inventory). Shown as a `book.pdl` for readability:
```
BOOK   | rpg-space | RPG Space | maps=pieces/system/maps/rpg-space
PAGE   | bridge   | Bridge   | kind=interior
PAGE   | region   | Region   | kind=surface
PAGE   | space    | Space    | kind=space
ENTITY | ship_1   | Ship     | kind=ship | hull=pieces/ship_01 | pages=bridge,quarters,hold,engine | at=space:5,5
```
  It is **generated from / checked against** the existing `game.pdl` and the map folders, so nothing is hand-duplicated. `tree_lint` (BUILT, 53/0) already validates `NODE` rows with `parent=` / `needs=`: an entity's interior pages and a page's owner are exactly such edges, so the same linter can be reused.
* **The header shows BOOK:PAGE from data** (`rpg-space:quarters`) in every game that has a `book.pdl`: no per-game renderer code (the khtpm house rule). 📖 The 3D debug overlay already prints `rpg-space:quarters`, so the engine knows the pair; the header is the missing display.
* **rpg-edit opens a book**, not "is a game": list the book's pages, show a page, then edit (cells, events, hotspots, entities) through ops that write the map files with a ledger row. **Export** = package the book + the pinned engine binaries + a launcher (design 16.game games-as-packages), and prove it by running the same playthrough gate on the exported copy.

## 3. Why "unshippable" today, in checkable terms (📝 the compliance gate)
A game is **BOOK:PAGE compliant** when `book_check <game>` passes: (a) it has a `book.pdl`; (b) every `PAGE` has a map folder with the required files; (c) every `ENTITY` `at=` names an existing page and every page in its `pages=` exists; (d) page ids are unique and valid names (the `book_page_op` rule: letters, digits, `-`, `_`, 1..48); (e) no map folder exists that is not a page; (f) the header shows `book:page` (a state-file check, not a screenshot). Until that passes for rpg-space, rpg-dust and rpg-edit, nothing built on top is shippable.

## 14. S3 re-scoped before any code: binding is NOT just "read the game's own pin" (read 2026-10-28, nothing run)
Reading the call sites of `page_bound_pdl()` in `bv_render_3d.c` (lines 1265, 1817, 3258) shows that a bound pin (`source=desk`) switches the engine into its **desk-page mode**: the scene becomes ONE 16 x 16 floor layer (`z_count = 1`), the hero and the chunk world are not loaded, entities are drawn as flat page sprites (`place_desk_sprites`). That is the livedesk / piececraft page look. rpg-space, rpg-dust and rpg-edit-hq are **painted multi-level maps** (`cells.txt`, the maker path, the ship decks, the planets below); flipping them to desk-page mode would REPLACE their 3D scene with a flat page. It would also hit every game at once, because the engines read one house-wide pin (the piececraft one, which is `source=board` today). So S3 cannot be "point the engines at the game's pin".
**What the standard actually asks** (PAGE-FILE.md: "terrain stays the page's map grid"; entities are rows): the MAP stays the game's own map book, and the ENTITY positions (hero, xelector, camera, later ship and pets) come from page rows. That is a third mode, "entity rows over the game's own map", which the engines do not have. Two ways to get there, one recommended:
* **S3a (recommended, safe, small): the page FOLLOWS the game.** The game (or a slow tick) re-runs `game_page_export` so the page file is always a true projection of the game's current state; the game stays the authority, the live engines are untouched, `book_check` and rpg-edit can read a page that is current. It proves the format on live data and shows every disagreement. Costs one small op call per tick (idle cost near zero if it only writes on change).
* **S3b (later, the real pivot): the game FOLLOWS the page.** Add the third engine mode and make the trainer / hero / xelector files projections of the rows. Needs the engine change above and a per-game opt-in pin, and must not change how the other games render.
**Decision for the owner:** S3a first, S3b after, or S3b directly? (My recommendation: S3a now; S3b only once rpg-edit actually needs to WRITE positions.) The live rpg-space stays `source=board` either way until S3b, because binding it would not change what the engine reads and could change what `pchq_board_projector` reads from the game's own pin (not read yet).
