## 2. For an agent (how to build an app without reading the renderer)
1. Make the folder `<app>/` with `manifest.pdl` (copy `projects/true-swords-clash/manifest.pdl`), an `icon/` sprite folder, `screens/<name>.xhtpm` + `.css`.
2. A screen is ONE layout: `<window class="<app> database-window phone-portrait">` (the `database-window` class is what makes the css `width/height` size the window), a `<module>` that is your op, chrome buttons (`x` = `onclick="CLOSE"`, `<` = `phone_op home`), and `${var}` values from `<instance>/.hq_manager/ui.txt`. Buttons are `<item action="'<op>' '<verb>' '<arg>' '${ARG3}'">`; **`${PKG}` is the folder of the layout file** (`screens/`), so reach your op as `${PKG}/../ops/+x/<op>` and the phone as `${HOUSE}/&.hq-apps/plus-phone/ops/+x/phone_op.+x`.
3. Your op has three jobs: the verbs (write files, append ONE byte to `marker.txt`), the module mode (republish `ui.txt` when the marker grew or every 5 s, end when the parent is gone), and `--once <instance>` for the harness.
4. State rule (no ghost data): the match/game state is an append-only ledger; a replay recomputes every row and refuses an edited one; chance is a hash of seed + row number. Ratings and similar are PROJECTIONS derived from finished ledgers.
5. Check with `app_check <package> <house>`, install with `phone_op install`, open with `phone_op open <instance> <app>`, photograph with `dump_frame_png_op <winid> out.png` and OPEN the PNG.
6. Write the harness case first or with it (`harness/README.md`; no Python, no new logic `.sh`; run gated via `cpu_gate`).
Traps found (each cost real time): a class set from a variable does not restyle visibly (put the state in the label text); a list taller than the window opens scrolled (trim to about 16 rows of 30 px); a sprite tile's caption must be one line; the first relay click after a restart is often dropped (retry and stop on the effect).

## 3. For a human
Open the phone (top bar `+`), tap an app. In app-edit pick a project, `check`, `export to the phone`, `open a phone`. Settings > the two colors (below) change the look of everything.

## 4. Consumer and enterprise
**Consumer (DESIGN):** apps and data packs are downloaded from the company's GitHub repos (section 28 of the phone design doc), paid in cones (a ledger row, not a flag); p2p play (TSC rated PvP) with a host list from GitHub. **Enterprise (DESIGN, OPEN):** the same packages, installed from a private repo or a private index (`packs.pdl` is just a URL and a sha256 list), with the signing rule for installable code still an owner decision; per-organisation themes use the two Settings colors; an audit trail is already the ledger of each app. Nothing here is verified against a real company deployment.

## 7. A usage framework: people use this however they want (owner 2026-11-15)
**Owner:** save the harnesses in the LyfeDesk Tools "office", which is very flexible user space; then, clarified: "not just the office, in general, but it's more of a usage framework than a hard rule, and I just don't want them to think of it like that" (that is: don't think of these things as boxed-in features).
- **It is a way of seeing the system, not a rule to enforce.** Tools, tests, apps, packages, screens and ledgers are open building blocks that a person or an agent can use for whatever they need. The office (`pre-design` book, page `office`, `@.apps/pre-design/harness.pdl`) is the clearest example: a workbench, not a feature list. But the same attitude applies to the phone, app-edit, the Tools menu and everything else.
- **What that looks like in practice (a leaning, not a checklist):** prefer plain, visible, editable things (a row in a `.pdl`, a folder, a layout file) over a hidden private menu or a hard-wired fixed list; don't label something "phone only" or "for X only" when it is just a tool someone may want elsewhere; assume the user may rename, reorder, delete or repurpose it. When in doubt, ask what the person would want to do with it, and keep the door open.
- **Done 2026-11-15 as one example:** the +phone / True Swords Clash / app-edit / placement / layout-preview cases are listed as tests of the office book (`phone_check`, `app_package_check`, `app_edit_check`, `tsc_rules_check`, `window_place_check`, `layout_preview_check`); the Tools menu shows each with its last verdict (47, 22, 14, 61, 15, 7 ok) and the book's own `office_tools` case (12 ok) checks the rows are valid.

## 8. Learnings and pitfalls for the next agent (2026-11-16; each one cost a run)
Read first: `PLUS-PHONE-LAYOUT-SPEC-2026-11-16.md` (the owner's layering, in his words), then this list. Harness cases that guard it: `phone_layers` 33, `plus_phone` 47, `app_package` 22, `tsc_rules` 61, `tsc_p2p` 32, `phone_hostlist` 23 (`harness/README.md`).

**The owner's rule behind most of it: use the STANDARD, do not "vibe" a new behaviour.** I invented a `nav-zero` special case in the SHARED renderer where a click on the bar's `+` fired at once and did not move nav; every other button is "first click moves nav focus, second click or Enter fires". The owner caught it on first use. Before adding a behaviour to a shared window or bar, find how the sibling already works (typed `0` already did the standard thing; only my click and `+` key paths deviated) and make the new thing the same. Fixed 2026-11-16 (`khtpm_core_render.c`, `click_focus_then_activate`).

**How the phone is built (what to know before touching it)**
1. **One window per phone, always.** `phone_op open|home|minimize|closeapp` must never relaunch the renderer; only `flip` (the window size changes), `relaunch` and `quit` may. `phone_op` writes the window's OWN layout file `<inst>/plus-phone[-landscape].xhtpm` (+ the css beside it) and the renderer re-parses it (the full-rebuild path; `incremental_reparse=0` in `hq_ui.pdl`). The test is a launch COUNT (`phone_layers`), not a feeling.
2. **A window's `<module>` (projector) starts ONCE, at window launch.** An app screen declares its own module (TSC: `tsc_op`). Swapping layouts in place therefore leaves the OLD projector running, and the new screen gets none of its `${vars}` (symptom: after `home` the picker was an empty grey box titled "main", "phone : tsc" in the tab). Fix in place: the phone window's module is ALWAYS `phone_projector`; `phone_op` rewrites the module line of an app layout to it, and `phone_projector` reads the open app's `<module src>` from the app's screen file and runs it as its CHILD while the app is open (silent meanwhile: one writer of `ui.txt` at a time), stops it on home. Child ends with its parent (`getppid()==1`).
3. **A projector that skips writing "when nothing changed" must forget its cache when another writer took the file.** `phone_projector` compares the new ui text with `last_ui`; after the app's projector overwrote `ui.txt` it believed its picker text was still on disk and wrote nothing. Clear the cache when the child stops.
4. **Tokens, one definition.** The phone's top bar block lives ONCE in `plus-phone.xhtpm` between `PHONE-BARS-BEGIN` and `PHONE-BARS-END`; an app screen carries the token `${PHONE_BARS}` and `phone_op` injects the block (dropping the `show="${app_open}"` guards: an app is open by definition). The bottom bar is the token `${PHONE_FOOTER}` built by `phone_op` (names only; see 5). An app screen that draws its own tab bar or footer is the old shape; the TSC landscape screen still has its own bars block (not migrated).
5. **The bottom bar is a window list, not a toolbar.** Compared with the LyfeDesk bottom bar (`khtpm_strip_bottom.xhtpm`, `strip_ui.txt`): one row of `dock-cell` items, entity cells first then HQ-window cells (`hw_N_label` = the window emoji + its NAME, `hw_N_minclass` = ` hqwin-minimized` when minimized, `hw_N_onclick` = `FOCUSWIN:<winid>:<pid>`), minimized cells dimmed with a dashed border (`.hqwin-minimized` in `entity_menu_default.css`). The phone copies that: a cell per open app, label `🪟 <manifest TITLE>`, click = `phone_op open` (restore). No rotate or leave cells (rotate is in the HQ menu, home is the "app picker" row). Owner: only names of apps and entities; entities (a hotbar) come later.
6. **Minimize is a UI preference, not app state.** `minimized.txt` names the app whose cell is dimmed; the app's ledger is never touched. TODAY a minimized app is NOT running in the background (its projector stops with the view). `closeapp` clears the cell.
7. **The SOURCE of an app screen is the app-edit project** (`&.hq-apps/app-edit/projects/<id>/screens/`), tracked in git; `&.hq-apps/plus-phone/apps/<id>/` is the installed COPY (mostly untracked). Edit the project, copy to the installed copy (or re-install); I edited both and checked they were identical before the edit.
8. **`phone_op close` DELETES the instance; `phone_op quit` closes only the window** and keeps the data. Use `quit` to tidy up a phone you opened while testing.
9. **A phone that was open with an app reopens WITH that app** (`+` reopens the lowest stopped phone with its match); do not assume a freshly opened phone shows the picker when you start a test; read `<inst>/.hq_manager/screen.txt`.

10. **`${PKG}` in an app screen = the screen file's own folder (`apps/<id>/screens`), NOT the package root.** Screens say `'${PKG}/../ops/+x/<op>'`. When I moved to in-window layouts I filled `${PKG}` with the package root and every TSC button pointed at `apps/true-swords-clash/../ops/...` (does not exist): dead buttons, found two hours later by the owner's request to install apps, not by a test. Guard: `phone_layers` asserts the path text and that the op exists. **Rule: after any change to how a screen is written, TAP a real button in a live phone and watch the ledger row appear (the engine cases and layout-text checks do not exercise the button path).** Fixed 2026-11-16, commit message has the evidence (ledger 1 to 3 rows).
11. **A reinstalled app keeps its OLD projector child until it is closed and reopened** (home, then open): after `phone_op install` the screen does not change (found 2026-11-16: the page label stayed blank until I reopened).
12. **A harness case must not copy the LIVE `apps` folder and then count apps** (`plus_phone` asserted exactly 2 and broke when the App Store and stock+x were installed): copy fixtures, or remove the extras in the scratch copy.
13. **A compile step inside a case that prints a lot of warnings can fail the case** (`stockx_ledger` setup exit=2 after the code grew format-truncation warnings): compile with `-w` in the case.
14. **Apps that need big data declare it as a dependency** (`DEP | <id> | <min version>`, installed to `deps/<id>/`, read from `apps/<id>/../../deps/<id>/`), not as a copy inside the package. See the App Store design doc sections 8 and 9.
15. **Harness `SLEEP | n` is MILLISECONDS** (`SLEEP | 2` was 2 ms): the `phone_layers` no-relaunch checks waited 2 ms and proved little until 2026-11-16 (now 2500). For a detached child's side effect use `WAIT_HAS | file | text | max_ms`, never a short sleep then EXPECT.
16. **A sabotage test must verify the sabotaged BUILD exists before running the case** (a silent gate refusal left the old binary and both sabotages "passed"): `rm` the binary, build, test it exists, then run. A negative that cannot fail is not a test.
17. **`WRITE` in a case keeps `$0`, `$1` and `${HOUSE}` literal and substitutes only `$T`** (good for writing `sh -c` menu fixtures). An unquoted `$` in a shell test line is expanded by YOUR shell first (my `grep` for `${n_pos}` came back empty).
18. **A negative needs a POSITIVE CONTROL that the thing you hide is really there** (2026-11-16, texting_core): a `RUN | /bin/sh | -c | printf ... >> "\$0"` append silently wrote nothing, so "a word only in another user's inbox is not found" passed for the wrong reason (the word was never there). Add `EXPECT_HAS` on the file first, and prefer `WRITE` (it works) over a `sh -c` append. Same trap in `trunk_op`: a sabotage that passes means a test gap, add a case where the sabotaged behaviour would change the result.
19. **Bars in text: `\p`** works in `EXPECT_*` text and in `WRITE` content; a raw `|` splits the row ("row has extra fields"). `EXPECT_OUT_LACKS` is the negative for output; `EXPECT_LACKS` is for files.
20. **A module that ends with its window must remember its PARENT pid** (2026-11-16, Texting): the copied loop `if (getppid() == 1) return 0;` never fires on this desktop, because an orphan is adopted by the user's systemd (`ppid` 1120), so every relaunch left a module running (two stale ones fought the new one over `ui.txt`; an old `tsc_op` orphan is still there). Use `pid_t pp = getppid();` at start and `if (getppid() != pp || pp <= 1) return 0;`; test it (harness `texting_app`: alive while the parent lives, gone after, with the old rule sabotaged). STILL BROKEN in: store_op, stockx_op, tsc_op, phone_projector, plugz_projector, app_edit_op (not changed: they ship in the public repo or are shared; ask first).
21. **A list opens at the BOTTOM by default** (chat convention); put `class="from-top"` on the `<scrolllist>` to start at the top. Until 2026-11-16 the renderer honoured that class only for a `<panel>` child; a `<page>` child works now (2 lines in khtpm_core_render.c). A `cli_io` placed after a long list scrolls out of sight: put it first.
**Testing and measuring (these produced wrong conclusions in one session)**
- **Identify a phone window by its instance, never by order or position.** X window ids are in CREATION order, not instance order, and phones are placed beside each other. I photographed phone 1 while editing phone 2's files and concluded "the renderer ignores layout changes" for an hour (recorded in design section 33, corrected). Match `window.pid` (`ps -o lstart`) with the window; `xdotool search --pid` does not work on these windows. Check that the dump is of the window you changed.
- **An empty verdict file is not a pass.** After a temp cleanup `/tmp/prisc` was gone and `tail -1 results/x.txt.verdict.txt` printed nothing; use the house copy (`&.widgits/board-viewer/system/prisc+x`) and test that the file EXISTS before reading it.
- **A negative test that cannot fail is worse than none.** The "no relaunch" check counted launches immediately; the relaunch is a detached worker, so the count was 1 even with `open` sabotaged to relaunch. Wait (2 s), then re-run the sabotage and see the check FAIL (calling the relaunch function directly from `open` fails three checks). Unexplained: a `spawn_self("relaunch")` from `open` did not produce a launch in the scratch house although `flip` does; the sabotage that works is the direct call.
- **A harness case must not touch the network.** One draft line of `stockx_fetch` had no `--file` and made a real request; run each case and read what it actually did. The check "no rotate cell" must test the cell's id (`ft-rot`), not the word (it also appears in the HQ menu row and in comments).
- **Check the build's output.** `build_phone.sh` printed warnings; I once sent its output to `/dev/null` and could not tell whether a sabotaged build had even compiled. Count the `OK` line.
- **Compile and relaunch rules still apply:** `cpu_gate` for every build (`LIVEDESK_NO_SPLASH=1` for the renderer), plain `button.sh reset` (never inside `cpu_gate`), and ask before relaunching the owner's windows. `/tmp/cc` scratch can vanish between days: keep scratch under the session scratchpad.
- **Photograph and LOOK.** Every claim above was checked with `dump_frame_png_op <winid> out.png` and by opening the PNG; byte-identical pictures (`cmp`) are the cheap proof that `home` restores the picker.
