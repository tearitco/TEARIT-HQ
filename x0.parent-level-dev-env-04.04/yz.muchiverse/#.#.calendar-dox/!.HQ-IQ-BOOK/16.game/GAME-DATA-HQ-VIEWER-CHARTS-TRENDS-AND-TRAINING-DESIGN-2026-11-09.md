# Game Data HQ: see the games that were played (tables, charts, history, trends, training data)

Owner request, 2026-11-09 (verbatim idea): "some kind of house tool x11-hq to view 1 or more games' data as a .csv or something, like xl, auto show charts of relevant information, including the history of these games, so we can see trends, train, etc. ... under Toys in the top tb of LyfeDesk for now ... auto-load the loadable sessions in the sidebar like chat-hai does its chats." Owner called it very important.
Status: **DESIGN ONLY, nothing built.** Labels: **FACT** = read in the code or data on 2026-11-09, **PROPOSAL** = my design, **OPEN** = owner decision or unverified.

## 2. The shape (PROPOSAL, the design-choice test answered)

1. **One authority per fact?** Yes: the ledger. Every CSV is a projection written by a named verb, safe to delete, regenerated byte for byte (NO-GHOST-DATA standard). The viewer never edits a game.
2. **Modular?** Three small pieces with files between them: (a) `export` verb of the game engine (data), (b) `chart_op` C op (pictures), (c) `game-data-hq` window (view). A game opts in by one row in its `game.pdl`, `GAME | export | <program> <args>`, the same data-row convention as `driver`, `chat` and `clock`; the viewer contains no game name.
3. **Scalable (the 10th consumer)?** Yes: Teropoly first, then the petslike games, Eden, anything with a ledger, each ships its own exporter and `schema.pdl`; the viewer reads the schema, not the game.
4. **Long term?** It feeds the roadmap items that need data: pet personalities (M10), balance tuning of prices and rules, the AI/learning layer, the franchise's rated-play features.
5. **House shapes?** Text files, `.pdl` for specs, C ops, marker files for "a new game was archived" (file size growth, not mtime), capped runtime files, a harness case that can fail for each piece.
6. **Cost and risk of the better one?** Highest cost is the chart rasteriser (about 400 lines of C) and the window; the exporter is small because the engine already replays. Low risk: read only.
Decision-log row: D58.

## 3. Data layer: tables (PROPOSAL)

`deskopoly export <game dir> <out dir>` (read-only verb, deterministic, header row, UTF-8, comma, no quoting needed because values contain no commas; capped) writes, per game:

| File | One row per | Columns (first draft) |
|---|---|---|
| `game.csv` | game | game_id, ruleset, seed, rules_hash, ledger_hash, n_players, drivers, rounds, rows, winner, over_reason |
| `rounds.csv` | player x round | game_id, round, player, name, driver, cash, net_worth, props, houses, hotels, mortgaged, position, in_jail, bankrupt |
| `events.csv` | ledger row | game_id, seq, round, actor, verb, args, result, cash_delta (derived), tile |
| `tiles.csv` | tile | game_id, tile, label, kind, price, owner_final, bought_round, bought_price, rent_collected, landings |
| `trades.csv` | offer | game_id, id, round, from, to, give, get, outcome (accept/reject/expire/cancel), rounds_open |
| `auctions.csv` | auction | game_id, tile, opened_round, bids, winner, price, price_vs_list |
`all_games.csv` = the union with `game_id` first (long format: what charts and trend queries want). `schema.pdl` describes every column: `COL | table | name | role time|category|measure|id | unit | chart hint`. Sessions the exporter can load: the live game, `archive/*`, any folder with a `ledger.txt`, and imported plain CSVs that have a schema row or a header the viewer can guess.

## 4. Chart layer (PROPOSAL)

- `chart_op <spec.pdl> <tables dir> <out.rgba|png>`: a C op that rasterises line, bar, stacked bar, histogram, scatter and box-less summary tiles with a small embedded bitmap font (the board-label font is the same kind of thing). Axis ticks, legend, one colour per group from a fixed accessible palette (the `dataviz` skill's rules: validated palette, labels, no colour-only encoding).
- `CHART | id | title | type | table | x | y | group | filter | agg` rows in `charts.pdl`. **Auto charts** (Excel's "recommended charts"): when no spec row exists the viewer picks by column roles: time x measure = line per group; category x measure = bar; one measure = histogram; two measures = scatter. Default set for Teropoly: cash by round per player, net worth by round, properties owned by round, rent collected per tile, auction price vs list, offers by outcome, game length.
- Drawn only when the selection changes (on demand); never per tick.

## 5. The window `game-data-hq` (PROPOSAL; shown to the user as "Game Data")

```
+------------------------------------------------------------------------------+
| Game Data                      [metric: net worth v] [chart: line v] [export]|
+-----------------+------------------------------------------------------------+
| SESSIONS        |  net worth by round (3 games overlaid)                     |
| [x] live  r8    |   $                                                         |
| [x] game-...607 |  3000|        ____---- B                                    |
| [ ] game-...414 |  2000|   ___--         ---- A                              |
| [ ] seed6 (har) |  1000|--/        ____---- C                                |
| [ ] + import csv|      +------------------------------------------>  round   |
| -- trends --    |  [chart] [table] [summary]                                 |
| win rate by seat|  game | rounds | winner | trades | auctions ...             |
| length of games |                                                            |
+-----------------+------------------------------------------------------------+
```
- **Sidebar = sessions**, auto-loaded by scanning (like chat-hai's history): live game on top, then `archive/*`, then harness/pinned games and imported files; each row has a check box (select 1 or more: multi-select overlays or compares); a "trends" group of cross-game charts. A new archived game is noticed through a marker file size (no polling of file times, no timer loop).
- **Tabs:** chart, table (paged rows, sortable by column header, the xl feel), summary (one line per game). The table tab is the CSV; "open in sql-hq" hands the table folder to `sql-hq` for free-form SQL.
- **Ships as** `&.hq-apps/game-data-hq/` with `toy.pdl` (appears under Toys), a manager that scans sessions and publishes `game_data_ui.txt`, an `.xhtpm`, a README; shape of `eden-viewer-hq`; shared renderer only, zero per-project C in it.
- **CPU:** idle near zero (no timers; redraw only on selection or when the marker grows); chart and export runs niced behind `cpu_gate`; row caps and output size caps recorded in `RUNTIME-FILE-GROWTH-STANDARD.md`.

## 6. History and trends (PROPOSAL)

A finished game appends one row to `games_index.csv` (an archive projection built from `game.csv`; regenerable). Cross-game charts: win rate by seat and by driver (human vs pet, personality), game length distribution, cash at round N, first tiles bought and their win correlation, rent collected by colour group, trades and auctions per game, how often each card kind fires. This is the balance and tuning instrument: it answers "is the first seat too strong?" with data, not feeling.

## 7. Training data (PROPOSAL, later phase, OPEN questions)

`export --train` writes one row per DECISION (state features at that moment by replay, action taken, outcome: game won, net worth change after N rounds) as CSV or JSONL for pet policies (M10). Rules: replay-derived only; pet-vs-pet harness games by default; games with a human seat are the owner's play data and are included only on an explicit flag; training runs happen on debil or the Mac, never this machine (offload rule); the viewer shows the dataset size and class balance, nothing more.

## 8. Phases and acceptance (what a human must SEE, and the check that proves it)

| Phase | Deliverable | Proof |
|---|---|---|
| P0 | `deskopoly export` verb, `schema.pdl`, `game.csv`, `rounds.csv`, `events.csv` | harness case: replay reproduces the tables byte for byte; a hand-edited CSV does not change the game; row counts equal ledger rows; a cash column ties to `status`; deleted tables regenerate identically; negative controls |
| P1 | `chart_op` + auto-chart picker + the Teropoly chart set | harness case: pixel probes (series colour at the expected point, axis ticks, a legend swatch), same CSV = same PNG bytes, empty table = an "no data" tile, OPEN the PNGs |
| P2 | `game-data-hq` window, sessions sidebar, one game, chart + table tabs, Toys entry | live PNG of the window with the sidebar listing the real archived games; `see` steps on the sidebar rows; a second game archived = a new row without a relaunch |
| P3 | multi-select overlay, trends group, `games_index.csv`, open-in-sql-hq | PNG of 3 games overlaid; a trend chart over at least 10 harness games |
| P4 | `export --train` and dataset summary | case: features at a decision equal the replayed state; no human rows unless flagged |
| P5 | second game provider (petslike or Eden) through `GAME | export` | the viewer lists it with no viewer code change |
Every phase ends with the compendium entry (what to look for), a decision-log OBS, and a commit; the owner's priority (human IO evidence): each item ends with a PNG and a click path.
