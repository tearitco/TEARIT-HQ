## 13. Make's `play` BUILT AND SEEN LIVE 2026-11-22 (decision D104; harness `teario_makeplay`, 63 checks)

- **What it is.** The Make window's popup has a `play` button (shown when the document has rows). It runs the verb `play <play_app> <play_state>` of `game_core` (the CLI has the same verb, the harness uses it). The verb: (1) refuses with the same rules as export and publish when the document is not a valid level (nothing written, no row); (2) archives the previous Play run (`archive/`, last 3 kept), writes the level text into the Play run folder as `level.pdl`; (3) opens the run with Play's own verbs (`new 7`, `join Maker human`, `start`); (4) appends `EVENT|n|author|play|-|<rows>|level=<hash>;rules=<Play rules hash>` to Make's ledger. If any step fails the run folder is removed and no row is written.
- **How Play gets the level.** `@.apps/teario-play/game.pdl` has `GAME | level_in_run | 1`: when `<run folder>/level.pdl` exists it is read INSTEAD of the `LEVEL | file` of board.pdl (meadow.pdl is never touched), and its text is part of the rules hash like any level, so a run of another level is refused (exit 1 "the rules say ..."). The copy is declared a CONFIG in Play's `state.pdl`. It is not a second authority: Make's `play` row holds its hash, Play's first ledger row holds the rules hash that covers its text, and Make's `clear` and `publish` re-derive the level hash from the document, so a forged copy proves nothing (harness: tampered copy refused, deleted copy refused, an old run on the new copy refused with a positive control for each).
- **Window handover.** `@.apps/teario-make/game.pdl` has `GAME | play_app | ../teario-play` and `GAME | play_handoff | 1`: after the row is written the driver runs `sh <play app>/button.sh run` and then ends the Make window (SIGTERM to the pid in `teario-make-pchq/pieces/system/board_window.pid`); the Make driver and its engine stack end with the window. One Teario window at a time is kept. A Play window that is already open is NOT retargeted (its driver read its config at start): close it first.

## 15. A broken brick stayed drawn in 2D (found live, fixed 2026-11-22, D107)

- **Cause (read in code, confirmed by a scratch run).** The 2D renderer (`bv_render_2d.c`, "Phase 2") blits the desk's `map.png`; the 3D engine reads `cells.txt`. The brick-break branch of the driver loop (`S.bricks != nb_seen`) ran the `scene` verb (cells.txt + marker) and `engine_reload()` but never rewrote `map.png`, which only `page_make` wrote (preview -> raw -> png). So 3D showed the break and 2D kept the old PNG until the game ended. Not a renderer cache and not a missed key `6`.
- **Fix.** `desk_picture()` in `game_core.c` (preview + raw_to_png, extracted from `page_make`) is now called by both. Cost: one preview + PNG encode per brick break (a level-sized image); idle cost zero, no polling, no per-frame work.
- **Harness.** `cases/teario_brickpic.pdl` (12 checks): the REAL driver (built from source) in a scratch house, human jumps under the brick, ledger brick row appears, `map.png` must differ from the copy taken before; the same source built with `-DGC_MUT_NO_PICTURE` (the old behaviour) leaves it byte for byte equal, so the check fails on the bug. It checks the PNG the 2D renderer blits, not a bv_render_2d frame.
- **Scratch-house trap.** The driver needs `raw_to_png.+x` under `<house>/&.widgits/_shared-lib/ops/+x/` and the atlas in the kept `teario-play-pchq/.../board/cells.rgba`; without them `cells.txt` appears but `map.png` silently does not.
- **Stale session (separate, NOT fixed).** `engine_reload()` / `engine_nudge()` read `bv_session=` from `board/state/ui.txt`; if that names a deleted session they silently do nothing (3D reload too). Decision left open.

## 16. TELEPORT block BUILT and SEEN LIVE 2026-11-22 (decision D111; harness `rule_teleport` 40, `teario_teleport` 63; commit 4530e5a83)
