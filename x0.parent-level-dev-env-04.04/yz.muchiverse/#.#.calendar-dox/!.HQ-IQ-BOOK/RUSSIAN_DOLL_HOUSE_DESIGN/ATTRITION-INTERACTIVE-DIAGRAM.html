📚 Concept Bank — the data layer A TEARIT reads/writes

Hub-and-spoke weighted concept nodes (&.widgits/concept-bank/data/masters/ + spokes/). Every other consumer (tomom's curriculum, FSM transitions, GOAP preconditions) is meant to read from this same bank — one shared vocabulary, not per-feature silos.

🟢 REAL, NARROW

🐾 tomom — the local learner, currently dormant

#.Z.HUMAN_LLM/3.stage.llm.tomom — a real, hand-built LLM/weight system. Eventually meant to attend to curriculum and the growing Concept Bank so routine work can be proposed by a local model instead of a paid agent.

Blocked on the same thing A TEARIT is blocked on: no live promotion loop exists yet for it to learn from. Until that loop is boring and proven, paid agents (Claude, Grok) and humans remain the employees.

🔀 FSM + GOAP — the decision layer

The model never writes a transition table directly. It only describes a desired transition or action; the real, deterministic events-hq compiler turns that description into an actual event page.

fsm_transition_describe and goap_action_describe are named future Concept Bank record types — neither is implemented yet.

Honest competency ceiling: mechanical tool-call reliability is HIGH (verified, 3 models). Reasoning competence is real but lightly tested — exactly one quiz, 2/2 on one model, one question. "Do not generalize it to 'the model is good at code review' yet." Every task should stay small, single-file, and verifiable.

Role in the attrition-model: produce demonstrations (tool traces, hand-tuned bank edits, event-command placements) that IRL can later learn from. Explicitly not the runtime. Nothing currently reads those demonstrations back into a training signal.

🏛️ Agent Hierarchy — boss / managers / workers / students

👤 BOSS (the owner) — approves every message in co-lab-hai, every write/cmd_exec ↓ 🧑‍💼 HIGH-AGENTS / MANAGERS (Claude, Grok) — own branches, decide architecture ↓ 🛠️ WORKERS (OpenRouter, via open-hai) — single-file, one-hop, verifiable tasks only ↓ 🎓 STUDENTS (Kilo, Hai, opencode) — promotable to worker/manager, mechanism NOT built yet

What's real: Co-lab-hai is already the boss + high-agent layer (approval-gated, per-agent feeds). Open-hai's delegation channel is already the high-agent → worker layer, same philosophy. Per-tool branches + worktrees are close to "each agent owns a scoped workspace."

What's missing: no permissions layer distinguishes "manager" from "student" — every named agent is currently a peer with equal privileges. Also missing: Claude/Grok have no persistent "embodied" self-storage — no pal holds their own chat-history compactions.

🆕 Three ideas this thread introduced, not yet fully built

"Real" vs "Magic" entity/event — ⚠️ corrected 2026-09-29

The house's existing binary is "real" (backed by actual state/process) vs "stub/placeholder" — not "physically embodied" vs "magic". New and useful, but corrected: a real entity has a full, complex body (walks, collides, occupies desk space); a magic entity/event has real state and behavior but a simpler body — not no body. Every entity still gets a body; this was only ever about how complex it needs to be. The teru-test babysitter's body is a 👻 ghost glyph plus its own custom, user-editable GUI. See AGENT_ROADMAP_ANSWERS.md §10.

BOOK:SYSTEM (proposed)

BOOK:PAGE is real and shipped, but every BOOK today is tied to a user login. There's no house-wide, unowned book. Proposed: BOOK:SYSTEM — would hold open-hai session pals and Claude/Grok's own self-storage pals under one system-owned book.

HQ-LAYOUT-STUDIO (new, proposed 2026-09-29)

A toy for visually creating and editing layouts for custom widgets — the babysitter's dashboard is the first use case, not the only one. Lives as a sub-entity inside the ☁️ (cloud) entity from the DSR-test concerns. A layout can read an existing event page, or have an event drag-and-dropped into it as usual — same convention every other event placement already uses. Needs its own design doc, not started.

Why isn't promotion automated yet, if the validator already works?

Only 1 of 4 EDIT record types (spoke_weight_delta) is implemented. Building auto-promotion on top of a quarter-finished validator, with no real volume of pending_review.txt entries to measure a failure rate from, means designing the promotion criteria from guesses instead of data. The recommended order is: finish the record types → let real review volume accumulate → THEN design promotion from what actually shows up.

Is OpenRouter capable of building DSR's economy, civ-test survival, or the teru-test babysitter?

Not the architecture — those need a human/Claude/Grok to decide the shape first. OpenRouter is a good fit for narrow, already-scoped pieces inside an architecture someone else fixed — e.g. implementing pc_place_voxel.c as the mirror image of the already-working voxel-removal path in piececraft-hq, which is the single best-scoped delegation candidate raised in this whole roadmap.

What's the actual relationship between DSR-test and WSR_PAL-PREFERED?

DSR is a NEW, dystopia-abstraction game with its own front door (castles/banks/stores/hotel). WSR_PAL-PREFERED is a from-scratch rebuild of the OLDER wsr-pal economic sim (bonds/loans/stocks/dividends). They are not the same project — but DSR's economic mechanics are the same math WSR_PAL-PREFERED already built and verified (Phase 1's shareholder registry, cent-exact dividend payouts). When DSR resumes, its manager should call into or port from WSR_PAL-PREFERED's ops rather than re-deriving the math.
