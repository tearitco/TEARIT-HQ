## 8.3 The load-bearing caveat

For every **Actor / Party / Character / Screen** command, "DONE" means:
the command compiles to real PAL, runs, and writes a correct
`key=value` line to a flat state file. It does **NOT** mean anything
visually happens — **nothing reads those `mr_*` state files back and
reflects it yet.** (Render layers exist — the khtpm tile mode,
board-viewer — they just don't consume this state; see §8.5.) This is
consistent across everything shipped
(`mr_character.c`'s own header says the same); it's a known boundary,
not a regression. Message commands (show_text/show_choices) DO produce
visible output.

## 8.5 How it all interfaces / depends

- **event → event:** `call_common_event` (nesting proven).
- **event → db row:** Actor/Party commands name items/skills/classes/
  states/animations from the matching `*.pdl`. Loose coupling (by
  string), no enforced FK.
- **event → runtime state:** flat files by the package —
  `switches.txt`, `variables.txt`, `master_ledger.txt`,
  `inventory.txt`, `messages.txt`, `choice_result.txt`; planned
  `system_flags.txt` for the Tier-1 access commands.
- **trigger → switch:** the common-events manager watches a named
  switch in `switches.txt` (edge-triggered Autorun / cooldown
  Parallel).
- **event → position (planned wiring, not missing):** the desk grid
  (`desks/*.pdl` + `desk_grid.pdl`) and board-viewer are live; no event
  command calls into them yet. See §8.2 Tier 4a + the status-board
  HTML's plan.
- **Genuinely missing:** a consumer that *reflects* the `mr_*` state
  files (Character/Screen commands write state nothing draws yet — do
  it once, after Tier 2/4 have state to show); a battle system
  (Enemies/Troops/States/Animations tabs, Battle Processing);
  Shop Processing.
