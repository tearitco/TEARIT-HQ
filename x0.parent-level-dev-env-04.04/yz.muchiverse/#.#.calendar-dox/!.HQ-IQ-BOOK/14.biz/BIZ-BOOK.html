THE HOUSE / HQ — elevator pitch (DRAFT — founder to refine)

Kept at the top of 14.biz/ on purpose: grab-and-go copy for a quick pitch without digging. Longer, audience-specific versions live in OUTLETS/<NAME>/.

One line

THE HOUSE is a plain-text, file-driven desktop + app platform you can read, script, and build games on — where every window, menu, and piece of state is a file, and an AI agent is a first-class user.

~15 seconds

THE HOUSE (a.k.a. HQ) is a self-contained desktop environment where the whole UI — windows, taskbar, menus, palettes — is rendered from declarative text files by one shared engine, and every bit of app state is a flat file you (or an AI, or another program) can read and write. That makes it scriptable end to end, easy to automate, and a natural base for tools and games.

~30 seconds

Most software hides its state inside a binary. THE HOUSE turns it inside out: menus and layouts are declarative markup + CSS, app logic runs as small separate "manager" processes that just publish and poll text files, and one generic renderer draws all of it. The payoff — every workflow is inspectable and automatable, an AI harness can drive any window through the same input path a human uses, and new apps or games are assembled from a shared vocabulary instead of built from scratch. On top of that platform we ship tools (RPG-Maker-style tile and crafting tooling, editors) and games (a gamified Bible RPG, plus original lore-driven titles).

The umbrella

"HOUSE" / "HQ" = the whole stack: the platform + the tooling + the games + the lore. When the audience is specific — RPG Maker devs, AI / harness users, Bible-game players, etc. — lead with the matching OUTLET instead (see OUTLETS/).

What it is NOT (keep pitches honest)

  • Not shipping at scale yet — pre-traction; outlets are small (see each

OUTLETS/<NAME>/00-INDEX.md for real follower counts).

  • Not a cloud service — it's a local-first environment.
  • Cross-platform (Windows / macOS) is designed-for, Linux-first today

(07-install-and-ship/windows-mac/).

1\. Executive Summary

Modern law firms and biotech organizations frequently handle high-stakes digital assets—including patent filings, litigation discovery documents, clinical trial results, and proprietary research outputs. 4\. Technical Architecture & Workflow

The system operates entirely around your existing documents, using lightweight automated scripts to generate cryptographic proofs.

Step 1: Local File Ingestion & Hashing

When a document is created, updated, or finalized in a target directory:

* A SHA-256 cryptographic hash is generated locally for the file.
* The original file remains in its native directory (e.g., SharePoint, AWS S3, local drive).

Step 2: Blockchain Anchoring

The generated hash, along with relevant metadata (author ID, file creation timestamp, version tag), is recorded to a private/permissioned blockchain node. { "file\_name": "clinical\_trial\_phase2\_results.csv", "file\_hash\_sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855", "timestamp\_utc": "2026-09-07T12:41:00Z", "author\_id": "usr\_9921\_biotech", "version": "v1.2", "blockchain\_tx\_id": "0x8f3c...b12a" }

Step 3: Automated Verification & Audit

Any party with access to the file can re-hash it locally and compare it to the blockchain ledger. If a single character or metadata tag was altered, the hash will not match, immediately exposing tampering.
