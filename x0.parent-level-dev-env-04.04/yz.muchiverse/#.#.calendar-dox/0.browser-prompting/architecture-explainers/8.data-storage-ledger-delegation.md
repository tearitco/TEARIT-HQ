## 🧠 The real mechanism (as verified this session, dated 2026-08-18)

1. **One-writer rule** — every state/ledger file has exactly ONE process that ever writes it.
   Anyone else only reads. Violating this is a real, named house pitfall (#17/#36 in TPMOS's own
   pitfalls doc) — causes frame lag / stale-looking UI, not a crash, which makes it sneaky.
2. **Append-only ledgers for history/audit** — `master_ledger.txt`-style files: every meaningful
   action gets ONE appended, timestamped line, never edited/rewritten. This session's own real
   example: `strip_input_history.txt` (`KEY_PRESSED:`/`MOUSE_EVENT:` lines, one writer, growing
   forever, readers `stat()` the size to detect new lines cheaply rather than re-reading the whole
   file).
3. **Marker/pulse files for "something changed"** — a SEPARATE tiny file, appended with a single
   byte, exists purely so readers can `stat()` it (cheap) instead of re-parsing a big state file
   on every poll tick (expensive). The marker's SIZE is the signal, not its content.
4. **Cursor-based incremental reads** — a reader remembers how many bytes of a growing file it's
   already consumed (a "cursor"), and only reads new bytes past that point each poll — never
   re-reads from the start. Real, proven pattern (`poll_agent_relay()`, `poll_captured_input()`
   in this session's own taskbar work) — first-sight NEVER replays backlog, truncation resyncs
   without replay.
5. **Shared state = a dedicated piece that owns it**, not a free-floating file everyone touches.
   If N entities need to see "the bank's gold total," the bank IS a piece with its own
   `state.txt`; the bank's own manager/ops are the only writer; everyone else reads.
