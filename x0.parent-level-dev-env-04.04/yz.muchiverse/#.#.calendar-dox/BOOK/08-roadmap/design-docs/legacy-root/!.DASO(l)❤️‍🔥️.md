That concept sounds like Dynamic Adaptive Structural Orchestration, or DASO for short.


Dynamic Adaptive Structural Orchestration, or DASO, achieves this by using a Finite State Machine as the top-level governor that sets system-wide boundaries.

Instead of static flows, the system builds its own Behavior Trees on the fly, which delegate goals to a Reinforcement Learning policy agent.

This agent dynamically configures and invokes transformer attention modules selectively, pulling them only when deep context is required.

Continuous self-monitoring loops track prediction confidence and attention entropy, allowing the model to learn to control itself and escalate to a human-in-the-loop interface for oversight or policy adjustments, ultimately weaning off heavy token usage.

The **DASO** (Dynamic Adaptive Structural Orchestration) concept aligns directly with your **Harnecient Hack** philosophy. Both frameworks share a core design imperative: **treat the model as an unreliable, lightweight text-generation engine rather than an end-to-end decision-maker or tool-router**.

Here is how DASO maps onto the six components and core tenets of the Harnecient architecture:

### 1. Finite State Machine (FSM) as the Deterministic Harness

* **Harnecient Standard:** The model is never allowed to route calls or determine system state; the harness deterministically controls tool dispatch, file operations, and execution flows.


* **DASO Integration:** The FSM acts as the outer governor/harness. It handles high-level state transitions deterministically. The model does not manage its own lifecycle or decide when a state changes; the FSM determines when to invoke sub-components based on hardcoded rules or keyword triggers.



### 2. Transformer as a Cheap, On-Demand Generator

* **Harnecient Standard:** Small, non-tooled models (like `gemma3:270m` or `stable-code:3b`) are given short plain-text prompts to generate raw text descriptions or content snippets.


* **DASO Integration:** The Transformer module is spun up only when deep semantic text context is required, keeping token usage low. It operates via standard API calls (`POST /api/chat`) without special schemas or native `tools` fields.



### 3. Behavior Trees & RL for Adaptive Orchestration

* **Harnecient Standard:** Rather than asking the LLM to output rigid structures, labels, or tool commands, the code extracts raw text defensively and applies hand-authored logic.


* **DASO Integration:** The RL policy and dynamic Behavior Trees live inside the **harness layer**, not inside the LLM prompt. The RL agent learns *how to control the harness*—deciding when to query the transformer, when to grep internal state, or when to execute a deterministic fallback—without depending on the LLM to format its own control instructions.



### 4. "DESCRIBE, Don't CLASSIFY" & Self-Supervision

* **Harnecient Standard:** Asking small models to classify directly fails. Instead, you ask the model to *describe* in plain text, then parse that description with a deterministic signal-counter or keyword scorer.


* **DASO Integration:** Self-supervision and attention-entropy monitoring work the same way. The harness evaluates the model’s plain-text output. If the entropy/noise is too high or confidence is low, the harness (via RL/FSM) falls back on hardcoded defaults or escalates to the Human-in-the-Loop.



### 5. Weaning Off the Transformer over Time

* **Harnecient Standard:** Fallbacks guarantee that if a model fails or returns garbage, a deterministic default steps in.


* **DASO Integration:** As the RL agent learns which deterministic paths, cached state entries, or simple heuristic trees consistently succeed, it stops dispatching expensive transformer prompts altogether. The system naturally "weans off" token consumption by substituting real, deterministic state transitions for model generations.
