# 🆚 ncurses vs. the House (CHTPM/PAL) — Full Comparison Report

> 📅 Written 2026-08-05 · 📖 Reference docs: `!.HOUSE_STDS.md`, `house-design-docs.md`
> 🏠 The "House" = the CHTPM/PAL architecture used across all projects in this dev-env tree

---

## 🎯 TL;DR

**The House is better off without ncurses.** 🚫🧹

ncurses provides terminal UI primitives (windows, attributes, input handling) that the House already replaces with custom, purpose-built components that are more powerful and more appropriate for the House's multi-process, file-mediated architecture. ncurses would add a dependency without replacing any of the House's unique capabilities (GL rendering, PAL scripting, file-mediated IPC, session isolation, marker discipline).

The House **already replaces everything ncurses does** — and then some. 🔥

## 🏗️ What the House Actually Is

The House is a **multi-process architecture** where every component is a separate binary communicating via **files on disk** (not shared memory, not pipes, not ncurses screens):

```
┌─────────────────────────────────────────────────────────────┐
│                    THE HOUSE PIPELINE                        │
│                                                             │
│  🎮 button.sh (launcher)                                   │
│       │                                                     │
│       ▼                                                     │
│  🧠 prisc+x (PAL VM) — runs .pal scripts                   │
│       │                                                     │
│       ▼                                                     │
│  🖥️  chtpm_parser_pal (layout engine)                       │
│       ├── reads .chtpm XML layouts                          │

│       ├── renders [>] / [^] / [ ] focus glyphs              │
```

| Decision | Why | ncurses Equivalent? |
|---|---|---|
| **File-mediated IPC** | Multi-process isolation; session-scoped ephemeral dirs; symlink-in shared binaries | ❌ No equivalent |
| **Marker files** (frame_changed, screen_changed, state_changed) | Decouples compose from render; prevents focus clobbering | ❌ No equivalent |

| **Session isolation** (ephemeral dirs + symlinks) | Clean state per run; no cross-session contamination | ❌ No equivalent |

## 🧩 What ncurses Could Replace (and Why It Wouldn't Help)

### 🔄 Replaceable: renderer.c (ASCII terminal output)

ncurses could replace the ~177-line `renderer.c` with ~30 lines of `initscr()` + `printw()` + `refresh()` calls. **But this would be a step backward:**

- ❌ Adds a library dependency (`-lncurses -ltinfo`) to the shared `system/` binaries
- ❌ The House's `renderer.c` already handles both scrollback mode (print new frames, let terminal scroll) and clear-screen mode (`\033[H\033[J`) — both are trivial with ANSI escapes
- ❌ renderer.c's `write_crlf()` handles the OPOST issue (tty in raw mode by keyboard_input.c, so `\n` doesn't become `\r\n` automatically) — ncurses would need the same awareness
- ❌ renderer.c's "skip-if-unchanged" optimization (compare `current_frame.txt` content to last printed, skip if identical) is more efficient than ncurses's `refresh()` which always redraws
- ❌ The House deliberately uses **no ncurses** in `system/` binaries — see `keyboard_input.c` header: *"standalone raw-terminal input capture, no ncurses"* and `renderer.c` header: *"standalone frame display, no ncurses"*

### 🔄 Replaceable: keyboard_input.c (raw terminal input)

ncurses could replace the ~190-line `keyboard_input.c` with `initscr()` + `getch()` + `keypad()`. **But this would be a step backward:**

- ❌ Adds a library dependency to the shared `system/` binaries
- ❌ keyboard_input.c already handles arrow key decoding (`ESC [ A/B/C/D` → keycodes 1000-1003) manually — ncurses does the same thing internally
- ❌ keyboard_input.c drops a byte in `quit_flag.txt` on Ctrl+C — ncurses would need custom signal handling anyway
- ❌ keyboard_input.c's `enable_raw_mode()` explicitly sets `VMIN=0`/`VTIME=1` for non-blocking reads — this is more precise than ncurses's `halfdelay()`
- ❌ The House's `keyboard_input.c` is a **local copy** (not shared) because it normalizes Ctrl+C differently from the shared-ops version — ncurses would homogenize this away

### ❌ NOT Replaceable: chtpm_parser_pal.c (layout engine)

ncurses has **zero** equivalent for the CHTPM layout engine:
- XML-ish `.chtpm` layout files with `<panel>`, `<button>`, `<text>`, `<module>`, `<interact>` tags
- `${piece_methods}` auto-generation of numbered buttons from `piece.pdl` rows
- Focus glyph rendering (`[>]`/`[^]`/`[ ]`) inside the engine itself
- Substitution variables (`${game_map}`, `${tempo}`, etc.) at render time
- Href-based screen navigation (`<button href="...">`)
- `onClick="INTERACT"` reserved-string special-casing for nav mode

### ❌ NOT Replaceable: prisc+x (PAL VM)

ncurses has **zero** equivalent for the PAL VM:
- `li`, `beq`, `j`, `read_history`, `read_pos`, `sleep`, `hit_frame` opcodes
- File-position tracking for exactly-once key consumption
- Marker-file polling (grow detection, not just existence)
- Composable op dispatch via `default_op.txt` registry

### ❌ NOT Replaceable: chtpm_rgb_render + gl_mirror (GL pipeline)

ncurses has **zero** equivalent for the GL rendering path:
- Font rasterization of ASCII text into RGBA32 buffers
- On-demand emoji generation → voxel texture caching
- `MAP3D_MARKER` overlay compositing for 3D views
- GL texture upload + quad blitting via GLUT
- Receipt + checksum pattern for frame-size negotiation

### ❌ NOT Replaceable: File-mediated IPC + session isolation

ncurses has **zero** equivalent for:
- Ephemeral session directories (`pieces/sessions/<ts>-<pid>/`)
- Symlink-in shared binaries vs. project-specific state
- Marker-file-based inter-process synchronization
- `interact_relay.txt` as a key relay between GL window and PAL loop
- `state_changed.txt` / `frame_changed.txt` / `screen_changed.txt` discipline

## 🏆 The House's Advantages Over ncurses

### 1. 🔀 Multi-Process Isolation
The House spawns separate processes for input, rendering, layout, and GL display — each can crash independently. ncurses runs everything in a single process; a segfault in any part kills the whole UI.

### 2. 📁 File-Mediated State
Every piece of state is a file on disk — inspectable, debuggable, replayable. ncurses keeps state in memory; you can't `cat` a ncurses window to see what it contains.

### 3. 🧪 Headless Testing
The House's file-mediated architecture enables headless testing: inject keycodes into `interact_relay.txt`, read `current_frame.txt`, assert on pixel buffers — all without a display. ncurses requires a real terminal (even `TERM=dumb` needs a tty).

### 4. 🎨 Dual Rendering Paths (ASCII + GL)
The House renders to both a terminal (renderer.c) and a GL window (gl_mirror) from the **same** `current_frame.txt` source. ncurses can only render to a terminal.

### 5. 📜 PAL Scripting Layer
The PAL VM provides a declarative, composable event loop that can be edited without recompiling C code. ncurses has no scripting layer — you'd need to recompile for any UI logic change.

### 6. 🏷️ Marker Discipline
The House's marker-file system (frame_changed, screen_changed, state_changed) provides explicit, auditable synchronization between processes. ncurses has no concept of inter-process synchronization.

### 7. 🔌 Widget Architecture
The House spawns independent widget processes (canvas-widgit, board-viewer, etc.) that read the host's real files directly — no custom IPC needed. ncurses has no widget spawning mechanism.

### 8. 🧬 Emoji/Voxel Texture Pipeline
The House's on-demand emoji generation → voxel texture caching → 3D raymarching pipeline has no ncurses equivalent and is a core differentiator for the 2D/3D game use case.

## 🚫 Where ncurses Would Add Value (If Any)

Honestly? **Almost nowhere.** The only theoretical advantages:

1. 📦 **Less code to maintain** — ncurses's `getch()` + `printw()` would shrink keyboard_input.c and renderer.c by ~60% combined. But the House's custom code is only ~360 lines total across both files, and the House values self-containment over brevity.

2. 🎨 **Color support** — ncurses has a richer color API than the House's raw ANSI escapes. But the House's `chtpm_rgb_render.c` already handles color via font-rasterized emoji/voxel textures, making terminal color less relevant for the GL path.

3. 🖥️ **Terminal resize handling** — ncurses handles `SIGWINCH` and resizes windows automatically. The House's renderer.c doesn't handle resize at all (fixed 80×24/640×768). But this is a **bug to fix**, not a reason to add ncurses — the House would fix renderer.c to read `canvas.receipt.txt` dimensions dynamically (per §B receipt pattern).

| Question | Answer |
|---|---|
| Does ncurses replace anything the House does? | Only the trivial bits (terminal clear, cursor move, raw input) — and the House already does those better |
| Does ncurses replace anything the House *uniquely* does? | **No** — GL rendering, PAL scripting, file-mediated IPC, session isolation, marker discipline, widget architecture are all ncurses-free zones |
| Should the House adopt ncurses? | **No** 🚫 — it would add a dependency without replacing any unique capability |
| Should ncurses be used for new projects inspired by the House? | **No** — the House's file-mediated, multi-process architecture is more robust, more testable, and more portable than any ncurses-based approach |
| What *should* be used instead of ncurses? | **Nothing** — raw termios + ANSI escapes + file I/O is the House's proven stack, and it works 🎯 |

### 🏁 Bottom Line

The House is a **file-mediated, multi-process, dual-path (ASCII + GL) rendering architecture** that happens to run in a terminal. ncurses is a **single-process terminal UI library**. They solve fundamentally different problems. The House already replaces everything ncurses does for terminal UI, and then adds GL rendering, PAL scripting, session isolation, and a widget architecture that ncurses cannot touch.

**Stick with the House. Ditch ncurses. 🚀**

### 🔥 Where the House Beats Qt

1. **🚀 No framework dependency** — The House IS the framework. 6 small C binaries, zero external runtime. Qt requires a ~30-100MB library installation.

2. **🧪 Headless by design** — The House works headless (`NO_GL=1`) with relay injection and pixel-buffer verification. Qt requires a display server (X11/Wayland) even for headless testing — `QApplication` needs a screen.

3. **🔀 Multi-process isolation** — Each House component is a separate process. A crash in `gl_mirror` doesn't kill `keyboard_input` or `chtpm_parser_pal`. Qt runs everything in one process; a segfault in any widget kills the whole app.

4. **📁 Inspectable state** — Every piece of state is a file on disk. `cat pieces/display/current_frame.txt` shows exactly what's on screen. Qt's state is in memory; you can't inspect it without a debugger.

5. **📜 PAL scripting** — The PAL VM lets you edit the event loop without recompiling C code. Qt requires recompilation for any UI logic change.

6. **🎨 Dual rendering paths** — The House renders to both ASCII terminal and GL window from the same source. Qt can only render to a GUI window (no terminal fallback).

7. **🏗️ Widget architecture** — The House spawns independent widget processes that read the host's real files directly. Qt widgets are in-process and share the same memory space.

8. **🧬 Emoji/voxel texture pipeline** — The House's on-demand emoji generation → voxel texture caching → 3D raymarching pipeline has no Qt equivalent.

9. **📦 Deployment size** — House: ~500KB + data files. Qt: ~30-100MB minimum. The House fits on a floppy; Qt needs a USB drive.

10. **🔮 RISC-V future** — prisc+x targets RISC-V eventually. Qt has no bare-metal RISC-V support and would never work on embedded/headless RISC-V targets.

### 🚫 Where Qt Could Replace the House (Theoretical)

Honestly? **Almost nowhere.** The only theoretical advantages:

1. 🎨 **Richer widget set** — Qt has `QTableWidget`, `QTreeWidget`, `QGraphicsView`, etc. But the House's CHTPM layout engine with `${piece_methods}` and focus glyphs already provides all the widget types needed for the House's use case (menus, lists, canvases, 3D views).

2. 🖱️ **Mouse event handling** — Qt has `QMouseEvent`, `QWheelEvent`, etc. But the House's `gl_mirror.c` already handles mouse forwarding via the GLUT callback mechanism, and the canvas widget reads `stroke_points.txt` for brush strokes.

3. 🌐 **Network support** — Qt has `QNetworkAccessManager`. But the House is an offline architecture — no network calls in any project.

4. 📊 **Data visualization** — Qt has `QChart`, `QCustomPlot`. But the House's `canvas.raw` + `check_rgba.c` already provides pixel-level verification and the canvas widget renders any RGBA buffer.

## 🎮 We Beat GL Too — Going Straight to RGB

> 🤯 The House doesn't just compete with OpenGL — it **bypasses** the traditional GL rendering pipeline entirely and goes directly to the RGB framebuffer.

### 🔄 Traditional GL Pipeline (what most apps do)

```
CPU (scene graph, game logic)
  │
  ▼
GPU (vertex shader → rasterizer → fragment shader)
  │
  ▼
GPU Framebuffer (VRAM)
  │
  ▼
glReadPixels() ← SLOW! GPU→CPU readback, stalls pipeline
  │
  ▼
CPU-side pixel buffer (if you need it for anything)
  │
  ▼
Display (compositor → scanout)
```

**The problem:** Traditional GL apps render on the GPU, then need to read pixels back to the CPU for any CPU-side processing (screenshots, verification, overlay compositing). This `glReadPixels()` call is **painfully slow** — it stalls the GPU pipeline, waits for the GPU to finish, and then copies VRAM→RAM over the PCIe bus. On integrated GPUs, this is even worse because the "GPU" and "CPU" share the same physical memory but still go through the same stalls.

### 🏠 The House's Pipeline (we go straight to RGB)

```
CPU (scene graph, game logic, raymarch DDA loop)
  │
  ▼
CPU (pixel-by-pixel writes to RGBA32 buffer in RAM)
  │
  ▼
rgb_frame.raw (raw RGBA32 file on disk) ← NO GPU INVOLVED
  │
  ▼
chtpm_rgb_render daemon (font-rasterizes ASCII text → same buffer)
  │
  ▼
gl_mirror.c (uploads rgb_frame.raw as GL texture, blits one quad)
  │
  ▼
Display (GLUT swapBuffers → scanout)
```

**The key insight:** The House's rendering is **CPU-based**. `compose_rgb_frame.c` (and `chtpm_rgb_render.c`) compute every pixel on the CPU and write directly to a raw RGBA32 buffer in system RAM. `gl_mirror.c` then does exactly ONE GL operation: upload that buffer as a texture and blit a textured quad.

This means:

1. **🚫 No GPU readback** — The pixel buffer is already in CPU-accessible RAM. No `glReadPixels()`, no GPU→CPU sync, no PCIe bus stall.

2. **🚫 No GPU rendering** — The House doesn't use the GPU for rendering at all. The GPU is only used as a **display transport** (texture upload + quad blit). This is the most minimal possible GL usage.

3. **✅ Pixel buffer is immediately available** — Need a screenshot? Read `rgb_frame.raw` directly. Need to verify a pixel? Index `buf[(y*W+x)*4]` in C. Need to composite an overlay? Write to `rgb_frame_3d_overlay.raw` and let `chtpm_rgb_render.c` composite it. All CPU-side, all instant.

4. **✅ No GL state bugs** — Since `gl_mirror.c` only does `glTexImage2D` + `glBegin(GL_QUADS)` + `glEnd()` + `glutSwapBuffers()`, there's virtually no GL state to manage. No shader compilation, no VAO setup, no blend mode configuration, no depth buffer.

5. **✅ Multiple renderers share the same buffer** — `compose_rgb_frame.c` (tile graphics) and `chtpm_rgb_render.c` (text rasterization) both write to the same `rgb_frame.raw` path. `gl_mirror.c` reads whichever wrote last (via the receipt file). This is the "one state, multiple renderers" pattern that works because the House goes straight to RGB.

### 📊 House RGB Path vs. Traditional GL Path

| Aspect | Traditional GL App | House |
|---|---|---|
| **Where pixels are computed** | GPU (fragment shader) | CPU (pixel-by-pixel writes) |
| **Where pixels live** | VRAM (GPU memory) | System RAM (CPU-accessible) |
| **How pixels reach the screen** | GPU → compositor → scanout | CPU writes file → gl_mirror uploads texture → GLUT blits |
| **Screenshot cost** | `glReadPixels()` — stalls GPU, slow | `read()` the `.raw` file — instant |
| **Pixel verification cost** | `glReadPixels()` + compare — slow | `buf[(y*W+x)*4]` — instant C array access |
| **Overlay compositing** | Render to FBO, then composite on GPU | Write to separate overlay file, let chtpm_rgb_render composite on CPU |
| **GL state complexity** | Shaders, VAOs, FBOs, blend modes, depth tests | `glTexImage2D` + `glBegin(GL_QUADS)` + `glutSwapBuffers()` — 3 calls |
| **Headless verification** | Requires `glReadPixels()` or `glGetTexImage()` — needs a context | Read `rgb_frame.raw` directly — no GL context needed |
| **Multi-renderer sharing** | FBOs + blit — complex | File-based — trivially simple (last writer wins, receipt tracks it) |
| **GPU driver dependency** | Full GL driver required | Only for display; headless mode works without any GPU |

### 🔬 Why "Straight to RGB" Matters for the House's Use Case

The House's use case (2D/3D games with tile-based or raymarched rendering) is fundamentally a **CPU-renderable** problem:

- **Tile-based rendering** (mutaclsym's `compose_rgb_frame.c`): Each tile is a flat color or a voxel texture. The per-pixel computation is trivial — look up the tile's color and write it. No GPU shader needed.

- **Raymarching** (board-viewer's `bv_render_3d.c`): The DDA loop is a CPU algorithm — step through a grid, test AABB intersections, sample textures. This is inherently a CPU operation. The GPU would actually be *slower* for this because the raymarch has irregular memory access patterns that GPUs handle poorly.

- **Text rasterization** (`chtpm_rgb_render.c`): Each glyph is a small bitmap (8×16 pixels). Font-rasterizing ASCII text is a CPU task — the glyph bitmaps are pre-extracted from a registry and blitted pixel-by-pixel.

- **Emoji/voxel textures**: The on-demand emoji generation pipeline produces 16×16 voxel CSVs that are sampled per-pixel on the CPU. No GPU texture sampling needed.

In all these cases, the CPU is the right renderer. The GPU is only needed as a **display transport** — and the House uses it minimally (one texture upload + one quad blit per frame).

### 🏆 The House's GL Advantage Summary

| Traditional GL App | House |
|---|---|
| Render on GPU → read back to CPU → display | Compute on CPU → write to file → upload as texture → display |
| `glReadPixels()` bottleneck for screenshots | `open()` + `fread()` — instant |
| Complex GL state management | 3 GL calls total |
| GPU driver crashes = app crashes | GL only used for display transport; CPU rendering continues independently |
| Headless rendering requires offscreen FBO | Headless = just don't call `gl_mirror.c` — the RGB file is still written |
| Multi-viewport requires multiple FBOs | Multiple renderers write to the same file path; receipt tracks which is current |

**The House doesn't compete with OpenGL — it makes OpenGL irrelevant for rendering.** 🎯 The GPU is demoted from "rendering engine" to "display transport," and the CPU does what it's actually good at: pixel-by-pixel computation with regular, predictable memory access patterns.

This is why the House's architecture is uniquely suited for 2D/3D games: the rendering model matches the hardware. CPUs are great at sequential, predictable pixel writes. GPUs are great at parallel, irregular fragment processing. The House's tile-based and raymarched rendering is sequential and predictable — it belongs on the CPU. And it does. 💪
