## 4. THE ACTUAL REMAINING CAUSE — found via angle 6 (house prior art)

Grepped khtpm_strip_parser.c (the taskbar, PROVEN working) for every
XCreateWindow / set_window_opacity call site, not just the first one.
Found this, already committed, already documented, in the taskbar's
OWN source (lines ~2404-2429), and never ported over when
khtpm_entity_menu_render.c's db-hq/events-hq/chat-hai/popup branches
were written:

    taskbar_soft_focus(dpy, win);

    /* KISS opacity-on-reset fix (2026-08-11, direct question: "did u
     * ever figure out how legacy would have transparency on bottom bar
     * (but only after reset)?" -- see opacity-bug-aug9.txt and
     * khtpm-refactor-plan.md's "Opacity-on-reset quirk" entry, both
     * previously inconclusive/deferred, not actually fixed). Leading
     * theory there: a compositor-timing quirk where Mutter/Xwayland
     * doesn't reliably honor _NET_WM_WINDOW_OPACITY set at map-time on
     * the FIRST paint of an override-redirect window, but does honor it
     * once the property is re-applied after the window has been
     * visible for at least one real frame -- which is incidentally
     * exactly what "reset" (a full process relaunch) does. Cheapest
     * possible fix matching that theory, never actually tried before
     * now: just re-set the SAME opacity property again here, after the
     * windows are already mapped/painted (first draw_header_win()/
     * draw_bottom()/draw_popup_win() calls above already ran), instead
     * of only once at XCreateWindow time. */
    XFlush(dpy);
    usleep(200000);
    double relaunch_opacity = load_theme_opacity();
    set_window_opacity(dpy, win, relaunch_opacity);
    set_window_opacity(dpy, hq_win, relaunch_opacity);
    set_window_opacity(dpy, popup_win, relaunch_opacity);
    XFlush(dpy);

This is a REAL, ALREADY-SOLVED, ALREADY-DOCUMENTED house quirk from
2026-08-11 — the taskbar itself only became reliably transparent once
this "set opacity again after first paint" workaround was added. The
entity-menu renderer (khtpm_entity_menu_render.c) was written later
(2026-08-16 per its own §5d.10/§5d.11/§5d.12 comments) and calls
set_window_opacity() exactly ONCE, immediately after XMapWindow, BEFORE
gc/buf/xftdraw_buf are even created and BEFORE the first redraw() call
— i.e. exactly the map-time-only pattern the taskbar's own 2026-08-11
comment says Mutter/XWayland does not reliably honor. This workaround
was simply never ported into the newer file. This matches the exact
symptom (property correct, override_redirect correct, hints correct,
still zero visible effect) with zero remaining unexplained variance.

## 5. FIX APPLIED (live, rebuilt, re-verified)

File: *.monads/*.livedesk-taskbar/ops/khtpm_entity_menu_render.c
