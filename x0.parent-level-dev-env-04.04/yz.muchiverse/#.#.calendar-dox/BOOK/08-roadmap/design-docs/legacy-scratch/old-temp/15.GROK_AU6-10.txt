2. K3 KEY INJECTION — WHAT IT IS HERE, AND WHAT TO FIX
================================================================

### Two injection layers (do not mix up — HOUSE_STDS §F.17)

| Layer | File | Format | What it proves |
|---|---|---|---|
| **A. Full CHTPM chain (classic k3)** | `pieces/keyboard/history.txt` | `[YYYY-MM-DD HH:MM:SS] KEY_PRESSED: <code>` | parser → module → frame |
| **B. Module relay only** | `pieces/apps/player_app/interact_relay.txt` | bare keycodes one per line | module loop only |
| **C. KHTPM entity relay (new, Aug-6)** | `<entity>/interact_relay.txt` | `RUN_METHOD:Label`, `NAV_KEY:Enter`, `ACTIVATE_NAV:N`, `CLOSE`, `SHOW_PAGE:...` | desktop window menus **without X11** |

k3 guide (`_.0.aigent-testing-k3.txt`) is the **discipline** (baseline → inject →
frame/state evidence → root `FRAME_REPORT_*` before code edits). The **mechanism**
for KHTPM is layer C, not layer A — there is no `pieces/keyboard/history.txt`
inside a pure KHTPM desktop window.

### What is already proven working (Claude 14 handoff §2b)
```
echo "RUN_METHOD:Read" > <pkg>/interact_relay.txt   # opens SHOW_PAGE
echo "NAV_KEY:Enter"   > <pkg>/interact_relay.txt   # picks focus row
```
Logged in entity `history.txt` as SHOW_PAGE / SHOW_PAGE_PICK(navkey) / SHOW_TEXT_FILE.
That **is** the agent-friendly k3 analog for KHTPM. Prefer this over `xdotool` /
`tp_test_send_key` for automation (X11 title collision: every gl_mirror is still
`"mutaclsym RGB mirror"`).

### What still needs "nav fix" for injection (scoped, product-useful)
Worth doing **because agents and scripts depend on it**, not because humans need
arrow keys in every popup:

1. **Stable, documented relay vocabulary** (RUN_METHOD / NAV_KEY / SHOW_PAGE /
   SHOW_TEXT_FILE / CLOSE) with one short HOW2 next to TILE_PICKER_DESIGN.
2. **Self-dismiss races** on SHOW_TEXT_FILE (observed: popup closed a few seconds
   later) — diagnose before authoring more event commands that rely on it.
3. **prisc+x long-path regression sweep** after the 512 fix: any `event.pal`
   with long absolute `exec` paths should be re-run once.
4. **Taskbar keyboard** is a *separate* problem (override_redirect + Wayland seat).
   File injection to *entity* relays does not require taskbar focus at all.

### What is NOT the k3 fix
Spending another long session on X11 grab / XSetInputFocus / global-focus fights
so that physical keyboard arrows work when a gedit or terminal also exists.
That is §3.

3. SHOULD WE MAKE KHTPM NAVS OVERRIDE X11 NATIVE WINDOWS?
================================================================

### Recommendation: **No as a priority. Optional later. Do not block EZ/events.**

Why:
1. **Root cause is environmental**, not a missing `XRaiseWindow` call.
   Aug-6 spent a full session proving: window-ID reuse, grab races, flock
   backlog, and finally **Wayland/XWayland compositor seat ownership** all
   produce "focus doesn't work" with different real fixes. Another "just raise
   the window" pass is likely to re-introduce the global-focus-fight regression
   already documented.
2. **Human path already works**: mouse clicks on KHTPM menus work.
3. **Agent path already works**: file relay (NAV_KEY / RUN_METHOD) never needs
   keyboard focus over gedit/terminal.
4. **Native tools (gedit, xterm) winning focus is correct desktop behavior**
   for a compositor. Fighting the compositor to steal keys from a focused
   terminal is the wrong product posture unless you are building a full WM.
5. User already leaned toward **rollback or mouse-primary** for the [N]/nav
   numbering experiment (14 handoff §4). That decision is still open — bring
   it back explicitly before more keyboard-nav engineering.

### If you still want "keyboard works on KHTPM when something else is focused"
Middle ground (matches option (c) in the handoff):
- Keep **[N] as display/addressing only** (agent can target row N unambiguously).
- Keep **file NAV_KEY** as the automation path.
- Drop ambitions for taskbar terminal-box to steal seat keys from gedit.
- Do **not** install global X grabs as default.

Only revisit full keyboard override if a *human* workflow truly requires
keyboard-only ranching with terminal open side-by-side — and then treat it as
a dedicated research spike with xev evidence, not a drive-by fix.

4. EVENTS EDITOR — WHAT WE ARE ACTUALLY DOING
================================================================

### The real goal (one sentence)
Build a **visual compiler for `.pal`**: GUI authoring → `event.ir.pdl` (truth) →
`event.pal` (`prisc+x` ISA) → desktop/KHTPM runtime executes it, with RPG Maker
page/condition/trigger semantics as the target model (highest page wins, etc.).

### Runtime model (must not re-derive wrong)
- Event = list of **pages**; continuous condition check; **highest eligible page**
  is active; trigger then runs that page's command list.
- Our data shape: `<pkg>/event_pkg/pages/page_N/{condition.pdl,event.ir.pdl,event.pal}`.
- Real opcodes are the register-machine ISA (`li`, `exec`, `sleep`, …) — not
  invented `show_text`/`ret` stubs from old scaffolding.

### The parallel variants (keep them honest)

| Variant | Path | Role | Status |

### Yes — with a hard boundary

**Use mock for:**
- RPG Maker layout muscle memory (command list column, page tabs, parameter
  dialogs, Commands vs Scratch feel).

  are painful to iterate inside full CHTPM session isolation.

**Do not use mock for:**
- Becoming the real compiler or the runtime.
- Saving "almost IR" that nothing else reads.
- Shipping as asa/ava "Events" product path long-term (today it is already
  exposed as "Events (mock)" — keep that label honest).

### Practical parallel track
1. **ez** keeps ownership of **IR + compile + proven commands**.
2. **mock** iterates **RMMV chrome / list editor UX** (can even hardcode a
   fake command list at first).
3. When mock UX stabilizes, **port chrome patterns into regular event-editor**
   (CHTPM layouts + compose), and point Save at the **same** `event.ir.pdl` +
   compiler entry point ez already has (extract compile into a shared op if
   needed — one compiler, multiple UIs).

That is faster than forcing RMMV beauty into ez *or* forcing compile into mock.

================================================================

### event-ez — stay bare bones on purpose

Design contract:
- **Only ship working features.** No dead "Show Choices" row until it compiles
  and runs (current cmdpick lists only Change Gold — correct discipline).
- UX = digit jump + cli_io + Save. Ugly is OK.
- IR is always truth; every Save **full rebuild** of `event.pal` (never patch).
- Gaps that are OK until named milestones: no edit-in-place, no load-into-form,
  conditions recorded but not evaluated.

**If ez "got off on the wrong foot":** redesign means *thinning*, not *fattening*.
Throw away leftover pet Chase/Flee UX if any remains in docs/UI; keep Gallery →
Page → CmdPick → Param → Save. Do **not** turn ez into a second RMMV clone —
that is regular event's job.

**Redesign triggers (only when):**
- Gallery/Page flow confuses humans more than it helps, or
- cli_io can't express a command class you need (then add one focused screen,
  not a full chrome overhaul).

### regular event-editor — mirror mock, share compiler

Design contract:
- **Look like RPG Maker** (use gl_mock + VISUAL_REF_* as the bar).
- **Behave like house CHTPM** (parser focus glyphs, digit jump, session isolation,
  marker discipline — HOUSE_STDS §A/§D).
- **Compile like ez** (same IR schema, same wrapper-exec rule, same prisc+x ISA).

Redesign should **more mirror mock** for panels/lists, and **more mirror ez**
for save/compile semantics. Today regular event is the opposite risk: some
chrome, weak compile.

### Shared non-negotiables across all variants
1. Never invent opcodes that `prisc+x` does not implement.
2. Never `exec op arg1 arg2` as two literals — wrappers only.
3. Precompute dynamic `${var}` for href targets (ez's lesson).
4. Atomic shared-state writes.
5. k3/file-injection proof before claiming a feature done.
6. One process-hygiene checklist before every GL test.
