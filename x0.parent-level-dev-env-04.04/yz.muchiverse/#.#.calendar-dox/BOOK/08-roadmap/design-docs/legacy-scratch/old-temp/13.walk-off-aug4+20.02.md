### 3️⃣ Tile-picker got a real "desktop placer"
Picking an emoji now:
- Writes a real, portable little package onto `#.desktop/tiles/<name>/`
- **Pops open a real, live GL window on your actual desktop** showing that emoji
- That window is draggable, snaps to the same invisible 80px grid your egg-pals already use, closes itself if you delete its package, and is capped at 30fps so it doesn't cook your CPU

First attempt was a bespoke window that **you literally could not interact with** — it didn't plug into this house's real keyboard pipeline. ### 5️⃣ Real bugs found and fixed along the way
- A build script was silently deleting tile-picker's own "what do these keys mean" file and replacing it with an unrelated stock-trading game's version — keys just did nothing, no error.
- The desktop-tray path math was wrong for how this widget is actually laid out — tiles were landing inside tile-picker's own folder instead of the real shared desktop.
- Missing font/emoji-generator files meant the window rendered blank, then colors-only.
- A double-numbering bug on the buttons (fixed).
- **A pile of leftover test processes were eating real CPU** (~40% from one alone) — cleaned up, and the live window now hard-caps its own framerate.

### 6️⃣ "Any window has a PID now" + the "^" aiming mode 🎯
You asked: can I drag a placed tile straight into a board-view window, even without pre-pairing them? Real answer: yes, and here's what that took:
- Every widget window now gets tagged with its **real process ID** (a standard X11 thing called `_NET_WM_PID` that nothing in this house was setting before) — found and fixed a sneaky bug where two windows open at once could get mixed up.
- New design (**replaces** an earlier "type in a PID" idea you decided you didn't like): press Enter on an emoji and instead of placing it immediately, it goes into **"^" mode** — a crosshair-style aim state. Click **anywhere on screen** — bare desktop, or inside a board-viewer window — and it places there. Escape cancels.
- **What works right now:** click on bare desktop → places for real. Click inside a board-viewer window → **detects** that correctly now (this took a second bug fix — the first version was quietly missing every board-viewer click and just placing on the desktop instead), but only *actually materializes into the game* if that game uses mutaclysm's tile format. Aomorai-editor's own 3D world doesn't yet — you'll see an honest "not supported yet" message there instead of it silently failing.

### 7️⃣ Daylight fix
New worlds in aomorai-editor now start at **noon**, not midnight — a real bug where every fresh world's sun started below the horizon. Also nudged the one live test-save so you could actually see the fix in the board-viewer window.

## 🤖 Part 2 — handoff to the next AI: how to grok this whole project and what's next

### The one-paragraph mental model
This house has exactly **one real input pipeline** (`keyboard_input.c`/`gl_mirror.c` → `history.txt` → `chtpm_parser_pal.c` → `interact_relay.txt` → `<project>_menu_input`), and every widget is a **fully self-contained session** (own copy of `system/`, own PAL loop, own CHTPM layout) that cross-links to a host only through small state files, never shared process infrastructure. **Read `&.widgits/tile-picker/TILE_PICKER_DESIGN.md` in full** — it has the complete, evidence-based build history, every real bug found this session, and exact file/function references. Don't re-derive any of it from scratch.

### The real scope, going forward
Direct instruction, 2026-08-04: the actual end goal is a **game editor** whose widgets let creators build and modify game entities either **on the literal desktop** or **inside a game/board view** — and, crucially, this is the *same* mechanism as letting end-users create and customize their own **desktop pets/items** (hikikomorai's whole premise). Tile-picker's desktop-placer + "^" aim mode is the **first working slice** of that unified idea — a "thing" (right now: a bare emoji) that can live on the desktop or inside a game view, movable between the two. Everything built this session is infrastructure for that bigger idea, not a one-off feature.

### What's next: the event editor, and why it's next
Direct instruction: desktop-placed things (and eventually in-game entities) need a **right-click context menu** with real methods — not just "Close" (which is all `egg_window.c` has today), but things like "open event editor for this," Play/Pause, Attack, Inventory, etc. (see `TILE_PICKER_DESIGN.md` §4.5 — this was already scoped once, now it's actually next). That means **the event editor has to exist first**, since "open event editor for this entity" is the very first real context-menu method worth building.

**There is already a mock of this to study/mirror**, at `201.rpg-maker-clone/` — a single freeglut binary that's both a map/event editor AND a player, deliberately shaped to match house data conventions (`project.pdl`, `switches.pdl`, `maps/<id>/map.txt`, `maps/<id>/events/ev_X_Y/state.txt` + `event.pal`) so it can be wired in later without a format rewrite. Read `201.rpg-maker-clone/ARCHITECTURE.md` and `README.md` before designing the real `&.widgits/event-editor/` build — this is the reference implementation's real shape (mode machine: Title → Map → Event → Play; event editor chrome: methods 1–8, pages 9–12, fields 13–16, contents 17–28, footer 29–34), not something to reinvent.

**A new design doc has been written inside `&.widgits/event-editor/` itself** (`EVENT_EDITOR_FOR_AOMO_AND_HIKIKOMORAI.md`) covering exactly how this applies to both aomorai-editor and hikikomorai going forward — read that before writing any event-editor code.

## 🕐️ Aug 5 — event-editor dispatch bug fixed, pets on screen for real, event-ez (4th variant) built and proven

### Real root cause found: house-wide shared VM bug, not an event-editor bug
The "Enter bug" (key presses reaching `history.txt`/`interact_relay.txt` but never taking live effect, despite the op working when run manually) was NOT in event-editor's own PAL script or ops. Root cause: `prisc+x.c`'s (the shared VM, in mutaclysm's `system/`) own `exec_custom_op()` interpolates a resolved script path **unquoted** into a `popen()`/`system()` command string. This house's own directory tree has a literal `&.widgits` path segment — an unescaped `&` in a shell command backgrounds/truncates it, so every PAL-driven custom-op call under `&.widgits` was silently mis-parsed by `/bin/sh` and never actually ran. Fixed by single-quoting the path in all three call sites. Rebuilt in mutaclysm (event-editor and event-ez both symlink `system/` from there, so both get the fix automatically). Verified live: real key injection (`8`+Enter, `5`+Enter) now correctly flips real state (`view_mode`, help messages) through the actual running window.

### Real asset thumbnails inside the actual product window (not just the mock)
Direct user question: "don't we create emoji atlas as jpg then convert to csv? can't we do the same with an image?" — yes, exact same mechanism. `tp_asset_to_sprite.+x` downscales a real photo to a 16×16 `voxels_16.csv`, registered under a real Unicode marker in `items.txt`, and `chtpm_rgb_render`'s existing emoji-blit path (built for map tiles) picks it up automatically wherever `ee_compose_frame.c` emits that marker byte sequence. Wired for asa (🎤, from `il-dj.png`) and ava (💃, from `nyeoni8.png`) — both showing real portrait pixels inside the real CHTPM window, confirmed via direct pixel inspection of `rgb_frame.raw` (RGBA, not RGB — a real gotcha in my own first verification attempt).

`ee_compose_frame.c` now reads a package's own `event.ir.pdl` (via `EE_PKG_DIR` env → `ee_state.txt`'s own `pkg_dir=` key) and renders its real NODE rows instead of the hardcoded door_guard demo — confirmed live, asa's own real event content rendering with the nav range correctly shrinking to match.

### Pets on screen for the first time — and a real, separate rendering bug found + fixed
Dog/cat/chicken spawned as real desktop windows for the first time (`@.apps/pets/pieces/{dog,cat,chicken}/button.sh`, mirrors asa/ava's own per-entity pattern). Direct user report: renders were "grainy, translucent, overlaid with multi-color static" but the correct image was still faintly visible underneath.
