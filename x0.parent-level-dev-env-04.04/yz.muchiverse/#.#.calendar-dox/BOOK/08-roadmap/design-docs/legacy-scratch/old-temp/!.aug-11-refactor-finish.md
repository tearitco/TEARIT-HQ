## The single most important thing this session learned

**"General functionality is done" was true by roughly the 4th live-test round. Every round after that surfaced a bug that looked cosmetic from the outside but turned out to be a real, deliberate, often highly-tuned piece of legacy logic that the port had approximated instead of copied.** The user's own words after the digit-jump bug: *"legacy code has the answer, ur not copying it right."* That's the whole lesson. Concretely, the failure pattern was:

1. Port a plausible-looking version of some behavior (e.g. "digits accumulate in a buffer, Enter jumps") without reading the ENTIRE relevant legacy code path first.
2. It looks like it works in isolation / passes a build.
3. Live test reveals it's wrong in a way that only shows up under real interaction (numbers too high, jump silently fails, wrong window, etc).
4. The real legacy code, once actually read in full, turns out to have significantly more nuance than assumed — validation against live state, a completely different trigger model (live-per-keystroke vs. on-Enter), a second/third file that also needs porting, etc.

**Do not assume a legacy function's behavior from its name or a one-line grep.** Read the FULL function, and read every function it calls, before porting. This is slower per-bug but every fast/assumed port this session had to be redone once live-tested.

## What was fixed this session, in order (see khtpm-refactor-plan.md for full detail + line citations)

1. Popup window given its own dedicated window (`popup_win`), separate from the persistent header (`hq_win`) — matches legacy's real `strip_win`/`popup`/`g_cliio_win` three-window architecture. Header no longer disappears when a submenu opens.
2. Header window sized to its REAL computed content width at creation (not a guessed constant, not the full screen) — `compute_header_width()`.
3. `[NAV]`/digit indicator moved from the bottom bar (leftover, pre-2026-08-09 legacy position) to the top header's reserved `STRIP_NAV_BOX_W` (64px) left box — matches legacy's real, current position.
4. `.pdl`-driven header offset: `strip_x_offset`/`strip_y_offset` now read from `#.desktop/livedesk_taskbar.pdl` at startup (`load_strip_offset()`), not hardcoded. The live config here is `500`/`50`, not `0`/`40`.
5. Startup keyboard focus grab (`taskbar_soft_focus()` called once at launch) — a **deliberate deviation from legacy**, not a port. Legacy has no proactive focus grab either; this was added because a fresh `override_redirect` window has zero focus until something claims it, and relying on incidental WM/pointer behavior was unreliable.
6. Header-cell nav-claims: legacy's `sync_strip_claims()` writes `KIND=btn|NAV=1..12` claims into the shared `livedesk_nav_claims.txt` — **this port never wrote them at all**, so `ktb_jump_nav()` could never find a header-cell target. Ported directly into `khtpm_taskbar_manager.c`, wired into `ktb_reload()`.
7. `ktb_jump_nav()`'s kind dispatch — was missing a real `"btn"` case (fell into the `"row"` catch-all, which does something genuinely different and real: injects `ACTIVATE_NAV` into a REMOTE entity's `interact_relay.txt`, confirmed by the user as intentional agent/harness infrastructure, not to be touched). Added the missing `"btn"` branch for local header-cell activation.
8. Visual separator line between the `[NAV]` box and cell 0 (HQ) — direct request, not a legacy behavior (legacy relies on padding alone).
9. **Digit accumulation algorithm — the last fix before quota ran out, NOT YET LIVE-TESTED.** `ktb_digit_push()` was a naive append (any digit, flat 8-char cap, no validation, never moved anything). Legacy's real algorithm (`tp_taskbar.c` ~line 4037-4116, comment: "chtpm_parser_pal digit_accum") is completely different: validates each new digit against `max_claimed_nav()` (the REAL currently-available nav range, read live from the claims file), caps the buffer to exactly the digit-count that range needs, restarts from a bare digit if the accumulated value goes out of range, and — critically — **moves the `[>]` cursor after every single valid keystroke** (not just on Enter) without activating anything; only Enter actually activates. Ported as `max_claimed_nav()` + `ktb_nav_digit_peek()` + a rewritten `ktb_digit_push()` in `khtpm_taskbar_manager.c`. **Build is clean but this was never live-tested — verify it first thing next session.**

Concrete things to check:

Check whether `popup_win`'s repeated `XMapRaised`/`XUnmapWindow` cycling (every time a submenu opens/closes) might be losing its opacity property on each remap — `set_window_opacity()` is only called once, at `popup_win`'s CREATION, not on every subsequent map. **This is a concrete, testable hypothesis**: try calling `set_window_opacity()` again every time `popup_win` is mapped (not just at creation) and see if that changes the intermittent behavior.
   - Check whether `XCopyArea` redraws (the offscreen-pixmap-then-blit pattern used everywhere) interact with compositor recomposition timing in a way that could visually "flash" opaque for one frame — i.e., is the intermittent opacity actually a REDRAW-TIMING flicker (opaque for one frame during a redraw, then transparent again) rather than a truly stuck state? Watching closely during a redraw-heavy interaction (e.g. rapid digit typing, which redraws every keystroke) vs. an idle bar would help distinguish "flicker during redraw" from "sometimes stuck opaque."
   - This project's own established finding (see the earlier session's opacity investigation) is that `xwd`/`XGetImage` CANNOT reliably verify compositor-level effects here (Wayland/XWayland) — any investigation of this must be a DIRECT HUMAN VISUAL check, described precisely (which window, what action preceded it, does it recover on its own or need a restart) — don't try to "prove" this with a screenshot tool.
