2. DOES 044 USE THE MASTER LEDGER? NO. THIS IS THE BIG ARCHITECTURAL DIFFERENCE.
================================================================================

  101.ledger-player-npc-simple+3 (per LEDGER_ADVANCED_STUDY.txt + +3_ARCHITECTURE_SUMMARY.txt
  doctrine, and confirmed on disk) has:
    - data/master_ledger.txt            <- single source of truth, append-only
    - players/<name>/ledger.txt         <- per-player ledger slice
    - system/game_manager.c             <- REAL C daemon: polls relay, drives turns,
                                            calls ops/computer_turn.c for NPC/AI turns
    - ops/ledger_append.c, ops/sync_player_ledger.c, ops/view_ledger.c, ops/game_tick.c,
      ops/game_init.c, ops/human_turn.c, ops/computer_turn.c
    - BOTH system/chtpm_parser.c AND system/chtpm_parser_pal.c (true C-mode + PAL-mode)
    - State is DERIVED by replaying the ledger, not stored as current-value flat files.

  044.pal-chat-irc+2 instead has:
    - rooms/<room>/messages.txt         <- flat append file per room, no turn/replay concept
    - users/<user>/profile.txt          <- current-value flat file, not ledger-derived
    - NO data/ directory, NO master_ledger.txt, NO game_manager.c, NO ledger_append/
      sync_player_ledger/view_ledger ops.
    - The PAL script (pal/main_loop_chtpm.pal) + chtpm_parser_pal.c ARE the whole "game
      manager" - there's no C daemon polling a ledger or driving turn order.

  Net: 044 is NOT built on the ledger-driven pattern at all. It's a simpler
  "current-state flat files + append-only messages.txt per room" model. This works fine
  for chat (no turn order, no NPC banking, no replay/time-travel need), but it means:
    - LEDGER_ADVANCED_STUDY.txt line ~731 lists "Pal-Chat-IRC (social messages)" as one
      of the pattern's proven use cases - that line is aspirational/historical, not an
      accurate description of the CURRENT 044 codebase. Worth flagging since it could
      mislead a future agent into assuming ledger replay exists here.
    - There is no crash-recovery-via-replay, no audit trail, no time-travel for chat
      history beyond "read messages.txt from the top" (which is close enough to a ledger
      in spirit but has none of the actor_type/turn_number/scale_bank machinery, and no
      game_manager.c to replay it into derived state).

  IS THIS A PROBLEM? Not necessarily - chat doesn't need ring-based turn order or NPC
  scale-bank fidelity. But it IS a real architectural divergence from the "canonical"
  101.ledger-player-npc-simple+3 reference, so don't assume 044 has ledger/replay/
  crash-recovery semantics when reasoning about it or writing the trace doc.

3. OTHER 044 vs 101 ARCHITECTURE DIFFERENCES (beyond the ledger)
================================================================================

  - 044's orchestrator launches persistent P2P daemons (palnet_peer, chat_inbox_watcher)
    that must survive tick-to-tick; 101's game_manager.c is itself the persistent daemon
    (single process, polls relay + drives ring/turn order) - different daemon topology,
    not just "same pattern, different ops."
  - 044 uses session-scoped directories under pieces/sessions/<ts>-<pid>/ with symlinks
    for multi-user isolation (each terminal = its own session); 101 is single-session,
    no session dir sharding.
  - 101 has a registry/ (word_bank.txt) + explicit turn/epoch/scale_bank config; 044 has
    no registry/, no turn concept at all (chat has no "turns").
  These are expected/appropriate differences given chat vs. turn-based-game domains -
  flagging them so the upcoming pc-irc-trace-j26.md doesn't get written as if 044 were
  ledger/turn-shaped when it isn't.
