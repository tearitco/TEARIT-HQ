## 🏷️ 2. Naming going forward: `home-🏠️/`, not `home`

You asked "when you say home, do you mean home-xyz?" — **yes**, and the fact you
had to ask proves the point. Today the per-user directory is literally named
`home/` inside `xyzfs/users/<uuid>/`. But we already have a Linux `$HOME` on
the same machine. Two "homes", one word = confusion for humans and tools.

**Convention from now on:**
- `home-🏠️/` = the **xyzfs user's home** (per-user dir inside `~/xyzos/xyzfs/`).
- `$HOME` / `home` = the **Linux home directory** (where `~/xyzos/` itself
  lives). Always lowercase/`$`-prefixed when we mean the OS one.

This matches the house's existing emoji-directory style
(`0.user-pal👤️/`, `44.xyz❤️‍🔥️00.10`, `01.avatar-creation👤️/`), so it's
idiomatic here, not a new invention.

**v1 caveat (honest):** the *physical* directory inside the copied apps is
still `home/` today (their ops hardcode it), and v1 keeps it that way — the
constraint wins. `home-🏠️/` is the label we use in docs, in new code, and in
the pointer file below, so there is exactly **one line** to change whenever the
userpal ops are next touched (see §3).

## 🧭 3. The pointer principle: a global `paths.pdl` instead of set-in-stone names

Your instinct is the right architecture: **don't hardcode layout names in ops —
resolve a logical name through one pointer file.** A name is a view; a path is
a fact; only the mapping file says which is which.

The pointer lives at `$HOME/xyzos/paths.pdl` (created by the installer, global
to that OS install — same spirit as `session.pdl`, `catalog.pdl`,
`installed_apps.pdl`, which the house already uses):

```
# $HOME/xyzos/paths.pdl — the ONE place logical names become real paths.
SECTION | KEY                 | VALUE
META    | piece_id            | xyzos_paths
META    | version             | 1.0
PATHS   | user_home_root      | xyzfs/users
PATHS   | user_home_dir       | home          ← physical dir TODAY (legacy name,
                                    see §2; the label going forward is home-🏠️)
PATHS   | account_registry    | apps/00.login-signup/users
PATHS   | identity_state      | apps/00.login-signup/xyzfs/session.pdl
PATHS   | installed_ledger    | app-store/installed_apps.pdl
PATHS   | catalog             | app-store/catalog.pdl
```

**The rule:** new ops/apps resolve `user_home_root` + `user_home_dir` from this
file and build paths from the result. They **never** write
`xyzfs/users/<uuid>/home/` as a literal. If the shape ever changes (Option A/B/C
below, or a rename to `home-🏠️`), you edit `paths.pdl` — and only the handful
of legacy ops that still hardcode — not every file in the tree.

**Why this matters for install:** the installer seeds `paths.pdl` to match
reality *today* (`home`), so the pointer is truthful from day one. When
migration happens, the pointer is the migration checklist: change it, grep for
hardcoded names, update those ops. Nothing else.

**Scope now:** the pointer is introduced by install v1 and read by **new**
infrastructure (installer, install op, KPI harnesses). The copied login/avatar
ops are left alone this pass — local dev tree untouched, per your constraint.

## ❓ 4. The one question, stated plainly

You said the layout should be `~/xyzos/xyzfs/<user-name>/<app>/` — "mirror the
linux file system." That sentence contains **two separate ideas** with very
different costs:

1. **Per-app subdirs under each user** (`<app>/`) — easy and safe (delivered as
   `home-🏠️/<app>/` under the pointer). Nobody disagrees with this part.
2. **Naming the per-user directories by the *user name*** (`xyzfs/alice/`)
   instead of a generated id — **this is the real decision.**

So the question is just: **what are the per-user directories called — the
login name, or a uuid?**

To make "mirror Linux" concrete: real Linux does BOTH — `/home/alice/` is named
by the login name, *and* a separate durable number (the UID) lives in
`/etc/passwd`. The design question is which one names the directory, and where
the other one lives.

## 🧭 6. The three options

### Option A — name-keyed dirs (your literal idea)
```
xyzfs/
  session.pdl
  alice/                    ← named by login name, like /home/alice
    profile.txt             ← name → uuid (uuid = the durable id)
    login/  avatar/  wallet.txt
```
- **What changes:** the 6 userpal ops + avatar ops — everything that computes
  `xyzfs/users/<uuid>`. Uniqueness already enforced.
- **What breaks:** live dev-tree data needs a one-time migration; any app
  developed against the old shape breaks until updated.
- **Feels like:** `ls xyzfs/` shows human names.

### Option B — keep uuid dirs, add per-app subdirs (no-break) ✅ recommended
```
xyzfs/
  session.pdl
  users/
    <uuid>/                   ← the uuid dir IS this user's home-🏠️ (uuid ≈ UID)
      profile.txt             ← uuid → login name (registry)
      home-🏠️/                ← NEW per-app data dirs live here
        login/  avatar/  wallet.txt
```
- **What changes:** nothing in the proven ops. `home-🏠️/<app>/` is additive.
- **What breaks:** nothing. Live data stays valid; in-tree == installed.
- **Feels like:** `xyzfs/users/<uuid>` = `/home`, registry = `/etc/passwd`.
- **With the pointer:** paths.pdl maps `user_home_dir = home-🏠️`, so even the
  physical rename later is a one-line change, not a codebase sweep.

### Option C — name-keyed symlink view on top of B (the bridge)
```
xyzfs/
  session.pdl
  alice -> users/<uuid>        ← a SYMLINK, created at signup
  users/<uuid>/home-🏠️/{login,avatar,...}
```
- **What changes:** one *additive* step after signup maintains the name
  symlink; ops keep writing `users/<uuid>`.
- **What breaks:** nothing by itself; two names point at one home-🏠️ — stale
  symlink risk on rename, two write-paths to learn.
- **Feels like:** you get `~/xyzos/xyzfs/alice/avatar/` for humans *and* apps
  never change.

## 🧭 8. Recommendation

**Option B, plus §2 naming (`home-🏠️/`) and §3 pointer (`paths.pdl`), with the
local dev tree untouched.**

- B is the only option with *zero* change to the proven apps — which is exactly
  your constraint. Install v1 ships with login+avatar unchanged.
- The per-app dirs you asked for are fully delivered as `home-🏠️/<app>/`.
- The `alice/` naming is a **view** (Option C) — a symlink, cosmetic, added
  only after B is proven, never a blocker.
- The pointer (§3) is the insurance policy: names aren't set in stone; the
  mapping lives in one file. Today it points at the truth (`home`); tomorrow a
  rename or an Option A/B/C switch is a one-line change plus a short grep.
- Local dev: **not changed now.** The pointer and naming are conventions for
  install v1 + new code; the copied apps keep their current behavior.

**If you still want full A:** the honest cost is a one-time rework of the 6
userpal ops + a migration script. It's cheapest while v1 is only two apps — but
it directly violates the no-break constraint, and with the pointer in place,
A's human-readable view is already available via C's symlink.
