## 1. THE REAL, CONFIRMED, LIVE SYMPTOM

Real human testing (not synthetic), via `@.apps/text-editor-xyz`,
`bash button.sh run`, with a real DISPLAY set (real GLUT/GL window,
NOT `NO_GL=1` headless mode):

  - Typing into the editor's own INTERACT-engaged canvas doubles every
    character: typing "hi" lands as "hhii" in the real, rendered
    editor_buffer.txt content. Confirmed multiple times, by the actual
    user, via real GL-mode typing.
  - The SAME app, run headless (`NO_GL=1 bash button.sh run`, ASCII-
    only, no GL window at all) does NOT double. Confirmed both by the
    user's own direct statement and by my own synthetic (raw key-
    injection) testing, which never once reproduced doubling - always
    under NO_GL=1.
  - This is the ONE clean, reliable behavioral split to reason from:
    GL enabled -> doubles. GL disabled -> does not double. Whatever the
    real cause is, it is DIRECTLY tied to gl_mirror.c's own presence/
    activity, not something purely in the ASCII-mode-only code path.
  - Also reported, possibly related, possibly separate: file-menu's
    own GL widget "acting crazy" (real navigation/selection glitches)
    when running alongside the editor - not confirmed root-caused
    either.

## 2. HOW INPUT IS *SUPPOSED* TO FLOW (the real, intended architecture)

Two independent real capture sources can feed keystrokes into this
pipeline:

  A) `system/keyboard_input.c` - raw termios stdin capture, runs in
     the FOREGROUND (blocking) as the last step of a session launch.
     Real terminal window, real OS keyboard focus required to receive
     anything.
  B) `system/gl_mirror.c` - a real GLUT window, real OS keyboard focus
     required (GLUT's own `glutKeyboardFunc`/`keyboard()` callback
     structurally cannot fire without real X11 keyboard focus on that
     specific window - this is enforced by the X server itself, not a
     convention).

BOTH of these, when a key arrives, call their own local `append_key()`
which writes:
  1. `pieces/apps/player_app/history.txt` (bare decimal int per line -
     read by prisc+x's own `OP_READ_HISTORY` opcode elsewhere, not
     part of this bug's own path)
  2. `pieces/keyboard/history.txt` (`KEY_PRESSED: N` per line - this
     IS part of this bug's own path, read by `chtpm_parser_pal.c`)

`system/chtpm_parser_pal.c` (the real, shared, persistent parser/
engine - agy-txt/text-editor-xyz read `014.wsr-pal💸️📌️+2`'s own LIVE
copy directly, no local copy of their own) polls `pieces/keyboard/
history.txt` for new `KEY_PRESSED: N` lines. For a real `<button
onClick="INTERACT">`-engaged element (the editor canvas), its own
`process_key()` calls `inject_raw_key(eff)` - **this is supposed to be
the ONE place a real keystroke gets forwarded into `pieces/apps/
player_app/interact_relay.txt`**, which the PAL script's own
`read_history` opcode reads, dispatching into `agy_edit_key.c` (the
real op that owns the editor buffer and actually inserts the typed
character).

So the INTENDED, single, correct path for ONE real keystroke is:

  real keypress -> (keyboard_input.c OR gl_mirror.c, whichever has
  real OS focus - never both) -> pieces/keyboard/history.txt ->
  chtpm_parser_pal.c's own process_key() -> inject_raw_key(eff) ->
  pieces/apps/player_app/interact_relay.txt -> PAL script's own
  read_history -> agy_edit_key.c -> ONE character inserted.

Given real OS-level window focus is supposed to guarantee only ONE of
{keyboard_input.c, gl_mirror.c} ever receives a given real keystroke
at a time, and `pieces/keyboard/history.txt` is a single, shared file
BOTH of them write into using the identical format, `chtpm_parser_
pal.c`'s own read/relay logic should never see or process the same
logical keystroke twice under this design - REGARDLESS of which of
the two sources produced it. That is the real, intended contract. It
is currently being violated somehow when GL is active.

## 3. A REAL, ALREADY-KNOWN, ALREADY-DOCUMENTED CLASS OF THIS EXACT BUG

This exact symptom (GL-mode typing doubling in this exact app) was
ALREADY found and "fixed" once before, 2026-07-30 (one day before this
handoff) - see `!.xyzos-pitfalls+1.txt` PITFALL 63 and `!.xyzos-
standards+1.txt` §38 in THIS house copy (both still present, both
describe the SAME bug). The original fix added a
`pieces/system/gl_focus.lock` file, written by `gl_mirror.c`'s own
`update_focus_lock()` while it's alive, checked by `chtpm_parser_pal.
c`'s own INTERACT branch immediately before `inject_raw_key(eff)` -
skip the forward if the lock exists, on the theory that gl_mirror.c is
ALREADY independently delivering the same key via some other path.

**This check is STILL present in the code right now** (confirmed,
`chtpm_parser_pal.c` ~line 3548-3550: `int gl_owns_input =
(lock_path && access(lock_path, F_OK) == 0); ... if (!gl_owns_input)
inject_raw_key(eff);`) and the bug is STILL reproducing. So either:
  a) the lock file isn't being found/written correctly in the live
     session (a real path-resolution bug, worth re-verifying - see §5
     below for exactly what WAS checked), or
  b) the original 2026-07-30 diagnosis itself was incomplete/wrong
     (the lock check treats gl_mirror as "the other independent
     deliverer" but does NOT actually verify gl_mirror is writing
     into interact_relay.txt via any path anymore - see §4, this was
     REMOVED during this investigation), or
  c) something else entirely, not yet found.

## 5. A REAL, CONCRETE, NOT-YET-FULLY-CHASED-DOWN LEAD: transient,
   wrongly-scoped `gl_mirror` processes

During live process inspection (mid-investigation), a SECOND, real
`gl_mirror` process was caught running with the WRONG working
directory (the file-menu PROJECT ROOT, not its own session
subdirectory) and NO `PRISC_PROJECT_ROOT` env var set - meaning ITS
OWN `gl_focus.lock` file would be written to (and checked from) the
WRONG path entirely, breaking the whole lock mechanism's own
precondition for that specific instance. This exact process was
caught TWICE, in two separate fresh-launch tests, each time appearing
~16 seconds into the session's life (not immediately at launch) and
then dying on its own within roughly 20-30 seconds - i.e., a real,
reproducible, but TRANSIENT extra process, not a permanent competitor.

**This was never fully root-caused.** `grep -n "gl_mirror"` on file-
menu's own `button.sh` shows only ONE launch site (inside `run_widget_
session()`, correctly after `cd "$SESSION_DIR"` and after `export
PRISC_PROJECT_ROOT="$SESSION_DIR"` - so the SCRIPT'S OWN code looks
correct). Where this second, wrongly-scoped process actually comes
from (self-fork inside gl_mirror.c on some GLUT/X11 error/retry path?
a second invocation from somewhere else in the process tree? genuinely
just a slow-dying leftover from an earlier kill, coincidentally
timed?) was NOT determined. Real next step: catch this process the
INSTANT it appears (e.g., a tight polling loop checking `pgrep -f
system/gl_mirror` every 0.1s right after launch, logging PID+cwd+ppid
+full cmdline+lstart for every NEW pid seen) and trace its OWN parent
process chain to find where it's actually spawned from.
