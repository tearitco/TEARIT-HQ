REAL/CLASSIC CHTPM'S OWN ARCHITECTURE (confirmed via direct code read,
`pieces/chtpm/plugins/chtpm_parser.c`, and the TPMOS Bible's own
"Standalone Operational Architecture" section): ops are invoked
SYNCHRONOUSLY, per keypress - `fork()`/`exec()`/`waitpid()`, inside the
SAME `process_key()` call that will go on to render, BEFORE that
render happens. There is no second, independently-polling process for
this at all. State changes and rendering are strictly, causally
ordered: key -> op runs and finishes -> render. A plain marker file
("did the content change") is sufficient and reliable in that design
PRECISELY BECAUSE there is no second process racing against the first
one's own writes - the thing this family calls "change-based," not
"poll-based."

THIS FAMILY'S ONLY INTENTIONAL DEVIATION FROM THAT (see sec. 10's own
PAL-VS-C-ARCHITECTURE.txt): op LOGIC should increasingly run as real
PAL/prisc+x bytecode instead of hand-written C - a change of
EXECUTION VEHICLE for an op's own internal logic, NOT a change to WHEN
or HOW that op gets invoked. A pal-native op is still meant to be
invoked SYNCHRONOUSLY, per keypress, exactly like a real TPMOS C op -
`system/prisc+x pal/some_op.pal` as a ONE-SHOT process (fork/exec/wait,
same as any other op binary), not as a PERSISTENT process that outlives
a single keypress and polls a relay file on its own independent timer.

WHERE THE UNINTENTIONAL DRIFT ACTUALLY CAME FROM: the "interact +
module" pattern (sec. 7) genuinely DOES need something that stays alive
between keypresses - but only because mutaclsym's own `pal/game_loop.pal`
(now `main_loop_chtpm.pal`) was modeled as a copy of its own regular,
already-existing `main_loop.pal` - which is itself a real, persistent,
always-running VM loop, because THAT'S how mutaclsym's regular (non-chtpm)
"run" mode was ALWAYS structured (`system/prisc+x pal/main_loop.pal`,
one long-lived process for the whole session, reading history.txt in a
loop). Reusing that SAME persistent-process shape for the CHTPM-mode
variant was a copy-paste of convenience, not a deliberate decision that
mutaclsym (or ANY project in this family) genuinely needs a background
process ticking independently of user input. Nothing in this family is
real-time; every op should be triggered BY a keypress and FINISH before
the next render, exactly like real chtpm's own synchronous model.

THE ACTUAL BUGS THIS DRIFT CAUSED (all documented in more detail in
their own sections below, but ALL trace back to this one root cause -
a persistent module process racing chtpm_parser_pal's own render cycle
via two independently-timed poll loops instead of one synchronous
call-then-render sequence):
  - sec. 16.3 / this same day: a project's own compose op writing
    directly to `current_frame.txt` (to paper over the lag a
    persistent, asynchronous module introduces) clobbers chtpm's own
    chrome/`${piece_methods}` output for any project where the module
    runs on EVERY interaction, not just during a continuously-engaged
    INTERACT mode.
  - sec. 17: `system/renderer.c`/`chtpm_rgb_render.c` only watching one
    marker misses a module-driven recompose entirely, because the
    module's own update and chtpm's own reaction to it are two
    separate, asynchronously-timed events instead of one atomic
    sequence.
  - The user-reported "press Enter twice" / "Back doesn't navigate"
    symptoms - all instances of the SAME race: the module hasn't
    finished (or chtpm hasn't noticed it finished) by the time a render
    happens, because there was never a guarantee the two would be
    synchronized in the first place.

THE STANDING RULE, going forward: do not "fix" a race between chtpm's
own render cycle and a project's own module/op by tuning sleep
intervals, adding settle-loops, or dual-writing outputs to route around
the asynchrony (all of sec. 16.3/17's own fixes are exactly this kind
of patch, and are known to be incomplete/leaky, per this section).
Those are stopgaps on top of an architecture that should not exist in
this shape at all. For any NEW project (or when revisiting an existing
one), ask FIRST: does this project's own logic need to keep running
BETWEEN keypresses (an actual real-time tick - monster AI, a clock,
something with no key involved at all)? If NOT (true of every current
`${piece_methods}`-driven pure-menu project - wsr-pal, egg-pals), its
op(s) should be invoked SYNCHRONOUSLY per keypress (via chtpm's own
`OP:`/`SET_` command-dispatch conventions, matching real TPMOS's own
op-invocation model exactly - a one-shot process, not a persistent one
reached through a relay file), not modeled on mutaclsym's own
persistent-process shape just because that shape already existed
somewhere else in the family. A persistent module process is ONLY
justified for a project with a genuine, continuous, keypress-independent
tick - verify this explicitly, don't assume it by copying the pattern.

1. SHARED-OPS: genuinely project-agnostic ops are SHARED SOURCE, not
   re-typed per project
========================================================================

THE RULE: if an op has zero hardcoded game content and zero hardcoded
per-project constants (map ids, world names, game ids) - i.e. it would
behave identically no matter which project's PRISC_PROJECT_ROOT it's
pointed at - its SOURCE lives once, at
`2.muchi-verse/shared-ops/<name>.c`, and every consuming project's own
`scripts/build.sh` compiles that file directly into its own
`ops/+x/<name>.+x`. Runtime behavior is unaffected: `pal/main_loop.pal`
still calls `ops/+x/<name>.+x` exactly like any other op, and the op
still resolves `PRISC_PROJECT_ROOT` (and `PRISC_PROJECT_ID` where
relevant) at runtime the same way a private op would. The only thing
that moves is where the .c file lives - one file edited once, instead
of N copies that silently drift apart.

THE CORRECTION THIS RULE MAKES: this project family's older "one op =
one binary, no shared headers" convention was being over-applied to
mean "never share any op across projects, ever" - re-typing the same
logic into every new project's own ops/ directory, even when the logic
was already 100% generic. That was wrong. "No shared headers" was
always about not coupling files WITHIN one project via fragile
.h-based structs (still true, still followed - see §1a below) - it was
never a mandate to duplicate genuinely identical, project-agnostic
logic forever. The concrete tell this had gone too far:
muchipal-editor-0.0's own `ops/piece_viewer.c` (before this refactor)
had a header comment reading "Identical in shape to
mutaclsym/ops/pdl_reader.c's own parse_method_line() - intentionally
duplicated, not shared, per this project family's doctrine" while ALSO
describing itself as "the concrete proof of cross-project
compatibility this editor exists to establish" - a THIRD independent
retyping of the same parser, in a project whose whole purpose is
proving cross-project compatibility.

THE REAL PRECEDENT (not invented - confirmed by direct code reads):
real 1.TPMOS's own `projects/fuzz-op/manager/fuzz-op_manager.c` (line
716) calls `'%s/pieces/system/pdl/+x/pdl_reader.+x' %s list_methods` -
fuzz-op has no private pdl_reader copy of its own; it calls a SHARED
implementation living under `pieces/system/pdl/`, exactly the way
`pieces/system/` already hosts other shared infrastructure
(`input_dispatcher/`, `master_ledger/`'s `piece_manager.+x`, also
called directly from fuzz-op_manager.c). `pieces/system/emoji_extract/`
is likewise used by wraith-alpha AND was used directly, this same
session, for both mutaclsym's and zoo_0000's own asset generation.
op-ed's own README calls itself a "Thin Engine" - a genuine
multi-consumer engine, not a single-purpose game with private copies of
everything. The real structure being mirrored:
`projects/<name>/` = project-specific content + project-specific ops;
`pieces/system/<service>/` = shared, project-agnostic infrastructure
any project calls into via a path outside any single project's own
directory. `2.muchi-verse/shared-ops/` is this family's own equivalent
of `pieces/system/`.

§1a. WHAT "NO SHARED HEADERS" STILL MEANS (unchanged, not touched by
     this correction): don't couple files WITHIN a project via a
     shared `.h` defining structs both files reach into - that's still
     real, live doctrine (cdda-tpm-std-fast.txt sec. 1) and still
     followed by every project's own `scripts/build.sh` (each
     translation unit compiled and linked on its own line, no `.o`
     intermediaries). Sharing a whole, self-contained, project-agnostic
     .c file as SOURCE across projects is a completely different thing
     from that, and was never actually prohibited by the real
     precedent above.

§1b. THE BAR for "belongs in shared-ops/": zero hardcoded game content,
     zero hardcoded per-project constants. A hardcoded `#define MAP_ID`
     or `#define GAME_ID` is disqualifying UNTIL genericized (see
     `shared-ops-refactor-plan.txt` §2 for the real worked examples:
     `move_entity.c`/`xlector_input.c`/`pet_export.c`/`pet_import.c`
     all had this fixed by replacing the hardcoded constant with a
     dynamic `world_*/map_*/<piece_id>/` directory scan - the same
     pattern `pdl_reader.c`'s own `resolve_piece_pdl_path()` and real
     `system/prisc+x.c`'s own `resolve_piece_state_path()` already use
     - which is a strict improvement, not just a refactor, since it
     also removes any single-map-only assumption as a free side
     effect).

§1c. WHAT IS DELIBERATELY NOT SHARED, NAMED NOT SILENT (see
     `shared-ops-refactor-plan.txt` §3 for the full reasoning):
     - `compose_frame.c`/`compose_rgb_frame.c` per project - render
       genuinely different content per project. The font-glyph

     - Genuinely project-specific game content (e.g. zoo_0000's
       `feed_pet.c`/`pet_pet.c`/`play_pet.c` - mutaclsym has no pets;
       muchipal-editor isn't a game at all).

6. CHTPM-TO-PAL LAYOUT BRIDGE: real 1.TPMOS's own declarative UI
   markup, usable directly - a fork, not a rewrite
========================================================================
Full rationale, the empirical test that justified this, and the exact
patch sites: `chtpm-to-pal-layout-plan.txt` (its own "STATUS UPDATE"
section supersedes the modular-rewrite design further down that same
file - read the status update). Real 1.TPMOS's `.chtpm` declarative
layout format (`<panel>`/`<text>`/`<button onClick= href=>`, `${var}`
interpolation) is directly usable by any pal-native project via two
shared files - NOT a from-scratch reimplementation, and NOT the
5-op modular rewrite an earlier pass in this same doc proposed before
testing the real thing first.

- `shared-ops/chtpm_parser_pal.c` - a TRACKED FORK of real
  `chtpm_parser.c`, exactly 2 patches (search "PAL-NATIVE PATCH" in
  that file for each): (1) `is_modern_layout()` detects a pal-native
  project via the real `PRISC_PROJECT_ID` env var instead of guessing
  from the layout path's own substrings; (2) `inject_command()` routes
  onClick-dispatched commands to `pieces/display/pending_command.txt`
  instead of the file prisc+x's own `OP_READ_HISTORY` reads - a
  CRITICAL correctness fix (confirmed by reading `prisc+x.c` directly:
  a non-numeric line left in that file would permanently wedge that
  opcode's own read cursor, not just misread once). The file's own
  input-reading loop is untouched, still reads its real, native
  `pieces/keyboard/history.txt` in `KEY_PRESSED: N` format.
- `shared-ops/keyboard_input.c` - `append_key()` dual-writes: the
  original bare-int line to `pieces/apps/player_app/history.txt`
  (unchanged, zero risk to any pal script's own `read_history`) AND a
  second `KEY_PRESSED: N` line to `pieces/keyboard/history.txt` for
  `chtpm_parser_pal.c` to read. wsr-pal's own `keyboard_input.c` is NOT
  switched onto this shared file (it genuinely differs on quit-key
  handling - see §1c's own "don't force-share" principle) but got the
  identical dual-write addition applied locally instead.
- Runs as a PERSISTENT process (`system/chtpm_parser_pal`), same
  category as `system/renderer.c`/`system/gl_mirror.c`, NOT a one-shot
  op. Needs `-Wno-unused-result -Wno-stringop-truncation` on its own
  compile line only (~20 pre-existing real-upstream warnings, none
  touched by either patch - confirmed via test build this reaches zero
  warnings with those two flags; every other file in each project
  still builds under plain `-Wall -Wextra`).
- onClick verbs: `send_command()`'s real upstream code only relays a
  SPECIFIC recognized set of prefixes (`SET_*`, `OP:`, `MP3:`,
  `LAUNCH:`, `LOAD_PROJECT:`, `KEY:n`, `BACK`, `RELEASE`,
  `PROJECT_ACTION:`, `SETTINGS_PAGE:`, `PROJECT_PAGE:`) to
  `inject_command()` - anything else is silently rejected before ever
  reaching the pal-native redirect (hit this live: a `GOTO:projects`
  onClick was silently dropped until renamed to `SET_SCREEN:projects`,
  which matches the recognized `SET_` prefix). Pick a recognized prefix
  for any onClick a pal-native layout needs relayed.
- REAL, LIVE-CAUGHT PITFALL when converting an existing screen to
  chtpm and handing off to an existing pal-driven flow (as done for
  muchipal-editor-0.0's own title screen): prisc+x's own pal script
  always starts its `read_history` cursor at byte 0 on a fresh launch.
  Since `keyboard_input` dual-writes every keystroke unconditionally,
  any keys pressed during the chtpm phase are ALSO still sitting at the
  start of `pieces/apps/player_app/history.txt`, unconsumed by prisc+x -
  starting prisc+x without truncating that file first replays those
  same keystrokes into the pal-driven side the instant it launches,
  silently double-dispatching (confirmed live: a single '1'+Enter used
  to leave the chtpm title screen landed the pal-driven side two
  screens deep instead of one, because it replayed that exact
  keystroke itself). Always truncate `pieces/apps/player_app/history.txt`
  at the moment of handoff, right before launching the pal-driven
  process.
- WHAT'S NOT DONE YET, named: no dynamic-length screen (a project list,
  a piece list) has been converted - chtpm's own markup has no
  repeat/loop construct, so a screen whose row count varies at runtime
  needs a small generator step (analogous to `load_dynamic_methods()`'s
  own "build a var containing pre-formatted `<button>` HTML" trick) not
  yet built. `inject_raw_key()`'s pal-native behavior is also
  undecided (would `onClick="KEY:n"` double-dispatch through both
  prisc+x's own pal script and this process's own `process_key()`?) -
  flagged in the fork's own header comment, not silently assumed safe.

7. THE INTERACT + MODULE PATTERN (real game-map control handoff -
   direct user priority, "a big deal")
========================================================================
Full mechanism (exact real code, exact mapping onto this family):
`chtpm-to-pal-layout-plan.txt` §8. Summary: a layout's
`<module>${module_path}</module>` + `<interact src="...history.txt" />`
+ a button `onClick="INTERACT"` together let arrow/number keys pass
STRAIGHT THROUGH a live game (a SEPARATE, PARALLEL persistent process,
launched by `launch_module()`) instead of being consumed by chtpm's own
UI nav - this is how real fuzz-op/wraith-alpha put a real, controllable
game map inside a chtpm menu shell. Every piece of this already exists,
completely unpatched, in `shared-ops/chtpm_parser_pal.c` - nothing
about the fork itself needs to change again for this.

For a pal-native project, THE MODULE = a second `system/prisc+x`
process running that project's own real `pal/game_loop.pal` (not a
hand-written manager.c). THE VIEW BRIDGE = an additive dual-write in a
project's own EXISTING `compose_frame.c` (writes
`pieces/apps/player_app/view.txt` alongside its normal output), not a
new op. `module_path` gets set directly in
`pieces/apps/player_app/state.txt` (already read unconditionally) -
zero chtpm_parser_pal.c patch needed. `onClick="INTERACT"` (verbatim,
not `SET_`-prefixed) is what process_key() actually checks for this -
separate from and unrelated to the recognized-prefix gotcha in §6
above.

REAL BUG, LIVE-CAUGHT, CORRECTED (built and verified in zoo_0000,
2026-07-17 - full account: `chtpm-to-pal-layout-plan.txt` §8.4):
`<interact src>` must NEVER point at the same file
`shared-ops/keyboard_input.c` already writes to directly
(`pieces/apps/player_app/history.txt`) - that file already gets every
keystroke unconditionally, for the project's own regular "run" mode.
Relaying interact-mode keys into the SAME file double-dispatches every
one of them (confirmed live: 2 right+1 down moved the game 4 rights+2
downs). Fix: `<interact src>` points at a genuinely separate file
(`pieces/apps/player_app/interact_relay.txt`), and the module reads it
via `read_history`'s NEWLY-FIXED literal-path 3-arg form,
`read_history <path> xD, xS` - `shared-ops/prisc+x.c`'s own literal-path
parsing used to silently default the position register to x0 (reset to
0 every instruction by this VM's own main loop), permanently breaking
incremental reads; fixed, with every existing 2-register
`read_history xD, xS` call completely untouched.
`shared-ops/prisc+x.c` was moved here the same way `keyboard_input.c`
was (confirmed byte-identical across all 4 projects first) - a real VM
fix belongs in one place. A project's own regular `pal/main_loop.pal`
stays completely unmodified; a NEW, separate `pal/main_loop_chtpm.pal`
(identical except the one `read_history` line) is what the module
launches instead - zero risk to the already-proven gameplay path.

Built and live-verified in zoo_0000, mutaclsym, AND egg-pals
(`./button.sh chtpm`), full round-trip through the real playable
interface each time (full detail: chtpm-to-pal-layout-plan.txt §8.4-
8.5). egg-pals is a genuinely different case worth knowing about: purely
digit-menu-driven (no map/movement), and its own `prisc+x.c`/
`keyboard_input.c` are NOT switched to shared-ops (real Windows/MinGW
support + a documented bug fix neither shared version has) - the same
literal-path `read_history` bug was patched in its own local copy
directly instead, matching §1c's "genuinely different, patch locally"
principle. wsr-pal has the base bridge only, not yet the full
interact+module pattern.

8. KILL_ALL.SH: family-wide surgical process cleanup
========================================================================
Real incident, this session: a Ctrl+C'd mutaclsym session left a
genuinely orphaned `system/prisc+x` + `system/keyboard_input` pair
running, found only by accident via `ps aux` - not by any project's
own `button.sh kill` action (which had independently been matching an
absolute path that never appears in these processes' real, relative-
launched command lines - see [[feedback_pkill_relative_path_gotcha]]).
Per direct instruction ("maybe it should run a kill_all.sh script like
1.tpmos does") - confirmed real 1.TPMOS has exactly this precedent,
`pieces/os/kill_all.sh`, including its own past real incidents with
this same class of bug (`#.dev-storage/#.dox/cpu-issues_/
emergency_kill.sh`/`sanity_kill.sh`).

`2.muchi-verse/kill_all.sh` - modeled directly on real 1.TPMOS's own
file (same `surgical_kill()` shape, SIGKILL, a nuclear-option
catch-all fallback at the end). Family-wide, not per-project - every
pal-native project shares the same binary names now (mostly literally
the same shared-ops/ source), so one script here is callable from any
project's directory instead of five near-identical copies. Every
project's own `button.sh kill` action calls it (`bash
".../2.muchi-verse/kill_all.sh"`) as the authoritative cleanup step,
in addition to (not instead of) that project's own fast local
`pkill -f "system/<name>"` pass.

WHY SIGKILL, NOT PLAIN `kill`: `chtpm_parser_pal.c` registers a SIGINT
handler but no SIGTERM handler - a plain `kill` still terminates it via
SIGTERM's own default disposition, but skips its own `cleanup_module()`
(only runs on SIGINT), potentially orphaning its own spawned module.
`kill_all.sh` doesn't rely on any process's own signal handling running
cleanly at all.

9. TWO MORE REAL BUGS, USER-REPORTED, FOUND VIA DIRECT KEY INJECTION
========================================================================
Both found testing a live "unresponsive ascii, no GL window" report in
mutaclsym's own `chtpm` mode - full account:
`chtpm-to-pal-layout-plan.txt` §8.6-8.7.

9.1 THE MODULE MUST NOT OWN A QUIT PATH OF ITS OWN
------------------------------------------------------------------------
Every `main_loop_chtpm.pal` originally kept the real `main_loop.pal`'s
own `beq x2, x9, quit` ('q' halts). chtpm's own `onClick="INTERACT"`
relays EVERY key through while engaged - including 'q' - so pressing
'q' while controlling the hero/pets (reasonable, since 'q' IS the real
quit key in normal gameplay) halted the MODULE specifically, while
chtpm itself had no way to notice and kept relaying keys into a file
nothing was reading anymore. Fixed by removing the quit path from all
3 `main_loop_chtpm.pal` variants entirely - the module never owns
quitting; that's chtpm's job alone (top-level 'q', or
`system/keyboard_input`'s own unconditional exit-on-'q', which takes
the whole session down together regardless of chtpm's own internal
state).

9.2 `pieces/system/quit_flag.txt` MUST BE RESET, NOT JUST AT "run"'s
    OWN TOP
------------------------------------------------------------------------
`system/renderer.c`'s own loop is `while (!quit_requested())`, checking
whether this file is non-empty - written by `keyboard_input.c` on
EVERY exit, any session. Every project's own `run` action already
resets it at its own top, but the new `chtpm` actions (and, found in
the same pass, zoo_0000's own pre-existing `run` action) did NOT. Once
ANY session anywhere was ever quit via 'q', this file stays non-empty
forever - so the NEXT launch's own renderer sees
`quit_requested()==true` before its own loop even starts: it prints
exactly one frame (the unconditional `render_frame()` call before the
loop) and exits immediately. Everything else (`chtpm_parser_pal`, the
module, `keyboard_input`) keeps running fine underneath, correctly
updating `current_frame.txt` - but nothing is left to print it to the
terminal, giving the EXACT "looks unresponsive" symptom reported live.
Fixed by adding `: > pieces/system/quit_flag.txt` to every `chtpm`
action (and to zoo_0000's own `run` action, which never had it at
all).

9.3 THE TEST METHOD THAT ACTUALLY FOUND BOTH (direct user request -
    "include that test method in our standards doc, it works much
    better") - PREFER THIS OVER A FIFO-SIMULATED KEYBOARD
------------------------------------------------------------------------
Earlier live tests in this family drove input through a real
`system/keyboard_input` process fed via a named FIFO, simulating an
actual terminal. That works, but is genuinely flaky for single,
isolated bytes (confirmed repeatedly: a lone ESC byte needed 2-4
retries before `read_key()`'s own follow-up timeout reads registered
it) - real timing noise, not a logic bug, but it wastes real test
cycles and can mask or manufacture false negatives.

THE BETTER METHOD, matching real 1.TPMOS's own `inject_raw_key()`/
`inject_command()` naming and spirit: skip `keyboard_input` (and any
FIFO) entirely. Launch `system/renderer` and `system/chtpm_parser_pal`
directly, then INJECT KEYS BY WRITING DIRECTLY to whichever file the
next consumer reads - `pieces/keyboard/history.txt` with
`KEY_PRESSED: N` lines for chtpm's own top-level nav (exactly the
bytes `keyboard_input.c` would have written), or
`pieces/apps/player_app/interact_relay.txt` directly with a bare
integer if testing the module's own reading in isolation. This is
strictly more deterministic (a plain `echo "KEY_PRESSED: 1001" >>
pieces/keyboard/history.txt` either lands or it doesn't - no raw-tty
timeout window to race against) and is EXACTLY how this file's own §9.1
and §9.2 bugs were actually found and confirmed fixed: inject Enter,
check the frame; inject an arrow, check the real piece `state.txt`
changed by exactly one step; inject 'q' while "in control," confirm
the module process is STILL alive via `ps aux` afterward, then inject
another arrow and confirm it still responds. Prefer this method for any
future interact+module work in this family; reserve the FIFO/real-
keyboard_input method only for the rare case of testing
`keyboard_input.c` itself (its own escape-sequence decoding, raw-mode
handling, etc.) rather than what's downstream of it.

10. PAL VS. C - READ PAL-VS-C-ARCHITECTURE.txt BEFORE ASSUMING "OPS ARE
    ALWAYS C"
========================================================================

Every op today is a C binary (sec. 1's own convention) - but that is
the CURRENT STATE, not the permanent design. `prisc+x` is named after
RISC-V on purpose, and the real, confirmed direction is eventually
compiling pal+ops directly to real RISC-V, gated on the architecture
staying in reasonably correct shape. `shared-ops/prisc+x.c` now has a
real `ecall` syscall instruction (file I/O + a `SYS_GET_KV_INT`/
`SYS_SET_KV_INT` pair matching every op's own duplicated `read_kv_int`/
`set_kv_int` idiom), and a real op's core logic (`ops/pet_pet.c`'s own
state mutation) has been prototyped running as native pal instructions
against zoo_0000's own live data, verified working.

Full rationale, the ECALL design, and - most importantly - which
projects are the CONFIRMED first real-conversion targets (zoo_0000 and
muchipal-editor-0.0, per direct instruction) and which kinds of ops are
good/bad candidates: see `PAL-VS-C-ARCHITECTURE.txt` in this same
directory. Read it before assuming a new op has to be C, and before
assuming an existing C op is untouchable architecture rather than "not
converted yet."

========================================================================
11. GL/RGB RENDERING FOR CHTPM MODE - shared-ops/chtpm_rgb_render.c,
    real wraith-alpha's own two-stage pulse pattern, and the mistakes
    that cost a full day of user-reported "still doesn't look right"
========================================================================

Full account, all real bugs found via live testing (not guessed), all
fixed and re-verified: `!.handoff-july17.txt` sec. 1-9c. This section
is the durable, going-forward RULE version of that whole thread - read
it before touching `shared-ops/chtpm_rgb_render.c`, any project's own
`system/gl_mirror.c`, or `ops/compose_rgb_frame.c` again.

11.1 THE TWO-STAGE PULSE IS MANDATORY, NOT OPTIONAL
------------------------------------------------------------------------
A renderer that writes `pieces/display/rgb_frame.raw` must grow
`pieces/display/rgb_frame_changed.txt` (a fixed name, matching real
`wraith_gl.c`'s own `WRAITH_FRAME_TRIGGER` convention closely) ONLY
AFTER that write is fully complete - `system/gl_mirror.c` watches
ONLY this file, NEVER `pieces/display/frame_changed.txt` (the
UPSTREAM trigger a renderer itself reacts to). Confirmed via a live
checksum trace (compare `rgb_frame.receipt.txt`'s own checksum against
`gl_display.receipt.txt`'s loaded checksum, sampled every ~30ms
through a keypress burst) that using the SAME file for both causes a
real, PERMANENT stall - not a brief lag - because the GL reader can
"consume" the upstream trigger before the renderer has even started
its own work, and then has no further signal once real output is
ready. `ops/compose_rgb_frame.c` and `shared-ops/chtpm_rgb_render.c`
both already grow this file correctly - copy that shape for any new
renderer, don't reinvent.

11.2 WRITE rgb_frame.raw AND rgb_frame.receipt.txt ATOMICALLY
------------------------------------------------------------------------
`fopen(path, "wb")` truncates before writing - a reader polling
frequently (a daemon re-rendering ~60/sec, unlike `compose_rgb_frame.c`
which only writes on an actual keypress) can catch a torn read.
`system/gl_mirror.c`'s own `load_texture()` does a plain `fread()` with
no retry and zero-fills on a short read - confirmed via reproduction,
not assumed. Write to `<path>.tmp` then `rename()` into place -
`write_file_atomic()` in `shared-ops/chtpm_rgb_render.c` is the
reference implementation.

11.3 SETTLE BEFORE READING A SEPARATELY-WRITTEN INPUT FILE
------------------------------------------------------------------------
`chtpm_parser_pal.c` grows `frame_changed.txt` and writes
`current_frame.txt` as two unsynchronized writes - a renderer that
reads `current_frame.txt` the instant it sees the pulse move can catch
it mid-rewrite (confirmed live: a real torn read showing a MIX of old
and new footer text). Real `wraith_rgb_daemon.c` has NO protection
against this at all (checked directly - not something to copy from
there). Fix used here: after detecting the pulse changed, poll the
TARGET file's own size until it reads the same value twice in a row
(capped at ~20 attempts) before reading its content - a direct check
on the actual file being read, not a blind fixed delay on an unrelated
proxy file.

11.4 gl_mirror.c MUST READ frame_w/frame_h FROM THE RECEIPT, NEVER
     HARDCODE THEM
------------------------------------------------------------------------
Different renderers writing the SAME `rgb_frame.raw` path can have
genuinely different real dimensions (`ops/compose_rgb_frame.c`'s own
640x304 game-viewport size vs. `chtpm_rgb_render.c`'s own taller
640x768 real-chrome-content size) - `gl_mirror.c` reads `frame_w`/
`frame_h` from `rgb_frame.receipt.txt` before every texture load
(same pattern `shared-ops/dump_rgb_png.c` already used successfully),
reallocating its buffer and calling `glutReshapeWindow()` on a real
size change, so window pixels always map 1:1 to texture pixels. Do
not reintroduce hardcoded `WIDTH`/`HEIGHT` `#define`s here - that was
the root cause of a real, confirmed "bottom of the map cut off" bug.

11.5 TILE-SHAPED CONTENT RENDERS AT NATIVE PIXEL WIDTH, NOT A TEXT-
     COLUMN WIDTH
------------------------------------------------------------------------
A matched emoji/tile glyph blits at its own real `VOXEL_PX` (16px)
width with NO downscaling - plain ASCII chrome text still advances by
the narrower `GLYPH_W` (8px). `blit_text()` tracks a running PIXEL
x-position, not a fixed column count, for exactly this reason (mixed
widths on one line break a fixed-column model). Confirmed via direct
math this isn't arbitrary: `VIEWPORT_W(40) * TILE_PX(16) = 640 =
FRAME_W` exactly - a full map row already fits the frame perfectly at
native tile size. Downscaling tiles to fit a uniform 8px grid (an
earlier, wrong version of this file) visibly squishes every icon for
no reason - real wraith-alpha's own precedent is a variable
`emoji_glyph_size`, not one fixed width for everything.

11.6 REAL EMOJI/TILE COLORS COME FROM THE REGISTRY, NEVER A HASH
------------------------------------------------------------------------
`terrain_types.txt`/`furniture_types.txt` already carry a real,
curated `rgb_top_emoji` field - read it (plus `unicode` for the
reverse lookup) instead of inventing an arbitrary hashed color per
glyph. Items/monsters (`items.txt`/`monster_types.txt`) have no such
field - `chtpm_rgb_render.c`'s own `load_emoji_assets_from()` gives
them a neutral flat backdrop instead, real voxel pixel art
(`pieces/registry/emoji_assets/<asset_id>/voxels_16.csv`, ported
`load_emoji_voxels()`/`blit_emoji_tile()` directly from `ops/
compose_rgb_frame.c`) drawn on top either way. Hero (🧑) and xlector
(🎯) have no registry row at all (hardcoded chars in every project's
own `compose_frame.c`) - hardcoded color-table entries for these two
specific real emoji strings are safe (they never collide with
ordinary chrome text, unlike special-casing the literal ASCII letters
'@'/'X' would - chrome text DOES contain real letters like 'X', e.g.
"MUTACLSXM").  Only fall back to a hashed color for a genuinely
unrecognized glyph.

12. CHTPM-LEVEL MENU NAV MUST BE ${piece_methods}-DRIVEN, NOT A
    HARDCODED BUTTON LIST - the SAME rule as section 10's own PAL-VS-C
    doc, applied to layouts, not ops
========================================================================

A chtpm layout with only ONE navigable `<button>` (e.g. a bare
"Control Hero") makes arrow-key/digit menu nav LOOK broken even though
the underlying mechanism (`chtpm_parser_pal.c`'s own real, unmodified
`focus_index` nav) is completely correct - there's simply nothing to
move between. Real `fuzz-op_manager.c` (confirmed via a full, not
excerpted, read) has ZERO menu-cursor logic of its own at all - the

 14a. KEY 9 / ESC: UN-POSSESS AND EXIT INTERACT
 ========================================================================

 REAL BUG, LIVE-CAUGHT (mutaclsym, 2026-07-25): Key '9' was supposed to
 be the explicit un-possess key (matching xyzos-standards.txt §14's own
 "'9'/ESC/joystick button 8, checked FIRST, unconditionally" rule) but
 the handler was lost during a refactor — key '9' fell through as an
 unused digit in choice.c's is_digit branch, doing nothing.

 KEY 9: BIDIRECTIONAL TOGGLE (possess ↔ un-possess).
   - Interact mode (interact_mode==1): snap cursor TO hero position
     (xlector → hero, NOT hero → xlector), then auto-possess (exit
     interact). The cursor re-centers on the player before taking
     control, so you always possess from where the hero is.
   - Possess mode (interact_mode==0): un-possess → enter interact mode.
     Cursor appears at hero's current position.

 ESC: EXIT INTERACT INSTANTLY. Does nothing in possess mode.
   - Interact mode (interact_mode==1): exit interact immediately,
     back to nav. Cursor disappears.
   - Possess mode (interact_mode==0): no-op. Entity stays possessed.
     If player re-enters interact later (via key 9), cursor appears
     at hero's position with possession still active.

 KEY 9 vs ESC:
   - Key 9 toggles possess ↔ interact. Always works.
   - ESC only exits interact mode. Does nothing when possessing.
   - Neither key possesses directly (key 9 does via snap+possess,
     but only from interact mode).

16. INTERACT MODE IS ONLY FOR CONTINUOUS, FREE-FORM KEY RELAY (A REAL
    MAP) - A PURE DISCRETE MENU (NO MAP) SHOULD NEVER USE onClick=
    "INTERACT" AT ALL, USE ${piece_methods} INSTEAD (see sec. 12)
========================================================================

REAL MISTAKE, CORRECTED (egg-pals/wsr-pal, 2026-07-18): an earlier pass
copied mutaclsym's own `<button label="Control Hero" onClick="INTERACT"
/>` gate pattern wholesale into egg-pals ("Control Pets") and wsr-pal
("Control Sim") - projects with NO map/movement concept at all, purely
digit-menu-driven (Feed/Clean/Sleep, Buy/Sell/Financing, etc). This was
overzealous copy-paste, not a considered design choice, and produced a
real, user-visible symptom: a needless manual "engage" step before ANY
menu option could be selected, for a project where every action is
already a single discrete choice - INTERACT's entire reason to exist
(let raw keys stream continuously to a live game loop, bypassing
chtpm's own nav, for map/cursor movement - sec. 7) simply does not
apply.

THE FIX, confirmed against real `chtpm_parser.c`'s own `process_key()`
(pieces/chtpm/plugins/chtpm_parser.c ~2589-2880): nav-mode button clicks
(`active_index == -1`, arrows/digits move `focus_index`, Enter fires
`send_command(el->onClick)`) ALREADY relay through to the module via
`inject_raw_key()` -> whatever `<interact src>` names, with ZERO need
for `active_index` to ever leave -1. INTERACT (`active_index` set to the
button's own index, gating ALL subsequent keys into the module
regardless of nav) is a SEPARATE, ADDITIONAL mechanism needed ONLY when
raw keys must stream continuously without a discrete per-key dispatch -
i.e., real-time map/cursor movement. A pure menu needs NONE of that:
remove the INTERACT button/gate entirely, and drive 100% of the menu
via `${piece_methods}` (sec. 12) - real fuzz-op's own layout proves the
combination (piece_methods for discrete pet actions, a SEPARATE "Control
Map" INTERACT button ONLY for actual map movement) is the intended,
proven shape - never piece_methods OR interact alone as a blanket
default; pick per-mechanism based on whether continuous relay is
genuinely needed.

16.1 `${piece_methods}` REQUIRES project_id + active_target_id SEEDED
     BEFORE THE FIRST FRAME, NOT JUST ON THE FIRST KEYPRESS
------------------------------------------------------------------------
REAL BUG, LIVE-CAUGHT (wsr-pal): `load_dynamic_methods()` resolves via
`get_var("project_id")` + `get_var("active_target_id")`, both loaded
from `pieces/apps/player_app/state.txt`. A project's own menu-input op
(this family's `wsr_menu_input.c`-shaped ops) naturally only writes
these fields AFTER processing a keypress - but chtpm renders its FIRST
frame BEFORE any key has ever been pressed. `button.sh`'s own initial
`state.txt` write (alongside `module_path=...`) must ALSO seed
`project_id=<project>` and `active_target_id=<default_screen_piece_id>`
directly, or `${piece_methods}` renders empty on first launch.

16.2 KEY:n ENCODING BREAKS ABOVE 9 ITEMS - THE RECEIVING OP MUST TREAT
     EVERY INCOMING VALUE AS AN ALREADY-RESOLVED SELECTION, NEVER
     RE-ACCUMULATE IT
------------------------------------------------------------------------
REAL BUG, LIVE-CAUGHT (wsr-pal, 32-item menu): `send_command()`'s own
`KEY:` handling (confirmed via direct read, both real `chtpm_parser.c`
and the `chtpm_parser_pal.c` fork) is `if (k >= 0 && k <= 9)
inject_raw_key('0' + k); else inject_raw_key(k);` - indices 1-9 get
ASCII-digit-encoded (so they look like an ordinary typed keystroke to
older/simpler receivers), but 10+ is written as the BARE INTEGER, since
no single ASCII byte represents two digits. `inject_raw_key()` writes
that value verbatim (`"%d\n"`) to whatever `<interact src>` names either
way. This is NOT a partial keystroke to re-accumulate - chtpm's own
nav-mode `digit_accum` (typing "1" then "3" moves ITS OWN focus to item
13) ALREADY resolved the full multi-digit selection, entirely inside
`chtpm_parser_pal.c`, before Enter ever fired `send_command("KEY:13")`
as ONE event. A receiving op with its own pre-existing digit-accumulator
(built for raw multi-keystroke terminal typing, predating this project's
own chtpm conversion) will mishandle this: indices 1-9 happen to still
look like a normal ASCII digit (harmless), but 10+ either falls through
every check silently, or - worse - the specific values 10 and 13
collide with real ASCII LF/CR and misfire as a stale Enter.

THE FIX: collapse any such op's own digit-accumulation + separate-Enter
dispatch into ONE immediate-dispatch branch: `resolved_item = (key >=
'0' && key <= '9') ? key - '0' : (key > 9 && key < 1000) ? key : 0;`
then dispatch immediately if `1 <= resolved_item <= item_count` - no
accumulator, no waiting for a second event, since chtpm never sends one
for the same selection. (Upper bound `< 1000` avoids colliding with this
family's own `ARROW_UP`/`ARROW_DOWN` = 1002/1003 codes, which arrive
separately and should stay handled by whatever `is_up`/`is_down` check
already exists.) This makes the true ceiling on `${piece_methods}` menu
size whatever `MAX_MENU_ITEMS`/buffer limits the layout and receiving op
otherwise allow - not 9.

16.2a A SECOND, SEPARATE OFF-BY-ONE: `load_dynamic_methods()`'s OWN
      `method_idx` STARTS AT 2, NOT 1 - CHECK THIS EXPLICITLY WHENEVER
      ${piece_methods} IS THE *ONLY* CONTENT IN A LAYOUT (NO HAND-
      AUTHORED BUTTON BEFORE IT)
------------------------------------------------------------------------
REAL BUG, LIVE-CAUGHT (wsr-pal, confirmed via direct key injection per
sec. 9.3's own test method - not guessed): `load_dynamic_methods()`
(`shared-ops/chtpm_parser_pal.c` ~line 992) initializes `method_idx = 2`
for any non-"loader" `active_id` - it assumes nav slot 1 is ALWAYS
already occupied by a hand-authored button before `${piece_methods}`
(true for mutaclsym's own "Control Hero" - sec. 12's own worked example
places it first in the layout, `${piece_methods}` after). Once sec. 16's
own fix removes an unnecessary INTERACT gate/button entirely (a pure
menu with nothing before `${piece_methods}`), this hardcoded offset is
now WRONG for that layout: every generated `onClick="KEY:n"` is exactly
ONE HIGHER than the piece.pdl's own 1-based METHOD row order. Confirmed
live: the visually-13th menu row ("Financing") actually generates and
dispatches `KEY:14`, silently selecting row 14 ("Private", an unrelated
no-op) instead - the screen never appeared to navigate anywhere,
looking exactly like a dead button, not an off-by-one.

THE FIX: when `${piece_methods}` is the ONLY navigable content in a
layout (no other button occupies slot 1), the receiving op's own
`resolved_item` computation (16.2 above) must subtract 1 uniformly:
`resolved_item = (key >= '0' && key <= '9') ? (key - '0') - 1 : (key >
9 && key < 1000) ? key - 1 : 0;`. Both the ASCII-digit and raw-integer
forms carry the IDENTICAL +1 offset (it comes from `method_idx`, not
from either encoding), so the same `- 1` applies to both branches
uniformly. Do NOT assume this offset only affects large menus (>9) -
verify item 1 dispatches as expected too, since the shift applies to
every row equally.

VERIFY THIS EXPLICITLY, DON'T ASSUME, whenever wiring a NEW project
onto `${piece_methods}`: if the layout has a hand-authored button
before it (mutaclsym's shape), `method_idx=2`'s start is already
correct, no compensation needed. If `${piece_methods}` is the first and
only thing (a pure-menu project with the INTERACT gate removed per
sec. 16), the receiving op MUST compensate by 1, or every selection
silently fires the WRONG menu row - a symptom (looks like a dead/no-op
button) easy to misdiagnose as something else entirely.

16.4 PERSISTED MENU-NAVIGATION STATE MUST BE RESET ON EVERY LAUNCH,
     NEVER JUST ON A SEPARATE "new-game"-STYLE ACTION - A CLASS OF BUG,
     CHECK EVERY FIELD, NOT JUST THE ONE THAT GOT REPORTED
========================================================================
REAL BUG, USER-REPORTED (wsr-pal, "starts from last open menu ... make
sure this never happens again for any reason"): a project's own
menu-input op (`wsr_menu_input.c`-shaped) persists its CURRENT screen
(`active_menu_piece`) and nav position (`cursor`, `digit_accum`) to a
state file that ALSO holds real game progress (`turn_number`, `cash`,
`ticker_on`, `active_corp_index`) - by necessary design, since quitting
mid-session must not lose real progress. But `button.sh`'s own "run"
action only ever reset `pieces/apps/player_app/history.txt`/
`interact_relay.txt`/`quit_flag.txt`/`gl_focus.lock` (all SESSION-
mechanics files) - it never touched THIS file at all. Whatever screen
was showing at the exact moment of the LAST quit (via a working Back
button, a direct 'q', a crash, anything) is exactly where the NEXT
launch starts too, because "which screen" and "session progress" were
never actually treated as separate concerns in the reset logic, only in
the data model.

THE FIX: `button.sh`'s "run" action must reset EVERY navigation-position
field in this file (`active_menu_piece`, `cursor`, `digit_accum`,
`prompt_active` if present) to their fresh-launch defaults, via a
targeted `sed -i 's/^field=.*/field=default/'` per field - and must NOT
touch any REAL progress field (`turn_number`, `cash`, `ticker_on`,
`active_corp_index`, anything else representing actual game state) -
those must survive a restart, matching what the project's own separate
"new-game" action already does correctly for `active_menu_piece` alone
(a real, working precedent this fix generalizes, not invents).

THE STANDING RULE, general to any future project built this way: when a
single state file mixes "where am I" (navigation/UI position) with
"what happened" (real progress), the LAUNCH reset must enumerate and
reset every navigation field explicitly - do not assume resetting one
field (the one a bug report happened to name) covers the class. Audit
the WHOLE file's own field list against "is this navigation-position, or
real progress" every time a new field is added to it, and add it to the
launch-reset list if it's the former - a silently-added new nav field
later reintroduces this exact bug for that field specifically, even
after this fix.

marker, `pieces/display/frame_changed.txt`, and only re-reads/re-prints
`current_frame.txt` when THAT file's size grows. `chtpm_parser_pal.c`'s
own `process_key()` grows this marker on every KEYPRESS-driven
recompose - but a module-driven recompose (chtpm noticing
`active_target_id` changed via a relayed `GOTO:` command, reloading on
its own `state_changed.txt`-triggered path, sec. 16.1/16.2 - NOT
synchronous with the keypress that triggered it) does NOT also grow
`frame_changed.txt`. Confirmed via direct testing (sec. 9.3's own
method): the CORRECT, fully-populated `current_frame.txt` was already
sitting on disk the whole time this looked "stuck blank" -
`system/renderer.c` simply never knew to re-read it.

THE WRONG FIX THIS SECTION ORIGINALLY RECOMMENDED: also watch
`pieces/apps/player_app/state_changed.txt`. This "fixed" the stale-
submenu symptom but caused a DIFFERENT, real regression, found live in
mutaclsym after sec. 0's own synchronous-dispatch fix: a brief BLACK
FLASH on every INTERACT-mode keypress. Root cause: `state_changed.txt`
is grown by a PROJECT'S OWN compose op BEFORE chtpm has actually
reloaded/recomposed anything - it is a pre-trigger, not a completion
signal. For a project whose own module ALSO writes `current_frame.txt`
directly as part of the same op (mutaclsym's own `compose_frame.c`,
sec. 0.1/16.3's own dual-write pattern - correct and needed there),
that op grows `state_changed.txt` too - so watching it here caught the
module's own INTERMEDIATE, chrome-less write and rendered/displayed
THAT, before chtpm's own subsequent correction landed. Under the OLD,
asynchronous-module architecture this race window happened to be wide
enough to rarely matter for mutaclsym; sec. 0's own synchronous-
dispatch fix made the two writes happen close enough together in real
time that this renderer (now polling both markers at ~16ms) reliably
caught the intermediate one and displayed it as a visible flash.

THE REAL FIX: `chtpm_parser_pal.c`'s own internal `compose_frame()`
(shared-ops/chtpm_parser_pal.c ~line 2575 - NOT a project's own
`ops/compose_frame.c`, a same-named but different function inside the
parser itself) grows `pieces/display/renderer_pulse.txt`
UNCONDITIONALLY, every single time it runs - regardless of whether a
keypress or a `state_changed.txt`-triggered reload caused it. This is
the authoritative "the CORRECT, chrome-composed `current_frame.txt` is
ready" signal chtpm itself already emits, and it was sitting unused the
whole time. Watch THIS instead of `state_changed.txt`: it never fires
early, and it never fires for a project's own intermediate/direct write
- only for chtpm's own finished composition, regardless of what
triggered it. The existing settle-loop (current_frame.txt's own size
stable across 2 consecutive checks, sec. 11.3's pattern) still applies
identically on top of this marker.

APPLIES TO ANY PROJECT with a module that can change
`active_target_id`/trigger a `${piece_methods}` reload mid-session, AND
to any GL/RGB rendering daemon reading the same `current_frame.txt`
(`shared-ops/chtpm_rgb_render.c` got the identical fix) - audit for
this single-marker gap, but use `renderer_pulse.txt`, never
`state_changed.txt`, as the fix.

16.3 DUAL-WRITING current_frame.txt + view.txt IS CORRECT AND NEEDED -
     THE REAL RULE IS "DON'T LET THE TWO OUTPUTS VISUALLY CONFLICT,"
     NOT "ONLY CHTPM MAY EVER WRITE current_frame.txt" (CORRECTED
     ENTRY - the original version of this section, written same-day,
     had the wrong fix)
------------------------------------------------------------------------
REAL BUG, LIVE-CAUGHT (wsr-pal): a project's own compose op (called
every tick from `main_loop_chtpm.pal`'s own loop) writing
`pieces/display/current_frame.txt` DIRECTLY, in addition to
`pieces/apps/player_app/view.txt`, produced visible flicker/duplicate-
menu artifacts - `${piece_methods}` buttons and the op's own old
hand-drawn text menu both appeared, alternating.

THE WRONG FIX THIS SECTION ORIGINALLY RECOMMENDED: stop writing
`current_frame.txt` from the compose op entirely, relying solely on
`chtpm_parser_pal`'s own delayed, separate-process
`state_changed.txt`-triggered reload to eventually pick up
`view.txt`'s new content. This "fixed" the flicker but introduced a
DIFFERENT real bug, also live-caught: a perceptible one-keypress INPUT
LAG - the screen only reflects a keypress once chtpm's own loop
notices the marker grew on its OWN poll cycle, not the instant the
module's compose op finishes. Confirmed by direct comparison against
mutaclsym's own `ops/compose_frame.c`, which shows NO such lag and
ALSO writes `current_frame.txt` directly, on purpose (see that file's
own header comment, "REAL BUG FIX ... this used to fopen(out_path)
... write ... re-open ... to READ ... that read-back is a real race
... Fix: build the whole frame in memory (open_memstream) ... write
the SAME buffer to both current_frame.txt and view.txt directly,
in-process, with no read-back and therefore no race window at all").

THE ACTUAL RULE: the flicker's real cause was never "two writers of
current_frame.txt" - `chtpm_parser_pal` (a separate process) ALREADY
writes that file on its own render cycle in EVERY project using this
pattern, mutaclsym included, and always has. The real cause was this
compose op's own output CONTENT visibly conflicting with chtpm's own
composed frame (a hand-drawn text menu duplicate of what
`${piece_methods}` already renders as real buttons). Writing the SAME
data to both `current_frame.txt` and `view.txt` is not just safe, it's
NEEDED - it's what makes fresh state visible immediately, without
waiting on chtpm's own separate poll-and-reload cycle to catch up.

THE REAL, VERIFIED FIX: keep dual-writing both files from every render
call (mutaclsym's own open_memstream-then-fwrite-twice shape, or an
equivalent - e.g. two `FILE*` targets written in parallel from the
same call sites, confirmed working). Just make sure whatever gets
written is something chtpm's own LATER recompose (from the SAME
underlying data, once its own marker check fires) will be consistent
with - i.e., don't hand-draw a numbered menu list a `${piece_methods}`
placeholder elsewhere in the layout already renders as real buttons.
Status/banner/message content (turn count, cash, wallet, etc.) is safe
to write to both outputs identically; menu-navigation UI is not, once
chtpm owns rendering it natively.

18. SWITCHING BETWEEN SCREENS MUST BE REAL `href`, ONE `.chtpm` FILE PER
    SCREEN - NOT A CUSTOM "GOTO:" STRING THAT SWAPS WHICH piece.pdl A
    SINGLE SHARED LAYOUT POINTS AT (DRIFT, CONFIRMED - wsr-pal)
========================================================================
Think of it like HTML: each screen is its own page (its own `.chtpm`
file), and a link between two screens is a real `<button href="...">`
- NOT a piece of app state that tells one page to pretend to be a
different page. Real chtpm/wraith-alpha has always worked this way -
confirmed by directly reading real wraith-alpha's own
`settings.chtpm`: `<button label="Back to Wraith Desktop"
href="projects/wraith-alpha/layouts/alpha-shell.chtpm" />`. chtpm's own
`process_key()` (`shared-ops/chtpm_parser_pal.c`, the `strlen(el->href)
> 0` branch) already handles the ENTIRE transition natively and
synchronously - sets `current_layout`, calls `parse_chtm()`,
`initialize_focus()`, `export_active_index()`, `compose_frame()` - zero
custom state, zero extra C code, one proven code path shared by every
screen transition in the whole family.

Section 12 (`${piece_methods}`) and this section are NOT the same
concern and do not replace each other: §12 is about rendering ONE
screen's OWN action list (a single piece's METHOD rows, still correct,
still keep using it); this section is about moving to a DIFFERENT
screen entirely. Confusing the two - building the multi-screen jump out
of the same machinery meant for a single screen's own button list - is
exactly the mistake below.

THE DRIFT, CONFIRMED (wsr-pal): every one of its 6 menu "screens"
(`wsr_main_menu`, `wsr_trade_menu`, `wsr_management_menu`,
`wsr_search_menu`, `wsr_derivatives_menu`, `wsr_financing_menu`) is
really just ONE `.chtpm` file (`pieces/chtpm/layouts/wsr.chtpm`) with a
single `${piece_methods}` placeholder. "Switching screens" means a
METHOD row's command is the string `GOTO:<piece_id>`, hand-parsed by
`wsr_menu_input.c`, which overwrites an `active_menu_piece` app-state
variable so `${piece_methods}` starts reading a DIFFERENT piece's own
`piece.pdl` on the next render - the same physical layout file,
pretending to be six different pages. This is a hand-rolled
reimplementation of exactly what `href` already does for free, built
before this correction existed - the SAME category of unintentional
architectural drift named in section 0 (this family's only deliberate
deviation from classic chtpm is "use more pal," never "reinvent a
mechanism chtpm already has natively").

CONCRETE DAMAGE THIS DRIFT CAUSED, VERIFIED (not theoretical): 3 of the
6 `piece.pdl` files (`wsr_management_menu`, `wsr_derivatives_menu`,
`wsr_financing_menu`) were authored with a 4-field METHOD row
(`METHOD | N | label | command`) while the other 3 use the real 3-field
format (`METHOD | label | command`). BOTH parsers that read these rows
(chtpm's own `load_dynamic_methods()` AND `wsr_menu_input.c`'s own
`load_menu_items()`) split on exactly the first two `|` characters -
confirmed by replicating the exact C split logic: on a 4-field row, the
"command" field ends up as `"8.Back to main menu | GOTO:wsr_main_menu"`
(the real label text plus a stray leftover pipe), which does not match
`GOTO:`/`RUN:`/`STUB`/anything - so EVERY button on those 3 screens
silently no-ops (shelled as a bogus literal command), not just Back.
This is the direct, likely explanation for this session's own
inconclusively-reproduced "Back doesn't work for wsr-pal" reports - a
custom hand-rolled format with no schema, drifting out of sync with
itself, exactly the kind of bug a proven native mechanism (a real
`.chtpm` file per screen, hand-authored, no row-format to get wrong)
does not have room for in the first place.

THE FIX (not yet done - named here so it isn't lost): split
`wsr.chtpm` into one real `.chtpm` file per screen (mirroring each
existing `piece.pdl`'s own content), with every `GOTO:<piece_id>` row
becoming a real `<button label="..." href="pieces/chtpm/layouts/
<piece_id>.chtpm" />` and every real action row becoming whatever
`onClick` prefix `send_command()` already recognizes (`OP:`, etc. -
see section 6's own reserved-prefix list). This retires
`wsr_menu_input.c`'s entire `GOTO:` dispatch branch, the
`active_menu_piece` app-state variable, and the piece.pdl-as-menu-
source indirection for NAVIGATION specifically (a piece.pdl can still
be kept as data for other purposes if still needed) - collapsing it
into the same one proven code path every other screen transition in
this family already uses.

19. HREF NAVIGATION MUST KILL+REAP THE OLD PERSISTENT MODULE BEFORE
    LAUNCHING A NEW ONE - A BARE current_module_pid RESET LEAKS A LIVE,
    RACING DUPLICATE (REAL BUG, LIVE-CAUGHT - pal-chain, 2026-07-19)
========================================================================
Any project using §18's own real href+persistent-`<module>` pattern
(this whole family's own norm now) has EVERY screen name the SAME
`<module>` command (e.g. `system/prisc+x pal/main_loop_chtpm.pal`) -
that's the whole point, one persistent loop survives every screen
switch via `launch_module()`'s own liveness check
(`current_module_pid > 0`, restored earlier this session - see this
file's own git history / HANDOFF docs for that fix).

THE BUG: `process_key()`'s own href branch (and the `LOAD_PROJECT:`
handler, same shape) used to reset `current_module_pid = 0;` and
`current_module_path[0] = '\0';` DIRECTLY, without ever checking
whether that pid actually named a still-alive process, let alone
killing it. Since every screen names the identical module command,
`launch_module()`'s own liveness guard was blinded (it can only refuse
a duplicate launch if it still remembers the old pid) and happily
forked ANOTHER instance on every single href click - confirmed live via
`ps aux` showing TWO `prisc+x pal/main_loop_chtpm.pal` processes after
exactly one navigation. Both instances then read the same
`interact_relay.txt` and read-modify-write the same project state.txt
concurrently, an unordered race that visibly corrupted state (a 7-field
state.txt collapsed to 1 surviving field after one click).

THE FIX (`shared-ops/chtpm_parser_pal.c`, already applied and re-synced
to every consumer as of 2026-07-19): both call sites now route through
`cleanup_module()` (a real kill+reap, already existed but was
previously called only from `handle_sigint()` on process exit) instead
of a bare variable reset. `cleanup_module()` itself also needed a fix -
its own `waitpid(pid, NULL, WNOHANG)` returned immediately regardless
of whether the just-SIGTERM'd process had actually exited yet, leaving
a `<defunct>` zombie behind every href click even after the kill itself
started working; changed to a blocking `waitpid(pid, NULL, 0)` (safe
here - it's a bounded wait on a process this same code just signaled
to shut down, not an open-ended wait on unrelated work).

VERIFICATION BAR: after any href click (or any code path that reassigns
`current_module_path`), `ps aux | grep prisc+x` (or the project's own
module binary name) must show EXACTLY ONE live process for that
project, no `<defunct>` entries accumulating - confirmed live for
pal-chain across a login -> signup -> wallet_main -> send_screen ->
mining_status navigation chain.

20. ONE VISIBLE FRAME WRITER RULE - AN OP MUST NEVER WRITE
    pieces/display/current_frame.txt DIRECTLY; chtpm_parser_pal.c's OWN
    compose_frame() IS THE SOLE WRITER (REAL, USER-REPORTED FLICKER,
    FOUND+FIXED - pal-chain, 2026-07-19)
========================================================================
Real 1.TPMOS precedent, ALREADY NAMED, not reinvented here: see
`1.TPMOS_c_+rmmp.0102.0028/!.gem-flashlite--yolo/#.docs/^.pmo.ld-faq+8/
PITFALLS_ACTIVE_2026-03-18.txt` #17 ("ONE WRITER RULE - current_frame.txt
must have a single owner/writer... Dual writers cause flicker/
corruption and nondeterministic behavior") and #36 ("ONE VISIBLE FRAME
WRITER RULE... only one component should own the user-visible current
frame... state files advance, visible frame lags, debugging becomes
misleading"). Read that whole file before touching ANY render/compose
op in this family - it is real, hard-won TPMOS institutional knowledge,
not project-specific advice, and this section exists only to record
where THIS family concretely violated it and how that was confirmed
and fixed, not to replace reading the source doc.

THE VIOLATION: `wsr_compose_frame.c` (and, copied from it verbatim,
pal-chain's own `chain_compose_frame.c`) wrote BOTH
`pieces/display/current_frame.txt` AND `pieces/apps/player_app/view.txt`
directly from the same in-memory buffer, justified by that file's own
(WRONG, checked directly against `chtpm_parser_pal.c`) header comment:
"writes BOTH... so a keypress's effect is visible immediately rather
than waiting on chtpm's own separate poll cycle." There is no such lag
to work around: `process_key()` already appends to
`pieces/display/frame_changed.txt` on EVERY keystroke unconditionally,
and the main loop's own dirty-marker check picks that up and calls the
parser's OWN `compose_frame()` (which reads `view.txt` via
`${game_map}` and writes `current_frame.txt` itself) on the very next
loop iteration - the two writes were never actually racing to be
"first," they were both writing the SAME file on every single
keystroke, and a renderer polling that file could catch either one
mid-transition. Confirmed live (user-reported): visible flicker while
navigating/typing in pal-chain's real cli_io-driven login screen.

THE FIX: the op's own compose step (`chain_compose_frame.c`, and any
future project's own equivalent) must write ONLY
`pieces/apps/player_app/view.txt` (plus whatever real marker file it
already pings to prompt a `load_vars()` reload - `state_changed.txt`
here) and NEVER open `pieces/display/current_frame.txt` for writing at
all. `chtpm_parser_pal.c`'s own `compose_frame()` remains the sole
writer of that file, exactly as pitfalls #17/#36 require. Any project
still doing the dual-write (wsr-pal's own `wsr_compose_frame.c` has not
been re-checked/fixed as of this writing - flagged here, not yet
verified) should be treated as carrying the same live bug until
confirmed otherwise.

21. THE ACTIVE-TARGET INDIRECTION PATTERN - HOW A PER-INSTANCE PAL OP
    (act on "whichever pet/piece is currently selected") WORKS AROUND
    prisc+x HAVING NO ARGV-INTO-A-LAUNCHED-SCRIPT MECHANISM (muchi-pals,
    2026-07-19, direct instruction: "this is a simple project, perfect
    place to use pal as much as possible")
========================================================================
Written per direct instruction, to solidify a reusable family-wide
pattern rather than a one-off hack local to one project - any future
project needing a pal op that acts on "whichever entity is currently
selected" (not a fixed, single target like an owner's own wallet/user
state) should use this, not reinvent it.

21.1 THE REAL BLOCKER, CONFIRMED BY DIRECT CODE READ, NOT ASSUMED
------------------------------------------------------------------------
`ecall`'s own path/key arguments (`SYS_OPEN`, `SYS_GET_KV_INT`,
`SYS_SET_KV_INT`) are COMPILE-TIME LITERALS baked into the instruction
stream at parse time (`i->literal_arg`/`i->literal_arg2`) - a `.pal`
script cannot compute or receive a path at runtime, only reference one
already written into its own source text. Separately, `main(int argc,
char **argv)` (confirmed by direct read, both `system/prisc+x.c` here
and `shared-ops/prisc+x.c`) only ever recognizes 4 argv positions -
`<prog> [mem_in] [mem_out] [ops_file]` - there is no argv[5]-into-a-
register convention, exactly as PAL-VS-C-ARCHITECTURE.txt sec.6 already
named as a real, still-open blocker. Together this means a general
`toggle_sleep.pal <pet_id>` - the direct pal-native equivalent of
`ops/toggle_sleep.c`'s own `argv[1]` - literally cannot be written today;
the only precedent (`z0.zoo_0000/pal/ops_native/pet_pet_prototype.pal`)
sidesteps this by hardcoding a single pet (`pet_mochi`) and says so
plainly in its own header comment.

21.2 THE PATTERN: A FIXED SCRATCH FILE STANDS IN FOR "THE ARGUMENT"
------------------------------------------------------------------------
One well-known, fixed path - `pieces/system/active_target.txt` - is
what every per-instance pal op's own `ecall` literal always names.
Whatever C op already knows which real piece is "current" (this
family's own dispatcher shape - `chain_menu_input.c`'s own
`get_current_piece_id()`, or a project's own equivalent tracking
`selected_pet`/`active_target_id`) does three things around invoking
such a pal op, all plain file I/O ("communicate via files, as usual" -
direct instruction, matching this whole family's own "if it's not in a
file, it's a lie" doctrine already applied everywhere else):
  1. COPY IN: read the real piece's own `state.txt`, write JUST the
     key(s) the pal op actually touches into
     `pieces/system/active_target.txt` (not the whole file - keep the
     scratch file narrow and disposable, not a shadow copy of the whole
     piece).
  2. RUN: `system/prisc+x pal/ops_native/<op>.pal` (a plain child
     process, synchronous - this family's whole architecture is
     already "dispatch, run to completion, then compose," sec.
     0-CORRECTED - no new concurrency concern here since dispatch is
     strictly serial per keypress).
  3. COPY OUT: read the (now-mutated) key(s) back out of
     `active_target.txt`, write them into the REAL piece's own
     `state.txt` (preserving every other line, same `read-all/rewrite-
     one-key` idiom every op in this family already uses), then
     truncate `active_target.txt` back to empty - it is a disposable
     scratch, never a piece of its own, never left holding stale data
     between actions.

This keeps the actual DECISION/MUTATION genuinely in pal - `asleep = !
asleep`, `poop_count = 0`, the token-deduct + hunger-clamp math - not
just a thin pal wrapper around a C op that does the real work. The C
side's job shrinks to pure file-addressing ("which real piece does
'active_target.txt' currently alias") - the "sys call" part of the
system, matching the direct framing this pattern was built under: "the
spirit of pal is to be easier than c programming so the user can edit
it and drag and drop ops... all the hard stuff is under the hood in
ops" - kernel/file-IO/GL-touching concerns (opening a pet's GL window,
generating a PNG trading card, scanning a skill registry) stay real C
"sys" ops; the actual per-instance gameplay RULES move to pal.

21.3 RESULT MESSAGES ARE BUILT IN C, AFTER THE PAL OP RETURNS - NOT
     INSIDE THE PAL SCRIPT ITSELF
------------------------------------------------------------------------
`SYS_WRITE_LINE` takes a compile-time literal string too (same
limitation as sec.21.1) - a pal script cannot construct "Claimed 10
tokens! Balance: 47" with a live number spliced in the way a C op's
`printf` can. Don't fight this: the dispatcher already read the
BEFORE value during copy-in and reads the AFTER value during copy-out,
in plain C - it builds the real user-facing message itself from those
two known-good integers once the pal op has finished, instead of
asking the pal op to report on itself. This is an honest division (pal
owns the mutation, C owns describing it to the player), not a
workaround hiding a gap.

21.4 WHAT THIS PATTERN IS NOT FOR
------------------------------------------------------------------------
Don't reach for this when the target is already fixed/singular (a
project's own single wallet/user state, matching how `claim_tokens.pal`
and `coin_flip.pal` operate directly on `pieces/world_01/map_lobby/
user_01/state.txt` with no indirection at all - there is only ever one,
its path never varies, so there's nothing to indirect). Only use
`active_target.txt` when the SAME op must apply to different real
pieces depending on what the player selected.

21.5 RANDOMNESS: NO NEW SYSCALL NEEDED - THE DISPATCHER SEEDS IT INTO
     THE SCRATCH FILE, LIKE ANY OTHER PRE-COMPUTED VALUE A PAL OP CAN'T
     DERIVE ITSELF (REVISED - an earlier draft of this section added a
     new `SYS_RANDOM` ecall instruction; reverted per direct feedback
     before it shipped, see below)
------------------------------------------------------------------------
`coin_flip.pal` needs a random bit, which `ecall`'s table has no
primitive for. The first draft of this pattern grew the syscall table
(`SYS_RANDOM`) to cover it - technically legitimate per
PAL-VS-C-ARCHITECTURE.txt sec.4's own "extend ecall when a genuinely
good candidate needs a syscall the table doesn't have," but overkill
here: direct user question, "cant it be done as an op that gives arg
io? or is that something else?", surfaced a real, already-available
path that needs ZERO VM changes at all.

Checked directly (not assumed): an ordinary custom-op call from a
`.pal` script (`generate_egg`, `tick_pets`, any bareword call) runs a
C binary and only ever ECHOES its stdout back through - `exec_custom_op`
never writes a called op's result into a register (`regs[i->rd] =
...` appears exactly ONCE in the whole file, inside a special-cased
`layout_op` branch unrelated to this). So a plain custom op genuinely
CANNOT hand a value back to the calling script through the CALL itself
- but sec.21.2's own indirection file is already the answer: the C
dispatcher that already does copy-in/copy-out around every
`active_target.txt`-based pal op can, for `coin_flip.pal` specifically,
generate the random bit ITSELF (plain C `rand()`, same as
`ops/coin_flip.c` always did) and write it into the scratch file as a
normal key BEFORE launching the pal script - which reads it back with
the ALREADY-EXISTING `SYS_GET_KV_INT` ecall, no new syscall, no VM
core change, same file-handoff shape as every other value crossing the
C/pal boundary in this pattern. `system/prisc+x.c` is unmodified by
this pattern entirely - not just "reverted," never actually needed a
core change in the first place once the file-handoff option was
considered.

22. THE REFACTOR STANDARD - HOW TO REFACTOR ANY PROJECT'S INPUT/RENDER
    MECHANISM (folded in from the former standalone PAL-REFACTOR-
    STANDARD.txt, 2026-07-19 - THIS FILE IS THE ONE DEFINITIVE PAL
    STANDARDS DOC, direct user instruction: "there should be one
    definative pal std document. use that one" - do not start a second
    standalone standards file again; add a numbered section here
    instead)
========================================================================
Written after a same-day refactor attempt (egg-pals' own menu, redone
to look like pal-chain's own UI) violated nearly every rule below and
had to be rolled back by the user. Read this BEFORE touching any
project's own input/render layer, not after.

22.0 THE ONE RULE EVERYTHING ELSE FOLLOWS FROM: A REFACTOR CHANGES HOW,
     NEVER WHAT
------------------------------------------------------------------------
"Refactor project X to use chtpm like wsr-pal/pal-chain" means: replace
the MECHANISM (how a keypress reaches an action, how a screen change
happens) with a proven, real one. It does NOT mean: redesign the
screens, rename anything, change wording, split or merge menus
differently, add new steps, or remove features you didn't fully trace
through first.

If you cannot point to the EXACT existing line of C code (or piece.pdl
row, or chtpm markup) that already produces a given screen/label/flow,
you do not have permission to invent a replacement for it - go find the
real line first. A refactor with a byte-for-byte identical user-visible
result (same screens, same wording, same option order, same messages)
and a completely different internal mechanism is a SUCCESSFUL refactor.
A refactor that "improves" wording or restructures screens along the
way is not a refactor - it's a rewrite wearing a refactor's name, and
it will be rejected, because nobody asked for new behavior, just a
sturdier way to produce the OLD behavior.

22.1 BEFORE WRITING ANY NEW CODE: EXTRACT GROUND TRUTH FROM THE REAL,
     CURRENT SOURCE - NEVER FROM MEMORY, A SUMMARY, OR A SIMILAR PROJECT
------------------------------------------------------------------------
Read the actual input-dispatch op and the actual render/compose op for
the project being refactored, in full, before writing a single line of
new code. Extract and write down (in your own scratch notes, not
guessed while coding):
  - Every screen name, in the exact order the code checks them.
  - Every option's exact label text, exact position/number, and exact
    resulting action (which op it shells out to, with which args).
  - Every navigation rule (which key goes where, any global shortcuts
    like a "back to main" key, any special-cased keys like quit).
  - Every piece of live data displayed (a token count, a stat, a status
    line) and exactly which file/field it's read from.

If a similar, already-refactored sibling project exists (e.g. wsr-pal
when refactoring egg-pals), it is a reference for the MECHANISM only -
its own screen names, wording, and menu structure belong to ITS OWN
game and must never leak into the project actually being refactored.
Copying a sibling's shape is right; copying its content is a mistake
that produces a different game, not a refactored one.

22.2 VERIFY THE MECHANISM AGAINST THE REAL REFERENCE SOURCE, NOT AGAINST
     AN EARLIER PASS'S OWN COMMENTS OR ASSUMPTIONS
------------------------------------------------------------------------
This family's own docs have, more than once, stated something as "how
real chtpm/fuzz-op works" that turned out to be wrong when someone
actually re-read the real reference source
(1.TPMOS_c_+rmmp.0102.0028/pieces/chtpm/plugins/chtpm_parser.c and
projects/fuzz-op/manager/fuzz-op_manager.c). A confidently-worded
comment citing "real chtpm's own architecture" is a CLAIM, not a
citation, until you've opened the actual file and the actual line
yourself. Before relying on any such claim (especially ones governing
blocking/non-blocking behavior, synchronous vs. async dispatch, or
which process does what), re-verify it directly. If it conflicts with
what you find, the real source wins, and the stale doc gets corrected
in place (marked superseded, not silently deleted - the record of what
was wrong and why it looked plausible has its own value for the next
person).

22.3 THE REAL MECHANISM, IN ORDER OF PREFERENCE
------------------------------------------------------------------------
  a. Real `href` between screens - each screen is its own `.chtpm` file;
     switching screens is a literal `<button href="...">`, handled
     entirely inside `chtpm_parser_pal.c`'s own `process_key()`. Zero
     custom code for navigation.
  b. Real `${piece_methods}` for a screen's own numbered action list -
     reads that screen's own `piece.pdl` METHOD rows, generates real
     `onClick="KEY:n"` buttons automatically. A dynamic-length list
     (a variable number of rows depending on live data) is handled by
     regenerating that one screen's own `piece.pdl` file before each
     render, not by hand-drawing a cursor over static markup.
  c. A persistent `<module>` process (`prisc+x` running a real,
     LOOPING pal script) is the correct, intended shape for dispatching
     those `KEY:n` actions to real one-shot ops and re-composing - this
     is NOT something to convert to a one-shot script "to match real
     chtpm." Real chtpm's own reference project (fuzz-op) is ALSO a
     persistent daemon with its own independent poll loop; a
     one-shot-per-keypress model is not the real pattern.
  d. Real, hand-authored `<cli_io target_id="...">` elements for any
     genuine free-text entry (a name, a password, an amount) - chtpm
     buffers those keystrokes entirely inside its own process; no
     module round-trip needed per keystroke.
  e. `onClick="INTERACT"` ONLY for genuinely continuous, free-form key
     relay with no discrete per-key dispatch possible any other way -
     real-time map/cursor movement, essentially. A pure, discrete menu
     (every action is a single numbered choice) should NEVER use
     INTERACT - use (b) instead. When INTERACT genuinely is needed, its
     own dispatch must be plain, fire-and-forget (matching real
     `chtpm_parser.c`'s own `inject_raw_key()` exactly) - never a
     blocking call that waits for the module to finish, which hangs
     the instant the module is (correctly) a persistent loop rather
     than a one-shot script.

22.4 DO THE CUTOVER CLEANLY - NEVER LEAVE TWO PARALLEL SYSTEMS HALF-WIRED
------------------------------------------------------------------------
A refactor is either fully done or not started - there is no safe
middle state where an old entry point and a new one both exist,
pointing at shared files (the same persistent module script, the same
default_op.txt) that only one of them was actually updated for. If a
new op/layout set needs to coexist temporarily with the old one for
testing, they must not share any mutable file the old system also
reads or writes (a shared `<module>` pal script rewired for the new
op names will silently break the old system's own entry point the
moment anything still points at it). Verify old and new don't collide
BEFORE building the new one, not after something breaks.

If you cannot complete a full cutover in one pass, stop at a clean
boundary (all old files untouched and still fully functional) and
hand off what's left as a written, explicit next step - do not leave a
half-migrated project as the working tree's default state.

22.5 VERIFY LIVE, END TO END, AGAINST THE REAL ORIGINAL - NOT A SPOT
     CHECK
------------------------------------------------------------------------
Before considering a refactor done:
  - Launch the refactored version and the original (or a frozen,
    known-good baseline copy of it) side by side if one exists.
  - Walk every screen, every option, in the same order, via real key
    injection (append `KEY_PRESSED: N` lines to the actual keyboard
    history file the parser reads, matching real keystroke timing -
    not a direct op invocation that bypasses the parser, which proves
    the op works but not that the UI wiring does).
  - Confirm the rendered text is IDENTICAL where it should be
    identical (same screen titles, same option wording, same live data
    format) - a visual diff, not "looks about right."
  - Confirm process hygiene: exactly one live process for the module
    after any number of screen switches (no leaked/duplicate
    persistent processes, no zombies, no runaway relaunch storms).
  - Confirm no flicker: writing the render output must have exactly
    ONE writer (the parser's own compose step reading a project's own
    `view.txt`-equivalent bridge file) - a project's own compose op
    writing the final rendered frame file directly, in addition to the
    parser also writing it, is a real, confirmed bug class (two
    writers racing on the same file), not a style choice.

If any of these don't hold, the refactor is not finished, regardless
of how much of the new code has been written.

23. SESSION ISOLATION - IMPLEMENTED (pal-forum, 2026-07-19), NEXT: PORT
    TO pal-chat-irc, THEN BACKPORT TO pal-chain. "KILL WHATEVER'S
    RUNNING" WAS THE WRONG FIX FOR CROSS-SESSION CONTAMINATION - THE
    REAL FIX IS PER-SESSION FILE ISOLATION
========================================================================
THE MISTAKE, LIVE-CAUGHT (pal-forum, 2026-07-19): every project's own
`button.sh run` writes its ENTIRE ephemeral UI/input state (`pieces/
keyboard/history.txt`, `pieces/apps/player_app/interact_relay.txt`,
`pieces/display/current_frame.txt`, `projects/<id>/manager/
gui_state.txt`, etc.) to ONE FIXED set of paths under the project root -
there is no per-invocation identity at all. An agent testing the same
project via direct, detached background process launches (`setsid
nohup ... & disown`, deliberately outliving any single tool call) left
several stray `chtpm_parser_pal`/`prisc+x` processes running
concurrently with the user's own real, separate `button.sh run`
session - ALL of them reading and writing the SAME shared files. The
user's own live typing got corrupted by an unrelated agent test's own
old keystrokes replaying into their session. A first-pass fix (this
file's own earlier draft) had `run` unconditionally `pkill` any
pre-existing process for the same project before starting - REJECTED
by the user: "we dont want to kill processes just because they are
running. we only want to kill them if the user is done running them."
Correct call - that fix punishes the exact legitimate case (two
genuinely concurrent, intentional sessions of the same project) it
should support, not prevent.

THE REAL FIX, USER-SPECIFIED (not yet built - this section exists so
the intent survives to whoever builds it): every `button.sh run`
invocation generates a session_id (e.g. timestamp+pid) and creates a
dedicated session directory (`pieces/sessions/<session_id>/` or
equivalent) holding ONLY that invocation's own ephemeral, mutable
runtime state - keyboard history, interact_relay, current_frame,
gui_state, quit_flag, and any other file a live session writes many
times per second. The session_id gets passed as a variable (an env var,
e.g. `PRISC_SESSION_ROOT`, read the same way `PRISC_PROJECT_ROOT`
already is) so N concurrent sessions of the same project never see or
touch each other's files at all - no locking, no coordination, no
"is anyone else using this" check needed, because there is genuinely
nothing shared to collide on.

WHAT STAYS SHARED (deliberately, not an oversight): the actual
PERSISTENT DATA a project's own ops read/write (pal-chain's `wallets/`+
`data/blockchain.txt`, pal-forum's `users/`, any future project's own
equivalent) is the real, single-source-of-truth database every session
of that project should see and mutate together - it must NOT be
session-scoped, or two windows of "the same user" would show different
balances/posts. Likewise the STATIC definitions (`system/*` binaries,
`ops/*`, `pal/*.pal`, `pieces/chtpm/layouts/*.chtpm`, `projects/<id>/
pieces/*/piece.pdl`, `default_op.txt`) never change per-session and
should stay read-only shared references, not copied per session.

IMPLEMENTATION, AS ACTUALLY BUILT (`pal-forum/button.sh`'s own `run`
action, 2026-07-19 - not a hypothetical shape anymore): `SESSION_ID=
"$(date +%s)-$$"`, `SESSION_DIR="$SCRIPT_DIR/pieces/sessions/
$SESSION_ID"`. Inside it: real, fresh, private dirs for `pieces/
system/`, `pieces/display/`, `pieces/apps/player_app/`, `pieces/
keyboard/`, `net/`, `projects/<id>/manager/` - and `ln -s` symlinks
back to the real project root for `system`, `ops`, `pal`,
`default_op.txt`, `pieces/chtpm`, `projects/<id>/pieces`, and `users/`
(pal-forum's own persistent database - the one deliberate exception to
"everything in the session dir is private"). `PRISC_PROJECT_ROOT` is
set to `$SESSION_DIR` for every process this invocation launches.

A REAL SUBTLETY THAT COST A DEBUGGING PASS TO GET RIGHT: chtpm_parser_
pal's own spawned module (`system/prisc+x`) is always launched via a
RELATIVE `./system/prisc+x` argv (the symlink target text is identical
across every session), so `pkill -f "system/prisc\+x"` CANNOT tell
sessions apart by argv alone - it would kill every OTHER concurrent
session's own module too, silently reintroducing the exact cross-
session damage this whole section exists to prevent. Fixed by matching
each candidate PID's own REAL cwd (`readlink -f /proc/$pid/cwd`)
against `$SESSION_DIR` before killing it - cwd is genuinely unique per
session (the whole reason `SESSION_DIR` exists), argv text is not.

Deleted entirely on exit (`trap ... EXIT INT TERM` does `rm -rf
"$SESSION_DIR"` after killing only this session's own processes) -
"starts a new" every launch, nothing to ever accumulate or manually
clean up.

LIVE-VERIFIED, not just built (two genuinely concurrent sessions,
typing DIFFERENT text into the SAME login screen's own `user_id_input`
field simultaneously): session A's own `gui_state.txt` held exactly
"alice", session B's own held exactly "bobby" - zero cross-talk.
Quitting session A (kill its own scoped processes, `rm -rf` its own
`SESSION_DIR`) left session B's own directory, process, and typed
state completely untouched, and left the shared `users/` directory
(real signup data from either session) intact and visible from the
real project root.

rate drops, not on a fixed calendar date - the local-copy convention's

instability; once that instability stops, the reason for paying its

confirmed tedious and error-prone across this same session) goes away

   real METHOD rows (this family's own pre-existing action-bar pattern,
   e.g. ops/choice.c's action_cursor/digit_accum - unchanged by this

   `[>]` in chtpm's own rendering (render_element()'s `pref` variable,
   chtpm_parser.c ~line 2373-2379).
2. INTERACT MODE (chtpm's own name: `is_map_control`, stored in a
   project's own session/state.txt, read back by

   THIS project's own game-input pipeline instead of being intercepted
   for NAV-list digit-jumping." ENTERED by pressing Enter on an
   ORDINARY, REAL, NUMBERED nav-list row whose method/onClick is the
   literal sentinel string "INTERACT" (fuzz-op.chtpm line 18:

   more row in the SAME numbered list every other real action already
   lives in). EXITED by ESC (chtpm_parser.c ~line 2860,

   piece-possession concept at all, it only manipulates active_index/

   whatever the PROJECT already wrote to ITS OWN state) - which
   specific piece (the free xlector cursor, or a possessed pet/unit)
   currently receives movement/method-dispatch WHILE interact mode
   (#2) is on. Tracked entirely by the project's own ops, in the
   project's own state.txt, under whatever field name that project
   picks (this family's own convention going forward: `possessed_id`,
   "none" meaning the free cursor).

------------------------------------------------------------------------
28.2 THE ONE RULE THAT MATTERS MOST - #2 AND #3 NEVER TOUCH EACH OTHER
------------------------------------------------------------------------
Toggling interact mode OFF (ESC, #2) does NOT reset, clear, or
otherwise touch possession (#3) - confirmed by direct read of chtpm's
own ESC handler, which has no code path that could touch a project-
local field it doesn't even know the name of. Re-entering interact mode
(Enter on the "interact" nav row again) resumes control of WHATEVER
possessed_id already was - if a unit was possessed before the last ESC,
it's still possessed after re-entering, with zero extra steps. Relinquishing
possession (returning control to the free cursor specifically) is its
own SEPARATE action - in fuzz-op's own real xlector/piece.pdl-driven
design, this is just another ordinary numbered METHOD dispatched via
the SAME mechanism as any other verb (matches key '9' in the reference
transcript producing "Returned to Xlector." while [ACTIVE] flips from
pet_01 back to xlector, with interact mode itself never leaving `[^]`
across that same transition - direct transcript evidence, now correctly
read in light of the source above rather than guessed at cold).

Concretely, per-project fields (this family's naming convention from
here forward - civ-pal/angler-empires are the first adopters):
  interact_mode (0/1) - #2 above. 0 = NAV, dispatch against whichever
    piece_id normally drives the top-level action bar (this project's
    own pre-existing convention, e.g. "hero"). 1 = ACTIVE, dispatch
    against whichever piece_id possession (#3) currently names.
  possessed_id (string, "none" or an instance id) - #3 above. Written
    ONLY by (a) a "possess"-flavored method on the free cursor's own
    piece.pdl (fuzz-op's own "scan" - examine-and-possess-on-a-match,
    matching examine_at()'s own already-correct behavior in this
    family's own ports) or (b) a "release"-flavored method on the
    currently-possessed piece's own piece.pdl. NEVER written by
    anything that also touches interact_mode - if a code change ever
    makes ESC or the interact-mode-entry method also reset
    possessed_id, that change is wrong, full stop, re-read this section.

28.3 HOW A ROW BECOMES "THE INTERACT MODE ROW" - A REAL METHOD, NOT A
     BOUND KEY
------------------------------------------------------------------------
chtpm's own convention: any nav-list element whose onClick attribute is
the literal string "INTERACT" gets this behavior automatically -
ordinary digit-jump/Enter, no different from any other row, EXCEPT its
Enter handler is chtpm's own built-in special case (chtpm_parser.c
~line 2846: `else if (strcmp(el->onClick, "INTERACT") == 0) {
active_index = focus_index; ...}`) instead of exec'ing an external
command. This family's own projects (civ-pal, angler-empires, ...) have
no chtpm layout at all (PAL-CRAFT-DESIGN.txt's own dox already
documents this architectural difference - "uses its own PDL METHOD-
table action bar instead... CHTPM is unnecessary over-engineering for a
single-game project like this one," a decision that still stands, not
reversed by this section) - the faithful, proportionate adaptation is:
add a real METHOD row named "interact" to whichever piece.pdl already
drives the NAV-mode action bar (e.g. hero/piece.pdl), and have the
project's OWN digit/Enter dispatcher special-case that METHOD NAME the
same way it already special-cases other named methods by string match
(this family's own pre-existing "craft"/"examine" panel-opening special
cases in ops/choice.c are the exact same pattern, already proven, nothing
new invented) - setting interact_mode=1 instead of exec'ing an external
handler. A placeholder handler path in the piece.pdl row is fine (never
actually executed, matches the existing craft/examine rows' own
convention of a METHOD row whose handler is effectively decorative once
special-cased).

Do NOT bind interact-mode entry to a dedicated raw key (e.g. 'i'/'I') -
three earlier attempts at this exact fix did that, and it was wrong
each time (direct user correction, verbatim: "interact mode isn't an
'i' selectable. its another indexed nav #1. there are other nav options
on menu."). The "other nav options" are simply whatever OTHER real
METHOD rows already exist (or get added later) on the same piece.pdl -
this mechanism composes naturally with them for free, precisely because
"interact" is an ordinary row and not a special parallel system.

and NAV mode's own digit/Enter dispatch is a completely separate input

While interact_mode==1 (ACTIVE), arrow keys move whichever piece
possession (#3) currently names: the free cursor (possessed_id="none",

xlector-cursor convention) or a possessed unit (possessed_id names a
real instance, walkable-checked movement against that instance's own

29. MULTI-MODULE chtpm_parser_pal.c SUPPORT, AND SIX LIVE-CAUGHT
    GOTCHAS FROM BUILDING muchi-pal-agent's "*" PATH-COMPLETION PICKER
    (2026-07-20/21)
========================================================================
Full task was porting gem-dev's "*" wildcard completion into muchi-pal-
agent, but as a genuinely live, auto-focusing, auto-closing "+-" tree
picker (not gem-dev's flat 5-slot menu) - new files: manager/
path_nav_manager.c, chat.chtpm's second <module> line. Along the way,
several REAL bugs in the shared engine itself got found and fixed, not
just this project's own code. Each is its own trap for the next person

------------------------------------------------------------------------
29.1 <module> TAGS WERE SINGLE-SLOT, NOT MULTI - FIXED, NOW GENUINELY
     CONCURRENT ("like html/js", direct instruction)
------------------------------------------------------------------------
launch_module()'s own guard (`cleanup_module()` before every fork) meant
a SECOND <module> line in one layout silently KILLED the first one on
every parse - confirmed live: chat.chtpm's own system/prisc+x got
reaped the instant a second <module> for path_nav_manager.+x was added,
with zero error surfaced anywhere. Fixed by adding a SEPARATE registry
(`g_extra_modules[]`, `launch_extra_module()`) for every <module> tag
AFTER the first: same liveness-guarded dedupe as launch_module()'s own
guard, but never evicts a different slot to make room. The first
<module> tag in a layout still goes through the original single primary
slot completely unchanged (current_module_pid/current_module_path,
run_module_synchronous(), cleanup_module() on href navigation - zero
behavior change for every existing single-module project). Ordinal-
tracked in parse_chtm()'s own tag loop (module_ordinal, 0-indexed: 0 ->
primary slot, 1+ -> extra registry). While fixing this, ALSO fixed a
pre-existing latent bug this exposed: the inner-text form of <module>
(`<module>path</module>`, used by every layout in this family) was
being double-dispatched - once via the TOKEN_TEXT branch, once via a
redundant fallback inside the TOKEN_OPEN_TAG branch - previously masked
because both calls hit launch_module()'s own single dedupe-by-path
guard; would have broken ordinal counting for the multi-module case.
Removed the redundant fallback. Ported to shared-ops/chtpm_parser_pal.c,
1.muchi-pal-agent's own copy, and 1.TPMOS_c_+rmmp.0102.0028/pieces/
chtpm/plugins/chtpm_parser.c (the original reference implementation) -
NOT yet propagated to the other sibling projects' own copies
(pal-chat-irc/pal-chain/mutaclsym/etc.) - that's a separate sync pass,
do it deliberately, not as a side effect of reading this section.

------------------------------------------------------------------------
29.2 NEVER cp A "SHARED" FILE WITHOUT DIFFING FIRST - LOCAL COPIES DRIFT
     FOR REAL REASONS (see sec. 24), AND shared-ops/ CAN BE THE STALE ONE
------------------------------------------------------------------------
Live mistake, caught and recovered mid-session: assumed shared-ops/
chtpm_parser_pal.c and 1.muchi-pal-agent's own copy were identical,
`cp`'d shared-ops's version over muchi-pal-agent's own without diffing
first. They were NOT identical - `diff` afterward (too late) showed
real divergence. Recovered by diffing 5 OTHER sibling copies
(mutaclsym/pal-chat-irc/pal-chain/user-pal/muchipal-editor-0.0) against
each other first: all 5 were byte-identical to each other, meaning

family, same build.sh convention referencing "mutaclsym's own standing

------------------------------------------------------------------------
29.3 gui_state.txt IS A FLAT, LINE-DELIMITED key=value STORE - NEVER PUT
    A LITERAL NEWLINE IN A VALUE
------------------------------------------------------------------------
get_var()/load_state_file() read this file via `fgets()` per line,
splitting on the FIRST '='. A value written with a real '\n' byte
embedded in it (e.g. a naively-concatenated multi-line markup blob)
gets silently truncated to whatever's before that first newline on
read-back - the rest either vanishes or gets misparsed as bogus
keyless lines. gem-dev's OWN g_menu_area (the precedent this project's
own nav_menu was modeled on) never has this problem because it
concatenates `<button ...><br/>` fragments with NO '\n' between them,
relying purely on `<br/>` tags for visual line breaks - copy that
convention exactly for any future dynamically-generated multi-element
markup written into a gui_state.txt value.

------------------------------------------------------------------------
29.4 TWO SEPARATE PULSE FILES, TWO SEPARATE JOBS - PULSING ONLY ONE
    LEAVES gui_state.txt UPDATES INVISIBLE FOREVER
------------------------------------------------------------------------
`pieces/apps/player_app/state_changed.txt` growth is what makes the
main loop call `load_vars()` + `parse_chtm()` again - the ONLY thing
that re-reads gui_state.txt and rebuilds the element tree.
`pieces/display/frame_changed.txt` growth ONLY triggers a redraw of
whatever tree is ALREADY parsed - it does NOT re-read anything. gem-
dev's own pulse_state_changed() + trigger_render() (always both, never
just one) is the precedent; an external process that writes a new
gui_state.txt value and pulses ONLY frame_changed.txt will render
forever from stale data with zero errors anywhere to indicate why.

------------------------------------------------------------------------
29.5 active_gui_index.txt vs active_index - ONE HAS A REAL SYNC PATH,
    THE OTHER HAD NONE (had to add one)
------------------------------------------------------------------------
Focus (`focus_index`) has a real, working external-write channel:
`pieces/display/active_gui_index.txt`, read back via
`sync_focus_from_saved_active_index()` - BUT that function was DEAD
CODE before this session (read `get_var("active_gui_index")`, a
variable NOTHING in the file ever calls set_var() for - always empty,
silent no-op for every project, gated to wraith-alpha layouts only on
top of that). Fixed to read the file directly (matching gem-dev's own
proven read_active_gui_index() pattern), and the wraith-alpha gate was
removed as harmless (nothing depended on the previous no-op). Whether a
cli_io is genuinely ACTIVE/typing (`active_index`, distinct from mere
focus) had NO external write channel at all before this session -
`export_active_index()` unconditionally overwrites
`active_gui_index.txt` AND a companion `active_gui_is_typing.txt` from
its own in-memory state every render, so an external process asking
for deactivation has to go through the SAME growth-tracked-marker
idiom as every other *_changed.txt file (added
`pieces/display/force_deactivate.txt`, checked in the main loop right
after the state_ch block, forcing `active_index = -1` and - critically
- re-exporting UNCONDITIONALLY, not gated behind "if already active",
or a stale export from earlier in the SAME pass never gets corrected).
`active_gui_is_typing.txt` (1 = genuinely active/typing, 0 = focus-
only) was already being written every render but never READ by
anything - safe to poll externally as a plain state signal with zero
engine changes.

------------------------------------------------------------------------
29.6 send_command()'s "KEY:n" WRITES THE DECIMAL ASCII CODE AS TEXT, NOT
    THE LITERAL DIGIT CHARACTER - THE #1 GOTCHA FOR ANY EXTERNAL LISTENER
------------------------------------------------------------------------
`onClick="KEY:1"` -> send_command() converts 1 to its ASCII digit
CHARACTER first (`'0'+1` = 49) -> `inject_raw_key(49)` -> writes
`fprintf(fp, "%d\n", 49)` = the two-byte text "49", NEVER the single
byte "1". This is true for EVERY key value inject_raw_key() ever
writes, not just KEY:0-9. An external process parsing
interact_relay.txt/history.txt for a specific key must decode the line
as a decimal integer and compare against the ASCII value ('0'..'9' =
48..57), never compare the line's raw TEXT against a literal digit
string. Live consequence of getting this wrong: an entire picker
feature (path_nav_manager.c) tested as "working" via hand-written
single-digit-character test files for two full rounds of Layer-1
testing, while every REAL selection (real keyboard Enter, real mouse
click, anything actually going through send_command()) was being
silently rejected the whole time - passed testing, failed in real use.
Generalizes: Layer-1 file-injection tests that hand-write the SAME file
format the real dispatch path produces are only trustworthy if that
format was itself verified against the real producer's code, not
assumed from a struct name or convention.

------------------------------------------------------------------------
29.7 A SECOND PERSISTENT <module> NEEDS ITS OWN SESSION SYMLINK AND ITS
    OWN REAP - button.sh's OWN bootstrap WILL SILENTLY OMIT BOTH
------------------------------------------------------------------------
button.sh's `run` action symlinks a fixed list of directories
(system/, ops/, pal/, pieces/chtpm, pieces/registry, pieces/world_01,
sandbox) into each fresh session dir - a NEW top-level directory a
second module's binary lives in (here: manager/, containing
path_nav_manager.+x) is NOT covered by that list and has to be added
by hand. Missing it fails completely silently: launch_extra_module()'s
own fork+execv has no output path on failure (`_exit(1)` in the child,
nothing written anywhere), so the symptom is just "the feature does
nothing," indistinguishable from a dozen other possible bugs, in EVERY
test EXCEPT one that happens to symlink the directory manually (which
is exactly how this stayed hidden through several rounds of manual
test-session construction in this same session, each of which had
manually added the missing symlink without realizing button.sh itself
never would). `kill_own_module()` (cwd-matched process reaping on
session exit) also only covered system/prisc+x by name - a second
persistent module needs its own identical cwd-matched pgrep/kill block
added there too, or it leaks as an orphaned background process on every
single `run`/exit cycle. Checklist for adding ANY second persistent
<module> to a project in this family: (1) symlink its binary's own
directory into button.sh's session bootstrap, (2) add its own
cwd-matched reap to kill_own_module(), (3) add it to the `kill` action's
own pkill list too.

------------------------------------------------------------------------
29.8 SUPPRESSING A RE-TRIGGER NEEDS IDENTITY, NOT PRESENCE - "IS THE
    TRIGGER CHAR STILL THERE" IS THE WRONG QUESTION
------------------------------------------------------------------------
Auto-closing the picker when the user reactivates the cli_io (direct
request: "if activated again, close picker") needed to suppress
REOPENING for the SAME dismissed '*' while the user kept typing past
it - but a first-cut boolean flag, cleared only once NO '*' existed
anywhere in the buffer, was wrong: typing a second, genuinely NEW '*'
later in the same message (e.g. "pieces/* hi how are u *") left the
FIRST '*' still present earlier in the string, so the flag never
cleared and the second, deliberate trigger was wrongly suppressed too
- live-reported as "didn't retrigger picker." Fixed by tracking the
DISMISSED star's own POSITION (`strrchr(...) - g_last_typed`, an
offset, not a bool) and comparing it against the CURRENT last-found
star's position on each check: same offset (user is still typing past
the one they already dismissed) stays suppressed; any different offset
(a '*' appeared somewhere new, earlier or later) is a distinct
occurrence and triggers normally. General lesson: when suppressing a
repeat of a dismissed event that's keyed on "does X still exist in
some larger state," track WHICH specific occurrence of X was dismissed,
not merely whether X-in-general is still present - the two diverge the
moment a second, legitimate instance of X can coexist with the leftover
first one.

------------------------------------------------------------------------
29.9 DEBUG LOGGING LEFT IN A HOT POLL LOOP IS ITS OWN BUG, NOT JUST MESS
------------------------------------------------------------------------
Temporary `fopen(...,"a")`/`fprintf`/`fclose` debug tracing added to
diagnose 29.5/29.8 above was left running inside path_nav_manager.c's
own 40-150ms poll loop across several test/fix iterations - real disk
I/O on every tick, live-reported as visible redraw "flicker" while
typing, and only PARTLY explained by the actual logic bugs it was
added to diagnose. Removed as its own fix, separate from whatever logic
bug prompted adding it. Any debug instrumentation added to a
persistent, tightly-looped process (any *_manager.c/*_pal_manager.+x
in this family) needs to be treated as a real perf regression the
moment it ships in a poll loop, not just cosmetic clutter to clean up
"eventually."

30. FRAME HEIGHT PADDING — UI CONVENTION FOR SCROLLBACK (2026-07-21)
========================================================================
Each rendered frame should pad to exactly 1 screen height (terminal rows).
This ensures only ONE full frame is visible at a time, and scrolling shows
the previous frame cleanly (not two frames cramped on one screen).

IMPLEMENTATION (C):
  1. Detect terminal height: LINES env var, ioctl(TIOCGWINSZ), or default 24
  2. After writing frame content to view.txt:
     - Count actual lines in the file
     - Calculate padding needed: terminal_height - line_count
     - Append that many blank lines
  3. Do this AFTER frame content is written, BEFORE frame history dump

PATTERN:
  static void pad_frame_to_screen(const char *view_path) {
      int terminal_height = 24;
      const char *lines_env = getenv("LINES");
      if (lines_env) terminal_height = atoi(lines_env);

      struct winsize w;
      if (ioctl(STDOUT_FILENO, TIOCGWINSZ, &w) == 0 && w.ws_row > 0)
          terminal_height = w.ws_row;

      FILE *f = fopen(view_path, "r");
      if (!f) return;
      int line_count = 0;
      char buf[MAX_LINE];
      while (fgets(buf, sizeof(buf), f)) line_count++;
      fclose(f);

      if (line_count < terminal_height) {
          f = fopen(view_path, "a");
          if (f) {
              for (int i = line_count; i < terminal_height; i++)
                  fprintf(f, "\n");
              fclose(f);
          }
      }
  }

VERIFIED WORKING (2026-07-21):
  ✅ muchi-pal-agent: pad_frame_to_screen() in compose_frame.c

BENEFIT:
  - User scrolls up in terminal, sees ONE complete previous frame
  - Not two frames crammed into view with partial content visible
  - Cleaner scrollback experience, matches typical terminal paging
  - Each frame takes exactly 1 screen, makes navigation predictable

31.1 THE FULL MODEL, ONE MORE TIME, TERSELY
------------------------------------------------------------------------
Three fields on the top-level control piece (conventionally "hero",
even though it never moves - it's the NAV-mode dispatch anchor, not an
avatar):
  interact_mode (0/1): 0=NAV ("[>]", digit/Enter dispatches hero's own
    numbered METHOD list), 1=ACTIVE ("[^]", arrows move whichever piece
    possession names, digit/Enter dispatches THAT piece's own list).
  possessed_id (string, "none" or an instance id): which piece receives
    ACTIVE-mode movement/dispatch. "none" = the free xlector cursor.
  xlector_pos_x/xlector_pos_y (ints, already existed pre-session): the
    free cursor's own position, separate from any possessed piece's.

Entry to ACTIVE: a real numbered METHOD row named "interact" on hero's
own piece.pdl (NOT a bound key - direct user correction, twice: "isnt
an 'i' selectable... another indexed nav"). Special-cased by NAME in the
dispatch op, same pattern as pre-existing "craft"/"examine" specials.

Exit/relinquish: ESC. Two-step, never both in one press (matches real
fuzz-op_manager.c's route_input(), read in full, sec. 30):
  - possessed_id != "none": relinquish only (-> "none"), interact_mode
    UNCHANGED (stays ACTIVE, controlling the free cursor now).
  - possessed_id == "none": deactivate interact_mode (-> NAV), restore
    action_cursor to "interact"'s own real index (never hardcode it -
    look it up fresh, method order can change) so "[>]" reappears
    immediately instead of vanishing.

Possessing: Enter, UNCONDITIONALLY, whenever dispatch_id=="xlector" (NOT
gated behind selecting a numbered "scan" method first - real, load-
bearing bug found and fixed this session, sec. 30.1). Scans real
instances (a units/ or anglers/ or whatever-the-project-calls-it/
directory) for a pos_x/pos_y match at the free cursor's CURRENT
position, possesses the first match.

dispatch_id, computed identically everywhere this matters (choice.c's
own dispatch AND compose_frame.c's/compose_rgb_frame.c's own footer -
all three must compute it the SAME way or the visible footer can lie
about what Enter/digits will actually do):
  interact_mode==0            -> "hero"
  interact_mode==1, unpossessed -> "xlector"
  interact_mode==1, possessed   -> possessed_id itself

31.4 "FIXED TO ONE CHARACTER" - A CONFIG-DRIVEN MODE, NOT A CODE FORK
     (direct user instruction: "for certain projects possession should
     be fixed to one character... make it something done in a config
     file, dont not port the code" - i.e. port the FULL, IDENTICAL
     possession machinery to every project regardless of genre, and let
     a config file decide whether it behaves as free multi-target swap
     (angler-empires/civ-pal - many real units, DF/Civ-style) or locked
     to a single fixed target (pal-craft/muchimon-pal - one player
     character, Minecraft/Pokemon-style) - so ANY project can be
     switched into free-swap mode later for debugging with ZERO new
     code, just a config edit)
------------------------------------------------------------------------
New registry-shaped config file, same pipe-delimited/key=value
convention as everything else in this family - NOT a new format:
  pieces/system/possession_config.txt:
    mode=free|fixed
    fixed_target_id=<instance_id>   (only meaningful when mode=fixed -
      e.g. muchimon-pal's own single player character's instance id)

Wiring (minimal - reuses 31.1's existing dispatch_id/possessed_id
mechanism entirely, does NOT branch the dispatch logic itself):
  - On process/session start (or simplest: read fresh every choice.c
    invocation, same "no persistent state beyond plain files" doctrine
    as everywhere else in this family), if mode==fixed: possessed_id is
    FORCED to fixed_target_id every tick (a one-line clamp, applied
    right after reading possessed_id off hero/state.txt, before any
    dispatch logic runs) - self-healing, so even if something else
    wrote "none" or a different id, it snaps back immediately.
  - ESC's own relinquish branch becomes structurally a no-op in fixed
    mode (possessed_id can never actually leave fixed_target_id, so the
    "possessed_id != none" check is always true and always re-clamps to
    the SAME id instead of "none" - same code path, no new branch).
  - interact_mode's own NAV<->ACTIVE toggle STILL WORKS NORMALLY in
    fixed mode (a fixed-target project still benefits from "ESC to stop
    controlling anything, browse the menu" - it's only the SWAP-WHICH-
    PIECE part of possession that's locked, not interact mode itself).
  - Flipping mode=fixed -> mode=free in the config file, with NO code
    changes, immediately unlocks full multi-target possession (Enter-
    to-possess-anything-at-cursor starts working again the instant
    possessed_id is no longer force-clamped) - this is the whole point:
    a debugging escape hatch that costs nothing to keep wired in.

Per-project defaults (design intent, not yet all built as of this
section being written - check each project's own dox before assuming):
  civ-pal, angler-empires: mode=free (many real units/anglers, swapping
    between them is the actual core mechanic of a DF/Civ-style game).
  pal-craft, muchimon-pal: mode=fixed, fixed_target_id=<the project's
    own single player character instance> (Minecraft/Pokemon-style -
    one player-controlled character, no reason to ever swap in normal
    play, but the SAME full machinery is present underneath, config-
    unlockable for debugging without touching code).

33. LLM-API CHAT PIPELINE - FIVE STANDARDS (see !.xyzos-pitfalls.txt sec.
    P1 for the full live-caught trace behind each one, 2026-07-21)

33.0 When a working reference implementation exists for the thing
     you're building or debugging, read ITS actual handling of that
     specific step BEFORE writing new code or a new theory - re-check
     this for every new symptom, not just once per project.
33.1 A single-owner poll/ownership state file (ai_state, curl_pid, or
     equivalent) is SESSION-PRIVATE data, not shared multi-user data -
     copy it fresh into $SESSION_DIR on every `run`, like pal-chat-irc's
     own pieces/apps/player_app/state.txt, never symlink it the way
     genuine multi-user data (users/, rooms/) is symlinked.
33.1a Trap SIGHUP alongside EXIT/INT/TERM in button.sh's own cleanup,
     and reap any live instance of the project's own binaries (matched
     by /proc/$pid/exe under the project root, not by cwd) at the START
     of every `run` as a backstop.
33.2 On completion, the process that detected it must trigger the
     render itself (system("./ops/+x/compose_frame.+x") or equivalent) -
     never just ping a marker and trust a separate, later poll to
     notice. Matches gem-dev_manager.c's own write_gui_state()+
     trigger_render() and pal-chat-irc's chat_inbox_watcher.c's own
     trigger_render() exactly.
33.3 A curl --max-time figure must come from a reference project's own
     real, hard-won debug handoff for the SAME model/host, not a
     comment's own unverified claim - and surface curl's real exit code
     as distinct messages (timeout vs. unreachable), never one generic
     "could not connect."
33.4 Always try an error.message (or equivalent REST error-body)
     extraction before falling back to a generic "empty or unparseable
     response" - port gem-dev_manager.c's own check_ai_status() pattern
     verbatim.

34. ENTITY-DRIVEN TURN QUEUE ARCHITECTURE (2026-07-23)
    "Each entity handles its own atomic turn - future-proof for
     multiplayer, P2P, and human-controlled entities"
========================================================================

PRINCIPLE: The game loop does NOT orchestrate gameplay. Instead, EACH
entity (hero, monster, future human player, NPC) is fully self-contained
and handles its OWN complete turn, updating game state and signaling the
renderer when done. This enables:
  - Multiplayer: just add execute_player_turn.c, same queue works
  - P2P: network code routes remote entity turns same way as local AI
  - Hybrid: human and AI entities in same queue, same architecture
  - Swappability: replace execute_monster_turn with execute_pet_turn

ARCHITECTURE (see mutaclsym's main_loop_chtpm.pal):

  GAME LOOP (thin, generic):
    loop:
      tick_next_entity  (figures out whose turn, calls handler)
      compose_frame     (render result)
      sleep 30ms
      j loop

  ENTITY HANDLERS (each self-contained op):
    - execute_hero_turn.c:
        Reads input from interact_relay.txt
        Calls move_player with keystroke
        Calls end_turn (metabolism, turn counter)
        Hits marker file (state_changed.txt)
        Returns (hero's turn complete)

    - execute_monster_turn.c <monster_id>:
        Calls pick_ai_strategy to decide action
        Reads decision from action.txt
        Executes action (move or attack)
        Updates monster position/hero hp as needed
        Logs messages (damage, etc)
        Hits marker file
        Returns (monster's turn complete)

    - (future) execute_player_turn.c <player_id>:
        Same pattern as hero/monster
        Could read network input, local input, or AI
        Complete entity abstraction - queue doesn't care

TURN QUEUE (dynamic, built per entity action):
  1. scan pieces/world_01/map_start/hero/ → "hero"
  2. scan pieces/world_01/map_start/monsters/ → "monster|zombie_01", etc
  3. (future) scan pieces/world_01/map_start/players/ → "player|player_1", etc
  4. Sort by name for deterministic order
  5. Current index stored in turn_state.txt
  6. Wrap to 0 when reaching end

MARKER FILE COORDINATION:
  Each entity handler hits pieces/apps/player_app/state_changed.txt when
  modifying state. chtpm_parser_pal watches this marker (via file size)
  and re-renders UI automatically. No explicit render calls needed - the
  handler updates state, hits marker, loop renders, display updates.

FLOW EXAMPLE (hero + 2 monsters):
  Turn 1: hero's turn
    - tick_next_entity → execute_hero_turn
    - reads "right arrow" from relay
    - calls move_player 1001
    - calls end_turn (hunger++, turn++)
    - hits marker (state_changed.txt grows)
    - compose_frame shows hero moved 1 right

  Turn 2: monster_01's turn
    - tick_next_entity → execute_monster_turn zombie_01
    - calls pick_ai_strategy (decides to chase)
    - reads action.txt (target 25,10, move toward hero)
    - updates zombie_01 pos_x/pos_y
    - hits marker
    - compose_frame shows zombie moved closer

  Turn 3: monster_02's turn
    - (same pattern for ghost_01)

  Turn 4: back to hero's turn (index wraps to 0)
    - Game waits for next key press

NO EXTRA KEY PRESSES: Player presses key once, hero acts, monsters
automatically act in sequence without needing additional input. Each
entity takes exactly one turn per cycle.

MULTIPLAYER ADDITION (future): Add network handler:

  execute_remote_player_turn.c <player_id>:
    Read action from network queue (or wait with timeout)
    Execute move/attack same as local hero
    Hit marker
    Return

  Same tick_next_entity, same queue - network player appears as just
  another entity, no special cases.

KEY INVARIANT: Each op is ATOMIC. Calling execute_hero_turn or
execute_monster_turn <id> completes that entity's ENTIRE turn:
input → decision → state update → marker file. No partial state,
no waiting for followup calls. This is why they work in a generic
queue where tick_next_entity doesn't know entity types in advance.

C:DDA-STYLE TURN SYSTEM (ALL PAL ROGUELIKE PROJECTS):
CRITICAL RULE: Player input drives time forward. Only player actions trigger
game-state advancement and renders. This applies to ALL projects in this
family (mutaclsym, future roguelikes, etc.).

RULE: Marker file grows IF AND ONLY IF hero/player performed an action.
  - Hero with input → hero acts → marker grows → ONE render
  - Hero idle (no input) → nothing happens → marker silent → no render
  - Monsters act → accumulate effects silently → no marker growth → no render
  - Back to hero's turn waiting for input

MASTER LEDGER + MARKER FILE COORDINATION (IMPLEMENTED):
Aligns with real TPMOS's master_ledger.txt pattern for auditability
and resilience. No timestamps needed - marker file IS the signal.

Architecture:
  1. execute_hero_turn.c ONLY logs if input was present:
       ENTITY_TURN_START: hero
       ENTITY_TURN_END: hero
       (grows marker file only on input)

  2. execute_monster_turn.c appends to ledger SILENTLY (no marker):
       ENTITY_TURN_START: monster|zombie_01
       ENTITY_TURN_END: monster|zombie_01 | action: attack | damage: 3
       (ledger only - no marker growth - silent accumulation)

  3. chtpm_parser_pal watches marker file, re-renders ONLY when it grows

  4. If process crashes, can replay from ledger to recover state

Benefits:
  - Auditability: append-only ledger for all actions (silent or not)
  - Signal-driven: marker file growing tells renderer "player acted"
  - No render spam: idle waiting doesn't trigger renders
  - C:DDA-accurate: time only advances on player action
  - Resilience: full action history for replay on crash
  - Debugging: complete sequence of entity turns
  - Multi-process: shared ledger for network/P2P coordination

IMPLEMENTATION (C:DDA pattern):
  - execute_hero_turn.c: only logs if input present, only grows marker if acted
  - execute_monster_turn.c: logs to ledger only (silent), NEVER grows marker
  - end_turn.c: updates metabolism/turn counter, NEVER grows marker
  - main_loop_chtpm.pal: polls marker size, only composes_frame if it grew
  - No timestamps, no time.h - marker file index IS the time

17. ORCHESTRATOR CLEANUP: 3-LAYER CASCADING KILL + BIBLE §3 COMPLIANCE
========================================================================

REAL BUG, LIVE-CAUGHT (01.lpns+map+4, 2026-07-24): orchestrator.c
used `system()` for both `compile_binaries()` and directory creation -
Bible §3 violation. Additionally, when Ctrl+C was pressed, child
processes (game_manager, chtpm_parser_pal, renderer, keyboard_input)
were not reliably killed, leaving zombie processes consuming CPU.

THE FIX - 3-LAYER CASCADING KILL (modeled on x0.moke orchestrator.c
and wraith-alpha_manager.c):

Layer 1: Process Group Kill (fast path)
  kill(0, SIGTERM);  // Send SIGTERM to entire process group
  usleep(100000);    // 100ms grace period

Layer 2: File-Backed PID Sweep (x0.moke HOLY Pattern)
  Read pieces/os/proc_list.txt
  Phase 1: SIGTERM to each tracked PID
  Phase 2: SIGKILL survivors + waitpid(WNOHANG)

Layer 3: kill_all.sh Final Sweep (nuclear option)
  Fork child, execl("/bin/bash", "bash", "pieces/os/kill_all.sh")
  Catches any processes missed by layers 1-2

THE SIGNAL HANDLER:
  void handle_signal(int sig) {
      should_exit = 1;
      kill_process_group();    // Layer 1
      kill_all_tracked();      // Layer 2
      run_final_kill_sweep();  // Layer 3
      _exit(0);
  }
  Registered for both SIGINT and SIGTERM.

BIBLE §3 COMPLIANCE - ALL system() REPLACED:
  // WRONG (Bible violation):
  system("gcc -pthread -o system/game_manager system/game_manager.c");
  system("mkdir -p data pieces/display ...");
  system("./ops/game_compose_frame");

  // CORRECT (fork/exec/waitpid):
  compile_single("system/game_manager.c", "system/game_manager", "-pthread");
  ensure_directories();  // fork + execl("/bin/mkdir", ...)
  initial_compose();     // fork + execl("./ops/game_compose_frame", ...)

Each helper function follows the same pattern:
  pid_t pid = fork();
  if (pid == 0) {
      freopen("/dev/null", "w", stdout);
      freopen("/dev/null", "w", stderr);
      execl(...);  // or execv(...)
      _exit(1);
  }
  if (pid > 0) {
      int status;
      waitpid(pid, &status, 0);
  }

kill_all.sh PATTERN (surgical_kill function):
  surgical_kill() {
      local name="$1"
      local pattern="system/${name}"
      if pgrep -f "$pattern" > /dev/null 2>&1; then
          pkill -9 -f "$pattern" 2>/dev/null
      fi
  }

  Targets: orchestrator, renderer, keyboard_input, chtpm_parser_pal,
           game_manager, prisc+x (*.pal$ pattern)

WHY SIGKILL, NOT SIGTERM: chtpm_parser_pal registers SIGINT handler
but NO SIGTERM handler - plain kill terminates it but skips cleanup.
kill_all.sh doesn't rely on any process's signal handling.

THE .pal FLAG (PAL vs C mode):
  button.sh --pal sets PAL_LAYOUT="pieces/chtpm/layouts/..._pal.chtpm"
  Orchestrator reads PAL_LAYOUT env var:
    if (pal_layout && pal_layout[0]) {
        launch("./system/chtpm_parser_pal", pal_layout, NULL);
    } else {
        launch("./system/chtpm_parser_pal", "pieces/chtpm/layouts/...chtpm", NULL);
    }

  PAL layout uses: <module>system/prisc+x pal/main_loop_chtpm.pal</module>
  C layout uses:   <module>system/game_manager</module>

  Parser's launch_module() splits on spaces automatically:
    "system/prisc+x pal/main_loop_chtpm.pal"
    → args[0] = "system/prisc+x"
    → args[1] = "pal/main_loop_chtpm.pal"

PAL SCRIPT SYNTAX - HOW TO CALL OPS:
  The instruction is `exec`, NOT `op`. prisc+x has no `op` instruction.

  Correct:
    exec ./ops/game_turn_input x10    # runs game_turn_input with value of x10
    exec ./ops/game_compose_frame     # runs game_compose_frame (no args)

  Wrong (does nothing or parse error):
    op game_turn_input x10
    op game_compose_frame

  exec takes:
    arg1: literal path to binary (required)
    arg2: register or literal (optional, passed as argv[1])
    arg3: register (optional, passed as argv[2])

  Example PAL dispatch loop:
    li x10, 4          # action code
    exec ./ops/game_turn_input x10
    exec ./ops/game_compose_frame
    hit_frame

32. POSSESSION MODEL - FINAL, CORRECTED (2026-07-25, mutaclsym)
    SUPERSEDES sec. 28/30/31 WHERE THEY CONFLICT - THIS IS THE
    AUTHORITATIVE POSSESSION DESIGN FOR ALL NEW PROJECTS
========================================================================
Written after direct user correction of sec. 28/30/31's own model:
"possession in standards document maybe flawed... always ask me till we
have it finalized." This section supersedes sec. 28/30/31 wherever they
conflict. Sec. 28/30/31 are kept as historical record (same as sec. 0
is kept but superseded by sec. 0-CORRECTED).

------------------------------------------------------------------------
32.1 THE THREE SEPARATE CONCERNS (corrected from sec. 28.1)
------------------------------------------------------------------------
1. NAV MODE - plain digit/Enter index-jump over a numbered list of
   real METHOD rows. The xelector's own methods appear here. Marker
   `[>]` in chtpm's own rendering.
2. INTERACT MODE - a single on/off flag meaning "raw keystrokes route
   to this project's game-input pipeline instead of being intercepted
   for NAV-list digit-jumping." ENTERED by pressing Enter on the
   "INTERACT" nav row. EXITED by ESC. ESC does NOT touch possession.
3. POSSESSION - which entity the xelector is currently controlling.
   Tracked by `possessed_id` (string: "none" or an entity id).
   Possession persists across interact-mode toggles. Released ONLY by
   the "9" hotkey (not ESC).

Key difference from sec. 28/30/31: ESC and possession are SEPARATE.
ESC only toggles interact mode. Possession release is "9" only.

------------------------------------------------------------------------
32.2 NO "HERO" - XLECTOR IS THE UNIVERSAL SELECTOR
------------------------------------------------------------------------
There is no "hero" piece. The xelector is the universal entity
selector/cursor. It can move freely (through walls) and possess
available entities.

- If a game has only 1 possessible entity, that entity is the
  de facto "hero" by default — but the model doesn't care. The
  xelector is still the selector, and possession is still how
  control transfers.
- The xelector's own methods appear in NAV mode (the action bar).
- When an entity is possessed, THAT entity's methods replace the
  xelector's in the action bar.
- "Default nav options" (see sec. 32.7) are always visible
  regardless of which entity is active.

------------------------------------------------------------------------
32.3 POSSESSION LIFECYCLE
------------------------------------------------------------------------
Entry:
  1. Xelector moves to entity's position (free movement, no collision).
  2. Enter → xelector possesses entity (possessed_id = entity id).
  3. Xelector glyph hidden. Entity glyph moves with xelector.

While possessing:
  - Entity's methods appear in the action bar (replacing xelector's).
  - Arrows move the possessed entity (walkable-checked movement).
  - Digit/Enter dispatches against the entity's own piece.pdl.

Release:
  - "9" hotkey → relinquish (possessed_id = "none").
  - Xelector reappears at the entity's CURRENT position.
  - Xelector's methods reappear in the action bar.
  - Entity returns to its own AI/behavior.

ESC does NOT release possession. ESC only exits interact mode (back to
NAV). Possession persists. Re-entering interact mode resumes control
of whatever possessed_id already was.

------------------------------------------------------------------------
32.4 DE-POSSESSIBLE - PER-ENTITY CONFIG FLAG
------------------------------------------------------------------------
A per-entity config flag in piece.pdl META section:

  META | de_possessible | true

When de_possessible is true:
  - The "9" hotkey cannot release this entity.
  - Possession is permanent for this entity.
  - The xelector is locked in — control stays on this entity forever.
  - ESC still exits interact mode normally (possession persists
    regardless of this flag).

When de_possessible is false (default):
  - "9" hotkey releases possession normally.

This is a CONFIG-DRIVEN mode, not a code fork. Same philosophy as
sec. 31.4's "fixed vs free" mode — flip a flag, no code changes.

Examples:
  - A game with 1 player character: set de_possessible=true on that
    entity. The xelector possesses it once and never releases. The
    player always controls that character.
  - A game with many possessible units: leave de_possessible=false
    (default). The xelector can swap between units freely.

------------------------------------------------------------------------
32.5 PIECE.PDL CONVENTION FOR CONFIG FLAGS
------------------------------------------------------------------------
Config/flag fields go in the META section of piece.pdl, NOT STATE.

  META = static, immutable, definitional:
    piece_id, type, version, determinism, capability, model,
    de_possessible, etc.
  STATE = dynamic, mutable, runtime:
    pos_x, pos_y, hunger, happiness, energy, level, status, etc.

Example piece.pdl with de_possessible:

  SECTION      | KEY                | VALUE
  ----------------------------------------
  META         | piece_id           | hero_unit
  META         | version            | 1.0
  META         | determinism        | strict
  META         | de_possessible     | true

  STATE        | name               | Hero
  STATE        | type               | unit
  STATE        | pos_x              | 5
  STATE        | pos_y              | 2
  ...

------------------------------------------------------------------------
32.6 FILE-BACKED STATE MODEL
------------------------------------------------------------------------
All possession state must be file-backed, per the "If it's not in file,
it's a lie" doctrine (TPMOS onboarding bible).

Fields on the top-level control piece (conventionally the xelector,
or whatever piece drives the NAV-mode action bar):

  possessed_id (string, "none" or an entity id):
    Which piece receives ACTIVE-mode movement/dispatch.
    "none" = the free xlector cursor.

  xlector_pos_x / xlector_pos_y (ints):
    The free cursor's own position, separate from any possessed
    piece's position.

  interact_mode (0/1):
    0 = NAV (xlector's own methods appear, digit/Enter dispatches
    xlector's own numbered METHOD list).
    1 = ACTIVE (possessed entity's methods appear, arrows move the
    possessed entity, digit/Enter dispatches THAT entity's list).

dispatch_id, computed identically everywhere this matters:
  interact_mode==0              -> "xlector"
  interact_mode==1, unpossessed -> "xlector"
  interact_mode==1, possessed   -> possessed_id itself

------------------------------------------------------------------------
32.7 DEFAULT NAV OPTIONS - THE fo-menu STANDARD PATTERN
------------------------------------------------------------------------
Source: fuzz-op's own layout (fuzz-op.chtpm lines 28-29) and the
fo-menu-sys.md document. This is now the STANDARD pattern for all
projects in this family.

The action bar (CHTPM layout or PDL-generated method list) has TWO
layers:

  Layer 1: Default nav options (hardcoded in the layout)
    Always visible, regardless of which entity is active.
    Examples: "Back to Selector (9)", "Exit to Menu"
    These are TEXT rows in the layout, not generated from PDL.

  Layer 2: Dynamic methods (generated from active target's PDL)
    Switches based on which entity is currently active.
    When xlector is active: xlector's methods appear.
    When entity X is possessed: X's methods appear.
    Generated by the manager via get_piece_methods_op or equivalent.

Layout example (from fuzz-op.chtpm):
  <text label="║  " />${piece_methods}<text label=" ║" /><br/>
  <text label="║  [ ] 8. [Back to Selector (9)]           ║" /><br/>
  <text label="║  [ ] 9. [Exit to Menu]                    ║" /><br/>

The ${piece_methods} variable contains the dynamic methods. The rows
below it are the default nav options — always present, always visible.

This pattern scales naturally:
  - Pure menu projects: only default nav options, no dynamic methods.
  - Map/cursor projects: both layers, dynamic methods switch on
    possession.
  - Fixed-target projects: dynamic methods always show the same
    entity's methods (de_possessible=true).

------------------------------------------------------------------------
32.8 XLECTOR VISIBILITY (corrected from sec. 31.3)
------------------------------------------------------------------------
The FINAL, correct rule:

  Draw xlector IF AND ONLY IF possessed_id == "none"

While possessing something:
  - Xlector glyph is NOT drawn.
  - Only the possessed piece's own glyph is visible.
  - Xlector position still tracks (for camera, for relinquish
    positioning), but it's invisible.

On relinquish ("9" hotkey):
  - xlector_x/y get set to the possessed piece's CURRENT pos_x/pos_y
    BEFORE possessed_id clears.
  - Xlector reappears exactly where the player ends up.

34. NO 'q' QUIT KEY, NO FORCED PERIODIC RENDER, SKIP-IF-UNCHANGED
    (2026-07-26, established during 01.muchi-pals mass-refactor pass)
========================================================================
Three related standing rules, all direct user corrections, all apply to
every project in this family going forward:

34.1 NEVER USE 'q' AS A QUIT KEY. "never use q to quit in any of the
refactors" (direct instruction). A bare letter doubling as global quit
means it can never be typed as ordinary content (username, cli_io text,
plain nav). Ctrl+C (ETX, byte 3) is the quit trigger instead - a real
control character, handled directly in keyboard_input.c's read loop
(not remapped to 'q', not forwarded into history.txt as input). Remove
EVERY independent place a project also special-cases literal 'q'/'Q'/113
as a second quit trigger (chtpm_parser_pal.c's own process_key() had one;
pal scripts can have one via a `beq x2,x9,quit`/`halt` pair) - not just
keyboard_input.c. A pal script owning a quit path this way is ALSO
already a sec.9.1 violation ("module must NOT own a quit path"),
independent of this rule - remove outright, don't rework to key on
something else.

34.2 NO FORCED PERIODIC RE-RENDER. A background game-logic tick (pet
metabolism decay, etc.) keeps running on its own timer, but must NEVER
unconditionally trigger a compose/render afterward - matches this
document's own sec.20 (ONE VISIBLE FRAME WRITER RULE) and real TPMOS's
own renderer.c comment verbatim: "DO NOT add time-based or event-based
render triggers. The marker IS the clock." Confirmed by direct testing:
muchi-pals' pal/main_loop_chtpm.pal used to `j render` unconditionally
after every ~3s pet tick, scroll-spamming a redraw at total idle (3
renders/4.5s observed). Removing the forced render (falling through
to continue the loop instead) cut this to 1 render/9s idle, with the
background tick itself completely unaffected - only the forced VISIBLE
redraw was removed.

34.3 SKIP RE-PRINTING AN UNCHANGED FRAME, EVEN IF THE PULSE MARKER GREW.
Real TPMOS's own pieces/display/renderer.c (confirmed by direct read,
1.TPMOS_c_+rmmp.0103.0001) does NOT diff frames - it reprints
unconditionally on every renderer_pulse.txt growth: 5 blank lines + a
"--- FRAME UPDATE ---" block + the whole frame, same as every project in
this family already does. On a fast, nav-heavy menu (muchi-pals) this
produces a visible scroll-jump on nearly every keypress, reported
directly as flicker. Direct user decision: KEEP scrolling/history mode
(do not switch to in-place/overwrite mode - that was considered and
explicitly rejected, since it would drop scrollback-through-history
entirely, a previously deliberate feature). Instead: renderer.c keeps a
copy of the last content it actually printed, and skips printing (and
skips the frame_history.txt audit entry) when the new current_frame.txt
content is byte-identical to that - a marker growing doesn't necessarily
mean anything visibly changed. This is a genuine addition beyond both
101.mutaclsym's and real TPMOS's own renderer.c - not a port of an
existing pattern. Applies regardless of which marker scheme (single vs
dual) a given project's renderer otherwise uses - orthogonal fix.

See also: mass-refactor.md (project root) for the full conversion plan
these findings came out of.

34. FRAME HISTORY AUDIT LOG + IDLE COMPOSE DISCIPLINE (2026-07-27)
========================================================================

FRAME HISTORY (audit):
  system/renderer.c (house copy) appends every painted frame to
  pieces/display/frame_history.txt with a `--- FRAME at <ts> ---`
  marker, and TRUNCATES that file when the renderer process starts
  (each new session). That is the canonical offline audit trail —
  same idea as scrolling `--- FRAME UPDATE ---` terminal history.

  Session-scoped apps (user-pal / START_BUTTON throwaway sessions)
  lose that file when the session dir is deleted. For durable audits,
  set PRISC_FRAME_HISTORY to an install-path log that button.sh

  this at debug/frame_history.txt).

IDLE COMPOSE (no spam):
  Pal loops that call `menu_input 0` every tick MUST NOT grow a
  screen_changed / frame_changed marker on every idle call. Only
  recompose when information changed (catalog fingerprint, layout,
  last_message, real key). Reference: mutaclsym composes only after
  game_dispatch handles work; see xyzos-pitfalls PITFALL 48.

  Wrong:  key==0 → bump_screen() always
  Right:  key==0 → recompute; bump only if fingerprint/state differs

ONE VISIBLE FRAME WRITER (sec. 20) still applies: ops write view.txt;
chtpm owns current_frame.txt; renderer only reads and logs.

35. GL IS PRIMARY UI — ASCII/TERMINAL IS SECONDARY (HOUSE LAW, 2026-07-27)
========================================================================

THIS IS HOW USERS ACTUALLY INTERACT WITH HOUSE PROGRAMS AND WIDGETS.
Future agents MUST NOT design new apps as "terminal-first, GL optional."
The correct default stack is:

  PRIMARY:   GL / RGB window (chtpm_rgb_render, gl_mirror, project GL
             surface — same frame pipeline as ASCII, different output)
  SECONDARY: ASCII terminal renderer (nice for dev, harnesses, audit
             scrollback, headless CI)
  AUDIT:     frame_history.txt / rgb receipts (always file-backed)

Mutaclsym already behaves this way in practice (terminal + GL mirror).
Widgets and nested "menus opened by another program" go further: they
often run **GL-only** (no useful terminal UI at all).

35.1 Two launch profiles every program should support
-----------------------------------------------------

Every house project that can be a normal app OR a widget MUST expose
config (PDL / button.sh / env) for:

  PROFILE A — APP (default interactive run)
    - GL window ON (primary)
    - ASCII renderer ON or optional (secondary; dev may keep it)
    - keyboard_input may attach to terminal AND/OR GL key path
    - registers in xyzfs runtime process list

  PROFILE B — WIDGET (opened by another program, or "open as widget")
    - GL window ON (required — this is the user interface)
    - ASCII terminal renderer OFF:
        * do not take over the caller's TTY
        * system/renderer stdout → /dev/null (or never launch ASCII
          renderer)
        * still write current_frame.txt + rgb_frame.raw + frame_history
          for audit/harness
    - no second terminal window required for the user
    - still a separate process/session under the hood (file-mediated),
      just not a second interactive shell

Config sketch (per project config/*.pdl or pieces/system/ui_mode.pdl):

  STATE | ui_primary       | gl          # gl | ascii  (default gl)
  STATE | ascii_renderer   | 1|0         # 0 in widget profile
  STATE | gl_window        | 1|0         # 1 required for widget profile
  STATE | launch_profile   | app|widget
  STATE | widget_capable   | 1           # advertises "can be embedded/spawned"

button.sh should accept:

  ./button.sh run              # app profile
  ./button.sh run-widget       # or: run --widget / RUN_PROFILE=widget
  ./button.sh run-widget --focus-pid <pid>   # optional parent context

35.2 How an app opens a widget (example: editor → file-menu)
-----------------------------------------------------------

User in **editor** activates FILE menu method:

  1. Editor does NOT href to an in-process file browser as the long-term
     design (may stub early). Canonical: **spawn file-menu as widget**.
  2. Editor sets / passes launch_profile=widget (env or argv or a one-
     shot pdl drop under exchange/xyzfs).
  3. file-menu starts its own pal session + GL window only.
  4. ASCII path silenced (no TTY fight with editor).
  5. Commands still flow on the **shared document / cmd bus**
     (xyzfs runtime inbox) — same as plan in
     &.widgits/file-menu/widget+plan.txt.
  6. Closing the GL widget unregisters; editor keeps running.

This is the opposite of "open another terminal tab for the widget."
Parallel **processes** yes; parallel **user terminals** no.

35.3 ASCII remains valuable — do not delete it
----------------------------------------------

Keep ASCII renderer codepaths for:

  - harness / agent testing (tk_inject_key, frame_history text asserts)
  - SSH / headless without display
  - developer debugging of layout chrome

But product UX, demos, and widget surfaces are GL-first. Docs and plans
that say "Step 2 optional GL" for widgets are **wrong** under this law —
GL is Step 1 for user-facing widgets; ASCII-only is a dev fallback.

35.4 Pipeline (both surfaces, one compose)
------------------------------------------

  ops compose → view.txt
  chtpm compose_frame → current_frame.txt (+ renderer_pulse)
  optional compose_rgb_frame / chtpm_rgb_render → rgb_frame.raw
  system/renderer     → TTY (if ascii_renderer=1)
  system/gl_mirror    → GL window (if gl_window=1)

ONE VISIBLE FRAME WRITER (sec. 20) still applies to current_frame.txt.
RGB has its own writer rules (sec. 11). Widget mode does not invent a
third UI toolkit — it turns outputs on/off.

35.5 House runtime ledger — process registry (REPLACES focus.txt scan)
----------------------------------------------------------------------

Every program (editor, widget, app, daemon) that runs in the user's
session must register itself in the SHARED, DURABLE xyzfs runtime
ledger. The ledger lives in the CURRENT USER'S xyzfs tree — the same
tree where avatars, wallets, and projects live — because the user owns
the processes (think `pkill` by user, not by session dir).

LEDGER PATH:
  <house>/<current_xyzfs>/home/runtime/ledger.txt

RESOLUTION CHAIN (three known paths, no config):
  house_root.txt                          — "where is the house?"
    -> <house>/0.user-pal/00.login-signup/current_login.txt
                                          — "who am i?" (current_user_uuid, current_xyzfs)
      -> <house>/<current_xyzfs>/home/runtime/ledger.txt
                                          — "what's running?"

SCHEMA (pipe-delimited, same shape as 101.ledger-player-npc-simple+3):
  timestamp|event|type|project_id|session_root|pid|display_name|inbox_path

  timestamp    — ISO 8601 (e.g. 2026-07-29T07:00:00)
  event        — ONLINE | OFFLINE
  type         — editor | widget | app | daemon
  project_id   — agy-editor | file-menu | mutaclsym | etc.
  session_root — the session dir (PRISC_PROJECT_ROOT at time of rego)
  pid          — process ID of the main/supervising process
  display_name — human-readable label ("text-editor-xyz", "FILE MENU")
  inbox_path   — relative to session_root (e.g. pieces/system/widget_cmds/inbox.txt)

OPS:
  ledger_append <event> <type> <project_id> <session_root> <pid>
                <display_name> <inbox_path>
    — appends one line to the ledger. Resolves the ledger path via the
      three-step resolution chain above. Same shape as the turn-based
      ledger_append.c in 101.ledger-player-npc-simple+3.

  ledger_peers <type>
    — scans the ledger for the latest ONLINE entry of each project_id
      matching <type>, checks that the PID is alive (/proc/<pid>).
      Returns a list of active peers with session_root and inbox_path.
      REPLACES the old focus.txt scan pattern (editor_menu_input.c's
      find_widget_session() which walked &.widgits/file-menu/pieces/
      sessions/*/focus.txt looking for session_root=<editor>).

LIFECYCLE:
  Program start (button.sh run / run-widget):
    ledger_append ONLINE <type> <project_id> <session_root> $$ \
                  "display name" pieces/system/widget_cmds/inbox.txt

  Program stop (cleanup trap, EXIT/INT/TERM):
    ledger_append OFFLINE <type> <project_id> <session_root> $$ \
                  "display name" pieces/system/widget_cmds/inbox.txt

  Crash (no OFFLINE written):
    ledger_peers checks /proc/<pid> — stale entries are skipped
    automatically. No heartbeat, no sweep daemon.

WHY THIS REPLACES THE OLD SCAN PATTERN:
  Previously, the editor discovered the widget by:
    1. Reading house_root.txt
    2. Walking &.widgits/file-menu/pieces/sessions/*/focus.txt
    3. Looking for session_root=<editor_path>

  This was editor-centric (editor initiates, widget waits), fragile
  (depended on focus.txt format and directory layout), and only worked
  for the editor-widget pair — not for general peer discovery.

  The ledger is BIDIRECTIONAL. Every program writes its own entry on
  start. Any program can find any peer by querying the ledger. The
  file is in the USER's xyzfs, not in any project's private session
  dir — so it survives session cleanup and works across projects.

RELATIONSHIP TO WIDGET CMD BUS:
  The ledger handles DISCOVERY (finding peers). The widget cmd bus
  (inbox.txt -> status.txt -> widget_bridge.txt, documented in
  widget+plan.txt and sec. 37 of the companion standards)
  handles COMMAND DELIVERY once a peer is discovered. They are
  separate concerns; the ledger is the address book, the cmd bus is
  the mailbox.

  [ ] New interactive project: gl_window defaults on for `run`
  [ ] widget_capable + run-widget path documented in button.sh help
  [ ] Widget spawn does not require a second human terminal
  [ ] ASCII can be disabled without breaking cmd bus / file state
  [ ] Harness can still assert via frame_history / files when ASCII off
  [ ] Do not design "widget = second TTY session the user must open"

36.1 Default: harness LIVES INSIDE the project under test

36.3 Cross-project / multi-instance harnesses (the one people forget)
---------------------------------------------------------------------

When the feature under test **is the interaction between two (or more)
running projects**, the harness does **not** belong inside only one of
them. It lives as a **sibling house directory** (often `#.`-prefixed
tooling), with scenarios that start/stop both sides.

Canonical example:

  #.drag-drop-test/
    button.sh
    ops/          # dd_set_positions, dd_drag_drop, dd_check_import, …
    scenarios/    # test_basic_import.sh
    README.txt

  Proves: muchi-pals egg_window → mutaclsym gl_mirror pet import.
  Neither project alone owns that story.

Other multi-process examples living *inside* one repo when both
"instances" are the same app (two sessions of chat):

  044.pal-chat-irc…/test-harn-same/scenarios/demo_2user_chat.sh
  → still under chat's harness, because both sessions are that project.

Rule of thumb:

  - Same project, N sessions  → stay under that project's test-harn-same
  - Project A × Project B      → house-level `#.<feature>-test/` (or
    exchange/ harness), ops may call both button.sh paths

For file-menu **as widget of editor** (GL spawn + LOAD into buffer):

  Option A (preferred once both exist):
    &.widgits/file-menu/test-harn-same/scenarios/demo_editor_load.sh
    → scenario starts editor session + widget session, asserts files
    (widget owns the cross-story because the feature is "widget drives
    host"; editor keeps its own unit harness for canvas typing)

  Option B (if the cross-story grows to many hosts):
    #.widget-host-test/ or #.file-menu-integration-test/
    → same shape as #.drag-drop-test

Both are valid; pick A until a second host needs the same harness.

Tightening 36.4 into something that can't be waved through by a green
proof/ dump, per #.haiku+/tpmos-re-dox/_.0.aigent-testing-k3.txt's own
three-level matrix (module/op level, black-box runtime, end-to-end
user flow — see that doc's Principle 2):

  - Level 1 (op-level, direct state/op assertions) alone NEVER earns a
    PASS / "works together" verdict in a harness README, USER_REPORT,
    or button.sh output. It is a real, valuable SUPPLEMENT (fast,
    precise, great for isolating a bug once level 2 finds one) —
    never a replacement. Say so explicitly in the harness's own
    README if it is currently level-1-only; do not let the claim
    outrun what was actually proven.
  - Level 2 (black-box) is the floor for any "X and Y work together"
    claim. Mechanics, exactly:
      * Key injection ONLY via pieces/keyboard/history.txt, format
        `[YYYY-MM-DD HH:MM:SS] KEY_PRESSED: <code>` (fixed timestamp
        is fine — see k3 doc's own dynamic-`date`-command pitfall).
      * NEVER write directly into interact_relay.txt to fake a
        keypress for a test. That file is populated BY
        chtpm_parser_pal relaying FROM keyboard/history.txt for
        pieces whose layout declares <interact src="...">; writing it
        directly skips the exact relay code path a real keystroke
        exercises, which defeats the entire point of testing at this
        level. (A direct, synchronous write into a WIDGET's own
        interact_relay.txt from a DIFFERENT process — e.g. editor's
        own do_fm() waking an already-known-alive file-menu — is a
        real, legitimate production signal, not a test shortcut; the
        rule above is about what a TEST harness does to itself, not
        about banning that pattern everywhere.)
      * Assert against RENDERED evidence (current_frame.txt content,
        pieces/display/frame_changed.txt growth, or a project's own
        pieces/debug/frames/session_frame_history.txt) IN ADDITION TO
        state-file assertions, never state files alone — a state file
        can be correct while the frame a real user would see is
        stale, which only frame evidence catches.
      * No-DISPLAY / headless is not an exemption — !.local-ux-
        testing-ai.txt and the k3 doc's own headless-safe subset
        (parser + renderer only, no live keyboard capture required)
        both already show how to do level 2 with zero real tty.
  - Mandatory Post-Test Report Gate: every harness run that claims a
    PASS/FAIL verdict publishes, before any code change lands on top
    of that result:
      FRAME_REPORT_<YYYYMMDD-HHMM>_<topic>.txt
    at the calling project's (or house) root — test scope, exact key
    injections performed, frame evidence lines (timestamps +
    snippets), PASS/FAIL/INCONCLUSIVE per level, explicit "safe to
    proceed with code changes" line. A harness's own proof/ directory
    of raw state dumps is NOT this report — the report is the
    human-readable verdict layer sitting on top of it.
  - RETROFIT RULE: an existing harness discovered to be level-1-only
    is not grandfathered. Its own README/USER_REPORT PASS language
    must be corrected to say what was actually proven ("cmd-bus
    contract only", etc.) until a level-2 pass is added alongside it —
    same requirement PITFALL 21 already put on pal-chat-irc.

37. RELATIVE PATHS HOUSE-WIDE — NO HARDCODED ABSOLUTE CROSS-PROJECT
    PATHS (2026-07-30)
========================================================================

RULE: any path stored in a registry/config file (model_list.txt-style
pipe-delimited rows, .pdl files, project.pdl, anything a human or a
future reorg might touch) that points at ANOTHER project - a sibling
directory under the same house root, a shared-ops source, an asset
generator, anything outside the referencing project's own tree - MUST
be stored RELATIVE to the referencing project's own project_root, never
as a hardcoded absolute filesystem path. This applies retroactively:
if you find one while working on something else, fix it in the same
pass (small, cheap, exactly the shape of PITFALL 60's own fix), don't
leave it for later.

WHY: this house has been renamed/reorganized more than once already -
directly observable evidence, not a hypothetical: PITFALL 60 (this
section's own citation) found a hardcoded absolute path
(`/home/no/Desktop/🤖️🪤️🏠️/🚽️🧻️/🚽️🥡️-00.00/ZEST-10.00/x0.parent-level-
dev-env-03.00/#.ref/^.IQABOD-llm-06.00`) sitting in a live registry file,
pointing at a directory tree from a PRIOR naming generation that no
longer exists at all under the CURRENT one
(`🥡️🪜️/🪜️-00.00/NNEST_CLEAN_PARENT/.../44.xyz❤️‍🔥️00.10`). The
dependent feature (an AI chat provider) had been silently, completely
broken as a result - no crash, no visible error, just a forked child
that `chdir()`'d into nothing and exited 127 every single time it was
used. This class of bug is uniquely dangerous in this house specifically
BECAUSE the file-mediated-relay architecture (§ everywhere in this
document) makes failures quiet by design - a failed fork/chdir/exec
doesn't propagate an exception up a call stack the way an in-process
function call would; it just silently fails to produce a file another
process is waiting on, and whatever's waiting either times out
unremarkably or (worse) proceeds with stale/empty data as if nothing
went wrong.

HOW: two projects under the same house root are SIBLINGS - resolve a
cross-project reference as `project_root + "/../" + <sibling dir name>`
(or however many `../` hops are actually needed for the real directory
depth - most references in practice are one hop, since most projects
sit directly under the house root). The house root itself moving/
renaming does NOT break this, because siblings move together as a unit
during a reorg - only the ancestor wrapper directories get renamed, the
relative structure between projects has stayed intact across every
reorg this house has been through so far. Do NOT try to resolve relative
to the CURRENT WORKING DIRECTORY at the time of use instead of
project_root - cwd is not a reliable anchor (may or may not equal
project_root depending on how the calling op was invoked/forked); every
op in this house family already has a `project_root` global populated
from `PRISC_PROJECT_ROOT` (or discovered) - anchor relative paths to
THAT, consistently, the same way every other path in this house's own
ops already does for in-project paths.

BACKWARD COMPATIBILITY: code resolving one of these paths should still
accept a literal absolute path (a string starting with `/`) as an
intentional manual override/escape hatch - just don't SHIP a hardcoded
absolute path as the default/committed value in a registry file. See
send_message.c's own iqabod-branch fix (PITFALL 60) for the exact
shape: `if (value[0] == '/') use as-is; else resolve against
project_root`.

SCOPE NOTE: this section governs NEW cross-project path references and
retroactive fixes found in passing - it does NOT mandate a dedicated,
standalone house-wide audit sweep of every existing path reference as
its own project (that would be a real, separately-scoped undertaking,
not a quick addition to this document). Fix what you find; don't go
looking exhaustively unless separately asked to.

37.1 The gotcha this rule almost missed: project_root is often a
     SESSION directory, not the true top-level project directory

Resolving a cross-project relative path against raw `project_root`
(the variable's own literal value at the point of use) is NOT
automatically correct just because it's relative instead of absolute -
PITFALL 60's own UPDATE section (2026-07-30, same day as the rule
above) found this the hard way: this house's own session-isolation
convention means `project_root` is frequently the SESSION-SCOPED
directory (e.g. `<project>/pieces/sessions/<id>/`, confirmed via direct
read of button.sh's own `PRISC_PROJECT_ROOT="$SESSION_DIR"`), not the
true top-level project directory sibling projects actually live beside
- a relative path that looks correct and tests correct from a manual
CLI invocation (run directly from the top-level project dir, no session
nesting) can silently resolve to the wrong, nonexistent location for
every REAL run through the actual app.

FIX SHAPE: before resolving a CROSS-PROJECT relative reference, strip
any trailing session-dir suffix to recover the true top-level project
root first (`derive_true_project_root()` in
045.muchi-pal-agent🤖️+1/ops/send_message.c is the reference
implementation - strips a trailing `/pieces/sessions/<id>` suffix,
falls through unchanged if not present, so it's safe to call
unconditionally regardless of whether the caller is session-scoped or
not). IN-project paths should keep resolving against raw project_root
directly, unaffected - this normalization is ONLY needed for references
that cross project boundaries.

VERIFICATION IMPLICATION: this is also a real, concrete instance of why
§36.6's own "prove it through the real running app" rule exists, not
just an op-level/CLI-level check - the CLI-level test for this exact fix
passed cleanly and was reported as verified; only a real level-2
harness scenario (real key injection through the real running app,
which necessarily runs session-scoped) caught that it was wrong.

38. SYNTHETIC KEY INJECTION PROVES DATA IS CORRECT, NOT THAT THE
    INTERACTION CONTRACT IS — WHEN A REFERENCE ARCHITECTURE EXISTS,
    DIFF AGAINST ITS OWN UX, NOT JUST ITS OUTPUT SHAPE

A "level-2" harness (§36.6 - real key injection through the real running
app, not an op-level shortcut) is necessary but was found, THREE
SEPARATE TIMES in one week, to still not be sufficient - each time
because the harness reached its assertion via the MECHANICALLY
SHORTEST path (a single deliberate file write, an op's own PASTE mode,
or jumping straight to a "confirm" control by digit) instead of the
NATURAL interaction order a real human actually uses (type character by
character, then press the domain-natural terminator - typically Enter -
expecting it to submit; press Esc expecting it to only stop typing, not
leave the whole screen).

THE THREE REAL INCIDENTS (2026-07-30, same week, cited together because
they're the same root pattern, not three unrelated bugs):
  1. The chtpm_parser_pal.c/gl_mirror.c dual-capture typing-doubling bug
     - invisible to any harness because synthetic injection writes
     exactly ONE line per intended character, deliberately - it cannot
     reproduce a race between two independent real OS-level capture
     processes. See PITFALL 63 for the harness-methodology write-up;
     this is the "why the doubling itself was possible" root cause.
  2. 102.agy-txt's own SAVE AS path-field display bug (still open at
     time of writing, xyz-agy-handoff-j30.txt in that project) - its
     own harness (test-harn-agy-txt) used PASTE mode for ALL path
     typing, so real single-keystroke typing into that specific field
     was NEVER exercised by anything before a live human tried it.
  3. &.widgits/file-menu's own file_browser mode - three real bugs
     (Enter-on-the-typed-field does nothing, Esc always exits the whole
     browser instead of just deactivating typing, no cursor indicator
     rendered) sat undiscovered inside an ALREADY-GREEN, ALREADY-SHIPPED
     harness (test-harn-ed-app) because that harness always used PASTE
     plus direct digit-jumps straight to the confirm button - it never
     once pressed Enter while sitting on the file field, and never
     pressed Esc mid-typing. See todo-how2-j30.txt in that project for
     the full account, including the exact reference comparison below.

THE RULE: when a level-2 harness scenario involves typed input, at
least one pass through it must use the NATURAL order - real per-
keystroke injection ending in the domain-natural terminator the field
itself is supposed to react to (Enter to submit, Esc to cancel-typing)
- not just PASTE-then-jump-to-a-separate-confirm-control. PASTE/digit-
jump shortcuts remain correct and useful for the OTHER assertions in
the same scenario (there is no need to re-type every marker string
character-by-character every time) - the rule is narrower: cover the
natural path AT LEAST ONCE per typed-input feature, don't cover it
NEVER.

THE REFERENCE-ARCHITECTURE CASE, SPECIFICALLY (why this document calls
it out beyond the general rule above): when the code under test is an
explicit PORT/MIRROR of a reference architecture that already has its
own real, working interaction contract (TPMOS's `<cli_io>` elements,
confirmed via 014.wsr-pal💸️📌️+2/system/chtpm_parser_pal.c's own
`strcmp(el->type, "cli_io")` branch: Enter SUBMITS and the field STAYS
focused, a real engine-level focus/active state exists distinct from
mere row-selection) - proving the PORT's output DATA matches the
reference's is not the same claim as proving its INTERACTION matches.
file-menu's own file_browser mode produces byte-correct saved files
(proven, repeatedly, by its own harness) while having a completely
different, and broken, interaction contract from the cli_io convention
its own sibling projects (102.editor, 102.agy-txt) already use - Enter
does nothing on the typed field, Esc has no narrower scope to fall back
into. Two architectures can agree on END-STATE data while disagreeing
on everything about HOW a user gets there.

FIX SHAPE / HOW TO GUARD AGAINST THIS GOING FORWARD: when porting or
building alongside a named reference architecture, read (or re-read)
that reference's own interaction contract for typed-input fields
specifically - does Enter submit-in-place or require a separate
confirm step; does Esc deactivate-only or exit the whole screen; is
there a visible focus/cursor indicator - and write it down (even one
paragraph) BEFORE trusting a PASTE-only harness as proof the port is
done. Same discipline §36.6 already demands for data correctness,
extended explicitly to cover UX/interaction-order correctness, which a
green data-only harness cannot see.

SEE ALSO: PITFALL 63 in !.xyzos-pitfalls+1.txt (the full incident
write-up); 102.agy-txt/xyz-agy-handoff-j30.txt; &.widgits/file-menu/
todo-how2-j30.txt (the concrete, cited, per-bug reference-comparison
this rule generalizes from)

39. HARNESSES MUST BE BUILT TO K3 HUMAN-INPUT-PARITY - NON-NEGOTIABLE,
    NOT A GUIDELINE

Direct instruction, 2026-07-30, stated as non-negotiable: every harness
in this house testing user-facing interaction MUST be built to the
standard in `#.haiku+/tpmos-re-dox/_.0.aigent-testing-k3.txt` (the "K3
testing guide") - real key injection through the real running app,
real frame/state evidence, and critically, the SAME interaction a real
human actually performs, not the mechanically shortest path to an
assertion. K3's own PITFALL 5 names this exactly: "False confidence
from op-only tests - direct op passes do not prove end-to-end
editor/save/load/script/play behavior." §38 (above) already covers the
typing-order half of this (Enter-submits, Esc-scoping); this section
is the CHECKLIST - concrete, mandatory dimensions a save/load-shaped
harness must cover, derived from three real bugs THIS HOUSE's own
harnesses missed in one week specifically because they took a
mechanical shortcut instead of the real human path:

  1. Real per-character typing into any live text field (not PASTE
     alone) for at least one pass per field - §38's own rule.
  2. Real Enter-submits AND real Esc-only-deactivates, both directions
     - §38's own rule.
  3. SELECTING A REAL LISTED ENTRY from a directory/file browser (real
     arrow-nav to it, one real Enter) - not just typing/pasting a path
     directly. Missed for a full week in this house's own file-menu
     widget: one real Enter on a listed file used to only pre-fill a
     text field, requiring an unsignaled SECOND Enter to actually load
     - found only by a human clicking a real file, never by any
     harness, because every harness always typed/pasted the path
     instead of ever selecting from the real listing. See
     @.apps/text-editor-xyz/test-harn-ed-app/scenarios/
     demo_fm_click_to_load.sh for the worked reference implementation
     - filter the listing to a known-unique fixture via a real SEARCH
     field first (so the target entry's index is deterministic
     regardless of whatever else a real user's own files put in the
     same directory), then real-arrow-nav to it, then ONE real Enter,
     then assert the real downstream effect (buffer content, rendered
     frame) - not just that a command was "sent."
  4. DIGIT-JUMP vs DIGIT-JUMP-AND-ACTIVATE, asserted EXPLICITLY, not
     inferred. A harness that always sends a digit press immediately
     followed by a real Enter cannot tell whether the underlying code
     jumps-only (the real standard - every chtpm-native buttoned
     layout in this house already follows it) or jumps-AND-activates-
     in-one-keystroke (a real, separate bug this house's own file-menu
     widget had for as long as it existed, invisible to every prior
     harness for exactly this reason). Assert the STATE immediately
     after the digit alone, BEFORE sending Enter, showing the mode/
     screen has NOT changed yet - see demo_fm_click_to_load.sh's own
     "digit press alone moved cursor... did NOT activate it" assertion
     for the concrete shape.
  5. A real on-disk file-existence check after any save-shaped action
     - not just a status message claiming success. Direct instruction,
     2026-07-30: "the harness should have tested for the creation of
     the file." A status line can say "ok" while nothing real landed
     anywhere findable (confirmed real bug, save-bug.txt).
  6. If the feature has any real containment/jail boundary (this
     house's own xyzfs user-home jail, see save-bug.txt), a real
     escape-attempt test - real `../` sequences typed through the real
     field, asserting BOTH a real rejection status AND that nothing
     landed at the real would-be-escaped target. Never trust that a
     jail exists just because the code that's supposed to enforce it
     was written - prove it against a real attempt.

WHAT THIS DOES NOT MEAN: rewriting every assertion in every scenario to
use the slowest, most literal path always. PASTE/digit-jump shortcuts
remain correct and valuable for assertions that are NOT the specific
interaction being proven (e.g. establishing a known starting state
before testing something else) - the rule is that the real human path
must be covered AT LEAST ONCE per interaction pattern in a project's
own harness suite, not that every single line of every scenario must
avoid every shortcut forever.

A NOTE ON HARNESS RELIABILITY ITSELF (2026-07-30, same day): running
several full app-launch-and-teardown cycles back-to-back with minimal
settle time between them produced one real, non-reproducible-on-retry
flake (all captured state/proof files from the failed run matched
expected values exactly when inspected afterward - point-in-time
evidence contradicted the pass/fail verdict, meaning the race was in
the RUN, not the assertions). Give a real app launch genuine settle
time before injecting the first key, and don't chain many full app
launches with zero gap between them, especially soon after any host-
level disruption (a reboot, a crash) where system load hasn't
stabilized yet.

guide itself); §38 above (the typing-order half); PITFALL 63 (the
original false-confidence incident); @.apps/text-editor-xyz/

41. EACH SCREEN GETS ITS OWN <module> - THE REAL STANDARD NOW (2026-07-31,
    supersedes the "one shared module per project" framing this house
    defaulted to until now)
========================================================================

DIRECT INSTRUCTION, confirmed against real TPMOS precedent before
adopting: "files that are shared across pages are handled by an
orchestrator in a separate fork, and then pages will have unique
functionality to them, that will be run as a module in a new fork."
Checked against the real reference source (`/home/no/Downloads/
1.TPMOS_c_+rmmp.0100.0110/pieces/chtpm/plugins/orchestrator.c`,
`chtpm_parser.c`) before rolling this out - both halves are real:

  - Shared infrastructure (keyboard/joystick/render/parser threads) IS
    already a separate, always-alive orchestrator process in every
    project's own system/orchestrator.c - this part was never broken,
    nothing to change here.
  - `launch_module()`'s own real liveness check (`strcmp(launch_str,
    current_module_path) == 0 && current_module_pid > 0` -> reuse,
    else kill+fork+exec) already supports a genuinely distinct
    `<module>` string PER SCREEN, not just per project - it was simply
    never used that way anywhere in this house before 2026-07-31.

WHAT CHANGES: every real screen (`.chtpm` layout) in a project should
declare its own dedicated `<module>` (e.g. `pal/pets_module.pal`, not
a shared `pal/main_loop_chtpm.pal` used identically by every screen).
Each new per-screen module can still call the SAME shared ops the old
single module called (splitting those ops into per-screen dedicated
files is a real, separate, further step - not required for this part).
Proven first in 01.muchi-pals-🥚️-13.01 (all six of its own screens),
confirmed via direct `debug.txt` evidence: real kill+fork+exec exactly
on genuine screen-to-screen navigation, real process reuse while
staying on one screen, no orphaned processes, correct first-frame
render. See 01.muchi-pals-🥚️-13.01/dox/06-per-screen-module-standard.md
for the full write-up and the house-wide rollout scope (every other
multi-screen project still needs this same split as of this writing).

WHAT DOES NOT CHANGE: §16 above (INTERACT is only for continuous, real
map/cursor movement, never a pure discrete menu) is still correct and
is a SEPARATE concern from this section - §16 is about which
INPUT MECHANISM a screen uses (${piece_methods} vs onClick="INTERACT"),
this section is about whether that screen's own module is a distinct
process from its siblings'. A pure discrete-menu screen still uses
${piece_methods}, it just now also gets its own `<module>` line instead
of sharing one with every other screen in the project.

REAL BUG FOUND DURING THIS ROLLOUT, NOT LIMITED TO THE MODULE SPLIT
ITSELF: giving screens their own modules is what surfaced PITFALL 66
(clear_saved_active_index() missing from every local, unsynced copy of
chtpm_parser_pal.c in the house) - a real, house-wide, pre-existing gap
that any real layout transition can hit (not specific to per-screen
modules), just made more visible by testing more transitions. Any
project adopting this section's own per-screen split should get
PITFALL 66's fix ported into its own chtpm_parser_pal.c copy at the
same time, not as an afterthought - see that pitfall entry for the
exact fix shape.

42. WHEN A SMALL LOCAL LLM NEEDS TO RENDER A JUDGE/VERDICT DECISION:
    DECOUPLE "DESCRIBE" FROM "CLASSIFY" BEFORE REACHING FOR A BIGGER
    MODEL — STANDING RULE, NOT A ONE-OFF FIX
========================================================================

DIRECT USER FRAMING (2026-08-02), stated as a standing priority, not
just a fix for one project: "i think its a big deal that we try to make
it work b4 going up 2 larger model." This section makes that a house-
wide rule for ANY project asking a small local LLM (this house's own
gemma3:270m, in practice) to render a binary/classification verdict -
APPROVED/REJECTED, A/B, WIN/LOSE, SAFE/DANGEROUS, or similar.

THE RULE: never ask the small model to directly classify. Ask it an
OPEN-ENDED DESCRIBE question about the same content instead (what it is
demonstrably good at - real, accurate, content-aware recall/description
when the task doesn't require it to also collapse that knowledge into a
decision), then run YOUR OWN deterministic keyword/sentiment scorer over
the real response text to derive the verdict. This is the SAME
"deterministic dispatch over free text, never another LLM self-
judgment" doctrine §"gemma_strategy.c" already established for tool-
detection (045.muchi-pal-agent🤖️+1's own real, live-tested finding:
"gemma is too small to reliably follow a TOOL: format, so tool
detection is fully deterministic and keyword-based, decided BEFORE any
LLM call") - PITFALL 69 confirms this generalizes from tool-detection
to judge/verdict tasks too, and is a DIFFERENT, separate finding from
the tool-format one (a model can have genuinely poor zero-shot self-
classification even when its underlying knowledge recall is accurate -
these are not the same capability).

WHY THIS MATTERS ENOUGH TO BE A STANDING RULE, NOT JUST A PITFALL: the
easy, tempting first move when a small model's own verdict "doesn't
seem right" is to reach for a bigger model (this house already has
gemma3:1b available on the same LAN box specifically for this reason -
see model_list.txt's own gemma-lan-1b entry). That IS a real, valid
fallback (live-tested, PITFALL 69: 1b got 6/6 correct with real
explanations on the exact test case that broke 270m) - but it should be
the FALLBACK, tried AFTER the describe+deterministic-score pattern,
not the default first reach. On the one real case tested so far
(PITFALL 69), describe+deterministic-score on the SAME small 270m model
matched the bigger model's own 6/6 correctness, with zero need to
upgrade at all - meaning the "problem" was never really model size, it
was asking the wrong SHAPE of question.

CONCRETE CHECKLIST for any project building a judge/verdict mechanic
against a small local LLM:
  1. Does the task require the model to CLASSIFY (pick between 2+ fixed
     options) rather than DESCRIBE/RECALL (produce open-ended text)? If
     classify: this section applies.
  2. Rewrite the prompt to ask for a description/explanation of the
     relevant content instead of a direct verdict.
  3. Write a small, hand-authored, auditable keyword/sentiment scorer
     over the real response text (a short positive-keyword list vs.
     negative-keyword list, simple counting, deterministic tie-breaking
     toward whichever default is "safer"/more conservative for the
     domain - see PITFALL 69's own example scorer).
  4. Test BOTH an obviously-should-pass case and an obviously-should-
     fail case, multiple trials each (N=1 is not enough - PITFALL 69's
     own first pass looked like a hard bias at N=2, turned out to be a
     strong-but-not-total bias at N=6), through the REAL production
     code path, not a one-off manual curl - build this as a real
     `test-harn-same/` scenario (see PITFALL 69's own
     demo_fda_review_discrimination.sh) so the finding is repeatable
     and the harness itself becomes a regression guard if a future
     prompt change reintroduces poor discrimination.
  5. Only escalate to a bigger local model (or an external API) if step
     2-3's own pattern still fails the step-4 test after real attempts
     at both a naive AND a reframed/few-shot describe-prompt - and
     document what was tried, same as PITFALL 69 does, so the next
     project doesn't re-spend the same effort finding this out again.
