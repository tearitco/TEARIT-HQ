# 🧑‍⚖️🔮 THE DESCRIBE-DON'T-CLASSIFY THEORY — how a tiny local model can judge things it can't decide, and what that means for 🌱IQABELLA and 🐋T@Q/tomo

> **STATUS:** Theory doc, grounded in ONE real, live-tested incident (`@.apps/my-biotech`'s FDA_REVIEW mechanic, `PITFALL 69` in `!.xyzos-pitfalls+1.txt`, `§42` in `!.xyzos-standards+1.txt` — read both before this doc, they're the primary evidence, this doc is the wider theory built on top of them). Everything about the CORE finding is real and measured. Everything about how it EXTENDS to 🤖045-agent/RL/BT-FSM/🐋T@Q/🌱IQABELLA is reasoning FROM that evidence, not yet separately tested against those systems — flagged clearly section by section.

---

## 📖 0. THE ONE-SENTENCE VERSION

**A small local model (`gemma3:270m`) can't reliably CLASSIFY content into a verdict zero-shot, even when it demonstrably HAS accurate knowledge about that exact content — but it CAN reliably DESCRIBE it — so build a deterministic classifier that reads the description instead of asking the model to self-judge.**

---

## 🔬 1. THE REAL EVIDENCE (recap — full detail in PITFALL 69)

Two test cases, run live against `gemma3:270m` on the LAN Ollama box, N=3-6 trials each:

| Prompt shape | Lethal compound (should REJECT) | Safe compound (should APPROVE) |
|---|---|---|
| 🎯 Direct classify ("Answer APPROVED or REJECTED") | ❌ 2/3 wrong (said APPROVED) | ✅ 3/3 correct |
| 🔄 Reframed classify ("SAFE or DANGEROUS", danger option listed first) | ❌ 3/3 wrong (said SAFE) | — |
| 💬 Classify + explain ("...followed by a colon and one sentence why") | ❌ still wrong, AND explanation was empty/non-substantive ("Approved", "AN APPROVED" — zero real content) | — |
| 📝 **Open-ended DESCRIBE** ("Describe the safety concerns in one sentence") | ✅ 3/3 gave real, honest, content-aware text ("highly toxic and potentially fatal") | ✅ 3/3 correct ("generally safe... mild stomach upset") |

**The tell:** when asked to explain a classify-answer, the model produced NOTHING — no real reasoning trace at all. When asked to describe instead of classify, it produced real, accurate, detailed content EVERY time. This isn't "the model is bad at chemistry" (it clearly knows real chemistry — the `ENRICH` calls in `my-biotech`'s own FSM prove this independently, same model, same session). It's that **collapsing knowledge into a binary decision is a genuinely different capability from recalling the knowledge**, and it's the capability that fails first as model size shrinks.

**The fix that worked:** ask for the description (what it's good at), then run a small, hand-written, auditable keyword/sentiment scorer over the REAL response text to derive the verdict ourselves. Matched a bigger model's own accuracy (`gemma3:1b`, 6/6 correct with real reasoning) WITHOUT needing to upgrade — the "problem" was never model size, it was asking the wrong SHAPE of question.

---

## 🧩 2. WHY THIS ISN'T A NEW IDEA — IT'S 045-AGENT'S OWN PATTERN, CONFIRMED TO GENERALIZE

`045.muchi-pal-agent🤖️+1`'s own `gemma_strategy.c` already established, independently, months before this incident: *"gemma is too small to reliably follow a TOOL: format, so tool detection is fully deterministic and keyword-based, decided BEFORE any LLM call."* That's the SAME shape — don't trust the small model's own structured self-output, trust deterministic code reading its free text (or, in that case, the user's own free text) instead.

**What PITFALL 69 adds that wasn't previously confirmed:** this doesn't just apply to *tool-call format* reliability. It applies to *judgment/verdict* reliability too — a genuinely different capability, and one that's easy to assume is "just a formatting problem, ask more clearly" until you actually measure it (the reframe/reorder/explain experiments in PITFALL 69 all failed before the describe-reframe worked — worth internalizing that "the model didn't understand the format" and "the model can't do this task shape at all, regardless of format" LOOK similar from outside and need separate diagnosis).

**Standing rule, now written into `!.xyzos-standards+1.txt` §42:** any time a small local model needs to render ANY kind of decision — tool selection, verdict, ranking, comparison, classification — try decoupling "describe what you know" (LLM) from "decide based on what you're told" (deterministic code) BEFORE reaching for a bigger model.

## 🎮 3. HOW THIS SHOWS UP IN BT/FSM GAME-AI PIPELINES (this session's own worked examples)

Both `my-biotech` and `my-lawyer` (design doc, `@.apps/my-lawyer/MY_LAWYER_DESIGN.md`) already encode this as a real FSM shape, independent of the judge-specific finding:

```
SELECT (weighted-random, deterministic, our own code)
  ↓
DESCRIBE/RESEARCH (the LLM call - open-ended, what it's good at)
  ↓
CLASSIFY/RECORD (deterministic code reads the LLM's own free text,
                 derives a decision/verdict/score - never another LLM
                 self-judgment)
```

This is directly the "shared `bot::*` vocabulary" concept named (but not yet built) in `#.haiku+/30.jul-30-handoff/2.ai/2-independent-ai-systems.md` §4 — a primitive that could be shared across EVERY BT/FSM-driven agent in this house (test bots, my-biotech's research agent, my-lawyer's case-builder, a future `genesis-txt` NPC opponent) rather than each project re-deriving it. **Concretely buildable, not yet built:** a small reusable op, something like `describe_then_classify.+x <persona> <question> <keyword_lexicon_file>`, that any project's own FSM step could call instead of hand-rolling its own version (as `my-biotech`'s own `mybiotech_fda_verdict.c` currently does, self-contained, matching this house's no-shared-headers convention for now — a real candidate for later consolidation once 2-3 projects independently need the same shape, per that convention's own "duplicate until a real third user justifies sharing" spirit).

## 🎯 4. HOW THIS SHOULD CHANGE `ROADMAP-models.txt` §11.2'S OWN "LLM-AS-JUDGE" RL PLAN

`ROADMAP-models.txt` §11.2 (real, existing design, self-labeled "nothing built") sketches an auto-training loop where an LLM judges IQABOD's own generated outputs to produce a reward signal, feeding a future RL loop. **This theory doc's real, direct implication:** if that judge call is shaped as "here's IQABOD's output, rate it 1-5" (a direct classify), it will likely suffer the EXACT same failure mode PITFALL 69 measured — a small/cheap judge model (which is what you'd WANT to use for a high-volume RL reward loop, for cost/speed reasons) may produce a reward signal that looks plausible but doesn't actually track output quality, silently poisoning the whole training loop with a broken signal nobody would notice until the trained result came out wrong.

**The fix generalizes directly:** don't ask the judge model "rate this 1-5." Ask it to DESCRIBE what's good/bad about the output in its own words, then run a deterministic scorer over that description (keyword-weighted, or even something as simple as description length/specificity as a rough proxy, tuned against a small hand-labeled validation set) to derive the actual 1-5 reward signal. This is MORE work to build than a bare "rate this" prompt, but PITFALL 69's own evidence says the bare version may simply not work at small model sizes — worth building the describe+score version FIRST, not discovering the bare version's brokenness after a training run already burned real compute on a bad signal.

**Not yet tested against IQABOD/RL specifically** — this section is reasoning FROM the my-biotech evidence, not a separate confirmed finding. Flagged honestly: if someone builds §11.2's judge loop, the FIRST thing to do is run the SAME kind of N=6-trial discrimination test PITFALL 69's own harness does (`test-harn-same/demo_fda_review_discrimination.sh` is a direct, reusable template) against whatever judge prompt is chosen, before trusting it to drive real training.

## 🌱 5. THE BIG ONE: WHAT THIS MEANS FOR IQABELLA (teacher/student distillation)

**IQABELLA's own design** (per `045.muchi-pal-agent🤖️+1/$.zest-er-summary`, DESIGN ONLY, not built — see `2-independent-ai-systems.md` §2 for the verified real/design split): gemma (teacher, genuinely coherent) → harvest real conversation transcripts → train IQABOD (student, currently "word-salad," needs real training data) on them.

**The naive version of this** just harvests gemma's raw outputs as unlabeled training text. **The describe-don't-classify theory suggests a real, concrete upgrade, buildable on top of the SAME harvesting infrastructure the design already calls for:**

- Anywhere IQABELLA's own harvest pipeline captures a gemma response that's ANSWERING AN OPEN QUESTION (description, explanation, recall) — that's exactly the shape PITFALL 69 confirms gemma is reliable at. Harvest it directly, high confidence it's real signal, not noise.
- Anywhere the harvest pipeline WOULD have captured gemma making a direct judgment/classification call (a "which is better, A or B" or "rate this" style turn) — **that's exactly the shape PITFALL 69 says NOT to trust at face value.** Two real options, not mutually exclusive:
  1. **Don't harvest those turns as ground truth at all** — they may be teaching IQABOD gemma's own unreliable-judgment bias, not a real skill.
  2. **Harvest them as (describe, deterministic-verdict) PAIRS instead of (question, raw-answer) pairs** — i.e., apply PITFALL 69's own pattern AT HARVEST TIME: reformulate the training example so IQABOD learns "here's a description, here's the derived verdict" (a task IQABOD itself might eventually learn to do reliably via the SAME externally-verified deterministic scoring, rather than inheriting gemma's own unreliable self-judgment habit).

**This is a real, concrete, buildable refinement to a design doc that already exists** — not a new IQABELLA feature request, a correction to how its harvest step should treat judgment-shaped transcripts specifically, grounded in real measured evidence from a completely different project (`my-biotech`) that happened to surface the underlying capability gap first.

**Not yet tested against IQABELLA/IQABOD specifically** (IQABELLA has zero code yet per the verified state table in `2-independent-ai-systems.md`) — this is a design-time recommendation for whoever builds the harvester, not a confirmed result.

## 🐋 6. WHAT THIS MEANS FOR TOMO / T@Q (tomom@qroq)

**T@Q's own real architecture** (verified, `#.resume/ai-dev-resume-aug1.txt`): NOT a transformer like IQABOD — a much smaller, per-curriculum "expert weights" model (7 floats per vocab entry: embedding/pe/weight/bias1-4; forward pass = attention over the whole vocab → residual → small MLP → output layer), one trained matrix set per subject curriculum (Astronomy, Biology, Chemistry, ... 10 subjects, each already beating its own uniform baseline as of 2026-08-01).

**Two live-relevant implications, reasoning from the same theory:**

1. **T@Q is almost certainly EVEN MORE capacity-constrained than `gemma3:270m`** (a real, general-purpose transformer, however small) — a per-curriculum expert with a tiny MLP head is architecturally suited to narrow recall/generation within its own trained subject, and there's no reason to expect it would be BETTER than gemma3:270m at self-classification/judgment tasks. If T@Q is ever asked to do anything judge-shaped (e.g., "is this generated Astronomy sentence good," a natural next step once its own MoE router (`chatbot_moe_v1.c`) needs to pick between candidate completions), **assume the same describe-don't-classify pattern applies, likely even more strongly** — don't ask T@Q to self-rate its own output; if a judge is needed, use gemma (or a deterministic scorer over T@Q's own output text) instead of asking T@Q to judge T@Q.

2. **T@Q's own curriculum training data could benefit from the SAME harvest-time correction as §5's IQABELLA recommendation** — if any of T@Q's 10 curricula's own source corpus (`curriculum/<Subject>/<Subject>.txt`) ever gets AUGMENTED with LLM-generated training sentences (a natural way to grow a curriculum beyond hand-authored content, similar to `ROADMAP-models.txt` §11.1's own "corpus generation via LLM API" plan for IQABOD), the same principle applies: sentences that are gemma DESCRIBING/EXPLAINING a subject-matter fact are high-confidence-reliable training data; sentences that would require gemma to have JUDGED something first (e.g., "here's the best example sentence for teaching X" — an implicit ranking/classification task) are exactly the shape PITFALL 69 says to distrust, and should either be avoided or reformulated as a describe+deterministic-score pipeline first.

**Not yet tested against T@Q specifically** — T@Q's own architecture wasn't examined for this doc beyond the verified summary in `ai-dev-resume-aug1.txt`; this section is theory extension, flagged as such.

## 🪜 7. THE ESCALATION LADDER, RE-READ THROUGH THIS LENS

`ai-dev-resume-aug1.txt`'s own "dream" escalation ladder: gemma handles small stuff → hands UP to llama3/opencode for management review → instructions back DOWN → loop, with the human barely involved. **A direct, useful reframe of PITFALL 69's own finding onto that ladder:** the ladder doesn't need to escalate on EVERY task gemma struggles with — specifically for JUDGE-SHAPED tasks, the fix isn't necessarily "hand it to a bigger model," it's "change what you're asking the small model to DO" (describe, not decide) and let deterministic code own the decision. Escalating model size (gemma3:270m → gemma3:1b → llama3-groq-tool-use:8b → opencode) is still a real, valid tool in the ladder — PITFALL 69 confirms `gemma3:1b` genuinely does better at raw self-classification too — but it should be reached for AFTER the describe+deterministic-score pattern is tried and found insufficient for a given task, not as the first response to "the small model's judgment seems off." This keeps more of the ladder's own weight on the cheap/fast/local tier, which is directly aligned with this house's own stated design philosophy (`#.haiku+/for-user/user.txt`: *"Builds modular, local-first AI/game ecosystems with extreme discipline"*).
