## What the user wants (their own words, distilled)
1. Never store big training data/corpuses on THIS machine (it's zipped and
   shipped daily). Even for the Linux node, store the heavy stuff ON the
   node ("the desktop"), not here.
2. Keep locally only a SMALL, compressed version of the weights.
3. The dream: iQabod holds small weights, and a gemma prompt can "expand the
   compressed weights she currently has, using approximation, asking fill-in
   questions" — i.e. regenerate/restore capability on demand without shipping
   megabytes.
4. Corpora broken up by curriculum, each with its own weights, plus a
   "meta weights" layer. Strictly never all-in-one-place.

## Translation to real ML terms (this IS possible — mostly already designed)
### A. "Compressed weights" ≈ a SEEDED CHECKPOINT, not magic
iQabod's full weights are already tiny (~88KB at 32-token vocab). The real
size problem is CORPUS TEXT, not weights. So:
- The "compressed brain" = **vocab file + weights + the corpus recipe**
  (topic, rung, vocab budget). On disk that's a few KB of manifest.
- "Expansion on demand" = a **train call**. Retraining is ~0.1s on the
  Linux node. The compressed brain IS the seed; expansion is one shell call.
- This is standard **knowledge distillation** when the teacher generates the
  missing knowledge, and **self-instruction / synthetic-data expansion**
  when the teacher "fills in the questions" to close gaps (<UNK>).

### B. "Gemma prompt 2 expand, fill-in questions" = on-demand teacher loop
Honest mechanism (no magic weights needed):
```
small iqabod weights + a gap report (<UNK> list, weak spots)
   → prompt llama3/gemma: "here's the vocab, here's what she can't say,
     write N sentences filling those gaps"
   → new corpus lines → vocab_only+train (0.1s) → expanded weights
```
The "asking fill-in questions" = the gap report driving the teacher's
prompt. This is EXACTLY the train-supervisor loop from 04.arch-strategy,
with one addition: the supervisor builds the gap report from evaluation.

### C. "Meta weights / per-curriculum weights + router" — YES, and it has a name
What you're describing is a **bank of experts + a router** — conceptually
Mixture-of-Experts (MoE) in spirit, but operationally SIMPLER and totally
standard: each curriculum = one small self-contained expert (own vocab +
weights). A router picks which expert to load per task/intent. ROADMAP §5.1
already designed this as a "bank/picker" — the mechanism exists on paper.
- Why NOT full MoE: real MoE runs all experts' weights with a gating network
  in ONE forward pass. Your strict "never all in one place" rule favors the
  simpler **checkpoint-per-curriculum + selector** model — one expert loaded
  at a time, nothing merged. Same spirit, matches your storage rule better.
- The "meta weights" = the ROUTER's own small config (topic → curriculum →
  endpoint/weights-path), plus the qualifications registry (§12.3) deciding
  which expert is allowed to be a teacher.

### D. Storage layout (satisfies the zip-and-ship rule)
```
LOCAL (this box, ships daily):    tiny manifest only
   pieces/registry/curricula.pdl  (name, topic, rung, expert location,
                                   weights size, last report verdict)
NODES (heavy data stays on the node it trained on):
   Linux 10.0.0.187: ~/iqabod-store/<curriculum>/  (corpus + vocab + weights)
   Mac   10.0.0.144: ~/iqabod-store/... + big-scale runs
```
Exact same philosophy as the xyz-installer's `pointers.pdl` — a pointer,
not the payload. The manifest row IS the "compressed version" the user can
ship; expansion happens on the node via the supervisor.

## Naming summary (for the user)
- What you want = **a curriculum bank of small experts + a router**, with
  **distillation** for expansion and **manifest-only storage** locally.
  It is NOT full MoE (you don't want experts merged/loaded together) — it's
  the simpler, storage-friendly cousin. Say "expert bank + router" and
  everyone (including future agents) will know what you mean.
- The "expand weights via gemma + fill-in questions" = **on-demand
  distillation with gap-driven teacher prompting**. Very buildable, no new
  theory required.
