# 01.assessment💼️.md — babysit vs set-and-forget + infra gaps
> 2026-07-31. Evidence-based, from the 5/5 harness runs + codegen probe +
> the J2 testing guide. NOTE: no local-model compute was used (constraint).

## 1. What the agent can do FOR REAL today (proven, not assumed)
Deterministic tool pipeline works end-to-end through the real chat UI:
- list_dir, write_file, edit_file (append), read_file, exec_cmd,
  search_in_files — all dispatched by keyword, Strategy A pre-execute,
  results rendered below their triggering message, no TOOL: hallucination.
- Model switch + persistence across boots (last_model.txt).
- iqabod provider path fixed (relative api_url) — real fork + generation.
So: "agentic coding" in the file-run-search sense is real. The dev drives
it one tool-turn at a time and the pipeline executes reliably.

## 2. What it CANNOT do (honest ceiling)
- 270m gemma cannot generate code. In the probe it produced invalid syntax
  (`except random.random() for num in range(...)`). The agent never asks the
  LLM for code — the USER/teacher supplies file content and commands; the
  deterministic matcher just detects which tool to run. The "gemma harness"
  is a TOOL-ROUTER, not a code-writer.
- Only qwen2.5-coder:7b produced valid, runnable code in our probe
  (SYNTAX OK, played correctly). It must run on the LAN machine, not here.
- No multi-turn autonomous loop: one turn = one tool call, synchronous,
  no self-correction, no plan-then-execute, no "go do this whole task".

## 3. Babysit vs set-and-forget: verdict
TODAY: strictly BABYSIT. It is a deterministic single-turn executor:
  - no background tasks (a long task would need a running session + watchdog)
  - no set-and-forget: sessions are wiped per launch (reap_stale_sessions),
    world_01 state is NOT conversation-continuous across runs
  - one known open render-freeze bug (jul-21-gemma-fix.txt) — first task if
    we make it autonomous
  - compile-on-launch rebuilds all ops every boot (~seconds each launch)
To reach SET-AND-FORGET (a long background job, e.g. distilling corpora or
generating a game on the LAN box), we need infra below.

## 4. Infra to make both easier (proposal, nothing built)
A. **LAN executor op**: ops/send_remote.c — ssh to the Mac, run a given
   command/codegen there, stream result back. The one op that makes
   "user-playable game on the LAN computer" and "distillation offload"
   possible from this box. Needs user-provided SSH info.
B. **Background job runner**: ops/bg_run.c (like exec_cmd but setsid +
   pidfile + logs/ + status poll), so a long training/corpus job can be
   kicked off and checked later — the set-and-forget primitive.
C. **harvest_room_to_corpus.c**: the designed-but-never-built op from
   CHAT-INTEGRATION-ARCHITECTURE sec. 4 / zest-er-summary 4.2 step 2 —
   the missing link for the IQABELLA distillation loop (teacher gemma-lan +
   student iqabod in one room → harvest → train → iterate).
D. **Model-router escalation log** (4.3): record when/why each escalation
   happened — that log IS the future curriculum signal.
E. **Watchdog/render-refresh fix** first if going autonomous (jul-21 bug).

## 5. Priority order proposed
1. Fix jul-21 render freeze (existing bug, blocks everything autonomous).
2. User provides Mac SSH info → build A (LAN executor) → spin up the
   playable game ON THE MAC, from this box, no local CPU.
3. Build B (bg_run) → set-and-forget distillation jobs.
4. Build C (harvest op) → IQABELLA loop goes from design to real.
5. D as the training-curriculum feedback signal.
