## The vision (restated as a pipeline)
```
                 ┌────────────────────────────────────────────┐
 user/keyboard → │ ROUTER (decision layer)                     │
                 │  detect intent → pick model/tool → execute │
                 └────┬───────────────┬───────────────┬───────┘
                      │               │               │
                gemma3:270m     iqabod(IQABELLA)   llama3 (Mac)
                (chat/route)   (tiny writer)      (management review)
                      │               │               │
                      └───── same toolset: write/edit/read/run/search ─────┘
   escalation: gemma does small stuff → hands UP to llama for review →
   llama hands instructions DOWN to gemma → loop until done, human barely involved
```

## Strategy 1 — IQABOD distillation harness (low supervision, llama3 teacher)
What exists: `generate_corpus.+x` (LLM→corpuses/<name>.txt, any provider),
`vocab_only`+`train` (~0.1s/10 epochs on Linux), `irc_agent_poll` (teacher/
student room pattern). Missing: the SUPERVISOR that runs the loop + reports.

Proposed `train-supervisor` (a harness, house-style shell + existing ops):
1. Read a **curriculum queue** (`curriculum-queue.txt`: topic + rung + vocab
   budget, e.g. "farm-animals | grade1 | ≤40 tokens"). Human writes queue
   once; supervisor runs unattended.
2. TEACHER = llama3:latest on Mac LAN via `generate_corpus` (provider=ollama,
   api_url=Mac). Pulls topic text → `corpuses/<name>.txt`.
3. TRAIN on Linux node: `vocab_only` → `train` (the two proven calls).
4. EVALUATE automatically:
   - loss from `loss.txt` (must descend below random floor — currently ~2.62
     = ln 14; this is our "is learning happening" gate)
   - `<UNK>` rate on a held-out eval prompt set (exact-match tokenizer makes
     this a clean number)
   - optional LLM-as-judge score (llama3 judging iqabod's output, §11.2's
     ask_judge idea) — keep optional, judge is slow
5. REPORT: append a row to `training-report.txt` (topic, tokens, epochs,
   loss, <UNK>%, judge, verdict). Supervisor prints one-line summary.
6. ACT on verdict: <UNK>% too high → regenerate corpus simpler/smaller;
   passing → advance rung / promote to next curriculum (§12 ladder). This is
   the low-supervision part: the queue drives everything, human only reviews
   the report.

## Strategy 2 — Gemma autonomous decision layer (RL/FSM/BT, minimal LLM)
Current: `gemma_strategy.c` = hardcoded keyword→Strategy A/B/C, weights
baked in. Roadmap §6 already DESIGNED a real FSM engine + banks, never built.

Proposal: **replace the hardcoded weights with a tiny decision engine** —
a behavior-tree (BT) core (one op, one config file), because BT handles
"if tool found, pre-execute; else if uncertain, escalate; else answer" far
more readably than raw C if/else chains, and stays fully deterministic:
- BT config (a text file, editable like op.txt): sequences/fallbacks/
  conditions = {keyword match, file exists, task-complexity heuristic,
  last-tool-result-ok, uncertainty score}. Leaves = {pre-execute tool, ask
  gemma, escalate to llama, ask human}.
- Meta-RL (§6.4/§11.2): the BT is DATA. Flipping a leaf from "ask gemma" to
  "escalate" is an edit, not a recompile. Later, judge feedback can re-weight
  leaves automatically (LLM-as-judge loop).
- This is what gives "autonomous and powerful even without full LLM": the
  tree does the deciding; gemma is one leaf, not the brain.

## Strategy 3 — The bridge (gemma + iqabod share the toolset)
Already mostly true: both are just `provider_kind` entries behind one router,
and the tool pipeline is provider-agnostic. The bridge is the DECISION LAYER:
- gemma = intent + route (what to do)
- iqabod = tiny generation (produce the fragment/word/line)
- router assembles iqabod fragments into statements, writes via write_file,
  runs via exec_cmd.
Test harness: scenario where user says "write a short story about a cat" →
router detects write intent → gemma routes → iqabod generates fragments →
write_file lands → read back → judge (llama) scores coherence. KPI = file
exists with N tokens, <UNK> below threshold. This harness is buildable now.

## Strategy 4 — Escalation ladder (gemma → llama → gemma)
New op `escalate_to_llama`: when BT leaf says "escalate", package
{task, gemma's draft/context, tool results} → llama3 (Mac) → returns
review/instructions → written back into gemma's context → loop continues.
Thresholds (task complexity, uncertainty, tool-failure count) are BT config.
This is the "management review" rung. Human only sees the summary report.

## Build order I recommend (prove-one-thing-first)
1. **train-supervisor v1** (strategy 1): closes the iqabod loop with real
   reports. Cheap (all ops exist except the supervisor script).
2. **Bridge harness** (strategy 3): proves gemma+iQabod share tools with a
   concrete KPI. Uses supervisor's freshly-trained curriculum.
3. **BT decision engine** (strategy 2): replaces hardcoded weights, adds the
   escalate leaf. Biggest new code (one C op + config format).
4. **escalate_to_llama** (strategy 4): last, because it needs 2&3 working.

## Revised supervisor design (ops + harness, per D3)
Ops (in ops/, self-contained C, house style):
- `train_step.c`   — take a queue entry (topic, rung, vocab budget, teacher
                     provider/api_url/model) → generate corpus via teacher →
                     run vocab_only + train on the target node (Linux/Mac) →
                     write eval numbers. Returns verdict string.
- `eval_curriculum.c` — held-out prompts → loss + <UNK>% + optional
                     llama-as-judge score → write report row. (Gap report =
                     the <UNK> list, feeds the teacher prompt per D6.)
- `list_curricula.c` — read curricula.pdl manifest (local, tiny).
Harness (%.harnesses/iqabod-loop/button.sh or agent scripts/):
- reads curriculum-queue.txt → calls the ops in order → appends to
  training-report.txt → prints one-line summary → sleeps (set-and-forget).
