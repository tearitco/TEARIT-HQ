# harness/ - pal harnesses (owner direction 2026-10-07: harnesses are pal + events, not sh, not C one-offs)

A harness is three small things:

| Piece | Where | What |
|---|---|---|
| **pal** | `<name>.pal` | assembly: `exec` the case op, `exec` the verdict op, `halt`. Run from this folder: `prisc+x <name>.pal` |
| **cases** | `cases/<name>.pdl` | data (pipe rows): scratch setup, the command to run, the expectations. This is the part a person edits, and the part that can later be stored as bank weights / training data |
| **ops** | `ops/harness_case_op.c`, `ops/harness_verdict_op.c` | compiled ops (build into `ops/+x/`, flags `-Wall -Wextra -O2`) |

**Why two ops:** prisc's `exec` ignores the child's exit status and discards its output (`prisc+x.c`, "exit status isn't consulted here"), so a pal cannot assert by itself. `harness_case_op` writes `PASS|<case>/<label>` / `FAIL|...` rows into `results/<name>.txt` (append-only ledger, one `RUN|` row per run); `harness_verdict_op` counts the rows after the last `RUN|` and writes `results/<name>.txt.verdict.txt` (`VERDICT|PASS|passed=N|failed=M|...` plus every FAIL row). **Read the verdict file** after the pal halts.

**Case verbs** (details in the header of `ops/harness_case_op.c`): `RESULTS`, `CASE`, `SCRATCH` (a `/tmp/hc_*` dir = `$T`), `MKDIR`, `COPY` (from `$HOUSE` into `$T`, keeps the mode), `WRITE`, `RUN` (fork/exec, **no shell**, fields are argv entries), `EXPECT_EXIT`, `EXPECT_FILE`, `EXPECT_NOFILE`, `EXPECT_HAS`, `EXPECT_LACKS`, `EXPECT_OUT`, `COPYDIR` (a whole tree under `$T`, with a skip list; added 2026-10-17), `CLEAN`. Every command runs with its cwd in `$T`; a case that forgets `CLEAN` is still cleaned up. **Never name a live path in a case; work under `$T`.** (Shell expansion bites when you *generate* a case file with an unquoted heredoc: `$T` becomes empty. Use `<<'EOF'`.)

**Run (scratch prisc until a house one is built; use the many-args VM, `prisc_exec_args.pal` tells you if the one you have is the old one):** `gcc -O2 -w -o /tmp/prisc system/prisc+x.c -lm` from `&.widgits/_shared-lib/system/`, then `/tmp/prisc <name>.pal` here. It prints `[Prisc Error] Could not open ops file .../default_op.txt`; that is harmless (the harness uses no custom ops).

## Scripted playthroughs: phase tables, the RESULT ledger, per-phase weights (2026-10-17)

`play_cdda_hq.pal`, `play_df_hq.pal`, `play_mcl_hq.pal` run a whole game from a fresh scratch copy to a meaningful end state through the game binary's own verbs. The story is DATA: `play/phases/<name>.phases.pdl`, one `PHASE` per step group, rows `DO | verb | args` (run the binary) and expectation rows (`SAY`, `HAS`, `COUNT`, `UI`, `EQ`, `DELTA`, ...). `ops/playthrough_op.c` is the one generic runner: `compile` turns a table into an ordinary case file (so `harness_case_op` judges it with its existing verbs), `ledger` turns the PASS/FAIL rows into the RESULT ledger and into live per-phase weights, `run` does all of it in one call (what a game AI calls with a phase list of its own). Full doc: BOOK `06-testing/GAME-PLAYTHROUGH-HARNESSES.md`; the AI picture: BOOK `17.ai/HARNESS-AS-GAME-BRAIN.md`.

| Piece | Where | What |
|---|---|---|
| phase table | `play/phases/<name>.phases.pdl` | tracked data; `example_proposal.phases.pdl` is what an AI would hand in |
| generated case | `cases/play_<name>.pdl` (shipped pals) or `play/cases/play_<name>.pdl` (proposals) | never edit; regenerated on every run |
| RESULT ledger | `play/results/play_ledger.txt` (append-only, git-ignored) | `PH\|run id\|game\|name\|phase\|PASS/FAIL/NOCHECKS\|ms\|pass=N\|fail=M\|first failed label`, one `PLAY\|...` row per run |
| per-phase weights | `play/results/ph/<game>__<phase>.txt` -> `play/bank/live/<game>__<phase>.behavior.pdl` | one PASS or FAIL row per run and phase; `harness_bank_op` turns them into WEIGHT = (passes+1)/(runs+2). Seeds are generated into `play/bank/` |
| whole-harness seed | `bank/play_<game>.behavior.pdl` | hand-written, same shape as every other seed; the pal's last line updates it |

Ask the bank which phases to trust: `ops/+x/harness_bank_op.+x find play/bank craft bandage`. Run a proposal: `ops/+x/playthrough_op.+x run play/phases/example_proposal.phases.pdl` (no prisc and no shell are involved in `run`; the pals are the same steps for people who prefer `prisc+x`). `playthrough_op` is built by `ops/build_harness_ops.sh`.

## Behavior bank (weights, synonyms, sentences)

Every harness has a seed `bank/<name>.behavior.pdl` (keywords, weighted synonyms, sentences about how it works, weighted slots to concept names = the hidden layer, corpus weights, the exec sequence). The last line of each pal, `exec ./ops/+x/harness_bank_op.+x cases/<name>.pdl`, adds this run's PASS rows to reward and FAIL rows to punish (cursor-based, counted once) and writes the live Laplace weight to the git-ignored `bank/live/`. Search: `ops/+x/harness_bank_op.+x find bank <word>...`. Design, inference and limits: `HARNESS-BEHAVIOR-BANK-DESIGN.md`. **Seed weights are guesses; only WEIGHT is measured.**

## palnet_peer over the LAN (manual procedure, 2026-10-08)

The loopback harness above proves the logic; this is how it was checked across real machines (this desk 10.0.0.238, debil 10.0.0.16, the Mac 10.0.0.144, key login for all). Not automated yet: the case runner has no ssh verb and a case file must not hardcode addresses. To turn it into a harness, add a hosts data file and an ssh-capable case verb.
1. On each machine, in a scratch folder under /tmp, compile only `palnet_peer.c` (on macOS use PATH with /usr/local/bin and /opt/X11/bin; the program is macOS-safe).
2. Start one peer per machine with its OWN address: `PALNET_BIND=<ip> PALNET_ADVERTISE=<ip> PALNET_SEEDS=<other ip>:9950,<other ip>:9950 PRISC_PROJECT_ROOT=<scratch>/proj PRISC_NET_ROOT=<scratch>/net palnet_peer chain t - <scratch>/out.txt <scratch>/in.txt chain` (detach it with `nohup` inside a subshell and `ssh -n`, or ssh hangs).
3. Append `TX|...` to one machine's out.txt; read the others' in.txt: each must have the line exactly once. Append on a second machine to check the reverse direction.
4. Stop all, restart WITHOUT `PALNET_SEEDS` (keep the proj folders): the message must still arrive once (address memory).
5. Stop by the pid in each presence file, delete the scratch folders. Result of the run on 2026-10-08: phase 1 once each, 2 remembered peers per node; phase 2 once each with no seeds; debil to the other two once each. Both ends keep the connection dialed by the smaller node id (commit after 9ed0c3693) and the receiver drops a replayed duplicate.
The IRC window version (the same peers started by `irc-chat-hq`, one scratch house per machine, relay-driven) is described in `08-roadmap/design-docs/MULTI-AGENT-NETWORK-USER-STORY-HARNESS-PLAN-2026-10-08.md` sections 9 and 10.

### RUN rows keep 48 arguments and fail loudly beyond that (2026-10-21)
`harness_case_op` used to copy only the first 16 fields of a `RUN` row (and `SPAWN`) and drop the rest silently; a long `BPWIN` row lost its tail steps while its `EXIT | 0` still passed. `RUNMAX` is now 48; more arguments fail the row ("too many arguments for a RUN row"), and `playthrough_op` rejects a `BPWIN` row of more than 36 steps at compile time. Re-run any older table with a long BPWIN row.
