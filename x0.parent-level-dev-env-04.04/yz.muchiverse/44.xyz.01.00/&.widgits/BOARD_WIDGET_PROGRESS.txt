DECISIONS ALREADY LOCKED IN (do not re-litigate, do not ask again)
================================================================================
- ONE shared, focus-adaptive widget (not two per-project ones), at
  &.widgits/board-viewer/ (name confirmed, not just a placeholder anymore
  unless told otherwise).
- Widget is a SEPARATE PROGRAM (own session, own GL window), spawned/
  focused via keypress from the host game — NEVER a same-session CHTPM
  href screen switch (this was the original mistake, already reverted
  once, do not reintroduce it).
- Real-time sync = widget reads the HOST's real project root directly
  (no polling/duplication plumbing beyond knowing which root to read).
- gl_mirror.c MUST be the 014.wsr-pal💸️📌️+2 version (has interact_relay
  forwarding) — NOT mutaclysm's own copy (mirror-only, no key forward).
- Full raymarch 3D IS in scope (not a simplified perspective-quad
  version) — 2D content gets EXTRUDED into real 3D geometry, ported/
  adapted from mutaclysm's own real, working ops/compose_rgb_frame.c
  raymarch machinery (raymarch_walls_3d, sample_voxel8_pixel, etc.)
- render_mode (2D/3D, key '0') and emoji_mode (flat/textured) are TWO
  SEPARATE, ORTHOGONAL flags — confirmed via direct code read of
  mutaclysm's own compose_rgb_frame.c:2280-2323. Do NOT collapse them
  into a single "N modes" selector (this was tried and corrected once).
- camera_mode 1-4 (POV presets) only meaningful while render_mode==1,
  exactly matching mutaclysm's own is_pov_key gating.
- ALL 4 camera modes are in scope for BOTH civ-txt and tactics-txt,
  regardless of board size — direct instruction: "it needs all the pov
  and camera views, if for no other reason than debugging. later they
  maybe locked but not for debug." (The lock mechanism itself is a
  separate, later, undesigned feature — don't build it prematurely.)
- Terrain extrusion is SELECTIVE (some tile types get real height, not
  a uniform "everything is a cube") — exact terrain->height mapping
  still open, see OPEN QUESTIONS below.
- Entity extrusion (cities/units/selector cursor) SHOULD be built for
  this widget — going further than mutaclysm's own current code, which
  has never built this (a real, documented, unfixed gap in mutaclysm's
  own extrude-emoji.md). Shape (billboard vs AABB) still open.
- Widget has real ASCII/headless testability (system/renderer + reading
  current_frame.txt directly) independent of GL — use this as the
  PRIMARY test path, GL-window verification is a manual/visual spot
  check only, matching every other harness built this session.
- CPU SAFETY: same discipline as the rest of this session — every test
  run wrapped in `timeout`, CPU checked via `ps` at every step, explicit
  kill + re-check between tests, NO unthrottled idle-poll loops (a real,
  documented crash happened in this house from exactly that mistake —
  see BOARD_WIDGET_ARCHITECTURE.md §8a).

Live-caught bugs (user testing real GL widget window directly), both fixed + rebuilt:

BUG: nav_mode never activates ("Enter Nav Mode" unreachable)
  ROOT CAUSE: bv_menu_input.c's digit dispatch used `(key - '0') - 1`
  for ASCII digit keys, double-decrementing an already-1-based value.
  Traced via chtpm_parser_pal.c's inject_raw_key()/relay mechanism:
  argv[1] really is the raw ASCII code of the digit key (e.g. "49" for
  '1'), confirmed NOT a pre-resolved item index. key='1' -> resolved_item
  = (49-48)-1 = 0 -> fails the `resolved_item >= 1` guard -> item 1
  (the only item when nav_mode=0) can never dispatch. Every other item
  was also shifted by one (pressing '2' fired item 1's command).
  FIX (bv_menu_input.c): `resolved_item = key - '0'` (ASCII branch),
  `resolved_item = key` (raw >9 branch) - matches 102.editor's own
  correct editor_menu_input.c convention.
  SCOPE: same exact copy-pasted bug confirmed present in ~11 OTHER
  menu_input ops across the house (civ_menu_input.c:225-226,
  mychara_menu_input.c:217, wsr_menu_input.c:339, chain_menu_input.c:274,
  forum_menu_input.c:248, chat_menu_input.c:399, avatar_menu_input.c:646,
  userpal_menu_input.c:260, mylawyer_menu_input.c:283,
  mybiotech_menu_input.c:249, tactics_menu_input.c:220) - NOT fixed
  there yet, only board-viewer's own copy fixed so far. Flagged to user,
  awaiting decision on whether to sweep the rest.

BUG: visible blank-space gaps between emoji tile columns (not rows)
  ROOT CAUSE: bv_compose_frame.c's cell-render loop unconditionally
  wrote a literal ' ' before and after every glyph regardless of
  selection state. chtpm_rgb_render.c advances by VOXEL_PX(16) per
  real emoji tile but GLYPH_W(8) per plain-ASCII space, so each cell
  got a real ~8px blank gap on both sides. Mutaclysm's own real
  convention (ops/compose_frame.c:1091, `fputs(viewport_emoji[r][col],
  out)` in a tight loop) packs cells edge-to-edge, ZERO separator
  between columns - confirmed via direct code read.
  FIX (bv_compose_frame.c): removed unconditional space padding;
  brackets `[ ]` now emitted ONLY around the actually-selected cell.

--- 2026-08-02 (still later): real raymarch step-budget bug, fixed ---
User-caught, real bug: "V shaped cutoff at bottom of map when camera
moves back, whole map disappears if it moves back further" (3D mode,
camera_mode 4 bird's-eye, moving camera away via z_level/pan).
Root cause: bv_render_3d.c's own per-pixel DDA loop used a FIXED
max_steps = board_w+board_h+8, sized assuming the camera starts near/
inside the board. Once panned/raised away, rays (especially shallow-
angle ones near the bottom-center of screen when viewed from altitude -
exactly matching the reported "V" shape) need MORE DDA steps just to
reach the board's own col/row range before they can ever test a real
hit - the fixed budget ran out for distant/grazing rays first, showing
as sky (missing map) even though a genuine intersection existed further
along the same ray.
FIX: compute a real per-FRAME (not per-pixel, cheap) max_steps that
scales with BOTH the camera's horizontal distance from the board's own
bounding box AND its altitude (eye.y) - both independently contribute
extra steps rays may need (confirmed via direct geometric reasoning,
not just horizontal offset - a camera centered directly above the board
but very high up needs the SAME extra budget for shallow rays). Verified
correct + CPU-safe via direct headless testing across z_level 5/15/30/60
- all stayed ~45ms/frame, no artifact, terrain naturally shrinks with
altitude as expected (not a sudden disappearance).
Applies to civ-txt AND tactics-txt automatically - board-viewer is one
shared codebase, no per-project fix needed.
