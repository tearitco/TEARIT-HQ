interact-fix-widget.txt
2026-08-02 — real root-cause investigation + fix for board-viewer's
"interact mode never activates" bug, requested directly by user:
"pls see other house references that are working like mutaclysm and
investigate and fix this final bug"

=== THE BUG, AS REPORTED ===
Live-testing the GL widget, pressing "1" to select the sole menu item
("Enter Nav Mode") never flipped the cursor glyph from "[>]" to "[^]"
and never allowed arrow-key control - even after the earlier digit
off-by-one fix (which was real, but not the actual blocker here).

=== WHAT I HAD BUILT (WRONG MODEL) ===
board-viewer's own P5/P6 passes invented a custom mechanism:
  - a piece.pdl METHOD row with command string "ENTER_NAV_MODE"
  - a hand-rolled nav_mode=0/1 flag in bv_state.txt
  - bv_menu_input.c reading that flag, gating arrow-key handling on it,
    and handling ESC itself to flip it back to 0

This looked plausible (mirrors "gate camera+selector behind one entry
point", the confirmed design decision) but was never actually wired
into the real engine mechanism mutaclysm uses. It was a parallel,
disconnected reimplementation.

=== HOW MUTACLYSM REALLY DOES IT (the reference, re-investigated) ===
mutaclysm's pieces/chtpm/layouts/game.chtpm:7:
  <button label="Control Hero" onClick="INTERACT" /><br/>

This is a REAL, STATIC, HAND-WRITTEN <button> element directly in the
.chtpm layout XML, with onClick set to the literal reserved string
"INTERACT". It is NOT a piece.pdl METHOD row, and it is NOT auto-
generated by ${piece_methods}.

"INTERACT" is a string chtpm_parser_pal.c (the SHARED engine, one copy
per project, e.g. 014.wsr-pal💸️📌️+2/system/chtpm_parser_pal.c) special-
cases directly, in multiple places:

1. On click (chtpm_parser_pal.c:3333, wsr-pal's copy):
     else if (strcmp(el->onClick, "INTERACT") == 0) {
         active_index = focus_index; clear_nav_on_next = true;
         export_active_index();
     }
   This sets the engine's own internal active_index - nothing written
   to any project-owned state file for this part.

2. While active (chtpm_parser_pal.c:3503-3517, wsr-pal's copy):
     else if (strcmp(el->onClick, "INTERACT") == 0) {
         int eff = key;
         if (key == ARROW_LEFT) eff = 1000; ... (RIGHT=1001, UP=1002, DOWN=1003)
         inject_raw_key(eff);
     }
   Raw keys (remapped arrows) are relayed into whatever the layout's
   own <interact src="..."/> tag names - board_viewer.chtpm already
   had <interact src="pieces/apps/player_app/interact_relay.txt" />
   (this part was already correct, unchanged).

3. ESC-exit (mutaclysm's own copy, chtpm_parser_pal.c:3080-3088,
   confirmed equivalent logic present in wsr-pal's copy): consumed
   INSIDE the engine, before the project's own op ever runs. Sets
   active_index=-1, resets focus. The project's own ops (bv_menu_
   input.c) never see or handle ESC for this at all.

4. The "[>]" -> "[^]" glyph swap (chtpm_parser_pal.c:2826-2830,
   render_element()):
     bool is_active = (idx == active_index) ||
         (strcmp(el->onClick, "INTERACT") == 0 &&
          current_project_is_map_control_active());
     if (is_active) strcpy(pref, "[^]");
     else if (is_focused ...) strcpy(pref, "[>]");
   Also entirely inside the engine - not drawn by any project's own
   compose_frame.c.

=== THE ACTUAL BLOCKER: piece.pdl METHOD rows CANNOT reach this path ===
Traced chtpm_parser_pal.c's own ${piece_methods} generator
(~line 1140-1155, wsr-pal's copy):
    is_parser_cmd = (cmd starts with "LOAD_PROJECT:" || "LAUNCH:" ||
                      "MP3:" || cmd=="BACK" || cmd=="RELEASE");
    if (cmd == "void" || !is_parser_cmd) {
        // becomes onClick="KEY:<method_index>"
    } else {
        // becomes onClick="<cmd>" verbatim
    }
"INTERACT" is NOT in that is_parser_cmd whitelist. So even if a
piece.pdl METHOD row's command column literally said "INTERACT", the
generated button's onClick would be "KEY:N" (a plain numbered-digit
relay into the project's own menu_input op), never the reserved
string. The special engine-level handling ONLY triggers for a real
onClick="INTERACT" attribute written directly in the .chtpm XML.

This is why my ENTER_NAV_MODE approach could never have worked no
matter how the digit dispatch was fixed - it was structurally routed
through the wrong mechanism from the start.

=== THE FIX ===
1. pieces/chtpm/layouts/board_viewer.chtpm - added a real, static
   button matching mutaclysm's exact convention:
     <button label="Nav Mode (camera + selector)" onClick="INTERACT" /><br/>
   placed directly in the layout, NOT inside ${piece_methods}.

2. ops/bv_compose_frame.c - removed the ENTER_NAV_MODE/EXIT_NAV_MODE
   piece.pdl METHOD-row generation entirely (piece.pdl no longer
   drives nav-mode entry at all). For the widget's own "Nav mode:
   ON/OFF" status line, now reads the engine's own real, already-
   exported signal instead of a custom flag:
     pieces/display/active_gui_is_typing.txt
   (written by export_active_index(), chtpm_parser_pal.c:2719 - "1"
   means active_index != -1, i.e. a real INTERACT element is currently
   engaged; "0" otherwise). This is read-only, informational - nothing
   gates on it in this project's own code anymore.

3. ops/bv_menu_input.c - deleted the entire custom nav_mode flag, ESC
   handling, and digit-dispatch/load_menu_items/MenuItem machinery.
   The op is now ONLY ever invoked with an arrow-key code (1000-1003)
   while genuinely inside real INTERACT mode, because the engine
   itself guarantees raw keys are only relayed into interact_relay.txt
   while the INTERACT element is the active one. Arrow handling is
   therefore unconditional now - the gate already happened upstream,
   inside the shared engine, exactly matching how mutaclysm's own
   xlector movement works (no per-project gating code needed there
   either).

=== SEPARATELY FOUND + FIXED WHILE INVESTIGATING (real, but different bug) ===
bv_menu_input.c's digit-dispatch used `(key - '0') - 1` for ASCII
digit keys, an off-by-one that made item 1 permanently unreachable via
a single digit keypress. This was a REAL bug (confirmed by tracing
chtpm_parser_pal.c's inject_raw_key(), argv[1] is genuinely the raw
ASCII digit code) and is now moot for board-viewer specifically (no
digit-dispatched METHOD rows remain in this project), but the same
copy-pasted bug still exists, UNFIXED, in ~11 other menu_input ops
across the house (civ_menu_input.c:225-226, mychara_menu_input.c:217,
wsr_menu_input.c:339, chain_menu_input.c:274, forum_menu_input.c:248,
chat_menu_input.c:399, avatar_menu_input.c:646, userpal_menu_input.c:
260, mylawyer_menu_input.c:283, mybiotech_menu_input.c:249,
tactics_menu_input.c:220). Flagged to user, awaiting decision on
whether to sweep the rest.
