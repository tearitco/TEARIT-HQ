# eden - the Eden conductor v0 + playable loop v1 (template files, not a live entity)

Built 2026-10-07 in alpha (spec `GAME-CONDUCTOR-ENTITY-AND-EDEN-DESIGN.md` sections 1-5 and 7). A **conductor** is an entity (glyph 🔘) whose context menu is a game's control panel: Setup, Start, Pause, Resume, Save/Load slots, Status, Add/Remove participant, Reset. Everything is RPG Maker-style event pages on the house clock; the one compiled piece is `ops/eden_op.c` (header = every verb). **Nothing here is installed anywhere: never copy it into live user data (`xyzfs/users`).** Asa and Ava are *scratch entities* spawned fresh from `conductor/participant_template/` (identity `ED<n>`, no copied PAL hash or uid); the harness works on `/tmp` scratch roots only. Headless: no window.

## Rules (all numbers in the .pdl files)
- **Grants** (append-only `grants.txt`): `GRANT|eden|<entity>|item/skill/param|<id>|<amount>|applied=<0/1>|day=<n>`; a triple already granted is skipped (Setup twice grants once); `applied=0` means the entity already had the skill (Reset does not take it away); items revoke up to what the entity still holds; params are additive deltas so they reverse. Registered commands `change_items` / `change_skill` / `change_hp` write `items.txt` `item_<id>`, `actor_skills.txt` `skill_1:<id>`, `actor_1_stats.txt`; `eden_op` writes the same files directly (a page cannot loop over a kit).
- **Acts** are derived: a skill is available if stored OR implied by a held item (`items.pdl grants_skill=`), the skill's `needs_item` is held, and its rule precondition holds (plant: seed and a free plot; water: dry growing plot and no rain today; collect: ripe plot; eat: hunger >= `eat_min_hunger` and food; trade: a mutual swap exists; talk: a partner; build: hoe and grain/seed for the hut; study: an unlockable node; rest: always). `acts <who>` lists them, `menu <who>` writes `acts_menu.pdl` METHOD rows.
- **Day Tick** (`eden_day_tick`): day+1, seeded weather (`rain_pct`), then per participant: hunger rises (HP loss at `starving_at`, floor 1), growing plots grow when watered (rain or the water act), then the **agent seat**: critical-need gate (hungry and food: eat), else one seeded weighted pick (`weights.pdl`) among the available acts. Dice = integer hash of (seed, day, participant ordinal, salt): no clock, no rand().
- **Ledgers**: `eden_history.txt` (DAY WEATHER NEED GROW RIPE ACT ITEM UNLOCK JOIN RETIRE SETUP RESET), `participants.txt` (JOIN / RETIRE tombstone), `grants.txt`, and the control ledger (SAVE/LOAD/START/PAUSE/RESET, outside the game tree so a Load does not rewind it). No wall time inside the tree, so runs compare byte for byte (`eden_op digest`).
- **Save/Load**: `game_snapshot_op` over the game tree (conductor + participants) with the clock state, `reminders.pdl` and `schedule_ledger.txt` as `--extra`; Load = `restore --apply --prune --extra-dir` (participants added after the save are pruned). A slot cannot be overwritten (the op refuses an existing id).

## Install note (by hand, in a scratch house first)
1. `gcc -std=gnu11 -Wall -O2 -o ops/+x/eden_op.+x ops/eden_op.c` (the `+x` programs are git-ignored); the pages find the op at `<conductor>/ops/+x/eden_op.+x`, so copy it there (a pal `exec` cannot name the house root). Also needed: digipet `event_page_op.+x`, `lc_clock.+x`, `game_snapshot_op.+x`.
2. layout: `<house>/game/conductor` (copy of `conductor/`), `<house>/common_events/eden_day_tick` (copy), `lc.+x` and `gso` beside `game/` as `wiring.pdl` says (edit `wiring.pdl` for any other layout).
3. run the row Setup (installs the clock `g1` and the schedule row `common:eden_day_tick`, `repeat=every:1day`), then advance: `lc_clock <house> cmd g1 advance 20d`, `lc_clock <house> step 0` (or `daemon`); `LC_CLOCK_EVENT_RUNNER=<house>/&.widgits/digipet/ops/+x/event_page_op.+x EVENT_PAGE_TRIGGER=parallel EVENT_PAGE_PRISC=<prisc>`.
4. Toys: nothing to do; `toy.pdl` is picked up by the scan (not verified in a GUI). A desk button would need a desk row for the conductor folder (not done).

## Gaps found (what the house cannot express yet) and how v0 sidesteps them
- **toy.pdl format**: the taskbar's `read_key_value` skips every line that starts with `META`, so the spec's `META|title` rows are never read; the real toys use `SECTION | title | X`. Used `SECTION`. The scan also only looks at direct children of the roots, so `toy.pdl` is in `eden/`, and `launch` is `conductor/button.sh` (run as `sh button.sh run`).
- **no variable compare / arithmetic / random / row loop in pages**: every such rule is a verb of `eden_op` (same answer as ring-board's tiny ops, but one op with many verbs because the rules read each other's state).
- **a page cannot learn the house root or take arguments**: paths live in `conductor/wiring.pdl` (relative, so two scratch runs have identical bytes); Save/Load slots and Add/Remove are separate triggers (`save1`...) and a SPARE list.
- **exec exit status is hidden and `event_page_op` exits 0 whenever a page ran**: a refused verb (Start before Setup, Save onto an existing slot) is only visible in `op_errors.txt`.
- **one target per house for a common event**: `common:eden_day_tick` resolves to `<house>/common_events/eden_day_tick` with one `target.pdl`, so two Eden games on one house cannot share the event; the harness uses a second scratch house for the peer game.
- **game_snapshot_op**: refuses to overwrite a slot id; a prune leaves empty directories (the digest ignores them).
- the registry's `change_items` etc. are PAL templates bound to `{STATE_DIR}`; not executed here (a block `eden_verb` was appended to the registry for the op).
- `needs_place` is a label (no map in v0: every place is present), `cost_ticks` is informational (one act per day), `event=` names the act, which is a verb, not a separate page.

## Playable loop v1 (2026-10-07, alpha; EDEN-PLAYABLE-LOOP-AND-BOOK-PAGE-HARNESS-PLAN.md section 2)
Headless, scratch roots only, harness `eden_loop.pal` (305 checks). Everything v0 still works (231 checks unchanged); v1 adds rows and verbs, no v0 number moved.
| What | How |
|---|---|
| **Start game / Stop game** (menu rows, pages 15/16, verbs `begin` / `stop`) | `begin` = Setup (idempotent) + the `PLAYKIT` grants (`settler`: spade, 5 coin, 6 grain, clay, feed + repair skills) + spawn the `WORLD` rows of `game.pdl` (`house count=1`, `chicken count=2`, `plant count=4`) from `world_templates/<kind>/` as `<kind>_<i>` with fresh `ED<n>` ids (no PAL hash, no uid) + start the clock. Every spawn is a `SPAWN` row of the append-only `manifest.txt`. A name already live in the manifest is skipped (Start twice = nothing new); a folder with a game name that is NOT in the manifest makes Start refuse. `stop` = pause the clock, then despawn **only** the live manifest entries (`DESPAWN` rows): participants get their grants revoked and their items written off first (the ledger still balances), the folder is removed with a path-under-root check; an unlisted sibling (world or participants dir) is never touched. v0 `Start` / `Pause` / `Resume` rows stay (clock only). |
| **Chickens** (`animals.pdl`, act `feed`) | feeding takes `feed_amount` of `feed_item`; a fed animal counts a `fed_day` at the next Day Tick; every `lay_every` fed days it adds `product` (egg) to the keeper (the last feeder) and logs `LAY`. Eggs are food and sellable. |
| **Evolution** (`evolution.pdl`) | `EVOLVE | chicken | to=cow | requires_meals=12`, `cow -> horse 30`; checked in the Day Tick; same folder and id, `kind.txt` changes, `EVOLVE` row. `rideable` is a column of `animals.pdl` and shows in Status; **riding is not implemented** (no verb). |
| **Digging** (`finds.pdl`, act `dig`) | needs the spade (`skills.pdl needs_item`, the spade also implies the skill); each dig goes one deeper at the same hole (`dig_depth`, back to 0 after `max_dig_depth`); the seeded roll (seed, day, participant, dig counter) picks among the rows whose `depth` is reached, `weight` = rarity (stone 40, clay 30, silver 12 from depth 3, gold 6 from depth 5, nothing 20). A find is an inventory-ledger row (`ITEM ... dig`) and a `FIND` row. |
| **Trading** | v0 swap, plus **selling**: an item with `value=` goes to the partner for that many `coin` (`currency=1` item) when the partner can pay; the audit proves every trade is zero-sum. |
| **Talking through tomom** | each `talk` asks the tomom-hq chatbot on a SCRATCH copy (`wiring.pdl tomom_bin` / `tomom_dir`; the binary is `chatbot_seed7`, the tracked `chatbot_moe_v1.c` with `srand(7)` that tomom-hq builds in its work folder), fork+exec+waitpid with a 5 s watchdog, cwd = that copy, prompt = one seeded word of the speaker's `words.txt`; the line goes to the listener's `phone.txt` (`MSG|day|IN|speaker|text`), the speaker's outbox, `eden_history.txt` (`TALK|day|from|to|path=tomom|prompt=..|text=..`) and an `ask_log.txt` row in the scratch copy (tomom-hq format). No binary, a missing path, a failing binary or an empty reply: `phrases.pdl` answers and the row says `path=phrase`. Not wired by default. |
| **House** (`house_1`) | `condition` wears 1 every `house_decay_days`; act `repair` (clay, `repair_gain`, only below `repair_below`); `rest` heals 1 + `house_rest_bonus` while `condition >= house_ok_at`. |
| **Garden** | with live PLANT entities the plots are shared (plot i = plant i; same state/grown/wet fields) and grown once per day; without them v0's per-participant plots are used unchanged. |
| **100 slots** | `save <n>` / `load <n>` / `resave <n>`, n = 1..`max_slots` (anything else is refused and nothing is touched). Cursor file `slot.txt` (outside the tree) with `slot [n\|next\|prev\|+10\|-10]`, `save-slot`, `resave-slot`, `load-slot`: the entity menu rows `Slot next`, `Slot prev`, `Slot +10`, `Save slot...`, `Resave slot...`, `Load slot...` call the op directly (`sh -c 'exec "$0/ops/+x/eden_op.+x" "$0" save-slot'`, `$0` = the conductor dir), no page per slot. `eden_op <conductor> gen-slots methods` writes `slots_methods.pdl` (200 METHOD rows to paste if an entity menu can hold them; not verified). |

### Toolbar slot menu (`toolbar_slots.pdl`, `slots_methods.pdl`; generated by `gen-slots`, the harness compares them with a fresh run)
Format read from `khtpm_taskbar_manager.c` (`livedesk_pdl_menu_rows`, `ktb_hq_activate`): rows `SECTION | <prefix>_menu_<N>_label | text` and `SECTION | <prefix>_menu_<N>_cmd | command` in `#.desktop/livedesk_taskbar.pdl`; an empty cmd closes the menu; a command that is not `livedesk:`/`quit` is run as `sh -c '<cmd>'` (so **no single quote** in a row) and every ` .` token is replaced by the house root. Each slot row is `cd . && game/conductor/ops/+x/eden_op.+x . save 7`; `eden_op` accepts a house root in place of the conductor dir when `<dir>/game/conductor/game.pdl` exists. 211 rows: 10 blocks of (header + 10 Save + 10 Load) and cancel. `eden_op <conductor> gen-slots toolbar <prefix> <base> <conductor path from the house>` re-generates with another prefix / first number / location.
**Does the taskbar need a code change? Not to ADD the rows:** pasting them under an existing pdl-driven prefix (`hq_`, `file_`, `network_`, `palettes_`; use `<prefix>` and `<base>` so the numbers continue) needs no recompile; the reader allows `KTB_LIVEDESK_DYN_MAX` = 256 rows per cell, so 211 fit only if the cell has at most 45 rows already, and the menu is FLAT (one long list). **Yes for anything nicer:** a dedicated "Eden" cell (own header cell + one dispatch line `else if (strcmp(cid, "eden") == 0) n = livedesk_pdl_menu_rows(house, "eden", ...)` in `ktb_hq_open`) and true 10-page navigation or a number prompt (submenus were deliberately removed, the planned `widget:` prefix is not built) need a change to `khtpm_taskbar_manager.c`, which this work did not touch. Whether a 211-row dropdown fits the screen or scrolls was NOT verified (no GUI).

### v1 gaps and sidesteps
- **no variable compare / args to pages / exit codes** (as v0): every rule is an `eden_op` verb, slots are separate op calls (`save 7` is an argv, not a page), refusals go to `op_errors.txt`; the harness reads exit codes because it calls the op directly.
- **a Start that doubles as Setup breaks v0's "Start refused before Setup" check**, so v1 added NEW rows (`Start game` / `Stop game`) next to the v0 ones instead of changing `Start`.
- **harness variable cap**: `harness_case_op` keeps 32 variables for the whole file (not per case); the case file reuses names `v0..vN` per case (the generator maps them) instead of raising the cap in a shared op.
- **state inside the tree changes digests**: `op_errors.txt` lives in the game tree, so a refused call makes a tree digest differ; the refusal cases compare `world/` and `participants/` instead.
- **SETUP row counts the clock install** (`changes=32` with a clock, 31 without): the reference tree of the save/load case gets its own scratch house and clock so the two histories are byte equal.
- **a running clock is x86400** after Start: a `step <real_ms>` of an hour fires 3600 days (the harness only uses `step 0` after Start).
- **tomom**: its answer ignores most of the prompt at the fixed seed (`shining cosmos millions the` every time); the line is odd but logged honestly. The binary does not exist in a checkout (compiled programs are in no branch): the harness builds `chatbot_seed7` from the tracked source into a scratch copy, the live tomom folder is never read or written.
- Not done on purpose: riding, GUI window, live install, music, souls/ghosts, evolution art.
