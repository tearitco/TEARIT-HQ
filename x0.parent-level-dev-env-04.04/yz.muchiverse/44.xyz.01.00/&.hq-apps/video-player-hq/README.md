# video-player-hq

An in-house player for testing videos (first slice). Drop a video file onto the window (the renderer's generic XDND `drop_action`, first dropped path) or add one with the `add` row; it plays IN the window (ffmpeg raw frames fitted to the centre panel and blitted by the generic `<canvas>`; sound by an `ffplay -nodisp` child), with a queue, pause/resume/stop/next/prev/clear as numbered rows (relay-drivable), and a **file check** that says what is in the file: streams, size, length, average frame rate, and a warning for sparse variable-frame-rate files (the first Eden presentation had 3 video frames over 23 s and would not play in VLC).

- Launch: `sh open_video_player_hq.sh <house_root>`. Backend `ops/video_player_manager.c` (publishes `video_player_ui.txt`, reads `video_player_action.txt` by cursor); `ops/video_player_op.c` writes the command rows. Build: `ops/build_video_player.sh`.
- Harness hook: `video_player_manager --probe <file>` prints the file check.
- Layout: queue, status and file check on the left; the picture fills the centre; the transport (play, pause, resume, stop, back/fwd 10 s, prev, next, clear) is a bottom footer. A `<footer>` breaks a flex-row page, so this is the plain sidebar + panel layout. Region widths in a flex page must be written one property per line, in px.
- Opens from the Toys menu (`toy.pdl`, launcher walks up to the house root when given `run`).
- Cost: the renderer used about 30% of a core while a 980x680 picture played; lower `BOXW`/`BOXH` in the manager on a weak machine. Pause and seek restart ffmpeg and ffplay at the remembered second.
- Not done: no seek bar (only +-10 s rows); no taskbar entry besides Toys; the XDND drop was not exercised with a real drag by the author (the renderer's drop path is the same one File Explorer and events-hq use). Other video code: `103.media-studio/103.vid-edit` (a timeline editor with a preview and ffmpeg export).

## Bug fixed 2026-10-08: the player froze when a second video was dropped (and then played the wrong one)
**Symptom:** the first video played; dropping or choosing another showed "playing ... 0:32 elapsed" but the picture stayed on the old video and nothing moved; the Play button restarted item 0.
**Cause (found with `ps` wait channel and `/proc/<pid>/fd`):** switching videos stops the old decoder with SIGTERM and then `waitpid`s for it. The ffmpeg child was blocked writing a frame into the pipe whose read end the manager still held, so it could not exit, and the manager sat in `do_wait` forever (a live deadlock: the manager waits for the child, the child waits for the manager to read). The sound child stayed a zombie because it was reaped after the stuck wait. Separately, the footer buttons pass extra words after the verb, and `play <words>` was read as number 0.
**Fix:** `stop_child()` closes the pipe first so the decoder gets EPIPE; `kill_one()` never blocks (SIGTERM, poll `WNOHANG` for 300 ms, then SIGKILL); `play` only takes an argument that starts with a digit, otherwise it means the current item. **Rule for any manager that owns a child writing to a pipe:** close your read end before you wait for the child, and never `waitpid` without a timeout.

## Hide panel
The footer's `hide panel` / `show panel` button folds the left panel (queue, status, file check) to a thin strip and lets the picture use the full width (frame box 1420x690 instead of 1100x680; the decoder restarts at the same second). The manager publishes `side_on`, `side_cls` and `side_label`; the sidebar takes its class from `${side_cls}` and its rows use `show="${side_on}"`.

## Bug fixed 2026-10-08 (second): playback was about 1 frame per second
**Symptom:** the picture moved in jerks although the status clock ran normally. **Measured:** distinct writes of `frame.raw` per second were 0.8 (target 10). **Cause:** the decoder writes into a pipe that holds 64 KB by default, one frame is about 2.7 MB, and the manager drained the pipe once per 40 ms sleep, so each frame took over a second to arrive. **Fix:** the pipe is enlarged (`F_SETPIPE_SZ` 1 MB), the loop `poll()`s the pipe and wakes when data arrives, and the ui file is rewritten only every 300 ms instead of every loop. **Measured after:** 10.2 writes per second. Cost while playing a 1100x618 picture on this machine: renderer about 38%, ffmpeg about 19%, manager about 10% of a core; lower `BOXW`/`BOXH` on a weaker one. **Rule:** always measure the real delivery rate (distinct file writes per second), not the elapsed clock.

## Scene list with thumbnails and the scroll thumb (2026-10-08)
**What you asked for:** use the house's scroll *thumb* (the generic scrollbar the h-ai chat uses for long conversations) to move through a video's scenes. **Built:** a `<scrolllist>` in the left panel with one row per scene: a 100x56 thumbnail and its time, one row every 10 seconds, capped at 120 rows (20 minutes). The generic scrollbar appears by itself, with its thumb and the nav-numbered ^ and v arrows; Page Up/Down and the wheel scroll the list; clicking a row seeks to that time (`seek <second>`); the current scene's row is highlighted. A `follow: on/off` row makes the list start at the current scene so it tracks playback (it does not move the thumb: the scroll position belongs to the renderer). `scene -`/`scene +`, `back 10s`/`fwd 10s` are footer buttons.
**How it is made:** on play, one low-priority ffmpeg writes `thumbs/t_001.png ...` (RGB PNG, drawn by the draw core's `stbi_load` path); the manager publishes `n_sc` and `c_N_sprite|text|cls|act` (the variable prefix is the bind name: `bind="c"` means `c_N_...`). **Gotchas found:** (1) a repeat's variables use the *bind* name, not the name you think (`sc_` rows rendered blank until renamed `c_`); (2) an item with a `sprite=` draws the picture *instead of* its label, and needs an explicit CSS `height` (64px here) or the layout under-counts row height and rows leak over the fixed rows above; (3) thumbnails take about 40 s to generate for an 8-minute video at low priority, rows show their time until the picture exists.
**Known gaps:** the first one or two scene rows still draw over the fixed rows above the list (a row-height/clip issue at the top of the list; not fixed); the scroll thumb does not follow playback and cannot be dragged (renderer limits: see `PANEL-MINIMIZE-AND-BOTTOM-TOOLBAR-LAYOUTS-PLAN-2026-10-08.md` for the proposed renderer work, a scroll value bound both ways); no hover pop-up; the footer shows one row until its `+` pager is pressed; CPU while playing a 1100x618 picture is about 40% of a core in the renderer.
