# PIECECRAFT-XYZ DESIGN — a tick-based, voxel roguelike

**Status: PLAN ONLY — nothing built yet.** Written 2026-08-03, from a direct
design conversation. Read `&.widgits/WIDGIT_BIBLE.md`, `@.apps/
BOARD_WIDGET_ARCHITECTURE.md`, and `@.apps/PORTABLE_ENTITY_ARCHITECTURE.md`
before touching any of this — this doc summarizes and extends them, it
doesn't replace them.

---

## 0. Product intent (one paragraph)

piececraft-xyz is a Minecraft-shaped roguelike: real voxel blocks (place,
break, stack in Y), procedurally generated biomes, crafting and survival,
mobs/NPCs — but **tick-based**, not real-time (the world only advances when
the player acts, same discrete-simulation contract CDDA/NetHack use, not
"pause menu freezes a running clock"). It reuses this house's existing
camera system, control scheme, and xlector-style cursor pattern wholesale
rather than reinventing them, and it never holds the whole world in memory —
distant terrain and NPCs get compressed into small abstract records and
decompressed again as the player approaches, the same shape CDDA's overmap
uses conceptually, expressed in this house's own file-mediated-state idiom.

## 0a. URGENT PREREQUISITE — board-viewer's hardcoding must go first

**Direct user correction, must be fixed before piececraft-xyz adds a third
glyph set to it:** board-viewer's terrain rendering is currently hardcoded
per-game in C. `&.widgits/board-viewer/ops/bv_render_3d.c`'s own
`terrain_height()` / `terrain_color()` / `terrain_asset_hex()` are literal
`switch` statements keyed on hardcoded glyph characters (`'.'`, `'^'`, `'#'`,
`'~'`) with civ-txt's and tactics-txt's own specific heights/colors baked
directly into board-viewer's own source. That means every new host project
(piececraft-xyz included) that wants a different glyph vocabulary — and a
full voxel game needs a much bigger one (`dirt`, `stone`, `grass`, `sand`,
`water`, `wood`, `leaves`, `ore`, ...) — would require editing board-viewer's
own C files again. **This is exactly the hardcoding board-viewer's whole
"shared, focus-adaptive widget" design was supposed to avoid** (see
`BOARD_WIDGET_ARCHITECTURE.md` §2's own focus-adaptive table — the intent
was always data-driven branching, not literal duplicated switch arms).

**Fix: a generic terrain/entity legend file, modeled directly on this
house's own proven `default_op.txt` shape** (`name type handler
{description}` — the exact convention every project's own op-dispatch table
already uses, see `@.apps/tactics-txt/default_op.txt`). Board-viewer reads
this from the FOCUSED host project's own root, never hardcodes it:

```
pieces/system/terrain_legend.txt   (per-host, like board.txt/entities.txt)
# glyph | height | r | g | b | emoji_hex (optional, "-" = no texture)
.       | 0.0    | 60  | 160 | 60  | -
^       | 0.8    | 140 | 120 | 100 | 26F0
#       | 1.4    | 90  | 90  | 90  | -
~       | -0.3   | 40  | 90  | 200 | -
```

Board-viewer loads this once per focused project (cached the same way
`get_voxel8_cached()` already caches texture assets), and `terrain_height()`/
`terrain_color()`/`terrain_asset_hex()` become table lookups against it
instead of C `switch` statements. civ-txt and tactics-txt each get their own
`terrain_legend.txt` generated by their own `button.sh` (same place
`board.txt`/`entities.txt` already get touched+symlinked) with their
*existing* glyph tables moved out of board-viewer's C source and into these
per-host data files — a pure refactor, zero behavior change for either game.
piececraft-xyz then just ships its own, much bigger, legend file — no
board-viewer C changes needed ever again for a new block type.

**This doc treats that refactor as Phase 0** — it should land, and be
verified against civ-txt + tactics-txt's own existing HANDOFF/walkthrough
tests, before any piececraft-xyz-specific board-viewer work begins. This is
implementation work, not just documentation — flagging it here so it's
tracked, but not starting it without you confirming the plan below is right
first.

## 1. World storage — real precedent, not invented

Direct pointer to an existing, real format:
`1.TPMOS_c_+rmmp.0103.0001/projects/fuzz-op/maps/map_01_z{0,1,2}.txt` — a
map's vertical levels are stored as **one flat ASCII grid text file per Z
level** (fuzz-op calls it Z; this house's GL/board-viewer code calls the
same up/down axis Y — same axis, two names, doc uses **Z** since that's the
storage-format convention this design directly reuses), referenced from a
map-level `state.txt`:

```
# pieces/world_01/state.txt
name=World 01
type=world
active=1

# pieces/world_01/map_01/state.txt
name=Map 01
type=map
map_file=map_01_z0.txt
map_file=map_01_z1.txt
map_file=map_01_z2.txt
```

Each `map_01_zN.txt` is a plain rectangular character grid, one glyph per
X/Y cell at that Z level — exactly `board.txt`'s own format, just one file
per vertical slice instead of one file for the whole board. **Important,
confirmed by direct code search:** this format exists in fuzz-op as a real,
correctly-shaped fixture, but nothing in live mutaclysm code (`ops/
generate_map.c`, `ops/move_player.c`, `ops/choice.c`) actually reads/writes
multiple Z levels or a `pos_z` field yet — piececraft-xyz would be the
**first project to actually wire this end-to-end**, not adopting a
battle-tested live mechanic. Worth knowing going in, not a blocker.

### 1a. Chunking (world too big for one map_NN tree)

fuzz-op's `map_01` is one fixed-size map. A real voxel world needs many —
**chunks**, each its own `map_<cx>_<cy>/` directory using the exact same
`state.txt` + `map_<cx>_<cy>_z<Z>.txt` shape, keyed by chunk coordinate
instead of a single fixed map id:

```
pieces/world_01/
  state.txt                       # world-level meta (seed, active, tick)
  chunks/
    chunk_0_0/
      state.txt                   # map_file=... lines, chunk status (see §2)
      chunk_0_0_z0.txt .. z<N>.txt
    chunk_0_1/
      ...
    chunk_-1_0/
      ...
```

Chunk size: **needs a number from you** — Minecraft uses 16×16 columns;
given this is ASCII-grid-per-Z-level (not a packed binary format), a smaller
chunk (e.g. 16×16 or 24×24) keeps each `_zN.txt` file small and each
generate/compress/decompress operation cheap. Z-height range also needs a
number (Minecraft-scale ~256 layers would mean 256 files per chunk, which is
likely too many — a smaller build range, e.g. 32 or 48 Z-layers, keeps the
file count sane while still allowing real vertical building/mining). *See
open questions §9.*

## 2. Compression / decompression — the "don't hold the world in memory" system

Every chunk has a `status` field in its own `state.txt`: `active` |
`compressed`. This is not a memory-residency flag in a running process (no
process holds "the world" resident at all — every op is a short-lived,
file-reading, file-writing binary, same as every other project in this
house) — it's a **disk-representation** flag: an `active` chunk has its full
per-Z ASCII grid files and full per-entity directories on disk; a
`compressed` chunk has those deleted/archived and replaced with one small
abstract summary file.

```
pieces/world_01/chunks/chunk_3_-1/state.txt
  status=compressed
  seed_offset=91827           # so regenerating matches what was there before
  summary=biome:forest,structures:2,last_tick_active=4821

pieces/world_01/chunks/chunk_3_-1/npcs_compressed.txt
  # one line per NPC that was in this chunk when it compressed
  npc_id|profession|hp|last_tick|abstract_goal
  zombie_014|zombie|20|4821|wander
```

**Trigger, tick-driven (matches §5's tick model):** on every player-action
tick, an op (`piececraft_chunk_manager` or similar) computes the player's
current chunk coordinate and a fixed **active radius** (needs a number from
you — CDDA-style "reality bubble" is typically small, e.g. a 3×3 or 5×5
chunk window around the player). Any chunk that falls outside that radius
and is currently `active` gets **compressed**: its NPCs get one summary line
each appended to `npcs_compressed.txt` (and a real, permanent line appended
to `data/master_ledger.txt` — see §2a), then its full per-entity directories
and per-Z grid files are deleted, keeping only `state.txt` +
`npcs_compressed.txt`. Any chunk that enters the radius and is currently
`compressed` gets **decompressed**: regenerate its terrain deterministically
from `seed_offset` (same terrain-gen op §6 would have produced originally —
real, not placeholder, since it's a pure function of the seed) and
materialize one real NPC directory per `npcs_compressed.txt` line, replaying
enough of its `abstract_goal` to give it a plausible current position/state
(e.g. a `wander` zombie just gets placed at a random walkable tile in its
old chunk, not its exact old position — the abstraction is real, not just a
compression codec for identical restoration).

### 2a. Master-ledger posting — real precedent, reuse wholesale

`data/master_ledger.txt` already exists as this house's append-only event
log (see `@.apps/tactics-txt/ops/tactics_menu_input.c`'s own
`ledger_append()`: `timestamp|turn|side|action_type|details`). piececraft-xyz
reuses this file and format directly — every chunk compress/decompress
event, every NPC's major state change while compressed (e.g. "died of
starvation while compressed" resolved abstractly on a later tick), gets a
real ledger line. This makes the compression system **auditable**: you can
read `master_ledger.txt` and see exactly when and why any chunk or NPC was
compressed/decompressed/abstractly resolved, without needing the world
loaded.

## 4. Architecture — ops-bank-driven, board-viewer extended not forked

Per direct instruction: **extend board-viewer itself** with per-app ops,
not a new widget. Concretely:

```
pieces/system/ops_bank.txt         # per-host, like terrain_legend.txt (§0a)
# action        type   handler                          {description}
PLACE_BLOCK      void   ops/+x/pc_place_block.+x         {place held block at xlector target}
BREAK_BLOCK      void   ops/+x/pc_break_block.+x         {mine block at xlector target}
CRAFT            void   ops/+x/pc_craft.+x                {attempt recipe from inventory}
INSPECT          void   ops/+x/pc_inspect.+x              {examine block/entity under cursor}
```

Board-viewer's own input handler, on receiving an action key that isn't one
of its own built-in camera/nav keys, looks up the resolved command string
against the FOCUSED host's own `ops_bank.txt` (same `default_op.txt` shape,
same lookup discipline `prisc+x` already uses for every project's own op
dispatch) and fork/execs whatever binary is listed there — **board-viewer
never needs to know piececraft-xyz-specific verbs like `PLACE_BLOCK` exist
in its own C source**, exactly the same decoupling `terrain_legend.txt`
(§0a) gives for rendering. civ-txt/tactics-txt's existing `OPEN_BOARD_WIDGET`
commands don't need this (those are dispatched by the HOST's own
`*_menu_input.c`, not board-viewer) — this is specifically for verbs that
only make sense *inside* the board widget itself (you're looking at the
voxel world, you press "place", something needs to happen right there).

This is the actual fix for the "none of this should have ever been
hardcoded" catch: **any future host project** (not just piececraft-xyz)
gets its own board-viewer verbs for free, by writing its own
`ops_bank.txt` + its own op binaries — zero board-viewer C changes,
matching the same story `terrain_legend.txt` tells for rendering.

piececraft-xyz's own ops (`pc_place_block`, `pc_break_block`, `pc_craft`,
`pc_chunk_manager` (§2), `pc_generate_chunk` (§6), `pc_mob_tick` (§10), ...)
live in piececraft-xyz's own `ops/` directory, same as every other project's
ops — board-viewer just knows how to find and invoke them via the bank file.

## 5. Tick model — roguelike means discrete, not real-time

Direct correction incorporated: "roguelike" here specifically means
**tick-based** — the world only advances when the player takes an action
(move, place, break, craft, wait) — not permadeath, not necessarily
procedural-only. Both tick-based and real-time should exist as **configurable
op options** later, but the v1 default and this doc's whole design assume
tick-based, CDDA/NetHack-style:

- `pieces/system/world_state.txt`: `tick=<N>` — a monotonic counter,
  incremented by exactly 1 per resolved player action.
- Every op that represents a player action (`pc_place_block`,
  `pc_break_block`, `MOVE`, `CRAFT`, ...) increments `tick` by 1 on success,
  then invokes `pc_mob_tick` (§10) and `pc_chunk_manager` (§2) once each —
  the same "one real thing happens, then the world catches up by exactly one
  step" loop tactics-txt's own turn/action-pool model already uses
  (`actions_remaining_this_turn`), just at finer grain (every single action,
  not a 5-action turn budget).
- Compressed chunks/NPCs do **not** tick live — they only get resolved
  abstractly, in one lump sum, at the moment they decompress (§2), using
  `last_tick` vs current `tick` to know how much time passed. This is the
  actual mechanism that makes "the world stops when the player stops"
  true and cheap — no background simulation of anything off-screen.

## 6. Terrain generation + biomes

Deterministic, seed-driven, per-chunk (so decompression in §2 can
regenerate identical terrain without storing it): `pc_generate_chunk
<chunk_x> <chunk_y>` reads `world_state.txt`'s own `seed`, combines it with
the chunk coordinate (same idea tactics-txt's own `CONFIRM_START` uses for
`srand()`-based board generation, but keyed so the SAME chunk always
reproduces the SAME terrain — needs a real seeded-per-coordinate hash, not
raw `srand(time())` like tactics-txt currently uses, which is intentionally
non-reproducible there but would break decompression here).

Biome assignment: a coarse per-chunk biome value (e.g. a second, larger-
scale noise/hash pass over chunk coordinates — needs your input on which
biomes matter for v1: forest/plains/desert/mountains/ocean is a reasonable
real starting set) determines which glyph-frequency table `pc_generate_chunk`
rolls against per-cell per-Z-level, output straight into `terrain_legend.txt`-
compatible glyphs (§0a) so board-viewer renders it with zero new code.

## 7. Block place/break + inventory

- **Break**: `pc_break_block` reads the xlector's current target cell
  (X/Y/Z), reads that cell's glyph from the relevant `chunk_*_z<Z>.txt`,
  looks it up in `terrain_legend.txt` for its "drops" (needs a `drops`
  column added to §0a's legend format, or a separate `drop_table.txt` —
  your call), overwrites that cell's glyph with `.`/air, adds the drop to
  the hero's inventory file, increments `tick` (§5).
- **Place**: `pc_place_block` is the inverse — held item -> glyph, written
  into the target cell, subject to a basic validity check (target cell is
  currently air, and is adjacent to a non-air cell — the usual "can't place
  floating in empty space arbitrarily" rule, unless you want free placement
  for v1).
- **Inventory**: `pieces/hero_01/inventory.txt`, simple slot-based key-value
  (`slot_0=dirt:12`, matching the flat `key=value` convention every state.txt
  in this house already uses) — no need to invent a new format.

## 8. Crafting + survival

- **Crafting**: recipes as data, not code — `pieces/system/recipes.txt`,
  one recipe per line (`result|qty|ingredient1:qty1,ingredient2:qty2`),
  `pc_craft` reads it, checks inventory, consumes+produces. New recipes
  never need an op rebuild.
- **Survival**: `hunger`/`health` fields on hero state, decremented by
  `pc_mob_tick`-equivalent-for-hero logic on each world tick (§5) at a rate
  needing your input (how many player actions before hunger matters — real
  Minecraft ticks hunger on a large fixed timer, this should probably be
  "N ticks per hunger point" for the same reason).

## 9. Mobs/NPCs + combat

- Mobs are entities under the active chunk's own directory
  (`pieces/world_01/chunks/chunk_X_Y/mobs/<id>/state.txt`, same
  `entity_type/hp/pos_x/pos_y/pos_z/owner_id` universal-field shape
  `PORTABLE_ENTITY_ARCHITECTURE.md` already establishes) while active;
  compressed to one summary line (§2) when their chunk isn't.
- `pc_mob_tick`, called once per world tick (§5), walks every mob directory
  under every currently-**active** chunk only (never touches compressed
  chunks — that's the whole point of §2) and runs simple per-profession
  behavior (wander/aggro/attack) — same "each entity's own directory, own
  simple state-driven behavior" shape mychara's own pets already use.
- Combat: needs real numbers from you (damage formulas, hit/miss, or a
  simpler direct-HP-subtraction model like tactics-txt's own P1 stub
  combat) — flagged in open questions, not designed blind.

## 9a. Hero automation — "Automate" widget (DOC ONLY, later work)

Direct instruction, added 2026-08-03: a future widget screen, under an
"Automate" entry, that lets the player hand the hero over to scripted
behavior instead of (or between periods of) direct control — "mine/build"
and other scripted AI options, up to full unattended play. **Not being
built now** — this section exists so the plan is on record before it's
forgotten, matching this doc's own "ask questions, write it down, build
later" pattern from §0a/§10.

**Real precedent to reuse, not reinvent — direct instruction: "it should
kinda use same ai behavior tree logic as npcs uses for reusability and
uniformity."** That logic already exists in this house, twice, and both
times as the SAME real chassis:

- `014.wsr-pal…/ops/corp_decide.c` — the original: a `decision_mode` tier
  system (`0=preset, 1=weighted, 2=rl-stub, 3=llm, 4=human-park-and-wait`),
  reads a piece's own state, decides, transitions state.
- `@.apps/my-chara-txt/ops/mychara_ai_decide.c` — a real, live port of that
  SAME chassis onto a totally different game (farming/pets, not corp
  trading), adding one clean orthogonal axis on top:
  `supervision_mode` (`manual` — the op is a no-op; `semi` — decide +
  execute ONE action, then pause for a human `CONTINUE_AUTO`; `full` —
  decide + execute repeatedly, self-throttled to ~1 real action/sec so it
  never floods `master_ledger.txt` or makes automated play unobservable).
  Called once per idle tick from `main_module.pal`'s own `no_key` branch,
  same ~30ms cadence the existing idle-sync poll already runs at safely —
  self-gating, so it costs nothing when `supervision_mode=manual`.

**Why this is directly reusable for piececraft-xyz, not just similar in
spirit:** §9's own `pc_mob_tick` already needs a per-profession decision
loop for mobs/NPCs (wander/aggro/attack). If the Automate widget's hero-
automation logic is built as the SAME `decision_mode`/`supervision_mode`
chassis — a `pc_ai_decide` op, called once per world tick (§5) for
whichever entity currently has `supervision_mode != manual` set on its own
state (hero OR any NPC, no special-casing which) — then "the hero can
mine/build on autopilot" and "mobs wander/aggro" are the SAME code path
with different preset rule tables per profession, not two separate
automation systems that drift apart. This is the actual meaning of "for
reusability and uniformity," confirmed against real, already-working code
rather than assumed.

**Sketch, not a spec (needs its own real design pass later):**
- Widget screen (paired with the game the same real way board-viewer now
  is — ledger discovery per §4/§0a's own follow-up, own GL window) shows:
  current `supervision_mode` for the hero, a preset-rule summary (`decision
  _mode=0` tier, e.g. "if hunger low, eat; if inventory has N wood, build;
  else mine"), and controls to change either.
- `decision_mode=0` (preset) ships first, matching both real precedents'
  own build order — 1/2/3 (weighted/rl/llm) are real, later, per-tier
  future work, not v1.
- Scriptable "add commands/ops" (the player authoring their own automation
  rules, not just picking a fixed preset) is a genuinely bigger feature —
  closer to `xelector-context.md`'s own event-editor idea (§3a) than a
  simple mode toggle. Flagged here as a real future direction, not
  designed yet.
