## 1. Bug #1 - character doubling on real typing - FIXED, CONFIRMED WORKING

TESTED: user confirmed live ("it works for me now") after this fix.

Symptom: typing "testing" into the editor canvas landed as
"tteessttiinngg" - every character exactly duplicated.

Root cause (confirmed via direct source read + one live isolation test -
a single manual `echo 88 >> interact_relay.txt` produced exactly ONE
character in editor_buffer.txt, proving the READ side, agy_edit_key.c's
main loop, was innocent): TWO independent capture paths each deliver the
SAME physical keystroke into `interact_relay.txt` whenever a real
gl_mirror GL window is open -
  (1) `014.wsr-pal💸️📌️+2/system/gl_mirror.c`'s own GLUT keyboard()/
      special_keyboard() callbacks append directly (see append_key(),
      line ~233).
  (2) `system/keyboard_input.c`'s terminal capture -> `pieces/keyboard/
      history.txt` -> `chtpm_parser_pal.c`'s `process_key()` INTERACT
      branch (around line 3467, `strcmp(el->onClick, "INTERACT")`) ->
      `inject_raw_key(eff)` at line 3499 (pre-fix) - a second,
      independent forward of the same key.

gl_mirror.c already had the intended fix mechanism sitting unused:
`pieces/system/gl_focus.lock`, written by gl_mirror while it's alive
(update_focus_lock()/remove_focus_lock(), gl_mirror.c line ~199-216),
with its own header comment CLAIMING "keyboard_input.c was updated to
check the same lock" - that claim was FALSE, confirmed via grep, zero
hits for "gl_focus"/"focus_lock" in either keyboard_input.c or
chtpm_parser_pal.c before this fix.

FIX APPLIED (2026-07-30) in the SHARED system source:
`014.wsr-pal💸️📌️+2/system/chtpm_parser_pal.c`, INTERACT branch, right
before the `inject_raw_key(eff);` call - now wrapped in:
```c
{
    char *lock_path = build_path_malloc("pieces/system/gl_focus.lock");
    int gl_owns_input = (lock_path && access(lock_path, F_OK) == 0);
    free(lock_path);
    if (!gl_owns_input) inject_raw_key(eff);
}
```
Skips the redundant forward ONLY when gl_mirror is actually alive for
this session. NO_GL/headless sessions never see the lock file, so
inject_raw_key still fires exactly as before there (the only path for
typed text in that mode). Button navigation is a completely separate
branch of process_key(), untouched.

REBUILD STATE: the shared binary at `014.wsr-pal💸️📌️+2/system/
chtpm_parser_pal` was recompiled from the fixed .c (gcc, compiles clean,
confirmed via checksum). It was then copied into BOTH `102.agy-txt/
system/chtpm_parser_pal` and `102.editor-📄️00.00/system/
chtpm_parser_pal` via each project's own `scripts/build.sh` (checksums
match the wsr-pal master - confirmed via `md5sum`). GOTCHA HIT WHILE
DOING THIS: a project's own `scripts/build.sh` does `cp ... 2>/dev/null
|| true` for these binaries - if ANY process for that project still has
the OLD binary open (ETXTBSY), the cp silently fails and the `|| true`
swallows it, but the script still prints "copied system/ from wsr-pal"
and exits 0. ALWAYS kill every live session for a project (`ps aux |
grep <project-dir>`) before rebuilding, then verify via `md5sum` against
the wsr-pal master - do not trust the build script's own success message
alone. This bit me once this session (a leftover manual test session I'd
forgotten to kill silently blocked agy-txt's own rebuild for one pass).

WHY NEITHER PROJECT'S OWN "level-2" HARNESS EVER CAUGHT THIS: both
test-harn-ed-app and test-harn-agy-txt inject keys via direct file
writes (one deliberate write per intended character) or via an op's own
PASTE mode - never a real OS-level keystroke. This class of bug (a race
between two independent real capture PROCESSES) is structurally
invisible to that kind of injection. See ed-app-vs-agy-txt.md §3 and
todo-j30.txt §5's 2026-07-30 UPDATE note (same handoff tree,
`#.haiku+/30.jul-30-handoff/1.ngn/`) for the fuller writeup - both
already updated with this finding before this handoff was written.

## 3. Separately - missing directory browser / back-navigation (real gap, not a bug - a scope miss)

User's own question: "where is file explorer and back functionality?"
Correct question - it doesn't exist. What agy-txt currently has is a
minimal stub:

`102.agy-txt/pieces/chtpm/layouts/file_browser_save.chtpm` (and
`file_browser_load.chtpm`, same shape) - just a raw PATH field
(blind-typed, no directory listing) + SAVE/LOAD + CANCEL (which goes
back to file_menu.chtpm - the ONLY "back" that currently exists, no
up-a-directory navigation within the browser itself, because there's no
browser).

The DISPLAY bug in §2 is inside `102.agy-txt/ops/agy_compose_view.c`,
function `compose_file_browser()` (~line 131-176). One cosmetic thing
noticed while reading it, separate from §2's real bug: line 157,
`snprintf(row, sizeof(row), "PATH: %s[X]", typed);` - the literal
`[X]` is a hardcoded SUFFIX meant to look like a cursor block, appended
after `typed` regardless of its content. It is not itself the bug (in
§2b's working test, `typed` correctly appeared BEFORE it - "PATH:
X[X]") but it's a confusing, easy-to-misread format either way and
worth cleaning up once §2's real bug is fixed.

Ops (`&.widgits/file-menu/ops/`):
  - `fm_scan_dir.c` - genuinely generic, zero project-specific paths,
    real, clean, reusable as-is. Interface: `fm_scan_dir <dir>
    [filter]`, prints to stdout one line per entry: `DIR|<name>|<size>|1\n`
    or `FIL|<name>|<size>|0\n`, sorted dirs-first then case-insensitive
    name.
  - `fm_menu_input.c` (564 lines, fully read) - the real dispatch, all
    of it in `handle_file_browser()` (line ~283-437), driven off a
    simple key-value state file (`pieces/system/fm_state.txt`: `mode`,
    `browse_mode` [save_as/load/pair], `browse_dir`, `cursor_pos`,
    `search_text`, `path_buffer`). FIXED LAYOUT INDEX SCHEME (line
    ~298-310): index 0 = SEARCH field, 1 = FILE field, 2 = BACK, 3..
    (2+entry_count) = directory entries (re-scanned live via
    `fm_scan_dir.+x` each dispatch, so the index range moves with
    however many entries are currently listed), then confirm, then
    cancel. Real up-navigation: BACK (line 323-333) does
    `strrchr(browse_dir, '/')`, truncates to the parent, writes it back
    to `browse_dir`, resets cursor to 0 - genuinely goes up a real
    directory level, not a fixed "return to file_menu" shortcut like
    agy-txt's own CANCEL. Real descend: selecting a DIR entry (line
    340-345) appends `/name` to `browse_dir` and resets cursor - you

    writes its full path into `path_buffer` and moves cursor to the
    FILE field (1) for review/edit before confirming. Confirm (line
    366-384) sends `SAVE_AS:<path>` or `LOAD:<path>` via
    `enqueue_cmd_with_path()`. Typing (search or path field) is plain
    per-keystroke append (line 417-436) PLUS a separate PASTE mode
    (`handle_paste()`, line 508-531, `fm_menu_input.+x PASTE "<text>"`)
    for whole-string/emoji-path insertion - same real reason as
    agy_edit_key.c's own PASTE mode (a keystroke is one byte, an emoji
    is not one keystroke).
  - `fm_compose_frame.c` - confirmed (grep, not full read) it renders
    off the EXACT SAME `browse_dir`/index scheme: `[<- BACK]` at the
    fixed BACK slot (line ~124), then one line per `fm_scan_dir.+x`
    result for the current `browse_dir` (line ~132-139). Read this file
    in full before implementing agy-txt's own render side - the exact
    line-formatting/numbering logic needs to match fm_menu_input.c's

  - `fm_set_focus.c`, `fm_enqueue_cmd.c`, `ledger_append.c`,
