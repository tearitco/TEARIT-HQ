Round 4 (same night, follow-up live reports on the scroll work above):
- REAL BUG FOUND AND FIXED: "thumb moves but doesn't change display" - the row-shift
  code only moved each <row> CONTAINER's own y, but css_layout_pass() (the shared
  layout engine) already gives every TILE inside it an absolute, independent y during
  its own recursion - draw_elem() reads e->y directly, never parent-relative. So
  scrolling moved the thumb and the row's own (invisible) box, but not a single visible
  tile. This is a real divergence from the OLD khtpm_hq_render.c's own hand-rolled
  layout engine, which didn't have this problem - porting that file's scroll snippet
  verbatim wasn't actually equivalent against the shared engine's different
  children-positioning model. Fixed with a new dbhq_pal_shift_subtree() that shifts
  the whole row subtree, not just the container. VERIFIED with real before/after
  screenshots of a live drag (not just a debug print of internal state, which is what
  missed this bug the first time) - content genuinely scrolls now, rows 9-49 became
  rows 5-49 after dragging.
- Scrollbar UP/DOWN ARROW BUTTONS added (a real, standard scrollbar affordance that
  didn't exist at all before - only track click/drag/wheel/Page keys existed).
- Made the arrows REAL, KEYBOARD-ACCESSIBLE, NUMBERED Elems per direct instruction
  ("they need to be numbered (1 and 2), with nav feature for accessibility / disabled")
  - not raw mouse-only pixels. Up is ALWAYS nav 1, down ALWAYS nav 2, regardless of
  enabled/disabled state (disabled is a separate concept from unnumbered - a disabled
  control keeps its identity/position in the tab order rather than silently vanishing
  and shifting every other number depending on scroll position). Disabled state dims
  the triangle color and is a harmless no-op on activate (the existing scroll clamp
  already prevents going past the limit). Dispatch goes through the SAME generic
  onclick path (dbhq_activate_elem, "scroll:up"/"scroll:down") every other tile uses,
  so a mouse click and a keyboard Enter-on-focused-nav share one code path.
- Added a real, GENERIC `badge_align_left` field to the shared Elem struct (khtpm_
  render_core.c) and wired it into draw_elem() (khtpm_draw_core.c) - live report: the
  arrow badges ran off the right edge of the screen, since they're tiny elements
  pinned at the window's own right edge and the normal badge position grows
  rightward from the label. This is a real, reusable capability (any edge-pinned
  element could hit the same problem), not a palettes-only hack - default 0 keeps
  every existing consumer's behavior unchanged. Verified with a screenshot: badge
  "[>]1." now renders fully on-screen, ending at the arrow's own left edge.
- Confirmed the same mechanism already applies to the emojis category automatically
  (gated on g_is_palettes && g_pal_has_grid, never category-specific) - no separate
  implementation needed; emojis' wide 20-col grid just doesn't need scrolling at its
  current tile count, so both arrows correctly show disabled/full-track-thumb there.
