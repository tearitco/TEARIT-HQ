# 2026-09-27 — MarS StreetRace: Windows port, and the game bugs it exposed

Session log. Superseded only by a later dated file.

## Result

Builds 31/31 and plays. Run it with one command from the project directory:

    .\run-win32.ps1

`run-win32.ps1` rebuilds when any input is newer than the binaries, then
launches. `-Force` always rebuilds, `-NoBuild` goes straight to playing.

The portability constraint held for the port itself: **no `.c` or `.sh` file
was changed to make Windows work.** All Windows adaptation lives in
`win32-compat/`, force-included via `gcc -include` or found via `-I`.

## The eight bugs, in the order they were found

Seven of these were invisible until the thing was actually run. Reading the
code would not have found any of them.

### 1. `select()` hot-spun on redirected stdin

`win32-compat/sys/select.h` returned -1 for a pipe, and eight programs poll
stdin with the classic non-blocking `select(0+1, &fds, NULL, NULL, &tv)`
"is a key waiting?" idiom. A console input handle becomes signalled when a
key waits; **a pipe read end never does**, so `WaitForSingleObject` returns
WAIT_FAILED. The result was an unbounded loop printing
`Input received: -1` forever.

Now probed per handle type: console via `WaitForSingleObject`, pipe via
`PeekNamedPipe`, disk file via `GetFileSizeEx` (which is what makes the game
drivable from a script at all).

### 2. `system()` returned 0 unconditionally — the port lied to the game

`setup_corporations.c` branches on `system()`'s return value. The shim
returned 0 whatever happened, so a command that had *failed* took the
success branch and printed "Analysis completed successfully". Now returns the
real child exit status via `GetExitCodeProcess`, as POSIX requires.

### 3. `robocopy` never seeded `data/`

`cp -r SRC data/` always yields a destination with a trailing separator, and
robocopy treats that as malformed: **exit 16, nothing copied**. So `data/`
was silently never seeded. The trailing slash is now stripped; robocopy
already copies SRC's *contents* into DST and creates DST if absent, which is
what the slash meant.

### 4. The launcher could not find the directory that plainly exists

Two separate faults, both about the emoji in the house directory name:

- It hand-built the name from code points and omitted **U+FE0F** (variation
  selector), so `Test-Path` rejected a directory that was right there. Names
  are now discovered by glob; the naming scheme already varies in emoji,
  variation selectors, ® and ™, and is not stable enough to re-derive.
- It spawned `powershell -File <path>`. A child process receives its
  command line through the **ANSI codepage**, so the emoji arrives as
  mojibake. This is the same limitation that made `_.start.<emoji>.sh` in
  the repo have a mangled directory name baked into it, and the same reason
  the build links non-ASCII outputs via an ASCII temp name (ld.exe has the
  identical constraint). The orchestrator is now invoked **in-process** via
  the call operator, which passes a .NET string with no code-page round trip.

### 5. `Resolve-Command` tested against a stale CWD, and the orchestrator hung

`Set-Location` does not move the process CWD, and `Test-Path` resolves
relative paths against `[System.IO.Directory]::GetCurrentDirectory()`, which
still pointed at wherever the shell started. So `Test-Path "+x/main.+x"` was
False for a file that existed. It went unnoticed because the function fell
through and returned the raw string, and `Start-Process` resolved it against
PowerShell's location instead — the lookup was **dead code that worked by
accident**.

The moment that dead lookup was trusted, the second fault appeared:
`Start-Process` returned no process object, and the watch loop dereferenced
a null `Proc` forever. Launching before building hung silently for the full
150s timeout instead of saying so. An unresolvable command is now reported
before anything starts, and the orchestrator exits 1 naming the missing
binary and the script that produces it.

### 6. Stdout block-buffered — the blank screen (hardest to diagnose)

The user reported the game never reached its screen. It had, in fact, and
this is the reason that report and this log exist.

The Linux orchestrator prepends `stdbuf -oL` to every command
(`l.button.<emoji>.g11.c:116`, macOS twin at `:120`) precisely to force line
buffering. The PowerShell orchestrator dropped it, with a comment claiming
there was no Windows equivalent. **There is: `setvbuf`.**

With stdout pointing at a file rather than a console, the C runtime
block-buffers. 4 KB of menu never reached the orchestrator's log, so nothing
was echoed, so the screen stayed blank — while `game.+x` sat alive at its
first prompt the whole time, holding the menu in a buffer it would only
flush on exit. It looks exactly like a hang.

This also **invalidated earlier evidence in this project**. The menu had only
ever been seen in runs where the process was subsequently killed or fed `n`
— and killing it is what flushed the buffer. Any "it works" claim verified by
killing the process and reading the log afterwards is worthless. Verify
while it is still running.

Fixed with a GCC `__attribute__((constructor))` calling
`setvbuf(stdout, NULL, _IONBF, 0)`, which reaches all 31 binaries via the
force-include. `_IONBF` rather than `_IOLBF` deliberately: the Microsoft C
runtime does not honour `_IOLBF` and treats it as full buffering, which
would reproduce the identical bug.

### 7. The grandchild's output bypassed the tee

With #6 fixed, the game was still blank **under the orchestrator** while
working perfectly when run directly. Isolating it showed `game.+x` alone was
fine, which located the fault in the process chain:

    orchestrator -> main.+x -> game_setup -> game.+x

`mars_run_console` used plain `CreateProcess` with no
`STARTF_USESTDHANDLES`, so the grandchild was handed the *console's* handles
instead of the ones its parent had been given. `game.+x` painted straight to
the terminal and the orchestrator's tee never saw a byte. Under Linux the
same chain inherits the pipe all the way down.

Fixed by duplicating the three std handles as inheritable and passing them
explicitly. `gl_cli_out.txt` went from 789 to 2167 bytes, which is the
missing game UI. Ownership of the duplicates is tracked, because closing an
original std handle on the duplicate-failure path would break the parent's
own stdio.

### 8. The build intermittently failed on files that compile cleanly

Not a source problem. Observed across consecutive passes, always transient,
always on files that compiled cleanly in isolation to the same output path:

    gcc.exe: fatal error: cannot execute '.../collect2.exe'
    collect2.exe: error: ld returned 15 exit status
    gcc exit 15, with completely empty stderr

alongside the host-side `Win32 internal error "No process is on the other end
of the pipe" 0xE9`. Spawning 31 compilers back to back from one PowerShell
process, on a OneDrive-synced path, exhausts something the session does not
get back.

An earlier fix retried only when the error text matched `"cannot execute"` or
`"ld returned"` — too clever, because the failures have no stable signature.
Now **any** nonzero exit is retried up to three times. A genuine compile
error is deterministic, so it fails all three and is reported with its real
message; only transient failures pass. Retries are counted and reported
rather than hidden.

Also worth knowing: the whole tree is on a OneDrive-synced path. Do not run a
build while a game instance is running — the linker cannot open its output.

## Game bug found and fixed (cross-platform)

`setup_corporations.c:468` called `system("./analysis_loop")`, but this
project builds `analysis_loop.+x`. That call was dead on **every** platform:
the shell failed, the non-zero status fell into the "Analysis failed"
branch, and initial stock prices were silently left unset.
`day_loop.c:25` already spelled it correctly. Verified after the fix:
"Analysis completed successfully", stderr clean.

This is the one `.c` change in the port, and it is a game bug, not a
portability change.

## Known pre-existing bugs — deliberately NOT fixed

The user's standing request is to fix the game for both platforms, so these
are recorded as decisions rather than omissions.

### The periodic economy does not exist

This is the significant finding, and it is much larger than it first looks.

- `dividend_loop.c` and `payroll_loop.c` are **380-line verbatim copies of
  `game.c`'s `main()`** — byte-identical function sets, all 14 of them. They
  print `Usage: ./game ...` and exit 1. This is the origin of the two stray
  "Usage:" lines at startup: they are `dividend_loop` and `payroll_loop`
  each printing a message belonging to a different program.
- `tax_loop.c` and `hour_loop.c` are **19-line stubs** that append
  `"Hello, TAX!"` / `"Hello, DAy!"` to a data file. `hour_loop` writes to
  `data/day.txt`, not to an hour file.
- `presets/schedule.txt` names `./+x/salary_loop.+x`, which no build
  produces — the source is `payroll_loop.c`. This is the
  `'+x\salary_loop.+x' is not recognized` message, and it fires again every
  in-game year.
- `news_loop.c` is the only genuine periodic implementation.

So tax, dividend, payroll and hourly ticks are unimplemented on **both**
platforms. Nothing about this is Windows-specific.

### Why the dividends were NOT implemented, despite being asked for

Implementing them was explicitly requested, and the data model does support
it: `marst-arch-j23.txt` documents the append-only ledger, lists `DIVIDEND`
as a valid action, and states dividends are "triggered by game, automatic";
corp sheets already carry `Dividend Yield` and `Dividend Payout Per Share`.
The obstacles found are not mechanical:

1. **Every dividend is currently zero.** `setup_corporations.c` writes
   `Dividend Yield: 0.00%` and `Dividend Payout Per Share: 0.00` for all
   corporations. A correct implementation pays $0 forever, so it cannot be
   distinguished from a broken one until someone actually sets a payout via
   `management.c` ("4. Set Dividend Payout").
2. **The schedule would not deliver it anyway.** `data/wsr_clock.txt` carries
   the date `0000-00-00` and only the time advances. `clockwise_loop` fires
   `3_months` when the quarter changes, so quarterly work runs **once at
   startup and then never again**. Every tick log reads `0000-00-00`.
3. **The ledger is empty and the reader is a stub.** `master_ledger.txt` is
   zero bytes; `master_reader.c` per its own documentation only handles
   incorporation events and needs extending to `DIVIDEND` before a posted
   dividend would actually credit anyone.
4. **The amount rule is genuinely unspecified.** Portfolios store
   *percent held* and *value in millions*, not share counts, so "payout per
   share × shares" has no share count to work from. The available
   substitutions (value × yield, or reconstructing shares from value ÷ price)
   are both defensible and produce materially different economies.

Payroll is weaker still: the only concrete fact anywhere is
`payroll_tax = gov.gdp * 0.0200` in `setup_governments.c`, with no
statement of who is assessed, who remits, or when.

Writing plausible-looking numbers would be fabricating game mechanics rather
than fixing a bug, and given (1)–(3) the result would be unverifiable. **The
required next input is a rules specification, not more code.** The four facts
above are the questions to answer.

`g11.c` could not be ported to C because it uses `pthread_tryjoin_np` and
`pthread_timedjoin_np`, GNU extensions mingw-w64's winpthreads does not have.
The logic is small, so the orchestrator is reimplemented in PowerShell
instead of rewriting the join machinery.

## Verified

- 31/31 artifacts, three consecutive clean runs
- `run-win32.ps1` auto-rebuilds on a header-only change, and `-NoBuild` /
  `-Force` both actually take effect (the `param()` block was missing, so
  they were silently ignored at first)
- Menu renders **while the process is still running**, and is captured in
  `gl_cli_out.txt`
- Game reads input and exits on `n`
- Orchestrator starts both `locations.txt` entries, tees combined output,
  shuts down when the killer exits, and fails in 1s with a clear message if
  `+x/` is empty
- `setup_corporations.+x` reports "Analysis completed successfully"
- stderr clean end to end
