## The task

The user wants a "mob spawner" feature: a small square room (e.g. 3x3 or 5x5 tiles) with walls around it and exactly ONE opening/doorway, containing a grave/headstone emoji tile in the middle, that acts as a monster spawner - it should always try to keep exactly 4 monsters alive that "belong" to it, spawning replacements automatically as the hero kills them, so the player has a renewable source of monsters to fight without needing map edits every time monsters die.

### What already exists (read these before writing code)

- pieces/registry/terrain/terrain_types.txt - glyph|id|name|walkable|rgb_top(R,G,B)|unicode|rgb_top_emoji(R,G,B). No grave/headstone entry exists yet - you'll need to add one (pick an unused glyph char - #=wall, .=floor, +=door, "=grass, :=dirt, ==pavement, %=rubble, ~=water_sh, W=water_dp, T=tree, '=window, >=stairs_down, <=stairs_up are all taken - pick something else, e.g. g for grave, walkable=1, since a headstone should probably not fully block movement - use your judgment). Real emoji: 🪦 (headstone) is the natural choice.
- pieces/registry/monsters/monster_types.txt - glyph|id|name|hp|damage|unicode. Currently has zombie (Z) and zombie_child (z). Reuse these, don't invent new monster types unless needed.
- pieces/world_01/map_start/ (and sibling maps map_02, map_gen_01, building_01_f2, building_01_gf) - each has map.txt (terrain glyphs, one row per line), furniture.txt (optional furniture layer, same shape, space = nothing), state.txt (width/height/turn keys), monsters/<instance_name>/state.txt (per-monster-instance dir, fields: pos_x, pos_y, hp, monster_type, optionally decision_mode/flee_hp_pct - see ops/tick_monsters.c's own header comment for what these mean), items/, hero/.
- ops/tick_monsters.c - runs once per hero turn (called from the pal loop after end_turn). Reads every monster instance dir under the CURRENT map's monsters/, moves each one toward/away from the hero, or attacks if adjacent. This is where per-tick spawner logic should probably be added (it already runs every turn, is already scoped to "the map the hero is currently on", and already has all the file-reading helpers you need - read_kv_int, read_kv_str, resolve_root, etc.). Read the whole file first, it's short, ~382 lines.
- ops/move_player.c around line ~580 - bump-attack/monster-death handling: `if (monster_hp <= 0) { ... rmdir(monster_dir); }`. This is how a monster instance directory gets deleted when it dies. Your spawner logic needs to detect "fewer than 4 of this spawner's monsters currently exist" and create new monster instance directories to top back up to 4 - read this function for the exact monster-dir-removal pattern so your spawn code creates dirs in a matching, consistent shape.

### Design requirements

1. Registry: add a grave/headstone terrain (or furniture - your judgment on which fits better; furniture might be more consistent since it's a decorative object placed on top of floor, matching how f_table/f_bed etc. work, but terrain also has precedent for one-off features like stairs - pick whichever is more consistent with existing conventions) entry with a real emoji (🪦) and a sensible rgb_top color (headstones are grayish, e.g. 120,120,130 or similar - match the tone of existing entries like t_rubble's 120,110,100).
2. Map authoring: build a small enclosed room (walls on all sides, ONE gap in the wall as the doorway) around the grave/headstone tile, and place it into an existing map (pick one, e.g. map_02 or map_start - check which has open unused space in its map.txt/furniture.txt grid first so you don't overwrite existing content) OR create a small new map area if that's cleaner - your call, but prefer editing an existing map's map.txt/furniture.txt over inventing a whole new map dir, to keep this simple and immediately visible to the user.
3. Spawner tick logic: every tick_monsters.c run (once per hero turn, when the hero is on the map containing the spawner), count how many currently-alive monster instances are tagged as belonging to this spawner (add a new state.txt field, e.g. spawner_id=grave_01, to every monster the spawner creates, so counting doesn't accidentally include unrelated monsters elsewhere on the map), and if the count is below 4, create enough new monster instance dirs (alternate between zombie/zombie_child or pick whichever you think fits - your call) with fresh state.txt (pos_x/pos_y placed somewhere reasonable inside or adjacent to the spawner room - not on top of the hero, not outside the room walls, not overlapping another monster), hp set to that monster type's registry hp, monster_type set correctly, and the spawner_id tag, to bring the count back to 4. This should keep working turn after turn indefinitely (a real, permanent renewable spawner, not a one-time spawn).
4. The spawner's own location (which map, which x/y the grave tile sits at, the room bounds) should be recorded somewhere sensible so tick_monsters.c knows where to count/spawn - could be a small new registry-style file (e.g. pieces/world_01/<map>/spawners.txt, one line per spawner: spawner_id|map_id|x|y|room_x0|room_y0|room_x1|room_y1) so the mechanism could support multiple spawners later without being hardcoded to one map/position - but don't over-engineer; a single hardcoded spawner is fine if a generic file feels like overkill. Use your judgment on how much generality is warranted; the user asked for ONE spawner, not a spawner system, but a tiny bit of structure (a data file rather than magic numbers baked into tick_monsters.c) will make it easy to extend later and is very low cost.
