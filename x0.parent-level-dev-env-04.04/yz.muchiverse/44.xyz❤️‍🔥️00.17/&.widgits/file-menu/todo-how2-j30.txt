## 0. Fixed layout-index contract (needed to read the bugs below)

`handle_file_browser()`, `ops/fm_menu_input.c` line ~298-310:
```
0 = SEARCH field
1 = FILE field
2 = BACK
3 .. 2+entry_count = directory entries (live, re-scanned every dispatch)
2+entry_count+1 = confirm button
2+entry_count+2 = cancel button
```
`cursor_pos` (persisted in `pieces/system/fm_state.txt`) selects which
row is current. Arrow keys move it; digit/Enter dispatch acts on
whichever row `cursor_pos` currently points at.

## BUG 1 - Enter on the FILE field does nothing (user: "hitting enter doesn't save the file")

`ops/fm_menu_input.c`, inside `handle_file_browser()`, the `key == 10
|| key == 13` branch, lines 318-321:
```c
if (cursor_pos == 0) {
    /* SEARCH field selected; typing goes to search_text */
} else if (cursor_pos == 1) {
    /* FILE field selected; typing goes to path_buffer */
}
```
Both branches are EMPTY - the comments describe what happens for
PRINTABLE keys (handled separately, lines 417-436), not what Enter
itself should do. Pressing Enter while `cursor_pos` is 0 or 1 falls
through every other `else if` in this same block and hits the trailing
`return;` at line 390 - genuinely a no-op. To actually save/load, the
user must separately arrow-navigate DOWN to the confirm button's own
index (`2+entry_count+1`) and press Enter THERE. Nothing in the UI
currently tells the user this - after typing a filename, the obvious,
expected action (press Enter) does nothing, which reads as "doesn't
work" exactly as reported.

**TPMOS/house-native comparison**: this house's own chtpm engine has a
real, DIFFERENT, richer convention for exactly this - `<cli_io>`
elements (`014.wsr-pal💸️📌️+2/system/chtpm_parser_pal.c`, the
`strcmp(el->type, "cli_io") == 0` branch, line ~3393-3421) treat Enter
as SUBMIT: syncs the typed value to gui_state, clears the input buffer,
and fires `inject_raw_key(13)` - dispatching a real KEY:13 action to
the project's own manager/op, i.e. Enter-in-the-field IS the confirm
action, no separate button to navigate to. TPMOS's own
`agy-text-editor_manager.c` (`1.TPMOS_c_+rmmp.0103.0001/projects/
agy-text-editor/manager/`) relies on exactly this - its own
`file_path_input`/`search_query` cli_io fields submit on Enter. FM's
buttonless architecture never adopted an equivalent - it has no
concept of "this specific row, when Enter is pressed, should trigger
the SAME action as pressing Enter on the confirm row instead of doing
nothing."

**Fix direction (not yet implemented)**: cheapest real fix staying
inside FM's own buttonless model - make the `cursor_pos == 1` (and
arguably `== 0`) Enter branch DO what the confirm-index branch already
does (jump to it: `cursor_pos = confirm_idx;` then fall through to that
existing logic, OR literally call the same code path). Do not invent a
parallel second implementation of the confirm logic - reuse the
existing `cursor_pos == confirm_idx` branch (line 366-384) by either
falling through to it or extracting it into a small helper both cases
call.

## BUG 2 - no "active typing" state; ESC always exits the whole browser (user: "the file name input never goes active so hitting esc exits the save as menu")

`ops/fm_menu_input.c`, `handle_file_browser()`, line 312-316:
```c
if (key == 27) {
    write_kv(fm_path, "mode", "main_menu");
    write_kv(fm_path, "status_line", "");
    return;
}
```
ESC is handled ONCE, unconditionally, at the top of the function,
regardless of `cursor_pos`. There is no separate "currently
typing/engaged" state anywhere in `fm_state.txt` (compare to `mode`,
`browse_mode`, `cursor_pos`, `search_text`, `path_buffer` - none of
these represent "actively receiving keystrokes" as distinct from
"this row happens to be selected"). Any printable key lands in
`search_text`/`path_buffer` purely because `cursor_pos` is 0 or 1 at
the time (lines 417-436) - there was never an explicit "engage" step
to begin with, so there is nothing for ESC to narrowly undo. The user's
report is exactly correct: there is no "active" state to enter, so ESC
can only ever do the one thing it's coded to do - leave the whole
browser.

**TPMOS/house-native comparison**: `<cli_io>` elements have a REAL
active/focused state, tracked by the engine itself (`active_gui_index`
family, `is_interact_typing()`-equivalent tracking, `export_active_index()`
in chtpm_parser_pal.c) - focusing a cli_io element is a distinct step
from having it merely be the nearest selectable row, and ESC on a
focused cli_io is understood by users as "stop typing here," not "leave
this screen" (matching editor.chtpm's/agy-txt's own onClick="INTERACT"
convention too - ESC exits INTERACT typing, stays on the same layout).
FM's own file_browser mode has no equivalent third state.

**Fix direction (not yet implemented)**: introduce a real
"editing"/"engaged" boolean into `fm_state.txt` (e.g. `field_active=1`),
set when the user does something explicit to begin typing into
SEARCH/FILE (a real "engage" action is needed here, since FM currently
has no such trigger AT ALL - could be as simple as Enter-on-the-row
setting it, or a dedicated key), and change the ESC branch to check it
first: if engaged, clear `field_active` and STAY in file_browser mode
(matching the other apps' own ESC-exits-INTERACT-only convention);
only exit to `main_menu` on ESC when NOT engaged. This is a real
behavior change, not a one-line fix - do not ship it without a level-2
harness scenario proving both ESC paths (engaged vs not) explicitly,
since this is exactly the kind of interaction-order bug synthetic
PASTE-only testing has already been shown (twice this handoff week) to
miss.

## BUG 3 - no cursor indicator on the FILE/SEARCH field while typing (user: expected `[^] 2. [hi_]`, got `[>] 2. [hi]` with no trailing marker)

`ops/fm_compose_frame.c`, lines 103-110:
```c
fprintf(f, " SEARCH: [>] %d. [%s]\n", idx + 1, search_text);
...
fprintf(f, " SEARCH: [ ] %d. [%s]\n", idx + 1, search_text);
...
fprintf(f, " FILE:   [>] %d. [%s]\n", idx + 1, path_buffer);
...
fprintf(f, " FILE:   [ ] %d. [%s]\n", idx + 1, path_buffer);
```
Only TWO visual states exist here: `[>]` (this row is `cursor_pos`,
i.e. selected) and `[ ]` (not selected) - there is no third `[^]`
state, and `path_buffer`/`search_text` are printed with no trailing
cursor glyph at all. This is a direct, expected CONSEQUENCE of BUG 2 -
there is no "engaged/actively typing" state in `fm_state.txt` for this
rendering code to check in the first place, so it has nothing to
render a distinct indicator FOR. The `[^]` convention the user expects
comes from the OTHER apps (agy-txt/editor's own INTERACT-typing status
line uses exactly `[^]` for "engaged" vs `[>]`/`[ ]` for merely
selected/unselected - see 102.agy-txt's own frame dumps from this same
handoff week for a direct visual reference).

**Fix direction (not yet implemented)**: once BUG 2 introduces a real
`field_active` state, this is a small, mechanical follow-up: render
`[^]` instead of `[>]` when `field_active` is set AND `cursor_pos`
matches this row, and append a trailing `_` to `path_buffer`/
`search_text` in that same case (matching agy-txt's own, separately
cosmetic, `[X]`-suffix attempt at a cursor glyph - see
`102.agy-txt/xyz-agy-handoff-j30.txt` §3 for that one; do NOT copy its
exact hardcoded-`[X]` approach, it doesn't track position and reads
oddly - a plain trailing `_` appended only while actually engaged, as
shown in the user's own example, is the simpler, correct version).
