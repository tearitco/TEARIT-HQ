6. chat-hai text sometimes gets truncated — real starting point
======================================================================

Direct instruction: "chat-hai's text sometimes gets truncated in
window. we will want to investigate a user friendly fix for that."

Real, confirmed starting point: &.hq-apps/chat-hai/ops/chat_hai_hq_
render.c, the real text-wrapping function (search "WRAP_MAX_LINES" in
that file, ~line 1024):

    if (*p && n == WRAP_MAX_LINES) {
        /* still more text left after hitting the cap - mark truncation
         * on the last line rather than silently dropping the tail. */
        size_t l = strlen(lines[n - 1]);
        if (l < WRAP_LINE_BUF - 4) snprintf(lines[n - 1] + l, WRAP_LINE_BUF - l, "…");
    }

This is a REAL, DELIBERATE cap (WRAP_MAX_LINES) on how many wrapped
lines a single message can occupy on screen — when a message's real
wrapped content exceeds that cap, the tail is cut and a "…" is
appended instead of silently vanishing. This is almost certainly what
the user is seeing as "truncation" - it's not a bug in the sense of an
accident, it's a real, intentional limit that may just be too
aggressive/surprising in normal use. Real investigation starting
points for whoever picks this up:
  - Find WRAP_MAX_LINES's own real value (grep `#define WRAP_MAX_LINES`
    in this file) and judge whether it's simply too small for how long
    real persona/chat replies tend to run.
  - Real "user friendly fix" options: raise the cap (simplest, may
    just push the same problem to even-longer messages), add a real
    scroll-within-message affordance (bigger, more correct fix - this
    file's own comment history (search "no more fixed-72-char content
    truncation" ~line 531) shows this house has ALREADY solved a
    similar problem once before by replacing a hard truncation with
    real wrapping - read that surrounding context for the house's own
    established pattern/preference before inventing a new approach),
    or make the cap dynamic based on real available window height
    instead of a fixed constant.
  - Verify live: send/inject a real long message (relay injection, see
    section 7 below) and visually confirm the fix via a real frame

7. Relay injection — how to test any of this for real
======================================================================

This house's entire testing convention for khtpm-family apps (open-hai
included, once renamed) is REAL LIVE TESTING via file-based relay
injection — never trust a "should work" from reading code alone; every
fix in this session's own local-2do-15.txt was verified this way.
Real, concrete recipe, using open-hai/open-hai as the running example
(same shape applies to chat-hai/db-hq/events-hq/entity windows, just
different relay file names/paths):

  RELAY FILE LOCATIONS (real, confirmed this session):
    - open-hai/open-hai's own UI-input relay (simulates keypresses):
        #.desktop/open_hai_agent_relay.txt
      Each line is a DECIMAL ASCII CODE, not a literal character:
        13  = Enter
        27  = Escape
        48-57 = digits '0'-'9' (nav-jump / multi-digit accumulator)
        112 = 'p' (dumps a real PNG frame - see below)
      Multi-digit nav jump: write the digits as SEPARATE lines in
      order, e.g. to jump to real nav index 24: write "2" then "4"
      then "13" (Enter) as three separate lines - the app accumulates
      digits itself, matching the real on-screen "[ ]24. ..." badges.

    - open-hai/open-hai's own REQUEST protocol (bypasses the UI
      entirely, talks straight to the manager - useful for testing
      backend/model logic without simulating keystrokes):
        &.widgits/open-hai/state/request.txt
      Write ONE line, e.g.:
        SEND|your message here
        APPROVE
        DENY
        NEWSESSION
      The manager polls this file, clears it immediately after
      reading (never re-fires), and acts on it within ~1 poll cycle
      (well under 1 second in practice).

  REAL "NEVER REPLAY BACKLOG ON FIRST POLL" GOTCHA (this bit EVERY
  relay test done incorrectly this session at least once - don't skip
  this step):
    Every khtpm app's own relay-polling code treats its FIRST read of
    the relay file after launch as just "establishing a baseline" - it
    does NOT process whatever's already sitting in the file at that
    moment (this is real, deliberate, prevents an app from replaying
    stale commands left over from a previous test run). Real, correct
    sequence:
      1. `echo -n > <relay_file>`     # clear it, empty
      2. sleep ~1 second               # let the app's first poll see
                                        #   the empty file and set its
                                        #   own baseline cursor
      3. write your REAL command(s) to the file (echo/printf > it)
      4. sleep ~1-2 seconds            # let the app actually poll and
                                        #   act on it
      5. check the real result (transcript.txt, a dumped PNG, etc)
    Skipping step 1-2 (writing your real command immediately after
    launch) means it gets silently swallowed as "pre-existing
    backlog" and NOTHING happens - this looks exactly like a bug in
    your fix when it's actually a test-timing mistake.

  REAL FRAME DUMPS (visually verify what the GUI actually shows,
  don't just trust text-file state):
    Write "112" (the digit code for 'p') to the UI relay file (same
    baseline-first rule as above) - every khtpm app this session
    touched has a real dump_frame_png()-style hook that writes a real
    PNG to a predictable path (e.g. open-hai/open-hai's own is
    &.widgits/open-hai/pieces/audit/open-hai-frame.png - check each
    app's own dump_frame_png() function for its exact real path if
    unsure). Read that PNG file directly (the Read tool renders images)
    to SEE the real, current on-screen state - this is how every
    layout/color/text bug in this session was actually confirmed
    fixed, not assumed.

  REAL PROCESS HYGIENE (do this every time, not just when convenient):
    Before launching ANY test instance: `pgrep -af "<app-name>"` first
    to confirm there isn't already a real, possibly-user's-actual-live
    instance running - launching a duplicate causes real confusing
    behavior (two windows, relay commands going to the wrong one,
    etc). After testing: kill ONLY the PID(s) you yourself launched
    (check parent/child PID relationships with `ps -o pid,ppid,cmd` if
    unsure which is which) - never blind-kill by name pattern if a
    real pre-existing user instance might share that pattern. If
    you're not sure whether a running instance is the user's real one
    or a stray from earlier testing, ASK rather than guessing/killing.

9. Taskbar bug: text and sprites stop rendering after running a while
   (bars still render) — investigated, NOT root-caused, real findings
   below for whoever picks this up next
======================================================================

Direct report: "there seems to be a bug that got introduced after
refactor, where tb will stop rendering text and sprites after running
for a while. (but the bars are still there.)"

Real investigation done this session (2026-08-16), real findings, NOT
a fix — could not reproduce live in the time available:

  - Checked *.monads/*.livedesk-taskbar/ops/khtpm_strip_parser.c's real
    text-drawing path (strip_draw_utf8()) — XftColorAllocValue/
    XftColorFree are correctly PAIRED, called and freed every single
    text draw. Not leaking.
  - Checked the 3 real cached Pixmap/GC/XftDraw buffers (g_hq_buf/
    g_popup_buf/g_strip_buf) — all 3 correctly guarded
    (`if (!g_strip_buf) { create }` / free-before-recreate-on-resize
    patterns) — created once, reused, not recreated every frame.
  - Checked the real sprite cache (tab_sprite(), g_sprite_cache[64] —
    KTB_MAX_TABS) — REAL, notable but likely NOT the cause: this cache
    only ever GROWS (new sprite paths get added, nothing ever evicts
    an old entry even after that entity/tab closes). Once all 64 slots
    are used, tab_sprite() returns NULL for any NEW path and that
    tab's sprite silently doesn't draw — but this wouldn't explain TEXT
    disappearing too, and this session alone opened/closed far more
    than 64 distinct entity paths during testing without (as far as
    directly observed) losing sprites - worth a real, harder look if
    revisited, but probably not the whole story.
  - Checked khtpm_taskbar_manager.c's real per-cycle functions (called
    every ~100-200ms via the main loop's ktb_reload() - load_tabs(),
    load_shortcuts(), load_theme(), sync_tab_claims/sync_strip_claims,
    registry_lock_acquire()) for fopen()/fclose() imbalances — all
    correctly balanced on direct inspection. (One early awk-based
    whole-file scan flagged ktb_fopen() as a false positive — that
    function is a Windows-only wrapper, `#define ktb_fopen fopen` on
    Linux, real code never even compiles that branch on this house's
    actual platform - don't waste time re-checking it.)
  - Real LIVE test: relaunched the whole desktop clean via `sh
    $.crypts/button.sh reset`, then monitored BOTH the strip parser
    (khtpm_strip_parser.+x) and the manager (khtpm_taskbar_manager_
    main.+x) real open-file-descriptor counts (`ls /proc/<pid>/fd |
    wc -l`) and real memory (`VmRSS` from /proc/<pid>/status) over a
    real 90-second window on an otherwise-idle desktop. ZERO growth in
    either metric on either process (4 FDs, ~12MB/~2.5MB RSS, both
    exactly flat start to finish).

REAL, HONEST CONCLUSION: no leak or resource-exhaustion pattern was
found in the code paths most likely to run repeatedly, and a 90-second
live idle test showed no measurable drift. This does NOT rule out a
real bug — it likely needs either (a) much longer real uptime than 90s
to manifest, or (b) real user interaction (opening/closing entities,
right-clicking, tab switching) to trigger, which the idle test didn't
exercise. Direct user decision after being offered "reproduce it live
and I'll inspect in the act" vs. "keep auditing blind": *"if u didn't
see anything out of the ordinary in code, i guess we will just have to
document it and move on."*

REAL NEXT STEPS for whoever picks this up:
  1. Best approach: catch it live. When it happens again, DO NOT
     restart/reset the taskbar — leave the broken process running and
     immediately check `ls /proc/<pid>/fd | wc -l` (compare against
     the ~4 baseline confirmed above - any dramatically higher number
     is a real, confirmed FD leak, not a guess), `cat /proc/<pid>/
     status | grep VmRSS` (memory growth), and `ls -la /proc/<pid>/fd`
     (to see WHAT kind of file descriptors are piled up - regular
     files vs sockets vs anonymous inodes point to different real
     causes). This is far more reliable than further blind code
     reading.
  2. If it turns out to be the sprite cache filling up (real,
     mechanically possible, just not confirmed) — real fix is adding
     real cache eviction (e.g., LRU, or evict entries for
     paths/entities no longer present in the current tab list) to
     tab_sprite()'s cache-full branch instead of just refusing new
     entries.
  3. Also worth checking, not yet investigated this pass: whether the
     REAL bug might be specific to db-hq/events-hq/chat-hai's own
     windows (which DID get real code changes this session - the
     white-flash fix, alloc_pixel("#141414") swap) rather than the
     taskbar binary itself (which was only ever rebuilt via the shared
     build_khtpm_strip.sh script, never actually edited this session -
     confirmed via a real byte-identical diff check before this
     session's own Stage 2c taskbar reconnaissance concluded no port
     was needed, see khtpm-merge-how2.md's own "SESSION CLOSE"
     section). If "tb" in the user's report means the taskbar's own
     top strip specifically (not a db-hq/events-hq/chat-hai sub-
     window), the real regression - if there is one - almost
     certainly predates this session's own changes, since the
