J2 Testing Guide (Existing + New Features)
Date: 2026-03-18
Purpose: Standardize how agents test features (especially via key injection + frame review) to prevent regressions.

SCOPE - which family this applies to (added 2026-08-09, real deviation
found live, not hypothetical)
------------------------------------------------------------------------
Everything below (pieces/keyboard/history.txt key injection) is written
for the chtpm_parser_pal/prisc+x family - programs that run their own
file-polling loop reading pieces/keyboard/history.txt for input. It does
NOT apply to raw-Xlib programs that read real X11 events directly via
XNextEvent() (e.g. &.widgits/livedesk-taskbar/ops/tp_taskbar.c,
tp_desktop_window.c) - those have no history.txt to poll at all; writing
KEY_PRESSED lines to a file does nothing for them.

For that second family, the equivalent black-box test interface is a
small, standalone XTest-based injector (XTestFakeKeyEvent/
XTestFakeButtonEvent/XTestFakeMotionEvent) that tails a plain text file
and translates each line into a REAL X11 event targeted at the running
program - genuinely indistinguishable from physical input to the
receiving client, since XTest injects at the X server level. First real
use: diagnosing/fixing a popup-keyboard-focus bug in tp_taskbar.c, see
!.HOUSE_STDS.md §F-19 for the full writeup (root cause: bare
XSetInputFocus on a fresh override-redirect window wasn't reliably
delivering input under this house's Mutter/XWayland environment, despite
XGetInputFocus reporting success - only found by building this injector
and testing empirically, not by reading code harder).

Before choosing an injection method for a NEW testing task: check
whether the target program has a pieces/keyboard/history.txt-reading
main loop (chtpm_parser_pal family - use the file-injection method
below) or is a raw Xlib/other-toolkit program reading real OS-level
events directly (use an XTest-style injector instead, or that toolkit's
own equivalent synthetic-event API). Don't assume file-injection
"should" work everywhere just because it's documented first/most often
in this house - verify which family the target actually is.

UPDATE 2026-08-10 - a real third option now exists for raw-Xlib programs:
give the program its OWN file-relay polling loop, additive alongside its
existing XNextEvent() loop, rather than reaching for an XTest injector.
First real instance: &.widgits/livedesk-taskbar/ops/tp_taskbar.c grew
poll_agent_relay()/agent_relay_dispatch(), polling
#.desktop/livedesk_agent_relay.txt on its normal ~300ms tick (see the
big comment above poll_agent_relay()'s definition in that file for the
exact contract). Direct instruction: built BEFORE any khtpm port of that
program, specifically so a rollback still has working agent access.

WHY THIS IS NOW PREFERRED OVER THE XTEST INJECTOR FOR THIS PROGRAM:
XTest-injected events (XTestFakeKeyEvent/XTestFakeButtonEvent) are
GLOBAL - they go to whichever window currently holds real X input focus,
which taskbar_soft_focus() (XRaiseWindow -> XSetInputFocus -> XFlush,
see !.HOUSE_STDS.md §F-19) has to forcibly steal to make injection land
reliably. That focus-stealing conflicts with a real human using the SAME
display at the same time - their mouse click/window switch mid-sequence
silently redirects the next injected key to the wrong window. A
real, live instance of exactly this cost significant debugging time
before being identified as a test-hygiene/environment issue, not a
tp_taskbar.c bug (see the "cell_for_nav mismatch" investigation,
2026-08-10, provisionally attributed to an index bug before this focus-
contention explanation was found).

The relay sidesteps this entirely: it's a plain file append (`echo "51"
>> #.desktop/livedesk_agent_relay.txt`), consumed by the SAME contextual
dispatch logic a real KeyPress already uses (local popup-row-digit vs
global-nav-digit semantics preserved exactly, see popup_digit()'s own
header comment in tp_taskbar.c). No XTest, no XSendEvent, no window IDs,
no shared input focus - a human can be actively using the browser or any
other window on the SAME display at the same moment an agent is driving
the taskbar via relay, with zero interference either direction. Format:
one bare decimal ASCII code per line (48-57 = digits, 13 = Enter, 27 =
Escape, 8 = Backspace, 32-126 = other printable ASCII for cli-io typed
text) - same bare-decimal convention chtpm_parser.c's own
inject_raw_key() already uses for pieces/apps/player_app/history.txt
(NOT the `[TIMESTAMP] KEY_PRESSED: N` format that's specific to
pieces/keyboard/history.txt/wraith-alpha - don't conflate the two, they
are different target files with different readers and different format
contracts even within the SAME chtpm_parser.c).

The house-standard harness for this program
(#.desktop/harnesses/livedesk-taskbar/) was updated 2026-08-10 to use
this relay by default; its old XTest key_injector.c is kept only as a
documented fallback for testing tp_taskbar.c's OWN real-human-input
handling (the XNextEvent path itself), not as the default agent-testing
method anymore. Any other raw-Xlib program in this house that grows an
equivalent relay should follow the same bare-decimal-per-line contract
for consistency, and should keep it truly additive (a new poll call site
plus new functions, zero changes to the existing XNextEvent KeyPress
handling) so existing real-human-input behavior can never regress from
adding agent support.

Principles
----------
1) Test existing behavior first (regression baseline), then test new behavior.
2) Test at three levels:
   - black-box runtime (key injection + frame review)
   - module/op level (direct state/op assertions)
   - end-to-end user flow (play full project, create/edit/save/load, script, and replay)
3) Record evidence in text (commands + observed output snippets).
4) In no-git mode, create manual backups before risky changes.
5) After each test pass, publish a frame-history report in repo root (`./`) before making code changes.

High-Value Test Interfaces
--------------------------
1) Key injection file:
- `pieces/keyboard/history.txt`
- **EXACT FORMAT REQUIRED:** `[YYYY-MM-DD HH:MM:SS] KEY_PRESSED: <code>`
- Example: `echo "[$(date '+%Y-%m-%d %H:%M:%S')] KEY_PRESSED: 10" >> pieces/keyboard/history.txt`
- *Note:* The parser strictly looks for the `KEY_PRESSED: ` prefix. Raw integers or malformed lines are ignored.
- **Timestamp Issues:** Dynamic generation of timestamps using the `date` command in the shell environment can be problematic due to parsing errors or command availability. If issues arise, using a fixed, valid timestamp (e.g., `[2026-04-21 08:08:15]`) is a reliable workaround.
- **Specific Key Codes:** Common key codes include 'Enter' (decimal code: `13`).
- **Behavioral Note:** Observed behavior indicates that some key presses, such as '1' on the main menu, might not consistently register or may require specific context. Further investigation may be needed for such cases.

2) Routed app input:
- `pieces/apps/player_app/history.txt`

3) Frame artifacts:
- `pieces/display/current_frame.txt`
- `pieces/display/current_layout.txt`
- `pieces/display/frame_changed.txt`
- `pieces/master_ledger/frame_changed.txt`

4) Runtime process checks:
- orchestrator / parser / renderer / clock daemon process presence

5) Project/runtime artifacts:
- `projects/<project>/...` piece/state trees
- project metadata (`project.pdl` and related fields)
- event/script files and bindings

Regression Test Matrix (Existing Features)
-----------------------------------------
R1) Stack launch + process health
- Launch runtime.
- Verify expected core processes are live.
- Verify frame file exists and is rendering.

R2) Key injection ingestion
- Inject key lines to `pieces/keyboard/history.txt` using the `[TIMESTAMP] KEY_PRESSED: <code>` format.
- Confirm new entries append and are consumed over time.
- Confirm frame updates continue after key injections.

R3) Layout/frame validity
- Confirm `current_layout.txt` points to a valid layout path.
- Confirm `current_frame.txt` is non-empty and structurally valid.

R4) Local app state integrity
- Confirm active status line in frame remains coherent (`ACTIVE`, `KEY`, `Z-LEVEL`).
- Confirm no broken placeholders in frame output.

R5) Op-level smoke checks
- Run `render_map.+x` and verify `view.txt` updates.
- For move/state ops, verify expected state deltas (or document if blocked by mode/context).

R6) Compile regression
- Run `./compile_all.sh` for touched areas before merge.

Nuanced Full-Project Test Matrix (Required)
-------------------------------------------
These are required for tester-grade confidence, not optional.

P1) Full project playthrough smoke (existing project)
- Enter project loader.
- Launch at least one target project (e.g., fuzz-op/op-ed-related flow).
- Perform nuanced interactions (nav, mode switches, map control, action menu paths).
- Verify frame + state coherence after each interaction cluster.

P2) Editor-driven project creation
- Enter editor flow.
- Create a new project or project-like playable state.
- Add pieces/entities and map content.
- Verify piece placement appears in rendered frame and corresponding state files.

P3) Save / load roundtrip (editor-created content)
- Save created project.
- Exit/re-enter flow.
- Load same project.
- Verify parity:
  - piece positions/states
  - map association
  - active layout/metadata sanity

P4) Script/event authoring and execution
- Create script/event definitions for the created project.
- Bind scripts/events to target pieces/actions.
- Trigger in runtime play.
- Verify expected state/result changes and response text.

P5) Local play from created/saved project
- Launch local play using saved project artifacts.
- Confirm no manual file edits required.
- Confirm project boots into expected layout/context.

P6) Metadata correctness checks
- Validate `entry_layout`, `player_piece`, and related metadata are resolved correctly.
- Ensure values are scan/registry-derived where appropriate (no stale hardcoded defaults).

P7) Cross-project sanity
- Ensure testing one project does not corrupt another project's states/layout pointers.
- Check at least one untouched project still launches normally.

New Feature Test Plan (Template)
--------------------------------
For each new feature F:
1) Define expected behavior in one sentence.
2) Add deterministic setup steps (files/paths/state).
3) Add key-injection path (if UI/input relevant).
4) Add frame assertions (what text/layout must change).
5) Add state-file assertions (which keys/values must change).
6) Add project artifact assertions (save/load/script binding persistence).
7) Add rollback/cleanup steps.
8) Add failure signatures (what indicates miswire/hardcode regression).

Recommended command skeleton:
- Baseline capture:
  - copy `current_frame.txt` and key state files to `/tmp/*before*`
- Inject/trigger:
  - append key/event inputs
- Post capture:
  - copy `current_frame.txt` and state files to `/tmp/*after*`
- Diff:
  - `diff -u before after`
- Log:
  - save key evidence lines in test report text file

Mandatory Post-Test Report Gate (Root `./`)
-------------------------------------------
This is required so review does not depend on hunting under nested folders.

Rule:
1) After every test cycle, create a root report file in `./` with:
- test scope
- key injections/actions performed
- frame evidence lines (timestamps + relevant frame snippets)
- PASS/FAIL/INCONCLUSIVE verdicts
- explicit "safe to proceed with code changes" line

2) Source evidence from:
- `pieces/debug/frames/session_frame_history.txt`

3) Report filename convention (root dir):
- `FRAME_REPORT_<YYYYMMDD-HHMM>_<topic>.txt`
- Example: `FRAME_REPORT_20260318-0950_scroller.txt`

4) Review gate:
- Do not begin implementation edits until this root report is written and reviewed.

**System Startup and Frame Viewing:**
- **System Startup:** The CHTPM orchestrator is launched using the `./button.sh run` command. This initializes the system and presents a text-based main menu.
- **Frame Viewing:** Frame updates are logged chronologically in `pieces/debug/frames/session_frame_history.txt`. This file is crucial for evidence gathering and post-test review.

Suggested command pattern:
- `cp pieces/debug/frames/session_frame_history.txt ./FRAME_HISTORY_RAW_<YYYYMMDD-HHMM>.txt`
- Create concise reviewed summary in:
  - `./FRAME_REPORT_<YYYYMMDD-HHMM>_<topic>.txt`
- Keep both raw copy and concise summary for traceability.

Known Testing Pitfalls
----------------------
1) Mode/context sensitivity:
- Same key can do nothing if active mode/context is not correct. Check the current layout and focused element.

2) Metadata/default traps:
- Missing `entry_layout` / `player_piece` guessed defaults can misroute tests.

3) Hardcoded-path drift:
- Tests may pass in one layout/project but fail in another if pathing is not canonical/world-map-first.

4) Cancellation sequence confusion:
- Multi-key injections can net-zero movement and hide real behavior.

5) False confidence from op-only tests:
- Direct op passes do not prove end-to-end editor/save/load/script/play behavior.

6) **INJECTION FORMAT ERROR & UNRELIABLE INPUT:**
- Key injection MUST strictly follow the `[TIMESTAMP] KEY_PRESSED: <code>` format. Raw integers, malformed lines, incorrect timestamps, or missing prefixes will be ignored by the parser. Issues with the shell's `date` command may necessitate using fixed timestamps.
- **Specific Key Codes:** Common key codes include 'Enter' (decimal code: `13`).
- **Behavioral Note:** Observed behavior indicates that some key presses, such as '1' on the main menu, might not consistently register or may require specific context. Further investigation may be needed for such cases.

7) **GHOST BUG HUNTING**: 
- If key injection is visible in the frame (e.g., in the `[KEY]:` status line), the input pipeline is functional. **Do not investigate "broken input" if the frame reflects the key.** If the application doesn't respond, check the application module's logic, active layout mode (Nav vs Active), or focus state.

8) **RACE CONDITION FALSE POSITIVES**:
- Sometimes a frame update happens just before an injection is processed. Always allow 1-2 seconds for the parser/module cycle to complete before capturing evidence.

9) **MENU NAVIGATION INCONSISTENCIES:**
- On certain menus, specific key presses (e.g., '1' on the main menu) may not appear to register or navigate as expected. This could be due to context sensitivity, an incorrect key code being used, or the need for a different action (like 'Enter'). Always verify frame updates and system state after injection.

10) **LINUX VS WINDOWS .+x BINARY DRIFT:**
- If `./button.sh run` fails with `cannot execute binary file: Exec format error`, inspect the target with `file`.
- A common cause is that `pieces/chtpm/plugins/+x/orchestrator.+x` or other `.+x` files are Windows PE binaries while the current agent/session is on Linux.
- Approved Linux recovery path:
  1. `sh #.dev-storage/#.tools/remove_binaries.sh`
  2. `./button.sh compile`
  3. Verify compile summary reports zero failed binaries and required binary check passes.
- This removes generated `*.+x` binaries and rebuilds Linux versions. It should not be treated as source-code deletion.

11) **API SANDBOX / NO `/dev/tty` HEADLESS TESTING:**
- Some agent/API shells do not expose `/dev/tty`. In that environment, normal `./button.sh run` may get past compilation but exit when `keyboard_input_linux.c` reports `open /dev/tty: No such device or address`.
- This does not prove TPMOS is broken on a real terminal; it means the API shell cannot run the terminal keyboard muscle.
- For frame-driven agent testing in this environment, use a headless subset:
  - Start parser: `./pieces/chtpm/plugins/+x/chtpm_parser.+x pieces/chtpm/layouts/os.chtpm`
  - Start renderer: `./pieces/display/plugins/+x/renderer.+x`
  - Inject keys by appending valid `KEY_PRESSED` lines to `pieces/keyboard/history.txt`.
  - If needed, append a marker such as `M\n` to `pieces/display/frame_changed.txt`.
  - Inspect `pieces/display/current_frame.txt` and `pieces/debug/frames/session_frame_history.txt`.
- Stop any manually launched parser/renderer processes after the test cycle and verify no `chtpm_parser`, `renderer`, `orchestrator`, `keyboard_input`, or `joystick_input` process remains.

12) **HEADLESS TEST CAN STILL PROVE KEY INGESTION:**
- In the API headless smoke test, starting only `chtpm_parser.+x` and `renderer.+x`, then injecting:
  `[2026-06-02 22:33:15] KEY_PRESSED: 13`
  moved the frame from the CHTPM main menu to `PIECEMARK LOADER` / `playrm/loader.chtpm`.
- This proves the file-based input parser and frame renderer can be tested without live keyboard capture.
- Use this pattern for Codex/agent validation when a real terminal is unavailable.

Best-Practice Additions for Future
----------------------------------
1) Build deterministic end-to-end harness scripts for P1-P7.
2) Add per-feature test fixtures under `#.tools/`:
- setup fixture
- run test
- verify expectations
- cleanup fixture

3) Keep an append-only session test report per day.
4) Require at least one full create->save->load->script->play cycle before accepting major feature work.

Minimal Daily Regression Checklist
----------------------------------
1) Runtime launches (processes alive)
2) Frame renders (non-empty current_frame)
3) Key injection path alive (history updates)

5) Compile check for touched code

7) At least one end-to-end project flow is validated (create/play or load/play)
8) Root frame report created in `./` and reviewed before edits

SCOPE ADDENDUM 2026-08-12 - external screen capture (xwd/PIL) is NOT
reliable once a real human may be USING the desktop concurrently
------------------------------------------------------------------------
Real bug hit live testing ai-cell (&.widgits/ai-cell/): an xwd capture
of a specific window ID returned ANOTHER real window's content
entirely (bleed-through), because the target window had been dragged
by the real user and was partially occluded at the exact moment of
capture. xwd captures what's window-stacking-composited at that
instant, not a guaranteed snapshot of one window's own content -
this is fine for solo agent-only testing (the pattern used all session
for db-hq/events-hq/taskbar/entities, no problems there) but breaks
the moment a real human is ALSO actively using the same display.

REAL FIX (direct instruction: "u should use png dump not pil capture.
from now on (or receipt) learn 2 rely on receipts"): any khtpm/-hq
window app should dump ITS OWN compose buffer directly (same
`dump_frame_png()` pattern db-hq/ai-cell both use - `XGetImage` on the
app's own offscreen Pixmap, standard 0xRRGGBB byte layout, not the
zeroed mask fields a bare Pixmap returns) instead of relying on an
external xwd/PIL capture of the mapped window. This can never race
with window stacking/occlusion because it reads what the process
itself drew, not what's visually on screen at capture time.

Write a RECEIPT file alongside the PNG (`<name>.png.receipt.txt`,
plain key=value line: ok/w/h/timestamp + whatever app-state fields are
useful to confirm, e.g. ai-cell's own `nav=... n_sessions=... n_msgs=...`)
- poll/trust the RECEIPT, not just the PNG's existence, since a
partially-written PNG file existing doesn't prove the write finished.
See `&.widgits/ai-cell/ops/khtpm_ai_cell_render.c`'s own
`dump_frame_png()` for a complete real example (bound to 'p' when not
in a text-entry context, plus a `--dump-and-exit` headless mode).

Any NEW khtpm/-hq window built after this point should get this from
day one, not bolted on after hitting the same bug live again.

SCOPE ADDENDUM 2026-08-13 — three real bugs found testing h-ai's model
selector, ALL caused by broken TEST METHODOLOGY, not (mostly) the app
------------------------------------------------------------------------
Real session, live: implemented a model-selector nav item for h-ai
(&.widgits/ai-cell/), code compiled clean, but ~2 hours of relay
testing produced totally inconsistent, unreproducible results ("works
sometimes, model.txt sometimes appears, sometimes doesn't"). Root
cause was NOT the feature code — it was three stacked testing mistakes
that any future agent WILL make again if this isn't read first.

MISTAKE #1 — `--dump-and-exit` is a SEPARATE PROCESS, not a peek into
the live one you're relay-testing.
  `khtpm_ai_cell_render.+x <house_root> --dump-and-exit` spawns a
  brand-new, disposable process: fresh X window, fresh
  `load_model_choice()`, `g_focus_nav` reset to 1, zero knowledge of
  anything you've relay-injected into a DIFFERENT already-running
  instance. Using it to "verify" whether relay codes landed on the
  live process proves NOTHING about that live process — you're just
  reading a brand-new process's default startup state every time,
  which is why the receipt kept showing `nav=1`/`nav=3` no matter what
  you'd actually injected.
  REAL FIX: to inspect a LIVE process's actual current state without
  killing/replacing it, send the `'p'` key THROUGH THE RELAY FILE
  (ASCII 112, one line, same file as everything else) — this calls
  `dump_frame_png()` from inside the SAME process you've been
  injecting into, so the receipt actually reflects your prior codes.
  `--dump-and-exit` is only useful for confirming "does this binary
  render without crashing," never for checking live relay-driven state.

MISTAKE #2 — nav item indices are NOT stable, and a test loop that
presses "New Chat" (usually nav item 1) will keep moving its own
target out from under itself.
  This is directly documented in README.md ("Nav numbers are NOT
  fixed... no static map you can hardcode into a test script") and was
  read and even quoted back to the user earlier THIS SAME SESSION —
  and still got violated by a brute-force "try digits 1 through 15"
  test loop. Every pass through that loop hit digit '1' first
  (New Chat), which calls `start_new_session()` and grows
  `g_n_sessions` immediately, permanently shifting every nav index
  after it on every single iteration. The loop could never land on a
  fixed target because the target kept moving. 26 stray empty session
  dirs were created this way before the mistake was caught.
  REAL FIX: before injecting ANY digit-jump, first send `'p'` via
  relay and READ THE RECEIPT'S `n_sessions`/`n_nav` fields to compute
  the CURRENT correct index right before every navigation attempt —
  never assume a fixed index across more than one action, and never
  run a test loop that itself performs an action (like New Chat) which
  changes the nav layout it's trying to test against.

MISTAKE #3 — repeated `sh button.sh` calls without confirming the
prior instance actually died first launches MULTIPLE CONCURRENT
PROCESSES, all racing on the same relay file and session directory.
  `pkill -9 khtpm_ai_cell_render` does not reliably match this
  binary's process (the emoji-laden house-root path passed as argv[1]
  appears to interfere with simple name-based pkill matching in some
  shells/environments — not fully root-caused, but consistently
  observed). Calling `button.sh` again without verifying zero prior
  processes launches a NEW instance on top of still-living ones.
  `ps aux | grep khtpm_ai_cell` during this session found FIVE
  simultaneously-alive processes, all independently polling the exact
  same `#.desktop/ai_cell_agent_relay.txt`, each with its own
  independent `g_relay_cursor`/`g_focus_nav`/session state, all racing
  each other to consume relay codes and all writing to the same
  `sessions/` dir and PNG receipt path. This alone explains most of
  the "flaky, unreproducible" behavior — there was never ONE
  ground truth to check against.
  REAL FIX: before starting a fresh instance for testing, always run
  `ps aux | grep khtpm_ai_cell_render | grep -v grep` and confirm ZERO
  results (kill any remaining PIDs individually by number, don't trust
  a single `pkill` call to have worked) — THEN launch — THEN
  re-confirm exactly ONE process exists — before injecting anything.
  `button.sh` itself has no built-in single-instance guard; don't add
  one to production code for this (multiple real windows may be a
  legitimate future use case), but ALWAYS enforce it manually in test
  procedure.

A REAL APP BUG found (not a testing mistake) once the above three were
controlled for: multi-digit nav-index accumulation is DEAD CODE once
`n_nav >= 9` (true almost immediately in normal use — a handful of
saved chats is enough). `handle_key()`'s digit branch checks
`if (d >= 1 && d <= g_n_nav) g_focus_nav = d;` BEFORE the multi-digit
accumulation branch, and since single digits 1-9 are almost always
`<= g_n_nav`, that branch always wins first — pressing '2' then '6'
sequentially jumps focus to item 2, then item 6, NEVER item 26. This
was confirmed live: with `n_nav=30`, sending '2' then '6' via relay
left `g_focus_nav=6`, not 26. Combined with relay's own ASCII-only
protocol (digits/Enter/Escape/Backspace/printable — no arrow-key
codes), this means **any h-ai nav item beyond index 9 is currently
UNREACHABLE via relay once several sessions exist** — real keyboard
arrow-key stepping still works (untested via relay, since relay can't
send arrow keysyms at all), but a pure-relay agent session cannot
reach deep sidebar items once session count grows. Flagged in
`&.widgits/ai-cell/ops/khtpm_ai_cell_render.c`'s own
`handle_key()` (~line 1717) for a future fix (needs a real digit
accumulator with an explicit "commit" trigger — e.g. only jump on
Enter, or use a short input-timeout window — not a same-session
priority fix, but real and worth tracking, NOT re-discovering from
scratch next time this area is touched).

PROCEDURE — going forward, testing ANY nav-indexed khtpm/-hq window
via relay should follow this order every time, not ad hoc:
  1. Confirm zero stray processes (`ps aux | grep <binary> | grep -v grep`).
  2. Launch exactly one instance, confirm exactly one PID exists.
  3. Send `'p'` (or the app's own live-dump key) via relay BEFORE every
     navigation attempt — read the receipt's live nav/session/focus
     fields, don't assume from a prior state or a spawned dump-and-exit
     process.
  4. Compute the CURRENT correct nav index from the receipt you just
     read, not from a hardcoded number or an earlier session's count.
  5. If `n_nav >= 9` and the target index is >9, single-digit relay
     jump CANNOT reach it (see the accumulator bug above) — don't loop
     digits hoping it'll work; this is a known, real, confirmed dead
     end until the accumulator itself is fixed.
  6. Clean up any test-created state (stray sessions, temp files)
     afterward so the next test starts from a small, predictable
     `n_nav` — don't leave debris that makes the NEXT session's nav
     math harder.

SCOPE ADDENDUM 2026-08-13 (later) — the digit-accumulator bug above
IS FIXED (ported the real `chtpm_parser.c` `digit_accum` standard into
`khtpm_ai_cell_render.c`'s `handle_key()`), relay-verified live: grew
a real instance to `n_nav=12`, confirmed `'1'` then `'2'` reaches item
12 (not item 2), confirmed overflow fallback (`'9'` then `'9'` → falls
back to item 9). Rule 5 above is now historical for ai-cell
specifically — multi-digit jump past index 9 works there. Still a
valid general caution for any OTHER khtpm/-hq window that hasn't had
this same fix ported yet — check whether the target window's own
`handle_key()` uses a real accumulator before assuming multi-digit
jump works.

A NEW real gotcha found while verifying the fix, worth its own rule:
**nav index order follows the CALL order of a window's `draw_*()`
functions inside its `redraw()` (or equivalent), NOT the textual/line
order those functions appear in the source file.** Concretely in
ai-cell: `draw_close_button()` is defined early in the file (so its
`nav_add(NAV_CLOSE, ...)` call is one of the textually-first nav_add
sites you'll grep to), but `redraw()` invokes it LAST — so Close
actually gets the highest nav index at runtime, and whatever nav item
is added by the SECOND-called `draw_*()` function gets index 1, not
whatever textually appears second in the file. Assuming file order equals
nav order sent a test digit at the wrong nav item (no crash — it just
silently activated a different, valid nav item than intended, which
is a worse failure mode than an error because it looks like it
"worked"). **Rule 7, added to the procedure above**: before computing
target nav indices for ANY khtpm/-hq window, grep that window's own
`redraw()` (or equivalent per-frame draw dispatcher) for the ACTUAL
call order of its `draw_*()` functions, and read each one's `nav_add()`
calls in that call order — never infer nav index from where `nav_add()`
happens to appear textually in the file.

**Rule 8, added to the procedure above (2026-08-13)**: "confirm zero
stray processes before launching" (Rule 3) applies to a window you are
ACTIVELY BUILDING and smoke-testing in the same session just as much
as to an existing one you're re-testing — no "just this once, quick
check" exception. If launching a binary a second time for any reason
without explicitly killing the prior instance first, check `pgrep -f`
before sending anything. Doubly true for any window whose actions
write to SHARED, non-disposable state (a real config another live
process reads) rather than its own private session dir. Real incident
+ full narrative: see PITFALL 71-adjacent entry in
`#.haiku+/!.xyzos-pitfalls+1.txt` (app-bug/incident writeups belong
there, not in this file — this file stays scoped to injection/nav
testing procedure only, per direct correction 2026-08-13).

SCOPE ADDENDUM 2026-08-20 — testing "interact mode"-gated 2D/3D map
systems (mutaclysm-family: real camera state updates correctly in a
state file but the render never visibly follows). Full incident +
root-cause writeup lives in `101.mutaclsym🧟‍♂️️19.00/SIMLINK_PITFALL.md`;
this entry is the PROCEDURE distilled from it, for any future
interact-mode/camera testing on this or a sibling project.

**Rule 9 — a state-file diff is NOT proof a render pipeline picked
something up.** `grep`-confirming `camera_mode=3` changed in a hero
state file only proves the INPUT side worked. Multiple independent
processes (a dispatcher, a 3D renderer, an RGB compositor, a window
mirror) can each read/write "the same" relative filename while
actually resolving to DIFFERENT real files if their working
directories or root-env vars diverge even slightly — this produces
a confirmed-changing state file next to a genuinely-frozen visible
window, with zero errors anywhere. Always finish a camera/render test
with a REAL pixel-level proof (`dump_rgb_png.+x`, which reads the raw
frame buffer file directly — no window-capture race, no reliance on
the GUI actually being visible on a shared desktop) and compare it
against the PRIOR dump, not just against a text description of what
"should" have changed.

**Rule 10 — "interact mode" is usually a real, separate engagement
gate, not just a label.** In this family, pressing a menu item's Enter
(e.g. "Control Hero") sets a real `interact_mode=1`/`active_index`
state that subsequent keys are checked against — some input ops (e.g.
`camera_control.c`'s pan/look) hard-return no-op if that gate isn't
genuinely on, while OTHER ops for the same game (e.g. plain movement)
may respond regardless of the gate's state, which LOOKS like "input is
working fine" even when the specific feature under test (camera) is
silently blocked. Before concluding a specific control doesn't work,
confirm via a fresh read of the actual gate field (`interact_mode`,
`active_index`, whatever the project calls it) at the moment you send
the test key — don't infer the gate state from whether an unrelated
control (movement) responded.

**Rule 11 — verify with the REAL capture path, not just a raw file
write, when input capture itself is in question.** A bare file-append
test (writing directly into a relay/history file) can produce a false
PASS if it bypasses a real, separate bug in the actual X11-capture →
relay-write chain (wrong keycode mapping, wrong window focus, a
WM/global-hotkey interception). When the capture path itself is
uncertain, prefer a REAL synthetic X11 keypress via an XTest injector
(`&.widgits/tile-picker/ops/+x/tp_test_send_key.+x <window-name-
substring> <keysym>` — confirmed working here against a live
`x11_mirror`-family window by exact title-substring match) over a raw
file write, so the test exercises the same code path a real human
keypress would.

**Rule 12 — a persistent (project-root) vs. session-local (CWD) file
split, once introduced (e.g. by a symlink-elimination pass), silently
breaks any writer/reader PAIR that doesn't agree on the same base.**
Before trusting that a fix for one half of a pipeline (e.g. the
dispatcher) is sufficient, explicitly check `/proc/<pid>/cwd` for
EVERY long-lived process in the chain (dispatcher, renderer,
compositor, mirror) — a library-level `chdir()` call you don't control
(e.g. inside a shared parser before launching a persistent module) can
silently move one process's own "relative path" resolution out from
under an otherwise-correct fix, and this never produces an error, only
a stale/frozen visible output next to correctly-updating state files.

End of testing guide.

UPDATE 2026-08-24 - PER-ENTITY RELAYS (tp_desktop_window_rgb.+x entity windows)
-------------------------------------------------------------------------------
The taskbar relay above is not the only agent surface anymore. Every entity
window spawned by the taskbar (ops/+x/tp_desktop_window_rgb.+x, one process
per <pal>) polls its OWN relay file on its main tick:

    <package_dir>/interact_relay.txt        (i.e. <pal>/interact_relay.txt)

Same write-once/consumed-and-truncated contract as every other house relay
(one command per line; first line wins per poll; file truncated after read;
every consumption logs "INJECTED: <cmd>" to that pal's own history.txt).
Find a live entity's package_dir via #.desktop/livedesk_open.txt
(PID=..|INDEX=..|ENTITY=..|PATH=..).

Command vocabulary is WIDER than the taskbar's bare-decimal codes - these are
string commands (case-sensitive):
    OPEN_CONTEXT          open the entity's right-click METHOD menu
    RUN_METHOD:<label>    dispatch meta.pdl row by LABEL directly (no menu
                          needed; e.g. RUN_METHOD:Dir, RUN_METHOD:Chat)
    CLOSE                 clean window close (removes DESK row + registry entry)
    RAISE                 XRaiseWindow only - raise-to-top IS the whole
                          observable focus model for these override_redirect
                          windows (see big comment at the RAISE branch)
    FOCUS_NAV:<n>         move [>] highlight inside an OPEN menu, no activate
    ACTIVATE_NAV:<n>      activate row claimed as nav number n in the OPEN menu
    (bare decimal codes also work where the entity reads keys itself)

HANDS-FREE MENU WORKFLOW (proved live 2026-08-24 driving cursword's Dir row
end-to-end without any mouse/XTest):
    1. echo "OPEN_CONTEXT" > <pal>/interact_relay.txt ; sleep ~1s
    2. read #.desktop/livedesk-nav-claims/livedesk_nav_claims.txt - each open
       menu claims a contiguous NAV range: KIND=row|PID=<pid>|NAV=<n>|ROW=<i>|
       LABEL=<label>|PATH=<pal>. Base = min NAV for that PID.
    3. echo "ACTIVATE_NAV:<base+row>" > <pal>/interact_relay.txt
    Prefer RUN_METHOD:<label> when you just want an action without caring
    about menu visuals - no claims-file step needed.

FAMILY MAP (all three coexist; they do NOT substitute for each other):
    - pieces/keyboard/history.txt   chtpm_parser_pal family ONLY, and ONLY in
      the [TIMESTAMP] KEY_PRESSED: N format (wraith-alpha flavor)
    - player_app-style history.txt  bare-decimal inject_raw_key() convention
    - interact_relay.txt / livedesk_agent_relay.txt   raw-Xlib programs grown
      their own polling loop (taskbar + all entity windows); strings or
      decimals per that program's dispatcher
Rule unchanged: before picking an injection method for a NEW target, verify
which family the target actually belongs to - don't assume.
