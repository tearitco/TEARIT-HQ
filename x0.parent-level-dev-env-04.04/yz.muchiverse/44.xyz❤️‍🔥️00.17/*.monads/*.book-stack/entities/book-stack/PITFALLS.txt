================================================================================
BOOK-STACK — LOCAL PITFALLS (this entity's own action= / METHOD strings)
================================================================================
Read before editing meta.pdl, menu.chtpm, or any downstream dispatch.sh/run.sh
in this entity. Real, confirmed bugs found+fixed 2026-08-18 — see
bookstack-path-bug.txt (house root, 44.xyz❤️‍🔥️00.17/) for the original
investigation report this superseded.

--------------------------------------------------------------------------------
PITFALL 1 — khtpm_entity_menu_render.c's decode_entities() does NOT handle
&gt;/&lt;, only &quot;/&amp;. FIXED 2026-08-18, but any FUTURE action= string
in menu.chtpm (or any other entity's menu.chtpm) that embeds a shell redirect
(`>`, `<`) inside its HTML-attribute-encoded value will hit this same bug again
if decode_entities() is ever reverted or copied to a project WITHOUT this fix.
--------------------------------------------------------------------------------
Real root cause: menu.chtpm's own "Read" action= string embeds real shell
redirects (`2>/dev/null`, from nested `$(find ... 2>/dev/null)` command
substitutions) INSIDE an XML/HTML attribute value, so they get entity-encoded
as `2&gt;/dev/null` in the source .chtpm file (correct, required XML encoding
for a literal `>` inside an attribute). The RENDERER's own decode_entities()
(&.widgits/*.livedesk-taskbar/ops/khtpm_entity_menu_render.c) only decoded
`&quot;` and `&amp;` — `&gt;` fell through UNCHANGED, so the REAL command
dispatch() ran contained the literal 4-character text `&gt;` where a real `>`
was needed. `/bin/sh` parses `find ... -type d 2&gt;/dev/null` as: `find`
with an extra bogus literal arg `2`, backgrounded (`&`), followed by a
nonexistent command `gt` given `/dev/null` as its own argument — a genuinely
broken pipeline. Both `$(find "$H" ...)` substitutions in the Read action came
back empty, so `MUTA_ROOT`/`READER_PATH` were both empty strings, and the
final `exec ""` (or `exec "/system/prisc+x"` with a blank prefix) failed
completely silently — dispatch()'s own wrapper backgrounds the command AND
redirects stdout/stderr to /dev/null (`%s '%s' '%s' >/dev/null 2>&1 &`), so
there was never any visible error, matching the exact reported symptom
("nothing happens, no error message visible").

Confirmed via direct reproduction: manually building the EXACT command
dispatch() constructs (correctly-typed, not entity-encoded) worked and showed
a real menu; only the REAL entity-decoded version (going through the actual
broken decode_entities()) failed. This is why a prior investigation's own
manual path-verification (bookstack-path-bug.txt) found every individual path
"correct" — it was testing hand-typed strings, never the real, entity-decoded
runtime string the live UI actually produces.

Fix applied: decode_entities() (khtpm_entity_menu_render.c, ~line 141) now
also handles &gt; -> '>' and &lt; -> '<', in addition to the original
&quot;/&amp;. Rebuilt via ops/build_entity_menu.sh. This is a SHARED, HOUSE-WIDE
fix (that file is not book-stack-specific) — any OTHER entity's menu.chtpm
using a shell redirect inside action= now benefits too, not just book-stack.

LESSON for whoever edits action= strings in ANY entity's menu.chtpm: if your
embedded shell command needs `>`, `<`, `2>&1`, etc., remember these get
XML-entity-encoded in the .chtpm source (`&gt;`/`&lt;`) — confirm the CURRENT
decode_entities() in khtpm_entity_menu_render.c actually decodes whatever
entities your command needs before assuming a "correct-looking" encoded string
will work at runtime. Test via the REAL UI trigger (actual menu click), not
just by manually re-typing the decoded command by hand — a hand-typed test
only proves the LOGIC is right, not that the REAL encode/decode round-trip
preserves it.

--------------------------------------------------------------------------------
PITFALL 2 — prisc+x needs default_op.txt relative to its OWN cwd at exec time,
not relative to the caller's cwd or the binary's own directory.
--------------------------------------------------------------------------------
prisc+x's own real path resolution (system/prisc+x.c, shared across all
chtpm/PAL-VM projects) tries `fopen("default_op.txt", "r")` relative to
whatever process cwd it inherits, and if that fails, falls back to resolving
relative to ITS OWN BINARY location via /proc/self/exe (i.e. looks for
`system/default_op.txt`, since prisc+x itself lives at `<project>/system/
prisc+x`). But the REAL default_op.txt for mutaclysm (and every other real
chtpm project checked this session) lives at the PROJECT ROOT
(`<project>/default_op.txt`), ONE LEVEL ABOVE `system/` — NOT inside
`system/` itself. So the binary-relative fallback path is ALWAYS wrong.

Every OTHER real invocation of prisc+x in this house goes through that
project's own button.sh, which ALWAYS `cd`s to the project root FIRST (see
button.sh's own `SCRIPT_DIR="$(cd "$(dirname "$0")/.." && pwd)"; cd
"$SCRIPT_DIR"` pattern) — so the "local cwd" check always succeeds for real
button.sh-launched sessions, and the broken binary-relative fallback never
actually gets exercised in practice. book-stack's own meta.pdl Read action was
the ONLY place found this session invoking prisc+x directly, without first
cd'ing into its own project root - so it was the one real place this
otherwise-dormant fallback bug actually got hit.

Fix applied (meta.pdl's Read METHOD, and its menu.chtpm HTML-encoded twin):
compute MUTA_ROOT once via the existing find command, `cd "$MUTA_ROOT"` BEFORE
the final `exec "$MUTA_ROOT/system/prisc+x" ...` call, matching button.sh's
own real, working convention exactly. Do NOT invoke ANY project's own prisc+x
binary directly from an action= string (or any other context) without first
cd'ing into that project's own real root — this is a real, general rule for
this house's own prisc+x/chtpm-family binaries, not a book-stack-specific
quirk.

--------------------------------------------------------------------------------
KEEP meta.pdl AND menu.chtpm IN SYNC
--------------------------------------------------------------------------------
menu.chtpm's own action= values are meant to be a 1:1 mechanical, HTML-entity-
encoded copy of meta.pdl's own METHOD values (per menu.chtpm's own header
comment, "same action strings verbatim... via the same real mechanical
conversion rule"). Both files were updated together for both pitfalls above -
if you fix one, fix the other the same way, or they'll silently drift and only
ONE of the two real trigger paths (depending on which UI surface is used) will
actually work.
