## 1. What this project actually is

A voxel-based 3D dungeon-crawler using board-viewer's real per-pixel DDA raymarcher for rendering
(stolen wholesale from `&.widgits/board-viewer/`), with mutaclysm's own classic interact-mode
input system (`+18.0G`'s `game_dispatch.c`/`move_player.c`/`choice.c`/`camera_control.c`) layered
on top — because board-viewer itself has NO interact mode, it's a passive map viewer.

The map is a real voxel chunk (`pieces/system/chunks/chunk_0_0/chunk_0_0_z*.txt`, one 16x16 glyph
grid per Z-level, 32 levels), auto-generated on first-ever launch (no manual "Confirm & Start"
step). Multiple Z-levels of terrain/walls are visible in ONE screen (the real point of using
board-viewer's renderer over mutaclysm's own old flat rasterizer) — this is different from the old
teleport-between-maps system, which is KEPT, unmodified, for map-to-map transitions.

## 2. The real render pipeline (read this before touching ANY rendering code)

```
interact_relay.txt (keys, decimal, one per line)
        ↓
game_dispatch.+x (per-tick, invoked by pal/game_module.pal's own `exec` loop)
        ↓
  move_player.+x / choice.+x / camera_control.+x   (classic +18.0G ops, write hero_01/state.txt)
        ↓
  compose_frame.+x   (writes current_frame.txt, INCLUDING the MAP3D_MARKER 0x01 byte
                       when render_mode==1 — this is compose_frame.c's OWN NATIVE
                       feature, board-viewer's own composer PORTED this FROM
                       mutaclysm, not the other way around)
        ↓
  sync_camera_to_bv_state()   (game_dispatch.c's own helper — mirrors cam_yaw/cam_pitch/
                                cam_pan_*/camera_mode/render_mode from hero_01/state.txt
                                into pieces/system/bv_state.txt, because muta_render_3d.c
                                — verbatim board-viewer code — reads camera state from
                                THAT file, a completely separate convention from hero_01/
                                state.txt. Without this sync, camera state changes are
                                invisible to the renderer no matter how correct
                                camera_control.c's own math is.)
        ↓
  muta_render_3d.+x   (board-viewer's real raymarcher — reads board_manifest.txt +
                        chunks/, writes pieces/display/rgb_frame_3d_overlay.raw)
        ↓
  system/chtpm_rgb_render   (PERSISTENT DAEMON, launched once by button.sh — watches
                              current_frame.txt for the MAP3D_MARKER byte, composites
                              the overlay into pieces/display/rgb_frame.raw itself.
                              classic compose_rgb_frame.c is NOT part of this path —
                              it's an old, separate, direct-RGB mechanism with zero
                              knowledge of the marker/overlay convention, and must
                              NEVER be called in the same dispatch chain as
                              muta_render_3d — it would silently clobber the real
                              output.)
```

**Critical: every single binary invocation in this chain (`run_op()` in `game_dispatch.c`, `exec`
in `.pal` scripts) needs the LITERAL `.+x` suffix.** `execl()`/PAL's `OP_EXEC` use the path exactly
as given — no suffix is ever appended automatically. This exact bug (missing `.+x`) was found in
THREE separate places this session (`game_dispatch.c`'s own `run_op()` calls, `pal/game_module.pal`'s
own `exec` line) and is present VERBATIM in `+18.0G`'s own original source — it was simply never
live-tested there. **If you add a new op call anywhere in this chain, include `.+x` or it will fail
completely silently** (stderr is redirected to `/dev/null` in `run_op()`).

### Two persistent state files, two different owners — do not conflate them

| File | Owner | Contains |
|---|---|---|
| `pieces/hero_01/state.txt` | mutaclysm's own classic ops (`move_player.c`/`choice.c`/`camera_control.c`) | Real game state: hp, pos_x/y/z, render_mode, camera_mode, cam_*, interact_mode, last_key |
| `pieces/system/bv_state.txt` | board-viewer's own renderer (`muta_render_3d.c`) | ONLY what `sync_camera_to_bv_state()` mirrors in each frame, plus `focused_project_root` (board-viewer's own multi-host widget pointer, set once at session start to point at itself) |
| `pieces/world_01/map_start/hero/state.txt` | **SYMLINK**, not a real file | Points at `hero_01/state.txt` — this is `compose_frame.c`'s own hardcoded `+18.0G`-era path (5 call sites, never updated when the voxel generator was added); the symlink is the minimal-risk fix, zero C changes needed |

## 3. Interact mode / nav mode separation (real house standard, "fuzz-op interact standard")

**Non-interact mode = menu nav only. Interact mode = map/hero control only. Never both at once.**

- The outer CHTPM menu (`[^] 1. Control Hero`, `2. End Turn`, `3. Eat`, ...) is driven by
  `pieces/keyboard/history.txt` (`[TIMESTAMP] KEY_PRESSED: N` format) and handled entirely inside
  `system/chtpm_parser_pal.c` — digit-nav, ACTIVATE, href navigation, and the ENTER-key dispatch
  that engages `onClick="INTERACT"` (only after a real Enter press while "Control Hero" is
  focused — simply being the default-focused item does NOT auto-engage it).
- Once engaged (`active_index` points at the INTERACT element), `chtpm_parser_pal.c`'s own
  INTERACT branch (~line 3718-3796) relays ALL non-ESC keys into `interact_relay.txt` — the menu
  nav digits become unreachable while this is active, by design.
- ESC exits interact mode (`set_interact_mode(0)`, ~line 3762) and resets `active_index`/
  `focus_index` back to top nav.
- **`interact_mode` in `hero_01/state.txt` is UI/session state, not game progress — `button.sh`
  now FORCE-RESETS it to `0` on every single launch** (not just first-ever world generation). This
  fixes a real, confirmed desync bug: `chtpm_parser_pal.c`'s own `active_index` always resets to
  `-1` on a fresh process start, but `hero_01/state.txt`'s `interact_mode` field persisted across
  relaunches (by design, so position/inventory survive) — a player who quit mid-interact-mode left
  `interact_mode=1` behind, and the next launch started nav-only at the CHTPM layer while game-side
  code still believed map-control was engaged. Confirmed fixed live: fresh launch now always shows
  `interact_mode=0` and no `[^]` marker until a real Enter press.

   frame (`chtpm_rgb_render.c`'s own `write_receipt()`, extended this session — local copy only,
   not symlinked to shared-lib, so this has zero effect on other projects). **You do not need to
   dump a PNG just to confirm a key registered or a state field changed** — `cat` the receipt
   first.
4. For actual VISUAL verification (does the render look right, not just "did the state change"),
   dump a real PNG from the raw frame file directly:
   `PRISC_PROJECT_ROOT=<session_dir> ops/+x/dump_rgb_png.+x <out.png>` — reads
   `pieces/display/rgb_frame.raw` directly, no window-capture race risk (contrast with
   `dump_frame_png_op.+x`, an XWD-style live-window capturer that's unreliable if a human is using
   the desktop concurrently — prefer the raw-file method).
5. Always confirm zero stray processes (`ps aux | grep chtpm_parser_pal | grep 19.00`) before a
   fresh launch, and `bash button.sh kill` when done testing.

## 5. NOT YET DONE — real, planned next step (map conversion)

**Direct user instruction, 2026-08-18**: port `+18.0G`'s own hand-crafted map content (the ORIGINAL
`pieces/world_01/map_start/` tree — `map.txt`, `furniture.txt`, `transitions.txt`, `items/`,

from the original — only wall geometry changes (flat → tall).

### What exists to work from

- **Source data** (untouched, in `+18.0G`, NOT `19.00`):
  `.../101.mutaclsym🧟‍♂️️+18.0G/pieces/world_01/map_start/map.txt` (40x16 ASCII, walls=`🧱`,
  floor=`🟫`, plus door/furniture/stairs glyphs), `furniture.txt`, `transitions.txt`
  (`x|y|dest_map_id|dest_x|dest_y`), `items/`, `monsters/` (zombie_01/02, zombie_child_01/02/03).
- **Target format** (this project, `19.00`, already real and working):
  `pieces/system/chunks/chunk_X_Y/chunk_X_Y_zN.txt` — one 16x16 glyph grid PER Z-LEVEL, plus
  `pieces/system/board_manifest.txt` (`z_base=`/`z_count=`) and `pieces/system/terrain_legend.txt`
  (`glyph|height|r|g|b|asset_hex|name`, already seeded this session with basic
  grass/wall/water/tree/mountain/wood/building/treasure/rubble/bridge entries — real content, not
  a placeholder, but built for a procedurally-generated test world, NOT yet matched against
  `+18.0G`'s own real map glyphs).

### The real, concrete conversion problem to solve (NOT yet designed, flag before implementing)

`+18.0G`'s `map.txt` is a SINGLE flat 40x16 grid (one glyph per X,Y — no Z dimension at all, since
the old renderer had no real multi-level rendering). The new format needs a SEPARATE 16x16 grid
PER Z-LEVEL (32 levels, per the existing `chunk_0_0` real example this session generated). A real
design decision is needed, not assumed:
1. **Dimension mismatch**: old map is 40x16, new chunk format is 16x16 per level (one chunk = one
   16x16 XY footprint). Does the OG map become ONE chunk (cropped/scaled to 16x16, losing real
   width), or MULTIPLE chunks tiled together (40x16 → e.g. 3 chunks wide x 1 chunk tall, needs
   `mua_generate_chunk.c`-equivalent multi-chunk stitching, not yet built)? **Flag this explicitly
   to the user before choosing** — it changes the real scope significantly.
2. **Wall height encoding**: a "10 voxel high" wall means the SAME XY wall-glyph position needs to
   appear as a SOLID (non-air) glyph on levels z=surface through z=surface+10, then air above.
   Floor/furniture/floor-level items stay single-level (at the surface z only). This needs a real
   per-glyph height-aware conversion pass — a wall glyph (`🧱`) written at 10 consecutive Z-level
   files at the same (x,y), a floor glyph (`🟫`) written at just the surface Z-level file, with air
   (a real "empty" glyph — check `terrain_legend.txt`'s own conventions for what glyph reads as
   navigable/empty) at every level above the wall's own top.
3. **Furniture/monster/item preservation**: these are currently SEPARATE files
   (`furniture.txt`/`monsters/*/state.txt`/`items/*/state.txt`) referencing X,Y (2D) positions — do
   they need a Z coordinate added now that the world is real-3D, or do they stay implicitly
   "at the surface Z-level," matching how `mua_generate_chunk.c`'s own real spawn logic already
   places the hero "one level above the ground surface" (see `muta_render_3d.c`'s own
   `default_current_z()` header comment, already documented in `muta-neo-fix-a17.md` §8.7 point 3)?
4. **Terrain legend gaps**: `terrain_legend.txt` (seeded this session) needs entries for EVERY real
   glyph `+18.0G`'s own `map.txt`/`furniture.txt` actually use (door, stairs, specific furniture
   icons) — the current legend was written for a generic test map, not audited against the real OG
   glyph vocabulary yet.
5. **Transitions/teleport system**: per direct instruction this session ("as far as the teleport
   system. leave it"), `transitions.txt`'s own `x|y|dest_map_id|dest_x|dest_y` format should be
   preserved AS-IS for map-to-map teleports — but each DESTINATION map (e.g. `building_01_gf`,
   `map_02`) needs its OWN real chunk data converted the same way, not just a dangling
   `dest_map_id` pointing at nothing (this was flagged as open in `muta-neo-fix-a17.md` §8.7 point
   6 already, still open).

### Recommended approach for whoever picks this up (delegate or otherwise)

Before writing any conversion code: read `+18.0G`'s own real `map.txt` + `furniture.txt` +
`transitions.txt` + one real monster/item state file in full, and read `mua_generate_chunk.c`'s
own real chunk-writing code (`ops/mua_generate_chunk.c`, ~line 275-340) to understand its EXACT
real chunk-file format byte-for-byte (glyph placement, `Z_COUNT` constant, surface_center
convention) before designing a converter — don't guess the format from this doc's own summary
above. Report a concrete plan (dimension-mismatch resolution, wall-height algorithm, legend
additions needed) BEFORE writing conversion code, matching this project's own established
"checkpoint before implementing" discipline from this session.

### 6.2 REAL, LIVE bugs found after conversion (direct user testing) — all root-caused, most fixed

**Bug: hero couldn't move at all.** Two stacked causes, found by direct manual op invocation
(`./ops/+x/move_player.+x <keycode>`, checking exit code and state diff — NOT trusting the live
loop alone):
1. `pieces/world_01/map_start/map.txt` (and `furniture.txt`/`transitions.txt`/`monsters/`/`items/`)
   were **never actually copied into `19.00`'s own directory** — the map converter reads them FROM
   `+18.0G` but the delegated agent's own report ("2D map files preserved... remain the gameplay
   source of truth") was misleading: preserved in `+18.0G` (untouched, correct), never copied INTO
   `19.00` where `move_player.c`'s own walkability check (`file_glyph_at()`) actually needs them.
   Missing file → default fallback glyph `'#'` (wall) for every single position → every move
   silently rejected as "blocked." **Fixed**: copied `map.txt`/`furniture.txt`/`transitions.txt`/
   `state.txt`/`monsters/`/`items/` from `+18.0G` into `19.00`'s own `pieces/world_01/map_start/`.
2. `pieces/registry/terrain/terrain_types.txt` (and `furniture/furniture_types.txt`) don't exist
   anywhere in the house except `+18.0G` — `glyph_walkable()`'s own missing-registry fallback is
   "only `.` counts as walkable," meaning **door glyphs (`+`) had never been walkable in ANY
   version of this game**, blocking every narrow-gap doorway in the OG map. **Fixed**: copied the
   real, complete registries from `+18.0G` (7-field format:
   `glyph|id|name|walkable|rgb_top|unicode|rgb_top_emoji` — my own first-draft `terrain_types.txt`
   from earlier this session only had 4 fields, which also silently broke the emoji lookup, see
   §6.3 below).

**Bug: xlector/possession model was backwards.** Direct user correction: intended design is
xlector-free-by-default (arrows move the cursor, hero stays still) until the player explicitly
possesses the hero via key `9` (arrows then move the hero). An earlier fix this session
(`possessed_id=hero` hardcoded at every launch) inverted this — reverted. Real root cause of `9`
never working at all: `choice.c`'s own key-`9` handler already has a working "reverse-jump"
re-possess branch (`else if (strcmp(last_possessed_id, "none") != 0)`), but nothing anywhere in the
codebase ever seeds `last_possessed_id` for a fresh game, so the very first `9` press matched
neither the release branch nor the reverse-jump branch — permanently a no-op. **Fixed**: `button.sh`
now seeds `last_possessed_id=hero` once, ONLY if the field is genuinely absent (append-if-missing,
never overwrites — this is real gameplay state that should evolve naturally once the player
actually starts possessing/releasing, unlike `interact_mode` which is pure UI-session state and
DOES get force-reset every launch, see §9.3/§10 of `muta-neo-fix-a17.md`).

**Real architecture mismatch found, resolved per direct instruction ("just copy piececraft
xelector. we can add richness later")**: mutaclysm's own `move_player.c` had TWO structurally
different branches — free xlector (uncollided, clamp-only, matches board-viewer) vs. possessed-hero
movement (real collision/combat/transition checks against the map, NOT present in board-viewer's
own simpler model at all). Compared directly against board-viewer's real, working reference
(`bv_menu_input.c` ~line 424-479): its own possession model is much simpler — the xlector ALWAYS
moves unconditionally (no collision, "even into the sky or underground" by design), and possession
just MIRRORS that same new position onto the possessed entity, no separate walkability pass.
**Fixed by porting this simpler model**: inserted an early-return right after `nx`/`ny` are
computed in the possessed branch — clamps to map bounds (same as the xlector's own free-move
clamp), writes the SAME new position to both `xlector_pos_x/y` AND the hero's own `pos_x/y`, then
returns immediately. **The original collision/combat/transition code is NOT deleted** — it's real,
working richness board-viewer's own simpler xelector doesn't have at all, just made unreachable via
the early return for now. Re-enabling it later (removing the early return) is the concrete "add
richness later" step, once basic movement is confirmed solid.

**Real, planned next richness (direct user instruction, not yet designed or implemented)**:
collision and vertical movement should become real **player traits** (not hardcoded always-on
behavior) — jump bound to the spacebar. This means the eventual re-enable of the collision code
below the early return should be conditional on a trait/flag, not a blanket restore, and jump is a
genuinely NEW mechanic (not present anywhere in `+18.0G`'s own original 2D game) needing its own
real design (a Z-axis velocity/height-clearance check against the voxel chunk data, most likely —
NOT the old 2D game's own flat collision model, which has no concept of vertical clearance at all).
