GRAND PLAN: Gemma Tool Scaffolding Architecture
Evolved 2026-07-21 — Tool Augmentation for Small LLMs
================================================================================

CORE INSIGHT:
Gemma (270M) cannot reliably follow JSON tool schemas or generate structured
tool calls. Instead of fighting the model's limitations, we pre-parse user
intent BEFORE hitting Gemma, execute tools deterministically, and only use
Gemma to wrap results conversationally. This is a three-layer architecture:

  Layer 1 (Intent Detection): keyword → tool lookup + strategy selection
  Layer 2 (Pre-execution): tool dispatcher → run in sandbox → capture output
  Layer 3 (Gemma Wrapping): template-fill response history → send to model

This doc explains the goal, current implementation (Phase 1), and concrete
technical roadmap through Phase 4.

ARCHITECTURE CURRENT STATE:
  Input: gui_state.txt message_input (user types text in chat box)
    ↓
  gemma_strategy: keyword detection + strategy random selection
    ↓
  strategy_execute_a: if strategy=A, pre-execute tool, log result
    ↓
  send_message: sends message to Gemma (context includes logged tool result)
    ↓
  check_response: parses Gemma response, looks for TOOL: lines (legacy Gemma hack)
    ↓
  Output: context_log.txt (appended), state.txt (updated), user sees result

KNOWN LIMITATIONS (intentional for scaffolding):
  - Tool detection is keyword-only, no semantic understanding
  - Argument parsing is fragile (extract_argument_after is basic)
  - No error handling if tool fails (just logs "Error" message)
  - Buffer sizes fixed at 4KB (will overflow on large outputs)
  - No multi-step tool sequences (each tool call is isolated)
  - No feedback loop to Gemma about tool success/failure (yet)

TECHNICAL DECISIONS & CONSTRAINTS
================================================================================

WHY THIS ARCHITECTURE (not "just make Gemma do tool calling"):
  1. Gemma-270M is too small; it hallucinates JSON and forgets schemas
  2. Fine-tuning Gemma for tool calling would require:
     - Thousands of tool-call examples
     - VRAM for training (not available)
     - Weeks of tuning (we want working tools now)
  3. Pre-parsing + weighted strategies lets us:
     - Get working tools immediately (pre-execute path)
     - Gracefully degrade to Gemma as a fallback (B strategy)
     - A/B test strategies without retraining
     - Layer in RL when ready (just adjust weights)

WHY STRATEGY WEIGHTS (not hard if/else):
  - Allows experimentation: what % of "read file" should pre-execute vs go to Gemma?
  - RL will eventually learn optimal % per tool per user
  - Easy to toggle: change one file, no recompile
  - Human-interpretable: 0.9 = "almost always pre-execute"

WHY EXECUTE IN SANDBOX/ (ops/+x/* environment):
  - Each op can read sandbox/config/context.txt for safety rules
  - All file paths are relative to sandbox/
  - User can't accidentally read /etc/passwd or write to /
  - Aligns with existing TPMOS tool precedent

WHY CONTEXT_LOG.TXT FORMAT (not JSON):
  - Pipe-delimited, one turn per line: simple, inspectable, append-only
  - No parsing overhead (strtok on pipe chars)
  - Easy to grep/tail when debugging
  - Matches mutaclsym's own handoff.txt documented choice

     Impact: If execute_tool is broken, even working pre-executed tools won't run

     Currently: extract_argument_after("read", msg) is extremely basic
     Issue: "read file.txt in /home/user" would extract everything including "in /home/user"
     Needed: Build a real argument parser (quoted strings, key=value, paths)
     Impact: Many tools won't work on sentences with multiple clauses

  ❓ 3. TOOL OUTPUT SIZE LIMITS
     Currently: strategy_execute_a.c uses 4KB fixed buffer
     Issue: Reading a large file will truncate silently
     Needed: Decide on max output size, handle gracefully (file too large → summary)
     Impact: Can't reliably read files > 4KB

  ❓ 4. ERROR HANDLING
     Currently: If tool fails, just logs "Error" string
     Issue: No distinction between "tool ran but had an error" vs "tool crashed"
     Needed: Capture stderr, exit codes, timeouts separately
     Impact: Gemma can't decide to retry differently

  ❓ 5. DEFAULT_OP.TXT REGISTRATION
     Currently: gemma_strategy and strategy_execute_a are NOT in default_op.txt
     Issue: Are they being compiled? Are they registered somewhere else?
     Needed: Verify build system includes them; add to default_op.txt if needed
     Impact: If not compiled, recent test success was a fluke

  ❓ 6. STRATEGY WEIGHTS PERSISTENCE
     Currently: weights are read from strategy_weights.txt at runtime
     Issue: Each gemma_strategy call re-reads the file (fine) but RL update path unclear
     Needed: Decide: does RL write to strategy_weights.txt directly, or separate file?
     Impact: If unclear, hard to build RL layer later
