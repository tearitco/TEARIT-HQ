# 03.IQABOD-test-report🔬.md — inference test + full write-up
> 2026-07-31. All compute on the Linux node (10.0.0.187); this box = zero model CPU.

## 1. What was tested
Copied prebuilt Linux ELF binaries (main_orchestrator.+x, generation_module.+x)
+ curriculum to the Linux node. Ran the real pipeline: vocab_only → train →
generate, plus the shipped pre-trained guess_the_word weights.

Binary deps confirmed minimal: only libm/libc (no GL/OpenCL/ffmpeg despite the
over-engineered compile script). Compile-on-target would be `gcc -O2 -lm`.

## 2. Results
### 2a. Pre-trained model (curriculum/guess_the_word, 32-token vocab, 88KB weights)
prompt "the cat" → `the cat likes happy <START> cats like <UNK> dogs they the cat
books dog love you plays dogs like games plays games he the books <UNK> i the
love cold ran we`

**Read**: real word order, bigrams/trigrams preserved, topic-consistent-ish
("cats/dogs", "plays games"). **Write**: grammar broken, <UNK> and <START>/<END>
spill into output, no coherent sentence > 4 words.

### 2b. Fresh corpus (5 short sentences, 14 tokens), full pipeline
- vocab_only: 0.019s; train 10 epochs: **0.109s**; train 30 epochs: ~0.3s.
  Training is essentially FREE on this hardware. This is the key enabler.
- generate from trained weights → `the cat fast happy happy <START> ran <PAD>
  ran a <START> a dog <START> <START> <END> <UNK> the milk <END> a <END>`
- Loss over 30 epochs: 2.6225 → 2.6211. **Descends but stalls at ~2.62 = the
  random-token floor (ln 14 ≈ 2.64).** The model is barely learning — the
  "same loss every time" worry in #.how2.3.txt is really "loss plateaus at
  random-chance", which looks identical across runs. Mechanism works, but the
  gradients/optimizer (lr=1e-5 in config.txt!) are far too weak to move loss
  off the floor. A learning-rate-10^2..10^3 problem.

## 3. Architecture truth (from source)
- dim=16, n_layers=2, n_heads=4, seq_len=32, FF=64, vocab≤32 (curriculum) /
  100k cap. SwiGLU FFN. RoPE. Real attention map output.
- Vocab is built per-corpus; no shared tokenizer. Training uses generation_module.
- → This is a **toy-scale char/word-model**: great as a mechanism testbed, not
  yet a language model. <UNK> is *expected* when vocab<corpus-token-space.

## 4. What this means for the GOAL (gemma + iqabod → code reader/editor/writer)
The user's goal: turn the two LIGHT models into code R/E/W agents.
- **gemma3:270m**: proven chat/tool-router. To make it a code *writer* we need
  fine-tuning, not prompting (prompting it for code fails syntax every time).
  Its natural slot: read + edit + route (understand intent, apply a diff,
  answer "what does this file do"), with the deterministic tool pipeline.
- **iqabod**: proven mechanism + free training. To make it a code *writer*:
  (a) fix loss (LR up 100–1000x; verify loss is a real cross-entropy, not a
      moving average artifact), (b) scale dim/layers modestly (16→64, 2→4 is
      still free at this speed), (c) grow vocab/tokenizer toward code tokens,
  (d) train on code corpora (harvested from the agent's own file sessions!).
  It cannot be a real code model at 16-dim/32-vocab — but it CAN be the
  always-on, always-cheap writer of *small structured fragments* (one token,
  one op name, one identifier) that the deterministic router assembles.

## 5. Honest recommendation (strategy, to discuss)
Split the R/E/W across the two models instead of asking either to do it all:
- **READ + EDIT**: gemma3:270m via the existing keyword pipeline (read/search/
  edit already work deterministically — that part of the goal is DONE today).
- **WRITE (structure)**: iqabod as the tiny generative fragment-engine, fed by
  harvested code corpora — with the LR/scale fixes above. It writes tokens,
  the router assembles statements.
- **WRITE (code)**: llama3:latest (Mac) today; the fine-tuned gemma later.
- Training offload: iqabod trains in <1s on the Linux node — do it there;
  distillation teacher (gemma) runs on the LAN. No local CPU, per constraint.
