1. WHAT ACTUALLY HAPPENED THIS SESSION (chronological, root causes not
   just symptoms)
================================================================================

STARTING POINT: api-fix.txt (a prior agent's diagnosis) claimed muchi-pal-
agent's async-polling architecture was fundamentally wrong ("random-words"
= corrupted JSON from a race condition) and proposed a full persistent-
daemon rewrite (Option A). That diagnosis was WRONG - checked live state
first and found "random-words" is a literal, working, intentional model
entry in model_list.txt (provider_kind=script, picks random words from a
wordbank, no network at all) - the user had it active during testing and
that's what confused a prior agent. No architecture rewrite was needed or
done. This was the first instance of a pattern that repeated all session:
check the actual live state / actual reference code before proposing a
big fix.

BUG 1 - GEMINI PERMANENTLY POISONED BY /model: `send_message.c`'s /model
listing command logged a role="tool" turn with tool_name=NULL.
build_gemini_request() treated ANY role="tool" line as a real
functionResponse, so it sent `{"name":"", ...}` - Gemini permanently
400s on that ("Name cannot be empty"), and because context is cumulative,
one /model command broke Gemini for the rest of the session. FIXED: that
listing line is now tagged kind="info", skipped by all four request
builders (ollama/gemini/gemma/llamacpp).

BUG 2 - GEMMA TOOL-CALLING REMOVED (direct instruction: "gemma should
never parse tool etc. we got tool to work, while using gemma by pre-
prompting our own fsm/or bt and running a script"): prompt_keyword.txt
used to instruct gemma to emit `TOOL: verb args` syntax; check_response.
c's gemma branch used to scan for it; gemma_strategy.c's own "Strategy B"
routed EVERY non-tool message (including a bare "hi") into that same
TOOL: prompt. All removed. Gemma is unconditionally plain conversational
text now - tool execution is 100% pre-decided by gemma_strategy.c
(keyword detection) + strategy_execute_a.c (pre-execution), matching
!.GRAND-PLAN-TOOL-SCAFFOLD.txt's three-layer design. Cross-referenced and
corrected an OLDER, conflicting plan in the one-level-up $.zest-er-
summary-FIN❤️‍🔥️+.txt sec. 4.1 (proposed giving gemma its OWN TOOL:
keyword parsing - superseded, corrected inline per that file's own
established [CORRECTION] convention, not deleted).

BUG 3 - THE REAL DOUBLE-LOG / STUCK-THINKING ROOT CAUSE: button.sh
classified `pieces/world_01/session_01/chat/` (state.txt holding
ai_state/curl_pid, context_log.txt) as SHARED, symlinked data - the same
bucket as pal-chat-irc's real multi-user `users/`/`rooms/`. Wrong
analogy: those fields are SINGLE-OWNER "am I mid-flight on one specific
API call" bookkeeping, the direct structural equivalent of pal-chat-irc's
own PRIVATE, per-session `pieces/apps/player_app/state.txt`. Confirmed
live via `ps aux`: THREE separate `button.sh run` sessions had
accumulated over an hour (closed terminals send SIGHUP, which the old
`trap ... EXIT INT TERM` never caught), all polling/mutating the same
shared files at once - that's the double-log mechanism, not a logic bug
in check_response.c itself. FIXED: button.sh now copies world_01 into
each session privately (seeded from canonical for continuity, persisted
back on exit), traps SIGHUP, and reaps any live instance of the
project's own binaries (matched by /proc/$pid/exe, not cwd - a rogue
prisc+x/chtpm_parser_pal pair launched directly from the project root,
bypassing button.sh entirely, was invisible to a cwd-only guard and had
been running for over an hour).

BUG 4 - RESPONSE COMPUTED CORRECTLY BUT NEVER RENDERED LIVE: even with
BUG 3 fixed, a single session could still show "Thinking..." frozen
indefinitely while the real answer was already correct on disk (only
visible after a full quit+restart). Root cause, found by reading gem-dev
_manager.c's main loop and pal-chat-irc's chat_inbox_watcher.c directly
(NOT by theorizing - see !.xyzos-standards.txt sec. 33.0): both references
have the SAME process that detects completion also trigger the render
itself, synchronously, right there - never just ping a marker and trust
a separate, later poll to notice. check_response.c only did the latter.
FIXED: added trigger_render() to check_response.c (ported directly from
chat_inbox_watcher.c's own function of the same name) - shells out to
compose_frame.+x the instant a response is ready, on every outcome
branch (success, PENDING_PERM, curl failure, error).

BUG 5 - CURL TIMEOUT TOO SHORT FOR THE REAL 8B MODEL: connect_op.c used
`--max-time 30`, justified by a comment claiming "groq-ollama (8B) in
<1s." Found gem-dev's own real debugging handoff for this EXACT model on
this EXACT host (1.TPMOS_c_+rmmp.0102.0028/projects/gem-dev/#.dox/groq-
api-handoff.txt, llama3-groq-tool-use:8b on 10.0.0.144:11434) - it needed
600s and documents curl timeout (exit 28) as a real, expected failure
mode, not rare. FIXED: connect_op.c now uses `-sS --max-time 600`
(matching gem-dev verbatim), and check_response.c surfaces curl's real
exit code as two distinct messages (timeout vs. host-unreachable)
instead of one generic "could not connect."

BUG 6 - GEMINI'S REAL ERROR TEXT WAS NEVER SURFACED: check_response.c's
gemini branch only ever tried the success shape (candidates[0].content.
parts[0].text/.functionCall) and fell through to a generic "empty or
unparseable response" on failure - silently swallowing Gemini's own real
error body (`{"error":{"message":"..."}}` - a malformed function-
declaration schema, safety block, quota hit, etc). gem-dev_manager.c's
own check_ai_status() already does an error.message extraction as a
fallback - ported it verbatim into check_response.c's gemini branch.

FEATURE - PER-SECOND "STILL WAITING" COUNTER (direct user request): the
existing "Thinking... [poll #N, frame #M]" display never actually told a
user how much real TIME had passed (poll rate isn't 1/sec, and compose_
frame only ran on state-change events, never on a plain idle tick, so
the counter looked frozen even during a real multi-second wait). FIXED:
send_message.c writes a `thinking_start` epoch timestamp when a request
begins; compose_frame.c computes and displays real elapsed seconds
(gem-dev_manager.c's own g_thinking_start/g_thinking_secs pattern);
main_loop_chtpm.pal now force-renders once per second (~10 idle ticks)
regardless of state change, so the counter actually visibly ticks.

DOCS: split the family-wide lessons between two files per direct
request ("i want to seperate this between !.xyzos-standards.txt and
!.xyzos-pitfalls.txt so one will be good for onboarding and one for
debugging") - !.xyzos-standards.txt sec. 33 has the terse, prescriptive
rule list; !.xyzos-pitfalls.txt (NEW FILE) sec. P1 has the full live-
caught narrative/evidence behind each one. Corrected the superseded
gemma-tool-use plan in $.zest-er-summary-FIN❤️‍🔥️+.txt sec. 4.1 (see BUG
2 above).
