## ⚙️ 2. THE ENGINE: cell-based orchestration (the 7 ops that make it work)

A **cell** = the smallest unit a 270m can reliably produce: one function body, one scene, one paragraph, one fix. Big tasks = many cells. The engine is a pipeline of ops, all house-style C/shell, each testable under K3:

| # | Op (new) | What it does | Model used |
|---|---|---|---|
| 1 | `plan_cells` 🗂️ | User task → **decompose into a cell list** (see S1). Output = a strict `plan.txt` (each line = one cell: `id | target | anchor | success-test`). | 270m (describe) + **deterministic normalizer** |
| 2 | `fill_cell` ✍️ | One tightly-scoped prompt: template + relevant context slice + anchor sentence → returns the cell's content. **Only** this cell's problem in the prompt. | 270m |
| 3 | `summarize_state` 🧵 | After each cell: "summarize what exists so far in ONE sentence" → rolling state line (S2). | 270m (describe = reliable) |
| 4 | `review_cell` 🧐 | **Describe-shape review** by 1b: "LIST concrete errors against this checklist" (never "rate it"). Returns a structured issue list. | 1b |
| 5 | `verify_cell` 🛠️ | **Deterministic** gate: compile/run (code), read-back + structure check (book), name/number consistency, diff sanity. Binary PASS/FAIL. | 0 models |
| 6 | `apply_cell` 🧩 | Deterministic stitch/patch of the accepted cell into the working file (append, insert at anchor, replace slot). Never free-form writes. | 0 models |
| 7 | `retry_cell` 🔁 | If `verify_cell` FAILs or `review_cell` lists issues → regenerate SAME cell with feedback + the failed diff appended, up to N tries (then escalate to 1b to rewrite, then give up honestly). | 270m (+1b fallback) |

The loop: **plan → (fill → verify → review → apply → summarize) per cell → final 1b pass → deliver.** This one pipeline is 80% of the 7-10. Everything below is ammunition for it.

## 💥 3. THE CREATIVE ARSENAL (strategies that feed the engine)

### S1 🥊 DOUBLE-PASS CHUNKING (your idea, fleshed out)
Pass 1: send 270m the whole task with "DESCRIBE the steps to finish this. One step per line." (describe-shape — reliable.) A **deterministic normalizer** (regex/slot, not the model) turns the lines into `plan.txt`: splits too-long steps, rejects gibberish lines, orders them, assigns each a success-test. Pass 2: execute cell-by-cell, each in an isolated tight prompt. Pass 3: 1b reviews the assembled result as a whole (sanity, not rewrite).
> Why it works: the 270m never holds the whole task in mind at once — it only ever sees ONE cell + the rolling state line. The big picture lives in `plan.txt`. 📝

### S2 🧵 ROLLING-SUMMARY MEMORY (unbounded context, the "notes" feature)
A 270m context window is ~small and collapses when filled. Fix: after every cell, `summarize_state` compresses "everything so far" into **one sentence**. Next cell's prompt = `[state: ...] [outline: ...] [current cell]`. The book/codebase never fits in context — the **compressed state line always does**. This is the classic **scratchpad / recursive-summarization** pattern, and "describe" is exactly what the 270m is good at. 🧠
> This replaces "long context" with "perfectly compressed short context." The file on disk is the memory; the state line is the working memory.

### S3 🩹 TEMPLATE + SLOT CONSTRAINED GENERATION (the anti-garbage guard)
Never ask for free-form code/prose. The harness owns the skeleton:
- Code: `skeleton.c` with one `__BODY__` slot per function → `fill_cell` writes ONLY the body → stitch → `exec_cmd gcc -c` compile (strict, zero-warning house bar). **Always GCC C, never Python.** The 270m can't break what it never touches. 🦺
- Book: chapter skeleton with named slots (`## SCENE: `, `[PROTAGONIST]`, `[SETTING]`) → one slot per call → `apply_cell` inserts at anchors.
- Prompt trick: **comment-first / spec-first** — first call asks 270m to write *one sentence describing what this function should do* (reliable), then the harness feeds that sentence back as the slot prompt "write the body that does exactly this." The describe pass pins intent; the code pass fills to it. 🎯

### S4 🎲 SAMPLE → FILTER → 1b-REVIEW → RETRY (ensemble, "voting")
Per cell: sample **3-5 candidates** (cheap, fast). Order of judgment, cheapest-first:
1. `verify_cell` (deterministic) filters out everything that doesn't compile/pass structure. ✂️
2. 1b **describes** strengths/errors per survivor, not a score.
3. Deterministic merger picks the survivor with fewest issues (or the one that best matches the anchor sentence).
4. None survive → `retry_cell` with feedback. 
This is **self-consistency + iterated refinement**, made affordable by 270m speed. Multiple weak draws → one strong pick. 🃏

### S5 🎯 TDD CANARY TESTS (the model works to a failing test)
The professor's rubric loves verifiable correctness. So: **the harness writes the test first** (one `canary_test.c` per cell, human-authored once), `fill_cell` writes code to satisfy it, `verify_cell` = `gcc` compile + run the test binary. PASS/FAIL is **mechanical — zero judgment needed**. The model never judges itself; the test does. This is TDD applied to the agent itself, and **everything is C** — the canary is compiled with `gcc`, executed, exit code is the verdict. 🧪
> Books: the canary is a **continuity checker** — "names used match the bible," "chapter numbers sequential," "every open plot thread from the outline is closed." Deterministic, brutal, fair.

### S6 🧮 PAL / CODE-AS-PROGRAM (the interpreter is the reasoner) — in C, always
**Program-Aided-Language** pattern: for anything arithmetic/logic/mapping, the 270m doesn't reason — it emits a **tiny C fragment** (a describe of what to compute), and the harness drops it into a minimal C program, compiles with `gcc`, and runs it. The compiled binary reasons; the model just wordsmiths. Handles the entire class of "counting, sorting, diffing, layout math" the 270m would otherwise butcher. 🔧 House rule: **no Python anywhere — the deterministic compute tier is GCC C** (matches this project's own all-C ops + zero-warning build bar).

### S7 🧑⚖️ CONSTITUTION CHECKLIST REVIEWER (every judge point is describe-shaped)
Wherever a model must "judge," the prompt is **never "rate/approve/reject"** (classify = unreliable) — always **"list what is wrong, missing, or inconsistent against this checklist."** A deterministic rule engine turns the list into actions (edit, retry, escalate-to-1b-rewrite). Applied at: cell review, chapter review, final delivery. Your `!.gemma-judge-tomo&iqa.md` already proved this pattern — now it's the standard. 📜

### S8 🔄 REVERSE ANCHORING + DOUBLE-DRAFTING (book craft, for free)
- **Reverse anchor:** for a chapter/scene, generate the *last sentence first* (fixed ending), then the body, conditioned on "must lead to: [ending]." Endings stop drifting. 🧷
- **Double draft:** write the scene twice, in two passes, then 1b merges the better parts; deterministic check keeps continuity. Two weak drafts + merge > one shaky draft.
- **Persona rotation:** same scene from two viewpoints, then merge — richer and more consistent than one shot. 🎭

### S9 📚 THE BIBLE KNOWLEDGE BASE (managed RAG, deterministic — the "note-taking" feature)
For a book: harness maintains a **bible file** (characters, places, continuity facts, chapter log) — extracted deterministically as cells are written (new name → auto-added, described by 270m). Each cell's prompt injects ONLY the bible rows relevant to that scene (keyword-matched, not semantic). For code: a **symbol index** (functions/files/what they do) built by grep, not embeddings. Retrieval = deterministic; context stays tiny. This is the "managed RAG" that actually fits a 270m: **digested facts, not raw chunks.** 🗂️

### S10 🚰 TWO-TIER PIPELINE (the "subagents" answer, within the gemma family)
270m = the **fabricator** (all cell production). 1b = the **quality control subagent** (reviews, merges, rewrites failing cells). The two never talk; the **harness is the router** between them. This is subagents without any model needing to "spawn" anything — the plan file IS the agent tree. 🤝

# 🕮 8. THE REAL CHALLENGE: WRITING + READING BOOKS AT BIBLE SCALE (long-term target)

> The wall I named in §5 (10k+ words) is NOT acceptable as a permanent boundary. The professor's real assignment, restated: **build a system that can create AND read books literally as big as the Bible (~783k words, ~31k verses, ~3.1M tokens) — coherent, consistent, navigable.** Here's the plan. And the fun part: 🎉 **the Bible itself already invented the technology we need.** We're not inventing book-scaling from scratch — we're copying the most successful long-form document in human history.

## 🧩 8.1 THE PROOF-OF-FORMAT: the Bible is an architecture, not a document

How did ~40 authors over 1500 years produce one consistent canon? Not by "holding it all in context" — that's impossible for humans too. They used:

| Biblical tech 📜 | What it is | Our engine equivalent ⚙️ |
|---|---|---|
| **Verses** | Atomic, addressable units (Gen 1:1) | **canon atoms** — every atom = one small file with a unique ID, never huge |
| **Books/Chapters** | Nested addressable structure | **canon.pdl** tree: book → chapter → section → atom |
| **Concordance** | A-Z index of every name/word → passages | **ledger index**: entity → atom IDs (built by grep + 270m describe) |
| **Cross-references** | "Mt 4:14 so it was spoken by Isaiah" | **ref edges**: atom → atom, deterministic |
| **Canon** | Fixed, authoritative text, never casually edited | **immutable versioned atoms** (a book IS a git repo 🕮) |
| **Scribes + redactors** | Copy, then a review layer reconciles | **270m scribe + 1b redactor** (our engine) |
| **Commentaries** | Notes about the canon, kept separate | **commentary layer** — annotations never touch canon atoms |
| **Reading plans** | Nobody reads the whole thing at once | **derived views** — read = index query + stream, not full load |

**The scaling insight, in one line:** a 270m never needs to know the book — it needs to know **ONE verse, its two neighbors, the relevant lexicon rows, and its thread card.** That's O(1) context forever, no matter how big the book gets. 📏
❤️‍🔥️
## 🏛️ 8.2 THE CANON STORE (the heart of Bible-scale writing)

```
canon.pdl            ← the master plan tree (book→chapter→section→atom IDs + thread cards)
canon/<book>/<ch>/<atom>.txt   ← immutable canon atoms (never rewritten, only superseded)
ledger/entities.pdl  ← entity → atom IDs, entity → description (the concordance)
ledger/threads.pdl   ← plot/prophetic/legal threads: OPEN/FULFILLED state per atom
refs.pdl             ← cross-reference edges (atom → atom)
commentary/<book>/<ch>.md      ← annotations (never part of canon)
outline/<book>.md    ← thread cards per chapter (tone, entities, promises, schedule)
```

**Writing rules (the law):**
1. `fill_cell` writes ONLY one canon atom at a time. 🧱
2. Prompt = `[prev atom][thread card][lexicon rows for entities in this atom][reverse anchor / next atom pointer][state line]` — never more. Locality is law. 🧿
3. Every atom is **immutable + versioned** on write (v1, v2...). No edits, only supersedes. That makes re-reading, rollback, and forking free. 🧬
4. `verify_cell` per atom: names resolve in the ledger, numbers sequential, no orphaned promise, references point to real atoms. 🛠️
5. **The promise ledger is the whole-tome backbone:** a prophecy in Gen must close in Rev. Threads are rows with OPEN/FULFILLED states; a canary per chapter asserts every thread the outline schedules to close actually closes. The 270m never tracks the arc — the **ledger does**, and the model only ever sees the one line that says "this chapter must fulfill thread #7." 🪢

## 📖 8.3 WRITING A WHOLE BIBLE (the pipeline, ~31k atoms)

1. **Genesis pass** 🗺️: outline the entire book as thread cards (book → chapters → sections → which promises/entities each must touch). Built the usual way — 270m describes, deterministic normalizer shapes it into `canon.pdl`. This IS the "story bible" and it fits in a few hundred lines.
2. **Exodus→Revelation pass** ⏳: write atom-by-atom in canon order. Each atom = one tight prompt (above). Context never grows.
3. **Redaction pass** 🧑⚖️: per book boundary, **1b council review** over the book's *aggregates* (ledger rows + sampled atoms + diff stats) — never the raw 30k atoms. Issues → `retry_cell` on flagged atoms only. O(changed), not O(book).
4. **Concordance pass** 🔍: entity extractor continuously updates `ledger/entities.pdl`; refs auto-created by deterministic matching.
5. **The final grade** 🎓: a read-through is done by *querying the ledger* ("show all atoms where Eli the priest appears," "show all OPEN threads"), and the deliverable ships as the canon repo.

**The fun math:** 31k atoms × ~1s (270m) ≈ **8-9 hours of LAN time = one overnight batch job.** The "impossible wall" is actually an overnight run + a database. The Bible being verse-sized is not a coincidence — it's the maximum reliable production unit for human and 270m alike. 😄

## 📚 8.4 READING A BIBLE-SCALE BOOK (the read side)

Reading at this scale is **never loading the text** — it's:
- **Derived views** 📃: "read chapter 23" = stream atoms 23.1 → 23.n in order. A view is a query, not a file.
- **Study/query** 🧭: "where does Moses appear?" = ledger lookup → atom list. Instant, O(log n) via index.
- **Commentary-safe** 🗒️: readers annotate the commentary layer; canon atoms stay pristine.
- **Editing at scale** ✍️: revise "book of Law" = edit atoms in place with version bumps → **only the affected ledger rows + ref edges re-verify** (incremental consistency, like `make` with dependency tracking). A 3.1M-token edit pass is a *diff job*, not a re-read job.
- **Bookmarks + reading plans** 🔖: the reading plan is a ledger query with cursors, not a position in a giant string.

## 💡 8.5 ALTERNATIVE IDEAS (if the canon-store architecture doesn't work)

1. **PLAN B — Ring-Buffer Canon (simpler, weaker)** 🔄: drop the full graph. Each cell sees the previous N atoms (fixed ring) + a **decade-capsule**: one summary sentence per book/era, recursively built by `summarize_state`. Super simple, decent continuity, weak cross-book prophecy. Best first prototype — cheap to build, proves the overnight-batch claim before the graph work.
2. **PLAN C — The Dictaphone (maximum reliability, zero graph)** 🎙️: write the book as pure single-sentence atoms, each a standalone describe call conditioned only on the previous atom + lexicon. Trivially verifiable, literally the Bible's structure, ~31k calls. Slowest, but it *cannot* drift far — each atom is a fresh tiny decision.
3. **PLAN D — Human-Bishop Canon (human-in-the-loop)** 🧎: 270m drafts atoms, the human approves/rejects like a bishop ruling on canon; approved atoms **lock** (immutable), rejected atoms go to 1b re-draft. Development energy goes only to rejected units. Great for real editorial control + a research paper's "human oversight" angle.
4. **PLAN E — Forked Traditions (the multiverse library)** 🌌: because atoms are versioned + refs are edges, **forking the whole canon is one command**: "canon-A" (prophetic tone) vs "canon-B" (legalistic) share most atoms, diverge at refs. The wall becomes a *feature* — the system is a library of related Bibles, and consistency is defined *per tradition* by its own ledger. Also a gorgeous demo for the professor.
5. **PLAN F — The Cosmology Ledger (invariants as data, strongest anti-contradiction)** 🔒: the things that MUST never vary (who God is, the laws, the fixed prophecies) live as **structured data rows**, not prose. Generation cells can only *reference* the ledger, never invent it. `verify_cell` mechanically rejects any atom contradicting a ledger row. This is the ultimate weapon against the coherence wall — the invariant knowledge is enforced like a schema, and the prose is only ever "shading" over an enforced truth.

## 🤖️ 11. AGENT-45 INTEGRATION — teaching the agent to use the pipeline

### The architecture (how agent-45 actually works)

Agent-45 is NOT a bare LLM — it's a **tool-augmented agent** that runs via `button.sh`:

```
User types → gui_state.txt → gemma_strategy.c (keyword detect)
    → strategy_execute_a.c (pre-execute tool deterministically)
    → result stashed in tool_result.pending
    → send_message.c (gemma sees result, generates response)
```

**Key principle:** Gemma is too small to reliably follow TOOL: format, so we:
1. Pre-parse user input to detect what tool is needed (keyword routing)
2. Execute the tool deterministically (no model involvement)
3. Give gemma the result and let it describe/respond

This is exactly PITFALL 69 in action — **the deterministic layer does ALL the work, gemma just sees results.** 🎯

### Available tools (agent-45's toolset)

| Tool | What it does | Model? |
|---|---|---|
| `list_dir` | List directory contents | ❌ none |
| `read_file` / `file_ops` | Read a file | ❌ none |
| `write_file` / `file_ops` | Write/create a file | ❌ none |
| `edit_file` | Edit/replace content in a file | ❌ none |
| `exec_cmd` | Execute a shell command | ❌ none |
| `search_in_files` | Grep/search across files | ❌ none |
| `send_message` | Send chat to gemma | 🟢 gemma |
| `switch_model` | Switch LLM model | ❌ none |
| `web_search` | Search the web | ❌ none |
| `tts_speak` | Text-to-speech | ❌ none |
| **`plan_cells`** 🆕 | Decompose chapter into cells | ❌ none |
| **`fill_cell`** 🆕 | Generate one cell's verses | 🟢 270m (LAN) |
| **`verify_cell`** 🆕 | 1b describe-shaped review | 🔵 1b (LAN) |
| **`apply_cell`** 🆕 | Assemble cells → chapter | ❌ none |
| **`grade_chapter`** 🆕 | Score vs gold (0-100) | ❌ none |

### How to trigger the W1 pipeline

The user types natural language → `gemma_strategy.c` keyword-matches → `strategy_execute_a.c` runs the op:

| User types | Detected tool | Op executed |
|---|---|---|
| "plan cells for solpen ch01" | `plan_cells` | `plan_cells.+x solpen ch01` |
| "fill cell 01 for solpen ch01" | `fill_cell` | `fill_cell.+x solpen ch01 cell_01` |
| "verify cell 01 for solpen ch01" | `verify_cell` | `verify_cell.+x solpen ch01 cell_01` |
| "apply cells for solpen ch01" | `apply_cell` | `apply_cell.+x solpen ch01` |
| "grade chapter solpen ch01" | `grade_chapter` | `grade_chapter.+x solpen ch01` |

### Progress indicator

For blocking LAN calls (fill_cell, verify_cell), the agent writes a status file:
```
pieces/world_01/session_01/chat/tool_progress.txt
```
Content during execution:
```
tool=fill_cell
status=running
detail=solpen/ch01 cell_01
started=1691234567
```
The renderer can poll this to show "⏳ fill_cell running..." while the LAN call is in flight.

### The workflow (what the agent does when asked to regenerate a chapter)

1. **Plan**: "plan cells for solpen ch01" → creates 7 cell specs
2. **Fill each**: "fill cell 01" → "fill cell 02" → ... → "fill cell 07" (each takes 2-30s)
3. **Verify each**: "verify cell 01" → ... → "verify cell 07" (1b reviews)
4. **Apply**: "apply cells for solpen ch01" → assembles chapter.generated.txt
5. **Grade**: "grade chapter solpen ch01" → deterministic score vs gold

The agent should present results after each step and ask the user before proceeding to the next step. This is a collaborative workflow, not a fully autonomous one — the human stays in the loop. 🤝
