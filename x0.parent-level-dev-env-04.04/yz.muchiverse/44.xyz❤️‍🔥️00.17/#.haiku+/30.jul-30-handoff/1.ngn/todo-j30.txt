PHASE B2: rtp_manager.c + rtp_map_editor.c + rtp_event_editor.c +
  rtp_palette.c as real CHTPM `<module>` daemons
  Editor-work equivalent: E1 + E3 (build from a real pattern; expect
  and fix real small wiring bugs as they surface).
  WHAT: layouts (game.chtpm / map_editor.chtpm / event_editor.chtpm /
  project_menu.chtpm / palette.chtpm) with `<module>` tags, switching
  via href/F-key WITHIN ONE SESSION - no second process spawn, this is
  the entire architectural difference from Track A. Reuse PHASE A2's
  own event-system DATA SHAPE (switches.pdl, event.pal command IR) -
  the data model should be IDENTICAL between rpg-xyz and rtp-xyz, only
  WHERE the editing UI lives differs. Do not invent a second event
  format for this track.
  PROOF, INCREMENTAL: prove layout-switching itself works BEFORE
  wiring real map/event editing into each module. UPDATE (2026-07-30,
  same day, found while building 102.agy-txt as this exact phase's own
  smaller-scale rehearsal - see 102.agy-txt/PLAN.md §1.5 for the full
  live-tested account): the original version of this bullet expected
  href navigation to keep the SAME process alive, checked via PID -
  that expectation was WRONG, tested directly. `href` respawns
  chtpm_parser_pal's own tracked module on EVERY transition
  (`cleanup_module()` runs unconditionally on an href click - confirmed
  by reading chtpm_parser_pal.c after a live 3-navigation test showed
  3 different PIDs). This does NOT block rtp-xyz - the reference
  architecture (slop-ed-dev) respawns on href too and works fine,
  because real state lives on disk, never in a process-resident
  variable. CORRECTED PROOF TARGET: inject the real key/href that
  should switch game.chtpm -> map_editor.chtpm, assert the layout
  actually changed (`current_layout.txt` + the rendered frame) AND
  that whatever disk state needs to survive the transition (map data,
  cursor position, whatever this phase's own stub state is) actually
  does - NOT that the PID stays constant, which was never the real
  requirement. If genuine same-process switching is ever needed for
  some other reason, chtpm_parser_pal.c has a separate
  `pieces/display/layout_changed.txt` pulse mechanism that looked like
  a real candidate but was not investigated further this session -
  read it first rather than assuming href-avoidance is possible/needed.

PHASE B3: Save/load, events, database - SAME phases as A1/A2/A3, same

Per WIDGETS_ROADMAP.txt §7's own convention (cross-project multi-

Both harnesses prove the SAME six things, per 1-rtp-rpg-xyz-scaffold.md
§5d (Create / Edit / Save / Reload / Play / Module-handoff for Track B
only) - copy that section's own numbered list rather than re-deriving
it here. The only new addition this document makes: BOTH harnesses
must be level-2 (real key injection) from the START, not upgraded
later - Phase 0's own finding (the existing map save/load proof is
level-1 only) is the direct, concrete lesson for why starting level-2
matters more than shipping fast here.

UPDATE (2026-07-30, ed-app-vs-agy-txt.md, same dir - full account
there): level-2 synthetic injection, as defined above, is necessary
but NOT sufficient. Real human keyboard testing of 102.agy-txt (a
small-scale Track-B-shaped rehearsal, see that doc) found a real
dual-input-capture bug in the SHARED chtpm_parser_pal.c/gl_mirror.c
system layer - every real typed character landing doubled - that both
that project's own level-2 harness AND text-editor-xyz's own already-
proven one had zero chance of catching, because synthetic injection
(a single deliberate write per intended character) cannot reproduce a
race between two independent real OS-level capture processes. Fixed
in the shared system source, rebuilt into every project that compiles
it. Both rpg-xyz's and rtp-xyz's own full-loop harnesses (immediately
below) should budget at least one genuine OS-level input test (xdotool
against the real GL window, or literal human testing) for any feature
that types while GL is active - synthetic-only proof is not enough for
that specific class of bug, even though it remains correct and
necessary for everything else level-2 already covers.

DECIDING "WHICH WORKS FIRST" (rpg-xyz-plan.md's own M5, made concrete):
  - Whichever track's OWN full-loop harness goes green FIRST, with
    real level-2 proof, wins the "works first" title for that specific
    milestone - track progress by harness color, not by vibes or how
    much code exists.
  - Expect Track A (rpg-xyz) to reach individual pieces faster (file-
    menu/tile-picker/map-picker already have real, if level-1-only,
    proof) but Track B to potentially close faster on FULL-LOOP once
    started, since B2's own module-switching risk, once proven once,
    de-risks map/event/save all at once within a single session -
    Track A's separate-widget-processes model pays a re-launch cost
    per tool switch that Track B's in-session layout-switch doesn't.
    This is a real, testable prediction, not a guess to leave
    unchecked - the harness timings themselves will confirm or refute
    it.
  - Per rpg-xyz-plan.md's own M5 ("Polish and compare... Decide
    direction"), this document does NOT pre-decide the winner -
    building both and comparing real harness results is the actual
    point of running two tracks, not a formality.
