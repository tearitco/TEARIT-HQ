# Haiku Agent — Virgin Startup Playbook
This file is for you (Claude Haiku) to read on a cold start. It's NOT for the user.

## FIRST: Load Context (120 seconds, non-negotiable)
Before answering ANY question or starting ANY work:

PRIORITY (always read):
1. Read #.haiku/for-user/user.txt — know who this person is
2. Read !.xyzos-standards.txt (parent dir, 2.muchi-verse-0.0/) — THE running rulebook for all projects
3. Read #.haiku/for-user/CURRENT_SESSION_PRIORITIES.txt — what they're focusing on RIGHT NOW

REFERENCE (always available, check if relevant):
4. Read #.haiku/for-user/index_context_summary.md — active projects, foundation, gotchas
5. Read #.haiku/for-agent/gotchas_by_project.txt — project-specific pitfalls I've found
6. Check zest-er-summary.txt (parent dir, if recent) — what happened last session

If any critical files don't exist, note it — you may need to ASK the user or CREATE them on first setup.

## SECOND: First Questions to Ask (in this order)

**If this is a cold-start session (no context files exist):**
- "Are you starting a new session on [date]? Should I create CURRENT_SESSION_PRIORITIES.txt?"
- "What's the main focus today?"
- "What are the current blockers or open questions?"

**If context files exist (normal case):**
- "What changed since [last session date]?" (only if months have passed)
- Nothing else — assume context is current and proceed

**NEVER ask:**
- "Should I read this file?" (yes, always)
- "Is this still relevant?" (check dates, check git log if unsure, ask only if genuinely confused)
- "Do you want me to [obvious next step]?" (just do it, or explain why you won't)
- "Should I proceed?" (on already-decided items — this is irritating)

## THIRD: Understand the Workflow

### Architecture-First Pattern
- Design docs come BEFORE code (always, even under time pressure)
- Read design docs IN FULL before writing code (don't skim, don't guess)
- Live-test everything with real running processes (file injection + frame reading)
- One pattern used everywhere: REGISTRY + SWITCH + SELF-CONTAINED OPS

### Session Isolation Pattern
Every project launch:
- NEVER run directly against project root (breaks session isolation)
- ALWAYS go through button.sh `run` or replicate its exact session setup (pal-scripts/launch_irc_agent.sh is the worked example)
- Kill by /proc/$pid/cwd, never by argv (argv text is identical across sessions)

### File-Injection Testing Pattern
To test without a real UI:
- KEY INJECTION: write directly to pieces/keyboard/history.txt (or gui_state.txt field + interact_relay.txt) — same state real keypress produces
- FRAME READING: read pieces/display/current_frame.txt (or project's view.txt) directly — that's the real data ops wrote
- Limitation: doesn't verify terminal rendering looks right (frame history/scroll) — do BOTH file injection + real terminal run

### Syncing Shared Code Pattern
- shared-ops/ holds CANONICAL copies (prisc+x.c, chtpm_parser_pal.c, etc)
- Each project keeps its OWN copy under system/ or ops/ (synced deliberately, never symlinked)
- ALWAYS diff before overwrite (check shared-ops-manifest.txt for exceptions)
- NOT yet synced to all projects: both prisc+x.c VM bug fixes from this session

## FOURTH: What to Check Before Starting Work

**On any work involving C ops:**
- Read the op's own header comment FIRST (don't assume what it does)
- Check xyzos-standards.txt sec. 23 for kill patterns (match the cwd-match-then-kill pattern used everywhere)
- Verify the op doesn't write to display/current_frame.txt (only chtpm does that)

**On any work involving .pal scripts:**
- Check if it uses @file include syntax (non-standard, specific projects only)
- Verify it's calling ops by their exact name (op_name.+x format in pieces/ops/)
- Test with file injection FIRST, then real terminal

**On any work moving/renaming directories:**
1. Run `ps aux | grep prisc+x` — find any stale processes
2. Check /proc/$pid/cwd on each — are they pointing to old paths?
3. Kill the stale ones by cwd match (don't use pkill -f)
4. Do this TWICE (once often isn't enough)

**On any work syncing shared files:**
1. Diff the canonical (shared-ops/) vs. local (project/system/)
2. Check shared-ops-manifest.txt for "don't sync" exceptions
3. ONLY copy if you've read the diff and understand what changed

## FIFTH: Escalation Patterns

**When to ask the user:**
- Ambiguity about what they want (not what's obvious next step)
- Architecture decision with real tradeoffs (ask BEFORE building)
- Estimates: "how long might this take?" (they like real numbers, not hedges)
- Novel problem I can't solve by reading the code + trying it
- Whether something is "worth doing" vs. "defer for now"

**When to just decide:**
- Implementation details ("which file should I edit?" → read the architecture, it's obvious)
- Testing approach ("how should I verify this?" → file injection first, then real terminal)
- Refactoring scope ("should I clean up X while I'm here?" → NO, unless it's load-bearing)
- Next step when priorities are already clear (just proceed)

**When to run code to verify instead of asking:**
- "Does this file exist?" → `test -f <path>`
- "What's the current state?" → `git log`, `git status`, `ls -la`
- "Will this compile?" → try it
- "Is this the right behavior?" → run it, check output
- Don't waste user's time asking things the codebase can answer

## SIXTH: Coherence Across Sessions

**Update these files as you work:**
- CURRENT_SESSION_PRIORITIES.txt — mark subgoals done/blocked, add new blockers
- gotchas_by_project.txt — add project-specific discoveries the moment you find them
- index_context_summary.md — add new projects, update active status if things change

**When ending a session:**
- Offer to update the context files (ask user if anything changed priorities)
- Don't create intermediate files (scratch work, temp analysis) — this isn't a chat log
- DO preserve surprising findings in gotchas_by_project.txt (this is permanent learning)

## SEVENTH: Tone & Style for This User

- Terse (one sentence per update is almost always enough)
- Direct (state results and decisions, don't narrate internal deliberation)
- No trailing summaries ("I can read the diff")
- No "should I" questions on obvious next steps
- No hedging on estimates (give a real number, explain reasoning)
- No re-litigating past decisions ("earlier you decided X" — don't)
- When correcting yourself: add correction alongside original text (don't delete)

## EIGHTH: The ONE Pattern That Shows Up Everywhere

Every single feature in this codebase reduces to: REGISTRY (plain-text file naming options) + SWITCH OP (rewrites state to activate one) + SELF-CONTAINED OPS (do the real work).

This applies to:
- Provider selection (model_list.txt + switch_model.c + send_message.c)
- Trigger routing (trigger_list.txt + script provider parsing)
- NPC behavior (npc_bank.txt + per-NPC script/fsm/rl selection)
- Terrain generation (terrain_registry.txt + parameterized generator ops)
- Scale fidelity (SCALE_BANK.txt, entity_type|domain|scale_level keys)

When you're stuck on "how should I add a new swappable behavior," this is almost always the answer. Don't invent new patterns.

## NINTH: When to Hand Off to Sonnet (Important)

Before handing off, ALWAYS try to break the task into smaller chunks first. Only if the task is GENUINELY too hard after that, create sonnet-handoff.txt:

**Signs this needs Sonnet (not Haiku):**
- Reasoning spans multiple projects/design docs that won't fit in my context window
- Task requires multi-step architectural decisions that build on each other
- Problem is novel enough that running code to verify won't help (need real reasoning)
- I've tried breaking it up and still can't fit it in my context

**How to hand off:**
1. Create #.haiku/sonnet-handoff.txt (template exists in that file)
2. Fill in: what you tried, why it's too hard, smaller chunks option, context for Sonnet
3. Message the user with the file path: "This feels too hard for Haiku. Should I hand off to Sonnet, or should we break this into smaller pieces first?"
4. Wait for user decision — don't just assume they'll use Sonnet

**When NOT to hand off:**
- Task looks hard but is just big (break it up into steps, do them sequentially)
- Task requires reading files (I can do that, just loads them in order)
- Task is unknown (I can grep/explore, that's what the Explore agent is for)
- Task is "novel but constrained" (run code to verify my reasoning)

Only hand off when the core work is reasoning that spans too much context, not when it's just big or unknown.

## ELEVENTH: Known Weak Points (Honest Self-Assessment)

- Small context window: load the context files FIRST, don't rely on me remembering things
- Slower reasoning: for hard design problems, ask the user to clarify or propose a direction
- Less reliable at novel problems: verify by running code, don't trust reasoning alone
- Will miss subtle gotchas: read xyzos-standards.txt every time you work on something new, don't skip "because it looks small"
- Can't hold entire codebase in mind: use grep, use Explore agent for codebase search, don't try to reason about unknown files
