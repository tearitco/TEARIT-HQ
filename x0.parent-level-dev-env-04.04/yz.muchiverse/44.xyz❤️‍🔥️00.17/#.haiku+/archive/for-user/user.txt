## What They've Built (The Pattern)
Every project in yz.muchiverse/2.muchi-verse-0.0/ follows this exact architecture:
1. prisc+x.c (tiny VM) runs .pal scripts (the control language)
2. chtpm_parser_pal.c (shared UI engine) renders to terminal OR RGB from same layout
3. Pile of small C ops: each does ONE thing, owns its own constants/root-resolution, no shared headers
4. Plain text state files (state.txt, context_log.txt, registry files) — NO databases, NO JSON-as-state, NO sockets unless networking is genuinely needed
5. DESIGN DOC FIRST (CHAT-INTEGRATION-ARCHITECTURE.txt, PAL-NET-STANDARD.txt, etc) before code

## Standing Conventions (Violate These = Reintroduced Bugs)
- SESSION ISOLATION: always launch via button.sh or replicate exactly (pal-scripts/launch_irc_agent.sh is the worked example)
- KILL BY /proc/$pid/cwd (never by argv — processes have identical command text across sessions)
- PRISC_PROJECT_ROOT is cached at startup (not live — stale processes keep writing to old paths after moves)
- ONE VISIBLE FRAME WRITER: only chtpm_parser_pal writes to display/current_frame.txt or project's own view.txt
- REGISTER-SENTINEL BUG: several prisc+x opcodes had unset fields default to 0 (valid register) instead of -1 sentinel — check for this exact bug class on any new opcode
- ALWAYS DIFF before overwriting synced shared files (check shared-ops-manifest.txt for "NOT synced from here" notes)

## The Tech Stack (One Paragraph)
prisc+x is a tiny custom VM (RISC-V-style registers, li/beq/j/custom-op bytecode) that runs .pal scripts. chtpm_parser_pal is the shared UI engine — real declarative <cli_io>/<button>/${piece_methods} layouts, drives BOTH terminal rendering and (via chtpm_rgb_render) real RGB pixel rendering from the SAME layout. Every project is: a chtpm layout (pieces/chtpm/layouts/*.chtpm) + a .pal script (the main loop, calls custom ops each tick) + a pile of small, self-contained C "ops" (each does ONE thing, owns its own root-resolution/constants, never includes shared headers) + plain pipe-delimited or key=value text files as ALL state (state.txt, context_log.txt, registry files) — no databases, no JSON-as-state, no sockets unless a project genuinely needs real networking (palnet_peer.c).
