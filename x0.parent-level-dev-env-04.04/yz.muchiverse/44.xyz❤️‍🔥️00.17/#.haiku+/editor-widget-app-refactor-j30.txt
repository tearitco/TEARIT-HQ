## 1. What "the app that uses widgets" actually is (don't confuse it
   with 102.agy-txt)

`102.editor-📄️00.00` (launched via `@.apps/text-editor-xyz`) +
`&.widgits/file-menu` are TWO SEPARATE PROCESSES/GL windows, connected
over a relay-file cmd-bus - the WIDGET-TOOLCHAIN pattern (per
`102.agy-txt/PLAN.md` §0, which explicitly contrasts this against
agy-txt's own "no second widget process" self-contained design).
file-menu is a real, SHIPPED, WORKING widget - PITFALL 63/64's own
fixes are already verified live against it. This refactor is a
style/architecture upgrade to bring it in line with the real
in-house dynamic-markup standard, NOT a bug-fix-a-broken-thing task -
treat every change here as "make it match the standard", verify it
still works exactly as before afterward, don't "fix" things that
aren't broken.

file-menu.chtpm declares
`<module>system/prisc+x pal/main_loop_chtpm.pal</module>` (the SAME
shared PAL loop 102.agy-txt's OLD editor.chtpm/file_menu.chtpm still
use) - this is PAL-driven dispatch, NOT a native C manager. `fm_menu_
input.c` receives its key as an argv value the PAL script passes in
directly (reading `pieces/apps/player_app/interact_relay.txt` itself)
- it does NOT poll files on its own. This means the ONE bug class
found this session that does NOT apply here: 102.agy-txt's NEW native
manager was found to be watching the wrong file entirely
(`pieces/keyboard/history.txt` instead of the real
`<interact src>` target) for KEY:n button-activation events - that bug
was specific to building a NEW native-C poll loop from scratch.
file-menu's PAL-driven dispatch already gets its key correctly (it's
real, shipped, working - confirmed by PITFALL 64's own live-tested
fixes) and needs NO change on that front.

## 2. The actual real work item (matches refactor-list-j30.txt Tier 3)

`fm_compose_frame.c` renders the file browser listing/menu with
hand-drawn `[>]`/`[^]`/`[ ]` text markers (confirmed via direct read
this session) instead of real, PARSER-owned, dynamically-generated
`<button onClick="KEY:n">` markup. `fm_menu_input.c` correspondingly
hand-tracks `cursor_pos`/`field_active` itself instead of letting
chtpm_parser_pal's own nav/focus/highlighting own that state (the
exact violation PITFALL 65 documents, and the exact thing
102.agy-txt's own rebuild this session fixed for its OWN browser).

CORRECTED 2026-07-30 (direct instruction, mid-implementation of this
exact section - a first pass at this got it wrong and is preserved
below only so the mistake and its real symptom are on record): file-
menu's THREE screens (main_menu/file_browser/peer_list) MUST become
THREE SEPARATE real `.chtpm` layout files connected by real
`<button href="...">` navigation - NOT one `file-menu.chtpm` with an
internal `mode` variable switching what `${game_map}` renders. This
is the actual point of the whole refactor (modularity/reusability,
direct instruction) and it is NOT optional/stylistic - it also fixes a
real, live-caught bug for free: a same-layout `mode` switch is NOT a
real chtpm layout transition, so `chtpm_parser_pal.c`'s own
`focus_index` CARRIES OVER from whatever nav position the user was on
in the PREVIOUS mode's element structure, landing on an unrelated
element in the new one (confirmed live: digit-jumping to "SAVE AS..."
in main_menu then activating it left focus pointing at an arbitrary
directory-listing entry in the freshly-rendered file_browser
structure, not SEARCH/index 0). A REAL href transition avoids this
entirely for free - `cleanup_module()`/`parse_chtm()`/
`initialize_focus()` all run fresh on every real href navigation
(confirmed via direct read of chtpm_parser_pal.c's own href-handling
code, the same mechanism 102.agy-txt's own editor.chtpm -> file_menu.chtpm
-> file_browser_save.chtpm/file_browser_load.chtpm chain already uses,
proven this same session). Do not reach for a manual `active_target_id`
toggle or any other same-layout focus-reset workaround as a substitute
for this - that was the first-pass mistake this note replaces, and it
only patches the symptom, not the actual architecture request.

Concrete steps (mirror 102.agy-txt's own real rebuild AND its real
multi-layout/href shape - both are already proven this session, do not
re-derive from scratch):

1. Split `&.widgits/file-menu/pieces/chtpm/layouts/file-menu.chtpm`
   into real separate files - e.g. `file_menu_main.chtpm`,
   `file_menu_browser.chtpm` (save_as/load/pair share one real layout,
   `browse_mode` stays as an internal variable ONLY for that one real
   sub-distinction - it's a single coherent screen, unlike main_menu
   vs file_browser which are genuinely different screens), and
   `file_menu_peers.chtpm`. Each declares its own real
   `<module>system/prisc+x pal/main_loop_chtpm.pal</module>` (same
   literal module path in all three, matching this house's own real
   "one shared module per project, branches on current_layout.txt"
   convention, confirmed universal this session) and its own real
   `<interact src="pieces/apps/player_app/interact_relay.txt" />`.
2. Write `&.widgits/file-menu/BROWSER_CONTRACT.md` (or reuse/link
   `102.agy-txt`'s own, adapting the project-specific paths) - the
   gui_state.txt key shape each layout's own dynamic markup will
   target. Keep KEY:n as the encoding (matches prisc+x's own confirmed
   integer-only limitation, jul30-house-refactor.txt §3 - this is not
   up for debate, it's a real VM constraint, not a style choice).
3. Rewrite `fm_compose_frame.c` to build real
   `<button label="..." onClick="KEY:n" /><br/>` rows (one per menu
   item / directory entry), matching
   `101.mutaclsym🧟‍♂️️+18.01/ops/compose_frame.c`'s own

   convention, same real size-suffix formatting, no hand-drawn
   `[>]`/`[ ]` prefixes (the PARSER draws focus/highlighting itself

   `current_layout.txt` (`strstr(layout, "file_menu_browser.chtpm")`

4. Each new layout's own real `<button href="...">` targets the OTHER

## 3. Two additional real findings from THIS session, generically
   applicable here too - check whether they apply, even though they
   surfaced while building 102.agy-txt's NEW native C manager (which
   file-menu does not have, being PAL-driven):

a. **gui_state.txt path is project_id-scoped, not a single universal
   path.** `chtpm_parser_pal.c`'s own `load_vars()` only auto-loads
   `pieces/apps/player_app/manager/gui_state.txt` when `project_id` is
   EMPTY. Any project whose own `state.txt` sets a real `project_id`
   (file-menu's own session state - verify what it sets) gets routed
   through `load_project_gui_state(proj_id)` instead, which checks (in
   order) `projects/<id>/manager/gui_state.txt`,
   `pieces/apps/<id>/manager/gui_state.txt`,
   `pieces/apps/<id>/loader/gui_state.txt`,
   `pieces/apps/<id>/session/gui_state.txt` - NOT the generic
   player_app path. If file-menu's own `fm_compose_frame.c` (or
   whatever ends up writing its new dynamic markup) writes gui_state
   to the wrong path, the symptom is: the RIGHT data is in the file,
   the render just silently never picks it up - no error anywhere in
   file-menu will match this against its own literal path, verify it
   works against a real project_id before trusting it.
b. **`state_changed.txt` vs `frame_changed.txt`.** Pulsing only
   `pieces/display/frame_changed.txt` re-renders the ALREADY-parsed
   element tree (a plain redraw) - it does NOT force
   `chtpm_parser_pal.c` to re-run `parse_chtm()`, which is the step
   that actually re-substitutes a raw `${var}`-as-markup line into
   fresh `<button>` elements. Also pulse
   `pieces/apps/player_app/state_changed.txt` after every real state
   change that should show up in dynamically-generated markup (matches
   `101.mutaclsym🧟‍♂️️+18.01/ops/compose_frame.c`'s own real
   precedent, and TPMOS's own `agy-text-editor_manager.c`'s own
   `trigger_render()` - both already pulse both files).
