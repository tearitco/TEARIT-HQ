## Standing rules for every project in this refactor (established during 01.muchi-pals, apply to 014/044/045 too)

**Never use 'q' as a quit key.** Direct user instruction: "never use q to quit in any of the refactors." A bare letter key doubling as global quit means that letter can never be typed as ordinary content (username, cli_io text, plain nav) without accidentally exiting the game. The working replacement is Ctrl+C (ETX, byte 3) - a real control character that can't collide with typed text - handled directly in `keyboard_input.c`'s read loop (not remapped to 'q' internally, not forwarded into history.txt as ordinary input). Any `chtpm_parser_pal.c`/pal-script code path that also special-cases a literal `'q'`/`'Q'`/`113` keystroke as a second, independent quit trigger must be removed too - it's not just keyboard_input.c's problem. A pal script owning its own quit branch (`beq x2, x9, quit` / `halt`) is also a `xyzos-standards.txt` §9.1 violation independent of this rule ("module must NOT own a quit path") - remove it outright rather than reworking it to key on something else.

**No forced periodic re-render.** A background game-logic tick (e.g. pet metabolism decay) must keep running on its own timer, but must NEVER unconditionally trigger a compose/render afterward. Rendering is marker-driven only (`frame_changed.txt`/`renderer_pulse.txt`/equivalent growing because something actually visible changed) - matches this codebase's own documented principle in `chtpm_parser_pal.c` ("compose_frame() ONLY fires when frame_changed.txt grows... DO NOT add dirty=1... caused triple-rendering") and real TPMOS's own renderer.c ("DO NOT add time-based or event-based render triggers. The marker IS the clock."). Confirmed via direct testing on muchi-pals: a `j render` after every background tick_pets call produced a scroll-spammed redraw every ~3s even at total idle; removing it (falling through to the next loop iteration instead) cut idle frame count from 3 renders/4.5s to 1 render/9s with zero functional loss (the background state still decays, only the forced visible redraw was removed).

**Skip re-printing a frame if its content didn't actually change**, even if the pulse marker grew. Real classic TPMOS's own `renderer.c` (verified by direct read, `1.TPMOS_c_+rmmp.0103.0001/pieces/display/renderer.c`) does NOT diff frames at all - it reprints unconditionally on every marker growth, 5 blank lines + a `--- FRAME UPDATE ---` block + the whole frame, same as this whole project family already does. That's the source of a distinct flicker complaint on muchi-pals ("flicker on nearly every keypress" in scrolling/history mode - fast menu nav produces a visible scroll-jump on every single legitimate render). Direct user decision: keep scrolling/history mode (don't switch to in-place/overwrite mode, which would have fixed it differently by dropping scrollback entirely), and instead have the renderer keep a copy of the last content it actually printed and skip printing (and skip the `frame_history.txt` audit entry) when the new `current_frame.txt` content is byte-identical to that - a marker growing doesn't necessarily mean anything visible changed. This is a genuine addition beyond both `101.mutaclsym` and real TPMOS's own renderer.c, not a port of an existing pattern - apply the same change to the other projects' `renderer.c` (014/044/045 currently use the dual-marker variant per the renderer note below, but the skip-if-unchanged content guard is an orthogonal, independently-worth-applying fix regardless of which marker scheme a given renderer ends up on).

## Renderer pattern conflict — needs a decision before converting `01.muchi-pals`

The three "standard" 101 projects don't agree with each other:
- `101.mutaclsym`'s `renderer.c` watches a single marker (`renderer_pulse.txt`) — **0** occurrences of `should_render`.
- `014.wsr-pal`'s `renderer.c` (already converted per above) uses the dual-marker `should_render` pattern (`frame_changed.txt` + `renderer_pulse.txt`) — **4** occurrences.
- `01.muchi-pals`'s current renderer has neither (0 occurrences, and no flicker fix at all).

**Decision (user, 2026-07-26): `101.mutaclsym` is the most advanced project and is flicker-free — use its single-marker `renderer_pulse.txt` pattern as the canonical reference, not the dual-marker `should_render` variant.** This means `014`/`044`/`045` (which already carry the dual-marker fix) are the outliers, not `101.mutaclsym`. When converting `01.muchi-pals`, port mutaclsym's renderer.c approach directly. `014`/`044`/`045`'s dual-marker renderers should be revisited to align with mutaclsym's simpler pattern rather than treated as already-done.
