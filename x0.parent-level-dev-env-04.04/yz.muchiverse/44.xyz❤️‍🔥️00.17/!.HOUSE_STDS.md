## A. Core CHTPM/PAL mechanics (applies to nearly every project here)

### A.1 The basic shape

Every project in this style has:
- `system/` — shared engine binaries (`prisc+x` the PAL VM, `chtpm_parser_pal` the menu/layout engine, `keyboard_input`, `renderer`, optionally `chtpm_rgb_render`/`gl_mirror` for a GL window). These are almost always **copied** (not symlinked) from a canonical source project into each consuming project — see §A.4.
- `ops/` — project-specific C binaries (compiled to `ops/+x/<name>.+x`) that do real work: read/write state, render content, dispatch commands.
- `pal/*.pal` — tiny PAL scripts that glue ops together in a loop (read a key, dispatch it, compose a frame, sleep, repeat).
- `pieces/chtpm/layouts/*.chtpm` — XML-ish layout files defining screens: buttons, text, substitution variables.
- `pieces/system/`, `pieces/display/`, `pieces/apps/player_app/` — where state, frame buffers, and trigger/marker files actually live.
- `default_op.txt` — registers every op name your `.pal` scripts can call, format: `name type handler {description}`.
- `button.sh` — the launcher; conventionally supports `run`/`build`/`kill`/`check` verbs at minimum.

### A.2 Session isolation

A "session" is `pieces/sessions/<timestamp>-<pid>/` — a fresh, isolated working directory for one running instance.

**HOUSE RULE: NEVER use symlinks anywhere in this tree** — not for session wiring, not for sharing sources/binaries between projects, not for anything. They do not survive Windows checkouts/copies (NTFS copies, zip transfers, non-admin junctions), which is exactly why the 2026-08-20/21 house-wide migration replaced every `ln -s` with a real `cp -r`. If you find yourself writing `ln -s`, stop and copy instead. Sharing is done by compiling from canonical source (`scripts/build.sh` walks up to `&.widgits/_shared-lib`) or by copying files outright.

The current model is **copy-in / persist-out**: at launch, `button.sh` COPIES read-only inputs (`system/`, `ops/`, `pal/`, `pieces/chtpm`, `pieces/registry`, ...) into the fresh session dir, and every genuinely-writable state file/dir gets its own copy-in AND a matching entry in `persist_session_state()`, which on session exit (EXIT/INT/TERM traps, before `rm -rf "$SESSION_DIR"`) copies each listed item back: single files overwrite the real root wholesale; directories merge (`cp -r src/. dst/`); every line is guarded by `mkdir -p` so a fresh checkout can't crash the trap. Consequences:
- A writable file missing from BOTH the copy-in list and `persist_session_state()` silently writes into the ephemeral session dir and vanishes on cleanup. This bug class has recurred across multiple projects both before AND after the migration — always audit `button.sh`'s copy-in + persist lists against every file your ops actually write.
- Binary/source rebuilds do NOT apply live to a running session anymore (they did under the old symlink model) — restart the session after rebuilding.
- Mid-session, real-root state does NOT change; anything reading "current" state mid-run must read the SESSION copy (`$SESSION_DIR/...`), not the project root. Harness scenarios included — several were fixed for exactly this during the migration.

### A.3 The digit-dispatch / numbered-button convention — READ CAREFULLY, a real mistake was made and corrected here

Almost every screen shows numbered items (`[>] 1. Label`, `[ ] 2. Label`...), driven by a `piece.pdl` file with `METHOD | Label | COMMAND` rows. **`resolved_item = (key - '0') - 1` is CORRECT for this dispatch path, not a bug** — this was gotten wrong once this session (a "fix" was briefly applied to civ-txt/tactics-txt's own copies, live-caught as breaking working code, and reverted before being tested/shipped). The reason it's correct: `chtpm_parser_pal.c`'s own `${piece_methods}` button-generator starts its internal `method_idx` at **2**, not 0 or 1 (`method_idx = (loader) ? 1 : 2`, `chtpm_parser_pal.c:1115`) — so the FIRST numbered row's `onClick` becomes `"KEY:2"`, which `send_command()`'s own `"KEY:"` handler turns into the raw ASCII digit `'2'` (not `'1'`) via `inject_raw_key('0'+k)`. `(key-'0')-1` is the correct compensation for that +2 offset: key=`'2'`(50) → `resolved_item=(50-48)-1=1` → `items[0]`, the real first item. **Do not "fix" this in any file whose numbered items are auto-generated via `${piece_methods}`** — that's the standard, dominant case across this house.

**Where the `-1` genuinely IS wrong**: only in code paths that receive a truly raw, literal keyboard digit that never passed through the engine's own `KEY:N` regeneration — e.g. a hand-rolled digit accumulator reading `interact_relay.txt` directly outside the normal numbered-button system (this was real, and fixed, in `board-viewer`'s own now-deleted nav-mode digit dispatch, before that whole mechanism was replaced by the real `onClick="INTERACT"` static button, §D.2 — that code path never went through `${piece_methods}` at all, so the +2 offset never applied there). **Before touching this formula in any file, first determine whether the numbers on screen come from `${piece_methods}` (almost certainly yes, and the `-1` is correct) or from something reading raw keys directly (rare, and only there might the `-1` be wrong).** When genuinely unsure, verify against `chtpm_parser_pal.c`'s own `method_idx` initial value directly, don't assume either direction.

### A.4 Real code over stale docs, always

Doc comments in this house are sometimes wrong/stale — several were found and corrected this session (mutaclysm's own `ops/choice.c` header claimed `'i'`/`'e'` were still live interact/emoji toggles; they'd been removed). **When a doc comment and the actual code disagree, trust the code, verify by direct read, and fix the doc** (standing instruction: "if u need to update stale docs, pls do, no need to have confusion in future agents"). Never assume a comment describes current behavior without spot-checking against the real function it's attached to, especially for anything load-bearing you're about to build on top of.

### A.5 The `[>]`/`[^]`/`[ ]` focus-glyph convention

Numbered/interactive elements render with a 3-char prefix: `[>]` = focused (navigable, not yet active), `[^]` = active/engaged (typing, or a real `onClick="INTERACT"` element currently owns input), `[ ]` = neither. This is drawn **entirely inside the shared `chtpm_parser_pal.c` engine** (`render_element()`), not by any project's own compose op — don't try to reimplement this glyph logic yourself.

### A.6 Marker discipline — what each marker file is for, and what ops may grow (two real bugs from building yahoo-app)

There are three marker files and their purposes MUST NOT be conflated (all live in a project's session `pieces/`):

1. `pieces/display/frame_changed.txt` — the render trigger. Compose ops and menu-input key-tails grow it; this is the **only** marker a compose op should ever touch.
2. `pieces/apps/player_app/state_changed.txt` — **never grow it from any op.** `chtpm_parser_pal.c`'s main loop reacts to ANY growth of this file by re-parsing and calling `sync_focus_from_saved_active_index()`, which restores focus from `pieces/display/active_gui_index.txt`. yahoo-app's ops pinged it on every idle compose AND every dispatched key → every arrow move was silently clobbered back to item 1 within ~1.5s ("arrows don't work"). my-chara-txt never grows it — that's why its arrows always worked despite byte-identical parser code.
3. `pieces/display/<project>_screen_changed.txt` — your own "something changed, re-compose" marker, polled by your PAL module loop. Grow it ONLY from the menu-input op's key-tail when a real action set a message, or from the idle-sync when the active piece id actually changed.

Related, hard-won: **read-KV helpers must strip the trailing `\r\n`** (my-chara's `read_kv_str_local` does `v[strcspn(v, "\r\n")] = '\0'`). A missing strip makes `strcmp(derived, current_target)` fail forever → the idle-sync branch writes the bridge + grows `screen_changed` every tick → the module loop's `beq x7,x8,check_key` never sees an unchanged marker → **relayed Enter keys are never dispatched**. That was yahoo-app's second bug: Enter on "Yahoo Finance (full)" produced no `broker_state.txt`. Fix reference: `@.apps/yahoo-app/ops/yahoo_menu_input.c` + `@.apps/my-chara-txt/ops/mychara_menu_input.c`.

### A.7 Runtime-configurable values in PDL files are always preferred over hardcoded constants

Any value the user may want to tweak without recompiling belongs in a `.pdl` file, not in C source. This includes positions, colors, sizes, labels, and toggles. The house already has working precedents for this pattern:
- `#.desktop/livedesk_theme.pdl` — `COLOR | bg | #000000` / `COLOR | fg | #00ff00`
- `#.desktop/livedesk_shortcuts.pdl` — `SHORTCUT | $ | command`
- `package_dir/meta.pdl` — `STATE | menu_stay_open | 1`, `STATE | grab_pointer | 1`

When adding a new tunable, create or extend the nearest existing `.pdl` rather than inventing a new config file. If no relevant `.pdl` exists yet, place it alongside the other house-wide runtime configs in `#.desktop/` (e.g. `livedesk_taskbar.pdl` for taskbar layout). Follow the existing `SECTION | KEY | VALUE` shape; missing keys must fall back to safe defaults so the binary runs even when the PDL is absent or incomplete.

### A.8 The proven PAL module loop — compose-on-change, relay-poll only when idle (farm/broker_select shape)

This exact shape is the house standard for a menu+module screen (`@.apps/my-chara-txt/pal/farm_module.pal`, copied into `@.apps/yahoo-app/pal/broker_select_module.pal`):

```
li x1, 0
drain:  read_history pieces/apps/player_app/interact_relay.txt x2, x1
        beq x2, x0, drain_done
        j drain
drain_done:
li x9, 0; <op>_menu_input x9; <op>_compose_frame; hit_frame
read_pos x7, "pieces/display/<op>_screen_changed.txt"
loop:
  li x9, 0; <op>_menu_input x9            ; idle-sync, early-returns if piece unchanged
  read_pos x8, "pieces/display/<op>_screen_changed.txt"
  beq x7, x8, check_key                   ; marker UNchanged → poll relay for a real key
  addi x7, x8, 0; j render
check_key:
  read_history pieces/apps/player_app/interact_relay.txt x2, x1
  beq x2, x0, no_key
  <op>_menu_input x2; j render
no_key:  sleep 30000; j loop
render:  <op>_compose_frame; hit_frame; sleep 30000; j loop
```

Never call `<op>_compose_frame` every idle tick — compose only on change (render path) and sync once before the loop. `hit_frame` grows `frame_changed.txt`; `read_history x2, x1` keeps a real byte-position register so each relayed key is consumed exactly once. `default_op.txt` must use `name type handler {desc}` rows (bare path-per-line form silently no-ops every op) — see `@.apps/yahoo-app/default_op.txt`.

### A.9 The `active_index == -1` dual-mode input model — the real reason arrows/digits never collide with camera/game keys

**Real, confirmed via direct source read of `pieces/chtpm/plugins/chtpm_parser.c`'s own `process_key()`** (the original TPMOS reference this whole engine descends from; cross-validated against mutaclysm's own live behavior and docs, 2026-08-30). This is the single mechanism that makes the WHOLE rest of this section's numbered-nav/glyph/digit-dispatch conventions coexist cleanly with a project's own real gameplay input, with zero per-project gating code needed anywhere. Genuinely elegant, easy to reinvent-badly if you don't know it exists — read this before building any new INTERACT-adjacent UI.

**The real branch, verbatim in shape:**
```c
void process_key(int key) {
    if (active_index == -1) {
        /* NORMAL NAV MODE - the ENTIRE rest of this document's own
         * numbered-button/glyph/digit-dispatch conventions live here. */
        if (key == ARROW_UP/DOWN) { move focus_index among navigable elems; }
        else if (isdigit(key))    { jump focus_index to that number (§A.3); }
        else if (key == ENTER)    { activate whatever focus_index currently is; }
    } else {
        /* ENGAGED MODE - the currently-active element owns EVERY key now. */
        UIElement *el = &elements[active_index];
        if (key == ESC) { deactivate, restore focus to whatever it was before; }
        else if (strcmp(el->onClick, "INTERACT") == 0) {
            /* Real arrows remapped to 1000-1003, relayed into whatever
             * <interact src="..."> names - THIS is where a project's
             * own camera/selector movement, and any project-specific
             * "1-4 = camera mode"-style keys, actually come from. */
        }
        else if (strcmp(el->type, "cli_io") == 0) { /* text typing */ }
    }
}
```

**Why this matters, concretely**: `active_index` is a single, real, engine-owned int. It is `-1` until something sets it (a real click/Enter on an `onClick="ACTIVATE"` or `onClick="INTERACT"` element, or Enter on a `cli_io` field) - see §A.5's `[>]`→`[^]` glyph swap, which is literally rendering this same variable. **The exact same physical keys mean completely different things depending on which side of that one boundary you're on** - arrow keys move MENU FOCUS while `-1`, move the CAMERA/CURSOR once engaged; digit keys JUMP-SELECT a numbered menu item while `-1`, become project-specific gameplay keys (e.g. board-viewer's own real `1`-`4` = camera_mode switch, `ops/bv_menu_input.c`) once engaged. **Escape is the real, native, engine-owned way back to `-1`** - a project's own ops never see or handle it for this purpose (confirmed: `&.widgits/interact-fix-widget.txt`'s own investigation record, and `bv_menu_input.c`'s own header comment: "any key that reaches this op AT ALL is already, by construction, genuinely inside real INTERACT/nav mode").

**The real, house-wide `click_two_step` setting is the other half of this** (`#.desktop/hq_ui.pdl`, `g_click_two_step` in `khtpm_core_render.c`, default ON): while in normal nav mode, a digit-press or click on an unfocused numbered item only MOVES focus there (real, visible highlight) - it does NOT activate on the same keypress/click unless `click_two_step=0` is set, or the item has no real nav_index at all. A **second** press/click on the now-already-focused item, or Enter, is what actually activates it. **Any new numbered UI in this house - including a khtpm-native window that reimplements this model locally (see below) - must read and honor this same real flag, not hardcode either behavior.**

**A khtpm-native window that needs to coexist with this model** (a real, live example: `run_pchq_board_mode()` in `khtpm_core_render.c`, piececraft-hq's board window) is its own separate process - it has no direct access to the legacy engine's own in-memory `active_index`. The correct, real pattern (not a guess - implemented and confirmed): **poll the same real state the engine's own `onClick="INTERACT"` click handler persists** (e.g. `pieces/hero_01/state.txt`'s `interact_mode` flag) to know which side of the boundary you're on, and route input accordingly - your own local nav (arrows+digits+Enter, honoring `click_two_step`) for File/Desk/whatever-else while OFF, unconditional forward-everything-to-the-relay while ON, mouse-click-only access to your own local controls while ON (matching the real "keyboard is 100% game input once engaged" contract above). To genuinely ENGAGE the legacy engine's own INTERACT element from outside its own process (a real click/Enter can't be called directly, it's a different process), forward a **synthetic click at the fixed screen position the legacy layout's own INTERACT button always renders at** (real, zero-reimplementation activation - the engine's own native click-hit-testing does the actual state transition, exactly as if a human had clicked it) rather than writing `interact_mode` directly (a raw file write from a separate process races the engine's own next render pass and gets silently overwritten - confirmed by direct read of `set_interact_mode()`/`export_active_index()`, which also update the RUNNING process's own in-memory `active_index`/`focus_index`, not just a file).

## B. The rendering/display pipeline, end to end

Understanding this chain is required before touching any GL-related work — most of the real bugs this session were races or misunderstandings within this pipeline.

```
your compose op (writes text)
  → pieces/apps/player_app/view.txt  (your own raw content)
  → pieces/display/current_frame.txt  (chtpm_parser_pal's own chrome-wrapped composition, substituting ${game_map} etc from view.txt)
      [trigger: pieces/display/frame_changed.txt grown by chtpm_parser_pal.c's process_key() on EVERY key, unconditionally]
      [trigger: pieces/display/renderer_pulse.txt grown by chtpm_parser_pal.c's own internal compose_frame(), also unconditional]
  → system/renderer (ASCII terminal path) — polls frame_changed.txt-equivalent markers, prints current_frame.txt, logs to frame_history.txt
  → system/chtpm_rgb_render (GL path, persistent background daemon) — polls BOTH trigger files above, font-rasterizes current_frame.txt into:
      pieces/display/rgb_frame.raw (raw RGBA32 buffer) + rgb_frame.receipt.txt (frame_w/frame_h/checksum)
      [trigger: pieces/display/rgb_frame_changed.txt grown once a new rgb_frame.raw is ready]
  → system/gl_mirror (real GLUT window) — polls rgb_frame_changed.txt, uploads rgb_frame.raw as a GL texture, blits one quad
      [receipt: pieces/display/gl_display.receipt.txt, for cross-checking source vs. what actually got uploaded]
```

**Key facts that cause real bugs if missed**:
- `chtpm_rgb_render` is a genuinely project-agnostic daemon — it has zero game-state awareness, it just rasterizes whatever text is in `current_frame.txt`. It re-renders on EITHER trigger file growing, and **both grow unconditionally on every key**, regardless of what your own project's ops do or don't call. You cannot suppress this from your side.
- If your own project ALSO writes `rgb_frame.raw` directly (e.g. a custom 3D renderer), you get a real write-write race against this daemon — see §E.1 for the actual fix (write a separate overlay file instead).
- The **receipt + checksum pattern** (`rgb_frame.receipt.txt`'s `frame_w`/`frame_h`/`checksum_fnv1a64`, `gl_display.receipt.txt` for the GL-upload side) is real, working, and load-bearing — `gl_mirror.c` reads its OWN window/texture dimensions from the receipt dynamically rather than hardcoding them, specifically because two different renderers can write different-sized frames to the same path. If you add a new renderer, follow this pattern rather than hardcoding dimensions anywhere downstream.
- **Headless GL verification**: `ops/dump_rgb_png.c` (real, working, in `101.mutaclsym🧟‍♂️️+18.01`) converts `rgb_frame.raw` into an actual viewable PNG — built specifically because an agent can't look at a live GLUT window. Port this (or just do direct pixel-buffer sampling in Python, which is what was actually used this session — see §G) rather than relying on eyeballing a screenshot.

## C. Testing & CPU-safety discipline (standing, non-negotiable)

- **CPU safety is paramount** — this house has crashed from unthrottled idle-poll loops before. Every idle-sync PAL loop pattern uses `sleep <ms>` between poll iterations; never remove that. Every automated test must be `timeout`-wrapped.
- **`timeout` does not reliably kill backgrounded children** of the script it wraps — verify no leftover process afterward (`ps aux | grep yourproject`) and clean up by PID directly (`kill <pid>`) if anything survived. This was a real, repeated issue this session.
- **`pkill` may be sandboxed/blocked** in some environments — every invocation returned a non-zero exit regardless of pattern, including `--version`, in this session's own environment. Use `ps aux | grep` + targeted `kill <pid>` instead of assuming `pkill` works.
- **Never touch the user's own live testing sessions.** If you see `run-widget`/other long-running processes you didn't start, leave them alone — they're very likely the user's own open windows.
- **Cross-session state contamination**: shared (non-session-scoped) state files can get stomped by a stale concurrent session. Kill all stale sessions before every test, or you'll chase phantom bugs that are really just two test runs fighting over the same file.
- **Headless testing technique**: `NO_GL=1 bash button.sh run-app <focus_root>` (or your project's equivalent) gets a real running session with zero display dependency. Inject raw decimal keycodes directly into `interact_relay.txt` (one per line) to simulate exactly what the real engine's key-relay would write — this is how every fix in this document was verified without ever opening a real window.
- **Verifying pixel-level output without a screen**: read the raw RGBA buffer directly in Python (`open(path,'rb').read()`, index by `(y*W+x)*4`), sample known coordinates or scan for known colors. This is real, fast, and was how both a horizontal-mirror bug and an upside-down-camera bug were confirmed and fixed — pure reasoning about the math got both wrong on the first attempt.

## D. Widgets — a separate GL-window program paired to a host project

### D.1 What a "widget" actually is here

A **separate program** (own `system/` binaries, own GL window, own PAL/CHTPM session) that:
- gets spawned by a host project via a real OS process (`setsid ... button.sh run-widget <host_project_root> &`), passing the host's real project root as a focus argument — **not** a same-session screen/view change inside the host's own CHTPM layout (that was a real, corrected architecture mistake early in this house's own history building this — `@.apps/BOARD_WIDGET_ARCHITECTURE.md` §0).
- reads the host's own real files directly (e.g. `board.txt`) for real-time sync — no new IPC needed, just knowing which root to read.
- renders as ASCII (headless/no-DISPLAY fallback) or a real GL window (default when `$DISPLAY` is set).
- `setsid` is required when spawning — plain `system(cmd) + &` does NOT create a new process group, so a `timeout` wrapping the HOST project's own test run can cascade-kill a supposedly-independent widget process.

### D.2 Nav mode — the real mechanism, do NOT reinvent it

`onClick="INTERACT"` is a **reserved string** the shared `chtpm_parser_pal.c` engine special-cases entirely inside itself — NOT something reachable via a dynamically-generated `piece.pdl` METHOD row (those always become `onClick="KEY:N"`, confirmed via direct code read of the engine's own button-generator; only a small whitelist of literal parser commands like `LOAD_PROJECT:`/`BACK`/`RELEASE` are exceptions, and `INTERACT` isn't one of them). It must be a real, hand-written `<button onClick="INTERACT">` in the `.chtpm` XML itself:

```xml
<panel time_reactive="true">
    <module>system/prisc+x pal/main_module.pal</module>
    <interact src="pieces/apps/player_app/interact_relay.txt" />
    <button label="Nav Mode (camera + selector)" onClick="INTERACT" /><br/>
    <text label="${game_map}" /><br/>
    ${piece_methods}
</panel>
```

Once engaged, the engine itself: sets its own internal `active_index` (nothing for your op to track), relays raw keys (arrows remapped to sentinel 1000-1003) into whatever your `<interact src>` names, consumes ESC itself before your op ever sees it, and flips the `[>]`/`[^]` glyph automatically. It also exports `pieces/display/active_gui_is_typing.txt` (`"1"`=active,`"0"`=not) for your own status display — read this, don't invent your own flag. **Consequence**: your own menu_input op needs almost no gating logic — it's only ever invoked with camera/arrow codes while genuinely inside real nav mode, by construction. Full investigation: `&.widgits/interact-fix-widget.txt`.

### D.3 Scaffolding — copy `board-viewer`'s shape

```
your-widget/
  button.sh                # two profiles: run-app (ASCII/headless), run-widget (GL)
  default_op.txt            # registers your project's own ops
  scripts/build.sh           # compiles ops, copies system/ binaries
  ops/
    yourwidget_compose_frame.c
    yourwidget_menu_input.c
    yourwidget_render_3d.c     # only if doing a 3D view
  pal/main_module.pal
  pieces/
    chtpm/layouts/yourwidget.chtpm
    registry/fonts/ascii/       # copied from wsr-pal
    registry/emoji_assets/      # real voxel textures, see §E.3
  projects/your-widget/pieces/<piece_id>/   # holds the dynamically-regenerated piece.pdl
```

`scripts/build.sh`: copy (never symlink) `system/prisc+x`, `chtpm_parser_pal`, `chtpm_rgb_render`, `keyboard_input`, `renderer` from `014.wsr-pal💸️📌️+2/system/` — **wsr-pal's own `chtpm_rgb_render` already has BOTH the generic on-demand emoji-generation feature AND the `MAP3D_MARKER`/overlay-compositing feature needed for a 3D view (§E.1)**. Do NOT swap this for mutaclysm's own fork — mutaclysm's copy has zero on-demand emoji generation (it only recognizes emoji hand-curated from its own registry files, which won't exist in your project), and swapping to it silently breaks 2D emoji rendering entirely. This was a real, live-caught regression this session — an earlier research pass incorrectly concluded wsr-pal's copy lacked overlay support; it does not, verify directly with `grep -n "blit_overlay\|MAP3D" system/chtpm_rgb_render.c` before believing otherwise. `gl_mirror` also comes from wsr-pal (real `interact_relay.txt` key-forwarding; mutaclysm's own copy is mirror-only, no forwarding). Also copy `ops/+x/emoji_gen_atlas.+x` + `emoji_xtract.+x` from wsr-pal (§E.3).

## E. The 3D view — three real, separate pieces

### E.1 Avoiding the rgb_frame.raw race

If your own 3D-render op writes `pieces/display/rgb_frame.raw` directly, it races `chtpm_rgb_render`'s own unconditional re-render (§B) — a real, live-caught bug (3D frame briefly shows, then reverts to stale 2D content within ~30ms). **The fix**: your 3D op writes to a SEPARATE file — `pieces/display/rgb_frame_3d_overlay.raw` + `.receipt.txt` (format: `overlay_w=%d\noverlay_h=%d\n`, no checksum) — and never touches `rgb_frame.raw` at all. `chtpm_rgb_render` watches for a single `0x01` (SOH) byte as a line's first character in `current_frame.txt`; on finding it, composites your overlay in at that row, then skips `ceil(overlay_h/GLYPH_H)` further source lines. Your own 2D compose op must therefore emit, only while `render_mode==1`:
```c
fputc(0x01, out); fputc('\n', out);
for (int i = 0; i < N; i++) fputc('\n', out);  // N = ceil(overlay_h_px / 16), MUST match your 3D op's own overlay height
```
Keep this constant in sync manually between the two files — no shared-header convention in this house's self-contained-ops style, so this is a real, easy-to-silently-break invariant; comment it loudly in both files, pointing at each other.

### E.2 Camera controls — full key scheme (ported from mutaclysm's `ops/camera_control.c`)

| camera_mode | q/e (yaw) | r/t (pitch) | w/a/s/d (pan) | c/v (z-level) | f (reset) |
|---|---|---|---|---|---|
| 1 — first person | ±10° | ±10°, clamp[-89,89] | ❌ locked to anchor | ❌ | yaw=180,pitch=6 |
| 2 — third person | ±10° | ±10° | ❌ locked to anchor | ❌ | yaw=180,pitch=6 |
| 3 — free roam | ±10° | ±10° | ✅ pans z/x | ✅ | pan=0,yaw=180,pitch=-90 |
| 4 — bird's-eye | ❌ no-op | ❌ no-op | ✅ pans y/x, ABSOLUTE coords | ✅ | pan **centers on your anchor/selector**, NOT (0,0) |

`'0'` toggles `render_mode` (bidirectional). `'1'`-`'4'` switch `camera_mode`, only while `render_mode==1`. **Real bug already fixed**: mode 4's default/reset pan must center on your widget's own selector position (matching where the 2D view starts), not `(0,0)` (the board's corner) — both the `'1'-'4'` switch handler and your render op's own read-side default need this.

### E.3 Camera basis math — two empirically-verified branches, do not collapse to one formula

```c
Vec3 dir = { cos(pitch)*sin(yaw), sin(pitch), cos(pitch)*cos(yaw) };
forward = normalize(dir);
Vec3 right, up;
if (fabs(forward.y) > 0.999) {                 // near-vertical (bird's-eye-like)
    Vec3 fallback_up = { 0, 0, 1 };
    right = normalize(cross(fallback_up, forward));
    up    = normalize(cross(right, forward));
} else {                                        // general/near-horizontal (FPS-style)
    Vec3 world_up = { 0, 1, 0 };
    right = normalize(cross(world_up, forward));
    up    = normalize(cross(forward, right));
}
```
Two earlier single-formula attempts each fixed one branch while silently breaking the other (a horizontal mirror in one case, upside-down in the other) — this is a well-known top-down-vs-forward-facing camera convention ambiguity, not something you can derive correctly by pure algebra. **Verify empirically** (§C, controlled test board with asymmetric corner markers + direct pixel sampling) before trusting any camera math, including this, if ported to a different coordinate convention.

### E.4 Real raymarching, not a rasterizer

A **rasterizer** (project 3D geometry to screen space, sort back-to-front, fill polygons with solid colors) is fundamentally different from, and visually inferior to, real raymarching — and was explicitly rejected in this house once asked directly ("did we do the real raymarching or cheat?"). **If asked for "real 3D" or "like mutaclysm," build the raymarcher.** Real raymarching = a per-pixel loop casting a ray through 3D space, testing it against actual geometry via an Amanatides & Woo grid-DDA walk, sampling real texture data at the hit point. Port these four pieces verbatim from mutaclysm's `ops/compose_rgb_frame.c`:
1. **`ray_aabb_hit_3d()`** — slab-method ray/box intersection, self-contained.
2. **`box_face_uv()`** — hit point + face index → 2D texture UV.
3. **`get_voxel8_cached()`/`sample_voxel8_pixel()`** — real voxel-texture CSV loading/sampling (resolution-agnostic despite the "8" in the name; size your pixel buffer for your assets' actual resolution).
4. **The DDA loop** — per pixel, `ray_dir = normalize(forward + right*a + up*b)` where `a=(sx-W/2)/focal, b=(H/2-sy)/focal`, then Amanatides & Woo grid-step testing `ray_aabb_hit_3d` per cell until first hit.

This house's own board-viewer simplified mutaclysm's floor-pass/wall-raymarch split into ONE unified per-cell AABB test (thin slab for flat/water terrain, real tall box for raised terrain) — reasonable if your terrain model is "one scalar height per cell," not mutaclysm's richer walkable/furniture registry. **Performance**: a 640×480 per-pixel raymarch against a ~14×14 board rendered in ~70ms — fast enough for every idle tick; verify your own timing before assuming this holds at a different scale.

### E.5 Real textures via the on-demand emoji-voxel pipeline — don't hand-pick colors

`system/chtpm_rgb_render.c` (wsr-pal's copy) has a genuine, working "GENERIC ON-DEMAND EMOJI GENERATION" path: any unrecognized UTF-8 codepoint gets shelled out to `ops/+x/emoji_gen_atlas.+x <emoji> <tmp.png>` (real FreeType + `NotoColorEmoji.ttf`) then `emoji_xtract.+x <tmp.png> 0 16 <csv>`, cached forever at `pieces/registry/emoji_assets/<hex-codepoint>/voxels_16.csv`. If your 2D compose op emits real emoji per terrain type, those exact voxel assets are already on disk by the time you build a 3D view — point your raymarcher's texture sampler at the same hex-codepoint path your 2D glyph-mapping uses, and 2D/3D show consistent textures for free. Also check `101.mutaclsym🧟‍♂️️+18.01/pieces/registry/emoji_assets/` for existing hand-curated assets (`t_grass`, `t_tree`, `t_water_dp`, `hero`, `zombie`, `xlector`, etc.) worth reusing directly.

1. **A dynamically-generated piece.pdl METHOD row can never trigger `onClick="INTERACT"`.** §D.2.
2. **`(key-'0')-1` is CORRECT for standard `${piece_methods}` numbered dispatch — do not "fix" it there.** §A.3 has the full, corrected writeup after a real mistake was made and caught this session. Only reading raw keys OUTSIDE that system needs the plain `key-'0'` form.

### F-18 report — the CWD-relative-command trap (taskbar HQ restart, 2026-08-08)

**Symptom**: HQ `$.restart` on the livedesk taskbar did nothing (windows never relaunched), while `sh button.sh r` from `$.crypts/` worked, and the `asa&ava` buttons were never actually hardcoded — they spawned fine. The trap is invisible to any sweep that greps for old absolute-path strings (`NNEST-11.15`, `00.10`, `00.11`, …): `$.crypts/button.sh` contains NO absolute house path at all, so a stale-path grep can never flag it. That is exactly why a "find all hardcoded paths" pass missed it.

**Mechanics**:
1. `tp_taskbar` (like every child crypt_autostart spawns) inherits the CWD its launcher had. Launched from `$.crypts/` (the documented `sh button.sh r` invocation site), the taskbar's CWD was `.../44.xyz❤️‍🔥️00.16/$.crypts`.
2. The HQ menu command in `#.desktop/livedesk_taskbar.pdl` is `setsid nohup $.crypts/button.sh run` — house-*relative*, resolved by `system()` from the taskbar's CWD.
3. `$.crypts` + `$.crypts/button.sh` = `$.crypts/$.crypts/button.sh` → missing file. `system()` returns nonzero; the taskbar swallows the rc (`(void)rc;`) and stderr goes to /dev/null → perfectly silent.

**Fix applied**: `tp_taskbar.c main()` now `chdir(house_root)` immediately after reading `argv[1]` (all its file paths are already `house_root`-joined, so the chdir is safe). Any relative command in the taskbar's PDL now resolves against the house root no matter where the binary was launched from.

**Standard to follow** (this is the rule, not the exception):
- Any process that executes PDL/user-configured command strings via `system()` must anchor relative tokens to `house_root` (resolve the first token against it, or `chdir(house_root)` at start). Never rely on inherited CWD.
- A stale-path sweep must ALSO check for *relative* indirection targets (`.crypts/`, `button.sh`, `ops/+x/...` invoked without a leading house-root anchor) — not just absolute old-path strings.
- Verify launch-path bugs empirically: `readlink /proc/<pid>/cwd`, then resolve the command's first token from that CWD.

### F-19 report — override-redirect popup keyboard focus under Mutter/XWayland (livedesk taskbar submenus, 2026-08-09)

**Symptom**: HQ menu and strip-button submenu popups (`&.widgits/livedesk-taskbar/ops/tp_taskbar.c`) opened and drew correctly (real windows, real content, real `[ ]`/`[>]` cursor at row 0), but arrow keys and digit keys typed while a popup was open did nothing — the focus cursor never moved, Enter/Escape never fired. Looked exactly like a logic bug in the popup's own key-handling code on first read.

**How it was actually diagnosed** — NOT by reading code harder, by building a real, repeatable test harness:
1. Confirmed the environment first (`$XDG_SESSION_TYPE=wayland`, `loginctl show-session ... -p Type=wayland`, `ps aux` showing `gnome-shell` + `/usr/bin/Xwayland :0 -rootless ... -auth /run/user/1000/.mutter-Xwaylandauth.*`) — this IS a Wayland session with X11 clients running through Xwayland, not a bare X11 session with a standalone compositor.
2. Built a small standalone XTest-based key/click injector (`XTestFakeKeyEvent`/`XTestFakeButtonEvent`/`XTestFakeMotionEvent`) that tails a plain text file (`#.desktop/tp_taskbar_debug/key_inject.txt`, lines like `KEY_PRESSED: Down` / `CLICK: <x> <y> <button>`) and translates each line into a REAL X11 event targeted at the running taskbar — genuinely indistinguishable from physical input to the receiving client, since XTest injects at the X server level, not by faking anything client-side.
3. Added temporary `fprintf(stderr, ...)` tracing directly in the popup's `KeyPress` handler AND right after the focus-request call (logging both the *requested* focus window and what `XGetInputFocus` reported *actually* got focus).
4. Injected a real click to open the popup, then a real `Down` key via the injector. Result: `XGetInputFocus` reported the popup window as focused (looked correct), but the `KeyPress` handler's own trace line never printed at all — the key event genuinely never arrived at the process for that window, despite the X-protocol-level focus claim reporting success.
5. Recalled that `taskbar_soft_focus()` (`XRaiseWindow` → `XSetInputFocus` → `XFlush`) was ALREADY proven working earlier the same session for the taskbar's own main strip window, confirmed via the exact same injector + a separate frame-history log showing real focus-index movement. The popup's own focus code called bare `XSetInputFocus` with no preceding `XRaiseWindow`.
6. Switched the popup's focus call from bare `XSetInputFocus`+`XFlush` to `taskbar_soft_focus()` (the same proven helper, not a new mechanism). Re-ran the exact same injector test: the `Down` key now correctly moved the popup's focus row (confirmed via the popup's own per-frame draw log, `popup_frame_log.txt`, showing `focus_row` change from 0→1 between two consecutive frames).

**Root cause, as far as confirmed**: this Mutter/XWayland environment does not reliably route real (or XTest-injected) keyboard input to a brand-new override-redirect window on bare `XSetInputFocus` alone, even though the X11 protocol-level focus state (`XGetInputFocus`) reports the request succeeded. An `XRaiseWindow` call immediately before the focus request was sufficient to fix it for this case — NOT independently re-derived as a general Mutter rule, just empirically confirmed to work here, twice (main window originally, popup window this session).

**Standard to follow**:
- Never trust `XGetInputFocus` alone as proof a window will actually receive keyboard input under this environment — it can report success spuriously. Verify empirically with real (or XTest-injected) key events and a visible state change, not just the focus-getter call.
- Any new override-redirect window in this house that needs real keyboard input (menus, popups, tooltips-with-input) should raise-then-focus-then-flush, matching `taskbar_soft_focus()`'s proven sequence — don't reach for `XGrabKeyboard` or another untested mechanism as a first move when an existing, working pattern already exists in the same file/project.
- When a keyboard-input bug is genuinely invisible from code review (this one was — the popup's key-handling logic itself was completely correct), stop reading code and build a real, repeatable injection-based test harness instead of guessing further. A small XTest key/click injector (tail a text file, translate lines to `XTestFakeKeyEvent`/`XTestFakeButtonEvent`) is cheap to build, reusable across this whole family of raw-Xlib programs, and gives a genuine, scriptable substitute for a human's eyes/hands — not just for this one bug.

**Addendum, 2026-08-10 — XTest injection has a real cost this section didn't originally flag: it requires GLOBAL X input focus.** `taskbar_soft_focus()` (the very sequence this section recommends) actively steals real focus to make injection land reliably — which works, but conflicts with a real human using the SAME display at the same time. Their mouse click or window switch mid-injection-sequence silently redirects the next synthetic key to the wrong window, no error, no crash — looks exactly like an app bug (a fresh multi-hour investigation this session provisionally diagnosed as a `cell_for_nav()`/index-mismatch bug before this focus-contention explanation was found and confirmed). **For agent-driven testing/control specifically (not diagnosing genuine human-input focus bugs like the one this section documents), prefer a file-relay polling loop instead of XTest injection** — see `_.0.aigent-testing-k9.txt`'s 2026-08-10 SCOPE update and `poll_agent_relay()`/`agent_relay_dispatch()` in `tp_taskbar.c` for the first real implementation. XTest injection remains the right tool for what THIS section is actually about — diagnosing/regression-testing the app's own real keyboard-focus handling — just not for routine agent task automation anymore.

If a user can navigate the main window with digits/arrows, they should be able to navigate anything opened from it the same way, with zero exceptions.

22a. **THE REAL bracket-badge format, verified against the actual reference implementation (do not trust any other doc's paraphrase of this, including an earlier version of #22 above): the bracket holds ONLY the state glyph, the number is a SEPARATE suffix drawn AFTER the closing bracket with a trailing period.** Ground truth, checked directly: `1.TPMOS_c_+rmmp.0103.0001/projects/wraith-alpha/ops/wraith_parser_alpha.c` lines ~2221-2224 (`pref` = `"[^]"` and `"[>]"` and `"[]"` and `"[ ]"` - literally just the 3-char bracket, nothing else) and line 2283 (`asprintf(&line, "%s%d.[%s]", pref, display_num, trimmed_label)` - the number and its trailing `.` come AFTER `pref`, outside the bracket). So the real composed shape is **`[>]1.`** / **`[ ]2.`** / **`[^]3.`** (bracket, then number, then period) — **NOT** `[>1]` / `[ 2]` / `[^3]` (number inside the bracket). Real bug, live-caught (2026-08-12, direct correction: "db-hq and hai are using nav index in not quite the std the std is [].<#> not [<#>]"): every khtpm/-hq window built this session (`khtpm_hq_render.c`/db-hq, `khtpm_events_hq_render.c`/events-hq, `khtpm_open_hai_render.c`/h-ai) had this wrong the entire time — the WRONG format even got written into #22's own text above as if it were the standard, which is exactly how this kind of drift compounds. Fixed in all three files (`snprintf(badge, ..., "[%c]%d.", ...)` pattern, not `"[%c%d]"`). **Any future khtpm/-hq window: copy the fixed `draw_badge()`/badge-`snprintf` line from one of those three files directly, don't retype the format from memory or from a doc's prose description — verify against the real source cited above if in doubt.**

23. **A real entity's portrait/avatar should be loaded from its own real `sprite.csv` (raw RGBA pixel dump, `# resolution=N` header + N×N `r,g,b,a` rows, one pixel per row in row-major order), NOT rendered via an emoji font.** Real, live-caught (2026-08-12, building events-hq): rendering an entity's `glyph.txt` emoji (e.g. 🥷) via Xft + "Noto Color Emoji" hit a genuine X server bug - `BadLength` on `RenderAddGlyphs` (the RENDER extension request for uploading that glyph's bitmap data exceeds some server-side limit) - and silently drew nothing, at multiple font sizes tried. The entity's REAL portrait already exists as `sprite.csv`, sibling to its `event_pkg/` dir, parsed by `01.muchi-pals-🥚️-13.01/system/egg_window.c`'s own `load_sprite()` (the function that already renders this exact entity on the live desktop) - reuse THAT parser (studied and ported line-for-line, not guessed) instead of reaching for a font. Since Xlib has no alpha compositing of its own, blend each pixel's alpha against the target panel's own known solid background color before `XDrawPoint`-ing it (see `khtpm_events_hq_render.c`'s `draw_entity_glyph()`) - fine for a small icon-sized target box (nearest-neighbor downscale from the source resolution), would need real compositing (an `XImage`/`XPutImage` blit) for anything larger.

24. **Any new raw-Xlib program should install a non-fatal `XSetErrorHandler` from the start, before it's needed.** Real, live-caught (2026-08-12): the emoji-font bug in #23 above triggered a real X protocol error that, by Xlib's own default handler, calls `exit()` and kills the WHOLE process over one decorative icon draw call. A custom handler that logs (`XGetErrorText`) and returns 0 instead of exiting means one bad request degrades gracefully (that single draw silently fails) rather than crashing an otherwise-working app. Cheap, general hygiene - add it to `main()`'s very first line, don't wait until something like #23 forces the issue.

25. **Scripts that depend on external asset paths (mounted volumes, NFS shares, USB drives) must validate they exist at runtime and either auto-mount or print a clear error message — never silently fail.** Real, live-caught (2026-08-12): book-stack's bible-text branch looked for verse content in `/media/no/b7ced73c-5231-4462-b98d-64e38fe2df9e/...`, a mounted external drive. When the drive wasn't mounted, the script silently fell back to a "binary missing" error message and showed no content, leaving the UI completely broken with no clue that a mount was missing. Symptom appeared as a rendering failure (window opened, text didn't display), not an environmental issue. **Fix pattern**: before `cd` into an asset directory that might not be mounted, check `test -d "$PATH" || exit 1` with a clear error message like `"ERROR: bible assets not found at $BIBLE_ROOT (is the drive mounted?)"` sent to stderr — let the error surface rather than cascading into silent empty content. If auto-mounting is possible in this environment, do it before the first check. **For any app shipping as a multi-machine installable product** (§I.17 reference), this exact failure class becomes critical — users won't have access to development workstation asset paths at all, so validate asset presence on startup, not during first use.

## H. The visual event compiler (event-ez/prisc+x) — real, hard-won lessons (2026-08-05)

Written building MUCHI_RANCHER's real "Show Choices"/"Change Gold" event commands through `event-ez`, authored via genuine k3 key injection (not hand-authored files) end to end. Applies to any project compiling a visual/GUI-authored script down to a real, executable `.pal`.

### H.1 `prisc+x`'s real `exec` opcode supports exactly ONE literal argument

Confirmed via direct source read (`system/prisc+x.c`, the `exec` parse branch) — a THIRD token (a second literal arg beyond the command path itself) is parsed but **silently discarded**; only a register value (`rN`/`xN`) is honored as a second arg, never a second literal string. The file's own comment already says so: *"a script needing 2 literal args should shell to a wrapper script that takes one literal arg and does its own further dispatch, matching every op-calls-op pattern already used family-wide."*

**Real, live-caught consequence**: a compiled `event.pal` line like `exec <op> <arg1> <arg2>` parses without error, `prisc+x` exits 0, but the op **never actually runs** — no crash, no stderr, just silent no-op. This is a nasty, unhelpful-feeling failure to debug UNLESS you already know the 1-literal-arg limit; verified by literally running the compiled `.pal` and finding no downstream state changed, then re-reading `prisc+x.c`'s own `exec` parser line by line.

**The fix, exactly as the code's own comment prescribes**: any real command needing 2+ literal arguments must compile to a real, tiny generated wrapper shell script (`chmod 755`, one per command instance, e.g. `page_dir/cmd_<id>.sh`) containing the full real command line baked in, with the `.pal`'s own `exec` line calling that wrapper with zero extra args. See `&.widgits/event-ez/ops/ez_menu_input.c`'s own Change-Gold compile step for the working reference implementation.

**Always literally run a freshly-compiled `.pal` before declaring the compiler done** — reviewing the generated text is not enough; this exact bug looked completely correct on inspection.

### H.2 `${var}` naked-substitution is a snapshot at `href`-commit time, not a live binding

`chtpm_parser_pal.c`'s own `parse_chtm()` (which performs `${var}` substitution) only re-runs when `active_target_id`/`piece_methods`/`input_text` change, OR on an explicit `href` commit (which calls it unconditionally, synchronously, in-process). A SEPARATE process (your own compose op, invoked by the PAL loop) writing a fresh `${var}` value into `gui_state.txt` **after** that commit does not itself trigger a re-parse — nothing watches `gui_state.txt` for the purposes of re-substitution. The result: dynamic, gallery-style content computed by an external op is **one render behind** on first navigation into a fresh screen — looks like a real render bug (content missing/duplicated) but is actually a benign race between two independent processes.

**The fix, matching the pattern this house already uses for pre-generating reachable `.chtpm` files**: precompute EVERY dynamic value a screen might need, **keyed per-target** (e.g. `command_list_rows_3`, not a single shared `command_list_rows`), at the moment the PARENT screen (the one whose click leads there) composes — never at the target screen's own compose time, which is provably too late for the very first render. See `&.widgits/event-ez/ops/ez_compose_frame.c`'s `build_command_list_rows()`/`compose_gallery()` for the working reference.

### H.3 Non-atomic `gui_state.txt` writes are a real, live-reproducible race

A plain `fopen(path, "w")` truncate-in-place, written by a process a SEPARATE, concurrently-polling process reads (`chtpm_parser_pal`'s own `load_vars()`), can be caught mid-truncate — same class of bug as any shared state file in this house, but easy to forget for `gui_state.txt` specifically since it "feels" like a private compose-op scratch file. **Always** write-to-`.tmp`-then-`rename()`, same as every other shared state file convention (`#.desktop/livedesk_*.txt`, etc). Symptom when unfixed: intermittent, non-reproducible-feeling duplicated or missing dynamic content — looked identical to §H.2's bug on the surface, was a genuinely separate, second real bug found in the same investigation.

### H.4 CPU/process safety, reinforced with a real, concrete failure mode

Beyond §C's existing rules — a specific, repeatedly-hit trap this session: **every `gl_mirror` window opened by this house's own event/CHTPM widgets shares the literal window title `"mutaclsym RGB mirror"`.** If more than one session is alive at once (very easy — a backgrounded `button.sh run-widget &` whose `trap ... EXIT` cleanup didn't fire, e.g. because the launching shell itself was backgrounded/disowned, or a hard crash), any name-substring key-injection tool (`tp_test_send_key.+x` and similar) has **no way to tell the windows apart** and may silently send real keystrokes to a stale, unrelated session — producing confusing, seemingly-random "wrong navigation" results that are actually just testing the wrong window. This cost significant real debugging time this session before being identified as a test-hygiene issue, not a product bug.

**Standing discipline, now mandatory before ANY k3-injection test of a CHTPM/GL session**:
1. `ps aux | grep -E "chtpm_parser_pal|gl_mirror|prisc"` — confirm zero stray processes before launching.
2. `xwininfo -root -tree 2>/dev/null | grep -c "<window title>"` — confirm exactly 1 after launching, before sending any keys.
3. `timeout <N>` wrap every test launch as a hard backstop, even when you intend to clean up manually.
4. After a real crash (not just end-of-test), don't assume state is clean — re-run both checks above before continuing; a reboot naturally clears everything, but a soft crash/OOM may not.

## J. TWO SEPARATE PARSER FAMILIES, both called "chtpm" — real, unmerged duplication (found 2026-08-15)

**Read this before assuming a `.chtpm`/CSS feature exists, or that "the chtpm parser" means one specific codebase.** This house has **two independent C implementations** that both read `.chtpm`-tagged layout files, and they have real, confirmed feature drift between them — not a hypothetical risk, concrete gaps found live this session.

### The two families
1. **Legacy `chtpm_parser_pal.c`** (§A above is entirely about this one) — the PAL-VM-based engine (`prisc+x`), text-grid rendering (`render_element()`), `${piece_methods}` numbered-button generation, `onClick="INTERACT"` special-casing, the `[>]`/`[^]`/`[ ]` glyph convention drawn by the shared engine itself. Canonical source: `014.wsr-pal💸️📌️+2/system/`. Used by widgets/apps built on the `pieces/chtpm/layouts/*.chtpm` + PAL scripting model (`&.widgits/*`, `@.apps/*`).
2. **The newer `khtpm_*` family** — raw Xlib/Xft rendering (no PAL VM, no `prisc+x`), its own from-scratch CSS-subset parser (`khtpm_css_parser.c`), its own `.chtpm` XML tag vocabulary parser (per-app, e.g. `chat_hai_hq_render.c`'s own `parse_chtpm()`), its own wraith-alpha-derived nav-index convention (`[>]N.` badges, digit-jump). Used by the taskbar (`khtpm_strip_parser.c`/`khtpm_taskbar_manager.c`) and every `-hq`/tb-launched sub-app - as of 2026-08-17, db-hq/events-hq/chat-hai (plus entity-menu/taskbar-settings) all now live in ONE shared binary, `*.livedesk-taskbar/ops/khtpm_core_render.c` (mode-selected, see `au11-hq/khtpm-merge-how2.md` Stage 5). `khtpm_open_hai_render.c` (open-hai) stays its own separate file, not part of that merge. See `khtpm-refactor-plan.md` (Index item 16) for the original, pre-merge architecture comparison - historical now, not the current file layout.

**These are not two views onto the same engine.** They are separate codebases that happen to share a file-format name and superficial tag vocabulary (`<window>`, `<button>`, `<panel>`, `onClick=`). A `.chtpm` file written for one is not portable to the other, and a feature working in one implementation tells you nothing about whether it works in the other.

### Real, confirmed drift found this session (chat-hai work, 2026-08-15)
- `khtpm_css_parser.c` does not implement `display`/`position`/`flex`/`flex-direction` at all — parsed into the rule table but never consulted by any layout code (`selector_tier_match()`/`css_compute_style()` only ever resolve color/font/padding/border/width/height). A `.css` file written assuming real flexbox (chat-hai's own `chat-hai.css` did, originally) silently does nothing; real layout in this family is 100% hand-rolled pixel math in each app's own `layout_pass()`. `chtpm_parser_pal.c`'s own layout model (text-grid, no CSS box model at all) doesn't have this problem because it never promised CSS in the first place — a DIFFERENT kind of layout altogether, not a subset/superset relationship.
- `khtpm_css_parser.c`'s selector matching supports a bare tag, one compound class chain (`.foo.bar`, same element), or an id — but NOT descendant/ancestor combinators (`.foo .bar`, space-separated). A selector like `.sessions .data-item` silently matches nothing, ever, no warning — real, live-caught bug (chat-hai's session sidebar rendered black-on-black for this exact reason, see `chat-hai-design.md`'s own session-2 writeup for the full incident). `chtpm_parser_pal.c` has no equivalent CSS selector system to compare against — again, a different mechanism, not directly portable intuition either direction.
- Taskbar menu items (`khtpm_taskbar_manager.c`'s `livedesk_build_ai_menu()` etc.) are C-hardcoded despite matching `.pdl` rows existing and looking live (see `TASKBAR-MENU-ARCHITECTURE.md`, Index item 18) — a real regression FROM a config-driven design back to hardcoded C, within the `khtpm_*` family itself, independent of the two-family split above but the same genre of "assume nothing, verify the actual code path" lesson.

### Standing direction: these are meant to be merged
Multiple docs (`khtpm-refactor-plan.md`, `!.chtpm-render-dedup-guidance.md` at house root) already flag renderer/parser duplication as a known, deferred consolidation target — this is not a new observation, but the concrete evidence above (real, user-visible bugs directly caused by the split, not just "duplicated code smell") makes the case sharper than it was when those docs were written. **Do not casually assume the two families share behavior, bug fixes, or feature support just because they share a file extension and superficial tag names.** When a `.chtpm`/`.css` feature doesn't work as expected in a `khtpm_*`-family app, check that family's OWN parser source (`khtpm_css_parser.c`, the app's own `parse_chtpm()`) before assuming it's a usage bug — it may simply not be implemented there, regardless of whether `chtpm_parser_pal.c` supports the equivalent concept.

**For a new agent working on ANY taskbar sub-app** (cell 6/db, 14/h-ai's chat-hai, events-hq, open-hai, or a new one): you are in the `khtpm_*` family, not `chtpm_parser_pal.c`'s. Section A of this document (CHTPM/PAL mechanics) does **not** apply to you — read `TASKBAR-MENU-ARCHITECTURE.md` instead for taskbar-side dispatch, and read the specific `khtpm_*_render.c` file you're extending (or the closest existing one, e.g. `khtpm_open_hai_render.c` for a new persistent tb-launched window) for the real, current rendering/layout/nav-index conventions — don't assume anything from §A carries over.

**Real merge work is NOT done this session** — this section documents the drift and the standing direction, it doesn't resolve it. A real merge would mean either (a) porting `khtpm_*`'s real, working feature set (window-standard chrome, nav-index badges, relay/agent-testing hooks) into `chtpm_parser_pal.c` and retiring the newer family, or (b) building out `khtpm_css_parser.c` into a real box-model/flex engine and formally deprecating direct pixel-math `layout_pass()` implementations across the `khtpm_*` apps — a real architectural decision for a future session, not something to attempt inside a feature-shipping task.

Real standing rules for ANY future khtpm/chtpm work in this house:
1. **Don't create new in-house `.h` header files.** `khtpm_css_parser.h` is pre-existing/grandfathered, not a license to add more. If real code (a struct + functions) needs to be shared across multiple standalone `.c` files with zero header, the mechanism is a direct `#include` of a plain `.c` file (see `&.widgits/_shared-lib/khtpm_render_core.c`'s own header comment for the worked example) — functions stay `static` so each consumer's text-include keeps them private to that binary, same effective result as hand-duplication, just from one real source.
2. **The real end state for same-shaped `khtpm_*` apps is a shared GENERIC SHELL binary + a separate per-app MANAGER binary for business logic — NOT one binary containing everything, and NOT N binaries each doing both rendering and business logic (today's shape).** Corrected same day after a first wrong guess ("one binary, fully data-driven") — direct question: *"is there a reason it includes the code instead of how chtpm tpomos does and calls the code as a `<module>` thru layout? did u miss this?"* Real finding: `<module>` in a `.chtpm` layout is a **runtime child-process launch** (`launch_module()` in `wraith_parser_alpha.c` — plain `fork()`+`execv()`, `current_module_pid` tracked, killed on switch/exit), not compile-time code sharing. The one shared binary is a generic shell that draws layout/chrome; each project's business logic lives in its own separate manager binary, launched as a child, talking through files. **Already-live local precedent**: `khtpm_strip_parser.c` (shell) + `khtpm_taskbar_manager_main.c` (separate manager binary, writes `strip_state.txt`/`strip_history.txt` for the shell to poll) IS this pattern — just not recognized as such until this correction. See `khtpm-merge-how2.md`'s STATUS section and `local-2do-15.txt`'s "Stage 2d, REDONE correctly" entry for the real per-app plan (planned, not executed).
3. Even the reference doesn't merge literally everything — the shell and each project's manager are always separate processes. "Shared" means the generic render/parse ROLE only, matching this house's own existing taskbar-manager-vs-strip-parser split, not "delete every other process" and not "fuse rendering and business logic into one file."

## K. UI/layout authoring standards — no hardcoded UIs; context windows; generic renderer mechanisms (added 2026-08-24)

### K.1 THE RULE: never hardcode a UI

**Every window/menu/layout is DATA, and is a GENERATED ARTIFACT of some store —
never hand-maintained, never baked into C code.** When tempted to add a domain
branch to a renderer, extend a GENERIC mechanism instead (§K.3), or generate the
layout file from the store:

| store (hand/data-owned)      | generated artifact (compiler owns)              |
|---|---|
| `event.ir.pdl`               | `event.pal`, `cmd_N.sh`, `msg_N.txt` (event-ez KEY handlers) |
| `<pal>/bookmarks.pdl`        | `<pal>/bookmarks.chtpm` + `.css` / menu rows (`&.widgits/bookmarks/bm_menu.sh`) |
| `dashboard.stats`            | `dashboard.chtpm` (`open_stats_hq.sh`)          |
| `meta.pdl` METHOD rows       | context-menu items (`load_meta()`)              |
| flat OBJECTS file            | SHOW_PAGE chooser rows (`load_flat_objects()`)  |

This is §A.7's runtime-config rule taken to layout level. Known live violation
genre to avoid repeating: cell 14/h-ai's C-hardcoded submenu (see §A.7's KNOWN
LIVE VIOLATION + `TASKBAR-MENU-ARCHITECTURE.md`).

### K.3 Generic renderer mechanisms (2026-08-24) — LOCATION CAVEAT

Two generic upgrades were added so ANY HQML window can do domain work without
domain branches in the renderer:
1. `onClick="open:<path>"` / `onClick="exec:<shell cmd>"` honored on EVERY
   element (the shared parser already captured the attr into `Elem.onclick`;
   consumers just never read it). Double-fork detached runner — cannot stall the
   render loop; orphan grandchild, no zombie bookkeeping.
   **REAL BUG FIX 2026-08-24 ("it still isn't opening the dir"):
   `apply_attr()`'s attribute matches were case-SENSITIVE ("onclick") while
   every house layout writes camelCase `onClick=` — the attribute was silently
   dropped, so the first real consumer's buttons had EMPTY actions and clicks
   did nothing with zero error output. Fixed via HTML-style case-insensitive
   attr-name matching (`attr_ci_eq`). The legacy dashboards never tripped this
   because they carry no onClick at all — their interactivity is renderer-side
   state. Lesson: a "captured by the shared parser" assumption needs ONE live
   end-to-end click before it counts as proven.**
2. Layout LIVE RELOAD: the window's own `.chtpm` is mtime-gated every tick;
   regenerate the file → running window swaps trees, no respawn.

**CAVEAT (honest status): both landed ONLY in `khtpm_hq_render.c` = the
stats-hq-only legacy binary (built by `build_db_hq.sh`). The merged
`khtpm_core_render.c` does NOT have them yet (grep-verified 0 matches,
2026-08-24). Porting them into the shared core of the merged binary is OPEN
WORK — do not assume an hq window supports onClick/live-reload until that port
lands.** db-hq-mode behavior in the merged binary is unchanged.

3. **XDND drop targets, data-driven (2026-08-24, IN THE MERGED BINARY)** — a
   `<window drop_action="sh -c '...'">` attribute opts that ONE window into
   being a real X11 XDND drop target (`khtpm_core_render.c` popup
   branch): on a drop of a `text/uri-list`, the first dropped DIRECTORY is
   exported as `$DROP_PATH` and `drop_action` runs with dispatch()'s exact
   `$0`=package_dir/`$1`=house_root convention — WITHOUT closing the window.
   Windows without the attribute never attach `XdndAware`: byte-for-byte
   unchanged (zero risk to the 7 existing menu.chtpm entities). House-history
   note recorded in source: gl_mirror.c removed real XDND over GLUT
   self-lookup + unthrottled-poll crashes — neither hazard exists here (own
    Window id, blocking select()+XNextEvent loop). Bookmarks was its planned
   first consumer but DECLINED it (user picked the db-hq-style window instead,
   §K.5) — the capability stays for future consumers.

4. **Generic onClick→nav-row pass (2026-08-24, `khtpm_hq_render.c`)** — EVERY
   element carrying `onClick=` is auto-numbered into the keyboard nav
   (`[>]N.` badge, arrows/digits/Enter) by a recursive pass at the start of
   `assign_nav_indices()` (chrome-close stays LAST per the 2026-08-12
   instruction). Includes a REAL BUG FIX worth remembering: that pass runs
   every `redraw()` while `g_n_nav` restarts at 0 each frame, so anything
   numbered ONLY by the pass was silently skipped after frame one (stale
   non-zero index ≠ 0 guard) — fix is zeroing the whole tree first,
   renumbering from scratch every pass. Symptom had been "event-commands
   still doesn't have nav".

5. **`onClick="input:<file>|<post cmd>"` text-input fields (2026-08-24,
   `khtpm_hq_render.c`, direct instruction "new+ should allow input from
   <cli-io>")** — an element with an `input:` action ARMS on Enter/digit/
   click (`[^]` armed glyph convention, typed line renders in place with a
   caret), printable keys type / BackSpace edits / Escape cancels / Enter
   COMMITS: appends the line to `<file>` then fires `<post cmd>` detached
   (same runner as `exec:`). No domain code in the renderer. v1 limits:
   ASCII typing only, no clipboard paste. First consumer: bookmarks' New+
   (zenity retired).

### K.6 STANDING RULE: no UI element without a mirror keyboard path (2026-08-25)

Direct instruction: *"there should be no ui element without mirror kbd
accesibility... get it?"* Every real interaction a mouse can do in ANY
khtpm-family window must have a keyboard path that genuinely reaches it — not
"technically possible via some obscure key," actually reachable via the same
keys someone's already using to navigate. This is elevated from a
project-doc pitfall note (`au11-hq/CREATOR_AGENT.md` §2.6/§2.7) to a house
standard because it's a real, repeatable review question, not a one-off fix.

**Concrete pattern, proven live on palettes' own grid scroll (2026-08-25) —
use this shape for any future scrollable/interactive widget:**
- A scrollable region's arrow keys must auto-scroll INTO VIEW at the edge,
  not just stop dead — off-screen rows are legitimately excluded from nav
  numbering (§A's own `w>0 && h>0` convention), so a keyboard-only user needs
  the SAME keys they're already pressing (not a separate, less-discoverable
  key like Page_Up/Down alone) to reach further content.
- Any mouse-only control (a scrollbar thumb, an increment button) needs a
  REAL Elem with a real `nav_index` and `onclick`, dispatched through the
  SAME generic `dbhq_activate_elem()`-style path every other tile uses — not
  a second, bespoke click-region check that only mouse events ever reach.
- **"Disabled" is a separate concept from "unnumbered."** A control that's
  temporarily inert (e.g. a scroll-up arrow already at the top) should KEEP
  its fixed nav position and identity — a keyboard user should be able to
  land on it and learn "this is disabled," not have it silently vanish from
  the tab order and reshuffle every other control's number depending on
  state. Disabling = dim the visual + make activation a harmless no-op
  (usually free, since the underlying clamp already prevents going past a
  limit) — never = stop numbering it.
- A narrow/edge-pinned Elem's nav badge can run off-screen if drawn with the
  normal inline-right position — use the real, generic `badge_align_left`
  field (`Elem`, `khtpm_render_core.c`) + its `draw_elem()` handling
  (`khtpm_draw_core.c`) rather than a one-off coordinate hack; default is 0
  (off) so every existing consumer is unaffected.

Reference implementation: `khtpm_core_render.c`'s `g_pal_arrow_up`/
`g_pal_arrow_down` (real synthetic Elems, same "outside the parsed tree,
checked explicitly before hit_test()" pattern `g_dbhq_close_elem` already
used), `dbhq_pal_scroll_to_y()` (click/drag-to-position), and the arrow-key
edge-autoscroll block in `dbhq_handle_key()`.
