## 1. Root cause, traced to the exact lines (confirmed, not guessed)

`102.editor-📄️00.00/ops/editor_widget_cmds.c` (and the byte-for-byte
identical copy at `102.agy-txt/ops/agy_widget_cmds.c` - both affected):

```c
if (strcmp(line, "SAVE") == 0) {
    ...
    /* relative paths under project_root */
    char full[PATH_BUF];
    if (fp[0] == '/') snprintf(full, sizeof(full), "%s", fp);
    else snprintf(full, sizeof(full), "%s/%s", project_root, fp);
    return do_save_to(full);                                    // line 218-222
}
if (strncmp(line, "SAVE_AS:", 8) == 0) {
    const char *p = line + 8;
    if (!p[0]) { set_status("SAVE_AS", "error", "empty path"); return -1; }
    return do_save_to(p);                                       // line 224-227, RAW, UNPREFIXED
}
```

Plain `SAVE` (re-saving to an already-known path) correctly prefixes a
relative path with `project_root`. `SAVE_AS:<path>` does NOT - it
passes whatever file-menu's own FILE field sent, completely
unprefixed, straight into `do_save_to()`, which just does
`fopen(path, "w")` (line 166-185) - resolved against the invoking
process's own CWD.

That CWD is `project_root` (the shell command that runs
`editor_widget_cmds.+x` always `cd`s into it first, matching the
established, already-confirmed pattern from PITFALL 62's own
investigation) - and for a REAL SAVE_AS-capable session, `project_root`
IS the EPHEMERAL, SESSION-SCOPED directory (`/tmp/.text-editor-xyz-
editor-<id>` for the app profile, or a `pieces/sessions/<id>` dir for
others) - the exact directory every project's own launcher `rm -rf`s
on exit.

So a bare typed filename (e.g. "hi.txt", as used in my own test
scenarios) DOES get written - `do_save_to()`'s own `set_status(...,
"ok", ...)` and "Saved N bytes to hi.txt" message are genuinely true
at the moment they're written - but the file lands directly inside the
ephemeral session directory, with no `docs/` prefix at all (the user
was never told they needed to type one), and is destroyed the instant
the session ends. From the user's real, persistent-storage
perspective, this is indistinguishable from "never saved anywhere" -
because functionally, it wasn't.

This is a DIFFERENT bug from PITFALL 62 (the `docs/` symlink nesting
bug) - PITFALL 62 only ever mattered for a path that ALREADY started
with `docs/`. This bug is that SAVE_AS never applies ANY prefixing
convention at all, so even a path that never mentions `docs/`
(file-menu's own FILE field has no built-in awareness that `docs/` is
supposed to be the convention - it's a generic, project-agnostic
widget, it doesn't know any given paired project's own internal
convention) silently vanishes.

## 2. What TPMOS's own real reference does (read directly, cited exactly)

`1.TPMOS_c_+rmmp.0103.0001/projects/agy-text-editor/manager/
agy-text-editor_manager.c`, `save_to_path()` (line 482-503):

```c
static int save_to_path(const char *rel_path) {
    if (rel_path[0] == '/' || strstr(rel_path, "projects/") == rel_path) {
        strncpy(active_file_path, rel_path, sizeof(active_file_path) - 1);
    } else {
        snprintf(active_file_path, sizeof(active_file_path), "%s/%s", current_dir, rel_path);
    }
    ...
    snprintf(full_path, sizeof(full_path), "%s/%s", project_root, active_file_path);
    ...
    char *op_argv[] = { "file_copy.+x", doc_path, full_path, NULL };
    run_op("pieces/system/file_ops/+x/file_copy.+x", op_argv);
    ...
}
```

The real pattern: a path starting with `/` (absolute) or with the
literal prefix `projects/` is used AS-IS; anything else (a bare
filename) is resolved relative to `current_dir` - the file browser's
OWN current location (`static char current_dir[MAX_PATH] =
"projects/agy-text-editor";` at file scope - defaults to the project's
own root, and changes as the user navigates the real directory
browser). Every SAVE, whether bare or explicit, is ALWAYS resolved
against a known, deliberate base directory - never a bare `fopen()`
against whatever the process's CWD happens to be. `load_from_path()`
(line 506-528) mirrors this exactly for LOAD.

TPMOS's own convention resolves bare paths relative to the PROJECT's
own tree (`current_dir`, `project_root`) - it has no separate concept
of a per-user home directory distinct from the project. That concept
does exist in THIS house though - see §3.

## 4. Proposed fix direction (NOT YET IMPLEMENTED - review before proceeding)

Mirror TPMOS's own STRUCTURAL PATTERN (§2) - always resolve against a
known, deliberate base directory, never a bare CWD-relative `fopen()`
- but make the DEFAULT base directory this house's own real xyzfs
user-home project tree (§3) instead of TPMOS's own project-relative
`current_dir`, since this house already has a real per-user home
concept TPMOS does not.

Sketch (naming/exact shape open for review, not committed):
  1. `do_save_to()`/`do_load_from()` (or a shared helper both SAVE_AS
     and LOAD call) resolve a bare path (no leading `/`) against a new
     `resolve_xyzfs_save_dir()` - same three-hop chain as
     `ledger_append.c`'s own `resolve_ledger_path()`, ending at
     `<house>/<current_xyzfs>/home/projects/<project_id>/` instead of
     `.../home/runtime/`. `project_id` already exists as a real,
     available value (`agy-editor`/`agy-txt`, matching each project's
     own `PRISC_PROJECT_ID`/state.txt convention already in use
     elsewhere this session).
  2. A path already starting with `/` (absolute) is used as-is,
     matching both TPMOS's own convention and this house's own
     existing `SAVE` handler's own `if (fp[0] == '/')` check - keep
     this as the deliberate escape hatch, per §37's own "backward
     compatibility" note in !.xyzos-standards+1.txt.
  3. `mkdir -p` the resolved target directory before the actual write,
     since (per §3) most projects' own xyzfs project-home dir does not
     exist yet - the FIRST real save for a given project should create
     it, not fail because it's missing.
  4. Apply the SAME fix to `SAVE`'s own existing `project_root`-
     prefixing branch too (line 218-222) - once a real xyzfs default
     exists, plain `SAVE` should also target it for a NEW file (no
     prior `file_path`), not fall back to the ephemeral session dir
     either. Re-saving to an already-resolved absolute `file_path`
     (the common case once a file has been saved once) is unaffected.
  5. Update the harness: `demo_fm_typing_ux.sh`, `demo_save.sh` should
     assert a REAL file exists under the NEW real target
     (`xyzfs/users/<uuid>/home/projects/<project_id>/...`), not just
     that a status message says "ok" - directly closes the gap named
     in §0.
