## 1. 🎯 The real mental model

- A **"desk session"** is a peer of a **"map session"** — not a mode inside the game/editor, a sibling kind of session.
- Living things (GL entity windows: pets, tile stamps, event-carrying entities) can exist:
  - **inside** a map session (rendered as part of a game world), or
  - **on the desk session** (an independent GL window living directly on the OS desktop, positioned via the same `state.txt` → poll → `XMoveWindow` pipeline egg_window already proves out), or
  - **in transit** between the two, as a `#.desktop/` package (file-based, source of truth, no process needs to be running for the handoff).
- Movement between these three states is always **file-mediated first** (write a package to `#.desktop/`, write/clear an open-request), with X11 Xdnd as an optional, later, purely-cosmetic accelerant on top — exactly the layering `xelector-context.md` already committed to ("file ops are source of truth... drag-drop can target desktop windows later").
- The **event system** (from aomorai-editor's event editor / mutaclysm's xelector context menu) is the thing that eventually drives how a desk-session entity moves/behaves — same event graph, different host (desk session instead of map session).

## 2. 🪟 hikikomorai app components

### 2.1 Terminal
A real terminal window, opened as part of hikikomorai's own launch, for direct `session:<session-id>(cli-io)`-style interaction with whatever's running on the desk session. (Naming note: grep confirms `session:<id>(cli-io)` as literal string is **not** an existing house convention — the real existing session identity mechanism is `session.pdl` key/value files, per `xyzfs` design, see §4. hikikomorai's terminal-facing display name can use the `session:<id>(cli-io)` label cosmetically, but underlying identity should key off the same `session.pdl`-style pattern already in use, not invent a second identity scheme.)

### 2.2 Task-bar widget
The visible "wrangler" for the desk session:
- Shows all **living procs/entities** currently on the desk session (each one an egg_window-style GL process + its `state.txt`).
- Lets the user switch focus between them.
- Lets the user manually reassign which micro-session/process "lives under" which parent session (rename/re-home, analogous to re-parenting a window).
- Is, conceptually, **another editor — but for a desk session instead of a map session**. Likely implication: it can reuse the same command-bus/focus.txt convention investigated for file-menu/map-picker/tile-picker (see `aomorai-editor-blueprint.md` §1.5), rather than inventing a fourth convention. This is an open question, not decided — see §5.

### 2.3 Desktop entity hosting
Reuses egg_window's real, already-proven pipeline:
```
brain (tick_*.c) → state.txt → renderer (egg_window-style .c) polls → XMoveWindow
```
Tile-picker and aomorai-editor's event editor should be able to target **the desktop** as a placement destination, not just a map — meaning their existing `PLACE_TILE`/event-package flows need a second destination mode: "place on `#.desktop/`" (already exists — see `#.desktop/tiles/`) plus "spawn as a live desk-session window" (new — the missing renderer-launch step that egg_window has, but tile-picker/event-editor don't yet call).

### 2.4 xyzfs integration
Desk-session state should live under the current logged-in user's `xyzfs` home, per the approved layout in `#.haiku+/30.jul-30-handoff/3.harness-install-xyzos~/4.install-v1-xyzfs-layout.md`:
- `xyzfs/users/<uuid>/home-🏠️/hikikomorai/` for saved desk-session layouts.
- Read current user via the same `session.pdl` file `apps/00.login-signup/xyzfs/session.pdl` (or wherever the resolved equivalent is per `$HOME/xyzos/paths.pdl`) that avatar-creation already reads.

## 3. 🔗 Relationship to aomorai-editor (aomo)

- Aomorai-editor's **event editor** (command-list + `RAW_PAL` escape hatch) is the authoring surface for entity behavior. hikikomorai is a **second host** for entities driven by that same event system — not a competing editor.
- Tile-picker's glyph (currently single ASCII `char`, needs widening — flagged in aomorai-editor-blueprint.md §12 open question 8) is shared infrastructure between "place tile on a map" and "place tile on the desktop" — the widening work benefits both.
- Practically: **do not build hikikomorai's editor UI before aomorai-editor's event editor's command format is settled** — hikikomorai's desk-session entities will want to consume the same compiled `.pal` event output, so building it first risks a second, divergent format.

## 4.5 🖱️ Context-menu methods on desk-session entities

Direct instruction, 2026-08-04: egg_window (`01.muchi-pals-🥚️-13.01/system/egg_window.c`) already has a real right-click context window — currently just one item, "Close" (`open_context_menu`/`draw_context_menu`/`close_context_menu`, POSIX build; `WM_RBUTTONUP`/`TrackPopupMenu` on Windows). Direct instruction: every living desk-session entity (tile stamps via `tp_desktop_window.c`, egg-pals, later event-carrying entities) should get a **real menu of methods** there, not just Close — e.g. opening the event-editor widget for that entity, Play/Pause (if the entity has its own tick), and entity-specific verbs (Attack, Inventory, etc.) that only apply to some kinds.

**What exactly goes in that menu is not decided yet** (direct quote: "im not sure exactly what methods, or how we will edit methods, probably a few different ways"). What's clear from the code that already exists:

- **The mechanism for a *variable* menu already exists in this house** — `pc_menu_input.c`'s `load_menu_items()` reads METHOD rows out of a `.pdl` file to build a screen's menu, rather than hardcoding cases (see `aomorai-editor-blueprint.md` §8, "data-driven, extensible menus"). The right shape for a desk-entity's context menu is almost certainly the same: a small METHOD table living in the entity's own package dir, not a hardcoded C `switch`.
- **Different entity kinds will want different method sets** — a tile stamp's real methods today are just "open event editor for this tile" (once that widget exists) and Close; an egg-pal's could include Play/Pause (self-tick on/off — the `self_tick_pet()`/`tick_config.txt` mechanism already exists) and later Attack/Inventory once combat/items are real for pets. **Do not build one universal method list** — read whatever METHOD rows exist for *that* package's `kind`, same principle as `pc_menu_input.c` only offering methods relevant to the current screen.

### Where would "give/remove a method" actually live?

Direct question: "tile is being added to desk, but where else? therefore we could edit its dir, and give/remove methods etc?" — answer, following what's real today:

A tile stamp currently lives in exactly **one** place on disk: `#.desktop/tiles/<name>/` (`glyph.txt` + `meta.pdl`, written by `tp_place_desktop.c`). There is no second copy anywhere else — the live GL window (`tp_desktop_window.c`) doesn't hold its own state, it just polls that same package dir and self-closes if it disappears (see §2.3). **This means giving/removing a method for one specific tile instance is just editing that same package dir** — most likely a new `methods.txt` (or additional METHOD rows appended to the existing `meta.pdl`, matching `pc_menu_input.c`'s own METHOD-row convention rather than inventing a second file format) sitting right next to `glyph.txt`. Whoever/whatever opens the context menu re-reads that file fresh each time (same "renderer polls a file" pattern as everything else in this house), so:
- **Giving** a method = appending a METHOD row to that tile's own `meta.pdl`.
- **Removing** a method = deleting that row.
- **A human editing the dir by hand** (`vim #.desktop/tiles/tile_X_.../meta.pdl`) would be a real, legitimate way to do this v1 — before any GUI method-editor exists, matching this house's general "the file is the real interface, the widget is optional sugar on top" convention.

An egg-pal's real methods (if/when it gets more than Close) would live the same way, in its own `pieces/world_01/map_lobby/<pet_id>/` dir — not a new global methods registry. **No central "all methods for all entities" file should exist** — each living thing's own dir stays the single source of truth for what it can do, matching how `#.desktop/README.txt` already frames packages as self-contained, portable units.

This is still open on exactly which methods ship first and how a human/agent edits them day-to-day (raw file edit vs. a future menu-editor widget) — tracked as open question 6 below.

## 5. ❓ Open questions

1. **Session naming**: adopt `session:<id>(cli-io)` as a cosmetic label only, or as the real identity key? (Leaning: cosmetic only, real identity stays `session.pdl`-based — avoids a second parallel session-ID scheme.)
2. **Task-bar's host-integration pattern**: reuse file-menu's `focus.txt` + inbox-cmd-bus convention, reuse board-viewer's `focused_project_root` convention, or a third pattern specific to desk sessions? Should be decided **alongside**, not before, the aomorai-editor convention-mismatch discussion (blueprint §1.5d/§12.7) — these are the same underlying question asked twice.
3. **Reparenting semantics**: when a user manually moves a micro-session from one parent to another via the task-bar, what actually changes on disk — just a pointer/registration file, or does the child's own `state.txt`/`project_root` move? (Leaning: pointer/registration only, to avoid the same "silent fopen failure if parent dir missing" class of bug flagged elsewhere in this house — see memory `reference_silent_fopen_write_failure`.)
4. **Does hikikomorai launch its own mutaclysm-independent world, or always require a host map-session to pull entities from?** i.e., can a desk session exist with zero map sessions running?
5. **Glyph-widening ownership** (shared with aomorai-editor blueprint open question 8): whoever does it first should own the shared header/format, not duplicate it.
6. **Method editing UX**: raw file edit of a package's `meta.pdl` (real, works today, zero new code) vs. a future dedicated menu-editor widget vs. exposing it through the event-editor itself (since methods and events are conceptually close - both are "what can this thing do"). Not decided - see §4.5.
