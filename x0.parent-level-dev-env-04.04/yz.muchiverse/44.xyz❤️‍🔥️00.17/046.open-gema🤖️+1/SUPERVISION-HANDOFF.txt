================================================================
1. WHAT THIS FOLDER IS (10-second recap)
================================================================
A CLI coding agent (like a mini-opencode) that runs on gemma3:270m over LAN
(no big LLM). gemma does NOT write big code from nothing: it ROUTES intent
through deterministic C tools (ops/) and REASONS over tiny RAG-retrieved
windows (rag/ + memory/). The tools are the ground truth, not the model.

The deliverable is src/agent.c, which gemma itself authors STEP BY STEP via
the builder loop (small spec -> gemma writes -> gcc check -> fix -> next).

================================================================
2. THE CO-EVOLUTION LOOP (keep this rotating forever)
================================================================
   [supervisor updates gemma's TOOLS: ops/, rag/, builder/, harness/]
            |
            v
   [gemma authors/builds src/agent.c through the tools]
            |
            v
   [harness proves read -> edit -> run -> document -> ask]
            |
            v
   [bottlenecks found -> supervisor updates tools again]
            |
            v
   [gemma rebuilds/extends itself -> LOOP REPEATS]

We are DONE only when the loop stalls and no new bottleneck appears.
Every single pass should leave a trace (see section 6).

3. YOUR JOB AS SUPERVISOR (the rules)
================================================================
R1. GEMMA COMPUTES, YOU ORCHESTRATE. This box only runs tools/compile/
    harness. gemma computes on the LAN Mac:
      http://10.0.0.144:11434  model gemma3:270m  (see ops/connect_op.c)
    Never try to run a big LLM locally here.

R2. GEMMA NEVER WRITES CODE FROM NOTHING. Give it ONE tiny spec at a time:
    - one function, zero ambiguity, stdio/stdlib/string only
    - "Write C that does EXACTLY this. Put it in src/agent.c."
    - mark append/splice points with // === STEP N === markers
    If the spec fits in a tweet, it fits in gemma's context. If not, break
    it down further. 270m CANNOT hold large specs — never fight this.

R3. COMPILE FEEDBACK IS THE CURRENCY. Every authoring step MUST end in
    `gcc -c src/agent.c`. On failure, feed the EXACT compiler error back:
    "fix ONLY this error, keep everything else identical" -> retry, max 3.
    On 3x failure: STOP, report the bottleneck. That report is the signal
    to improve YOUR tools (step decomposition, RAG injection, error format).

R4. TOOLS ARE GROUND TRUTH, NOT THE MODEL. list/read/search/edit/run must
    fire with ZERO LLM calls (that's harness K7/K8). Only the `ask` path
    touches gemma. If a tool is slow/broken/ambiguous, FIX THE TOOL first.

R5. KEEP THE TOOL GRAMMAR STABLE. ARCH-DOC.txt defines the contract
    (read|edit|write|search|run|list|rag|ask). Changes ripple into
    agent.c routing + harness scenarios. Change the grammar ONLY when the
    loop truly demands it, and update ALL of: ARCH-DOC.txt, ops/, builder
    steps, harness.

R6. ALWAYS VERIFY WITH THE HARNESS. harness/k3-cli.sh feeds stdin commands
    and asserts on stdout + disk truth (K1..K8). Green harness = real
    progress. A passing gcc -o is NOT proof; a passing harness is.

================================================================

================================================================
7. WARNING SIGNS (when to STOP and reconsider, not push through)
================================================================
- gemma "hallucinating" tool calls in replies -> context window too big
  for the spec, OR the RAG window is polluted. Shrink, don't retry harder.
- harness flaky (passes then fails on same input) -> make asserts
  deterministic (exact substrings, disk checks); a flaky harness poisons
  the whole loop.
- builder spends 3x retries on step N repeatedly -> step N is too big.
  Decompose it, don't brute-force it.
- any op/ hangs or forks the LAN Mac -> fix timeouts in ops/connect_op.c
  first; the box orchestrates, never blocks.
