4.1 Scaffolding Gemma to act like llama-groq-tool-use, but cheaper
--------------------------------------------------------------------------
THE PROBLEM: groq-tool-use-mac (llama3-groq-tool-use:8b via ollama) is the
one proven, reliable tool-calling model in model_list.txt - native tools[]
schema, real function-call JSON, build_ollama_request already handles it
correctly. It is also SLOW (an 8B model). gemma-lan (gemma3:270m) is ~30x
smaller and dramatically faster/cheaper to run on the same LAN Mac GPU, but
it has NO native tool-calling schema at all - it just emits plain text.

THE PLAN (concretely, this is what a future agent should be told to build -
paste this whole subsection as the prompt if that's easier than summarizing
it further):

  "Gemma doesn't support native tool-calling, so instead of tools[] JSON, we
  are going to teach it a plain-text KEYWORD CONVENTION and parse that
  convention out of its raw completion text - the exact same shape
  send_message.c already uses for provider_kind=llamacpp, which ALSO has no
  native tool schema and is already handled by manually building a raw
  prompt (text_to_pal_prompt.c) instead of relying on the API to understand
  tools[]. Reuse that same pattern for gemma, don't invent a new one:

  1. Write a new system-prompt template (or extend text_to_pal_prompt.c)
     that teaches gemma a fixed marker syntax for calling a tool, e.g.:
       TOOL: read_file <path>
       TOOL: edit_file <path> <old> <new>
       TOOL: exec <command>
       TOOL: speak <text>
     one call per turn, plain text, no JSON required at all.
  2. Add a new parser (same shape as json_parser.c, but scanning for the
     `TOOL: <verb> <args>` line instead of parsing JSON) that runs on
     gemma's raw completion text and extracts verb+args if present.
  3. Dispatch the SAME tool ops that already exist and are already proven
     (file_ops.c, edit_file.c, cmd_exec.c, list_dir.c, search_in_files.c,
     web_search.c - do not rewrite these, they are provider-agnostic
     already) - only the PARSING layer is new, the EXECUTION layer is
     reused untouched.
  4. TTS is the one genuinely new op needed: write ops/tts_speak.c, self-
     contained like every other op, shelling out to whatever local TTS
     binary is available (espeak/piper/similar;[!.user: we use "edge-tts , .c script"]) with the text argument -
     matching the family's own 'op wraps one external program' convention
     (see chat_post_message.c or connect_op.c for the shape).
  5. Feed the tool's result back into context_log.txt as a tool-result turn
     (append_log_turn already supports a 'tool_name' field for exactly this
     - see how execute_tool.c does it for the existing PENDING_PERM flow),
     then let the SAME check_response.c/send_message.c tick loop already in
     main_loop_chtpm.pal re-invoke gemma with the updated context - this is
     already 'reloop using context,' no new engine work needed, it's the
     exact same mechanism every other provider_kind already uses.
  6. Add a new provider_kind, e.g. 'ollama_keyword' (or extend 'ollama' with
     a sub-flag), so model_list.txt can point gemma-lan at this new request-
     builder instead of the native-tools one groq-tool-use-mac uses.

  Net effect: same read-file/edit-file/exec/speak/prompt-user/reloop
  capability as groq-tool-use, at a fraction of the compute, because gemma3:
  270m is that much smaller than the 8B tool-use model - the tradeoff is
  slightly less reliable tool-call formatting (a plain-text convention is
  easier to get wrong than a schema-validated JSON call), which is worth
  testing empirically once built, not assumed.; refine "

--------------------------------------------------------------------------
4.6 SCALE_BANK - a fidelity-configuration layer, orthogonal to WHAT a
    module is (this is the big one - its own section as asked)
--------------------------------------------------------------------------
THE CORE IDEA: scale is not a property of a GAME or a WORLD as a whole -
it's a property of one (ENTITY TYPE, DOMAIN) PAIR at a time. A car in a
driving game might need deep, "large scale" simulation of its physics
domain (tires, gas, engine mechanics, combustion) while needing almost
nothing for its "conversation" domain (cars don't talk). An NPC in that
same game might need large-scale fidelity for ITS driving-knowledge domain
(so it drives convincingly) but only small-scale/cheap fidelity for its
conversation domain (a few canned lines is enough). Two different entities,
same domain (driving), can independently need different scale too - a
"simple cheap racing game" config might deliberately choose small-scale
physics for cars even though large-scale is available, because the
PRODUCT doesn't need it this time.

WHY THIS IS A BIG DEAL, concretely: without this, a project either (a)
hardcodes one fixed fidelity level for everything (wasteful when cheap
would do, or worse, hardcodes CHEAP and can't later add depth without a
rewrite), or (b) builds bespoke one-off fidelity switches per feature,
each its own special case, none of them reusable. SCALE_BANK makes "how
much detail does this need" a first-class, swappable, reusable config
decision - the SAME mechanism as every registry described above (a
pipe-delimited bank naming options, a switch/config picking one), just
keyed by (entity_type, domain) instead of a single id.

CONCRETE SHAPE (same pipe-delimited registry convention as model_list.txt/
trigger_list.txt/the npc_bank idea in 4.4 above - not a new file format,
a new KEY shape):
  entity_type|domain|scale_level|module_id
  car|physics|large|tire_engine_combustion_full_sim
  car|physics|small|simple_speed_accel_abstraction
  car|conversation|small|none
  npc|driving_knowledge|large|full_driving_rules_module
  npc|conversation|small|random_words_or_light_fsm
  npc|conversation|large|full_llm_persona_module

  - entity_type/domain: which kind of thing, and which subsystem/behavior
    of it (physics, conversation, biology, driving_knowledge, whatever the
    domain needs - not a fixed enum, project-defined).
  - scale_level: which fidelity tier this row represents (large/small, or
    more tiers later if actually needed - don't over-design past 2 tiers
    until a 3rd is genuinely wanted).
  - module_id: which actual generator/behavior module (an op, a script/
    fsm/rl entry from the existing picker, a wordbank) implements THIS
    specific (entity_type, domain, scale_level) combination - reuses
    whatever registry mechanism that domain already has (e.g. conversation
    scale rows point at provider_kind=script/iqabod/gemma entries the same
    way model_list.txt already names them).

A SEPARATE, PER-PROJECT/PER-GAME CONFIG FILE then picks which scale_level
is ACTIVE for each (entity_type, domain) pair for THIS specific game/
simulation - e.g. "simple cheap racing game" config picks car|physics|
small, while "hardcore sim racer" config picks car|physics|large, using
the exact SAME underlying SCALE_BANK rows either way. This is the same
registry-vs-active-selection split as model_list.txt (the bank) vs.
state.txt's current_model_id (the active pick) - not new machinery,
the same pattern with a 2-part key.

REUSE ACROSS DOMAINS, directly answering "get it?": this is NOT game-
specific. The exact same SCALE_BANK mechanism applies to:
  - AI TRAINING CORPORA (4.2/4.5's own "corpuses at scale" point) - a
    corpus itself can have a scale_level (a tiny starter wordbank vs. a
    full trained curriculum for the same domain).
  - WSR's future humans/employees/customers and organisms/animals/plants/
    microbes (4.4's own npc_bank note) - an "employee" entity might need
    large-scale job-skill modeling but small-scale biology modeling; an
    "animal" might need the exact opposite (large-scale biology, no job
    skills at all). Same bank shape, same per-(entity,domain) key, totally
    different actual content per project.

BUILD ORDER (same "prove one thing before generalizing" discipline as
everywhere else in this file): pick ONE real entity type with a genuine
two-tier need (e.g. mutaclysm's own car-or-NPC, once 4.4's modularization
work has already happened there), write its SCALE_BANK rows, wire ONE
config file to pick between them, verify both tiers actually work end to
end, BEFORE generalizing SCALE_BANK into a shared, cross-project
mechanism. This is genuinely valuable but also genuinely new machinery
(unlike 4.1-4.5, which mostly reuse existing patterns) - budget real
design-doc-first time for it, matching this family's own standing
convention, before writing code.

STANDING CONVENTIONS THAT APPLY EVERYWHERE (violate these and you will
reintroduce bugs that were already found and fixed once):
  - SESSION ISOLATION: every project's button.sh `run` action creates a
    throwaway pieces/sessions/<id>/ dir, symlinking in shared/static code
    and shared/persistent data, with real private ephemeral UI state -
    deleted on exit. Never launch a second instance directly against a
    project's own root - always go through button.sh's own session
    creation, or replicate it exactly if scripting around it (see pal-
    scripts/launch_irc_agent.sh for a worked example).
  - KILL BY CWD, NEVER BY ARGV: every session's own processes have
    IDENTICAL argv text (`system/prisc+x pal/main_loop.pal` etc.) - a bare
    `pkill -f` will kill the WRONG session's process. Always match
    /proc/$pid/cwd against the specific session dir you mean to kill.
  - PRISC_PROJECT_ROOT IS CACHED, NOT LIVE: every op/process reads this
    env var ONCE at startup into a static buffer. Moving/renaming a
    directory updates a running process's kernel cwd (Linux follows
    renames), but NOT this cached string - a leftover process can keep
    writing to the OLD path indefinitely. Always re-sweep for orphaned
    processes (by real /proc/$pid/cwd, not by name) after any directory
    move, and do it TWICE - once isn't always enough.
  - ONE VISIBLE FRAME WRITER: no op writes pieces/display/current_frame.
    txt (or a project's own view.txt) directly except chtpm_parser_pal's
    own internal compose step - an op writes its OWN view.txt, then pings
    frame_changed.txt.
  - REGISTER-SENTINEL BUG CLASS in prisc+x.c's own opcode parsers: several
    opcodes (OP_READ_HISTORY, OP_EXEC) had a parsing bug where an unset
    register field defaulted to 0 (a REAL register, hardwired-reset every
    instruction) instead of an explicit "not given" sentinel (-1). If a
    new opcode or new calling form is ever added, check this exact class
    of bug before trusting it - "does an unset field default to something
    indistinguishable from a valid value" is the actual question to ask.
  - DESIGN-DOC-FIRST: every real feature in this family's history has a
    doc written and read BEFORE code - don't skip this even under time
    pressure, it's what keeps multi-session work coherent.
  - ALWAYS DIFF BEFORE OVERWRITING a synced shared file - check
    shared-ops-manifest.txt for "NOT synced from here" notes before
    blindly copying a canonical file over a project's own fork of it.
  - REGISTRY + SWITCH + SELF-CONTAINED OPS is the one pattern that shows
    up in every single feature in this family (see section 5 above) -
    when in doubt about how to add a new swappable behavior anywhere,
    this is almost always the answer.
