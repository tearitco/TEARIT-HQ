PART 1: MULTIPLAYER TURN STRUCTURE (Game Loop)
================================================================================

CURRENT STATE (from game.c and ai_manager.c):

The game runs with a turn-based multiplayer loop:

  1. Initialize players (human and/or AI)
     - players[num_players] array, each with name, cash, type (HUMAN or COMPUTER)
     - current_player_index = 0

  2. Game loop iterates while game_running:
     - Display menu for players[current_player_index]
     - If player is HUMAN: wait for input, process choice
     - If player is COMPUTER: invoke AI decision engine (described below)
     - On "End Turn" (choice 17): increment current_player_index
     - current_player_index = (current_player_index + 1) % num_players
     - Loop back to step 2

TURN SEQUENCE EXAMPLE (2 players: ab=HUMAN, ba=COMPUTER):

  Turn 1: ab's turn
    - Display menu
    - ab enters choice (e.g., "12" for Buy/Sell)
    - ab completes action
    - ab presses "17" (End Turn)

  Turn 2: ba's turn (COMPUTER type = 0)
    - AI engine runs (see PART 2)
    - AI reads corporation data and master ledger state
    - AI decides trade action (buy, sell, finance, etc.)
    - AI POSTS trade entry to master_ledger.txt
    - AI's turn ends automatically

  Turn 3: ab's turn again
    - ab's menu displays
    - ab can see market state updated by ba's trades (if implemented)
    - Loop continues

CRITICAL: Turn structure is hardcoded in game.c main loop (line 304-418).
  - Players take turns sequentially
  - No concurrent turns (turn_index cycles 0→1→2→...→num_players-1→0)
  - Each player's state is stored in players[i] struct
  - Current player is always players[current_player_index]

2B. DISPATCHER (ai_manager.c, extended)
────────────────────────────────────

Current: ai_manager.c is minimal (display only, no decision logic yet)

DESIGN: Add dispatcher logic to ai_manager.c:

  void run_ai_turn(Player *ai_player) {
    1. Read ai_player->strategy_id from player state
    2. Look up strategy_id in data/ai_strategy_registry.txt
    3. Extract module_name (e.g., "ai_module_0_apprx.+x")
    4. Load corporation data from corporations/generated/
    5. Load master_ledger.txt to see recent trades
    6. Shell to strategy module:
       ./+x/<module_name> <player_name> <master_ledger.txt> <corporations_dir>
    7. Strategy module returns trade action(s):
       "action_type|ticker|quantity|price|reason"
    8. Validate action against player cash/holdings/market rules
    9. POST action to master_ledger.txt with timestamp and player name
    10. Update player balance sheet (deduct cash, add holdings)
  }

INVOCATION: When game loop detects current_player is COMPUTER type:

  if (players[current_player_index].type == COMPUTER) {
    run_ai_turn(&players[current_player_index]);
  }

  This replaces manual choice entry; AI turn ends automatically.

2C. STRATEGY OPS (ai_module_*.c files)
────────────────────────

Each strategy module is a self-contained C program:

INTERFACE (input):
  Argument 1: player_name (e.g., "ba")
  Argument 2: path to master_ledger.txt
  Argument 3: path to corporations directory

INTERFACE (output):
  Stdout: newline-separated trade actions
  Format: action_type|ticker|quantity|price|reason

  Example actions:
    BUY|ACME|50|150.00|cash_reserves_high
    SELL|XYZ|20|50.00|losing_position
    SHORT|ABC|100|75.00|bearish_signal
    COVER|ABC|50|80.00|signal_reversed

EACH MODULE'S LOGIC (example: ai_module_0_apprx.c):

  1. Read master_ledger.txt from last_processed line
     (use master_reader.txt pattern: track current position)

  2. Load all corporation data from corporations/generated/

  3. For each corporation:
     - Calculate: book_value = equity / shares_outstanding
     - Calculate: leverage = debt / equity
     - Calculate: expected_return = div_yield + earnings_growth_rate
     - Score: risk_score = leverage * volatility

  4. Decision logic (conservative example):
     - If risk_score < threshold AND expected_return > 5%:
       → RECOMMEND: BUY (add to watchlist)
     - If earnings_decline OR debt_spike:
       → RECOMMEND: SELL (reduce position)
     - Prefer dividend payers (high div_yield)

  5. Output each recommendation to stdout

IMPLEMENTATION EXAMPLE: ai_module_0_apprx.c skeleton

  #include <stdio.h>

      return 1;
    }

    // Parse player's holdings from ledger (all past BUY/SELL/SHORT/COVER for this player)
    // Build: holdings[ticker] = quantity

    // Load corporation data from corps_dir
    // For each corporation:
    //   - parse balance sheet
    //   - calculate fundamentals
    //   - score stock
    //   - emit recommendation if score meets threshold

    // Example output:
    printf("BUY|ACME|50|150.00|conservative_buy_signal\n");
    printf("SELL|XYZ|20|50.00|risk_reduction\n");

WHY SEPARATE MODULES?
  - Each strategy can have different complexity (conservative vs. aggressive)
  - Add new strategy = new .c file + one registry row, no dispatcher changes
  - Dispatcher doesn't need to know HOW each strategy decides, just WHICH to call
  - Easy to disable/enable strategies by editing registry
  - Easy to benchmark (run each module in isolation with sample ledger data)

3A. MASTER LEDGER DESIGN
───────────────────────

File: data/master_ledger.txt (append-only transaction log)

FORMAT: pipe-delimited time-series of financial events

  Time|Player|Action|Ticker|Quantity|Price|Amount|Notes

Example rows:

  2025-01-01T09:00:00|ab|BUY|ACME|50|150.00|7500.00|Starting portfolio build
  2025-01-01T09:15:00|ba|BUY|ACME|100|150.00|15000.00|Aggressive entry
  2025-01-01T10:00:00|ab|SELL|ACME|25|151.00|3775.00|Taking profit
  2025-01-02T08:00:00|ba|SHORT|XYZ|50|50.00|2500.00|Bearish on XYZ
  2025-01-02T09:00:00|ab|BUY|ACME|30|152.00|4560.00|Adding to position

PROPERTIES:
  - Append-only (never delete or modify past rows)
  - Each row is ONE atomic transaction
  - Timestamp = game_time (not wall-clock)
  - Player = who made the trade
  - Action = BUY, SELL, SHORT, COVER, DIVIDEND, TRANSFER, LOAN, etc.
  - Amount = transaction value (quantity * price, or cash transferred)
  - Notes = reason/context (optional, for auditability)

CRITICAL: Master ledger is the SOURCE OF TRUTH for all financial state.
  - Player balances = SUM of all past transactions
  - Portfolio = SUM of BUY/SELL/SHORT/COVER for each ticker, per player
  - Debt = SUM of LOAN transactions
  - Dividends received = SUM of DIVIDEND transactions

3B. MASTER READER (master_reader.c)
───────────────────────────────────

Purpose: Process NEW entries from master_ledger.txt and execute them.

Current implementation (master_reader.c):
  1. Open data/master_reader.txt (tracks last_processed_line)
  2. Read last_processed_line number (e.g., 47)
  3. Open master_ledger.txt
  4. Skip first 47 lines
  5. For each NEW line (48+):
     - Parse transaction fields
     - Match action type (BUY, SELL, etc.)
     - Execute corresponding operation (e.g., update corporation ownership, stock price)
     - Write last_processed_line = current_line_number
  6. Close files

WHY THIS PATTERN?
  - Ledger can grow unbounded (never delete old transactions)
  - Master reader processes incrementally (only new lines each tick)
  - No race conditions (reader file locks prevent concurrent writes)
  - Auditability: full history preserved

CURRENT LIMITATION: master_reader.c only handles "incorporation.+x" events.
  Need to extend to: BUY, SELL, SHORT, COVER, DIVIDEND, LOAN, etc.

3D. HOW AI READS LEDGER STATE
──────────────────────────────

AI module needs current state to make decisions:
  - Player's cash balance
  - Player's stock holdings
  - Recent trades (to detect trends)
  - Corporation fundamentals
  - Market conditions

PATTERN: AI module reads entire master_ledger.txt and reconstructs state

  void reconstruct_player_state(FILE *ledger, const char *player,
                               PlayerState *state) {
    float cash = starting_cash;          // From starting_data.txt
    int holdings[MAX_TICKERS];           // ticker → quantity
    float cost_basis[MAX_TICKERS];       // ticker → avg purchase price
    memset(holdings, 0, sizeof(holdings));

    // Scan entire ledger, sum transactions for this player
    char line[512];
    while (fgets(line, sizeof(line), ledger)) {
      // Parse: Time|Player|Action|Ticker|Quantity|Price|Amount|Notes

      if (player_matches && action == "BUY") {
        holdings[ticker] += quantity;
        cost_basis[ticker] = ((cost_basis[ticker] * old_qty) + (price * qty)) / new_qty;
        cash -= amount;
      } else if (player_matches && action == "SELL") {
        holdings[ticker] -= quantity;
        cash += amount;
      } else if (player_matches && action == "LOAN") {
        cash += amount;
        state->debt += amount;
      } else if (player_matches && action == "DIVIDEND") {
        cash += amount;
      }
    }

    state->cash = cash;
    memcpy(state->holdings, holdings, sizeof(holdings));
    memcpy(state->cost_basis, cost_basis, sizeof(cost_basis));
  }

EFFICIENCY: Instead of rescanning entire ledger every turn, AI could:
  - Keep a snapshot of state at end of each turn
  - Only re-read ledger entries since last turn
  - Cache corporation fundamental data (update daily, not per-turn)

3E. TRADE VALIDATION
────────────────────

Before posting BUY/SELL/SHORT/COVER to ledger, dispatcher must validate:

  BUY: Require player.cash >= quantity * price
  SELL: Require player.holdings[ticker] >= quantity
  SHORT: Require player.cash >= quantity * price * MARGIN_REQUIREMENT (e.g., 25%)
  COVER: Require player.short_positions[ticker] >= quantity
  LOAN: Require player.credit_limit >= amount
  DIVIDEND: Triggered by game (not by player/AI), automatic

IMPLEMENTATION:

  bool validate_trade(Player *player, Trade *trade,
                     const MasterLedger *ledger) {
    PlayerState state;
    reconstruct_player_state(ledger, player->name, &state);

    switch (trade->action) {
      case BUY:
        return state.cash >= (trade->quantity * trade->price);
      case SELL:
        return state.holdings[trade->ticker] >= trade->quantity;
      case SHORT:
        return state.cash >= (trade->quantity * trade->price * 0.25);
      // etc.
    }
    return false;
  }

SUMMARY
================================================================================

MULTIPLAYER TURN FLOW:
  1. current_player_index cycles through players
  2. If HUMAN: wait for input, process choice
  3. If COMPUTER: run_ai_turn() invokes strategy module
  4. All trades posted to master_ledger.txt
  5. Master reader processes trades, updates state
  6. Next turn, all players see updated market state

AI DECISION FLOW (COMPUTER PLAYER):
  1. Dispatcher reads strategy_id from player
  2. Dispatcher looks up strategy in registry
  3. Dispatcher shells to strategy module with (player_name, ledger_path, corps_dir)
  4. Strategy module reads ledger, reconstructs state, calculates decisions
  5. Strategy module outputs recommendations to stdout
  6. Dispatcher validates, posts to ledger
  7. Master reader executes trades, updates prices/balances

MASTER LEDGER ROLE:
  - Single source of truth for all financial state
  - Append-only audit trail (all history preserved)
  - Master reader processes incrementally (only new rows)
  - Player balances = SUM of ledger transactions
  - Enables time-travel replay (reconstruct any past game state)

PATTERN CONSISTENCY:
  - Same registry + dispatcher pattern as monster AI
  - Modular strategy ops (new strategies = new binary + registry row)
  - No changes to dispatcher when strategies change
  - Extensible: can add new action types without rebuilding core

This architecture supports multi-player trading, AI decision-making, and
full auditability via the master ledger, all following the proven muchiverse
registry + dispatcher pattern.

PART 8: IRC/CHAT INTEGRATION (44.pal-chat-irc ARCHITECTURE)
================================================================================

8A. HOW IRC FITS INTO THE ECOSYSTEM
──────────────────────────────────

Mars Street Trading can be played as a SOLO game (human vs. AI) or as
COLLABORATIVE/COMPETITIVE multiplayer. The IRC system provides the SOCIAL LAYER:
  - Players communicate in real-time during trades
  - NPCs (non-player characters, also using strategy modules) can post messages
  - Trading rooms can have live chat (#energy-trading, #tech-stocks, etc.)
  - Master ledger can record chat as context for trades (audit trail)

ARCHITECTURE PARALLEL:
  Trading Sim → Master Ledger (financial events)
  IRC Chat   → Messages Log (social events)
  Both append-only, both processable incrementally, both distributed via P2P

8B. PAL-CHAT-IRC CORE COMPONENTS
─────────────────────────────────

1. USER MANAGEMENT (chat_create_user.c)
   Input: user_id, display_name
   Output: users/<user_id>/profile.txt (key=value format)
   Pattern: Self-contained op, no registry (users are implicit, not templated)

2. ROOM SYSTEM (implicit, no separate op)
   - Rooms created implicitly by first message posted to them
   - rooms/<room_name>/messages.txt (append-only log)
   - Same "lazy creation" pattern as corporations in trading sim

3. MESSAGE POSTING (chat_post_message.c)
   Input: room_name, user_id, text
   Output: DOUBLE WRITE
     - rooms/<room_name>/messages.txt (local persistence)
     - net/outbox.txt (P2P broadcast queue)
   Format: MSG|msg_id|room|user_id|timestamp|text

   PARALLEL TO MASTER LEDGER:
     Trading: BUY|ticker|qty|price → ledger.txt + outbox.txt
     Chat: MSG|room|user|text → messages.txt + outbox.txt
     Both: local + network copies

4. P2P NETWORKING (palnet_peer.c)
   Symmetric peer-to-peer, NO client/server distinction

   Discovery:
     - Presence directory: net/presence/<node_id>.txt
     - kind, project_id, piece_id, host, port, pid, last_seen (all key=value)
     - Each node publishes its own presence file
     - Others scan directory for live (non-stale) nodes to connect to

   Protocol:
     - TCP sockets for live data (outbox → inbox propagation)
     - HELLO handshake: announce node_id and kind
     - DATA lines: relay messages (with sender_node_id prefix)
     - Append-only on receiver side (write_inbox appends, never overwrites)

   Resilience:
     - Heartbeat: presence file updated every 5 seconds (STALE_SEC=15)
     - Backlog replay: new peer catches up on ALL messages since start (not just latest)
     - Non-blocking sockets: 100ms select timeout (responsive, not wasteful)
     - Best-effort: partial message on recv is dropped, retransmitted on next tick

8E. P2P CHAT VS. CENTRALIZED SERVER
────────────────────────────────────

PAL-CHAT-IRC DESIGN: Fully decentralized P2P (no server)

  Pros:
    - Any player can host a node (presence file + listening port)
    - No single point of failure (any 2+ players can chat)
    - Append-only guarantees no loss of past messages (even if nodes crash)
    - Same pattern as blockchain nodes (pal-chain) - players already know it

  Cons:
    - Eventually consistent (messages may arrive out of order across nodes)
    - Network partitions: if two groups can't reach each other, they have divergent chat
    - No central moderation (handled by convention, not enforcement)

MARS STREET TRADING USE CASE: Good fit
  - Players are few and known (2-8 typically)
  - Chat is supplementary to trading (not primary)
  - Append-only messages match trading's append-only ledger
  - P2P discovery via presence directory is lightweight

8F. HOW NODES DISCOVER EACH OTHER
──────────────────────────────────

Presence Discovery (palnet_peer.c lines 203-252):

  1. Each node writes presence file at startup:
     net/presence/<node_id>.txt
     Example: net/presence/mars-street-1-project-node-5432.txt
     Content: kind=chat, project_id=mars-street, piece_id=1, host=127.0.0.1, port=9901, pid=5432

  2. Other nodes scan presence directory:
     - Non-blocking scan of net/presence/ directory
     - Filter by kind (optional seek_kind parameter)
     - Check last_seen timestamp (discard stale > 15 sec)
     - Connect to candidates not already connected

  3. Connection (lines 510-527):
     - If seek_kind="chat", actively seek chat nodes
     - Open TCP socket to candidate
     - Send HELLO handshake
     - Request backlog (replay_backlog_to_peer)

  RESILIENCE: If node crashes, presence file goes stale (unlinked on cleanup_and_exit).
              Other nodes stop trying to connect within STALE_SEC window.

8G. MESSAGE PROPAGATION FLOW
──────────────────────────────

Example: Player ab posts "Selling ACME" in #trades room

  STEP 1: Local chat UI invokes chat_post_message.c
    chat_post_message.+x trades ab "Selling 50 ACME"

  STEP 2: chat_post_message writes TWO places
    A. rooms/trades/messages.txt (local persistence):
       MSG|msg_001|trades|ab|1719144000|Selling 50 ACME

    B. net/outbox.txt (broadcast queue):
       MSG|msg_001|trades|ab|1719144000|Selling 50 ACME

  STEP 3: palnet_peer daemon reads outbox.txt (lines 311-331)
    - Tracks g_outbox_offset (byte position already sent)
    - On each select() tick, reads NEW lines from g_outbox_offset onward
    - Sends "DATA|<node_id>|<line>" to all connected peers

  STEP 4: Remote node's palnet_peer receives DATA line (lines 360-365)
    - Parses: sender_node_id=<ab's node>, content=MSG|...
    - APPENDS to local net/inbox.txt:
      <ab's node>|MSG|msg_001|trades|ab|1719144000|Selling 50 ACME

  STEP 5: Chat UI reads inbox.txt and displays to users
    - Shows who posted, where, when
    - integrates into room history

  BACKLOG REPLAY (lines 339-354):
    - If new peer connects late, palnet_peer replays EVERY message since start
    - Not just "last message" (that was the bug described in lines 284-307)
    - Ensures peer catches up on full history

8H. COMBINING REGISTRY PATTERN WITH IRC
─────────────────────────────────────────

IRC DISPATCHER: NOT in palnet_peer itself (it's P2P only)

Instead, a CHAT SERVICE DISPATCHER would:
  1. Read default_op.txt (registry of chat operations)
  2. On menu input, dispatch to appropriate op
  3. Ops: chat_create_user, chat_post_message, chat_browse_rooms, etc.

Example from prisc+x (PAL-CHAT-IRC's frame renderer):
  default_op.txt:
    chat_menu_input void ops/+x/chat_menu_input.+x
    chat_compose_frame void ops/+x/chat_compose_frame.+x

  Renderer calls:
    ./+x/chat_menu_input.+x (reads user choice)
      → Returns action (e.g., "post_message")
    Dispatcher routes action to chat_post_message.+x
      → Writes to rooms/ + net/outbox.txt
    ./+x/chat_compose_frame.+x (reads rooms/, renders view.txt)
      → Displays updated chat history

SEPARATION: Dispatcher (prisc+x) doesn't know about networking.
            palnet_peer.+x doesn't know about UI.
            Each is independent, composable, testable in isolation.

PART 9: UNIFIED PATTERN ACROSS THREE SYSTEMS
================================================================================

All three architectures (Monster AI, Trading Sim, IRC Chat) use the same
foundational pattern:

┌─────────────────────────────────────────────────────────┐
│ REGISTRY + DISPATCHER + OPS + APPEND-ONLY LOG          │
└─────────────────────────────────────────────────────────┘

MONSTER AI:
  Registry:    ai_strategies.txt (id|name|op_name|description)
  Dispatcher:  pick_ai_strategy.c (read ai_mode, look up, shell)
  Ops:         decide_chase.c, decide_flee.c, etc.
  Log:         (implicit in entity state files)

TRADING SIM:
  Registry:    ai_strategy_registry.txt (id|name|module_name|description)
  Dispatcher:  run_ai_turn() in ai_manager.c (read strategy_id, look up, shell)
  Ops:         ai_module_0_apprx.c, ai_module_1_real.c, etc.
  Log:         data/master_ledger.txt (all trades, timestamped, append-only)

IRC CHAT:
  Registry:    default_op.txt (name type handler description)
  Dispatcher:  prisc+x (frame renderer, reads registry, dispatches ops)
  Ops:         chat_*.c (create_user, post_message, browse_rooms)
  Log:         rooms/<room>/messages.txt (all messages, timestamped)
              net/outbox.txt (for P2P broadcast)
              net/inbox.txt (received from peers)

PATTERN BENEFITS:
  ✓ Adding new strategies/ops = new .c file + registry row (no dispatcher changes)
  ✓ Each op is self-contained (can be tested/benchmarked in isolation)
  ✓ Append-only logs enable time-travel replay, auditability, crash recovery
  ✓ P2P networking works with any append-only log (trades, chat, blockchain, etc.)
  ✓ Same developer experience across all three projects (and future ones)
