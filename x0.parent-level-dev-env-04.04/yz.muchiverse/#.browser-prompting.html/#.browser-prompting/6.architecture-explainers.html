🏗️ Architecture Explainers

Five real architecture questions, each with its own explainer + delegation shape.

🤝🎲 Collaborative entity games

Multiple entities operating on the same game mechanic (roguelike, business sim, farming).

The real, existing building blocks

  • Sessions = games. Each game instance is a session folder.
  • Desks = maps. A session can have multiple desks.
  • Pals = placed entities. An entity instance on a desk, own state.txt, same piece-containment model as everything else.
  • Multiple entities on one desk is already the base case, not a special mode.
  • The real open question: how entities on the SAME desk read/write SHARED state without a one-writer-rule violation — see the ledger section below for the mechanism to reuse.

Prompt shape

CONTEXT: [this section + the data-storage-ledger section below]
CODE: [an existing multi-entity desk's real manager, as reference]
PROMPT:
  "Design a [bank/store/market] piece that N other entities read/write shared state on. Use the
  house's real one-writer-rule + append-only-ledger pattern - the piece itself owns writes,
  everyone else reads its published state."

📒🔒 Backend data storage & sharing ledger

How the house's data storage/sharing ledger actually works — the numbered, dated replacement for "too much, unsure if current" prior docs.

The real mechanism (verified 2026-08-18)

  1. One-writer rule — every state/ledger file has exactly ONE writer. Anyone else only reads. Violating this is a real, named house pitfall.
  2. Append-only ledgers for history/audit — every meaningful action gets ONE appended, timestamped line, never edited/rewritten.
  3. Marker/pulse files for "something changed" — a separate tiny file, appended with a single byte, so readers stat() it instead of re-parsing a big state file.
  4. Cursor-based incremental reads — a reader remembers how many bytes it's already consumed, only reads new bytes past that point.
  5. Shared state = a dedicated piece that owns it, not a free-floating file everyone touches.

Prompt shape

CONTEXT: [this section + taskbar-history-txt-migration-investigation.md]
CODE: [the specific state/ledger file's current writer]
PROMPT:
  "Add [new shared data need] following the house's real one-writer-rule + append-only-ledger +
  marker-pulse pattern. Identify the ONE process that should own writes before writing any code."

🎨🧰 Palettes (tile/sprite picker) as toys/pals

Real open decision

Real reference: &.widgits/tile-picker/. The open question: is a palette (a) a pal — placed entity, own toolbar tab, saves per-desk — or (b) a project-scoped tool with no toolbar presence?

Decide before prompting

These are architecturally different. A browser AI given ambiguous scope will guess wrong more often than not — no existing precedent for "a tool that's ALSO a pal" to copy from.

Prompt shape

CONTEXT: [platform primer + TASKBAR-MENU-ARCHITECTURE.md]
CODE: [tile-picker's own real source]
PROMPT:
  "I've decided palettes should be [pals with their own toolbar tab / project-scoped tools - PICK

  [pal state-save / project-scoping] conventions already used elsewhere."
