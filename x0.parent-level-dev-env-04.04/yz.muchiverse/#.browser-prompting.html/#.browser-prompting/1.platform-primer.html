🧱 Platform Primer

This IS your "1 context file" for most prompts. Paste this whole page (or trim sections irrelevant to the task) as the CONTEXT upload alongside your PROMPT and CODE files. Written so a browser-window AI with zero prior exposure to this house can orient in one read.

What this codebase is

A file-backed, module-driven desktop OS ("the house" / "muchiverse"), built as a spiritual successor to TPMOS (1.TPMOS_c_+rmmp.0103.0001/, a sibling dir one level up). Everything real is a file on disk — "if it's not in a file, it's a lie." No hidden memory-only state that matters survives a restart.

The core shape: PIECE → MODULE → OS

  • PIECE 🧬 — a directory with state.txt (+ a .pdl descriptor). Owns its own state.
  • MODULE 🧠 — a background daemon (*_manager.c) that orchestrates pieces. "Thin" — delegates real work to standalone ops (small, independently-testable .c → +x/*.+x binaries), never inlines business logic into the manager itself.
  • OS / renderer 🎭 — the "theater" layer. Substitutes ${var} into layout files, routes input, composes the visible frame. Should NOT contain business logic or piece-specific lookups.
Safe assumption

You will almost always need BOTH a layout file (.chtpm markup) AND a manager (*_manager.c) back from any real feature.

Input flow — the real, house-standard shape

KEYBOARD/MOUSE capture (raw termios, or Xlib KeyPress/ButtonPress, or XTest-injected for testing)
       ↓ writes decimal codes / KEY_PRESSED:/MOUSE_EVENT: lines
a shared relay/history FILE (e.g. livedesk_agent_relay.txt, pieces/keyboard/history.txt)
       ↓ ONE reader polls it
DISPATCHER (game_dispatch.c-style, or khtpm's dispatch_key_code())
       ↓ mutates state.txt, composes a frame
RENDERER (never touches raw input itself — pure "read state, print/draw")
Rule of thumb

Capture and render should be SEPARATE concerns/processes. Combining them causes real, subtle bugs — raw termios disables \n→\r\n translation for ANY writer on that tty, a real staircase-rendering bug this house hit in August 2026.

State/config conventions

  • PDL files (.pdl): pipe-delimited, SECTION | KEY | VALUE — the house's .ini-equivalent.
  • State files: key=value\n per line, or the pipe-delimited PDL shape depending on subsystem.
  • Marker/pulse files: append a byte ("P\n") to signal "something changed, redraw" — never a dirty=1 flag. stat() the marker's size to detect growth cheaply.
  • One-writer rule: exactly one process ever writes a given state/frame file. Violating this is a real, named house pitfall.

Directory shape (top-level, informal)

  • @.apps/ — system tool apps — some drift/lag behind current conventions, verify before trusting.
  • &.widgits/ — shared reusable widgets/libraries (_shared-lib/ is the real single source of truth for build-time-copied files).
  • xyzfs/bin/<app>/ — the "installed app" convention (only muchi-pet/livedesk-clock fully migrated so far).
  • Numbered project dirs (101.mutaclsym…, 103.media-studio/, etc.) — individual games/apps, each usually self-contained.
  • #.desktop/ — the taskbar's own live runtime state.

Before you build anything new

  1. Check if the pattern already exists elsewhere in this codebase.
  2. If not, check TPMOS (1.TPMOS_c_+rmmp.0103.0001/) — it's the grandfather program, often more feature-complete.
  3. Don't invent a new state-file format, relay convention, or dispatch pattern without checking both first.
