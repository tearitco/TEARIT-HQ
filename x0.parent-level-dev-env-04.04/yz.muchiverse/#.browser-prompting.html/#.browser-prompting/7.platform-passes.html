🪟🍎 Windows/Mac compatibility catch-up

Bring Windows usability back up to date after heavy Linux-focused refactors. Some shims exist but untested since the refactors.

Real cross-platform rules (from TPMOS's own real standards)

  • #ifndef _WIN32 for Linux/macOS blocks, #ifdef _WIN32 for Windows — NEVER refactor established POSIX logic "to clean it up" for Windows compat. Surgical wraps only.
  • Linux: fork()+exec()+waitpid(). Windows: _spawnl() with _P_NOWAIT (shared console) or _P_DETACH (background daemon).
  • Linux orchestrators block on pthread_join(). Windows needs a persistent while(!should_exit) { Sleep(100); } loop — detached Windows processes return immediately.
  • Path separators: / for all internal logic/fopen(), only convert to \ for native Windows _spawn/system() calls.
  • setpgid has no Windows equivalent — needs explicit taskkill or tracked-PID cleanup.
  • Hardcoded Linux font paths will crash Windows — always provide a C:/Windows/Fonts/ fallback.

🎬🎨 103.media-studio continuation

Location: 103.media-studio/ — subdirs: 100.tts-point-2-anything, 103.3d=blender-clone, 103.daw, 103.img-editor, 103.vid-edit, shared/.

The real decision

Option A — keep building out-of-house-spec (no navs/manager pattern): faster short-term, but every app is a FUTURE merge cost, no relay/dispatch/render conventions.

Option B — merge into house spec now: slower per-feature, but immediately taskbar-integrated and testable the same way this session tested the taskbar (relay injection, audit trails).

Honest guidance

Given this is ALSO about to hand off to browser AI, Option B compounds better — house-spec code is exactly what the Platform Primer describes in one upload. Out-of-spec code needs its OWN bespoke context doc every time. Pragmatic middle path: let Grok prototype fast for a genuinely new feature's FIRST pass, but require merge-to-house-spec as the SECOND pass before it's done.
